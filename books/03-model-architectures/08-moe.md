# M08　MoE 从路由到专家合并：每个 token 到底执行了谁

[本卷导航](README.md) · 前置：[M05](05-dense-decoder.md) · 下一章：[稀疏注意力](09-sparse-attention.md)

MoE 的“专家”是有独立参数的子网络，不是几个独立聊天模型在开会。最常见的语言模型 MoE 把部分 FFN 换成多组专家，并为每个 token 选择其中少数。Attention、embedding、共享专家等其他部分仍可能每次执行，因此不能用“总参数除以专家数”估计激活参数。

## 1. 先做一个两专家手算

输入两维向量 x。设 router 为单位矩阵，因此路由 logits 等于 x。专家0计算 `E0(x)=ReLU(x)`，专家1计算 `E1(x)=2ReLU(x)`。

对 x=`[2,1]`，softmax 概率约 `[0.7311,0.2689]`。若 top-1 且在选中集合内重归一化，则权重为1，输出 `[2,1]`。对 x=`[1,2]`，选专家1，输出 `[2,4]`。

若 top-2，两专家都被选中，则第一个 x 输出 `0.7311*[2,1]+0.2689*[4,2]≈[2.5379,1.2689]`。你现在可以明确区分三个步骤：算分数、选择专家、确定混合权重。真实模型可能在某一步加入额外 bias、sigmoid、归一化或缩放，不能统一当成这套 softmax toy。

## 2. 路由选择与混合权重可能不同

有些路由策略用调整后的分数选择专家，但输出混合仍使用原始分数。这样负载修正可以影响“去哪”，而不直接污染“怎么加权”。如果把选择 bias 也混入最终权重，可能不改变 top-k 集合，却静默改变输出。

本卷的简化实现使用同一 softmax 概率做选择与混合，并在 top-k 内重新归一化。`audit` 返回原概率、chosen、weights、counts、dropped，便于逐步检查。这个接口不是为了漂亮日志，而是让路由错误有可观察证据。

Tie-breaking 也要明确。两个专家分数相同时，本实验稳定选择编号较小者。生产不同 kernel 的 top-k 平局行为可能不同，确定性评估需要将此纳入条件。单纯固定随机 seed 不一定控制 top-k 的实现细节。

## 3. Capacity 为什么属于模型与系统的交界

若一个批次的大量 token 都去同一个专家，其他专家空闲而该专家工作过多。训练中常引入 capacity，限制每个专家接收多少 token；超限 token 可能被丢弃、重路由或通过残差绕过。不同选择会改变函数，不能只说“容量满了排队”就结束解释。

我们的 capacity 是每个专家可接受的 token-expert assignment 数量。按 token 顺序处理；超过限制则该条贡献为零，其他已接收贡献保留，丢弃后不再次归一化。这个策略有序依赖，故专门注明为可教学的确定性语义，不冒充最优生产策略。

对 `[3,1]`、`[2,1]` 两个 token，top-1 都选专家0。capacity=1 时第一个输出正常，第二个输出零。若外层还有残差，第二个 token 的旧表示仍可能沿残差保留；如果你只看完整 block 输出，未必容易发现专家贡献被丢掉。

## 4. 负载平衡与能力并非同一个目标

一个简化指标可写作 `E*sum(mean_probability_e * assignment_fraction_e)`，用于观察路由概率与实际分配的偏斜。它不是本卷实现的完整训练方案，也不能机械套到所有 top-k、shared expert 或辅助损失设计中。

让所有专家完全均匀不一定保证最强能力；让 router 任意集中也可能导致训练资源浪费和部分专家缺乏学习。真实训练要在任务损失、负载平衡、通信、专家容量之间权衡。你需要能区分正向计算定义、训练辅助目标与运行时负载策略。

推理时 expert parallel 把专家放到不同 GPU，token 需要按路由发往持有专家的设备，计算后再收回。通信成本受 token 数、隐藏宽度、top-k、专家放置和互连影响。激活参数少并不自动保证延迟低；小批次时大量分散的小 GEMM 也可能利用率差。

## 5. 从逐 token 循环到 grouped GEMM

参考实现按 token 再按专家 slot 循环，优点是每项贡献可以打印。高性能实现通常先按专家把 token 分桶、做排列，再对每个专家计算矩阵乘法，最后按原 token 位置合并。

需要保存的索引包括：原 token ID、expert ID、该专家的局部 token 偏移、top-k slot、混合权重，以及可能的 padding 对齐。最危险的 bug 是计算本身正确、回写顺序错位。一个简单测试是让每个专家返回不同的常数标识，确认每个 token 接收的是自己选中的专家结果。

分桶算法还要处理空专家、只有一个 token 的专家、重复路由、capacity 截断和共享专家。这些边界比“普通随机 batch 正常”更能验证你读懂了实现。算子卷可以在此基础上把逐专家矩阵乘换成 grouped kernel。

## 6. 参数量、激活量、存储量分别计算

设有 E=8 个 routed experts，每个 FFN 有 P=1000 个参数，每 token 选 k=2，另有一个始终执行的 shared expert 1000 参数，其他主干 4000 参数。总参数为 `8*1000+1000+4000=13000`；粗略激活参数为 `2*1000+1000+4000=7000`。这仍不能直接等于 FLOPs，因为不同参数可能在一次 token 计算中被使用不同次数，attention 还依赖上下文。

所有 routed expert 权重通常仍需能被访问。即使每 token 只激活少数专家，也不能默认只把两专家权重放在显存而不付动态搬运成本。Offload 可以改变权重驻留位置，却需要单独计算通信、延迟和调度。

## 7. 练习与答案

运行 `python -m labs.models.run_lab moe`。

1. **top-1 手算。** 对 `[2,1]`、`[1,2]` 验证两个输出。答案见开头；若输出还乘了0.7311，说明你没有按本实验约定对 top-1 重归一化，但那可能是另一种合法模型，必须明确区别。
2. **容量故障。** 将 capacity 从1改为0。验收：所有专家贡献为零，audit 的 dropped 全为 True，不发生除零。解释外层 residual 如何处理这种情况。
3. **实现专家分桶。** 将循环版改成每专家一批矩阵乘，再 scatter-add。验收：无 capacity 与有 capacity 两种情况下均与参考一致；重复 token contribution 使用累加，不能最后写入覆盖前面。
4. **构造路由平局。** router 全零、三专家、top-2。答案：本实现选择 `[0,1]`，权重各0.5。写测试固定这一约定，再讨论它对负载分布的不利影响。
5. **增加 shared expert。** 对每个 token 无条件添加 shared FFN 输出。验收：不占 routed capacity；总输出等于 routed 输出加 shared 输出。不要把 shared expert 放进 top-k 竞争而改变定义。
6. **统计每专家工作量。** 把 counts 转成直方图，报告 max/mean、空专家数、丢弃比例。参考：概率均匀未必实际选中均匀，尤其在确定性平局时。必须同时观察概率与 assignment。
7. **真实项目拓展。** 在官方模型代码中找到 router 的激活函数、选择 bias、top-k、重归一化、shared experts 和 routed scaling 六项。提交与本卷差异表和一个手算例子。只写“模型用了MoE”不算源码理解。

通过标准：你能从输入 token 追踪到专家再回到原顺序，能写出分桶版并验证与逐 token 参考等价，也能解释 capacity 语义对数值结果的影响。
