# M06　KV Cache、MHA、GQA、MQA：保存什么，省掉什么

[本卷导航](README.md) · 前置：[M05](05-dense-decoder.md) · 下一章：[低秩与 MLA](07-latent-attention.md)

KV Cache 是后续推理框架学习的关键桥梁。它不是保存最终答案，也不是把历史 token 原文放进显存。它保存特定层在特定位置算出的 key/value，使下一步不用重新计算那些已经确定的量。

## 1. 从重复计算开始推导缓存

假设已有 token `a,b,c`，要预测 d。完整前向计算 a、b、c 各层的表示。采样出 d 后，再用 `a,b,c,d` 预测 e。对于严格因果结构，a 的隐藏状态不依赖后面出现的 b/c/d；b 不依赖 c/d。因此前面位置每层的 K/V 已经固定，可以复用。

当前新位置的 Q 还要与历史 K 比较，并读取历史 V；KV Cache 没有消除标准 attention 对历史的读取。它减少重复的历史投影和层计算，却可能让 decode 越来越受 KV 读取带宽限制。把 cache 理解成“开启后注意力成本就与上下文无关”是错误的。

为什么通常不缓存所有旧 Q？下一步只需要新 query 去读历史记录，旧 query 的输出早已算完。对于其他算法或训练反向场景可能需要不同状态，因此“永远没有 Q cache”也不是普遍定理；这里讨论标准自回归 decode 的常见路径。

## 2. 正确缓存必须同时带身份与位置

逻辑上每块 cache 属于某个请求、某一层、某个 KV 头、某个位置范围和某套模型权重。即使形状相同，不同请求内容或不同层投影得到的 K/V 也不能混用。

本卷把一层 cache 表示为 `(K,V)`，整个模型 cache 是长度等于层数的列表。它简单但低效：每次 `concatenate` 都会复制历史，适合测试而不适合生产。框架通常使用预分配块、paged 布局或专门的状态池。数学语义相同，不等于内存管理方式相同。

RoPE 之后保存的 K 已经带有它的绝对位置旋转；追加 token 时要给新 Q/K 正确位置。若重复旋转旧 K，会二次编码；若新 K 位置始终为零，会让距离信息失真。测试完整前向与逐 token decode 是最直接的发现方法。

## 3. Prefill 与 decode 是同一模型的不同工作形状

Prefill 一次处理 prompt 的多个 token，因果关系已知，通常能形成较大的矩阵计算。Decode 每个活跃请求往往只新增一个 token，使用已保存的历史 K/V。两阶段不是使用不同的“预填充模型”和“生成模型”，而是同一参数在不同输入形状、状态条件下执行。

在 chunked prefill 中，一个长 prompt 可以分块处理：新块有多个 query，旧块已在 cache 中。mask 既要允许读取旧历史，又要阻止块内未来位置。单纯使用方阵 `tril` 不足以描述这种情况，必须结合全局位置。

本卷 `TinyDecoder` 暂时实现完整 prefill 与单 token step，练习要求你扩展块式接口。这不是把未完成核心藏到未来：单 token 与完整前向已完整可运行；块式接口是让你迁移已掌握依赖关系的实作题。

## 4. GQA 把共享发生的位置说清楚

MHA 中每个 Q 头对应独立 K/V 头。MQA 让所有 Q 头共享一组 K/V。GQA 在二者之间：例如 8 个 Q 头、2 个 KV 头，每 4 个 Q 头共享一个 KV 头。

不同 Q 头即使读同一 K/V，也可以产生不同注意力权重，因为 Q 由不同投影产生。共享 K/V 不意味着把所有头合成同一个 attention 输出。合并输出时仍保留所有 Q 头的结果。

我们的 `grouped_attention` 使用 `np.repeat` 展开 KV 作为可读参考。**这会在数组层面重复数据，因此不是节省 KV 物理内存的生产实现**。生产 kernel 通常按头映射直接读取同一存储，不必物化重复。测试参考函数负责证明头映射正确，算子实现负责高效实现这个映射。

将现有 MHA checkpoint 直接删掉 K/V 头并不能自动获得相同性能。GQA 是训练/转换配方与结构设计问题。原始 GQA 论文提出从 MHA checkpoint 进行 uptraining；本卷不把“共享头数可以调参数”误当任意权重都可无损转换。

## 5. 显存公式必须附带假设

对传统逐层 K/V 缓存，元素数近似为：

$$ N=2\times B\times L\times T\times H_{kv}\times d_h. $$

乘以每元素字节数得到 bytes。假设 B=1、L=4、T=100、Hkv=2、dh=8、每元素 2 字节，则容量为 `2*1*4*100*2*8*2=25600 bytes`，即 25 KiB。若 Hkv 从 2 改为 8，其他不变，变为 100 KiB。

这个公式不能直接套给所有模型：MLA 可能保存低秩 latent 与额外位置分量；线性注意力保存固定维度状态；混合模型不同层不同；量化 cache 有 scale 等元数据；paged 分配有块尾碎片；共享层可能减少重复；encoder-decoder 还可能有不同来源的 cross-cache。必须先读实际状态契约。

此外容量公式不包含权重、临时 workspace、CUDA graph buffer、通信缓冲和框架预留。总显存“理论够”不能证明一个部署必然启动成功。本卷的任务是让你能算对各项，再由推理系统卷把它们合并。

## 6. cache 正确性实验

```bash
python -m labs.models.run_lab kv_cache
python -m labs.models.run_lab gqa
python -m unittest tests.test_models_core.ModelMechanismTests.test_decoder_cached_matches_full -v
```

测试对 Hkv=1、2、4 分别比较。误差允许 `1e-10` 量级，是因为本地 NumPy float64 小矩阵；这个阈值不能直接用于 BF16 GPU kernel。生产验证应按 dtype、规模和后续误差敏感度制定阈值，必要时同时检查最大误差、相对误差与输出分布。

缓存测试要比较每一个位置的 logits，不只比较最后 argmax。两个明显不同的分布可能恰好拥有相同 argmax，而长序列后会放大差异。反过来，两个接近分布在近似并列时也可能选到不同 argmax，不能仅凭 token 不同就判断实现数学完全错误。

## 7. 练习与答案

1. **画头映射。** Hq=12、Hkv=3，写每个 Q 头读哪个 KV 头。答案：0–3→0，4–7→1，8–11→2。对应整数除法 `h // 4`。
2. **计算缓存。** B=2、L=12、T=1024、Hkv=4、dh=64、BF16，答案 `25,165,824 bytes=24 MiB`。要求列出每个因子，避免把 K/V 的 2 与两字节混成一个因子。
3. **检测跨请求污染。** 先跑请求 A，再不传 cache 跑 B，与全新模型实例跑 B 比较。答案必须一致。本卷没有把 cache 隐藏在 model 成员内，因此不传 state 明确表示新请求。
4. **实现块式 prefill。** 把 `[1,2,3,4,5]` 分成 `[1,2]` 和 `[3,4,5]`，每层计算新块 K/V 并追加旧块。验收：所有新块位置 logits 与完整前向一致。参考关键：每层旧状态独立、位置从旧长度起、mask 横向包含旧与新 KV。
5. **量化 cache 实验。** 仅将保存的 K/V 模拟为 int8 再解量化，比较多个步的 logits。参考：它不再严格等价，报告误差随长度变化；不可直接使用原 float64 等价阈值宣称失败。要区分有意近似与实现 bug。
6. **内存布局题。** 本实现每步 concatenate 的总复制量随 T 约为 O(T²)。参考：第 t 步复制 O(t)，求和得 T(T+1)/2。提出预分配数组+有效长度或分页块列表，解释容量管理与注意力数学如何分离。

通过标准：你能写出 full、step、chunk 三种路径之间的关系，能计算缓存预算，也能解释 GQA 保存的是哪个维度。
