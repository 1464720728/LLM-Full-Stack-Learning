# A10 持久化、幂等与恢复：进程死了之后仍知道发生过什么

## 内存变量不等于持久状态

普通 Python 字典活在进程内存中。程序退出，字典就消失。写到 JSON 文件或数据库才可能在重启后恢复，但“写过”还不自动等于事务完整、崩溃一致或跨机器可见。持久化设计首先要回答：在什么时间点，你愿意向外宣布某一步已经完成？在这个点之前或之后崩溃，恢复行为分别是什么？

本卷使用 SQLite 是因为它随 Python 标准库提供，适合本机学习事务、唯一键和条件更新。它不是“只能用于玩具”的意思，也不是“任何规模都够”的承诺。课程选择让你先把语义学清楚，再根据部署拓扑决定数据库、备份、并发和运维方案。

状态快照保存当前任务全貌，工具 ledger 单独记录每个动作是否开始和结果。为什么分开？因为工具效果与对话检查点之间可能有崩溃间隙：工具已完成、结果已记录，但 messages 还没保存。恢复时可以从 ledger 取回结果，而不是再次执行工具。

恢复不只是找到同一个 run_id。教学 State 没有自动保存或验证完整配置指纹，因此调用方必须保证模型、消息协议、工具 schema 与工具实现版本兼容，并使用同一业务存储与权限上下文。否则昨日叫 create_ticket 的工具和今日同名工具可能有不同效果，旧协议材料也可能无法被新适配器正确解释。生产扩展应记录这些版本及代码提交，加载时检查兼容性，并为确实需要升级的旧状态编写迁移；不能仅凭函数同名就自动继续。

还要区分数据库回滚与 Python 对象回滚：本实现通常先修改内存 State，再尝试保存。如果检查点写入抛出 Conflict、磁盘错误等异常，数据库可能没有接受这些修改，但内存对象已经变化。此时丢弃该对象，从最后持久快照重新读取，查阅 ledger 与不确定标记，再决定恢复动作；不能捕获异常后对同一内存对象继续 step 或无条件重存。重新加载也不授权重放未知副作用，必要时仍需人工核对。

## 三个时间窗

考虑 `create_ticket`：

1. 还没调用工具就崩溃：可以重新决定是否执行。
2. 工具创建了工单，但本地尚未记录结果就崩溃：效果未知，盲重试可能重复创建。
3. 本地 ledger 已保存结果，但任务快照尚未加入 tool 消息就崩溃：可以读取已存结果，继续构造历史。

第三种可以由本地结果账本解决；第二种跨越本地数据库和外部业务系统，需要业务幂等或查询机制。你不能用本地事务同时原子控制另一家服务的 HTTP 副作用，除非双方有额外协议支持。很多“Agent exactly-once”宣传没有说明这个边界，读实现时必须追问。

## 账本结构与调用身份

`tool_ledger` 的主键是 `(run_id,call_id)`。run_id 区分任务，call_id 区分这次任务中的调用。signature 由工具名与原始参数字符串计算，防止同一个 ID 被复用为另一动作。status 只有 running 与 done，output 在 done 时保存。

使用原始参数签名意味着 `{a:1,b:2}` 与字段顺序不同但语义相同的 JSON 字符串可能有不同 hash。这是本例刻意保守的身份检查，不是完整的业务语义规范化。若你需要跨重试稳定参数签名，可以在严格解析后用 canonical JSON，但仍要定义浮点数、Unicode、缺省值和等价参数怎样处理。对于副作用，业务 request_id 往往比“参数恰好一样”更明确。

`start` 发现已有 done 记录就返回缓存输出；发现 running 且工具有副作用，就抛 UncertainExecution；发现 running 且声明为纯工具，可以允许重放。这个规则依赖工具声明正确。一个标记 pure 却偷偷写文件的函数会破坏保证。因此工具元数据需要代码审查与测试，不能由模型随口指定。

## 业务幂等与调用去重的区别

ledger 去重针对某次调用身份，业务幂等针对用户想完成的同一个业务动作。模型可能在两个不同 call_id 下重复请求创建同一工单；只按 call_id 去重会执行两次。`TicketBook.create` 接受稳定 request_id，以唯一键保证同一业务请求只创建一行；再次调用会返回既有记录。

如果同一 request_id 携带不同 title，工具拒绝冲突。它不能默默把新标题覆盖旧标题，否则“重复请求”会变成“修改请求”。这种语义必须由业务明确约定。返回的 created 布尔值说明本次是否新建，不应被解释为整体任务是否成功；重复请求复用已有结果通常仍满足用户目标。

运行 `15-idempotency`，第一次 created=true，第二次 false。再运行 `25-ticket-project`，审批后创建工单，重放仍只有一行。这是可手算也可在数据库中验证的幂等性。它比在内存中记录“我好像执行过了”强，因为进程关闭后唯一键仍存在。

## 事务怎样保护本地不变量

TicketBook 在同一数据库事务中检查已有 request_id 并插入。单进程教学场景中这足以展示逻辑；多连接并发时，还要处理唯一约束冲突和数据库锁行为。最终唯一键是数据库级防线，不能只靠先 SELECT 再 INSERT 的应用判断。

对更复杂任务，比如“扣库存并创建订单”，两项本地修改应在同一事务里提交。否则进程在中间崩溃可能只扣库存没有订单。若第二项是外部 API，就不能直接用 SQLite 事务保证，需要 outbox、幂等消费者、补偿流程等架构。学这些模式时仍要从具体故障窗口出发，而不是背名词。

Outbox 的思想是：把业务状态和“需要发送的事件”写入同一个本地事务，之后 worker 发送事件；发送可能重复，因此消费者仍需幂等。它改善的是“状态已改却忘记发事件”的问题，不是让网络天然 exactly-once。补偿也不是时间倒流，例如邮件发出后无法真正收回，只能发更正或更新状态。

完整参考实现在 `advanced_solutions.Outbox`。这里不只检查唯一键，还要检查相同键对应的内容相同。SQLite 默认连接中，`with connection` 内的 SELECT 不会自动取得写锁；两个连接可能都查到不存在，随后竞争 INSERT OR IGNORE，失败者的不同内容被静默忽略。参考实现先 INSERT OR IGNORE 取得写锁，再在同一事务中 SELECT 并比对实际内容；任何不一致都会回滚。生产者同时核对 task title 和 outbox payload，消费者核对 inbox payload；消费者冲突时绝不能把生产者 sent 标成1。工作簿二有双连接确定性回归，不依靠线程调度碰运气。

## 恢复操作应当可审计

进入 uncertain 后，操作者应看到请求 ID、参数摘要、开始时间、已知观察和可查询目标。恢复可以有几种明确动作：确认已完成并补录结果；确认未发生并允许重试；执行补偿；终止并保留证据。每种动作都应写事件，而不是直接在数据库里改一个字段无人知晓。

当前 Harness 为避免过度复杂，没有实现通用人工 reconciliation API。它会停止并保留 ledger，你可以查询课程数据库并按练习扩展。这个功能边界不意味着本章只给概念：不确定状态识别、持久存储、幂等业务工具、检查点恢复均有可执行实现；更完整的运维恢复界面由练习推动你主动完成。

## 练习与参考解法

1. **跨进程恢复。** 运行到模型返回工具请求后关闭 Store，再重新打开并恢复。验收：最终答案正确，工具调用数为 1。参考：`16-checkpoint` 已给可运行基线，自己把流程拆成两条命令和一个固定临时工作目录。

2. **完成结果重放。** 直接调用 `_execute` 两次同一副作用调用。验收：真实函数只执行一次，两个结果字符串相同。参考：用计数器记录函数执行次数，不能只比较最终文件内容，因为两次同样写入可能掩盖重复效果。

3. **未知窗口。** 手工插入 running ledger，再恢复一个副作用工具。验收：uncertain，业务函数没有自动调用。参考：对纯工具使用相同测试应允许重放，证明策略按语义区分。

4. **不同 ID 同一业务请求。** 用两个 call_id 调用相同 request_id。验收：账本有两次调用，工单表仍只有一行。参考：调用身份与业务身份两个层级缺一不可。

5. **幂等冲突。** 相同 request_id 不同 title。验收：明确拒绝，原记录不变。参考：这是冲突，不是“成功去重”；错误码应能让上层请求人工澄清或生成新业务动作。

6. **实现恢复命令。** 添加 `inspect-run` 与 `resolve-uncertain` CLI。验收：resolve 必须携带预期 run version 和具体 call_id，写审计事件，不允许批量无条件把所有 running 改 done。参考：审批的对象是具体动作与证据，不是一个笼统“继续”按钮。

7. **Outbox 小项目。** 在一个 SQLite 事务里插入工单和待投递通知，worker 从 outbox 读取并写入模拟收件箱。故意在投递后、标记完成前崩溃。验收：恢复后模拟收件箱仍只有一条业务通知。参考：收件箱使用事件 ID 唯一键，不能靠 worker 内存去重。

通过门槛：你能画出每个外部副作用的崩溃窗口，解释哪些可以自动重放、哪些必须查询或人工处理；能用数据库约束证明一个业务请求不会重复创建对象，而不是只说“已经加了重试和 checkpoint”。
