# A12 多 Agent：分工、通信、证据合并与成本边界

## 先证明单个 Agent 为什么不够

把一个任务交给五个模型角色，并不自动比一个模型更可靠。每个角色都需要上下文、调用预算、工具权限、输出契约和失败处理；角色之间还会产生通信成本与信息丢失。合理的多 Agent 设计通常来自任务具有可分离子问题、不同工具权限、不同模型能力或独立验证需求，而不是因为“团队”听起来高级。

例如分析三个互不依赖代码模块，可以并行派工；一个人调查来源、另一个人独立复核结论，可以提高错误发现机会。反之，如果每一步都依赖同一共享文件的最新状态，让多个 Agent 同时修改可能只增加冲突。先画任务依赖图，再考虑角色划分。

多 Agent 也不等于多个进程。一个进程中可以轮流调用多个有独立上下文的模型角色；一个 Agent 的工具也可以在多个进程中执行。角色、会话、进程、机器和模型实例是不同层级。术语清楚才能正确估算延迟与费用。

## 常见组织形式

监督者模式中，一个 coordinator 分解任务、派发 worker、收集结构化结果并决策；流水线模式中，每个角色处理一个明确阶段；辩论或互评模式中，角色提出和审查结论；分层模式中，子 Agent 可以继续委派。每种形式都需要停止规则，尤其分层委派可能指数膨胀。

本卷用 `bounded_fanout` 表示并行任务调度，用 `merge_claims` 表示证据合并，避免把通信逻辑隐藏在大量提示词里。真实 worker 可以是 Harness 实例，也可以是确定性程序。你应该先用可控 worker 验证派工和合并，再接模型。否则调度 bug 和模型能力不足同时出现，很难归因。

一个任务描述至少含目标、输入材料、允许工具、禁止越界范围、交付 schema、预算、依赖和验收方法。仅发送“你是研究员，调查一下”会让 worker 自行猜测成功标准。上下文分配过少导致重复探索，过多又会浪费 token 并泄露无关信息。

## 结构化交付与证据

研究 worker 不应只回一段漂亮总结，最好回 claims 数组，每条有 subject、value、source、时间和不确定性。编辑 worker 应回修改 diff、涉及文件、运行测试和剩余问题。这样 supervisor 可以在合并时执行规则，而不是必须再用模型猜测另一个模型想表达什么。

`merge_claims` 把相同 subject 按不同 value 分组，并标记 conflict。它不会用“多数票”自动决定真相。三个 worker 都从同一个错误网页复制内容，不比一个权威原始来源可靠。独立性是证据来源与方法的性质，不是模型会话数量的性质。

运行 `22-multi-agent`，两个 worker 对版本给出 v1 和 v2，结果 conflict=true，同时保留两个 source。正确下一步是检查时间、来源权威和版本适用范围，而不是把字符串平均成某个不存在的“v1.5”。工程数据常有范围差异：一个是接口版本，一个是包版本，表面冲突也可能只是语义不同。

## 共享状态与写入所有权

多个 worker 最好各自拥有明确文件区域或独立 worktree，最终由整合阶段合并。若同时修改同一文件，哪怕 Git 能自动合并，语义仍可能冲突。一个 worker 改函数参数，另一个改调用端使用方式，如果基于不同假设，代码可能能导入却在运行时失败。

分工协议要包含接口契约和变更通知。比如规定 Evidence 对象有 id、source、text、timestamp，所有 worker 按同一版本使用。需要变更时先通知依赖方，再更新测试。把接口写入共享文件或 schema，比只在聊天里约定更能抵抗长任务上下文丢失。

Supervisor 不应盲信 worker 的“已完成”。它要检查文件实际存在、测试实际运行、引用实际可访问、结果是否满足验收。验证可以按风险抽样或全量进行，但不能把所有责任交给模型自评。最终负责交付的系统必须区分“worker 报告成功”与“整合验收成功”。

## 费用与延迟的计算

设三个独立 worker 用时分别 5、8、6 秒，顺序约 19 秒，并行理想约 8 秒，再加调度与合并。费用不会因为并行自动减少：每个 worker 的输入输出照样计量，supervisor 还要读结果。若每个 worker 都重读 20k token 公共材料，成本可能明显高于单一上下文。

可以发送共享摘要或按需引用降低重复，但摘要会有信息损失。把完整源放在共同工具可访问位置，worker 只读相关片段，是另一种取舍。任何性能结论都应测量，不要把“使用多 Agent”当作质量提高的因果证据。实验比较时固定总预算，才知道收益来自分工还是单纯花了更多 token。

## 失败、超时和部分交付

子任务失败时，supervisor 可以重派、降级、等待人工输入或交付明确部分结果。重派需要考虑副作用：调查可以重做，发送邮件不能无脑再做。每个 worker 的任务 ID 与 attempt ID 应分开，业务动作再有自己的幂等键。这样既能区分不同尝试，又能避免同一业务效果重复。

worker 还可能陷入循环、返回超大内容、请求超出职责的工具或继续委派。系统应有全局预算，而不只是每个子 Agent 独立预算。深度限制、总子任务数、总模型调用数、总费用和总 deadline 需要在共同账本中预留，防止每个局部都合规而总体爆炸。

## 练习与参考解法

1. **是否该分工。** 对三个任务写设计：并行查三份文档、连续修改同一函数、独立审查一个 patch。验收：每项说明依赖与收益，不默认都多 Agent。参考：独立查询适合并行；共享编辑常应串行或分支隔离；审查角色需要与作者不同验证路径。

2. **结构化 worker。** 用两个 ScriptedModel worker 返回带 source 的 claims，supervisor 验证 schema。验收：缺来源的“结论”不得进入 verified 集合。参考：存在来源字符串也不意味着来源真实，后续还要解析与读取证据。

3. **冲突合并。** 让三个 worker 说 v1，一个说 v2，但 v2 来源更新且权威。验收：不能单纯多数票。参考：把 source age、scope 和 authority 作为人工或程序核查对象，输出解释冲突原因。

4. **共享文件冲突。** 两个 worker 基于同一 hash 修改同一文件。验收：第二个因陈旧版本拒绝，不静默覆盖。参考：复用 A08 的 expected_sha，说明它是单工作区顺序工具的检查，跨 worker 完整所有权仍需更强机制。

5. **全局预算。** 三个 worker 各申请 3 次调用，但总预算只有 5。验收：真实发出的总调用不超过 5。参考：中心化预留配额，不能只在每个 worker 完成后才汇总统计。

6. **公平对照。** 同一任务集比较单 Agent 与两 worker+supervisor，总 token 上限相同。验收：报告成功率、成本、耗时、失败类型，不只挑展示成功案例。参考：多次采样并保留成对任务结果；小样本的差异要体现不确定性。

7. **接口变更演习。** Worker 输出字段 source 改名为 sources，故意保留旧 consumer。验收：契约测试失败，而不是运行到最后才发现证据空缺。参考：schema_version 与迁移逻辑一起设计。

通过门槛：你能解释每个角色存在的必要性，能把子任务结果作为待验证产物整合，并在成本受限条件下证明分工带来的实际收益。更高级的多 Agent 能力不是多几个 persona，而是更可靠的任务、状态与证据协调。
