# A06 超时、重试、预算与取消：让循环有明确边界

## 失败首先是分类问题

“出错就重试三次”并不是完整容错策略。参数格式错误，重复同一请求通常不会改善；认证失败，重试会浪费额度并增加日志噪声；临时限流可能需要等待；响应超时则可能代表服务没有执行，也可能代表已经执行但结果丢在路上。不同失败的安全行动不同。

一个实用分类包括：永久输入错误、权限错误、临时服务错误、资源不足、结果不确定、程序实现 bug、用户取消。分类依据应来自结构化状态码、异常类型和业务语义，不要只靠字符串里有没有“timeout”。对不了解的错误，保留证据并停止，比自动把一切当成瞬时波动更可控。

本卷的 `retry` 只重试显式的 `TransientFailure`。`PermanentFailure` 立即向上传播。调用者负责把实际 HTTP 错误映射到正确类别，也负责证明操作可重试。这样重试函数本身不需要知道所有提供方规则，业务层也不能把危险决策藏在通用 HTTP 包装里。

## 退避与抖动的数值例子

设基础等待 0.1 秒，指数增长，上限 2 秒。第一次失败后的等待上界为 0.1，第二次为 0.2，第三次为 0.4。Full jitter 从 `[0,上界]` 随机取等待时间。如果一千个客户端都固定等 1 秒，它们容易同步再次冲击服务器；随机等待可以分散重试波峰。

`max_attempts=3` 表示总共最多请求三次，不是初次加三次重试。第三次仍失败时直接抛错，不再等待，因为没有下一次请求。运行 `10-retry`，你应看到 attempts=3，并有两个退避值。测试注入 `sleep=delays.append`，只记录计划等待，不真的睡眠。这叫依赖注入：把时间和随机源作为参数，能让测试快速、稳定且可复现。

如果服务器返回 Retry-After，应按服务契约处理并结合总 deadline；不要为了盲目遵守长等待把任务拖过用户允许时间。也不要在每层各自重试三次：模型客户端三次、Harness 三次、任务队列三次可能导致最多 27 次真实调用。应记录请求层级，定义唯一或协调的重试所有者。

## 超时有不同范围

连接超时限制建立连接；读取空闲超时限制等下一段数据的时间；单次请求 timeout 限制一次操作；工具 timeout 限制工具执行；任务 deadline 限制整个任务。单次请求 30 秒，不代表包含十轮交互的任务也能在 30 秒内结束。

使用 monotonic clock 判断经过时间，避免系统时间校准导致“时间倒流”。本卷 Harness 的 deadline 在每次转移前检查，适合说明任务层预算；它不打断正在执行的同步 Python 函数。`live.py` 另外给 HTTP 请求设置 timeout。真实长工具需要协作取消、子进程终止或服务端任务取消，不能只在外层检查时间就声称强制超时。

一个重要细节：Python 线程超时等待通常只让等待方返回，工作线程可能还在继续。若它正在写数据库，系统不能在 UI 上说“超时所以什么都没发生”。对可能产生副作用的工具，应有操作 ID、查询结果接口和补偿机制，而不仅是一个计时器。

## 多维预算

请求次数只是最容易实现的预算，远不等于费用预算。不同请求的输入长度、输出长度、模型价格、缓存命中情况都不同。实际工程至少考虑模型调用数、工具调用数、总 token、费用、执行时间、上下文体积、文件与网络字节数。

设模型输入每百万 token 费用为 p，输出为 q，某任务各轮输入数量为 `I_t`、输出为 `O_t`，粗略费用为 `sum(I_t*p + O_t*q)/1e6`，如果有缓存或单独计价工具还要加对应项。不要把最后一轮 context 长度当作总输入量：每轮都可能重复发送历史。四轮输入分别 1k、2k、4k、8k，总输入是 15k，而不是 8k。

本卷 Budget 明确用 `tool_output_chars`，不是 token。它用于测试程序容量限制，不能拿来推算厂商费用。真实 token 计数需要相应 tokenizer、模板和服务 usage；预测预算与实际账单应分开。保守预留输出预算可减少超支，但服务是否严格按上限计费和推理 token 怎样计入，必须按当前模型契约确认。

次数与字符额度必须是非负整数。Python 中 bool 是 int 的子类，而 NaN 与普通数的比较并不遵守你可能预期的大小关系；仅检查 `value < 0` 会让 `True`、1.5、NaN 混入计数预算。参考实现采用 `type(value) is int` 加非负检查，0 表示没有额度，不表示无限。`max_transitions` 与图的 `max_steps` 同样接受非负整数；并发槽位则必须至少为1，语义不同。参数验证发生在任何状态变更和调用之前，错误输入不能顺便消耗一次模型请求。

## 在哪里扣预算

模型调用预算在网络请求前保存。否则进程在计费后崩溃，恢复可能再次以“免费未执行”状态请求。工具调用预算在执行前检查；实际结果字符预算在工具返回后才能知道。如果返回过大，本卷保留 ledger 结果并进入 limit，而不是截断 JSON 成坏结构继续发送。

这仍是教学版的取舍：副作用工具执行后才发现输出超大，动作已经发生，不能因为输出预算失败就说动作没有发生。生产中可以先为工具定义最大输出，再预留配额，或者让工具把大结果存为 artifact 并返回短引用。预算策略应贴合不同资源的产生时机。

成本控制还需要决定“到上限时怎么结束”。硬停止、请求一段受限总结、保存待办并返回进度，都是可能策略。但如果你为了总结又无条件调用一次大模型，就可能越过预算。结束动作也应有单独预留额度或使用无需模型的确定性摘要。

## 取消是一个协议

用户取消后，系统至少应停止安排新的动作，尝试终止正在运行的操作，保存已完成效果，并返回明确状态。取消不是回滚。已经发送的消息、创建的工单或写入的文件不会因为取消按钮自动消失。

本卷 `cancel` 保存 cancelled 终态，`run` 随后不再发起请求。`19-cancellation` 的 model_calls 应为 0。这个实验只覆盖取消发生在外部操作之前。你应在后续练习覆盖取消发生在模型调用中、工具执行中和结果写入后等不同时间点，列出每种情况下还能保证什么。

## 练习与参考解法

1. **次数语义。** 写一个总是瞬时失败的操作，max_attempts=3。验收：调用 3 次，等待 2 次。参考：最后一次失败不再 sleep，日志里区分 attempt_index 与 retries_used。

2. **不可重试错误。** 模拟认证失败映射到 PermanentFailure。验收：只调用一次。参考：不要让捕获 Exception 的外层逻辑再次把它包装成 TransientFailure。

3. **嵌套重试。** 两层各最多三次，内层每次失败。手算真实调用次数，再写测试。验收：发现 9 次，并改为单一层负责。参考：若外层重试的是整个多步骤任务，副作用和费用可能不止简单乘法，还要分析每一步。

4. **假时钟。** 注入一个可控 clock，恰好等于 deadline 时不得请求模型。验收：不使用真实 sleep 也能测到边界。参考：先检查预算再安排操作；`>=` 与 `>` 的差别在边界测试中应明确。

5. **大输出。** 工具返回超过字符预算的 JSON。验收：状态 limit、ledger 可查询结果、消息不出现坏 JSON。参考：结果已经存在与已送给模型是两种状态，不能混为一个布尔值。

6. **响应丢失。** 一个工具先创建记录再抛 timeout。验收：系统进入 uncertain，不自动再次创建。参考：查询业务 request_id 的记录确认效果；如果接口没有幂等或查询能力，就无法凭客户端重试获得 exactly-once 保证。

7. **设计费用预算。** 给三轮 input/output 用量和单价，算总费用，再加入缓存输入单价。验收：列明单位和每轮累积，不把 token 与字符混算。参考：预算账本应保存服务返回 usage 和估算值，若缺 usage 标为 unknown，而不是填零。

通过门槛：面对一个失败，你能先判断它是否值得重试、是否允许重试、还有没有预算重试，再决定怎样重试，而不是只会把重试次数调大。
