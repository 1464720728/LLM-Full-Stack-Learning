# A08 文件、编辑与进程：把工具放进真实执行环境

## Python 字符串怎样变成文件副作用

模型输出一个路径字符串，文件系统则按进程当前目录、用户权限、符号链接和挂载关系解释它。二者之间不是直接等号。`notes/a.txt` 是相对路径，含义取决于工作目录；`/etc/...` 或 Windows 盘符路径是绝对路径；`../` 可以向上走；符号链接可以让表面在工作区里的名字指向外部。

本卷 `Workspace` 先把根目录解析为实际绝对路径，再只接受不含 `..` 的相对路径，逐级拒绝符号链接，最后检查解析结果仍在根目录内部。这可以防止常见意外越界，但它不是对抗恶意并发进程的完整沙箱：检查后到打开前，路径可能被其他进程替换，这叫检查与使用之间的竞态，也常称 TOCTOU。

理解这个限制很重要。教学代码可以安全地处理可信临时夹具，不应因此用于执行互联网上任意仓库的恶意代码。真实沙箱需要操作系统级权限与隔离、资源限制、网络策略和挂载控制；文件路径校验是其中一层，不是全部。Docker 也不是魔法，容器如果挂载整个宿主目录、使用 privileged 或暴露 Docker socket，就可能拥有远超预期的能力。

## 小文件读取与大文件策略

`Workspace.read` 最多读取 `max_bytes+1` 个字节，超过上限就拒绝。为什么多读一个？如果只读 max_bytes，你无法区分文件恰好这么大还是被截断。多读一个字节可以判断是否存在额外数据，又避免把整个大文件加载到内存。

读取后尝试 UTF-8 解码。二进制内容不应使用 `errors='ignore'` 假装文本，因为静默丢字节可能改变语义。对于大日志，应该设计分页、行号范围、关键词检索、尾部读取等工具，而不是一次把整个文件塞给模型。工具返回还应说明是否截断、原始大小、返回范围和编码，这样模型不会把局部观察误当成全文。

读结果包含 sha256。这个 hash 用于后续编辑确认“我正在修改我刚才读过的那个版本”，不是用于证明文件内容正确。hash 相同表示字节一致；如果文件本来就错，hash 一样也不会把它变对。

## 精确编辑与乐观冲突

参考工具 `replace_text` 接收 path、old、new 和 expected_sha256。执行时重新读文件，检查 hash，要求 old 在当前文本中恰好出现一次，构造新内容，再通过临时文件和 `os.replace` 替换。

为什么不使用 `text.replace(old,new)` 默认替换所有？因为模型可能只想修改某个函数，却匹配到了另一个相似函数。要求恰好一处出现，使歧义转成明确错误。为什么要 hash？因为模型读文件后，用户或其他 worker 可能已修改它；直接写回会覆盖别人的新内容。为什么写临时文件？因为直接打开原文件写入时进程崩溃可能留下半个文件；rename/replace 通常使读者看到旧文件或新文件，而不是半写状态。

但“原子可见”不等于“整个读—校验—写过程原子”。另一个 writer 可以在校验 hash 后插入修改，仍可能被覆盖。真正多 writer 系统需要锁、版本管理或受控提交操作。跨文件修改也不是一个 `os.replace` 就有全工程事务性；编码 Agent 常借助独立 Git worktree、提交 diff 与测试来管理边界。

运行 `14-edit`，修改 `answer = 41` 为 42。随后手动在读取后写入一个不同版本，再试编辑，应该得到 file changed since read。不要通过取消 hash 检查“修好”这个报错；正确行动是重新读取并基于新版本提出 patch。

## Shell 工具的本质

shell 接受一段字符串并解析变量、引号、管道、重定向和命令替换。`subprocess.run(['tool','arg'])` 的参数数组通常不会经过 shell 解析；`shell=True` 则会把字符串交给 shell。二者风险和行为不同。用户输入中的空格、分号、`$()` 等如果被错误拼进 shell 字符串，可能从普通参数变成新命令。

因此窄工具尽量使用参数数组，并限制可执行程序、工作目录、环境变量、超时和输出。不是所有命令都适合开放给模型：一个“运行测试”的工具可以固定测试命令，比“执行任意 shell”更容易理解。编码助手确实常需广泛命令能力，但应在专门环境里授予，而不在主机日常账户上默认开放所有文件与凭据。

`run_trusted_fixture_tests` 用当前 Python 的 `-I -B -m unittest discover` 运行课程生成的测试。`-I` 减少用户环境对导入的影响，`-B` 不写字节码缓存；二者均不是安全沙箱。测试代码仍拥有普通进程能访问的资源。这里的安全前提是夹具由课程生成且可信，不是“加了 -I 所以任意代码都安全”。

## 退出码与输出解释

进程退出码 0 通常表示成功，非零表示错误，但具体语义由程序定义。测试命令 0 可能代表测试全通过，也可能代表根本没有发现测试，因此还要检查测试数量。日志出现“PASS”不等于退出码成功；某条测试通过后进程仍可能崩溃。反过来，程序写到 stderr 不一定失败，有些工具把正常进度输出到 stderr。

工具应返回 exit_code、stdout/stderr 或合并日志、是否超时、是否截断、运行目录和必要版本信息。模型需要看到足以定位错误的内容，但日志不能无限塞进上下文。本例把输出写临时文件，返回最多 8192 字节，并标记截断；它没有实现磁盘配额，因此仅用于有界可信测试。正式环境要限制进程输出总量，而不仅限制展示量。

## Windows、WSL 与 Linux 服务器

Windows 路径、WSL 路径和 Linux 服务器路径属于不同环境。不要把本机 `C:\...` 直接交给远程 Linux 工具。Windows 原生 Python 的进程与 WSL Python 也是不同解释器，依赖不会自动共享。SSH 只是让你向另一台机器执行命令；它不会自动把本机未提交代码同步过去。

本卷实验全部可在 CPU 上完成。你可以先在个人 PC 原生 Python 跑，再在 WSL 或 Linux 服务器复制运行，观察路径与权限差异。这里不需要 H100；GPU 并不能加速路径检查、SQLite 小事务或工具调度逻辑。真正使用本地模型时，模型推理硬件与工具执行环境也可以分离，Harness 经 HTTP 调用服务即可。

## 练习与参考解法

1. **路径矩阵。** 测试正常相对路径、绝对路径、`../`、符号链接、文件不存在。验收：每项行为明确，根外文件不被读取。参考：在临时目录建夹具，不使用真实敏感目录。

2. **陈旧 patch。** 读取 hash 后人工修改文件，再执行 replace。验收：拒绝且保留新内容。参考：测试不仅检查异常，还要重新读取文件，确认没有部分写入。

3. **重复匹配。** 文件有两个 `return 1`，尝试只替换该字符串。验收：必须拒绝歧义。参考：扩大 old 上下文到函数定义或采用结构化 patch；不要直接允许全局替换。

4. **进程结果。** 写三个可信脚本：成功、抛异常、超时。验收：结果能区分退出失败与 timeout，且 stdout 内容不被当作状态码。参考：固定很小超时仅用于测试夹具，不把真实性能表现作为断言。

5. **输出截断。** 生成超过展示上限的日志。验收：返回 truncated=true，并保留可定位的错误尾部或明确分页方式。参考：截断策略要有文档；只截开头可能丢掉最后 traceback。

6. **隔离设计。** 为陌生开源仓库写测试沙箱方案，列出挂载目录、用户、网络、CPU/RAM/PID/时间限制和密钥注入策略。验收：能够解释为什么不挂载宿主 Docker socket，不使用 privileged。参考：方案应经过环境测试，不能仅以 Dockerfile 存在就宣称安全。

通过门槛：你能解释从模型路径字符串到系统调用之间的每个信任边界，能实现不会静默覆盖用户修改的编辑工具，并能清楚说出自己的沙箱到底保证了什么、没有保证什么。
