# A05 流式输出：从不完整字节到可执行动作

## 流式不是“每个 token 一个 JSON”

网络把数据分成若干字节块传输，块边界由缓冲、网络和客户端读取方式决定。模型 token、Unicode 字符、JSON 对象、SSE 事件和 HTTP 读取块是五种不同边界。一个中文字可能跨两个字节块；一个事件可能跨十个块；一个块也可能含多个事件。把每次 `read()` 得到的 bytes 直接当作完整 JSON 解析，是流式客户端最常见的错误之一。

可靠实现至少分四层：字节流 → 增量字符解码 → 事件分帧 → 协议事件解释。最后，工具参数增量还需要按调用身份重新组装。把这些层揉进一个大循环会让 bug 很难定位：到底是 UTF-8 被截断、SSE 空行没处理、JSON 尚未结束，还是两个工具参数拼混了？拆层后，每层都有独立测试输入。

## 字节与字符的手算例子

字符串“鲸”在 UTF-8 中占多个字节。假设网络第一次只交付前一个字节，`chunk.decode('utf-8')` 会认为输入不完整并报错；如果使用 `errors='ignore'`，则可能直接丢失内容。增量解码器会暂存不完整前缀，等待下一块字节组成完整字符后再输出。

`streaming.sse_events` 使用 `codecs.getincrementaldecoder('utf-8')()`。每次传入新 bytes，decoder 输出当前可确定的完整文本。流结束时用 `final=True` 通知解码器不会再有字节；此时残缺字符必须作为错误处理，而不是悄悄消失。你可以把“保留部分状态”视为流式系统的基本性质：一段输入不够决定结果时，程序需要等待而不是瞎猜。

## SSE 的帧边界

SSE 中一条事件由若干行组成，空行表示事件结束；`data:` 行可以有多行，内容按规则组合。常见行尾有 LF 和 CRLF。注释行与非 data 字段不一定属于模型内容。我们的简化解析器关注 data，支持 LF/CRLF、多行 data 和 UTF-8 分块，遇到最终不完整帧会报错；它不是实现所有浏览器 EventSource 重连语义的完整库。

运行：

```bash
python -m labs.agents.experiments 06-sse
```

实验把完整数据拆成一个字节一个块，你仍应得到两个事件字符串，其中一个含完整中文字，另一个是 `[DONE]`。这是最苛刻但很便宜的边界测试。真实 HTTP 数据不会总按这种方式分块，但你的解析逻辑不应该依赖“正常情况下块比较大”。

一个需要明确的区别是：SSE 帧结束不等于模型任务完成。某个 `data:` 事件可能只是参数的中间片段，`[DONE]` 也属于具体协议约定，不是 SSE 自身强制定义。应当在协议解释层识别正确完成事件与停止原因。连接关闭却没有终止标记时，可以选择标记 incomplete；不要把“服务器没再说话”自动等同成功。

## 并发工具参数怎样拼

假设模型同时生成两个工具调用。调用 index=0 参数依次是 `{"a":1,` 与 `"b":2}`；index=1 参数依次是 `{"a":` 与 `2,"b":3}`。网络到达顺序可能是 1 的第一片、0 的第一片、1 的第二片、0 的第二片。若只有一个全局 arguments 字符串，它会变成无效 JSON，甚至恰好拼出错误但可解析的 JSON。

`ToolDeltaAssembler` 使用字典 `parts[index]` 保存每个调用的 id、name 和累计 arguments。index 是本次响应内部的组装位置；call_id 是以后工具结果的关联身份。两者不能混为一谈。最终按 index 排序交付调用列表，同时检查 metadata 完整、ID 不重复、参数是合法 JSON。

此实现把重复出现且相同的 id/name 视为可接受，把冲突值视为协议错误。arguments 是追加增量，因此若网络重放同一个 delta，简单重复 feed 会重复参数。这揭示另一个边界：**流式重连需要事件身份与去重语义，不能随意从头重放增量。** 我们的实验不实现重连；生产客户端应按提供方协议使用事件 ID、序列号或重新发起整个可管理请求。

## 什么时候可以执行工具

“目前拼出的前缀看起来像完整 JSON”不足以授权执行。后面可能还有字段、修正或其他内容。必须等待该调用的正式结束事件，再做完整验证与权限判断。低延迟系统有时希望提前准备资源，但准备和产生副作用要区分：提前解析查询键可以，提前发出付款或删除不行。

如果你希望实时显示参数，可以把它展示成“正在生成的草稿”，但 UI 不应把中途参数当作最终批准内容。审批绑定最终参数 hash，后续变化使批准失效。对代码生成也是一样：流式界面显示了十行代码，不意味着这些代码可立即运行。最终语法、内容审查和测试都在完整结果上进行。

## 背压、取消和容量

如果模型输出很快而消费者很慢，中间队列会不断增长。无界队列把延迟问题变成内存问题。设置有界队列后，上游读取会等待下游腾空间，这就是背压。工具参数、事件帧、总体响应都应有容量限制，否则一个无终止的大事件可能吃光内存。

本卷解析器设置单事件字符上限和工具参数长度上限，但它没有完整 HTTP 流式 transport，因此不在这里演示网络缓冲调优。实现时还应有连接超时、读取空闲超时和总 deadline；它们针对不同问题。用户取消后应关闭响应流、停止新工具执行，清理挂起任务，同时记录已经完成的观察。取消屏幕显示不等于取消底层请求。

## 练习与参考解法

1. **全部切点。** 给固定 UTF-8 SSE 数据，遍历每个可能字节切点，分两块输入。验收：所有输出一致。参考：测试文件已经示范此方法；扩展到三个块能覆盖更多组合，但不必穷举巨大输入，短样本即可发现边界错误。

2. **多行 data。** 输入两条 `data:` 行再空行。验收：结果中按换行连接，不是分别变成两个事件。参考：帧结束条件是空行，不是每条 data 行；当前实现已经支持，先预测再验证。

3. **交错调用。** 让三个工具调用按随机顺序交付参数片段，但保持每个调用内部片段顺序。验收：最终参数与未切片版本一致。参考：分别保存调用缓冲，不要使用一个共享字符串；随机种子固定以便复现。

4. **截断测试。** 删除最后一个空行、截断最后一字节、删除参数末尾右括号。验收：三类失败分别在 SSE、UTF-8 或 JSON 完整性层被识别。参考：异常不需要都叫同一个名字；清楚定位层次比统一成“网络错误”更有用。

5. **重放反例。** 把某个 arguments delta 发送两次，观察简单累加器失败。设计 seq 去重扩展。验收：重复 seq 不重复追加，不同内容共用 seq 报错。参考：seq 只能作为你自定义测试协议中的功能；真实提供方是否有此字段需查文档，不能擅自要求服务器支持。

6. **背压实验。** 用 asyncio.Queue(maxsize=2) 连接一个快速 producer 与慢 consumer；记录队列峰值。验收：峰值不超过 2，取消后两端任务均退出。参考：使用同步事件或短可控 yield 测试逻辑，不用脆弱的毫秒耗时断言证明正确性。

通过门槛：你能把“页面流式显示乱码”“多工具参数串线”“连接断了却显示成功”分别定位到正确层次，并能写可复现的最小输入证明修复。
