# 源码工作簿三：把自己的 Harness 接到真实模型、真实工具与真实评测

本工作簿把 A02、A07、A09、A12、A13、A15 连起来。前两本工作簿已经让你能够追踪单步和崩溃窗口；现在你要证明这种理解能迁移到陌生接口与开源项目。最终交付不是一张架构图，而是一组协议夹具、一个有明确边界的模型适配器、一份带权限的工具目录、一个受总预算控制的任务组，以及可重复运行的评测报告。

本节离线部分均可在普通 CPU 上完成。真实模型阶段显式启用 API，优先使用小任务与短上下文。没有任何必要为了学习 HTTP、工具验证和工作流而占用 H100。等你需要比较自部署模型的 Agent 行为，再把模型 endpoint 指向受控的推理服务；Harness 其余部分应尽量保持不变，这样比较才有解释力。

## 第一站：读懂一次 HTTP 请求的全部来源

打开 `live.ChatModel.complete`，不要急着运行。逐个找变量从哪里来：endpoint 来自命令行；model 来自明确配置；key 从命名环境变量读入；messages 来自 Harness 的持久历史；tools 来自注册表的 definition；extra 来自用户确认的提供方附加参数。把这些变量标成三类：程序定义、用户配置、模型或工具产生的数据。

这张来源表有实际意义。endpoint 与 key 不能由检索文档中的文字随意替换，否则一段外部材料就可能把授权头发到新地址。tools 也不能由模型自己在参数中创建；它由宿主注册表选择。messages 虽含模型与工具数据，仍由 context builder 决定如何发送。数据来源不明确时，权限也容易在各层之间悄悄扩大。

`body=dict(self.extra,model=...,messages=...,tools=...,stream=False)` 显式填核心字段。构造函数已经禁止 extra 覆盖这些字段，所以调用者不能用一个看似无害 extra_json 偷换 model 或 history。它不禁止所有提供方字段，因为不同服务确实有不同配置；但每次增加字段应来自明确文档和验证，不应由“网上有人这么写”推断兼容。

`Request` 中 Content-Type 指明 JSON；body 经 json.dumps 编为 UTF-8 bytes；Authorization 使用 Bearer 形式。这里 key 从未进入模型输入，因此模型本身不需要知道密钥。不要为“让模型自己会调用 API”把 key 写进系统提示词。模型决定动作，宿主提供凭据并执行，是更清楚的职责分离。

HTTP transport 拒绝重定向。即使目标服务通常不会重定向，也值得明确默认行为，因为 Authorization 是能力载体。你可以在自己的 localhost 测试服务中返回重定向，验证客户端拒绝，并确认日志不打印 key。这个测试在离线环境即可完成，不需要向真实服务发送假凭据。

## 第二站：建立脱敏协议夹具

一次真实成功请求只能证明那一次路径通了。可靠适配器需要覆盖正常文本、单工具、多工具、空内容、截断、拒绝、坏参数、未知内容块、额外字段和缺字段。你可以先手写 fixture，再用自己实际收到的脱敏响应补充。不要把真实用户全文或 provider key 放进 fixture。

一个 fixture 应包含输入语义说明、原始 payload、期望统一结果或错误、需要保留的不透明字段和不能默默丢弃的字段。例如 Responses 带 reasoning 项加 function_call，期望统一 Turn 提取工具请求，但 continuation 保留完整原 output。若你只测试最终文字提取，就发现不了重放丢失状态的错误。

把测试写成数据驱动：循环每个 fixture，调用 parser，比较所需字段。错误 fixture 应断言具体层次，不是只要任何异常就算通过。比如缺 choices 应报 malformed response，参数 JSON 坏则应在执行边界报 invalid arguments，二者整改位置不同。若整个测试只写 `with raises(Exception)`，一个无关的拼写错误也能让它“通过”。

协议 fixture 还应保存验证日期与服务版本信息，但不要声称所有 future 响应都符合当前记录。提供方新增 item type 时，保守拒绝比静默忽略更容易调查。等你了解新语义，再加入支持与测试，这就是契约测试驱动升级。

## 第三站：把任务目标从可裁剪历史中独立出来

A07 的最小 context selector 只保留 system 和最近完整片段。真实任务可能长到初始用户目标被挤出窗口。解决方式不是把“永远记住目标”再写一次提示，而是在应用状态中单独保存当前任务契约，再每轮构造上下文。

`advanced_solutions.pinned_context` 接受 goal、constraints、history 和预算。它先保留前导 system，再生成一条 user 消息，内容是结构化 current_task 与 constraints，然后挑选最近完整片段。这里 goal 仍属于用户数据，没有因为“需要固定”就升级为 system 权威。系统规范与任务目标的优先关系应保留。

请运行测试 `test_pinned_goal`，观察非常长的旧消息被裁剪，但 repair 目标和 no network 约束始终存在。这个测试同时检查角色为 user，防止维护者为了方便把所有输入都拼入 system。实际应用中约束可能来自用户、组织政策和工具权限，不同来源应分别表示，不能合成一条没有来源的万能文本。

再制造超预算情况：目标本身很长，连固定片段都放不下。函数应明确失败。你可以设计更复杂的任务摘要，但要保留原文和版本，并验证摘要没有改变约束。不能把失败“修复”为任意截断目标前半段，因为关键禁止条件可能就在后半段。

这一站的交付是上下文构建报告：每轮固定内容、选入历史、丢弃历史、预算单位和保留原因。先用字符数验证算法，再在真实模型中替换为官方 token 计数或经过验证的 tokenizer。测量 token 时记录模板开销与服务 usage，不拿中文字符数直接套英文经验系数。

## 第四站：构建一份能力最小化的工具目录

假设你的 Agent 需要查询文档、读取课程代码、修改自己的实验文件和运行可信测试。不要把整个硬盘和任意 shell 都暴露出去。分别建立 read_docs、read_workspace、edit_workspace、run_fixture 四种能力，声明根目录、大小限制、副作用、输入输出 schema 和是否允许重试。

工具目录不是单纯的一张 name 列表。它还应包含执行身份：哪一个用户发起、哪一个租户、哪一个工作区、哪一项任务授权。模型参数不应自行选择更高权限租户。例如不能允许模型通过 `tenant_id='admin'` 获取另一个知识库；执行上下文应由宿主传入，业务工具内部用它过滤。跨卷项目会示范这一点，用户身份与检索内容必须重新校验。

工具结果引用也要在使用时检查权限。假设检索时有权，最终回答前权限撤销，不能因为证据 ID 已在历史中就继续输出私有内容。你需要决定撤销语义、缓存失效和输出再验证策略，而不是只在第一次检索检查一次。这个问题同时涉及上下文、存储、工具和最终 verifier，是专家能力区别于简单 demo 的典型场景。

输出 schema 包装器能提前发现工具返回结构变化，但它不是权限检查。如果 search 工具返回了一个完全符合 schema 的越权文档，结构验证仍会成功。因此每个工具至少有三类测试：结构错误、业务不变量错误、权限错误。你可以把这三类测试写成矩阵，避免某一层“已经有校验”掩盖其他层空缺。

## 第五站：全局预算的可运行解法

多个 worker 各有本地预算，并不能限制总体。`AsyncBudget` 用一把 asyncio.Lock 包住检查与预留：如果 used+amount 超过 total，返回 false；否则在锁内增加 used，再允许调用者发起操作。网络请求不在锁内执行，因此不会把整个系统串行化。

你应特别注意“预留”与“结算”的差别。参考实现预留后不归还，适合请求次数预算：即使请求失败也可能消耗资源。若预算单位是连接槽，完成后应归还；若是费用额度，可能先预留最大输出成本，再按实际 usage 结算。不能把所有资源都套用同一个 acquire/release 模式。

完整实验：

```python
import asyncio
from labs.agents.advanced_solutions import AsyncBudget

async def main():
    budget = AsyncBudget(3)
    async def worker(i):
        accepted = await budget.reserve()
        if not accepted:
            return {"id": i, "status": "budget_rejected"}
        await asyncio.sleep(0)
        return {"id": i, "status": "completed"}
    results = await asyncio.gather(*(worker(i) for i in range(7)))
    print(results)
    print("used", budget.used)

asyncio.run(main())
```

验收重点是恰好3个被接受、used=3，其余明确拒绝。哪个 worker 先拿到额度在更复杂调度中可能不同，不应把固定任务 ID 的顺序当成业务保证。需要优先级时，应由调度队列明确安排，而不是依赖协程创建时序。

这个锁仅保护同一个事件循环中的对象，不是跨进程总预算。如果你把 worker 放到多个进程，每个进程各有一个 AsyncBudget(3)，总额度就可能变成6、9或更多。分布式预算需要共享事务存储或专门配额服务，且必须测试网络失败和重复预留。你应在设计文档写明保证范围，不能把单进程测试结果宣传成集群级控制。

## 第六站：按资源键序列化冲突动作

`resource_fanout` 要求每个 job 带 id 和 resource_key。相同 key 共用一把锁，不同 key 可以并发。全局 semaphore 限制在途总量。它先等待资源锁，再拿全局槽，避免一个等待热门资源的任务长时间占住全局槽，把其他独立资源也饿住。

假设八个任务交替访问文件 A、B，limit=4。虽然全局允许四个，实际上同一时刻最多两个不同资源上的任务进入主体，因为每个资源一把锁。这个结果不是浪费，而是资源冲突定义带来的必要限制。若两次都是只读，你可以设计读写锁放宽，但读写锁又有公平性、升级和死锁问题，不能只凭“看起来能并行”跳过语义。

测试 `test_resource_serialization` 在 worker 入口记录 active 资源集合，若同一资源已存在就说明发生重叠。这个检查不靠耗时，只靠控制流和 yield，具有可重复性。你可以把 worker 改成读—修改—写一个计数文件，验证没有丢更新；再删除资源锁观察稳定复现竞态。

锁字典只在一个有限 batch 内构造，结束后释放。长寿命服务若不断为任意 key 建锁却从不删除，可能无限占内存。真实资源调度还要防止攻击者制造海量 key。把生命周期写进实现，而不是仅展示一个 defaultdict(asyncio.Lock) 片段就结束。

## 第七站：流式去重的完整解法与边界

`SequencedAssembler` 演示一个自定义具有 seq 的流协议。第一次 seq=0 接受，重复相同 seq 和相同内容返回 false，不重复追加；同一 seq 不同内容报冲突；新 seq 跳号也报错。只有成功应用到内部 ToolDeltaAssembler 后才记录 seen 和 last，避免失败事件被误标已处理。

这个顺序很重要。如果先写 seen 再组装，组装抛错后重试会被当成重复而丢弃，系统可能永远无法恢复。事务思维不只存在数据库中，在内存事件应用也有类似“先声明完成还是先真正完成”的顺序问题。

请先运行 `test_duplicate_delta`，再手写四个事件：一个合法首片、一个相同重放、一个不同内容重放、一个跳号。写出每次 seen、last 和 arguments 的变化。然后解释为什么这个功能不能直接套到一个不提供 seq 的真实 API：你无法从字节块编号推断服务端事件身份，因为重连后的分块可能不同。

生产接入时，若服务不提供可恢复流事件语义，最简单的安全策略可能是把断流标记 incomplete，停止执行未完成工具，重新发起明确的新请求；但重复计费和上下文延续仍需记录。不要把本地去重器变成对远端能力的虚构承诺。

## 第八站：把多 Agent 的“意见”变成可验证产物

让两个 worker 分别分析同一个函数，一个提出 patch，一个检查测试。这并不天然独立，因为 reviewer 可能受作者解释诱导，只重复作者结论。更好的做法是让 reviewer 直接读取原任务、原文件、diff 和测试结果，使用自己的验证步骤，并明确标出无法确认的事项。

合并结果时，先校验结构，再查实际文件或来源，最后决定是否采纳。对于代码产物，检查文件存在、diff 范围、测试运行及输出。对于研究产物，检查原始链接是否支持具体 claim、是否过期、是否有条件范围。对于外部动作，检查业务系统的实际状态。每类结果都有自己的 verifier，不必全部交给另一个模型评分。

给 worker 设置“返回简短总结”可能丢失关键证据；给它设置“返回所有日志”又会淹没 supervisor。合理交付结构是摘要加可定位的证据引用与验证命令。Supervisor 读取必要证据后才能承担最终结论。这个过程类似软件评审：作者说明帮助理解，测试与源码支持判断，但任何一项单独存在都不够。

你可以用本卷 merge_claims 做最小合并，再接跨卷 Evidence 对象。注意 evidence_id 仅是引用，不是权威证书；必须在当前运行与当前权限下解析。若 worker 自己发明一个 id，最终验证器应拒绝，而不是把看起来格式正确的引用渲染成可信来源。

## 第九站：真实开源源码阅读的可交付任务

选择 mini-swe-agent 或 LangGraph 之一，创建单独学习目录，不修改本教材参考实现。clone 后记录提交 SHA、Python 版本和依赖锁定结果。先运行官方最小例子，再把同一个课程任务移植进去。不要一开始就阅读整个仓库，也不要从随机一个5000行文件第一页往下硬读。

用 `rg` 找入口和关键符号，沿调用图追踪一次请求。第一遍只关注数据结构：输入在哪里生成、消息是什么对象、工具结果何时写回。第二遍关注控制：循环如何停止、异常由谁捕获、预算在哪扣。第三遍关注持久化与观察：状态在哪里保存、trace 怎样关联、进程重启后加载什么。每一遍都用实际运行验证，而不是只凭函数名猜测。

交付五份小产物：一页调用链、一个原始/归一化消息对照、一项故障注入测试、一项行为修改和一份与本卷 Harness 的差异报告。行为修改可以是增加工具输出大小上限、给超时增加明确错误码、保存一个额外关联 ID。选择你已能理解的边界，不要一上来重写整个调度器。

如果真实项目版本变化导致教程路径不存在，先用 repository search 和 rg 找符号或行为。课程强调机制与入口定位法，避免假装某个行号永远有效。你的笔记应记录“在提交X中从符号Y进入”，让未来自己能复现，而不是写“最新版大概在那里”。

## 第十站：一份合格的实验报告

最终报告至少回答：任务是什么，成功标准是什么，使用哪个模型/协议/版本，工具与权限是什么，预算是多少，多少任务与每题多少次，怎样处理失败和重试，输出如何验证，哪些数据来自离线替身，哪些来自真实服务。若使用开源项目，还要记录提交与环境；若用本地推理服务，还要记录模型权重与部署关键配置。

结果表应保留失败。可以有成功率、每题调用次数、输入输出 token、费用、延迟、超时率和错误分类。费用缺失标 unknown，不能填0；网络或环境故障应单列，是否计入任务失败必须预先定义。模型随机波动则通过重复采样与成对任务比较处理，不要只挑一次最好的轨迹。

当你改了一个机制，比如保留完整工具原子组，就应设计相关失败任务作为回归集，说明它修复了哪类错误。若总分变化不显著，仍可能有明确工程价值，例如彻底消除孤立 tool 消息。相反，总分偶尔上升也不一定证明新机制有效，可能只是随机性或任务样本变化。

## 本工作簿的最终验收

你应提交一个能从头运行的目录，包含协议 fixture、自己的工具目录、上下文构建器、预算与并发测试、一个真实框架对照实现和评测报告。离线部分应一条 unittest 命令完成；线上部分必须单独命令显式启用，不在 CI 自动花钱。用自己的话解释每一个测试保护什么不变量，至少展示三次由测试抓到并修复的错误。

参考答案已经以独立函数和测试提供在 `advanced_solutions.py`、`test_agents_advanced.py`、`evaluation.py` 中。你可以对照，但最终至少重新实现其中两项，并加入参考答案没有覆盖的新边界。做到这里，你已经不只是会把 SDK 调用串起来，而是能设计、验证和修改 Agent 系统中的关键基础设施。接下来把知识检索、长期记忆和图结构接入，是在稳固执行机制上增加能力，而不会再把所有复杂性塞进一个无限循环。
