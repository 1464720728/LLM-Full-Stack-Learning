# A01 从零写出一个能观察、行动和停止的 Agent

本章的起点非常低：你会运行 Python 文件，知道函数接收参数并返回值，能够看懂列表和字典。你不需要先理解神经网络训练，也不需要安装某个 Agent 框架。我们要完成的事情是把一句“请帮我完成任务”拆成可以观察、执行、检查和停止的软件过程。先用完全可控的模型替身把程序逻辑弄明白，再在后面的章节换成真实 API。整个过程在普通 CPU 上运行。

读完本章，你应当能从空文件写一个最小工具循环，逐条解释发送给模型的消息，指出每一次环境改变由哪行代码发生，并区别“模型说完成”“循环结束”和“任务真的满足要求”。这些能力看似基础，却决定了以后你能否判断复杂框架究竟帮你做了什么。

## 第一课：先区分语言、建议和真正的动作

假设你在聊天窗口输入“帮我把 17 与 25 相加”。模型回复“42”。这次任务可以只靠生成文字完成，因为你的目标就是获得一个数值答案。再换一个任务：“把 result.txt 里的数加一并保存”。模型回复“已经保存好了”，并不会自动让硬盘文件改变。文字是一个输出对象，文件是操作系统管理的另一个对象；两者之间需要真实程序连接。

这个连接不是神秘能力。Python 可以调用 `Path.write_text` 写文件，也可以调用数据库接口保存一条记录。模型可以产生一个结构化请求，说明希望调用哪个函数、传入哪些参数；你的程序读取请求，检查它，然后调用函数。函数返回的结果再被装进下一次模型输入。我们把负责连接这些环节的软件称为 Harness。中文可以理解为运行与执行支架，但学习时保留英文名字更便于阅读开源工程。

这里至少有四种不同的东西。模型负责从输入生成下一次输出；工具负责执行一个被定义的操作；Harness 决定何时调用模型、如何处理工具、保存什么状态和何时停止；环境是文件系统、数据库、网页、终端或其他被观察和改变的对象。某个框架可能把这四部分包在一个 `Agent` 类里，也可能拆成几十个模块，职责不会因命名方式改变。

为什么先分职责？因为一出错，你需要知道该改哪里。模型选择了错误工具，可能是提示、工具描述或模型能力的问题；正确工具收到错误参数，可能是生成或解析问题；工具已经成功但系统又执行一遍，通常是状态与恢复问题；工具结果正确但最终答案胡说，可能是结果理解或验收问题。把所有故障统称为“Agent 不聪明”，会让你失去可操作的修复入口。

再考虑“我准备查询库存”和“库存查询结果为 8”两句话。前者表达意图，后者声称观察到了环境。你的程序必须保留二者的区别：计划不是证据，工具请求不是执行记录，执行返回也不总是任务成功。例如库存工具返回 8 件，只证明在某个时间、某个权限和某个仓库范围内观察到 8 件，不能自动证明订单已经下好。这就是我们后面反复要求标注身份、时间、来源和状态的原因。

## 第二课：把一次普通函数调用看清楚

先暂时忘掉模型。观察最普通的函数：

```python
def add(a, b):
    return a + b

answer = add(17, 25)
print(answer)
```

执行 `def` 时，Python 创建函数对象，并把名字 `add` 绑定到它；函数体这时不会立刻执行。执行第二段的调用表达式时，实参 17、25 分别成为函数内部局部名字 `a`、`b` 的值。`a + b` 计算出 42，`return` 把这个对象交给调用者，调用者把名字 `answer` 绑定到 42。最后的 `print` 负责把文本显示到终端，它不是加法计算本身。

这段代码里，调用者事先知道要调用 `add`，也事先写好了参数。工具调用只是在这个基础上多出一步：让模型先提出“调用 add，参数是 17 和 25”。注意，模型输出通常不是一个可以直接执行的 Python 函数对象。它来自另一台服务器，经过网络传输，是 JSON 等数据表示。你的程序必须把“描述一个动作的数据”转换成“允许执行的函数调用”。

最危险的捷径是把模型输出直接交给 `eval` 或 `exec`。这样模型不只是选择允许的加法工具，而是获得执行任意 Python 表达式或语句的入口。本课程从开始就采用明确注册表：工具名只能映射到你已经登记的函数。模型提出一个未知名字时，程序返回错误观察；不会替它去导入任意模块，也不会把名字拼进系统命令。

注册表是一个字典，它把外部名称映射到内部函数。下面代码里的函数对象没有被调用，只有最后一行括号真正触发执行：

```python
def add(args):
    return args["a"] + args["b"]

tools = {"add": add}
name = "add"
arguments = {"a": 17, "b": 25}
function = tools[name]
value = function(arguments)
assert value == 42
```

`tools[name]` 是按键查找；结果是一个可调用对象。`function(arguments)` 则是函数调用。把这两步分开写，是为了让你看见“选择工具”和“执行工具”是两个不同动作。如果名字不存在，字典查找会抛出 `KeyError`。成熟的工具边界不会把内部异常堆栈原样当成普通答案，而会把它转换成模型和上层程序都能理解的错误结果。A03 将把这一步展开为完整契约。

## 第三课：消息历史到底是什么

模型不会自动读取你 Python 进程里的全部变量。一次请求只包含你实际发送的内容。假设程序中有变量 `secret_answer = 42`，但没有把它放入请求，远程模型就不会因为变量存在而知道它。工具写了文件但没有返回文件名、内容或其他可用观察，模型也不能从程序的内存和硬盘中凭空取得这些信息。

为了让多轮行为连续，我们通常保存一个有序消息列表。列表保持顺序，顺序表达交互发生的先后。一个最小历史可以是下面这样：

```python
messages = [
    {"role": "user", "content": "请使用 add 工具计算 17 + 25"}
]
```

外层方括号表示列表。列表的第一个元素是字典；字典的 `role` 表明消息在协议中的角色，`content` 是这条消息携带的内容。`user` 不表示当前计算机用户名，它是模型对话协议中的一种角色。后面的 `assistant` 表示模型一方产生的消息，`tool` 表示工具结果消息。角色标签与真实业务身份不是同一个系统：给一条消息写上 `user`，不会自动授予它访问数据库的权限。

为什么必须保存模型提出的工具请求，而不能只保存工具结果？因为结果需要说明自己回应哪个请求。假设同一轮模型要求“查北京天气”和“查上海天气”，两个工具都返回字符串“晴”。只保留两个“晴”，后续程序无法可靠判断各自属于哪座城市。调用标识符解决关联问题；工具请求和结果共同形成一个可解释片段。

历史也不是越多越好。真实模型有输入长度、计算时间和费用约束，工具可能返回很长的日志。但你不能因此随便从中间删掉一条消息：删掉请求保留结果，或者保留请求删掉部分结果，都可能破坏协议和任务语义。本章先保留全部短历史；A07 会教你按照完整交互片段组织上下文，而不是机械保留最后几条。

## 第四课：用数据表示一个工具动作

本仓库的 `ToolCall` 有三个关键字段：`id`、`name`、`arguments`。`id` 是调用身份，`name` 是工具名，`arguments` 是原始 JSON 参数字符串。我们把参数保持为字符串，是为了在执行边界检测无效 JSON、重复键、非有限数字和类型错误，而不是假装网络输入一开始就是可靠的 Python 字典。

```python
from labs.agents.contracts import ToolCall

call = ToolCall(
    id="call-1",
    name="add",
    arguments='{"a": 17, "b": 25}',
)
assert call.id == "call-1"
assert type(call.arguments) is str
```

外层单引号属于 Python 字符串语法，内层双引号属于 JSON 语法。二者不是重复装饰。Python 首先产生一段文本，之后 JSON 解析器再把这段文本解释成对象。`'{"a": 17}'` 与 `{"a": 17}` 在 Python 中分别是字符串和字典，即使你打印时看到相近内容，它们也不是相同类型。工具协议中的参数片段在流式传输时甚至可能只有半个字符串，所以不能提前按完整对象使用。

调用 ID 的主要作用是关联与去重，不是表达业务含义。你可以把它看成一次快递的运单号：同一物品可以在不同寄送中有不同运单号；同一次寄送的查询和签收记录必须指向同一个运单号。业务操作的幂等键则更像业务订单号，两个网络请求可能都指向同一个订单。A10 会详细区分这两种身份；本章只要求你不把工具名当成调用身份。

一次模型响应也可能包含多个工具调用。因此本仓库把模型一轮输出定义为 `Turn`：它有文本字段和调用列表。文本为空但调用列表非空是有意义的：模型正在请求动作。文本非空且列表为空通常表示模型给出了最终答复。文本和列表同时为空则没有产生可用进展，不能悄悄当成成功结束。

```python
from labs.agents.contracts import Turn, ToolCall

turn = Turn(
    text="我先进行计算。",
    calls=[ToolCall("c1", "add", '{"a":17,"b":25}')],
)
assert len(turn.calls) == 1
```

`calls=[...]` 创建的是列表，不是单个调用。之后代码应遍历这个列表，每个调用都得到自己的结果。不要只处理第一个元素再丢掉其他请求；那样简单任务可能偶尔成功，多工具任务却会以看似随机的方式失败。

## 第五课：建立一个确定可控的模型替身

很多新手一开始就把真实 API 接进主循环，遇到错误后又不知道错误来自网络、协议、模型选择还是自己的状态机。软件测试通常把外部依赖换成可控替身：它按照事先准备的脚本返回结果。替身没有语言智能，但可以准确制造你希望研究的成功或失败路径。

这里的脚本模型第一轮请求加法，第二轮返回最终答案。它的职责不是自己算答案，而是提供已知响应，让我们验证 Harness 有没有真正执行工具、保存正确历史和停止。你应该把“脚本模型会回答 42”和“工具执行得到 42”分别记录；两者一致是一个测试条件，不是自然保证。

```python
from labs.agents.contracts import ToolCall, Turn
from labs.agents.runtime import ScriptedModel

model = ScriptedModel([
    Turn(calls=[ToolCall("c1", "add", '{"a":17,"b":25}')]),
    Turn(text="42"),
])

first = model.complete(messages=[], tools=[], index=0)
second = model.complete(messages=[], tools=[], index=1)
assert first.calls[0].name == "add"
assert second.text == "42"
```

这里的 `index` 明确指定脚本位置。本仓库没有把游标只藏在模型对象里，而是由持久化的模型调用次数推导索引。这样进程恢复后，脚本替身也能接着对应的位置继续。在本章的最小实现中，我们可以暂时只用一个普通整数计数；理解恢复时再引入持久状态。先学清一个机制，再增加另一个机制，比一次解释十种故障恢复策略更容易形成准确模型。

替身还有另一个重要用途：制造真实 API 很难稳定给出的坏输出。例如连续返回同一个调用 ID，返回不存在的工具，返回错误参数类型，或在第二轮抛异常。你不需要反复提示真实模型“请一定犯错”来验证容错代码。相反，真实模型评测应该关注它面对真实任务是否会选对动作，而不是替代这些确定性软件测试。

## 第六课：从空文件写一个最小循环

下面代码是独立可运行的教学版本，只依赖 Python 标准库。把它保存到自己的练习文件，例如被 Git 忽略的 `.practice/minimal_agent.py`。它不使用仓库成熟 Harness，目的是让控制流程全部出现在眼前。这个版本没有持久化、并发和真实网络，不应被当作后面复杂需求的完整实现。

```python
import json


def add(args):
    if type(args) is not dict or set(args) != {"a", "b"}:
        raise ValueError("expected exactly a and b")
    if type(args["a"]) is not int or type(args["b"]) is not int:
        raise ValueError("a and b must be integers")
    return args["a"] + args["b"]


def execute(call, tools):
    name = call["name"]
    if name not in tools:
        return {"ok": False, "error": "unknown_tool"}
    try:
        args = json.loads(call["arguments"])
        value = tools[name](args)
    except (json.JSONDecodeError, ValueError, TypeError) as exc:
        return {"ok": False, "error": type(exc).__name__}
    return {"ok": True, "value": value}


def run(script, goal, max_rounds=5):
    if type(max_rounds) is not int or max_rounds < 0:
        raise ValueError("max_rounds must be a nonnegative integer")
    messages = [{"role": "user", "content": goal}]
    tools = {"add": add}
    used_ids = set()
    model_calls = 0
    tool_calls = 0
    for turn in script[:max_rounds]:
        model_calls += 1
        calls = turn.get("calls", [])
        text = turn.get("text", "")
        if not calls:
            status = "finished" if text.strip() else "error"
            messages.append({"role": "assistant", "content": text})
            return {"status": status, "final": text, "messages": messages,
                    "model_calls": model_calls, "tool_calls": tool_calls}
        ids = [call["id"] for call in calls]
        if len(set(ids)) != len(ids) or set(ids) & used_ids:
            raise ValueError("duplicate call id")
        used_ids.update(ids)
        messages.append({"role": "assistant", "content": text,
                         "calls": calls})
        for call in calls:
            result = execute(call, tools)
            tool_calls += 1
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": json.dumps(result)})
    return {"status": "limit", "final": "", "messages": messages,
            "model_calls": model_calls, "tool_calls": tool_calls}


script = [
    {"calls": [{"id": "c1", "name": "add",
                "arguments": '{"a":17,"b":25}'}]},
    {"text": "42"},
]
result = run(script, "请使用工具计算 17 + 25")
assert result["status"] == "finished"
assert result["model_calls"] == 2
assert result["tool_calls"] == 1
print(json.dumps(result, ensure_ascii=False, indent=2))
```

先看输入合同。`script` 是预设响应列表，`goal` 是初始用户任务，`max_rounds` 限制最多处理多少次模型响应。由于这里直接遍历脚本，代码没有网络调用；我们把每消费一个脚本元素视为一次模型调用。`script[:max_rounds]` 是切片，产生前若干元素；它不改变原列表。后续真实客户端应该每轮调用模型方法，而不能一次预先获得全部未来响应。

接着看状态初始化。`messages` 保存交互历史；`tools` 保存允许执行的函数；`used_ids` 保存已经见过的调用身份；两个计数器分别记录模型和工具次数。它们分开是因为一轮可以请求多个工具。把所有计数都叫 step 会使预算含义混乱，例如十个并行工具可能是一轮模型响应，却是十次实际环境访问。

再看最容易误读的一段：没有工具请求时，程序检查文本是否为空。`text.strip()` 去掉两端空白后如果仍为空，意味着没有可用最终答复，因此状态为错误。这里的三元表达式只负责选择字符串，不会调用外部模型。然后程序保存最终 assistant 消息并返回整个结果对象。`return` 会结束 `run` 函数，不只是结束当前循环。

工具分支先验证调用身份。`set(ids)` 把 ID 去重，如果集合长度与列表长度不同，说明同一轮出现重复。`set(ids) & used_ids` 是集合交集，如果非空，说明与以前出现过的身份冲突。完成检查后才把模型请求写入历史。这个顺序让记录中不会出现一个已知违反契约、却看起来像正常动作的请求片段。

工具循环的顺序也有含义。先执行，再把结果写入历史，结果上的 `tool_call_id` 来自当前调用。我们没有根据返回结果到达的顺序猜身份。虽然当前实现是串行，保留显式关联能够为后面的并发版本打好基础。`json.dumps` 把 Python 结果对象序列化成字符串；为什么工具 content 是字符串，以及不同协议怎样表示结果，A02 会分别展开。

最后的返回发生在循环耗尽之后。耗尽可能是预算不够，也可能是脚本没有提供下一轮响应。这个最小版本统一返回 limit；真实 Harness 会更细致地区分外部故障和预算停止。这里最重要的不变量是：不能因为 `for` 结束，就自动声称任务成功。成功必须来自明确的终态条件，而不能来自“程序没有再执行下一行循环”。

## 第七课：用一张状态表逐步运行，而不是凭感觉读代码

现在不要运行程序，先拿纸把轨迹写出来。初始时消息数为一，内容是用户任务；模型调用数与工具调用数都是零。第一轮脚本响应提出 c1，加法还没有执行。这是一个经常被跳过的瞬间：系统已经有一个计划，但环境中还没有出现这个计划的结果。此时如果程序退出，你最多只能说“模型请求了加法”，不能说“加法已完成”。

当 assistant 工具请求被加入历史后，消息数变成二。接着执行 `execute`，解析 JSON，调用已注册函数，得到结果对象。函数返回之后，结果被序列化并加入第三条消息。第二轮脚本给出最终文本，程序加入第四条消息并返回 finished。每次增加历史都有一个明确来源，模型不能替工具伪造一条具有同等可信度的环境观察。

| 时刻 | 历史末尾 | 模型计数 | 工具计数 | 已知事实 |
|---|---|---:|---:|---|
| 初始化 | 用户任务 | 0 | 0 | 系统收到任务 |
| 收到第一轮 | 尚未附加或刚附加请求 | 1 | 0 | 模型提出调用 c1 |
| 工具返回 | c1 的工具结果 | 1 | 1 | 加法函数确实返回 42 |
| 收到第二轮 | 最终 assistant 文本 | 2 | 1 | 模型把 42 作为答复 |

这张表还能帮助你发现计数器设计中的歧义。如果工具函数抛出异常，工具调用次数应否增加？本章把一次尝试视为一次调用，因为它确实占用了执行过程。若你只在成功时计数，模型可以不断触发失败工具而不消耗预算，这通常不是你想要的策略。成熟系统可以同时保存 attempts、successes、failures 三个指标，但必须给每个名字一个明确含义。

再改成一轮两个工具：c1 计算一加二，c2 计算十加二十。第一轮 assistant 消息有两个请求，之后分别增加两个 tool 消息，第二轮 assistant 给出三十三。总消息数变成五，模型调用数仍为二，工具调用数变成二。你不应在 c1 结果之后立刻调用模型，因为同一轮的 c2 还没处理完；否则下一轮看到的是不完整的前一轮交互。这是后面上下文装配和并发汇合的基础。

状态表也揭示了“保存日志”和“保存可恢复状态”的差别。打印一行“执行了 c1”供人看，不能自动让重启后的程序知道下一步该做什么。要恢复，程序需要机器可读的 pending、计数器、结果和版本等信息。本章只在内存里运行，所以关掉进程后状态消失是预期行为。不要因为终端仍显示过去输出，就以为程序能够从那个位置继续。

## 第八课：把动作循环写成严格的状态转移

我们用一个简化状态向量表示运行过程：当前历史、待处理调用队列、模型调用数、工具调用数和状态标签。写成数学记号是 `S=(H,P,M,T,Z)`。这里的括号只是把若干部分捆成一个整体，不代表实际代码必须使用元组。一个类、字典或数据库行都可以承载同一逻辑结构。

模型转移在没有待处理工具时发生。它读取历史 H 和工具描述，返回一轮响应。如果包含工具调用，系统把响应附加到 H，并把调用放入 P，状态标签改成 tools。如果没有调用而有有效最终文本，则把响应附加到 H，标签改成 finished。工具转移从 P 取出一个调用，得到观察，把观察附加到 H，并从 P 移除这项。P 为空后再允许进入下一次模型转移。

这样的定义把程序的合法动作限定在当前状态上。你不能在 pending 非空时忽略未完成调用去请求下一轮模型，也不能在 finished 之后继续偷偷执行新的工具。状态标签不是随意给用户看的文字，而是控制哪些操作可以发生的条件。A04 会进一步讨论状态机，但你现在就可以使用这个原则来检查自己的循环。

不变量是每一步之后都必须成立的性质。第一条是调用结果必须指向已经存在的请求身份。第二条是同一调用身份不会在正常历史中产生两个互相冲突的结果。第三条是模型调用预算和工具预算分别计数，不能相互替代。第四条是终态之后不会产生新动作。你可以在纸上检查它们，也可以写测试自动检查；不变量不是只存在于数学教材中的词。

考虑一个错误实现：先从 pending 删除调用，再执行工具。如果执行过程中抛异常，而且没有其他持久记录，这个调用就从队列消失了，系统既没有结果也不知道应该重试什么。另一个错误实现是执行完成后马上再次进入模型分支，却忘记附加工具结果；模型只看见自己提出了动作，没有看到观察。这两个错误在最终字符串上可能都表现为“模型答非所问”，但状态转移位置完全不同。

本仓库把 `step` 设计为推进一个重要阶段，而不是在一个大函数里跑完所有事情。这样你可以运行一步，打印状态，比较预测，再运行下一步。这个接口也使故障注入变得可控：你能在模型请求之后、工具结果落盘之前等明确边界停下来。不要把“函数短”当成唯一理由；真正的价值是把可观察和可恢复的边界暴露出来。

## 第九课：接到仓库的完整教学 Harness

现在把最小版本中的职责映射到仓库实现。下面的程序可以直接在仓库根目录执行，不需要外部依赖或 API Key。它使用严格参数契约、事件记录和内存 SQLite 存储，比前面的最小循环多了恢复相关结构。

```python
from labs.agents.contracts import Tool, ToolCall, Turn, object_schema
from labs.agents.runtime import Harness, ScriptedModel

schema = object_schema({
    "a": {"type": "integer"},
    "b": {"type": "integer"},
})
tool = Tool("add", "计算两个整数的和", schema,
            lambda args: args["a"] + args["b"])
model = ScriptedModel([
    Turn(calls=[ToolCall("c1", "add", '{"a":17,"b":25}')]),
    Turn(text="42"),
])
harness = Harness(model, [tool])
state = harness.new("my-first-run", "请使用工具计算17加25")
while state.status in {"ready", "tools"}:
    harness.step(state)
    print(state.status, state.model_calls, state.tool_calls,
          len(state.messages), len(state.pending))
assert state.final == "42"
```

`object_schema` 创建对象参数结构；它把 a 与 b 标成必填，并拒绝未声明的额外字段。`Tool` 把名字、说明、schema 和 Python 函数放在一起。这里的 lambda 是只有一个表达式的匿名函数，它接收 args 字典，返回两个字段的和；如果你对 lambda 不熟，完全可以改写成前面用 `def` 定义的 add，两者在这个位置承担同一职责。

`Harness(model, [tool])` 中的方括号很重要：构造函数接收的是工具列表，然后建立按名称查找的字典。它还会检查重名。如果两个不同函数都叫 add，模型输出只包含名字时就无法唯一选择实现，所以启动阶段必须拒绝这种配置。发现配置错误越早越好，不要等模型碰巧选择了冲突工具才暴露问题。

`new` 创建 State，放入用户消息，记录 run_started 事件并保存检查点。`step` 首先检查是不是终态；如果是，它直接返回，不产生额外动作。若存在未确认的在途模型请求，它进入 uncertain；若截止时间已到，它停止；若 pending 非空，它进入工具分支；否则才考虑模型调用。这些条件的顺序体现了恢复和资源规则优先于继续“想下一步”。

工具分支里的关键顺序是：执行边界获得结果，检查输出预算，移除 pending，增加计数，追加 tool 消息，记录事件，保存新状态。输出超过历史预算时，工具可能已经执行成功，结果仍保存在 ledger 中。因此“因为输出太长停止”不意味着工具没有发生作用。你此时还不需要掌握 ledger 的实现，只要记住错误发生的位置决定了可以作出的结论。

模型分支则先预留一次调用、标记 inflight_model 并保存，再调用模型。这样进程如果在网络请求途中消失，恢复时不会假装这次请求从未发生。响应成功后，程序检查返回类型、调用 ID 唯一性和空最终答案，再清除在途标记、更新历史与 pending，最后保存。这里没有声称远程模型请求天然 exactly-once；它只是显式保留“结果可能未知”的事实。

`run` 是在 `step` 上包了一层有限循环。实现特别检查最后一个允许的转移是否已经到达终态。如果恰好最后一步成功完成，不能在循环退出后无条件把状态覆盖成 limit。这个边界看起来细小，却是实际调试中很常见的错误。判断预算耗尽时，要问“是否仍有必须继续的活动状态”，而不是只问“循环次数是否到了数字上限”。

## 第十课：停止条件、成功条件和验收条件分别属于谁

把这三个条件混在一起，会产生看似成功的错误系统。停止条件回答“程序是否继续做动作”；成功条件回答“用户目标是否满足”；验收条件回答“我们根据什么证据判断目标满足”。它们有联系，但不能用一个布尔值随意代替全部含义。

例如循环因为达到预算停止，这是停止但未成功。模型说“完成了”，所以协议层结束生成，这也只是一个结束信号；文件可能还没有改对。测试通过是一种验收证据，但如果测试只覆盖了部分输入，不能推出所有需求都正确。课程中的 finished 表示模型给出了合法非空最终响应，不自动等于每个外部业务目标已经实现。跨卷项目会在最终输出外再做证据验证。

对加法练习，可以分别定义三个检查：最终文本是不是四十二、加法工具是否真的执行、工具结果是否被正确放进历史。第一个检查衡量答案，第二个检查衡量行动过程，第三个检查衡量协议与状态。如果题目要求“必须通过工具计算”，只检查答案会遗漏一个重要失败：模型直接猜对答案，但没有执行任何工具。

对文件修改任务，验收应该读取最终文件内容，与预期变更比较，并检查没有修改不相关内容。只在对话中搜索“已保存”没有意义。对数据库任务，验收可能需要按业务键查询记录，检查状态、数量和版本。对代码修复任务，验收可能需要复现原失败、运行相关测试并检查差异。不同任务的 verifier 应根据实际目标设计，不能用一段通用“请评价自己是否成功”的提示完全替代。

更严格地说，模型可能同时承担提出方案和解释结果的工作，但最终业务权限与验收规则由宿主程序定义。即使模型非常强，也不能因为它输出“无需检查”就关闭你原本要求的验证。你可以允许模型建议新的测试，但是否采用、是否已经满足原有要求，应当有独立判断路径。这是构建可信 Agent 的起点。

## 第十一课：工具错误怎样变成下一轮可用观察

假设模型请求 `add`，却把 a 写成字符串“十七”。如果宿主程序直接崩溃，模型没有机会观察错误并修正。如果宿主程序把字符串悄悄转成某种数字，则输入契约变得模糊，某些场景还会产生错误业务行为。常用方式是返回结构化错误观察，清楚说明此次工具调用未按要求完成，让模型或上层策略决定如何修复参数。

错误观察应该有稳定的机器字段，例如 ok 为 false、错误码为 invalid_arguments，并带有足够但不过量的说明。模型可以阅读说明，但上层评测也应能按错误码统计。不要把所有异常都转成“发生错误，请重试”，因为未知工具、缺参数、权限拒绝、服务暂时不可用和副作用结果未知，需要不同的处理。

本章的最小循环为了易读，把部分输入和纯计算异常放在一个分支处理。仓库完整 Harness 则明确区分调用前校验与真正进入工具函数后的异常。这个区别决定你能否证明“工具没有开始”。一个写入工具可能先写入数据库，再在序列化返回值时出错；异常名字即使叫 ContractError，也不能证明写入没有发生。A06 与 A10 会把这些失败窗口逐个展开。

模型也不一定能修复错误。未知工具可能来自工具描述不清，也可能来自模型坚持使用不存在能力；错误参数可能因任务本身缺少信息而无法确定。此时正确行为可能是询问用户、选择另一条允许路径或停止，而不是无限重试。重试是一个有前提的策略，不是把失败包装成循环的万能方法。

为了让错误修复可测试，你可以准备两轮脚本：第一轮使用错误类型，第二轮改成整数。再给第三轮最终答案。观察历史应该保留第一次失败，而不是偷偷把失败消息删除后表现得仿佛从未犯错。这样你才能区分“一次成功”和“经过一次修复后成功”，也才能计算额外调用与成本。

## 第十二课：三个常见故障的完整诊断

第一种故障是消息中有最终答案，但工具计数为零。先看脚本是否第一轮就返回 text 而没有 calls，再看循环是否进入无工具分支。若是，这不是工具执行器出了问题，而是脚本没有请求动作。修复取决于任务：如果只要求答案，这可能允许；如果要求工具使用，应把验收条件写成工具计数和结果证据都满足，而不是强行把任意最终文本当作调用请求。

第二种故障是工具打印出四十二，但结果对象中的 value 为 null。最小复现是在 add 中写 `print(args['a'] + args['b'])` 却没有 return。Python 函数没有显式返回时返回 None，JSON 序列化后就是 null。终端输出和函数返回值属于不同通道。修复是返回计算值，并让展示层决定是否打印；不要通过读取终端上最后一行文字掩盖函数合同错误。

第三种故障是第一轮两个工具，却只有一个结果。先打印调用列表长度，再在循环中记录每个 ID，最后检查是否有一个错误的 return 放在工具循环内部。放在内部的 return 会结束整个 run，而不只是结束当前工具。另一个可能原因是用了 `turn['calls'][0]`，从一开始就只取第一项。修复后加入两调用测试，要求结果 ID 集合与请求 ID 集合相同，不能只断言工具计数大于零。

再补一个容易混淆的故障：改成两轮上限后，程序恰好在第二轮产生最终答案，却报告 limit。定位时把状态检查放到循环结束处，观察是否无条件执行了停止覆盖。正确实现应先看最后一次转移后的状态，已经 finished 就保留它；只有仍处于 ready 或 tools，且不允许继续推进，才记录预算停止。这种边界测试比把预算设成很大更有教学价值。

## 第十三课：十二道分级练习与完整参考答案

### 练习一：只看记录，判断发生了什么

给出记录“用户要求写文件；assistant 请求 write；下一条 assistant 说已写好”，但中间没有 tool 结果。哪些结论成立？参考答案：可以确认模型提出过请求，并声称完成；不能仅据此确认文件被写入。也不能断言绝对没有写入，因为可能是结果记录丢失。你应先检查执行日志或目标文件，再区分未执行、已执行未记录和记录格式错误。这个题的重点是避免把“没有证据”随意改写成确定的正面或负面事实。

### 练习二：计算消息数量

初始一条用户消息，第一轮模型一次请求三个工具，三个工具都各返回一次结果，第二轮模型给最终文本。模型调用两次，工具调用三次，消息数是六：一条用户、第一轮一条 assistant、三条 tool、最终一条 assistant。不能把三个工具请求算成三条 assistant，因为它们属于同一轮响应里的三个动作。若某协议把内容拆成多个 item，应该另外定义 item 数量，不能把协议 item 和本题消息单位混用。

### 练习三：布尔值为什么不自动当整数

把 a 设置为 true，b 设置为二。Python 中 bool 与 int 有继承关系，`isinstance(True, int)` 为真，但本章明确整数参数不接受布尔值。因此参考检查使用 `type(value) is int`。输出应该是错误观察，不能默默计算为三。这里不是说任何工具都必须拒绝布尔值，而是输入语义已经定义为整数加法，调用者应明确传入整数。把语言内部的兼容关系当成业务允许规则，会在预算、计数和权限字段中留下难发现的歧义。

### 练习四：修复一个没有返回值的工具

错误函数只执行 print。完整修复如下，调用者负责展示结果。验证必须同时检查返回值和副作用，不能仅看终端是否出现数字。

```python
def add(args):
    if type(args.get("a")) is not int or type(args.get("b")) is not int:
        raise ValueError("expected integers")
    return args["a"] + args["b"]

result = add({"a": 17, "b": 25})
assert result == 42
print(result)
```

如果你的测试只是捕获 stdout 并查找四十二，错误函数仍可能通过。更合适的契约测试直接调用函数检查返回对象；展示函数的测试再单独检查输出文本。一个测试应针对自己声称验证的接口，否则正确的表象会掩盖错误的程序结构。

### 练习五：增加纯读取工具

实现一个只读取给定字典中商品价格的工具；未知商品必须报错，不允许凭空生成价格。下面是完整参考实现，字典是合成环境，不代表任何真实商品报价。

```python
prices = {"pencil": 2, "notebook": 7}

def price(args):
    if type(args) is not dict or set(args) != {"item"}:
        raise ValueError("expected item")
    if type(args["item"]) is not str:
        raise ValueError("item must be text")
    if args["item"] not in prices:
        raise ValueError("unknown item")
    return {"item": args["item"], "unit_price": prices[args["item"]]}

assert price({"item": "pencil"}) == {"item": "pencil", "unit_price": 2}
```

返回对象同时带商品身份与价格，是为了使观察可以独立解释。只返回二并非永远错误，但当历史被整理、多个工具并发或结果被单独检查时，携带对象身份更容易验证。增加信息也有成本，所以这里保留必要字段，而不是把全部商品表都返回给模型。

### 练习六：写一个独立过程验收器

验收器应检查指定调用身份确实有成功结果，而不是信任最终文本。下面实现针对本章最小历史结构，解析失败会返回 false。它不是所有协议通用的验证器，但接口范围明确。

```python
import json

def observed_value(messages, call_id, expected):
    matches = [m for m in messages
               if m.get("role") == "tool" and m.get("tool_call_id") == call_id]
    if len(matches) != 1:
        return False
    try:
        payload = json.loads(matches[0]["content"])
    except (TypeError, json.JSONDecodeError):
        return False
    return type(payload) is dict and payload.get("ok") is True and payload.get("value") == expected

assert observed_value([
    {"role": "tool", "tool_call_id": "c1", "content": '{"ok":true,"value":42}'}
], "c1", 42)
```

为什么要求恰好一条匹配？零条说明缺少观察；多条可能是重复记录，也可能是互相冲突的结果。在尚未定义重复交付规则时，验收器不应随便选择第一条或最后一条。A10 会教你如何在明确的幂等与事件规则下安全处理重复，而不是靠列表位置决定真相。

### 练习七：两次工具调用怎样关联

构造 c1 对应一加二、c2 对应十加二十。最终结果应分别是三与三十。完整脚本如下，可直接传给本章最小 run。正确的最终答案三十三仍需由脚本指定；这个脚本验证循环，不验证模型加总能力。

```python
script = [
    {"calls": [
        {"id": "c1", "name": "add", "arguments": '{"a":1,"b":2}'},
        {"id": "c2", "name": "add", "arguments": '{"a":10,"b":20}'},
    ]},
    {"text": "33"},
]
```

先按 c1、c2 顺序执行，再在一个独立实验中交换执行顺序。若你的验收按 ID 关联，两种顺序都能识别相同的业务结果；若依赖“第一个结果属于第一个问题”的隐含假设，异步版本迟早会出错。保持可追踪身份，比假设网络总按顺序返回更可靠。

### 练习八：检测重复身份

把上题两个调用都改成 c1。参考答案是启动工具执行前拒绝整轮，不能先执行第一个再发现第二个重名。理由是调用身份已经无法唯一关联结果；继续执行会让后续去重、恢复和统计都变得含糊。验收不仅检查抛错，还应使用一个计数工具确认实际执行次数为零。若只检查最终状态为 error，仍可能遗漏“已经做过一次动作才报错”的副作用。

### 练习九：预算的边界

脚本有两轮，第一轮调用工具，第二轮给出答案。max_rounds 等于一时，应在完成第一轮允许的工具处理后返回 limit；等于二时，应返回 finished；等于零时，不消费任何脚本响应，模型计数为零。这里的预算单位是模型轮次，工具数另算。不要把一轮中的三个工具当成额外三轮，也不要因为轮次预算够大而省略工具预算；两者约束不同资源。

### 练习十：构造“答对但过程不合格”

只提供一轮最终文本四十二，没有任何 calls。答案正确性检查会通过，工具过程检查会失败。参考报告应保存两项结果，而不是只留下一个模糊 success。对于要求工具验证的任务，可以将二者逻辑与作为最终通过条件。这个小实验说明评测必须在运行前定义目标；如果看到结果后再决定是否要求工具，就会把评价标准变成对当前结果的迁就。

### 练习十一：手写状态快照

为每次循环推进保存一个只包含计数与状态的快照。必须复制值，而不是把同一个可变字典对象反复 append 到列表。否则最后修改该字典时，过去所有记录可能一起改变。完整参考写法是构造新的字典：

```python
snapshots = []
for status, model_calls, tool_calls in [
    ("ready", 0, 0), ("tools", 1, 0), ("ready", 1, 1), ("finished", 2, 1)
]:
    snapshots.append({"status": status, "model_calls": model_calls,
                      "tool_calls": tool_calls})
assert snapshots[0]["model_calls"] == 0
assert snapshots[-1]["model_calls"] == 2
```

本题使用不可变标量值，所以浅构造足够；如果快照还包含嵌套消息列表，就需要明确复制或不可变结构策略。不要从这个小例子推出“任何字典复制都能形成完整历史快照”。基础卷的别名知识在这里开始直接影响 Agent 的可审计性。

### 练习十二：独立复写并解释失败

关闭参考代码，重新实现一个只有加法和价格查询的循环，支持每轮多工具、未知工具、非法参数、空最终输出和轮次预算。验收输入至少覆盖正常、错误后修正、重复身份和预算边界四组。完整参考实现就是第六课的 run 与第五题的 price 注册组合；要求你重新写，是为了检验是否掌握职责，而不是让你发明不同语法。完成后逐项对照：你在哪一步保存请求，在哪一步产生真实观察，在哪一步决定停止？不能回答这些问题，即使测试偶然通过，也说明还需要回到状态表练习。

## 第十四课：把本章组合成一个微型购物核算项目

项目目标是“查两支铅笔和一本笔记本的单价，计算总价并给出带依据的回答”。环境只有上面定义的合成价格表。第一阶段让脚本模型请求两个价格查询；第二阶段根据已知价格请求加法工具；第三阶段生成最终文本。这里没有乘法工具，你可以把两支铅笔先通过加法得到四，再与七相加得到十一，借此观察多轮依赖。

依赖意味着第二阶段的参数必须来自第一阶段观察。如果你在脚本中预先写死价格，它仍可用于测试 Harness 的消息轮转，但不能宣称验证了模型会读取结果。要测试真正的动态使用，你可以写一个极小规则策略：从历史中找到价格工具结果，按商品身份读取单价，再产生下一次调用。这个规则策略是环境驱动策略，不是语言模型；它能帮助你验证后续动作确实随观察改变。

把铅笔价格从二改成三，期望最终总价从十一变成十三。若系统仍输出十一，说明某处偷偷依赖了旧常量。这个变化测试比重复运行同一输入更能揭露闭环是否成立。你可以进一步让价格工具返回未知商品错误，检查系统是否停止并解释缺失信息，而不是自行编造一个价格继续计算。

提交物应包括脚本或策略、完整消息历史、每轮状态表、成功验收器和四个失败案例。报告中分别写清模型替身、工具实现、环境数据与 Harness 的职责。这个项目小到不需要框架，却已经包含真实 Agent 系统的核心关系：外部观察影响后续动作，动作结果进入历史，最终目标由独立规则检查。
