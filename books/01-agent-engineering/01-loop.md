# A01 从一次函数调用到一个 Agent 循环

## 先把四件事分开

模型是一种根据输入产生输出的计算服务。工具是一段能观察或改变环境的程序。Harness 是连接模型、工具、状态和停止条件的软件。Agent 系统通常由这些部分共同组成。你问“帮我修复测试”，模型可以输出一段文字；只有 Harness 把它提出的读取、修改和测试请求交给工具执行，并把结果送回下一次模型调用，任务才开始真正推进。

这几个名词不是固定的代码目录名。有的项目把主循环叫 Agent，有的叫 runner、executor 或 session。判断组件身份应当看输入输出和职责，不要看到 `Agent` 类名就认为它涵盖全部系统。例如一个只有 `model.invoke(prompt)` 的类可能只包装一次生成；一个没有任何 `Agent` 命名的 while 循环却可能实现完整工具交互。

模型输出的“我已经测试通过”是声明；测试工具返回退出码和测试报告是观察；你事先定义的验收规则据此得出的成功结论才是判定。三者不能互换。这个区别会贯穿本卷：最终文字可以很好看，而环境中的目标可能仍未完成。

## 一个可以手算的闭环

任务只有“计算 17 + 25”。工具 `add` 接受两个整数，返回一个整数。初始历史 `H0` 只有用户任务。第一次模型调用得到 `call_id=c1, name=add, arguments={a:17,b:25}`。Harness 验证参数后执行 Python 的加法，获得 42，把“请求 c1”和“结果 c1”一起保存在历史。第二次模型调用得到最终文字“42”。

用状态转移描述：

\[
H_{t+1}=H_t\;\Vert\;a_t\;\Vert\;o_t
\]

这里 `a_t` 是模型动作，`o_t` 是工具观察，符号 `||` 表示有序拼接。模型只看得到你实际发送的内容。工具在硬盘创建了文件，却没有把文件路径或结果送回模型，模型就不能凭空知道文件创建情况。相反，模型说创建了文件但工具没有执行，文件也不会因为一句话而出现。

本例有 2 次模型调用、1 次工具调用，却只有一个用户任务。因此“步数”必须定义单位。有人把一次模型响应叫 step，有人把一次工具执行叫 step，还有人把完整的模型和所有工具一轮叫 step。比较两个 Harness 的 `max_steps=100` 前，先确认它们是不是在数同一件事。

## 阅读参考实现：从数据走向控制

打开 `labs/agents/contracts.py`。`ToolCall` 的三个字段分别是调用身份、工具名和原始 JSON 参数字符串。为什么参数不直接定义成 Python 字典？因为真实模型协议经常交付一个尚需解析的 JSON 字符串；把解析放进工具边界，才能测试坏 JSON 的行为。`Turn` 则表示一次模型输出，可以同时带文字和若干工具请求。

打开 `runtime.py`，先只看 `Harness.new`、`step` 和 `run`。`new` 建立用户消息并保存检查点。`step` 只推进一个重要阶段：如果有待执行工具，执行一个工具；否则请求模型。`run` 重复调用 `step`，直到状态到达 `finished`、`limit`、`error` 等终态。拆成 `step` 的好处是，你可以在任何阶段停下来检查，而不必把整个循环作为一个不可分割的黑盒运行。

`ScriptedModel` 不调用网络，它按保存的模型调用索引返回预设 `Turn`。这不是用规则假装语言智能，而是软件测试中的替身。要验证“参数错误不会被当成成功”，完全没必要每次付费请求模型再祈祷它输出坏参数。可控替身能稳定覆盖罕见失败。真实模型能力应当在后面的端到端评测里单独衡量。

运行：

```bash
python -m labs.agents.experiments 01-loop
```

预期 `final` 是字符串 `42`，`model_calls` 为 2，`tool_calls` 为 1。事件依次含 `run_started`、`model_requested`、`model_completed`、`tool_completed`、下一轮请求与完成。你看到的是逻辑顺序，不是 GPU Kernel 执行时间线。此时不需要 H100，也不需要 5070 Ti；程序的工作只是普通 CPU 上的数据转换和控制流程。

## 为什么不是“只加一个 while True”

真正的循环至少要回答六个问题。模型没有工具请求时是否一定完成？输出为空、被截断、被拒绝时不能都视为正常完成。模型请求不存在的工具怎么办？应返回结构化错误，不能直接把工具名送给 `eval`。工具抛出异常怎么办？只读失败和写入后丢失响应不是同一种情况。模型一直重复同一动作怎么办？需要预算与循环检测。程序进程被关掉怎么办？需要持久状态。用户取消怎么办？要停止新动作，并说明已经发生的效果。

这些需求不是复杂业务才有。一个“读文件并总结”的助手也会遇到路径不存在、文件太大、网络超时、重复请求和错误权限。先用小系统把异常行为设计清楚，比先接几十个工具再补漏洞更容易理解。

最小循环的责任边界可以写成三个函数：`model(history, tool_definitions) -> turn`；`execute(call) -> observation`；`update(state, turn, observation) -> new_state`。第一项与模型服务相关，第二项与现实环境相关，第三项与系统状态相关。将它们分开后，你可以换模型而保留工具，也可以保留模型而替换运行环境。

## 如何构造一个有意义的工具

工具定义中的描述并不是说明书装饰，而是模型选择工具时的重要输入。`add` 的描述应告诉模型它负责整数加法，而不是“有用的函数”。工具参数应尽量表达业务语义。例如日期查询使用 `start_date` 和 `end_date`，比允许模型随意拼 SQL 更容易检查。工具返回也应表达状态：`{"ok":true,"value":42}` 比混合在一句随意文字中的答案更容易处理。

不过，结构化并不意味着一切都应该变成巨大的 schema。工具接口过细会让模型需要更多往返，过宽会增加误用范围。假设读取一个文件要先拿目录 ID、再拿文件 ID、再拿块 ID、最后读字节，模型可能把简单任务执行成十轮；一个可以在限定目录读取小文件的工具就足够。设计接口时，应把“方便可靠地完成任务”与“权限足够小”同时纳入考虑。

## 分级练习与参考解法

1. **手工追踪。** 不运行程序，写出每次 `step` 后的 `messages`、`pending`、计数器和状态。验收：最后出现 4 条消息：user、assistant 工具请求、tool 观察、assistant 最终文本。参考：第一次模型调用后 `pending` 长度为 1，第二次 `step` 清空它，第三次 `step` 才生成最终答案；不要把工具结果当作用户消息。

2. **两工具一轮。** 让脚本模型一次请求 `1+2` 与 `10+20`，然后回答 33。验收：模型调用数仍为 2，工具调用数为 2，两个结果匹配各自 ID。参考：构造两个不同 ID 的 `ToolCall`；不要在两次工具结果之间插入新的模型调用。顺序执行和并发执行可以得到同一逻辑 transcript，但本例先保持顺序。

3. **错误即观察。** 把第一个参数改成字符串 `"17"`。验收：不能自动悄悄转成整数；工具结果 `ok` 为 false，循环能把错误交给下一轮。参考：参数验证在执行函数之前发生，修复由模型或上层策略决定。自动转换会让输入契约不再明确。

4. **终止规则。** 让脚本模型返回空 `Turn()`。验收：状态为 `error`，不是 `finished`。参考：没有工具并不等于有可用最终答案；还要检查文本、拒绝和截断等语义。真实协议完整性在 A02 展开。

5. **从零复写。** 新建自己的练习文件，仅保留 `ToolCall` 和 `Turn`，写一个最多 5 轮的循环。要求支持未知工具、错误参数、至少两个工具调用和模型最终文字。参考流程：先定义状态与不变量，再逐项测试；不要直接复制 `Harness`。验收测试由同学或另一个独立测试文件驱动，输出不能靠硬编码 `42` 通过。

6. **反例设计。** 构造“最终文字正确但工具完全没执行”的模型脚本。验收：报告中分别写 `answer_correct=true`、`tool_executed=false`。参考：如果任务只要求算答案，它可能仍算成功；如果任务要求使用工具以验证能力，它应失败。评测标准属于任务定义，不能运行完之后才临时改变。

## 常见卡点与掌握门槛

如果 `python -m` 找不到模块，先确认终端在仓库根目录，再确认正在使用的 Python 解释器；不要通过把随机目录加进 `sys.path` 掩盖问题。如果你能跟着输出解释结果，却写不出字典遍历和异常处理，回基础卷补这些语法，再返回本章。通过门槛是：关掉书，能画出一次工具调用的请求、执行、观察与下一次模型输入，能独立实现最小循环，并用一个失败用例说明为什么模型声明不是验收证据。
