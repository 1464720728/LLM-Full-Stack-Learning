# A13 评测、追踪与回归：用证据判断 Agent 是否真的进步

本章从一个最小算术任务开始，把任务、环境、Agent、执行器和验证器分开。你会构造故意失败的轨迹，验证评测能识别假成功；手算成功率与多次采样指标；比较成对配置；记录成本、延迟和失败原因；最后建立一套离线评测报告。目标不是获得漂亮分数，而是能解释一次修改改善了什么、证据覆盖什么、还有哪些变量未控制。

本章所有主实验使用 ScriptedModel，不调用真实 API。脚本模型让我们准确触发错误参数、预算停止和虚假完成，用于验证宿主与 verifier；它不能代表真实模型能力。真实模型评测需要另行配置任务、模型、预算和数据版本，报告必须明确区分离线机制回归与端到端能力实验。

## 第一课：先定义成功，再让系统运行

用户说“算出二加三”与“使用 add 工具算出二加三”是两个不同任务。前者可能允许模型直接回答五，后者要求实际工具调用证据。若评测只比较最终文本，两者会被混淆。成功标准必须在运行前写清楚，不能看见某系统表现好后临时改变要求。

一个评测任务至少包括输入、初始环境、允许工具、预算、停止条件和 verifier。编码任务可能要求通过受保护测试且修改范围符合要求；检索任务要求答案与引用对应；工单任务要求数据库中同业务键恰好一条正确记录；审批任务要求拒绝路径没有副作用。不同任务的证据类型不同，不能统一用模型自报“已完成”代替。

| 组成 | 回答的问题 | 示例 |
|---|---|---|
| 任务输入 | 用户要求什么 | 使用 add 计算二加三 |
| 初始环境 | 从什么状态开始 | 空对话、空调用账本 |
| 工具与权限 | 允许做什么 | 只允许 bounded add |
| 预算 | 最多消耗什么 | 两次模型、一次工具 |
| verifier | 怎样独立判定 | 工具成功值五且最终答案五 |
| 报告 | 保存什么证据 | 终态、调用数、分类、配置 |

验收既要检查发生了什么，也要检查不应发生什么。任务要求只读分析，最终报告正确但修改了文件，仍然失败；用户拒绝创建，系统返回“已拒绝”但数据库已有记录，也失败。副作用日志与环境差异是必要证据，不能只看自然语言输出。

成功定义也应处理部分完成、合理弃答和结果未知。它们可能比错误回答更安全，但不一定满足任务目标。报告可以分别统计正确完成、正确拒绝、部分交付、未知与错误，不应把所有非异常都算成功。业务价值与控制流 finished 是不同维度，A11 已经展示正常到终点也可能 outcome=declined。

## 第二课：评测对象是整个系统还是某个组件

同一模型配不同工具 schema、上下文策略、重试、预算和环境，端到端表现可能不同。把整个 Agent 系统分数直接称为“模型能力”会隐藏这些因素。你应明确实验单位：协议解析器、工具执行器、状态恢复、工作流、模型选择策略，还是完整用户任务。

单元测试检查局部合同，例如 bool 不当整数、重复 JSON 键拒绝、调用编号匹配。集成测试检查多个组件连接，例如模型提出调用、执行器验证、工具运行、账本保存、恢复回填。端到端评测使用真实模型与任务环境，观察目标完成与成本。三层互补，不能用一层替代其他层。

脚本模型是测试夹具。它按预设返回 Turn 或异常，让你稳定覆盖难以由真实模型重复生成的轨迹。真实模型偶然成功不能证明崩溃恢复正确；脚本测试全部通过也不能证明真实模型会选择正确工具。报告应把“已验证宿主行为”和“已测真实模型表现”分开列出，避免夸大证据。

测试环境也属于系统。依赖缺失、文件权限、网络限制、服务版本和数据快照都会影响结果。一个配置在本机通过，不代表用户 Win11 或公司 Linux 服务器已经验证；报告应记录实际环境与未执行项。没有 GPU 的 Agent 基础评测可以完全在 CPU 上跑，不能把未运行硬件实验写成通过。

## 第三课：逐行读算术任务 verifier

课程 `run_case` 构造两个脚本响应：先调用 add，再返回预期和。bad_argument 把 a 改为布尔，false_claim 直接输出错误数字，tool_budget 把工具额度设零。运行后提取所有 role=tool 消息并解析 JSON，再同时检查终态、最终答案、工具观察数量、ok 标志和工具值。

```python
from labs.agents.evaluation import Case, run_case

cases = [Case("normal",17,25), Case("negative",-3,5),
         Case("bad",2,3,"bad_argument"), Case("claim",2,3,"false_claim"),
         Case("budget",2,3,"tool_budget")]
rows = [run_case(case) for case in cases]
assert [row["success"] for row in rows] == [True,True,False,False,False]
```

预期是两个成功、三个失败，不是全部成功。评测器的正确性在于识别故意失败样本。若你把 success 条件放松到只看最终答案，bad_argument 的脚本仍返回正确数字，可能被误判成功；若只看 status=finished，false_claim 也可能通过。多个条件对应任务不同要求，缺一项就可能接受假成功。

`observations[0].get('ok') is True` 使用精确布尔，防止字符串 true 或数字一被当成成功标记。工具值必须等于预期和，且观察恰好一条，符合本任务“使用一次 add”的具体合同。真实任务若允许多次探索调用，数量条件应按任务定义调整，不能把这个算术 verifier 生搬硬套所有 Agent。

当前 classification 部分利用 case.behavior 这个已知测试标签来给错误分类，因此它是确定性 fixture 报告，不是通用生产故障诊断器。真实轨迹分类应读取事件、状态和工具错误码，未知情况标 unknown，不能根据任务名称猜原因。这是源码导读必须指出的边界。

## 第四课：验证器也需要反例测试

验证器是评测的测量仪器，它自己出错会让所有分数失去意义。应构造已知应通过与应失败的样本，检查边界。例如正确答案但无工具、工具成功但最终答案错、工具错误但模型声称成功、重复副作用、测试发现零项、来源存在但不支持结论。每个反例对应一种可能被系统利用或误判的漏洞。

```python
import json
from labs.agents.runtime import Harness, ScriptedModel
from labs.agents.contracts import Turn, ToolCall
from labs.agents.tools import arithmetic_tool

def verify_add_task(state, expected, require_tool=True):
    answer_ok = state.status == "finished" and state.final == str(expected)
    observations = [json.loads(m["content"]) for m in state.messages if m.get("role") == "tool"]
    tool_ok = len(observations) == 1 and observations[0].get("ok") is True and observations[0].get("value") == expected
    return answer_ok and (tool_ok if require_tool else True)

h = Harness(ScriptedModel([Turn("5")]), [arithmetic_tool()])
s = h.run(h.new("answer-only","calculate"))
assert verify_add_task(s,5,require_tool=False) is True
assert verify_add_task(s,5,require_tool=True) is False
h.store.close()
```

这段验证器明确把工具要求作为参数，展示同一轨迹在不同任务合同下可以得到不同判定。评测报告必须保存所用合同版本，不能只保存布尔结果。否则将来改变 verifier 后，你不知道历史分数对应什么标准。

验证器应尽量独立于 Agent 可修改区域。编码 Agent 可以修改公开测试来获取反馈，但最终验收应在受保护测试或干净环境中应用补丁后执行。若 Agent 删除测试文件，unittest 发现零项可能退出零，这不代表任务通过；验收需要检查预期测试身份或独立隐藏测试。不要把退出码零当作所有任务的万能成功标准。

独立也不意味着永远正确。隐藏测试可能覆盖不足或需求解释错误，模型裁判可能偏好某种措辞，人工评分也可能不一致。应版本化 verifier，保存争议样本并做复核。发现 verifier bug 后可以重新计算旧轨迹，但应说明版本变化，不能悄悄改历史成绩。

## 第五课：成功率的分子、分母与缺失值

十个任务成功八个，成功率是八除十。看似简单，却常被错误分母污染。超时任务是否计入，拒绝任务是否计入，运行崩溃是否被丢弃，重复尝试按任务还是按 trial 统计，都必须事先定义。只保留有结果的运行会高估性能，因为最严重失败可能恰好没有正常输出。

课程 metrics 把 outcomes 长度作为分母，只把 success is True 计入成功。空列表返回 None 而不是零，因为没有样本无法估计成功率。零成功和没有数据是不同事实，图表与报告应明确区分。把缺失填零可能低估，把缺失删掉可能高估，正确做法是按预先政策处理并报告缺失原因。

```python
from labs.agents.reliability import metrics

summary = metrics([{"success":True,"model_calls":2,"tool_calls":1},
                   {"success":False,"model_calls":1,"tool_calls":0}])
assert summary["success_rate"] == 0.5
assert summary["mean_model_calls"] == 1.5
assert metrics([])["success_rate"] is None
```

若任务难度不均，整体平均会掩盖分层表现。十个简单题全对、十个困难题全错，平均五成，但系统能力结构与每类都一半不同。可以按任务类型、长度、工具数、恢复场景和权限风险分层报告，同时保留总分。分层过细样本又会太少，因此需要平衡可解释性与统计稳定性。

任务加权也应明确。每题等权反映任务集合平均，按业务频率加权反映特定使用分布，按价值加权反映另一目标。不能在看到结果后选择最有利权重。若使用真实业务频率，记录来源和时间，避免把过期分布当作长期保证。课程先用等权小集合建立概念，再让你根据实际目标设计权重。

## 第六课：多次采样与 pass@k 回答不同问题

同一任务运行四次，一次成功，单次样本成功率是四分之一。若允许从这四份结果中不放回选两份，只问其中是否至少有一份成功，则六种二元组合里三种含成功，比例二分之一。这就是 pass@k 估计所表达的“给多次候选机会，至少存在一个成功”的问题，不等于系统能自动选出正确候选。

设 n 次采样中 c 次成功，随机取 k 份没有成功的组合数是从 n-c 个失败里选 k，全部组合数是从 n 个里选 k，因此至少一次成功的估计为一减两者比值。若失败数量少于 k，任何 k 份组合都包含成功，结果为一。要求一到 n 之间的整数 k，不能拿只有两次采样的数据计算 pass@十。

$$
\widehat{\mathrm{pass@k}}=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

```python
from labs.agents.evaluation import pass_at_k

assert pass_at_k(4,1,1) == 0.25
assert pass_at_k(4,1,2) == 0.5
assert pass_at_k(4,1,4) == 1.0
assert pass_at_k(4,0,2) == 0.0
```

这里的 pass@四等于一，只说明当前四份样本至少有成功，不保证未来每次生成四份都成功，更不保证一个选择器能识别它。实际部署若运行多个候选再由模型裁判选择，成功率还包含选择器错误。应单独报告候选存在成功率、选择准确率和最终交付成功率，避免把离线 oracle 选择当成真实系统能力。

重复采样次数也影响成本。让一个系统每题尝试十次，另一个只尝试一次，然后比较至少一次成功率，不是公平的单次能力比较。可以在相同总预算下比较策略，或明确展示质量随预算变化的曲线。多次尝试可能有价值，但价值需要与费用、延迟和选择机制一起评估。

任务内 trial 通常不是独立业务样本。它们共享同一问题、环境和难度，统计不确定性时不能把一百题各十次简单当成一千个完全独立任务。可以先按任务汇总，或使用按任务分组的重采样。均值计算可能看起来一样，置信区间与泛化解释却不同。

## 第七课：小样本区间为何不会在全对时变成百分之百

十题全对，观测成功率是一，但样本有限，不能断言真实任务分布上永远正确。一个简单二项模型把每次任务成功看作概率 p 的试验，我们只能根据样本估计 p。Wilson 区间是一种比例区间构造，较常见的朴素正态区间在接近零或一时表现更合理；本章用它演示不确定性，不把统计假设藏起来。

课程实现先验证 successes 与 n 是精确整数、n 大于零、成功数在合法范围内。然后计算样本比例、分母修正、中点与半宽，最后把边界限制在零到一。默认 z 对应常用正态分位数；若你改变 z，应确保它是合理有限正数，当前短函数没有完整配置校验，调用方不能随意传 NaN 后把输出当有效区间。

```python
from labs.agents.evaluation import wilson_interval

low, high = wilson_interval(16,20)
assert 0 <= low < 0.8 < high <= 1
perfect_low, perfect_high = wilson_interval(10,10)
assert perfect_low < 1 and abs(perfect_high - 1) < 1e-12
zero_low, zero_high = wilson_interval(0,10)
assert zero_low == 0 and zero_high > 0
```

边界公式使用浮点运算，理论上一的上界可能得到极接近一的数，因此测试用明确容差比较，而不要求逐位相等。这个修正只处理数值表示，不改变统计解释。

区间的频率学解释不是“真实 p 有百分之九十五概率落在这次区间”，而是这种构造在相应重复抽样条件下具有目标覆盖性质。对于初学工程实践，最重要的是知道点估计有不确定性，并明确方法和假设；不要把一个小数点后两位的百分比当作精确能力值。

任务不独立、样本经过挑选或环境持续变化时，简单二项模型可能不合适。十个几乎相同模板题不能提供与十个不同业务任务相同的信息；只报告成功演示更无法估计总体性能。统计公式无法修复数据选择偏差。先保证任务集合与目标分布关系合理，再计算区间。

区间很宽不是实验失败，而是证据不足的诚实表现。你可以增加任务多样性与样本量、减少不必要变量，或把结论限定在当前小集合。不要为了让区间变窄把同一轨迹复制很多次，这不会增加独立信息。课程强调可解释范围，胜过虚假的精确数字。

## 第八课：成对比较保留同一任务的信息

比较配置 A 与 B，最好在相同任务和相同初始环境上运行。每题产生一对结果，差值是 B 成功标志减 A 成功标志，只可能为负一、零或一。平均差说明 B 相对 A 的任务成功率变化，配对保留了题目难度信息。分别在两组不同任务上测量，差异可能只是任务集合不同。

```python
from labs.agents.evaluation import paired_bootstrap

before = [1,1,0,0,1,0]
after = [1,0,1,0,1,1]
comparison = paired_bootstrap(before,after,repeats=1000,seed=7)
assert abs(comparison["mean_difference"] - 1/6) < 1e-12
same = paired_bootstrap(before,before,repeats=100,seed=1)
assert same["mean_difference"] == 0 and same["percentile_95"] == [0,0]
```

课程 paired_bootstrap 先计算每题差值，再以任务为单位有放回重采样，得到许多平均差，取经验分位数作为区间示例。固定 seed 让报告可复现，repeats 控制重采样次数，不是新的真实任务数量。增加 repeats 只让数值近似更稳定，不会创造更多业务证据。

为什么不能分别打乱 A 与 B 再重采样？因为同一题的关联被破坏，简单题与难题可能错配，差值方差不再反映配对设计。任务内多 trial 时，应先定义任务级指标或使用分层重采样，不能把所有 trial 当独立任务。课程短函数只接受二元任务结果，不是任意复杂实验的通用统计包。

区间跨零表示当前样本下差异方向不够明确，不等于两个系统严格相同；区间不跨零也不代表实际业务收益一定大。需要同时看效果大小、成本、延迟和风险。例如成功率提高一点点但费用翻倍，是否值得取决于用户目标。统计显著性与工程价值不是同一个问题。

## 第九课：延迟指标要按用户体验与资源生命周期定义

一个 Agent 任务可能先等待队列，再发模型请求，随后工具调用，最后生成答案和保存结果。总延迟应从用户提交到可用结果交付；首字延迟反映交互感受；工具完成时间反映业务效果；清理结束时间反映资源回收。只测模型 API 耗时，会漏掉调度、检索和整合瓶颈。

平均值容易被慢尾影响，也可能掩盖少量极慢任务。可以报告中位数、较高分位数和超时比例，但样本小的时候高分位数非常不稳定。十个任务的所谓百分之九十九分位基本由最大值决定，不能装成精细的长期性能估计。报告任务数、计算方法与超时处理，读者才知道数字意味着什么。

超时任务不能简单从延迟统计删除，否则最慢失败消失，系统看起来更快。可以单独报告超时率和截止时间，成功任务延迟作为条件指标，同时保留全部任务的受限耗时。若任务被取消，也应记录取消原因与发生时间，区分用户主动停止和系统性能问题。

时间测量使用单调时钟差值，不使用可能被校准的墙上时钟计算短时延迟。日志仍可保存人类可读时间戳用于跨系统关联，但不同机器时钟偏差需要考虑。离线测试用假时钟验证逻辑，真实性能测试用实际时钟和固定环境，二者证据范围不同。

并发系统还应记录排队时间与执行时间。某 worker 很快完成自身函数，但等资源锁很久，用户仍然慢。A09 的资源获取顺序可能改善排队而不改变函数耗时；如果指标只看函数内部，就看不到改进。观测点应围绕用户任务与资源边界，而不是恰好容易计时的代码行。

## 第十课：成本账本要包含失败、缓存与未知用量

总成本包括所有模型尝试、重试、工具费用、协调者调用和可能的存储或执行资源。只统计最终成功那轮，会低估失败探索与恢复开销。多 Agent 系统尤其要按 run、task、attempt 与角色汇总，避免每个 worker 局部看起来便宜，整体却远超预算。

输入 token、输出 token、缓存相关用量和其他计价项应保留原始服务字段或明确映射，不能把字符数填进 token 列。价格应带版本或生效时间，报告使用假设价格还是实际账单。课程所有费用算例使用人工单价，不声称当前厂商报价；真实成本需要按所选服务核查。

用量缺失应标 unknown 或 estimated。流式连接中断可能没有收到最后 usage，不能因此记零。可以使用本地估计作为上界或近似，但报告估计方法与误差范围。预算预留与最终结算也分开，A06 的未决预留帮助避免未知成本被释放后继续超支。

成功率与成本可组合为“每个成功任务平均成本”，但要明确分母与失败费用是否包含。若把所有任务费用除以成功数，体现为了获得成功结果总体付出；若只平均成功任务自身费用，会忽略失败代价。两者都可有用，但名称应清楚，不能挑较小数字误导。

成本优化还要检查质量回退。减少上下文、降低模型规格或缩短重试可能省钱，却丢失必要证据或增加未知状态。应在固定任务集上同时报告质量、成本与延迟，形成可比较的取舍表。一个单一总分往往隐藏关键变化，尤其用户关注安全边界与恢复正确性时。

## 第十一课：trace 是因果证据，不是把所有文本都存下来

一次有用 trace 应能连接用户任务、模型请求、工具调用、状态版本、外部操作身份和 verifier。最少记录 run_id、step、event_kind、call_id、配置版本、输入摘要、结果状态、耗时和用量。需要深入诊断时再通过受控引用读取原始材料，而不是默认把全部提示、文件内容和授权头复制到日志。

trace 的顺序要与实际提交点一致。model_requested 表示请求已预留并可能发出，model_completed 表示已获得可接受响应，tool_completed 表示结果已进入相应记录。不能用同一个 completed 事件同时表示函数返回、账本保存和用户已收到结果。不同观察层的事件名称应该清楚，A04 的事件与状态关系提供基础。

输入摘要可以帮助确认两次运行是否使用相同材料，但哈希不是匿名化保证。可猜测文本仍可能被枚举，摘要也不能代替访问控制。日志应避免敏感数据进入，必要字段按角色授权读取，保留期限与删除政策明确。结构化脱敏优于事后正则兜底，但任何简单规则都不能承诺识别所有秘密。

```python
from labs.agents.reliability import redact

record = {"authorization":"Bearer secret", "nested":{"api_key":"private", "message":"public text"},
          "items":[{"password":"hidden"}]}
clean = redact(record)
assert clean["authorization"] == "[REDACTED]"
assert clean["nested"]["api_key"] == "[REDACTED]"
assert clean["items"][0]["password"] == "[REDACTED]"
assert clean["nested"]["message"] == "public text"
```

课程 redact 按一组敏感键递归处理字典和列表，再用一个有限正则识别特定形状字符串。它不是完整数据防泄漏系统：未知字段、不同密钥格式、编码内容和私人正文都可能漏掉。正确日志设计先采用字段白名单，只记录诊断必需信息，再用脱敏作为额外保护。不要把授权头写入日志后寄希望于正则全部清除。

trace 也会改变性能和行为。同步记录巨大内容会增加延迟，异步日志可能在崩溃时丢尾部，过多事件会占存储。应区分必须持久的业务事实与可采样诊断数据。工具效果账本不能因为日志采样被丢弃，调试细节则可以按策略降低频率。观测系统不应成为新的不确定性来源。

## 第十二课：失败归因从第一次偏离开始

两个配置面对同一任务，最终一个成功一个失败，先找轨迹第一次不同：上下文材料不同、模型选择不同、参数编码不同、工具结果不同、路由不同还是验证不同。后面的所有差异可能只是早期偏离的连锁结果。逐步比较比只读最后回答更容易定位原因。

失败分类可以分为目标理解、工具选择、参数合同、工具实现、环境依赖、上下文缺失、预算、协议适配、状态恢复、授权和 verifier。分类应基于证据，无法确定就标 unknown，并保留最小复现。不要为了让报表完整给每个失败猜一个原因，错误标签会把后续优化引向错误方向。

一个任务可以有主要原因和次要因素。错误参数导致额外重试，重试耗尽预算，最终表现为 limit；若只按终态分类为预算不足，就可能错误增加预算，而真正问题是参数生成。应记录最早违反的合同与最终停止原因，两者都重要。A06 的阶段分类在评测归因中非常有用。

环境失败也要审查是否属于系统能力范围。若任务合同要求能在预置环境运行，依赖缺失可能是评测环境问题；若任务本身包含建立环境，依赖处理就是能力的一部分。不能一概把环境失败剔除，也不能一概归模型错误。任务说明必须预先定义职责，报告按同一标准处理所有配置。

失败样本应进入回归集，但不要把完整评测保留集都变成开发样本后继续用同一分数宣称泛化。可以把发现的机制 bug 提炼成新的人工最小 fixture，保留原任务作为冻结结果；或明确更新开发集与另设新的保留集。数据治理是长期评测质量的一部分，不只是统计公式。

## 第十三课：四个评测事故复盘

事故一，系统分数提高，因为超时运行被日志管线丢弃。修复为每个预先登记任务建立记录，运行结束无论成功、失败或中断都有状态；缺失结果单独报告并按政策计入。验收故意让一个任务抛异常，报告任务总数仍不减少。分母完整性比漂亮平均更重要。

事故二，编码 Agent 删除测试后退出码零，评测判成功。修复在受保护环境运行冻结 verifier，并检查测试发现数量或身份；Agent 自己的测试输出只作为反馈。验收零测试必须失败，不能把“命令执行完成”当“需求验证通过”。

事故三，新配置只在开发过程中反复使用的题集上提升。报告却称为普遍能力提升。修复区分开发、验证与保留集，记录调参过程和任务版本；冻结最终配置后再评估保留集。若样本太少，明确结论范围，不用同一批题反复挑最好结果。

事故四，团队系统 pass@五高于单 Agent pass@一，被宣传为协作更强。修复固定总预算或同时展示预算曲线，并把候选选择器纳入端到端成功率。验收记录所有尝试费用，不能只保留被选中的成功样本。更多机会与更好组织是不同因果解释。

## 第十四课：十二道完整练习与答案

练习一，正确答案但未调用工具，在两种任务合同下如何判定？答案复用 verify_add_task，普通问答通过，要求工具的任务失败。评测定义应保存 require_tool，避免同轨迹被不同标准解释却没有记录。

```python
h = Harness(ScriptedModel([Turn("9")]), [arithmetic_tool()])
s = h.run(h.new("nine","calculate"))
assert verify_add_task(s,9,False) is True
assert verify_add_task(s,9,True) is False
h.store.close()
```

练习二，工具返回正确但最终答案错误也应失败。答案脚本调用 add 得九，随后回答十，verifier 拒绝。只检查工具值会漏掉最终交付错误，用户实际读到的答案也是合同一部分。

```python
h = Harness(ScriptedModel([Turn(calls=[ToolCall("c","add",'{"a":4,"b":5}')]),Turn("10")]), [arithmetic_tool()])
s = h.run(h.new("wrong-final","calculate"))
assert verify_add_task(s,9,True) is False
h.store.close()
```

练习三，空评测集应返回未知而非零成功率。答案检查 n 与 None，展示“没有样本”不是“全部失败”。报告渲染时应写无数据，不能画成零分柱子误导比较。

```python
empty = metrics([])
assert empty["n"] == 0 and empty["success_rate"] is None
assert empty["mean_model_calls"] is None
```

练习四，手算 pass@一、二、四。答案四次一成功分别为四分之一、二分之一、一。无效 k 超过 n 应报错，不能外推。这个指标不包含选择正确候选的能力。

```python
assert [pass_at_k(4,1,k) for k in (1,2,4)] == [0.25,0.5,1.0]
try:
    pass_at_k(2,1,3)
except ValueError:
    pass
else:
    raise AssertionError("unsupported k accepted")
```

练习五，十次全对的 Wilson 下界仍小于一。答案同时检查全错上界大于零。样本极端结果不等于真实概率已被精确确定；增加独立样本才增加信息。

```python
assert wilson_interval(10,10)[0] < 1
assert wilson_interval(0,10)[1] > 0
```

练习六，两个配置逐题相同，配对差与区间应为零。答案用包含成功失败的数组，避免只测全成功。bootstrap 重复次数不产生新任务，结果反映当前配对差全为零。

```python
same = paired_bootstrap([1,0,1,0],[1,0,1,0],repeats=200,seed=9)
assert same["mean_difference"] == 0
assert same["percentile_95"] == [0,0]
```

练习七，手工计算配对胜负。答案 A 成功 B 失败为退步，A 失败 B 成功为改进，其他为平。净差等于改进数减退步数除任务数，保留这张表比只报两个总分更直观。

```python
a = [1,1,0,0,1]
b = [1,0,1,1,1]
wins = sum(x==0 and y==1 for x,y in zip(a,b))
losses = sum(x==1 and y==0 for x,y in zip(a,b))
assert (wins,losses) == (2,1)
assert (wins-losses)/len(a) == 0.2
```

练习八，分类不能只看最终 limit。答案构造已知 bad_argument fixture，最终虽可能继续回答，classification 仍 invalid_tool_input。这里分类依赖人工 fixture 标签，真实系统需从 trace 提取，不能照搬该实现当通用诊断。

```python
bad = run_case(Case("bad-input",2,3,"bad_argument"))
assert bad["success"] is False and bad["classification"] == "invalid_tool_input"
limited = run_case(Case("limited",2,3,"tool_budget"))

```

练习九，脱敏规则不能证明未知字段安全。答案展示 secret_value 这个未列入敏感键的普通字符串会保留，因此设计应使用日志字段白名单。这个反例不是让你增加一个键就宣称完成，而是理解黑名单的有限性。

```python
leaky = redact({"secret_value":"private plain text"})
assert leaky["secret_value"] == "private plain text"
def safe_log_projection(record):
    return {key:record[key] for key in ("run_id","status","model_calls") if key in record}
```

练习十，零测试退出零不能算成功。完整答案要求退出码零且发现与通过的必要测试集合覆盖合同。真实测试框架应使用结构化结果或受保护测试身份，不能只解析任意 stdout 文字。

```python
def verify_test_run(exit_code, required_tests, passed_tests):
    return exit_code == 0 and bool(required_tests) and set(required_tests) <= set(passed_tests)
assert verify_test_run(0,{"t1"},{"t1"}) is True
assert verify_test_run(0,{"t1"},set()) is False
assert verify_test_run(0,set(),set()) is False
assert verify_test_run(1,{"t1"},{"t1"}) is False
```

练习十一，缺失结果不能缩小分母。答案先登记任务集合，结果缺失者标 missing，成功率按全部任务计算。具体缺失是否等同失败应在政策中说明，本题采用未证明成功即不计成功，同时单独报告缺失数。

```python
def complete_registry(task_ids, observed):
    rows = []
    for task_id in task_ids:
        rows.append(observed.get(task_id,{"task_id":task_id,"success":False,"status":"missing"}))
    return rows
registered = complete_registry(["a","b","c"],{"a":{"task_id":"a","success":True,"status":"finished"},
    "b":{"task_id":"b","success":False,"status":"failed"}})
assert len(registered) == 3
assert sum(row["success"] is True for row in registered)/len(registered) == 1/3
assert sum(row["status"] == "missing" for row in registered) == 1
```

练习十二，成本必须包括失败尝试。答案三次费用分别一、二、三，最后成功，获取该成功的总费用六。只报告最后三会低估一半；若没有成功，成功单位成本不可定义，应报告总费用与零成功。

```python
attempts = [{"cost":1,"success":False},{"cost":2,"success":False},{"cost":3,"success":True}]
total = sum(x["cost"] for x in attempts)
successes = sum(x["success"] is True for x in attempts)
assert total == 6 and total/successes == 6
```

## 第十五课：完整小项目，生成一份可复现离线评测报告

项目把任务列表、配置、逐题结果、汇总和统计范围一起保存为普通字典。它不写真实用户文件，不发网络请求。报告包含明确 purpose，防止读者把脚本回归当真实模型 benchmark；包含 expected_pattern，使测试能证明故意失败样本仍被识别；包含任务版本和 verifier 版本，便于以后比较。

```python
from collections import Counter
import hashlib

EVAL_CASES = [Case("normal",17,25),Case("negative",-3,5),Case("bad",2,3,"bad_argument"),
              Case("claim",2,3,"false_claim"),Case("budget",2,3,"tool_budget")]

def offline_report(cases):
    ids = [case.id for case in cases]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate case id")
    results = [run_case(case) for case in cases]
    count = len(results)
    successes = sum(row["success"] is True for row in results)
    configuration = {"task_version":"arithmetic-v1","verifier_version":"tool-required-v1",
                     "model":"ScriptedModel","network":False}
    encoded = json.dumps(configuration,sort_keys=True,separators=(",",":"))
    return {"purpose":"deterministic harness regression, not model capability",
        "configuration":configuration,"configuration_sha256":hashlib.sha256(encoded.encode()).hexdigest(),
        "results":results,"summary":metrics(results),
        "failures":dict(Counter(row["classification"] for row in results if row["success"] is not True)),
        "illustrative_interval":None if count==0 else list(wilson_interval(successes,count)),
        "interval_scope":"illustration only: curated fault fixtures are not random production tasks"}

report = offline_report(EVAL_CASES)
assert [row["success"] for row in report["results"]] == [True,True,False,False,False]
assert report["summary"]["n"] == 5 and report["summary"]["success_rate"] == 0.4
assert report["failures"] == {"invalid_tool_input":1,"unverified_claim":1,"budget":1}
assert json.loads(json.dumps(report))["configuration"]["network"] is False
```

这里对五个刻意挑选的故障 fixture 计算区间只作公式演示，不能解释为生产成功率区间，因为样本不是从目标任务分布随机抽取。报告专门保存 interval_scope，避免数字脱离假设。更好的真实评测应另建立有代表性的任务集，使用相同报告结构但写清采样方式。

配置摘要只包含选定非敏感字段，不能把整个环境变量或 API key 加入。摘要帮助识别配置是否相同，不替代完整可复现配置与依赖版本记录。任务输入和工具实现版本也会影响结果，真实报告应包含其受控引用。这个小项目保留最小结构，方便你理解每项字段的用途。

failures 使用 Counter 汇总已知分类，逐题结果仍完整保留，避免汇总掩盖具体反例。后续修复如果让 normal 失败，或者让 bad 错误通过，expected_pattern 会检测到。评测器不仅检查 Agent 变好，也检查测量规则没有被放松。维护这类反例是长期工程质量的重要部分。

### 深入一：任务集合怎样覆盖真正能力

一个完整 Agent 评测集不应只有短问答。可以按能力划分：理解目标、选择工具、构造参数、处理多步依赖、检索与引用、修改代码、审批拒绝、预算停止、取消、持久恢复和多角色整合。每类再覆盖正常与故障场景。这样分数下降时能定位能力区域，而不是只有一个总数。

任务难度应来自真实机制，而不是故意模糊措辞。比如让两个工具结果顺序交错，测试编号关联；让参数是布尔而 schema 要整数，测试类型合同；让副作用提交后响应丢失，测试不确定恢复。这些任务有明确预期，适合机制回归。开放研究与代码修复则需要更丰富环境和验收，不能用同一简单字符串比较覆盖。

任务输入、初始数据和 verifier 都应版本化。修改一个隐藏测试会改变成功定义，更新文档快照会改变事实答案，调整工具权限会改变可达路径。报告保存 task_version 与 environment_version，比较时确认它们一致。若必须更新任务集，可以同时保留旧集回归与新集能力结果，避免把两个不同考试的分数直接相减。

开发集用于调试与选择策略，保留集用于冻结配置后的评估。反复查看保留集失败并针对性修改，就逐渐把它变成开发集。实际小项目不一定能保持完全盲测，但应诚实记录使用方式，必要时收集新的任务。不要用术语 test set 掩盖已经被反复调参使用的事实。

代表性也不是数量越大越好。大量同模板算术题可以精确测某个窄机制，却无法代表复杂编码或研究任务。应把结论限定到覆盖范围，或者按目标业务分布采样。用户希望自学 LLM 全栈，课程回归应覆盖工程边界；真实产品上线则需要来自产品目标的任务与风险模型，两者不能直接互换。

### 深入二：环境重置防止前一轮污染后一轮

Agent 会改变文件、数据库和缓存。如果第二次运行继承第一次结果，可能看起来更快更准，却不是独立尝试。每个 trial 应从明确初始状态开始：复制受控工作区、创建新数据库、固定检索快照、清理本任务缓存或记录缓存政策。重置范围只针对评测资源，不使用广泛系统清理。

有些实验故意研究持续学习或长期记忆，此时不应重置全部状态，但必须把跨任务记忆作为处理变量。记录哪些信息可继承、何时写入、是否包含答案泄漏，比较时双方使用相同政策。把一个带历史记忆系统与一个每题冷启动系统比较，可以有意义，但结论应说明差异来自状态使用，而不是只归因于模型。

缓存也会影响延迟与成本。冷缓存与热缓存是两种环境条件，最好分别报告或固定预热流程。若配置 A 先运行填热共享缓存，配置 B 后运行获益，顺序会偏置比较。可以交错或随机化运行顺序，隔离缓存，或者把顺序作为设计因素记录。相同任务不自动意味着相同环境。

外部网页与 API 会变化，实时评测需要保存受控响应或记录获取时间和内容摘要。若任务目标本来就是当前信息，完全冻结资料可能不符合目标，但至少应让两个配置在尽量相近条件下运行，并保留差异来源。课程离线 fixture 的优势是稳定，代价是不能代表最新线上行为；两种证据应并存。

随机种子也有限。固定 Python random 不会控制远端模型采样、服务路由、网络时序或非确定工具。报告 seed 的同时说明它控制哪个组件，不能把一个 seed 字段当作完全可复现保证。真正复现需要任务、配置、环境、工具结果和状态版本共同记录。

### 深入三：模型裁判如何使用而不替代事实验证

有些输出无法简单精确匹配，例如研究报告是否覆盖要点、解释是否清晰。这时可以使用人工或模型裁判按 rubric 评分。rubric 应列具体维度与锚点，例如事实准确、引用支持、约束遵守、完整性和表达，而不是只问“这个答案好吗”。评分应保留逐项理由和证据位置，便于复核。

模型裁判可能偏好更长回答、特定风格或先出现的候选，也可能被答案中的指令影响。可以隐藏系统身份、随机化顺序、要求只依据任务与证据、用已知好坏样本校准，并抽样人工复核。裁判输入中的待评答案仍是不可信数据，不能允许它修改评分规则或访问额外工具。

对可确定事实，优先使用程序验证。例如工具是否实际调用、数据库是否创建一行、测试是否通过、引用编号是否存在，都不需要模型猜。模型裁判适合补充难以形式化维度，不能覆盖确定性 verifier 已发现的失败。一个文笔流畅但越权写文件的答案，不能因综合评分高而算成功。

裁判一致性也需要测量。同一答案多次评分波动很大，或不同裁判分歧很大，说明 rubric 或任务存在歧义。可以记录分布与争议，不强行压成精确小数。对高影响决策，必要时采用人工复核和明确责任边界。评测器本身是系统组件，也需要版本、测试和成本统计。

不要把模型给出的理由当作它真实决策过程的证明。理由可以帮助人类审查评分是否符合 rubric，但最终仍应核对答案和证据。若裁判理由引用了不存在内容，应标记评测错误并修复，而不是让被评系统承担错误分数。公平评测需要同时审查被测系统与测量工具。

### 深入四：轨迹指标怎样与业务结果配合

最终成功率告诉你任务是否完成，过程指标解释怎样完成。可以记录模型调用数、工具调用数、无效参数率、重复查询率、上下文裁剪次数、审批等待、恢复次数和未授权请求尝试。过程指标有助于发现成本与稳定性问题，但不能替代最终结果。调用少不一定好，可能因为过早放弃；调用多不一定坏，可能因为必要验证。

安全相关过程指标尤其要区分尝试与效果。模型提出越权调用，执行器拒绝，说明模型策略有问题但边界有效；模型没有明显越权文本，却通过宽泛工具实际读取敏感文件，属于效果失败。评测应同时检查请求日志和实际环境差异，不能只读最终拒绝声明。

恢复指标可以记录未知状态识别率、重复效果次数、结果回填正确率和恢复后终态保持。一个系统遇到故障总停止 unknown，可能安全但可用性不足；另一个自动重试成功率高却重复副作用，也不可接受。应该同时报告安全停止与自动恢复能力，避免单一成功率奖励危险猜测。

过程指标也可能被优化到失真。若只奖励少调用，系统可能跳过必要工具；若只奖励引用数量，系统可能堆无关来源；若只奖励测试通过，系统可能改测试。指标应围绕任务目标，并配合反例防止取巧。A03 的合同和受保护 verifier 是抵抗指标游戏的基础。

### 深入五：从 trace 建立最小反例

真实失败轨迹可能很长，包含大量无关对话。把它提炼成最小反例，可以更快定位并防止回归。例如从十轮任务中抽出导致 tool_call_id 串线的两条调用与两条结果；从长编码过程抽出旧摘要覆盖新文件的两次编辑；从复杂团队中抽出重复 message_id 不同内容。最小反例保留触发机制，去掉敏感和无关信息。

提炼时要保持关键属性。删除中文可能让 UTF-8 分块 bug 消失，统一调用编号可能制造新冲突，删除等待点可能让并发竞争不再发生。应先写明失败所依赖的属性，再构造人工数据保留它们。这样可以把私人轨迹转成公开、可重复的课程 fixture，而不暴露原始内容。

回归测试应先在旧实现上失败，再在修复后通过；若无法运行旧实现，至少解释反例对应的错误路径。不要只写一个与新代码实现完全相同的测试，容易两者一起错。测试应表达外部合同，例如效果只一次、状态不覆盖、来源可追溯，而不是断言某个内部辅助函数被调用了几次。

失败归因修复后还要检查相邻边界。修复最后一步 finished 被覆盖后，应同时测试 error、uncertain 和 cancelled 的最后步终态；修复 bool 作为整数后，检查预算与并发配置是否也受影响。扩展范围应由同一机制驱动，不是无目的增加测试数量。必要检查通过后继续交付，不重复跑没有新信息的巨大套件。

### 深入六：配对报告必须按任务身份对齐

两个结果数组长度相同，不代表第一个元素对应同一任务。异步执行可能按完成顺序返回，缺失任务可能被过滤，文件读取顺序也可能变化。配对比较前应按稳定 task_id 对齐，检查任务集合完全相同，重复编号拒绝，缺失明确报告。否则统计公式再正确，也是在比较错配数据。

```python
def align_paired_rows(before_rows, after_rows):
    def index(rows):
        result = {}
        for row in rows:
            task_id = row["task_id"]
            if task_id in result:
                raise ValueError("duplicate task id")
            if type(row["success"]) is not bool:
                raise ValueError("strict boolean outcome required")
            result[task_id] = row
        return result
    left, right = index(before_rows), index(after_rows)
    if set(left) != set(right):
        raise ValueError("paired task sets differ")
    ids = sorted(left)
    return ids, [left[key]["success"] for key in ids], [right[key]["success"] for key in ids]

ids, left, right = align_paired_rows(
    [{"task_id":"b","success":False},{"task_id":"a","success":True}],
    [{"task_id":"a","success":True},{"task_id":"b","success":True}])
assert ids == ["a","b"] and left == [True,False] and right == [True,True]
paired_report = paired_bootstrap(left,right,repeats=500,seed=4)
assert paired_report["mean_difference"] == 0.5
```

严格布尔验证避免 success 字段里混入一、字符串或缺失值。课程 paired_bootstrap 本身接受二元等价值，外部报告入口可以更严格，保证数据来源清楚。排序只为稳定展示，真正配对依据 id。若任务版本不同但 id 相同，还应把版本纳入身份或先拒绝比较，避免把修改后的题目当同题。

这段两题示例的差值很大，但样本太小，不足以得出普遍胜出结论。它用于验证对齐与统计管线。真实报告应保存每题差、胜负数、区间、成本差和失败样本，读者可以看到改进来自哪些任务，而不是只看到一个总分。

### 深入七：风险事件与普通错误不宜混成一个平均数

一个系统在九十九个简单任务成功，却在一个任务泄漏私有数据，平均成功率可能看起来很高。对权限、重复付款、破坏性修改等高影响事件，应单独设硬性验收与风险指标，不能让大量低风险成功抵消。任务成功、约束遵守和严重效果应分别报告。

风险测试集合通常刻意覆盖边界，不代表真实发生频率。你可以报告“这些对抗场景中出现几次越权效果”，但不能直接把比例解释为日常用户遭遇概率。真实风险估计还需要任务分布与暴露条件。机制测试证明边界是否有效，生产监控估计实际发生情况，两者角色不同。

误拒绝也有成本。执行器过于保守可能阻止合法任务，系统总返回 uncertain 也会降低可用性。可以同时记录不安全接受与不必要拒绝，按任务风险决定取舍。不要为了提高完成率取消关键约束，也不要为了零风险分数把所有任务拒绝后宣称优秀。验收应要求在授权范围内有效完成。

对需要人工批准的任务，正确等待是过程成功，但整体业务尚未完成；用户明确拒绝后不执行是正确行为，不能按普通完成任务计失败而诱导系统绕过批准。评测任务应把用户事件脚本作为环境的一部分，分别定义批准、拒绝、取消和无回应路径的预期结果。

### 深入八：实验变量与消融设计

如果同时修改模型、提示词、工具 schema 和上下文策略，最终分数变化无法归因。消融实验每次移除或替换一个组件，观察变化，帮助判断它是否贡献价值。比如固定模型和预算，比较有无固定任务合同；固定检索结果，比较有无来源验证；固定工具实现，比较不同重试政策。

消融也可能改变其他条件。去掉摘要节点会减少成本但增加上下文长度，去掉审查者会减少调用却可能改变预算分配。应记录这些连带变化，必要时设计预算匹配对照。实验不是机械“只改一行”，而是让因果解释尽量清楚。无法完全控制时，明确承认结论范围。

任务运行顺序可以随机化或交错，降低时间相关服务变化影响。固定种子控制顺序生成，保存实际顺序；但如果服务状态持续变化，仍不能完全消除偏差。多次独立批次可以帮助观察稳定性，批次间差异也应报告，而不是挑最好一批。

调参需要预先定义停止规则。反复试很多提示，最后选最高分，再用同一集报告，会产生选择偏差。可以保留验证集选择配置，最终只在冻结保留集评估一次或明确报告多次探索。小项目也应记录尝试过哪些配置，避免自己被偶然波动误导。

### 深入九：长期监控与离线评测形成反馈闭环

离线任务集无法覆盖所有真实输入，线上监控可以发现新的失败类型。但线上数据可能包含私人内容，采集应最小化并遵循用户与应用权限。可以先记录结构指标、错误类别、状态与受控摘要，再在需要时通过明确流程获取脱敏样本。不能为了评测方便默认保存所有对话和文件。

监控可以设置明确阈值，例如无效参数率突然上升、某协议错误激增、未决副作用积压、平均调用数异常增加。阈值应结合基线和样本量，避免少量随机波动触发频繁告警。告警指出需要调查，不自动证明模型退化；可能是服务更新、数据分布变化或工具故障。

发现问题后，先构造最小复现并加入回归，再修复，随后运行相关组件与端到端样本。发布后继续监控同类指标，确认修复没有转移问题。例如减少超时可能增加截断答案，降低上下文可能增加遗漏，强化权限可能增加误拒绝。反馈闭环需要多个指标共同解释。

版本回退也要考虑持久状态兼容。新版本已经写入新 schema，简单回滚代码可能无法读取；工具行为改变后旧 pending 也可能不兼容。评测发布流程应包含状态迁移与回退演练，而不只是模型回答分数。A10 与 A11 的恢复合同是长期 Agent 产品评测的重要部分。

### 深入十：一份报告怎样让别人真正复核

报告应首先说清测了什么和主要结果，然后提供任务数、配置、预算、环境、verifier 与不确定性。逐题明细和失败样本作为可追溯附件，读者能够从汇总回到原始证据。不要只放截图或最好看的运行视频，它们难以证明分母完整和失败处理。

例如可以写：“在固定五项离线宿主回归中，两个正常样本通过，三个故障样本按预期拒绝；这验证了工具合同与 verifier，不代表真实模型成功率。”这句话比“通过率四成”更准确，因为此集合的目标是识别故障。真实能力评测则应写成功任务数与总任务数、费用和延迟，并说明采样与限制。

报告还应列未执行项及原因。没有 API key 就写真实模型调用未执行，没有 GPU 就写 GPU 集成未验证；不能用编译通过替代运行通过。用户可以据此决定下一步投入。诚实边界不会降低成果价值，反而让后续扩展有明确起点。

每个结论应有对应证据。声称没有重复效果，需要业务记录计数或幂等测试；声称审批有效，需要拒绝与参数变化反例；声称更便宜，需要完整费用账本；声称更快，需要相同环境下延迟数据。若找不到证据，就把它改成假设或待验证事项，而不是用自信语气补足。

### 深入十一：课程掌握门槛与真实小评测方案

完成本章后，先独立复现五个算术 fixture 的预期模式，解释每个失败为何被拒绝；再给 verifier 添加一个假成功反例，证明测量规则没有漏洞；随后对两个离线配置按 task_id 对齐比较，报告净差与成本。这个过程应完全不依赖真实模型，确保你掌握评测管线本身。

真实小评测可以选择十个你能人工验证的任务，每题固定三次尝试，两个配置使用相同总预算和工具环境。任务包括简单工具、多步依赖、检索引用、只读约束和一个受控失败恢复。提前写成功标准，冻结配置后运行，保存每题每次结果、usage、耗时、失败轨迹与人工复核结论。不要自动扩展到昂贵大规模运行。

样本小的时候，结论应以发现问题和建立流程为主。某配置多成功一题，可以报告观察到的差异和区间，不宣称普遍领先。若差异集中在同一类任务，设计新的独立任务验证假设；若费用增加明显，分析是否来自重复上下文、重试或协调者开销。实验结果应推动下一项具体改进，而不是只成为展示数字。

你最终应能回答：这次修改改变了哪个组件，预期改善哪个失败机制，用什么任务与 verifier 测量，哪些变量固定，哪些仍可能影响结果，成本和风险怎样变化。能清楚回答这些问题，就具备把 Agent 从演示推进到可维护系统的评测能力。

### 深入十二：当验证器不是完美测量仪器时

若使用自动裁判判断答案正确，裁判可能误判。可以抽取一组人工确认样本，构造混淆表：真实正确且判正确、真实错误却判正确、真实正确却判错误、真实错误且判错误。前者与后者是正确判定，中间两类分别是误接受和误拒绝。只看裁判总体准确率，可能掩盖对关键错误的高误接受。

精确率回答“被判正确的结果里有多少真正确”，召回率回答“真实正确结果里有多少被识别”。对高风险动作，误接受尤其重要；对学习反馈，误拒绝也会让用户浪费时间。指标选择应对应测量用途，不能因为一个数字高就把裁判当绝对权威。人工标签本身也要有清楚标准和争议复核。

```python
def judge_metrics(truth, judged):
    if len(truth) != len(judged):
        raise ValueError("paired labels required")
    if any(type(x) is not bool for x in truth + judged):
        raise ValueError("boolean labels required")
    tp = sum(a and b for a,b in zip(truth,judged))
    fp = sum((not a) and b for a,b in zip(truth,judged))
    fn = sum(a and (not b) for a,b in zip(truth,judged))
    tn = sum((not a) and (not b) for a,b in zip(truth,judged))
    return {"tp":tp,"fp":fp,"fn":fn,"tn":tn,
            "precision":None if tp+fp==0 else tp/(tp+fp),
            "recall":None if tp+fn==0 else tp/(tp+fn)}

judging = judge_metrics([True,True,False,False],[True,False,True,False])
assert judging == {"tp":1,"fp":1,"fn":1,"tn":1,"precision":0.5,"recall":0.5}
```

分母为零时返回 None，仍然遵守没有数据不等于零的原则。若裁判从不判正确，精确率没有定义，不能说它精确率百分之百；若样本没有真实正确项，召回率也不能估计。报告应保留原始四格计数，帮助读者判断样本构成。

裁判误差会影响系统排名。两个配置的回答风格不同，裁判可能偏好其中一种，即使真实正确率相同；一个配置更简短，可能被误判不完整；另一个引用很多无关内容，可能被误判证据充分。使用受保护确定性 verifier、人工抽查和风格无关 rubric，可以降低这类偏差，但不能承诺完全消除。

还有一个选择偏差来自只复核裁判判错的样本。若从不检查判对样本，误接受会长期隐藏，系统分数可能虚高。抽查应覆盖判对与判错，并按风险或任务类型分层。发现某类误判后更新 verifier，同时重新计算受影响历史结果，报告版本变化。测量系统需要持续维护，和 Agent 本体一样。

最后，不要把评测与训练数据边界混淆。若把保留集答案放进检索库或长期记忆，Agent 可能直接找到答案，测到的是泄漏后的表现。对于允许检索的任务，应明确哪些资料属于合法环境，哪些是隐藏验收标签；二者分开存储和权限。答案泄漏可能来自文件路径、测试名称、错误信息或缓存，不只来自显式训练。构造干净环境与来源审计能帮助发现这些问题。

评测数据还应区分训练可见、开发可见和最终验收可见。公开测试帮助 Agent 迭代，隐藏测试检查泛化；但隐藏并不意味着可以随意改变需求。最终测试必须对应任务说明中的合理行为，不能靠未告知的任意规则惩罚系统。若发现任务本身有歧义，应修订任务版本，并把旧结果标记为不可直接比较。

对于长期任务，成功可能在评测窗口之后才得到确认。例如远端工单创建结果未知，稍后对账发现已成功。应保存初始状态与最终核验状态两个时间点，明确指标按何时截断。若把后来成功悄悄回填成当时成功，会掩盖用户经历的等待与不确定；若永远不更新，也会丢失最终业务事实。可以同时报告及时完成率与最终确认率。

这类指标需要稳定运行身份与不可覆盖审计。初次 verifier 结果、后续核验结果和原因都应保留，派生报表再选择时间范围。A10 的追加核验事件正好提供基础。评测系统不应为了整洁只保存最后一个 success 布尔，否则无法分析恢复价值和用户体验。

当你能从一份报告追溯到任务合同、环境快照、真实动作、验证器版本与后续核验，就已经建立了比单次演示更扎实的证据体系。接下来修改提示词、工具或框架时，都可以在同一体系里判断进步与回退。

报告生成失败也必须被记录，不能让测量管线异常把整个批次从统计中消失。先登记运行清单，再逐项补齐结果，最后检查清单完整性，是避免幸存者偏差的简单有效做法。
