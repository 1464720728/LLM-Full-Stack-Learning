# A13 评测、追踪与回归：知道系统何时真的进步

## 先写成功标准，再运行 Agent

一个系统输出“任务完成”不构成评测。你要先定义任务输入、初始环境、可用工具、时间与调用预算、停止规则和 verifier。编码任务可以用独立测试与差异检查；检索任务可以核对答案与证据来源；工单任务可以查询最终数据库状态。不同任务需要不同证据，不能统一用模型自己打分替代。

本卷算术评测要求“使用 add 工具算出答案”。因此只输出正确数字但没有调用工具，仍不满足这个特定任务标准。另一个只要求答案正确的任务可以允许心算。规则必须事先固定，不能看见某个模型表现好后临时改变分母或成功定义。

评测对象也要明确：测模型本身、测协议适配器、测工具执行器、测 Harness，还是测完整 Agent 系统？同一个底层模型，换工具接口、提示词、上下文裁剪、重试策略和环境，端到端结果都可能不同。把整个系统分数直接称为“模型智商”会掩盖这些变量。

## 三层测试与证据

单元测试检查小机制：布尔参数不能当整数、重复 JSON 键被拒绝、工具 ID 配对正确。集成测试检查跨组件：模型提出调用→验证→执行→ledger→恢复→最终消息。端到端评测使用真实模型与真实任务环境，观察目标完成率、费用和延迟。

这三层互补。单元测试全通过，不说明真实模型会选择正确工具；真实任务偶尔成功，也不说明崩溃恢复没有 bug。课程中的 ScriptedModel 用于确定性回归，线上模型用于能力和策略比较。每个报告必须标明测试类别，不要把几十个离线 fixture 通过包装成真实 Agent benchmark 高分。

运行：

```bash
python -m labs.agents.evaluation
python -m unittest tests.test_agents_core tests.test_agents_evaluation -v
```

离线评价故意包含两个成功场景和三个失败场景。正确结果是 `[true,true,false,false,false]`，不是“全部成功”。测试的目的在于 verifier 能识别失败。如果你改代码让五项全绿，却只是放松验收，那是评测失效而不是 Agent 变强。

## 平均成功率、pass@k 与重复采样

假设一个任务独立尝试四次，只有一次成功。样本平均成功率为 1/4。若允许从这四个样本中不放回抽两个，至少一个成功的比例是 `1-C(3,2)/C(4,2)=1/2`，这对应一种 pass@2 估计。它们回答不同问题：单次成功的水平，与给多次机会后至少一次成功的水平。

一般式为：

\[
\widehat{\mathrm{pass@k}} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}
\]

其中 n 是同任务采样数，c 是成功数，要求 k≤n。这个统计量本身不告诉你怎样自动识别哪次是正确答案，也不代表“运行 k 次然后让模型挑一次”的实际成功率。后者还受选择器影响。

如果每题重复 N 次再取平均，统计单位可以是“每题平均成功率后再平均”，也可以把所有 trial 混合计数；在每题次数相同时数值可能相同，但方差估计与任务难度分层不同。报告里应写清任务数、每题次数、聚合方式和选择规则，不把 repeats=N 简化成 pass@N。

## 小样本不确定性

20 个任务成功 16 个，点估计是 80%，但不能说真实性能精确等于 80%。`wilson_interval` 提供二项比例区间示例。即使 10/10 全成功，下界也低于 100%，因为样本有限。区间计算有统计假设；任务之间高度相关或数据经过挑选时，简单二项模型可能低估不确定性。

比较系统 A 与 B，应尽量使用相同任务和相同初始环境，保留成对结果。某题 A 成功 B 失败与另一题反过来，提供的信息不同于两个无配对总分。`paired_bootstrap` 以任务为单位重采样差值，展示一种估计差异不确定性的做法。重复 trial 存在任务内相关时，应按任务聚合或做分层/簇 bootstrap，不能把所有 trial 当完全独立样本随意放大样本量。

用户关心量化前后小幅精度变化时，这些问题尤其重要。即使底层推理固定随机种子，Agent 会与环境交互，工具时序、文件状态、网络内容、重试、时间限制都可能改变轨迹。确定性模型输出是一个控制变量，不是完整实验可复现性的全部。

## 分层归因与轨迹比较

失败分类可以包括模型未理解目标、工具选择错误、参数错误、工具故障、环境缺依赖、预算耗尽、上下文信息丢失、验证器错误和不可确定副作用。分类应基于 trace，不凭最终文字猜测。初始输入相同而第二轮开始分岔时，比较上一轮模型动作、工具执行、观察编码和上下文构建，定位第一次不同发生在哪里。

一个有价值的 trace 包含运行 ID、模型请求 ID、工具调用 ID、输入摘要/hash、配置版本、时间、usage、状态转移和 verifier 结果。不要默认保存全部密钥或私人内容；`redact` 展示结构化敏感字段过滤。正则只能兜底，不能承诺发现所有秘密。最好在日志设计时根本不把授权头与原始私有文件写进去。

运行 `24-redaction`，嵌套 api_key 与 authorization 被替换。再故意把秘密放在一个未知字段，思考为何简单 key 列表不足。生产观测需要按数据类别和访问权限设计，而不是写一个正则就认为万无一失。

## 数据泄漏与验证器被修改

编码 Agent 能修改测试环境时，必须防止它通过删除测试、改断言或改测试发现规则“获得通过”。常见方法是把最终 verifier 放在受保护位置，Agent 只看到部分公开测试，最终在干净环境应用 patch 再运行。Agent 自己运行的测试属于有用反馈，但不能直接替代独立最终验收。

评测任务也应与开发调参集分开。你反复看同一批题修提示词，再报告这批题分数，测到的是对开发集适应。保留冻结测试集、版本化任务与环境，记录调参过程。小课程可以先分开发集和保留集，不必一开始就建设庞大平台。

## 练习与参考解法

1. **假成功。** 模型输出正确答案但没有调用 add。验收：工具任务失败，普通问答任务可成功，两种判定独立。参考：把任务要求写进 verifier 参数，不能硬编码一种标准适用所有任务。

2. **统计手算。** n=4、c=1，计算 pass@1、pass@2、pass@4。答案为 0.25、0.5、1。解释最后一个 1 只说明现有四次样本包含成功，并不代表选择器肯定选到正确结果。

3. **失败标签。** 构造错误参数、工具异常、预算不足和空最终回答四类轨迹。验收：报告能区分原因，不能统一叫 wrong answer。参考：分类程序读取状态事件和 verifier，未知情况标 unknown，不猜测。

4. **成对比较。** 两系统十题结果分别给定，计算每题差与平均差，跑 bootstrap。验收：两系统完全相同结果时差区间为 [0,0]。参考：bootstrap 保留任务配对，不分别打乱两个数组。

5. **测试篡改。** 模拟 Agent 删除公开测试，使本地测试发现零项。验收：独立 verifier 仍拒绝。参考：检查预期测试身份或在保护环境运行冻结测试，不只看 exit_code=0。

6. **协议回归集。** 保存至少六份脱敏响应 fixture：普通文本、单工具、多工具、截断、拒绝、未知项。验收：升级适配器时逐项稳定检查行为。参考：fixture 不是线上性能证据，但能防止重复引入协议 bug。

7. **真实小评测。** 选择 10 个你能人工验证的任务，固定每题三次、固定预算，分别运行两个配置。交付每题 trial 表、成功定义、总费用、错误轨迹和不确定性说明。参考：样本小则结论保守，不把一次 1 题优势写成普遍胜出。

通过门槛：你能给出“这个改变改善了什么、证据在哪、哪些变量仍未控制”的回答，并能用失败样本推动修复，而不是只展示最好看的运行录像。
