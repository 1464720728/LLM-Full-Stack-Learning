# A09 并发与调度：更快地做独立工作，而不制造重复效果

## 先区分并发和并行

并发表示多个任务的生命周期相互交错；并行表示它们在同一时刻实际执行。一个单线程事件循环可以并发等待多个 HTTP 请求，但不能因为写了 async 就让 CPU 密集 Python 计算自动利用多个核心。GPU 并行又属于另一层。本章关注 Harness 如何调度独立 IO 操作、限制资源、收集结果和处理取消。

例如检索三个互不依赖的文档库，每个请求都要等待网络，顺序耗时大致是三个延迟相加；并发耗时接近最慢请求加协调开销。但如果第二个请求的查询条件依赖第一个结果，它们就不能随意并发。决定能否并发的是依赖关系和副作用，不是函数名是否有 async。

## 工具调用列表不保证可安全并发

模型一轮输出两个工具请求，只说明它在同一响应中提出了两项动作。第一项写 `config.json`，第二项读它，可能有顺序依赖；两个工具同时修改同一个文件，会产生覆盖；两个支付动作即使参数不同，也可能共享账户约束。

调度器应有工具元数据，例如只读、可重试、资源键、最大并发、是否要求顺序。对只读且互不依赖的查询可以并发；对共享状态的操作需序列化、锁或事务。模型可以提供依赖提示，但不能作为唯一可靠依据。业务工具作者更了解资源语义，应当把这些约束显式暴露。

我们的主 Harness 选择顺序执行待处理工具，方便初学者追踪与恢复。并发实验单独放在 `bounded_fanout`，避免在尚未理解持久状态之前把调度复杂度混入主循环。你后面的扩展任务会把它们接起来，但必须先定义并发工具结果怎样保存和排序。

## Semaphore 怎样限制在途任务

`asyncio.Semaphore(limit)` 可以理解为有 limit 张通行证。每个 worker 执行前获得一张，完成或异常退出时归还。`async with` 保证离开区域时释放资源。设 limit=2，六个独立任务最多两个处于工具主体中；剩余任务等待，避免瞬间把 API、数据库连接或文件句柄用尽。

槽位数的类型也是安全边界。本课程的 `bounded_fanout` 与 `resource_fanout` 都要求严格正整数，并拒绝布尔值、1.5、NaN、无穷大和字符串。不能假设底层 Semaphore 自动完成业务参数验证：分数计数递减时可能绕过以零为边界的阻塞判断，使看似有限的配置实际上放行所有任务。先验证，再创建任何 worker；回归测试除了正常 limit=2 的并发峰值，还检查所有错误输入下 worker 一次都没运行。

运行 `20-fanout`。结果值为 `[0,1,4,9,16,25]`，peak 不超过 2。这里并发峰值通过计数器和明确 yield 检查，不依赖真实耗时。测试关注逻辑约束，不能用“在我的机器上 0.02 秒完成”证明没有超过并发上限。

`asyncio.gather` 的返回顺序与输入任务顺序一致，即使完成顺序不同。这个性质方便把结果绑定任务列表，但你仍应携带调用 ID；一旦改用 as_completed 或事件流，顺序就可能不同。不要把数组位置作为唯一业务身份。

## 失败时清理剩余任务

假设三个并发查询中第一个失败，其他两个仍在运行。上层立刻抛错却不取消它们，会产生孤儿任务：它们继续占连接、写日志甚至产生副作用。参考实现捕获失败后，取消所有任务，再用 `gather(...,return_exceptions=True)` 等待它们完成取消清理，最后重新抛出原失败。

取消任务不是随便丢弃 Python 对象。协程通常在 await 点响应取消，函数应在 finally 中释放资源。若里面直接运行阻塞函数，事件循环无法及时调度取消。对外部副作用，取消不能证明动作没发生，所以即使任务对象被取消，业务层仍可能需要查结果。

还有一种策略是收集所有结果而不是 fail-fast。如果任务相互独立，部分成功仍有价值，可以把每个结果包装成 success/error，等待全部结束。但这应是明确产品语义。不要一边声称“任何失败就停止”，一边偷偷保留后台动作继续执行。

## 并发状态修改为什么危险

下面的伪过程容易出错：两个 worker 都读 budget.remaining=1，都认为还可以请求，然后各发一次请求，最后都写 remaining=0。最终账本看起来没超支，实际发了两次。这是典型检查—执行竞态。正确做法是把预算预留放在同一锁或数据库事务中，发请求前先成功拿到配额。

文件写入、任务领取、工具调用 ID 去重也有类似问题。async 单线程并不自动消除竞态，因为每次 await 都允许其他协程修改共享状态。你应把“哪些代码之间不能插入别人的修改”作为设计对象，而不是只背“Python 有 GIL”。GIL 并不能提供跨 await 的业务事务，也不能保护多进程或外部系统。

本卷 SQLite Store 假设一个 run 只有一个执行所有者。它用版本防盲覆盖，用 ledger记录效果，但没有实现租约续期和多 worker 任务领取。要扩展分布式 worker，需要独立设计 owner_id、lease_expires、心跳、重领规则和业务幂等；这些机制不是把 `sqlite3.connect` 换成 PostgreSQL 就自动拥有。

## 公平性与背压

一个长任务可以发出大量子请求，如果它占满全局并发槽，其他短任务会挨饿。调度器常需要全局上限、每用户上限、每任务上限、每提供方上限同时存在。资源限制也不止请求数：输入 token 很大的请求与短请求占用不同服务资源，简单计数只能作为近似。

排队本身需要上限。无限接受任务会把过载藏进越来越长的等待时间。你可以拒绝、限流或返回明确排队位置；重要的是让系统对外表达真实状态。对于课程里的单用户学习工具，简单 bounded queue 足够建立概念；生产系统再根据服务目标选择更复杂策略。

## 练习与参考解法

1. **峰值限制。** 把 limit 改为 1、2、4，记录逻辑 peak。验收：每次不超上限，返回结果集合相同。参考：性能未必严格随 limit 增大改善，尤其真实提供方有限流；正确性测试不要断言加速倍数。

2. **完成乱序。** 用 Event 控制各 worker 完成次序，确认 gather 结果仍按输入排列。参考：另外输出带 task_id 的完成事件，展示完成顺序与结果排列不同。

3. **故障回收。** 一个 worker 抛错，其他 worker 在 finally 记录退出。验收：函数返回或抛出后没有仍存活子任务。参考：取消后必须 await 回收，不只是调用 cancel。

4. **共享预算竞态。** 构造两个 worker 在读余额后同时 await，然后都扣减。验收：稳定复现超发，再用 asyncio.Lock 修复。参考：锁覆盖配额预留，不应把整个网络等待都锁住，否则退化为串行。

5. **冲突资源调度。** 工具声明 resource_key，相同 key 串行，不同 key 可并发。验收：两个写同一文件的操作不会重叠，两个独立读可以。参考：锁字典需要生命周期管理，避免资源 key 无限增长。

6. **部分结果策略。** 实现 `collect_all`，每项返回 `{id,ok,value/error}`。验收：一个失败不丢其他结果，同时任务整体状态明确为 partial 而非全部成功。参考：让调用方选择 fail-fast 或 collect-all，别隐藏在异常处理内部。

通过门槛：给你一组工具动作，你能先画依赖和资源冲突，再决定哪些并发；能证明取消后资源被回收、预算没有被同时穿透，而不仅是“代码看上去有 async”。
