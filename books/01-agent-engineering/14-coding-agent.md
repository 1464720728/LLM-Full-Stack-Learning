# A14 综合项目：构建一个能修复、验证、解释修改的编码助手

## 项目交付是什么

编码 Agent 的任务不是生成一段可能正确的代码，而是在给定仓库与约束下改变实际文件，并提供可验证结果。一个完整闭环包括环境准备、阅读任务、定位代码、提出修改、应用 patch、运行测试、解释失败、继续修正和最终验收。真实工程还会涉及依赖安装、构建系统、测试时长、并发修改、网络权限和成果提交。

本卷提供一个完整、可运行、确定性的修复夹具，用来验证 Harness 与工具协同。它不声称 ScriptedModel 具备代码推理能力。你先把这个工程闭环跑通，再把模型适配器替换成真实服务，用更复杂任务测能力。这样不会在同一时间调试工具执行、协议错误和模型行为三类问题。

## 项目中的错误

课程创建 `price.py`：

```python
def total(price, rate):
    return price * (1 - rate)
```

需求是税后总价 `price*(1+rate)`。公开测试覆盖 price=100、rate=0.2，期望120；另一项覆盖零税率，应保持100。初始程序返回80，因此首个测试失败。正确修改应只把减号改为加号，而不是删除测试或硬编码120。

算例小，但执行边界完整。模型先读文件获取原文与 hash，然后请求精确替换，再调用可信测试工具，最后给解释。独立 verifier 再次运行测试，不直接相信 final 里的“通过”。这正是大型编码任务仍需要的基本骨架。

运行：

```bash
python -m labs.agents.experiments 26-coding-project
```

预期 before_exit 非零、after_exit 为0、status=finished、success=true，model_calls=4、tool_calls=3。所有文件在临时目录中创建和清理，不修改你的其他项目。没有网络请求，不使用 GPU，不需要任何 API key。

## 逐轮分析真实代码

打开 `capstones.coding_project`。首先写入可信源文件与测试，运行 before 测试确保问题真实存在。若 before 已通过，说明夹具不再覆盖预期 bug，此时就不能把后续“修复成功”当成有意义证据。随后 Workspace 限定文件访问范围，Store 保存 Agent 状态，ScriptedModel 给出四个阶段输出。

第一轮 `read_file` 返回 path、text 和 sha256。第二轮 `replace_text` 携带旧代码片段、新代码片段和期望 hash，避免基于陈旧阅读覆盖文件。第三轮 `test_fixture` 返回退出码、输出、截断标志。第四轮最终文字只解释已经验证的事实。最后项目函数在 Agent 之外再次检查环境，计算 success。

你应该注意测试工具被注册为纯操作只是课程夹具语义中的简化。真实测试可能写数据库、发网络请求、留下缓存或操作外部服务，不能一概标只读。正式编码 Agent 的测试环境应当隔离且可重置，才能把重复测试视为可接受行为。将任意企业测试套件都当“安全纯函数”会产生严重误判。

## 我们实际遇到的缓存故障

开发本项目时，首次测试运行会产生 Python 字节码缓存。若同一秒内把源文件修改成相同字节长度的新内容，基于时间戳与大小的缓存判断可能继续使用旧代码，出现“文件已改、测试还按旧逻辑跑”的现象。这个问题在短小自动化夹具中特别容易触发。

本项目使用全新临时目录，并让所有夹具测试进程带 `-B`，避免初次测试写入 pycache。`-B` 并不保证忽略已经存在的所有旧缓存，因此前提“新建可信夹具”同样重要。面对真实仓库，应调查其缓存策略与测试隔离，不要把删除整个项目缓存当成无脑通用解法，更不要执行不加范围的清理命令。

这个故障说明“代码文件看起来正确”与“测试实际执行了哪个代码对象”也要区分。调试时可以输出被导入模块路径、源码 hash、解释器路径与版本，逐层确认。Agent 工程中的很多失败来自执行环境，而不是模型没有理解算法。

## 从小夹具扩展为真实任务

建议按四级提升。第一级是单函数、明确测试、无第三方依赖；第二级是多个文件、接口变更和回归测试；第三级是已有小型开源项目的一项真实 issue；第四级是多步骤仓库任务，需要阅读文档、定位测试、分析失败并提出最小 patch。

每级都保持同样验收原则：初始失败可复现、修改范围可审查、最终独立验证、保留失败轨迹。不要直接跳到数百万行仓库，用几次失败判断自己“不适合编程”；也不要永远只做一行改错，以为已经掌握大型工程。难度应同时增加代码规模、依赖复杂度和问题不确定性，每次不要把所有维度都拉满。

## 开源项目阅读任务

[mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent) 适合观察较小编码 Agent 的主循环、模型层与环境层。核查时仓库说明当前为 v2，并提供 v1 迁移入口，因此阅读旧教程前先确认版本。不要依赖固定行号；clone 后记录 `git rev-parse HEAD`，用 `rg 'class .*Agent|def step|def run'` 找控制入口，再沿调用追踪模型请求和环境执行。

任务一：找到任务文本进入模型输入的位置，画出配置、Agent、model、environment 的调用关系。任务二：找到错误观察怎样回到下一轮，新增一个可测试的环境错误 fixture。任务三：确认停止条件与预算是数模型步、工具步还是环境命令。任务四：对比自己的 Harness，把最重要的两项差异写成可运行测试，而不是只比较代码行数。

真实项目安装命令、配置 schema 与分支会变化，所以你需要按锁定提交的 README 和 pyproject 配环境。课程不把未经实际检查的某个 pip 版本包装成“永远可运行”。首轮使用你可手工验证的小任务，禁用真实外部副作用，并给模型与环境预算。

## 练习与参考解法

1. **独立复写项目。** 不复制 capstones.py，用现有组件搭建相同闭环。验收：初始失败、修改成功、独立测试通过、预算计数正确。参考：先构造确定性脚本，所有组件正常后再接真实模型。

2. **错误修复方向。** 让模型把公式改成 `price + rate`。验收：测试失败，最终 success=false，即使模型文字说“修复完成”。参考：verifier 只读实际结果，不读模型自评作为评分依据。

3. **多轮修正。** 脚本先做错误 patch、运行测试，再读取最新 hash、改成正确公式。验收：第二次编辑基于新版本，不能复用第一次读取 hash。参考：把每一轮代码与测试观察保存到 trace，分析模型需要哪条信息才能纠正。

4. **保护测试。** Agent 工具只允许编辑源文件，最终测试位于独立位置。故意请求修改测试断言。验收：权限拒绝，最终 verifier 仍能测真实功能。参考：路径根目录限制不足以表达“可读但不可写测试”，需要更细资源策略。

5. **加入真实模型。** 在受控夹具中使用 ChatModel 替代 ScriptedModel，先限模型调用4次、工具8次，再观察是否需要调整。验收：记录实际模型、输入输出与成功率，失败也保留。参考：线上结果不是确定性单元测试，不写成 CI 中必须通过的网络断言。

6. **真实开源小任务。** 选择一个你已能手工理解的 bug，先自己写失败测试，再让 Agent 修。验收：你能解释 diff 的每一行，并证明没有为了通过而放松测试。参考：不知道代码为何正确时，即使测试绿也暂不算完成学习。

7. **跨卷知识助手。** 进入仓库 `projects/README.md`，把有来源与权限的检索工具接到 Harness。验收：检索结果必须由当前权限再次核查，最终答案引用真实证据。参考：这将 A 卷执行机制与 R 卷知识系统连接起来，而不是把 RAG 当一个黑盒工具名。

通过门槛：你能从一个真实失败测试出发，独立组织读取、编辑、测试、修正与验收；你可以解释每处权限和恢复边界，也能在模型给错建议时用代码与证据纠正它。
