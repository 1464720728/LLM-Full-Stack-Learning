# A03 工具契约：从一段模型参数到可以验证的业务动作

一个工具接口至少有六个问题需要回答：允许什么输入，输入在业务上是否合理，谁有权执行，执行会改变什么，返回值表示什么，失败后是否可以重试。只写一个函数名和一句描述，远远不足以回答这些问题。本章从最小加法开始，把输入解析、结构验证、业务约束、权限、输出与副作用逐层展开，最后组合成一个可以独立审查的工具边界。

先修是 Python 字典、函数、异常与 JSON。若你还不能分清字符串 `"17"` 与整数 17，先回基础卷做类型练习；本章仍会用具体输入重讲相关区别。全部主要案例使用合成数据和 CPU，不接真实账目、工单系统或公司文件。这样我们可以大胆制造错误，而不会把学习过程变成对真实业务的试验。

## 第一课：从完整加法工具建立可执行合同

### 合同不是提示词，而是可执行的边界

模型可以根据工具描述生成请求，但它生成的内容仍是外部输入。它可能缺字段、拼错名称、使用错误单位，也可能在读取材料后误把材料里的指令当成用户要求。工具描述提高选择正确动作的机会，执行边界则决定哪些动作实际允许发生。两者相互配合，不能互相替代。

以“创建工单”为例，描述可以告诉模型 title 表示标题，request_id 用来避免重复。但只有数据库唯一约束和业务检查，才能真正阻止同一操作创建两张工单。提示词中写“不要重复”不构成数据库原子性；schema 中写 `type:string` 也不能决定当前用户是否有权创建工单。每一层应承担它能实际验证的责任。

合同可以拆成输入前置条件、执行过程不变量和输出后置条件。前置条件是调用前必须成立的条件，例如金额为正、目标存在、版本匹配。不变量是在执行过程中必须保持的关系，例如扣款与记账总额一致。后置条件是成功返回后应成立的事实，例如新记录已存在且返回的 ID 指向它。失败也需要合同：没有开始、已回滚、已完成但结果丢失，分别意味着什么。

为什么这对 Agent 比普通手写业务程序更显眼？传统调用者往往由开发者固定编写，输入变化范围较小；模型调用者会根据任务、历史和工具描述动态组合参数，容易遇到开发者没有想到的组合。但这并不意味着应该为模型发明另一套随意的接口规则。恰恰相反，明确合同让动态调用者也能在受控边界内工作。

本课程 Tool 对象把 name、description、schema、function 和 side_effect 放在一起。它没有把所有业务规则都塞进一个巨大结构，而是提供最小必要连接：模型可见说明与本地可执行函数有一个对应关系。注册时名字必须唯一，执行时只按这个注册表查找。模型不能通过生成一个 Python 名字就调用进程中的任意对象。


### 先把加法工具的完整合同写出来

我们规定工具 add 接收且只接收 a 与 b 两个字段，两者必须是明确整数，各自在负一百万到一百万之间；工具返回二者的和。这里的范围不是数学加法本身的限制，而是教学接口的资源与行为约束。Python 整数可以很大，但允许任意长度数字会增加解析、序列化和计算成本，也会扩大测试范围。

```python
from labs.agents.contracts import object_schema, Tool

schema = object_schema({
    "a": {"type": "integer", "minimum": -1000000, "maximum": 1000000},
    "b": {"type": "integer", "minimum": -1000000, "maximum": 1000000},
})
add = Tool("add", "计算两个范围受限整数的和", schema,
           lambda args: args["a"] + args["b"])
```

把一个具体输入按顺序检查：文本是否是有效 JSON；解析后的顶层是否是对象；a 与 b 是否都出现；是否包含未声明的字段；每个字段是否为整数；每个值是否落在允许范围；全部通过后才执行加法。这个顺序把不同失败的责任分开，不会在函数内部偶然触发 KeyError 后才发现输入根本没有 b。

对于 `{"a":17,"b":25}`，每层都通过，得到四十二。对于 `{"a":"17","b":25}`，JSON 解析成功，但类型检查失败。对于 `{"a":17}`，顶层类型正确，但必填检查失败。对于 `{"a":17,"b":25,"mode":"fast"}`，两个数字都有效，但多余字段被拒绝。每个反例针对不同性质，你不能用其中一个代替所有输入测试。

你还需要说明成功结果的范围。两个输入都在正一百万时，和是二百万，所以输出范围与单个输入范围不同。如果你把输入 schema 原样拿去验证输出，就可能错误拒绝合法结果。接口设计必须根据函数关系推导输出约束，而不是为了方便复制一份结构。

这里使用纯工具，没有持久状态改变。即便如此，也不能把所有错误都说成调用者的问题。函数作者写错键、返回字符串或产生不可序列化对象，属于工具实现违反合同。区分输入错误与输出错误，能让评测和维护找到正确责任方：模型调整参数无法修复工具作者把 return 写成 print 的 bug。

## 第二课：JSON 解析为什么也是合同的一部分

在进入 schema 验证前，参数通常还是字符串。解析器必须先决定这段字符串代表什么对象。若不同组件对同一字符串的理解不同，后面的检查即使各自看起来正确，整个系统仍可能执行与审核不同的动作。因此“解析成功”必须有统一且明确的规则。

重复键是最直观的例子。文本 `{"amount":10,"amount":1000}` 中同一个键出现两次，有的处理方式保留前一个，有的保留后一个，有的直接拒绝。假设显示界面展示前一个，而执行器采用后一个，审核和执行就面对不同金额。即使你没有独立审核界面，重复键也会让调试记录产生歧义。本课程直接拒绝重复键，避免把不明确输入带入后续层。

`parse_json` 使用 object_pairs_hook 接收对象键值对序列。这个钩子在普通字典建立之前运行，所以能看到重复项。如果先调用普通 loads 得到字典，再检查键是否重复，就已经太晚：重复信息可能已经被覆盖。这个例子说明验证必须发生在信息尚未丢失的边界。

```python
import json
from labs.agents.contracts import ContractError

def unique_object(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ContractError("duplicate key: " + key)
        result[key] = value
    return result

value = json.loads('{"a":17,"b":25}', object_pairs_hook=unique_object)
assert value == {"a": 17, "b": 25}
```

这段代码中的 pairs 不是字典，而是保留顺序和重复项的二元组序列。循环每次取出一个 key 与 value，先检查 result 是否已经有该键，再保存。对于嵌套对象，解析器也会调用钩子，因此重复检查不是只针对最外层。异常一旦抛出，解析不会继续返回一个貌似正常的部分对象。

另外，Python 的 JSON 解码器在默认设置下可以接受某些非标准数值常量。本课程通过 parse_constant 拒绝 NaN 与 Infinity。它们在数学与数值计算中有用途，但工具协议若没有明确允许，应该遵循 JSON 数值边界。尤其 NaN 不等于自身，范围比较可能产生让人意外的结果；把它当普通业务金额或计数会破坏简单不变量。

JSON 解析器也不能代替大小限制。一个语法完全正确、却有几百万个嵌套元素的参数，可能在解析或递归验证时消耗大量内存与时间。课程 Harness 先限制参数字符数，再解析和验证，这个先后关系很重要。生产系统还可能需要字节数、嵌套深度和元素总数限制；不要以为每个数组单独限制长度，就已经限制了整个对象的规模。

## 第三课：对象字段与精确数值类型

### 对象字段、必填与额外字段

schema 中的 properties 描述已知字段怎样验证，required 描述哪些字段必须出现，additionalProperties 控制未声明字段。三者解决不同问题。仅在 properties 里写了 title，并不自动意味着 title 必须存在；只在 required 中列出 title，也不自动为其值定义类型。阅读 schema 时要把这些规则合在一起，而不是只扫一眼字段名字。

本课程 object_schema 默认把给出的所有属性设成必填，并拒绝额外字段。这是一个便于教学的辅助约定，不是所有 schema 系统的普遍默认行为。如果你明确传入 required 列表，可以让某些字段成为可选。可选表示键可以不出现，不表示出现时可以使用任意值；一旦出现，仍要符合对应子 schema。

```python
from labs.agents.contracts import object_schema, validate

schema = object_schema({
    "title": {"type": "string", "minLength": 1},
    "priority": {"type": "integer", "minimum": 1, "maximum": 3},
}, required=["title"])
validate({"title": "检查日志"}, schema)
validate({"title": "检查日志", "priority": 2}, schema)
```

如果 priority 缺失，业务函数需要自己决定默认值。默认值应在哪里产生？一种清楚的做法是在验证之后建立规范化参数对象，再显式填入默认值，并把实际执行参数记录下来。不要让模型以为 priority 是二，而函数内部隐藏地使用三；也不要让不同执行路径采用不同默认值。默认并不是无关细节，它可能改变调度顺序和业务影响。

额外字段拒绝可以抓住拼写错误。模型把 priority 写成 prioirty，如果允许额外字段且函数忽略它，工具可能按默认优先级成功执行，表面没有报错，语义却与请求不同。拒绝额外字段能让错误尽早显现。另一方面，有些公开接口为了向前兼容允许额外字段；这需要明确版本与兼容策略，不能在没有设计的情况下任由字段被忽略。

必填与空值的区别也要手算。`{"title":null}` 中 title 的确存在，所以 required 检查通过；但它不符合 string 类型，因此类型检查失败。`{"title":""}` 的类型是字符串，但长度为零，可能违反 minLength。`{"title":"   "}` 长度大于零，却可能没有业务意义，需要额外的非空白检查。三种输入分别穿过不同层，正好说明结构验证与业务验证不能合并成一句“不能为空”。


### 整数、数字、布尔值与精确语义

Python 类型体系中 bool 是 int 的子类，因此 isinstance 判断与工具业务语义可能不同。本课程 integer 使用 `type(x) is int`，number 使用明确的 int 或 float 并要求有限，boolean 使用 `type(x) is bool`。这种精确判断的目的不是追求某种风格，而是让接口合同与调用者可见的类型一致。

这里还要区别任意精度整数与浮点数。Python 的普通整数没有无穷值，因此 number 对精确 int 直接通过类型与有限性判断，再检查 minimum/maximum；只有 float 才调用 math.isfinite。把巨大整数先送入 math.isfinite 会隐式转换为浮点数，可能抛出 OverflowError，这不是预期的合同错误。当前实现已经避免这种转换，回归测试用一千零一位整数验证：没有最大值时接受，有 maximum=100 时明确产生 ContractError。接受巨大整数不代表任何业务工具都应允许它，工具仍应设置合理范围及参数字符预算。

如果参数是重试次数，true 在 Python 中参与算术可以当一，但它表达的是布尔选择，不是明确计数。若接口错误地接受 true，模型也许是把“是否重试”理解成了“重试次数”。拒绝这种混淆比静默纠正更有利于发现工具描述问题。你可以在另一个工具中明确接受布尔值，但不要靠语言的隐式兼容决定业务含义。

浮点数与整数也不能只看显示效果。17.0 在数学上等于十七，但在本课程 integer 合同下不是 int。某些 JSON Schema 实现对整数的数学定义与此教学子集不同，因此你必须说明验证器实际采用哪种语义。课程的选择是严格区分 Python 解码后的类型；迁移到成熟验证库时，应增加兼容测试，而不是假定同名 integer 总有完全相同的实现行为。

金额适合用明确最小单位整数表示，例如以分为单位的 amount_minor_units，并同时给出 currency。这样可以避免二进制浮点无法精确表示某些十进制小数的问题。但“用整数”不是完整金融设计：你还需要币种、舍入规则、精度来源和业务范围。本课程只用合成账本讲接口，不连接真实账户，也不把一个加减整数演示包装成完整支付系统。

枚举检查也涉及类型。Python 中 true 等于一，如果只是执行 `value in [1,2]`，可能把布尔值当成枚举整数。课程 validate 在比较 enum 时同时要求类型相同与值相同，避免这种暗中合并。对字符串枚举，还要决定大小写是否区分、是否允许别名；如果需要规范化，应显式记录转换，而不是在验证器深处偷偷改值。

数值边界至少有三类：单字段范围、跨字段关系和执行后结果范围。a 与 b 都各自合法，不保证 a 乘 b 的结果满足另外的业务限制；start 与 end 都是合法时间，不保证 start 早于 end。schema 子集能表达第一类的一部分，后两类通常需要业务逻辑。你应为每一类写不同反例，不要把“输入 schema 已通过”当成所有数值性质都已成立。

## 第四课：数组与递归验证的逐步轨迹

假设工具一次创建多个任务，参数是 items 数组，每个元素有 title 与 priority。递归验证的含义是：验证大对象时，遇到小对象继续调用同一个验证函数，只是当前值、schema 和错误路径改变。它不是某种特殊模型能力，而是普通程序对嵌套数据结构的遍历。

```python
from labs.agents.contracts import object_schema, validate

item_schema = object_schema({
    "title": {"type": "string", "minLength": 1, "maxLength": 80},
    "priority": {"type": "integer", "minimum": 1, "maximum": 3},
})
batch_schema = object_schema({
    "items": {"type": "array", "minItems": 1, "maxItems": 3,
              "items": item_schema}
})
validate({"items": [{"title": "检查日志", "priority": 2}]}, batch_schema)
```

手工追踪一个失败输入：items 有两个元素，第二个 priority 是字符串 high。第一层验证路径是美元符号，确认顶层对象；进入 items 后路径成为 `$.items`，确认数组并检查长度；第一个元素路径是 `$.items[0]`，内部字段通过；第二个元素路径是 `$.items[1]`；进入 priority 后成为 `$.items[1].priority`，在此发现类型错误。这个路径告诉调用者究竟要修哪一个位置。

错误路径也是接口的一部分。若每次错误只说“类型不对”，模型可能修改错误字段，开发者也要花更多时间定位。若路径稳定，测试可以直接验证某个坏值被正确归因。不过不要把内部对象地址、数据库路径或密钥拼进 detail；定位需要的是公开参数结构，而不是全部内部实现信息。

数组还要定义顺序和重复的语义。若工具输入是一串执行步骤，顺序重要；若输入是待查询 ID 集合，顺序可能只影响返回排列；若输入允许重复，重复是否表示重复执行还是重复查询？这些问题不是 array 类型自动回答的。你可以通过业务检查拒绝重复 ID，或者明确承诺按输入顺序返回，每个元素保留自己的身份。

批量接口还必须定义失败原子性。三个元素中第二个无效时，是整批拒绝，还是第一个已经执行、第三个继续？对写入工具，两种策略带来的恢复行为完全不同。常见易理解做法是先验证全部元素再执行，减少明显输入错误造成的部分效果；但执行阶段仍可能失败，所以还需事务或逐项结果合同。不能因为用了一个数组参数，就把多项操作误称为原子操作。

## 第五课：字符串长度、空白、编码与规范化

字符串看起来简单，实际上有多个不同的“长度”。Python len 对普通字符串计算代码点数量，UTF-8 编码后的字节数可能更大，用户看到的一个字形也可能由多个代码点组成，模型 token 数量又是另一种分割。课程 schema 的 minLength 与 maxLength 使用 Python 字符串长度，不等于文件字节限制，也不等于精确 token 预算。

为什么要分清？假设工具允许最多一千个字符，你把结果保存到一个最多一千字节的字段里，中文内容可能超出字节上限。反过来，如果为了限制模型输入费用，只按字符数量截断，也只能得到近似控制。接口应明确单位，必要时同时检查编码字节数。变量名写成 max_chars、max_bytes 或 max_tokens，比统一叫 limit 更容易避免误用。

空白规范化也会改变语义。标题可以去掉两端空格，但代码片段中的缩进不能随便删除，密码或签名字段更不能自动修改。你应针对字段定义规范化策略，并在执行前把规范化后的值作为实际参数记录。不能建立一个“所有字符串统一 strip”的通用步骤，然后假定它适用于路径、代码、查询和业务标识符。

Unicode 还可能有不同表示形式看起来相似。对于需要稳定比较的业务标识，可以选择明确的规范化方式；对于原始证据或文件内容，则通常需要保留原字节或原文本，并另外生成搜索用规范化视图。这里的关键不是背某个函数名，而是分清“为了匹配生成派生形式”和“修改原始事实”是两件事。

输入字符串中包含引号、分号或命令语气，并不自动意味着应该拒绝所有文本。工具可能本来就负责保存代码或日志。更可靠的原则是不要把数据拼接成可执行语法：SQL 使用参数绑定，子进程使用参数数组，路径经过明确解析。只靠禁止几个字符无法替代正确的执行接口；任意文本字段也不会因为内容像命令就获得额外权限。

路径尤其说明这一点。schema 可以证明 path 是字符串，但不能证明它位于允许目录。文件系统解释路径时还涉及绝对路径、父目录、符号链接和并发重命名。A08 会逐层分析；本章只要求你把“类型正确”和“资源访问允许”分开，不要给路径加一个后缀检查就宣布已经完成隔离。

## 第六课：验证器的支持范围与递归控制流程

### 验证器支持范围必须明确

课程 validate 支持一个刻意有限的关键字集合：type、properties、required、additionalProperties、enum、items、长度与数值上下界，以及 description。它不支持完整 JSON Schema 的全部组合、引用、格式或条件表达能力。代码首先拒绝未知关键字，正是为了防止开发者以为某条约束已经生效，实际却被静默忽略。

假设你给字符串加了 pattern，想限制工单号格式。若验证器无视 pattern，任何字符串仍会通过，而工具作者可能据此取消后续业务检查。这种“看起来写了规则”的状态比明确报不支持更危险。要新增能力，必须同时扩展实现、输入边界和测试，而不是只把关键字加入 allowed 集合让报错消失。

schema 本身也需要验证。一个开发者可能把 minimum 写成字符串，把 required 写成错误结构，或者在 required 中引用未定义字段。课程验证器主要检查调用值，不是完整的 schema 元验证器。实际系统通常在工具注册或启动阶段先检查工具定义，使配置错误尽早暴露。不要等模型第一次调用，才发现工具作者写了无效合同。

同名关键字在不同实现中也可能有边界差别，例如整数的数学定义、字符串长度口径、格式是否只是注释、额外属性如何与组合规则交互。迁移到成熟库时，应记录采用的规范版本与库版本，并用当前业务反例验证。库更完整并不意味着可以忽略自己的业务规则，反而更需要清楚区分规范保证与应用假设。

工具定义发送给模型服务后，还可能受到服务端支持子集限制。客户端可以验证某个 schema，并不代表模型服务接受同一个 schema；服务接受也不代表客户端不必验证实际返回。最清楚的设计是维护“模型可见 schema”和“本地执行验证”的一致合同，并在无法表达时显式缩小支持范围。不要让两边各自默默解释一套不同规则。

从工程生命周期看，工具合同应有版本。若你把 priority 从一到三改成一到五，旧测试、旧会话和恢复中的待执行调用可能受影响。某些变更只是放宽输入，某些变更改变结果含义或副作用。记录版本不是为了形式完整，而是让已保存的调用能够知道自己原本面对哪一份规则。A10 会把工具版本纳入恢复兼容性讨论。


### 逐行读递归验证器的实际控制流程

validate 的第一个局部集合 allowed 表示本实现认识哪些关键字。`set(schema) - allowed` 计算 schema 中未知的键；集合差不是删除原 schema，而是生成一个新的集合。如果结果非空，函数抛出 ContractError。这个检查发生在值类型检查之前，因为如果规则本身不被理解，继续检查值会制造虚假的确定感。

接着 typ 从 schema 取 type，checks 字典把类型名映射到判断函数。函数对象在这里相当于小型策略：object 检查精确字典类型，array 检查列表，string 检查字符串，number 还要求有限。`checks[typ](value)` 先查出对应函数，再调用它。这与 A01 的工具注册表是同一种基本编程结构，只是这里选择的是验证行为。

若类型未支持或缺失，函数直接拒绝。若类型不匹配，也立即拒绝。这样后面的字符串长度、数值比较和对象键遍历就有了前提。例如只有确认 value 是对象后，才对它调用 keys；只有确认是数字后，才比较 minimum。把类型检查放后面会让内部 TypeError 混进业务错误，使错误归因更混乱。

对象分支先拿 properties，计算缺失必填字段，再计算额外字段。缺失字段通过 required 集合减去实际键集合得到；额外字段通过实际键集合减去已声明属性集合得到。最后只对实际出现且已声明的字段递归验证。可选字段未出现时不会凭空产生默认值，这与前面说明的合同一致。

数组分支要求存在 items schema，然后 enumerate 每个元素，把索引拼进路径。它同时检查数组整体长度。你可以思考检查长度应该放在递归前还是后：若数组明显过大，先拒绝可以减少工作；课程代码顺序主要服务可读性，生产边界应结合资源限制优化。这个优化不能改变哪些合法输入被接受，只应减少不必要计算。

字符串分支检查长度，数值分支检查范围，enum 检查精确类型与值。所有这些函数正常返回时返回 None，含义是“没有发现违反本合同的情况”，不是返回经过修正的新对象。调用者必须理解这是验证函数而非规范化函数，不能写 `args = validate(args, schema)`，否则会把参数错误地替换成 None。

最后一个细节是异常作用域。验证器抛出的 ContractError 表示在调用前发现不符合规则；如果业务函数内部也抛出同名异常，不能因此自动判定业务没有开始。完整 Harness 把前置验证和执行放在两个不同 try 作用域里，利用发生位置而不是异常名字判断副作用是否可能发生。这个结构比在一个大 except 中列出更多异常类型更可靠。

## 第七课：跨字段业务规则怎样实现

很多重要规则根本不属于单字段类型检查。预订开始时间要早于结束时间，批次内任务 ID 不能重复，两个输入相乘后的结果不能超过业务上限，更新必须针对读取过的版本。schema 可以帮助表达一部分关系，但你仍需要把业务不变量落实为明确代码，而不是寄希望于描述文字。

下面的乘法工具分别限制输入范围，再限制乘积。输入范围与结果范围是两层不同合同：

```python
from labs.agents.contracts import ContractError, object_schema, validate

multiply_schema = object_schema({
    "a": {"type": "integer", "minimum": -1000000, "maximum": 1000000},
    "b": {"type": "integer", "minimum": -1000000, "maximum": 1000000},
})

def multiply_checked(args):
    validate(args, multiply_schema)
    value = args["a"] * args["b"]
    if abs(value) > 100000000:
        raise ContractError("product exceeds business limit")
    return {"product": value}

assert multiply_checked({"a": 10000, "b": 10000}) == {"product": 100000000}
```

如果 a 与 b 都是一百万，输入 schema 仍然通过，但乘积超出一亿，业务检查拒绝。这个反例说明“每个字段合法”不推出“组合合法”。你应把这种组合反例写进测试，因为随机生成的小值可能长期碰不到真正边界。

时间区间也需要明确表示。若输入是整数分钟，开始与结束的单位和时区问题暂时被简化，仍要检查 start 小于 end。如果输入是日期字符串，还需要解析格式、时区和业务日历。不要因为某字段名叫 date，就假定它已经是可比较的时间对象；两个字符串按字典序比较只在特定统一格式下才可能符合时间顺序。

规范化之后再验证，还是验证之后再规范化，需要按规则拆开。通常先验证原始类型与允许形式，再执行明确的规范化，最后验证规范化后的业务关系，并记录实际使用的值。例如把标题两端空白去掉后再检查非空；但对代码补丁不能擅自去缩进。把这些步骤写成不同函数，更容易为每种变换建立测试。

业务规则还可能依赖当前状态。expected_version 必须与数据库中的实际版本一致，这不是只检查参数整数范围能完成的。检查与更新应在同一个原子操作或事务中完成，否则检查之后可能被另一个写入者改变。A10 会深入事务；本章先记住：依赖外部可变状态的规则，不能仅靠离线 schema 证明。

## 第八课：身份来自宿主，不能由模型自己填写

假设文档工具参数包含 user_id，模型可以自由选择该字段，然后工具按它读取文档。即使 schema 严格要求 user_id 为字符串，也无法证明这个身份属于当前调用者。模型生成的数据不是认证证据。真实用户或服务身份应来自宿主已经验证的会话、凭据或授权上下文，并通过函数闭包或独立 context 参数传入执行器。

下面使用合成文档演示最小边界。模型只能选择 doc_id，不能选择 tenant 或 user。宿主固定上下文，工具根据上下文检查访问范围。

```python
from dataclasses import dataclass
from labs.agents.contracts import ContractError, Tool, object_schema

@dataclass(frozen=True)
class Caller:
    tenant: str
    user: str

records = {
    "d1": {"tenant": "t1", "readers": {"alice"}, "text": "演示资料"},
    "d2": {"tenant": "t2", "readers": {"bob"}, "text": "其他租户资料"},
}

def make_reader(caller):
    def read(args):
        row = records.get(args["doc_id"])
        if row is None or row["tenant"] != caller.tenant or caller.user not in row["readers"]:
            raise ContractError("document unavailable")
        return {"doc_id": args["doc_id"], "text": row["text"]}
    return Tool("read_doc", "读取当前调用者可访问的文档",
                object_schema({"doc_id": {"type": "string"}}), read)

reader = make_reader(Caller("t1", "alice"))
assert reader.function({"doc_id": "d1"})["text"] == "演示资料"
```

这个例子不实现真实登录系统，它假设 Caller 已由可信宿主建立。frozen 数据类减少本地意外修改，但不是密码学证明，也不是跨进程认证。教学重点在于参数通道与身份通道分开：模型可选择业务对象，不能通过输出一个字段获得另一个租户的身份。

权限检查应与实际操作足够接近。若你在展示工具列表时检查一次权限，之后权限被撤销，真正执行时仍应重新检查相关条件。工具对模型可见只是选择提示，不是永久授权。缓存结果也必须带权限与版本语义，否则一次合法读取的结果可能在权限变化后继续泄露给不再允许的调用者。

错误信息本身也可能泄露资源存在性。示例把不存在与无权限统一表达为 unavailable，是一个可选的接口策略；实际业务是否需要区分，要按用户体验与信息边界设计。无论选择哪种策略，都要保持一致并记录内部诊断，不要把全部数据库行或权限集合直接放进模型可见错误中。

## 第九课：输出契约与序列化失败

输入合法只是开始。工具可能返回错误类型、缺少字段、包含 NaN、包含数据库连接对象，或者输出大到无法进入模型上下文。输出合同回答的是成功结果应当怎样解释。一个检索工具返回空数组，表示查询成功但没有匹配；返回错误对象表示查询未完成。把超时也伪装成空数组，会让模型错误地得出“没有证据”的结论。

本仓库 advanced_solutions 中的 output_checked 给纯工具增加输出 schema。它先执行函数，再验证返回值；验证失败会转成运行错误，区别于调用者的输入错误。该包装器明确拒绝副作用工具，因为副作用已经发生后，输出验证失败不能安全地当作无效果失败处理。这种限制不是不够灵活，而是避免把恢复语义隐藏在一个方便装饰器里。

```python
from labs.agents.contracts import Tool, object_schema
from labs.agents.advanced_solutions import output_checked

input_schema = object_schema({"a": {"type": "integer"}, "b": {"type": "integer"}})
output_schema = object_schema({"sum": {"type": "integer"}})
tool = Tool("add_object", "返回包含sum的对象", input_schema,
            lambda args: {"sum": args["a"] + args["b"]})
checked = output_checked(tool, output_schema)
assert checked.function({"a": 17, "b": 25}) == {"sum": 42}
```

序列化是另一道后置边界。返回值通过某个输出 schema，不代表一定能被所有传输格式编码；反过来，能够编码成 JSON，也不代表符合业务输出合同。课程 Harness 使用 allow_nan 为 false，拒绝非有限数字被编码成非标准 JSON。对于大文件、图像或长日志，通常返回受控引用、摘要、大小与校验信息，而不是把全部内容塞进一个字符串。

输出中的单位、来源和版本也属于合同。例如价格需要货币与最小单位，搜索结果需要文档身份和版本，时间需要明确时区或统一时间表示。若只返回 balance 为一百，模型无法知道是一百元、一百分，还是某个已过期快照。描述里说明单位有帮助，结果字段中显式携带单位更便于程序验证与后续复用。

最后要考虑输出预算达到上限时的语义。工具可能已经完成了写入，只是结果太大不能进入历史。此时应保留执行结果的持久证据并停止或缩减展示，而不是把工具当成未执行后重试。执行合同、结果保存合同与上下文展示合同是三个边界；把它们分开，才能在失败时准确说明已经发生了什么。

## 第十课：错误分类、副作用与幂等

### 把错误分成可以行动的类别

错误结构至少应该让调用者区分“请求不符合合同”“权限不允许”“目标状态已变化”“外部服务暂时失败”“工具实现出错”和“副作用结果未知”。这些类别对应不同后续动作。参数错误可以修改参数，权限拒绝不能靠重复相同请求解决，版本冲突需要重新读取状态，结果未知需要对账而不是盲目重试。

错误码应稳定，错误说明应帮助定位，内部日志可以保留更详细诊断，但模型可见输出不应包含无关秘密或大量堆栈。稳定不代表永远只有一个模糊错误码；它意味着同一种语义不会因为底层换了数据库驱动，就从 timeout 随机变成一个完全不相关的字符串。调用者应依赖公开合同，而不是解析某个 Python 异常的英文文本。

| 失败位置 | 能确认的事实 | 合理下一步 |
|---|---|---|
| JSON 或 schema 验证前后 | 业务函数尚未开始 | 修正输入或解释缺失信息 |
| 权限检查 | 当前上下文不允许该操作 | 停止或走正式授权流程 |
| 版本条件失败 | 读取快照与当前状态不一致 | 重新读取并重新判断 |
| 纯工具执行异常 | 本工具声明无业务写入 | 按错误类别有限重试或修复实现 |
| 写入工具调用后异常 | 效果可能已经发生 | 保留未知状态并对账 |
| 成功结果无法展示 | 执行与展示的状态不同 | 使用已保存结果或受控摘要 |

课程 Harness 把调用前 ContractError 包装成 invalid_arguments。这个标签在教学实现中涵盖未知工具、参数过大、解析和 schema 错误，不是完整企业错误分类体系。纯工具内部异常则返回 tool_failed；写入工具内部任意异常进入 uncertain。你可以扩展更细类别，但不能为了漂亮错误码丢掉发生位置这个关键事实。

为什么不能按异常名字判断是否安全重试？因为一个工具作者可能在完成写入后，发现返回对象不符合自己的检查，于是抛出 ValueError 或 ContractError。名字听起来像输入问题，实际上效果已经发生。只有调用边界知道异常出现在前置验证之前还是进入函数之后。把两个 try 作用域分开，是把这种知识落实成代码结构。

retryable 字段也不能只用一个无条件布尔值表达全部情况。某次超时可能在幂等键保护下可重试，另一次没有幂等保证则不能；版本冲突可能在重新读取后可重试，但原参数直接重试没有意义。更清楚的设计是说明允许的恢复动作及其前提，例如 reconcile_then_retry、refresh_version 或 correct_arguments。A06 会给出具体策略，本章先建立错误类别与行动之间的对应。


### 副作用、幂等与重复调用的接口含义

副作用指调用改变了函数返回值之外的可观察状态，例如写文件、插入记录、发送消息或启动外部任务。只读工具也可能有日志、缓存或计费等附带行为，所以这里的 side_effect 是课程对业务效果的声明，不是宇宙中完全没有任何状态变化的证明。声明必须与实际工具实现一致，不能为了方便重试把写入工具标成纯工具。

幂等表示重复执行同一个业务意图不会不断增加额外效果。它不等于函数每次返回完全相同文本，也不等于工具调用 ID 重复时简单返回缓存。假设用户要创建一张标题相同的新工单，重复标题不一定意味着重复业务；反过来，同一业务请求在不同网络尝试中可能有不同调用 ID。接口需要一个明确业务操作键，并定义相同键与不同参数冲突时怎样处理。

课程 TicketBook 使用 request_id 作为业务键。同一键与同一标题再次调用，会返回已经存在的工单，并通过 created 字段说明这次没有新建。同一键却带不同标题，属于冲突，不能悄悄返回旧结果，也不能创建第二条。这个合同让调用者知道幂等键绑定的是哪一个意图，而不是把任意请求都折叠到同一个缓存槽里。

```python
from labs.agents.tools import TicketBook
from labs.agents.contracts import ContractError

book = TicketBook()
try:
    first = book.create("request-1", "检查演示日志")
    again = book.create("request-1", "检查演示日志")
    assert first["created"] is True
    assert again["created"] is False
    try:
        book.create("request-1", "另一个标题")
    except ContractError:
        pass
    else:
        raise AssertionError("same key cannot silently change intent")
finally:
    book.close()
```

这个例子在一个教学数据库中演示业务键，不承诺完整分布式 exactly-once。并发多连接、跨服务事务、进程中断和回调丢失还需要更完整的恢复设计。重要的是先把接口语义定义清楚：哪个键标识意图，哪些字段必须一致，结果如何区分新建与复用，未知状态如何查询。没有这些合同，后面的持久化技术也不知道要保护什么。

“先查询有没有，再决定是否插入”在并发下不是天然原子。两个执行者都可能先看到不存在，再同时尝试插入。数据库唯一约束能阻止重复记录，但调用者仍需要处理冲突与读取已有结果的路径。A10 会把这种竞争展开；本章在读工具合同的时候，就应主动问一句：去重判断和业务效果是否处于同一可验证的原子边界？

## 第十一课：工具粒度、描述与选择消歧

### 工具粒度决定模型需要承担多少工作

同一个业务目标可以暴露为不同层级的工具。最低层是执行任意 SQL，中间层是设置某对象字段，更高层是把工单分配给某人。能力越通用，模型需要理解的底层结构越多，执行边界也越难验证。能力越窄，任务表达更清楚，但可能需要更多工具种类或更频繁扩展接口。正确粒度取决于目标与环境，而不是简单追求工具数量最多。

以“把工单分配给当前值班人员”为例，execute_sql 要求模型知道表结构、关联条件、事务和权限；set_field 让模型知道字段名，却仍可能绕过状态转换规则；assign_ticket 可以直接检查工单状态、目标人员资格和 expected_version。第三种接口把业务知识放在确定性程序中，让模型主要负责选择意图和提供必要参数。

然而，编码助手的目标常常开放，无法提前为每种修改定义一个业务工具。它可能需要读取文件、编辑文本和执行受控命令。这不是前面原则失效，而是执行环境承担更多隔离与恢复责任。你应把通用能力放在明确工作区、资源预算与可审查变更流程中，而不是拿业务数据库的窄工具规则直接套到所有场景。

工具过细也会产生问题。假设读取一段文档需要先查询目录 ID、再查询文件 ID、再查询块列表、最后读取某块，简单任务可能需要很多轮，任何一步失败都会增加恢复成本。你可以提供一个有清楚边界的 read_document 工具，让程序内部完成机械步骤。模型应负责需要判断的选择，程序应承担已知确定流程；不要为了显示 Agent 在“做很多事”而把机械步骤拆给模型。

粒度还影响观察质量。一个工具返回“成功”，但不返回变更对象、版本或可核验结果，模型很难判断下一步；一个工具返回整个数据库转储，又会淹没重要信息。好的结果设计提供与下一步决策相关的证据，同时保留必要身份和边界。你可以在工具设计前先画下一步要回答什么问题，再反推输出字段。


### 描述、名称与工具选择的消歧

工具名应短而稳定，描述应解释何时使用、接受什么、返回什么，以及关键限制。不要用“一个非常有用的工具”占据模型上下文，因为它没有帮助区分候选能力。也不要把内部数据库缩写直接暴露为名字，让模型靠猜测判断业务意义。名称与描述是接口的一部分，应与实现和测试一起维护。

若同时有 search_docs 与 read_doc，描述应说明前者返回候选片段与身份，后者读取指定版本的正文。若同时有 list_tickets 与 get_ticket，描述应说明批量摘要与单条详情的区别。否则模型可能用搜索结果摘要替代原文证据，或为了查询一条记录反复枚举全部列表。调用函数“没有报错”不代表工具选择合理。

参数描述应解释单位和范围，而不是重复类型。例如 timeout_seconds 说明单位与最大允许值，amount_minor_units 说明币种的最小单位，expected_version 说明它必须来自最近读取结果。对于字段之间的关系，也可以在描述中提示，但最终仍由程序检查。描述帮助模型少犯错，代码保证犯错时不会越过合同。

工具列表越长，选择与上下文成本可能越高。一个可扩展系统可以先按任务与已授权能力选择相关工具，再把较小列表交给模型。这个选择器本身也需要验证：它不能因为检索到一段工具描述就自动授予权限，不能把旧版本工具定义与新实现混用，也不能隐藏完成任务必需的能力后把失败全部归咎于模型。

工具选择策略与执行授权应分开。某个工具暂时不展示给模型，是降低选择复杂度；某个工具展示了，但当前对象不允许操作，执行器仍应拒绝。模型手写了一个未展示的工具名时，是否允许调用取决于你的注册与授权规则，不应根据“它居然猜到了名字”来决定。可见性只是信息组织，能力边界来自明确宿主策略。

## 第十二课：注册时检查与执行时检查

注册阶段可以发现重名、空描述、非可调用实现和错误副作用标记。这些错误与某个具体参数无关，应尽早失败。下面的完整辅助函数展示最小注册检查；它不取代 schema 元验证，也不证明函数体正确。

```python
import inspect
from labs.agents.contracts import ContractError

def register_tools(tools):
    registry = {}
    for tool in tools:
        if type(tool.name) is not str or not tool.name.strip():
            raise ContractError("tool name must be nonempty text")
        if tool.name in registry:
            raise ContractError("duplicate tool name")
        if type(tool.description) is not str or not tool.description.strip():
            raise ContractError("tool description must be nonempty text")
        if type(tool.side_effect) is not bool:
            raise ContractError("side_effect must be boolean")
        if not callable(tool.function):
            raise ContractError("tool implementation must be callable")
        inspect.signature(tool.function).bind({})
        registry[tool.name] = tool
    return registry
```

signature.bind 检查这个函数签名能否接收一个位置参数，并不执行函数体。它能发现把需要两个独立参数的 add(a,b) 错误注册到“接收一个 args 字典”的接口中，但不能证明返回值、异常和副作用符合约定。反射检查有用，却不能代替实际契约测试。

执行阶段检查的是具体请求：参数大小、JSON、schema、业务关系、权限与当前状态。即使工具注册正确，某一次调用仍然可能不合法。输出阶段则检查函数实际返回的结果。把这三个阶段分开后，你可以给错误不同责任标签，也可以在启动时避免重复做与请求无关的昂贵检查。

动态替换工具还涉及一致性。一个运行中保存了旧工具请求，恢复时同名工具实现已经改变，可能产生不同含义。最简单的教学策略是恢复要求使用同一兼容版本；更完整系统会给工具集生成配置指纹并在恢复时核对。不能只看名字相同，就认定合同、权限和副作用语义没有变化。

## 第十三课：四个从症状追到根因的故障案例

故障一：模型传入 priority 为 true，任务却以优先级一执行。最小复现是使用 isinstance(value,int) 作为唯一整数检查。原因是语言类型继承与业务语义不同。修复应在边界拒绝布尔值，并增加 true、false、一、一点零四个对照输入。只测试 true 会抓住当前问题，却不能说明其他边界仍正确。

故障二：工具声明只能修改自己工作区的文本，模型传入一个以 txt 结尾的越界路径却读取成功。原因是把字符串格式当成资源授权。修复需要在执行环境解析路径并检查实际目标，不能继续增加几个文件后缀规则来掩盖。A08 会解释符号链接与并发路径变化为什么还需要额外边界。

故障三：创建工单返回时序列化失败，系统自动重试后产生两张工单。原因是把任何异常都当成无效果失败，同时业务没有稳定幂等键。修复分两层：调用后异常保留 uncertain；业务操作在明确原子边界记录请求键，并提供对账入口。只在日志里写“可能重复”没有改变程序行为，不能算修复。

故障四：检索服务超时，包装器返回空数组，最终答案断言知识库没有相关资料。原因是失败被伪装成成功的空结果。修复输出合同，区分 query_failed 与 succeeded_empty，并让上层选择重试、告知暂时无法检索或使用其他证据。这个例子说明工具结果的语义会直接影响模型结论，不能只检查结果是否能被 JSON 编码。

## 第十四课：十二道契约练习与完整参考答案

### 练习一：逐层判定五个输入

依次检查正常整数、缺少 b、额外字段、a 为 true、a 为超范围整数。参考答案分别是成功、必填失败、额外属性失败、整数类型失败、数值范围失败。你应记录第一个失败层，而不是只写全部失败。这样才能证明程序没有在输入尚未合法时调用业务函数。为工具加一个调用计数器，四个错误输入都应保持计数零；如果计数已经增加，说明检查发生得太晚。

### 练习二：证明重复键在普通字典形成前处理

使用 `parse_json` 解析含两个 a 的文本，期望 ContractError。再使用普通 loads 观察其结果，解释为什么得到字典之后已经无法知道最初重复了几次。完整验证如下：

```python
import json
from labs.agents.contracts import parse_json, ContractError
text = '{"a":1,"a":9,"b":2}'
assert json.loads(text)["a"] == 9
try:
    parse_json(text)
except ContractError:
    pass
else:
    raise AssertionError("duplicate key accepted")
```

不要把普通 loads 的行为当成规范鼓励的业务选择。本题只是展示信息丢失发生在哪一步；课程接口选择拒绝歧义。若你的日志系统保存的是解析后对象，它也无法还原原始重复键，因此需要在允许范围内记录解析失败类别，而不是只保存一个被覆盖后的参数字典。

### 练习三：区分缺省、null、空串与空白

对可选 title 字段分别输入缺省、null、空串与三个空格。若合同要求“出现时为非空白标题”，缺省可以由业务默认处理，另外三者应拒绝。schema 的 string 加 minLength 一只能拒绝 null 与空串，不能拒绝全空白。完整业务补充是先确认字符串，再执行 strip 后检查是否为空；若规范化结果用于执行，还应把它作为实际标题保存，而不是验证一个值却执行另一个值。

```python
def normalize_title(value):
    if type(value) is not str:
        raise ValueError("title must be text")
    result = value.strip()
    if not result:
        raise ValueError("title must contain non-whitespace characters")
    return result

assert normalize_title("  检查日志  ") == "检查日志"
```

### 练习四：实现跨字段区间合同

输入 start 与 end 都是非负整数分钟，要求 start 小于 end，区间长度不超过六十分钟。完整参考解如下。边界输入零到六十应成功，零到六十一失败，十到十失败。不能只分别限制 start 与 end，因为合法的单字段值仍可以组合成错误区间。

```python
from labs.agents.contracts import object_schema, validate, ContractError
interval_schema = object_schema({
    "start": {"type": "integer", "minimum": 0},
    "end": {"type": "integer", "minimum": 0},
})

def interval(args):
    validate(args, interval_schema)
    duration = args["end"] - args["start"]
    if not 0 < duration <= 60:
        raise ContractError("interval must be positive and no longer than 60 minutes")
    return {"duration_minutes": duration}

assert interval({"start": 0, "end": 60}) == {"duration_minutes": 60}
```

### 练习五：给批量任务增加唯一 ID

每个元素除了标题，还要有 id；同一批内不允许重复。结构验证通过后，提取 ID 列表，比较列表长度与集合长度。完整核心如下，可以放在第四课 batch schema 验证之后；实际 schema 需要同时声明 id 为非空字符串。参考语义是整批在执行前拒绝，而不是创建第一项后才发现第二项重复。

```python
def unique_ids(items):
    ids = [item["id"] for item in items]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate item IDs")
    return tuple(ids)

assert unique_ids([{"id": "a"}, {"id": "b"}]) == ("a", "b")
```

这里使用集合要求 ID 可哈希，所以前置 schema 保证字符串类型很重要。若你跳过结构验证，让 id 变成列表，内部 TypeError 就会混入业务错误。每个检查都依赖前面已经建立的条件，这正是明确分层的价值。

### 练习六：发现未支持 schema 关键字

把 pattern 加到一个字符串 schema，再调用当前 validate。参考结果必须是明确拒绝未支持关键字，不能接受任意字符串。若你决定增加正则支持，应先定义匹配是整串还是子串、错误正则怎样处理、是否存在昂贵表达式，以及与长度限制的顺序。只写一行 re.search 并把 pattern 加入 allowed，还不足以说明你实现了某个完整规范的全部语义。

### 练习七：输出合同失败归谁负责

输入合法，工具本应返回 `{"sum":42}`，实际返回 `{"sum":"42"}`。参考答案是工具实现违反输出合同，不能让模型再把参数从整数改成字符串来“修复”。使用第九课 output_checked 包装器会发现这个错误。还应加入一个正常整数返回对照，防止包装器无条件失败。输出合同让依赖该工具的下游不用猜测类型，也使工具版本升级更容易做回归。

### 练习八：模型不能自行选择租户

给第八课读取工具传入额外 tenant 字段，结构验证应拒绝，因为 schema 只有 doc_id。随后请求属于其他租户的 d2，执行阶段应按宿主 Caller 拒绝。两个测试对应不同层：前者阻止未声明参数，后者验证资源权限。即使删除额外 tenant 参数后请求仍能表示 d2，也不能因此允许访问；资源身份与调用者身份是两种不同数据。

### 练习九：相同幂等键的两种重复

重复提交 request-1 与同一标题，返回 created 为 false；使用同一键但不同标题，拒绝冲突。第十课程序是完整参考解。进一步要求你解释为什么“标题相同”不能自动作为幂等依据：用户可能真的需要两张标题相同的独立工单。幂等键来自业务意图标识，而不是从任意相似内容中猜测。若希望从参数生成摘要键，也必须先定义哪些请求在业务上算同一次操作。

### 练习十：检测副作用后的异常

构造一个函数先向内存列表 append，再抛 ContractError。调用前列表为空，捕获异常后列表已有元素。完整反例如下。它证明异常类型本身无法保证没有效果，虽然这个列表不是持久业务系统，逻辑上的先后关系已经相同。

```python
from labs.agents.contracts import ContractError
changes = []
def changed_then_failed(args):
    changes.append(args["value"])
    raise ContractError("failure after effect")
try:
    changed_then_failed({"value": 7})
except ContractError:
    pass
assert changes == [7]
```

把这个函数标记为副作用工具接入 Harness 时，应进入 uncertain，而不是 invalid_arguments。教材已有对应回归测试。修复不能是把异常改名，因为真实函数可能在任何位置抛多种异常；应由执行边界保留调用阶段信息。

### 练习十一：改写一个模糊接口

原工具叫 run，接收 data 字符串，描述只有“处理请求”，返回一百。你的参考改写应明确业务，例如 `get_balance_snapshot(account_id)`，返回账户身份、amount_minor_units、currency、observed_at 和数据版本，并由宿主绑定权限。这里不要求连接真实账户。每个新增字段都要说明解决哪个歧义：单位、币种、时间、对象身份或版本。不能只是把 run 改成更长名字，却保留相同的含糊参数和结果。

### 练习十二：从错误集合反推完整合同

为一个新工具先写十二个坏输入或失败情景，再写 schema 和业务函数。参考集合应覆盖缺字段、额外字段、错误类型、边界数值、重复身份、跨字段关系、权限拒绝、版本变化、输出类型错误、过大结果、写入后异常和重复请求。每个用例标出由哪层处理。这个逆向方法能防止你只围绕一个正常输入设计接口，也能发现 schema 根本不能承担的责任。

## 第十五课：小项目——一个可审查的批量任务工具

项目使用内存或临时 SQLite 数据，不连接公司系统。目标是接收一到三个任务，每个任务有稳定 ID、非空白标题与一到三的优先级；整批输入先验证，拒绝重复 ID；宿主固定创建者；结果按输入顺序返回任务身份、状态和是否新建。第一阶段只实现纯验证函数，第二阶段实现存储，第三阶段接入模型工具注册表。每阶段都保留上一阶段的独立测试。

完整参考可以组合本章的 batch_schema、normalize_title、unique_ids 与 TicketBook，但要明确新合同与原 TicketBook 字段不同，不能把未支持的 priority 默默丢掉。最简单做法是先把任务对象规范化为一个稳定 JSON 载荷作为教学存储值，并在结果中明确返回该载荷；更完整做法是建立包含优先级与创建者的独立表。无论采用哪种形式，都要让实际存储与公开结果一致。

验收首先检查无效整批不会产生任何记录。然后检查同一业务键同一载荷重复调用不会新增记录，不同载荷会冲突。再制造一个结果序列化失败，观察系统是否错误地把操作当成完全没发生。最后把工具的输入与输出字段画成表，每个字段写明类型、单位、默认、来源和失败条件。能够解释这些字段如何对应实际代码，才算真正掌握了工具合同，而不是只会写一段 schema。

本章下一步是 A04。你已经知道一次动作的边界，现在要把多次动作放进一个可观察状态机：什么状态表示待执行，什么状态表示未知，什么时候可以保存，什么事件能证明程序实际走过某一步。工具合同给每个动作清楚的含义，状态机负责让这些动作按可验证的顺序发生。

### 批量项目的完整内存参考实现

下面的版本把“先验证全部输入，再形成候选状态，最后替换状态”完整写出来。它只保证这个单进程、同步、无并发教学调用中的逻辑原子性，不是数据库事务的替代品。候选字典建立失败时，原 records 不变；全部检查通过才进行一次状态替换。由于没有文件、网络和后台任务，这个例子可以专注观察整批拒绝的语义。

```python
from copy import deepcopy
from labs.agents.contracts import object_schema, validate, ContractError

TASK_BATCH = object_schema({"items": {
    "type": "array", "minItems": 1, "maxItems": 3,
    "items": object_schema({
        "id": {"type": "string", "minLength": 1, "maxLength": 40},
        "title": {"type": "string", "minLength": 1, "maxLength": 80},
        "priority": {"type": "integer", "minimum": 1, "maximum": 3},
    }),
}})

class BatchTaskBook:
    def __init__(self, creator):
        self.creator = creator
        self.records = {}
    def create(self, args):
        validate(args, TASK_BATCH)
        normalized = []
        for item in args["items"]:
            title = item["title"].strip()
            if not title:
                raise ContractError("blank title")
            normalized.append({"id": item["id"], "title": title,
                               "priority": item["priority"], "creator": self.creator})
        ids = [item["id"] for item in normalized]
        if len(ids) != len(set(ids)):
            raise ContractError("duplicate IDs inside batch")
        candidate = deepcopy(self.records)
        results = []
        for item in normalized:
            old = candidate.get(item["id"])
            if old is not None and old != item:
                raise ContractError("business identity conflict")
            candidate[item["id"]] = deepcopy(item)
            results.append(dict(item, status="open", created=old is None))
        self.records = candidate
        return results

book = BatchTaskBook("host-bound-user")
args = {"items": [{"id": "t1", "title": " 检查日志 ", "priority": 2}]}
assert book.create(args)[0]["created"] is True
assert book.create(args)[0]["created"] is False
before = deepcopy(book.records)
try:
    book.create({"items": [
        {"id": "t2", "title": "新任务", "priority": 1},
        {"id": "t1", "title": "冲突标题", "priority": 3},
    ]})
except ContractError:
    pass
else:
    raise AssertionError("conflict must reject whole batch")
assert book.records == before
```

最后一个测试特意把合法的新任务放在冲突项之前。如果实现边检查边直接改原 records，t2 会在后面发生冲突时残留；候选状态方案则不会留下它。这是一种针对顺序的反例，比只在第一项就放错误更有价值。你应该继续把冲突移到第一、第二和第三项，确认结果不依赖错误出现的位置。

创建者来自构造函数，没有出现在模型参数 schema 中，因此请求不能通过增加 creator 字段替换身份。返回结果携带实际规范化后的标题，调用者看见的内容与存储一致。重复请求比较的是规范化后的完整意图，而不是只比较标题；优先级不同也会被识别为冲突。这些细节共同构成合同，缺少其中一项都会使“重复同一次操作”的含义变得模糊。

把本例搬到数据库时，不能简单把字典替换为几条独立 SQL 就宣称保留了整批原子性。必须让唯一性、冲突检查和写入处于同一事务边界，并针对并发连接设计测试。你现在应先能用本例解释预期语义，再在 A10 学习怎样用持久化机制实现它。这样学习顺序是先明确要保证的性质，再选择实现技术。
