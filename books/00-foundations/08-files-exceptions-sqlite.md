# F08 文件、异常、上下文与 SQLite：失败时也保持数据正确

> 先修 F06–F07。实验：`python -m labs.foundations.file_io`、`python -m labs.foundations.sqlite_lab`。目标不是背SQL，而是能保存、读取、校验和恢复程序状态。

## 1. 一个函数为什么不能永远假定成功

文件可能不存在、目录不可写、磁盘已满、文本编码错误、JSON截断、数据库约束冲突。异常提供一条把失败传给调用者的路径。`try/except` 不应变成“把错误藏起来”；捕获异常后必须有明确策略：补充上下文、转成业务错误、返回可识别失败，或清理后继续抛出。

```python
try:
    value = int(text)
except ValueError as error:
    raise ValueError("batch_size must be an integer") from error
```

`from error` 保留因果链，帮助你看到外层业务错误来自哪个底层转换。捕获所有Exception后返回None，会让真正错误在更远处变成 `NoneType` 问题，增加诊断距离。

`finally` 无论正常或异常都执行，适合清理。`with` 把常见进入/退出模式组织成协议，文件和数据库经常使用它。注意数据库连接的 `with db:` 主要管理事务，通常不代表退出后连接自动关闭；本课程显式调用 close。

## 2. 原地覆盖的中断窗口

假设原报告是合法JSON。你直接打开最终文件mode='w'，旧内容已经截断；接着程序写到一半崩溃，最终文件既不是旧报告，也不是完整新报告。一个十行脚本在这种情况下可能破坏唯一副本。

更好的模式是写临时文件，成功后替换名字：

1. 在目标父目录创建临时文件。
2. 完整序列化，写入换行。
3. flush把用户态缓冲送给操作系统，fsync请求把文件数据同步到存储。
4. `os.replace` 将临时文件替换到最终路径。
5. 失败时清理剩余临时文件。

为什么临时文件放在同目录？原子rename/replace的保证通常依赖同一文件系统；跨文件系统可能不支持这种替换。为什么还要讲局限？文件数据fsync、目录项持久化、网络文件系统和掉电语义并非完全相同。本实现不承诺所有文件系统上的完整断电持久性，也没有对目录执行fsync；它展示的是避免常见部分写入的原子替换模式。

## 3. 逐行读原子保存函数

`NamedTemporaryFile(delete=False)` 创建唯一临时文件并保留名字，便于关闭后replace。`temporary=None` 让finally知道创建是否已经成功。`json.dump(..., allow_nan=False)` 拒绝NaN/Infinity这类不符合严格JSON数值语义的内容。序列化失败时，不触碰旧报告。

`os.replace(temporary,path)` 成功后，临时名字不再存在，所以finally里的 `unlink(missing_ok=True)` 不会报错。不要把清理写成删除整个目录；清理必须只作用于你明确创建的那个临时文件。

测试先保存 `{"value":1}`，再尝试保存包含NaN的数据，确认报错后旧内容仍为1，目录里也没有遗留临时文件。这比只检查“成功路径能写文件”更接近真实可靠性需求。

## 4. JSON文件什么时候不够

只有一个小配置时，JSON直观、容易审阅。若需要按条件查询许多记录、保证唯一ID、同时修改多个字段、避免重复任务，数据库提供更强的数据组织与约束。

SQLite是嵌入式数据库：应用进程直接使用库访问数据库文件，不需要单独数据库服务进程。它适合本课程的本地任务存储和可复现实验，但并不意味着任意并发写入、大规模分布式场景都适合它。先把事务、索引、约束和参数化查询学透，再迁移到其他数据库更有意义。

一张表可以理解为按模式组织的记录集合。行是一条记录，列是字段。主键标识记录，NOT NULL禁止缺失，CHECK限制合法值，UNIQUE防止重复。这些不是文档备注，而是数据库执行的合同。

## 5. SQL基础与参数化

```sql
CREATE TABLE counters (
    name TEXT PRIMARY KEY,
    value INTEGER NOT NULL CHECK(value >= 0)
);
```

插入用INSERT，读取用SELECT，更新用UPDATE，删除用DELETE。WHERE限制哪些行匹配，没有WHERE的UPDATE会影响所有行。练习只在内存数据库或专用临时文件进行，不拿公司数据库做试验。

```python
db.execute("INSERT INTO counters VALUES (?, ?)", ("tokens", 10))
```

问号是参数占位符，数据通过另一个参数传入。不要把用户输入用f-string拼进SQL语句。参数化让字符串里的引号和SQL片段作为数据处理，而非被当作新语法执行。列名和表名通常不能用普通值参数替代；若必须动态选择，应从固定允许集合映射。

SELECT没有ORDER BY时，不应依赖返回顺序恰好像插入顺序。本课程所有对输出顺序有要求的查询都明确ORDER BY。

## 6. 事务：多个修改作为一个逻辑整体

实验先插入tokens=10并提交。随后一个事务里先把它改成20，再插入value=-1的记录。第二条违反CHECK约束，事务回滚，因此最终tokens仍是10。预期输出 `[('tokens',10)]`。

这是“全成或全不成”的原子性。若你在第一条之后立即提交，第二条失败也无法撤销已提交的20。因此事务边界是业务设计的一部分：哪些动作必须一起成功？对于Agent，“记下工具调用已发出”和“记下结果已收到”往往不能简单塞进同一数据库事务，因为外部网络系统不共享该事务；那需要状态机、幂等键与恢复流程，后续Agent卷会深入。

事务并不解决所有问题。SQLite连接线程约束、锁等待、隔离级别和并发写入都需要理解。教学服务采用串行HTTP服务器简化并发，不宣称是高并发生产架构。

## 7. 错误应该在哪一层翻译

底层json解析器抛JSONDecodeError，数据层可以转换为InvalidRecord并补上行号；CLI层把它显示给用户并返回非零退出；HTTP层把合同错误映射成400。业务核心不应该直接决定终端颜色或HTTP头部。

这样的分层让同一个统计函数可以同时用于命令行、测试和API服务。你以后构建Agent工具时，也应把“执行某个动作”的核心函数，与“把工具调用JSON翻译成参数”的适配层分开。

## 8. 七个练习与详细答案

**F08-1 失败保留旧值。** 在atomic_json序列化阶段触发异常，确认旧文件不变。验收：原值可读取且无临时残留；已有test可作为参考。

**F08-2 捕获边界。** 文件不存在和JSON非法应分别由什么异常表示？答案通常为FileNotFoundError和JSONDecodeError；不要用同一个“读取失败”丢掉原因。

**F08-3 回滚手算。** 在事务内执行value=20后再制造约束错误，预测最终值。答案10；若移除共同事务并提前commit，可能留下20。

**F08-4 参数化反例。** 把 `Robert'); DROP TABLE tasks;--` 当title插入F16任务表。验收：它作为普通标题保存，表仍存在。现有项目测试演示此合同。

**F08-5 查询排序。** 插入三个不同名称，分别按name和value排序。验收：输出由ORDER BY决定，而不是靠当前SQLite行为猜顺序。

**F08-6 唯一性。** 为请求ID建立UNIQUE约束，插入同ID两次。答案：数据库拒绝重复；应用层仍需决定这是可重试成功、冲突还是数据错误，不能把约束异常直接展示给最终用户。

**F08-7 小型检查点。** 用atomic_json保存已处理行数和输入文件摘要。验收：重启时拒绝把旧检查点用于不同输入文件。参考设计：存schema_version、processed_lines、输入内容hash；恢复前校验。仅保存行数会在文件被替换后错误跳过数据。
