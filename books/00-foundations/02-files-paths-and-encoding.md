# F02 文件、目录、路径与编码：从字节一直追到程序读写

本章回答一个看似简单、实际贯穿全栈的问题：程序说“读取这个文件”时，到底怎样找到目标，读到了什么，以及这些内容怎样变成文字。你将亲手建立目录、比较路径、处理 UTF-8、识别链接、追踪打开与删除的区别，并完成一个稳定的小文件清单器。所有破坏性练习都只在自己的 `.practice/f02` 或临时目录里进行。

先修 F01。主实验是 `python -m labs.foundations.paths`。本章会先给出不依赖 Python 高级语法的直觉，再逐步对应到 pathlib 的具体操作；涉及函数的部分可以与 F06 交叉阅读。

## 第一课：一个文件首先是一串字节

### 1.1 名字、格式与内容是三个不同层次

把文件先理解成按位置排列的字节序列：第零个字节、第一字节、第二字节，直到文件末尾。每个字节有八个二进制位，可以表示二百五十六种不同模式。字节本身没有“这是汉字”或“这是图片”的天然标签；不同格式规定怎样解释这些模式。文本编码把字节解释成字符，图片格式规定像素及元数据的编码方式，程序文件也有自己的结构。

文件名是某个目录中的名称，扩展名通常只是名字的一部分。把 `photo.png` 重命名为 `photo.py` 不会转换内容；Python 仍然会读到图片字节，无法因此把它当作合法源码。相反，一个没有 `.txt` 后缀的文件也可以保存 UTF-8 文本。扩展名对人和许多工具很有帮助，但不是内容真实性的证明。

文件格式是生产者与消费者之间的协议。例如 JSON 文本必须满足 JSON 语法；一份文件即使能按 UTF-8 解码，也不代表它就是有效 JSON。解码成功只完成了“字节变成字符”这一层，后面还需要语法解析与业务验证。LLM 工具接收的配置文件、模型 tokenizer 文件和评测记录都会经过这种分层。

### 1.2 文件大小的单位

一个字节不是一个字符。ASCII 范围的常见英文字母在 UTF-8 中通常占一个字节，许多常见汉字占三个字节，但 Unicode 还有其他长度情况。你看到文件里只有几个可见字符，不代表磁盘上只有几个字节。换行、空格和控制字符也会占字节，只是不一定以可见符号展示。

还要区分十进制与二进制单位。某些工具使用千为倍率显示 KB，另一些使用一千零二十四并写 KiB；输出的人类可读缩写有时不够明确。比较两个存储数字时，应确认单位定义，而不是看到都带一个 G 就直接认为相同。课程里的字节题尽量使用整数计数，先避免单位缩写掩盖真实大小。

大文件的逻辑长度和实际磁盘占用也可能不同。例如稀疏文件可以有很大的逻辑范围，但某些区域没有真正分配存储块；压缩文件系统、硬链接和缓存也会影响观察。文件大小是一个属性，存储设备已经使用多少空间是另一个问题，不能让同一个“大小”词语覆盖所有含义。

## 第二课：目录是一种命名结构

### 2.1 从树形结构理解查找

目录把名称关联到下一级文件或目录。Linux 的绝对路径从根目录 `/` 开始，例如 `/home/learner/course/notes.txt` 可以理解为：从根查找 home，再查找 learner，再查找 course，最后找到 notes.txt。路径不是一个神秘地址字符串，而是一组沿命名结构前进的步骤。

一个目录中的名称必须区分开，但不同目录中可以存在相同名字。两个 `config.json` 不一定是同一个文件。你阅读错误提示时，最好记录完整路径或至少记录相对路径的基准目录；只说“config.json 找不到”往往不足以定位问题，因为工程可能有多个同名文件。

在常见 Linux 文件系统中，大小写通常有区别，`Data` 与 `data` 可以是两个名字。Windows 与不同挂载文件系统的规则可能不同，因此跨平台工程不要依赖仅大小写不同的两个关键文件，也不要假定路径比较永远可以简单转为小写。正确处理路径，需要尊重目标文件系统的规则。

### 2.2 文件路径与目录路径

路径字符串本身不保证目标类型。`Path("reports")` 只是描述一个路径，它可能还不存在，也可能是目录，甚至可能被某人创建成普通文件。只有实际查询或操作时，程序才会根据当前文件系统状态得到结果。这个区别与 Agent 的“计划操作”和“已经执行”类似：构造路径对象不等于创建了文件。

文件操作经常要求父目录已存在。向 `reports/day1/result.json` 写文件时，如果 day1 不存在，普通写入不会自动替你建立所有目录。应当先明确创建父目录，或者把缺失作为配置错误。课程中的 `target.parent.mkdir(parents=True, exist_ok=True)` 表示允许建立缺失父级并接受目录已存在，但如果某个同名位置是普通文件，仍应报错，而不是悄悄覆盖。

### 2.3 主目录、根目录与工程根目录

这三个“根”或“家”的说法很容易混淆。Linux 根目录 `/` 是整个路径命名树的起点；用户主目录通常保存该用户的个人文件和配置；工程根目录是项目约定的入口目录，例如包含 README、books 和 labs 的位置。它们可以嵌套，但含义完全不同。

Shell 中的 `~` 常被展开为用户主目录，这种展开通常由 Shell 完成，不是所有程序收到波浪号后都会自动理解。Python `Path("~/notes.txt")` 默认只是包含波浪号的路径表示，需要显式调用 expanduser 才按用户主目录展开。环境变量也类似：一个字符串里写着 `$HOME`，不代表任意程序都会替你替换成主目录。

## 第三课：相对路径的基准是谁

### 3.1 当前工作目录属于进程

相对路径从进程当前工作目录开始解析。你在 Shell 中使用 cd，通常改变这个 Shell 进程的当前目录；随后启动的子进程继承相应目录。Python 在普通文件操作中使用 `"data/input.txt"` 时，通常依据当前工作目录，而不是自动依据源码文件所在目录。

这解释了一个典型现象：同一个脚本从不同位置启动，读取结果不同。脚本代码没有变化，但执行环境变化了。要判断原因，打印 `Path.cwd()` 与源码的 `__file__`，你会看到当前目录和源码位置是两个独立事实。不要用“脚本就在这里，所以它一定从这里读文件”作为推理前提。

```python
from pathlib import Path

print("cwd:", Path.cwd())
print("module:", Path(__file__).resolve())
print("relative target:", Path("data/input.txt").resolve())
```

这段代码应保存为脚本运行，因为某些交互环境没有普通文件意义上的 `__file__`。第一行查询进程工作目录，第二行查询当前源码文件的路径，第三行将一个相对目标按当前目录解析为绝对表示。三者分别回答不同问题。

### 3.2 点与点点的手算

`.` 表示当前目录，`..` 表示父目录。假设当前目录是 `/home/learner/course`，路径 `notes/a.txt` 指向 course 下的 notes；`./notes/a.txt` 含义相同；`../data/a.txt` 先回到 learner，再进入 data。你可以把每个路径段写成操作序列，逐步计算结果。

若路径含符号链接，单纯按字符串消去 `name/..` 可能与实际解析产生差异，因为 name 可能指向别处。基础手算先在没有链接的普通目录树中进行，随后再加入链接观察。不要把“看起来可以约掉”当成所有文件系统语义下都成立的代数规则。

### 3.3 两种合理的路径设计

有些程序约定输入路径相对于调用者当前目录，适合命令行工具，因为调用者通常希望处理自己当前目录的文件。有些程序需要读取随源码分发的静态资源，可能依据模块位置或包资源接口定位。两种设计都可以合理，关键是合同要明确，并在帮助信息和测试中覆盖。

不要把所有路径都硬编码成自己机器上的绝对目录。这样程序在你的机器运行一次可能很方便，却无法移到另一台机器。也不要默认所有相对路径都正确。工程中常见做法是由配置或命令行传入根目录，再在程序内部用明确规则构造其下的路径，这样调用者和实现者都知道基准是谁。

## 第四课：在一个小目录中练习基本操作

从仓库根目录执行以下 Linux 命令：

```bash
mkdir -p .practice/f02/notes
printf '%s\n' 'first line' '第二行' > .practice/f02/notes/example.txt
pwd
ls -l .practice/f02/notes
cat .practice/f02/notes/example.txt
wc -l .practice/f02/notes/example.txt
wc -c .practice/f02/notes/example.txt
```

mkdir 创建目录，`-p` 允许创建缺失父目录并接受所需目录已经存在。printf 按格式输出文字，`%s` 表示一个字符串，换行转义使每个参数单独成行。大于号由 Shell 解释为输出重定向，使 printf 的标准输出写入指定文件。若文件已存在，普通大于号通常先截断旧内容；这就是为何必须在自己的练习目录操作。

ls 的长格式展示类型、权限、大小和时间等元数据，cat 展示文本内容，wc 分别统计换行或字节。元数据与内容是两种观察。一个文件大小为零可能表示合法空输入，也可能表示写入被中断，还可能表示重定向已经截断但后续程序失败。看到零长度后应结合操作历史判断，而不是直接断言文件“坏了”。

追加重定向 `>>` 把输出写到现有内容后面。它不会判断你是否已经添加过同一行，因此重复执行配置追加命令可能产生重复内容。一个看似无害的命令如果不具备幂等性，反复运行就会不断改变状态。这个概念后面会在任务服务与 Agent 重试中再次出现。

在 Windows PowerShell 中，部分同名命令可能是别名或不同实现，参数语义不保证与 Bash 工具完全一致。学习 Linux 文件操作时请在明确的 Linux 或 WSL 环境执行，跨平台 Python 例子则可以在 Windows 原生解释器运行。不要让表面相同的命令名称掩盖实际解释程序不同。

## 第五课：字符、码点、字形与编码

### 5.1 人眼看到的一格不是统一计算单位

“字符”在日常语言中常指屏幕上看见的一个符号，在程序中可能指 Unicode 码点，在文本排版中又可能涉及字形和组合。一个带组合音标的字母可以由多个码点形成；某些表情序列也包含多个组成部分。因此 Python `len(text)` 与用户感知的“几个字”不保证一致。

本课程多数手算先使用简单英文、常见汉字和换行，以便把编码关系算清楚。以后设计文本长度限制时，必须先定义限制的是字节数、码点数、用户感知字符数还是模型 token 数。它们解决不同问题，不能用其中一个直接代替另一个。例如网络协议字段可能要求字节长度，而模型上下文限制关注 token 数。

### 5.2 encode 与 decode 是方向相反的转换

encode 把字符串按照指定编码变成字节，decode 把字节按照编码规则解释成字符串。写文件时往往需要编码，读文本文件时往往需要解码。编码名称是双方必须一致理解的协议，不能让读端凭文件扩展名猜测所有细节。

```python
text = "hello\n学习\n"
raw = text.encode("utf-8")
print(len(text))
print(len(raw))
print(raw.decode("utf-8") == text)
```

字符串包含五个英文字母、两个换行和两个汉字，码点数为九。UTF-8 中本例的英文字母与换行各一字节，两个汉字各三字节，因此总字节数为十三。最后的往返比较为真，说明这段文本在此编码中能无损编码与解码。它不证明任何任意字节都能按 UTF-8 解码，也不证明另一种错误编码会自动被发现。

### 5.3 UTF-8 为什么需要变长

Unicode 定义大量字符的码点，UTF-8 使用一个到多个字节表示不同范围的码点。变长设计让常见 ASCII 文本保持紧凑，也能够表达更广泛字符。你不必在本章背下所有位模式，但应理解：一个文本字符可能跨多个字节，因此按任意字节位置切割文件，可能切在一个字符编码中间。

如果网络每次给你一块字节，不能把每一块都独立当成完整 UTF-8 文本直接解码。例如一个三字节汉字被分成前两字节与后一字节，第一块单独解码会失败。应使用增量解码器，或者先按协议收集完整内容再解码。流式模型响应中的分片与字符边界不同，这个基础问题会在 Agent 流式协议章节直接出现。

## 第六课：错误编码、换行与不可见内容

### 6.1 报错与乱码是两种不同失败

字节不符合所选编码规则时，解码器可能抛出 UnicodeDecodeError。但错误编码也可能接受这些字节，产生看起来奇怪却合法的字符串。后一种失败更容易被忽略，因为程序继续运行了。正确性不能只靠“没有异常”判断，还要核对来源格式和预期内容。

`errors="ignore"` 会忽略某些无法解码的内容，`errors="replace"` 会用替代字符保留错误位置的痕迹。它们在特定展示或恢复场景有用途，但不能作为数据管道默认的“修复乱码”按钮。忽略坏字节可能改变文档内容、破坏引用位置或让日志字段悄悄合并。用于证据与训练数据的流程尤其需要记录发生了什么损失。

### 6.2 换行符也是数据

常见文本中会遇到 LF 与 CRLF 等不同换行表示。文本模式读取可能按语言和平台规则处理换行，二进制模式则保留原始字节。比较文件哈希、网络 Content-Length 或二进制协议时，必须基于真实字节，不能用经过换行转换的文本长度替代。

wc 的行数统计通常关注换行字符数量，而 `splitlines()` 根据文本行边界拆分。内容 `a\nb` 只有一个换行符，却能拆成两行文本。编辑器可能把最后一行也显示为一行，所以你看到的“行数”与某些命令的输出不同。设计 JSONL 日志时，明确每条记录是否必须以换行结束，有助于增量读取与追加。

### 6.3 BOM、制表符与尾部空白

某些文本文件开头可能带有字节顺序标记。对于 UTF-8，部分工具会写 BOM，部分不会；错误处理可能让首个字段名带上看不见的字符。读取外部 CSV 或配置时，若第一个键看起来正确却匹配不上，应检查其 repr 表示和原始字节，而不是继续目测猜测。

制表符与空格在显示上可能相似，但在代码缩进、字段分隔和协议中含义不同。尾部空格也可能影响严格字符串比较。`strip()` 会移除两端某些空白，但它不是所有输入的正确预处理：若文本本身允许前后空格，随意 strip 就改变了内容。应先定义哪些空白属于格式，哪些属于数据。

## 第七课：Path 对象怎样描述与操作路径

### 7.1 描述操作与副作用操作

`Path("notes/example.txt")` 构造一个路径对象，通常不会创建文件，也不会证明它存在。`path.name`、`path.suffix`、`path.parent` 等操作主要解析路径表示；`exists`、`stat`、`read_text`、`mkdir` 等则需要接触文件系统当前状态。区分这两类操作，能帮助你理解哪些代码可能受权限、并发和磁盘变化影响。

使用 `/` 运算符拼接路径，不是执行数学除法，而是 Path 类型定义的路径组合行为。`root / "notes" / "lesson.txt"` 比手工拼斜杠更容易跨平台表达目录层级。若后面拼入一个绝对路径，可能会改变原本预期的根，因此接收不可信输入时必须先建立相对路径合同，不能仅凭写了 root 前缀就假定结果受限。

### 7.2 resolve、relative_to 与相对表示

resolve 将路径解析为绝对形式，并处理可解析的符号链接等。relative_to 则回答“这个路径相对于指定根怎样表示”，它要求路径关系满足相应条件，不是任意两个路径之间都自动求一条路线。不要把“转为绝对路径”和“确认位于根目录内”当成同一个动作：一个逃出根目录的路径也可以被正常解析为绝对路径。

本课程 `contained_path` 先解析 root，拒绝用户提供绝对路径，再拼接并解析 candidate，最后检查 candidate 是否处于 root 下。这是一个清楚的教学合同：输入必须是根目录内部的相对位置。它还没有解决所有操作系统级竞态，也不是完整安全沙箱，后面会单独说明。

### 7.3 stat 与实际文件属性

stat 查询大小、时间、权限等元数据。它反映查询那一刻的状态，之后文件仍可能被修改、替换或删除。你先检查 exists 为真，再调用 read_text，仍可能遇到文件不存在，因为另一个进程在两步之间删除了它。正确程序应处理实际操作的失败，而不是把前置检查当成永不失效的保证。

对符号链接，某些查询会跟随目标，另一些可以查看链接本身。统计文件清单时必须明确是否跟随链接，否则可能重复计算同一内容、进入根目录外部或遇到循环。初学项目可以选择只处理普通文件并拒绝链接，让合同足够简单；以后再按需求扩展。

## 第八课：逐行追踪课程路径实验

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    root = Path(directory)
    target = root / "notes" / "lesson.txt"
    target.parent.mkdir(parents=True)
    target.write_text("hello\n学习\n", encoding="utf-8")
    text = target.read_text(encoding="utf-8")
    raw = target.read_bytes()
    print(len(text), len(raw), text.splitlines())
```

TemporaryDirectory 创建供本次实验使用的临时目录，with 结构在离开块时负责相应清理。F08 会展开上下文管理器语义；此处先观察它如何把实验生命周期限制在一个明确范围内。root 是路径描述，target 通过组合得到目标位置，此时 lesson.txt 还不存在。

mkdir 创建 notes 目录。write_text 把字符串按 UTF-8 编码并写入文件。read_text 进行反向解码，返回 str；read_bytes 不解码，返回 bytes。最后打印的三个结果分别从字符、字节和文本行三个视角观察同一份内容。你应当在运行前算出九、十三与两行，而不是运行后才把结果抄进答案。

离开 with 后，临时目录被清理，所以你不能把其中路径长期保存并期待下次仍能读取。临时目录适合隔离测试与短期中间数据，正式学习成果则应写到你明确管理的持久目录。文件路径是位置，不是内容备份；仅记录一个已经清理的路径无法恢复数据。

## 第九课：打开文件之后，程序持有什么

### 9.1 文件句柄与读写位置

打开文件后，进程获得一个用于后续操作的句柄或文件对象。在 Linux 底层通常还会涉及文件描述符这个小整数标识。文件对象可以保存当前读写位置，所以连续两次 read 不一定都从开头读取。若第一次已经读到末尾，第二次可能返回空内容，这不意味着文件被清空，只是当前读取位置位于结尾。

seek 可以调整位置，但对文本模式中任意字节偏移要谨慎，因为字符可能变长，文本层还可能处理换行。二进制文件的位置语义更直接地对应字节。对大文件逐块读取时，应清楚每个块是字节块还是文本块，以及是否可能跨字符或记录边界。

### 9.2 打开模式决定旧内容怎样处理

常见模式包括只读、写入截断、追加和排他创建。写入模式可能在真正写出新数据之前就截断旧文件，所以即使后续序列化失败，原内容也可能已经丢失。排他创建在目标已存在时失败，适合“必须新建，不能覆盖”的合同。追加适合某些日志，但不等于多个进程同时写任意长度内容都自动形成完整事务。

文本模式返回字符串，需要编码规则；二进制模式返回字节，调用者自己解释格式。不要将 bytes 与 str 随意拼接后期待自动转换。明确的边界转换能帮助你发现协议问题，而自动猜测往往把错误推迟到更难定位的位置。

### 9.3 关闭、刷新与持久化不是一个动作

程序调用 write 后，数据可能先进入用户态缓冲，再交给操作系统缓存，最后才由存储设备持久保存。flush 通常推动语言层缓冲向下传递，fsync 请求操作系统对相应对象执行同步，但真正的持久化保证还取决于文件系统、设备和操作序列。关闭文件会完成必要的资源释放，却不能被简单描述成“所有可能断电情况都绝对安全”。

本课程多数初级练习关注正常运行与常见异常中的完整性，不宣称覆盖任意硬件故障。理解这些层次仍然重要，因为日志报告、模型检查点与 Agent 状态保存都需要明确自己承诺的恢复边界。

## 第十课：复制、移动、删除与链接

### 10.1 复制会产生什么

普通内容复制通常让目标成为另一份可以独立修改的内容副本，但元数据是否保留、是否使用写时复制优化、如何处理链接，取决于具体工具与选项。初学时先在两个小文件中写入相同内容，修改其中一个，再观察另一个是否变化，以建立“独立副本”的基本语义。

不要只根据复制命令返回成功就推断完整备份已经可恢复。备份还涉及保存位置是否独立、内容是否完整、权限是否合适、恢复过程是否验证。对于教材练习，复制小文件足够；对于重要实验结果，应至少能从备份重新读取并核对内容。

### 10.2 移动可能是重命名，也可能涉及复制

同一文件系统内的重命名通常主要修改目录命名关系，不需要重新复制全部内容。跨文件系统移动则可能退化为复制再删除，因而耗时、失败边界和原子性不同。看到 mv 很快完成不能据此推出所有移动都只改一个名字；看到大文件移动很慢，也不必先怀疑文件损坏，应检查是否跨越不同挂载点。

### 10.3 硬链接与符号链接

硬链接可以理解为同一个文件对象的另一个目录名字。在支持的文件系统语义下，通过任一硬链接修改内容，其他名字也能看到变化，因为它们不是独立内容副本。硬链接通常有跨文件系统等限制，目录硬链接也受到特别约束，不应把它当作任意目录树快捷方式。

符号链接保存的是另一个路径。访问链接时，系统继续按目标路径解析。目标可以不存在，形成悬空链接；目标位置变化后，链接也可能失效。相对符号链接的目标通常相对于链接所在目录解释，而不是你当前 Shell 所在目录，这一点值得亲手测试。

### 10.4 删除名字不总等于立刻释放内容

在典型 Linux 文件语义中，删除一个目录项主要移除这个名字。如果仍存在其他硬链接，或仍有进程打开该文件，内容可能继续存在，空间也不一定立即释放。因此“删除了一个很大的日志文件，磁盘使用量没明显下降”可能与仍打开的文件有关。

这并不意味着你应随意杀死所有进程。正确排查需要确认具体文件、具体进程与责任，再按自己的服务生命周期处理。F04 会讲进程观察，F13 会讲容器中的日志与持久化。此处先建立概念：路径名、文件对象、打开句柄是不同实体，删除其中一个关系不一定立刻结束全部关系。

## 第十一课：路径边界与目录穿越

### 11.1 为什么不能只检查字符串前缀

假设允许根目录是 `/tmp/course`，字符串 `/tmp/course-other/private.txt` 也以这段文字开头，但它不在 course 目录内部。路径归属是目录组件关系，不是普通字符串前缀关系。同样，`notes/../../outside.txt` 在最初字符串中看起来从 notes 开始，解析后却可能逃出根目录。

```python
from pathlib import Path

def contained_path(root, relative):
    root = Path(root).resolve()
    part = Path(relative)
    if part.is_absolute():
        raise ValueError("relative path required")
    candidate = (root / part).resolve()
    if not candidate.is_relative_to(root):
        raise ValueError("path escapes root")
    return candidate
```

这段代码与课程实现的核心一致。它不禁止所有含点点的输入，因为 `a/../b.txt` 可以仍在根内；它检查解析后的结果。是否允许这种写法也可以由更严格业务合同决定，但不能把“包含点点”与“必然逃出目录”混成同义词。

### 11.2 链接与检查使用竞态

即使某一刻检查通过，另一个进程仍可能在你真正打开文件之前改变符号链接或目录结构。这种“检查时成立，使用时已改变”的问题叫检查与使用之间的竞态。普通 Path 检查只能提供某一时刻的判断，不等于操作系统层面的隔离保证。

生产级受限文件工具可能需要以目录文件描述符为基准进行操作，限制符号链接跟随，并结合权限、容器或其他隔离机制。基础课程不要求你在这里实现完整沙箱，但必须准确表述当前函数的能力范围。把路径校验函数命名成“绝对安全读取”会误导后续使用者。

### 11.3 程序内部路径也需要合同

即使输入不是来自攻击者，路径合同仍然重要。用户可能误输入绝对路径、把文件夹当文件、写错大小写或传入包含空格的名字。清楚的报错应告诉他违反了哪个规则，而不是把所有错误都包装成“读取失败”。教学工程中的良好边界设计会直接迁移到 Agent 工具接口和检索摄取管道。

## 第十二课：从整文件读取到逐块处理

小文件可以一次读取全部内容，代码简单，适合建立参考实现。但日志、数据集和模型文件可能非常大，直接读入内存会增加资源压力。此时可以逐行或逐块读取，边读边处理。选择方式取决于格式：逐行适合明确定义行记录的文本，逐块适合字节流，二者不能随意互换。

逐行读取并不保证一行一定很小。若一个恶意或异常输入没有换行，单行可能很大，因此对外部数据还需要长度限制。逐块读取也不能直接把每块当一条完整记录，因为记录边界可能跨块。你需要维护尚未完成的尾部状态，等待下一块补齐。这与后面流式 SSE 解析、网络帧处理的思想相同。

```python
from pathlib import Path

def count_lines(path):
    count = 0
    with Path(path).open("r", encoding="utf-8") as stream:
        for _line in stream:
            count += 1
    return count
```

这个函数按文本迭代器提供的行计数，不等同于直接数原始换行字节。它用 with 确保正常结束或异常传播时文件对象按上下文协议关闭。变量 `_line` 的前缀只是向读者表示此处不使用行内容，并不是 Python 自动忽略某种特殊变量。F07 会解释迭代器如何逐次提供数据。

对于完整性校验，可以逐块更新哈希，而不把全部文件读入内存。哈希将任意长度内容映射到固定长度摘要，适合检测意外变化和比较内容身份，但不是文件内容本身，也不是仅凭名字就能推导出来的属性。相同文件名可能内容不同，相同内容可以有不同名字。Git 的内容对象、数据集缓存和检索文档身份都会用到类似区分。

## 第十三课：保存结果为什么需要完整写入策略

直接打开最终结果文件写入时，旧内容可能先被截断；若程序在写到一半时失败，其他读者可能看到半份结果。对于 JSON 配置或学习进度，这种状态通常不满足格式合同。更稳妥的做法是在同一目录创建临时文件，完整写入并关闭后，再用原子替换更新最终名字。

“原子替换”的直觉是读者看到旧版本或新版本，而不是把两者混在一起的半个版本。但它不自动解决所有问题：临时文件必须与目标满足文件系统要求；多个写者可能互相覆盖；断电持久性还涉及同步；业务版本冲突需要额外检查。F08 会给出完整代码并分析这些责任，此处先把保存拆成可失败的多个步骤。

课程的 `atomic_json` 在目标同目录创建临时文件，序列化合法 JSON，刷新并对文件执行同步，然后替换目标，最后清理残余临时文件。它明确没有完成所有文件系统上的断电持久化保证，也没有提供并发写者的版本控制。一个函数可以在其限定合同内有用，同时承认没有解决的边界；这比泛称“原子所以安全”更加严谨。

对学习项目，首先确保保存失败不会悄悄产生看似有效的半份结果。然后根据业务需求逐步增加备份、版本号、并发控制和恢复测试。不要一开始就堆叠复杂机制而不知道每一层解决什么故障，也不要因为数据很小就认为完全没有失败可能。

## 第十四课：四个故障诊断工作台

**工作台一：相对路径漂移。** 在自己的练习目录创建同名文件，然后从两个不同当前目录运行同一脚本。观察程序读取的内容是否随目录变化。记录 cwd、目标绝对路径和源码位置，确认差异来自路径基准。修复可以是明确要求调用目录，或显式接收根目录参数，或按模块资源定位；选择应与工具用途一致。

**工作台二：乱码但不报错。** 用已知 UTF-8 内容建立文件，分别以正确方式读取原始字节和文本。不要随意尝试未知编码后宣布某个看起来正常的结果正确；应拿原始已知文本作 oracle。若处理外部来源，应保留原始字节副本与来源说明，避免不可逆地覆盖唯一数据。

**工作台三：尾行与行数不一致。** 分别创建 `a\nb` 与 `a\nb\n`，比较字节数、换行数量、splitlines 结果和逐行迭代结果。解释为什么不同指标回答不同问题。修复不是强迫所有工具输出同一个数字，而是明确你的数据合同和统计口径。

**工作台四：清单器走出根目录。** 在练习根内创建指向根外测试目录的符号链接，观察跟随链接与拒绝链接两种策略的差别。不要链接到真实敏感目录，只使用自己创建的合成小目录。验收是清楚知道程序列出的每个文件是否属于允许范围，以及这个判断在哪个时刻完成。

**工作台五：文件写到一半失败。** 将一个完整旧 JSON 保存好，再模拟新写入在序列化前或替换前失败。比较直接写最终文件与临时文件替换的差别。实验中的失败应可控，例如使用无法序列化的对象，而不是试图真实制造断电。结果只证明所模拟的故障边界，不能扩大成所有存储故障保证。

## 第十五课：十二道分级练习与完整答案

### 题一：字节与字符手算

预测 `"A学习\n"` 的码点数和 UTF-8 字节数。答案分别是四与八：英文字母一字节，两个本例汉字共六字节，换行一字节。再用 encode 验证。若改成包含组合字符或表情的文本，不能直接沿用“每个可见符号三字节”的简化规则，应实际查看码点与编码。

### 题二：路径逐段解析

当前目录为 `/tmp/course/notes`，解释 `../data/./x.txt`。在不含链接的普通目录树中，先回到 course，再进入 data，点保持当前位置，最终指向 `/tmp/course/data/x.txt`。答案应包含每一步的目录，而不只给最终字符串。加入符号链接后，需要按实际解析语义重新核对。

### 题三：扩展名是否改变格式

把一个 UTF-8 文本复制为不同后缀，比较 read_bytes 的结果。答案是内容不因改名而改变。若某个编辑器采用不同展示方式，那是工具依据名称选择了解释策略，并不表示磁盘字节已经被转换。有效格式仍需由相应解析器验证。

### 题四：相同内容与相同对象

创建内容副本和硬链接，分别修改目标并观察另一名字下的内容。参考判断：普通独立副本不会因为另一份修改而同步；硬链接对应同一文件对象，内容修改可被另一名称观察到。实验依赖系统支持的链接语义，不能在不支持时伪称完成，应记录实际环境与结果。

### 题五：实现明确编码的文本复制

```python
from pathlib import Path

def copy_utf8(source, destination):
    source = Path(source)
    destination = Path(destination)
    text = source.read_text(encoding="utf-8")
    destination.parent.mkdir(parents=True, exist_ok=True)
    destination.write_text(text, encoding="utf-8")
```

这是一种文本复制，可能受到文本模式换行处理影响，不能用于要求字节完全相同的任意二进制文件。若合同是字节副本，应使用 read_bytes 与 write_bytes 或流式二进制复制。答案的关键不是代码短，而是准确说明它复制的是解释后的文本还是原始字节。

### 题六：检查受限相对路径

使用本章 contained_path，测试普通子路径、根内的点点、越界点点和绝对路径。参考结果：普通子路径接受；`a/../b.txt` 在解析后仍在根内则接受；`../b.txt` 逃出根则拒绝；绝对路径按本合同拒绝。还要说明符号链接改变与检查使用竞态未被此函数彻底解决。

### 题七：逐块计算摘要

```python
import hashlib
from pathlib import Path

def sha256_file(path, block_size=65536):
    if type(block_size) is not int or block_size <= 0:
        raise ValueError("positive integer block size required")
    digest = hashlib.sha256()
    with Path(path).open("rb") as stream:
        while True:
            chunk = stream.read(block_size)
            if not chunk:
                break
            digest.update(chunk)
    return digest.hexdigest()
```

循环每次读取有限字节，空 bytes 表示已到末尾。对同一文件用不同块大小得到的摘要应相同，因为分块不改变总字节序列。测试应覆盖空文件、短于一块、恰好整块和含尾块。这个性质与后面分块注意力的“分块方式不改变数学目标”有相似的验证思想，但具体算法完全不同。

### 题八：稳定的小文件清单器

```python
from pathlib import Path

def inventory(root):
    root = Path(root).resolve()
    rows = []
    for path in sorted(root.rglob("*")):
        if path.is_symlink():
            continue
        if path.is_file():
            resolved = path.resolve()
            if not resolved.is_relative_to(root):
                raise ValueError("outside root")
            rows.append({"path": path.relative_to(root).as_posix(),
                         "bytes": path.stat().st_size})
    return rows
```

本例明确跳过符号链接，并按路径排序，使同一静态目录的输出稳定。它仍不保证目录在遍历过程中不被其他进程修改，因此生产清单需要更明确的快照或竞态策略。as_posix 用于统一报告中的分隔符表示，不会改变实际文件系统内容。

### 题九：不要把空文件当成缺失

编写检查分别返回不存在、存在但为空、存在且非空三种状态。参考实现可以先尝试 stat 并捕获 FileNotFoundError，再判断 st_size 是否为零。关键解释是“零字节”与“没有这个名字”不是同一状态；若在检查后立即读取，仍需处理读取时发生变化的可能。

### 题十：增量解码跨字节块

```python
import codecs

raw = "学习".encode("utf-8")
decoder = codecs.getincrementaldecoder("utf-8")()
parts = [raw[:2], raw[2:5], raw[5:]]
text = "".join(decoder.decode(part, final=False) for part in parts)
text += decoder.decode(b"", final=True)
assert text == "学习"
```

前两字节不是一个完整汉字，所以独立解码该块会失败。增量解码器保留未完成尾部，等后续字节到来后再生成字符。final 为真表示输入结束，若仍有不完整序列，应按错误策略处理。不要把最后刷新步骤省掉，否则尾部错误可能没有被正确报告。

### 题十一：文本长度合同

为一个字段设计“最多十个字节”和“最多十个码点”两种验证，给出一个结果不同的例子。参考答案可用四个常见汉字：码点数四，小于十；UTF-8 字节数通常十二，超过十。模型 token 上限又是另一规则，需要 tokenizer 计算，不能在本题中用字符数冒充。

### 题十二：清单器综合验收

在临时目录中建立空文件、中文名文件、含空格文件、嵌套目录和一个链接。调用清单器，手工列出预期路径与大小，再比较结果。新增一个文件后应只多出相应记录；修改内容后大小或摘要应变化；目录自身不应被当普通文件统计；输出应按稳定规则排序。完整交付是程序、合成夹具、预期表和失败说明，而不是只截图一份输出。

## 第十六课：进一步精读文件系统的名字与元数据

### 16.1 目录项与文件对象为何需要分开

在典型Linux文件系统模型中，目录项将名字映射到文件对象的标识，文件对象的元数据描述类型、大小、权限和数据位置等信息。常见的inode概念可以帮助你理解这种分离，但不能把某个inode编号当作跨所有文件系统、跨时间永久唯一的身份。文件被删除并重建后，系统可能复用编号；跨文件系统也可能出现相同数值。

路径是从目录关系一路查找得到的名称，而打开的描述符引用已经解析到的对象。因此，在一个进程已经打开文件后，另一个进程把路径重命名，前者可能仍能继续读取原对象。原子替换也是利用类似区别：路径改为指向新对象，已经打开旧对象的读者不必突然把一半旧内容与一半新内容拼在一起。这个模型能解释许多表面上像“文件路径与程序读取结果不一致”的现象。

硬链接增加的是名字到同一对象的关系，而复制建立的是另一个内容对象。符号链接则是一种保存目标路径的特殊对象，访问时还要继续解析。把三者画成关系表后，你会看到“另一个名字”“另一个对象”“一个会跳转的名字”是三种不同结构。这样理解比只背cp、ln和ln -s更容易迁移到备份、数据缓存与工作区管理。

### 16.2 文件时间戳能证明什么

文件可能记录内容修改时间、访问时间及元数据状态变化时间等。Linux语境中的ctime通常指inode状态变化时间，不应仅凭字母c就翻译成创建时间。某些系统还提供单独的创建时间信息，但可用字段和语义依赖文件系统与平台。读取跨平台元数据时，必须查明实际字段，而不是让字段名称触发不准确的直觉。

时间戳可以帮助缩小问题范围，却不是可靠的内容身份。两个内容不同的文件可能具有相同修改时间，复制工具也可能保留原时间。分辨率、时钟调整和同步策略还会影响比较。若你的缓存正确性要求“内容完全相同才能复用”，只依赖时间戳和大小可能不足，应选择更强的内容摘要或版本机制。

另一方面，给每次小检查都重新计算巨大文件摘要也可能昂贵。工程需要根据风险与成本选择层次：先用元数据快速发现明显变化，必要时再核对内容；或者由写入端维护可靠版本。这个选择应该写进合同。读者不能把一次方便的文件筛选方法误解成对所有并发修改都严格可靠的快照系统。

### 16.3 名字中看不见的差别

文件名可以包含空格和许多Unicode字符，这对用户友好，却会让手工命令解析更容易出错。空格在Shell中可能分隔参数，因此把路径作为一个参数传递时要正确引用；Python列表形式的subprocess参数则能明确保留参数边界。文件名中的换行更会使基于一行一个路径的简单文本处理发生歧义，严肃工具应采用明确的分隔与编码协议。

某些视觉上相同的Unicode文本可能使用不同码点序列。例如组合形式不同的字符在显示时很相近，二进制比较却不相等。是否进行Unicode规范化取决于业务和文件系统语义，不能为了“看起来统一”就擅自重命名用户文件。文本内容的规范化与路径标识的保留也应分开设计。

因此，排查一个看起来相同却匹配不上的名字时，使用repr、字符码点或字节展示比肉眼重复看更有效。对于自己创建的教学工程，可以主动选择简单、稳定、跨平台的命名规则，例如小写英文字母、数字和连字符；这是一种减少无关复杂度的工程约定，不表示系统只能处理英文文件名。

### 16.4 选择文本格式之前先写数据合同

纯文本适合人阅读，JSON适合表达嵌套结构，JSONL适合逐条追加与流式处理，CSV适合相对规则的表格数据。每种格式都有边界。CSV里的逗号、引号和换行需要遵守转义规则，不能用简单split逗号替代完整解析器；JSON数组可以跨多行，不能把每行都当一个完整JSON对象；JSONL则要求每条记录有明确的行边界。

文件格式还不等于业务模式。一个合法JSON可以是数字、字符串、列表或对象；你的请求配置可能只允许对象，并要求某些字段有特定类型。读取流程应分为字节获取、文本解码、格式解析、业务验证四层。每层分别给出错误，能让使用者知道是文件位置错、编码错、语法错，还是字段合同错。

以日志记录为例，若latency字段允许浮点数，就还要说明单位、是否允许缺失、是否接受非有限值、失败请求如何表示。把这些决定留到统计时临时猜测，会导致同一文件被不同脚本算出不同结果。F15的日志项目将把这种合同落实为解析器和测试；本章先要求你在写第一个文件前就意识到格式和语义需要共同设计。

### 16.5 清单统计中的重复与成本

假设目录里有两个不同名字都通过硬链接指向同一份十字节内容。按路径列清单会得到两条记录，逻辑大小相加为二十；按底层对象去重可能只计算一次。两种统计都可能有用，但回答的问题不同：前者问用户能通过多少个路径看到多少逻辑内容，后者更接近独立存储对象的视角。再加入符号链接、稀疏区域和文件系统压缩后，简单求大小总和更不能自动等于实际占用。

因此清单器应在报告里写清楚统计口径。若作数据集样本清单，两个路径是否算重复样本还要看业务定义；若作存储诊断，需结合文件系统工具；若作备份验证，可能需要同时保存路径、类型、大小和摘要。不要让一个没有定义的total字段承担所有含义。

递归遍历本身也有成本。目录包含百万个小文件时，查询元数据和打开文件的次数可能成为主要开销，即使总字节量不大。反过来，只有几个巨大文件时，读取全部内容计算摘要可能更昂贵。优化前应先区分是目录遍历、元数据查询还是实际字节读取占时间，再决定缓存或并发策略。这里的分析会为后面性能测量建立直觉：数据量不只由一个文件大小数字描述，还包括对象数量与操作方式。

最后，为清单器建立一个可重复夹具：三层目录、两个同名但不同路径的文件、一份空文件、一个中文名文件和一条链接。先手工写出按路径统计的预期，再运行程序；改变链接策略后重新写预期。你会发现，测试的核心是先确定语义，而不是让程序输出一个看起来整齐的表格就宣布完成。

再把整个夹具复制到另一个临时根目录运行一次。相对路径清单应保持一致，绝对路径部分可以变化。这个检查能识别代码中意外硬编码了个人目录的情况，也能验证报告是否真正使用约定的根目录作为基准。

## 完成门槛

你应能把一条路径分解为基准与组件，把一次文本读取分解为定位、打开、读取字节、解码和业务解释，并说明每一步可能出现什么错误。你还应能区分文件名、文件对象、链接和打开句柄，独立编写清单器与逐块摘要函数，解释为什么路径校验不是完整沙箱。

继续学习 F03 时，你会看到 Shell 如何把文件名、空格、通配符和重定向组织成命令参数；进入 F08 时，会进一步把异常与原子保存接到本章的文件生命周期。不要把这些内容当作互不相关的命令表，它们共同构成程序与外部数据交互的基础。
