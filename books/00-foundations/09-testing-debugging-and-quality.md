# F09 测试与调试：把“看起来对”变成证据

> 先修 F06–F08。实验：`python -m labs.foundations.debugging`。本卷测试：`python -m unittest discover -s tests -p 'test_foundations*.py' -v`。

## 1. 测试不是为了让屏幕变绿

测试把某些输入、预期性质和失败方式写成可重复执行的检查。它不会自动证明程序绝对正确，也不能用覆盖率百分比代替业务判断。一个函数被执行过，并不代表它处理了所有重要边界。

最有价值的起点是把需求改写成具体合同。对batches：所有输入元素恰好出现一次；顺序保持；每批不超过size；非法size拒绝。对Budget：超额操作失败后状态不变。对文件保存：失败不能破坏旧报告。这样的测试即使实现重写仍然成立。

相反，如果测试只是把实现中的每行算法复制一遍算预期，它可能和实现一起犯同一个错。矩阵运算可以用手算小矩阵、独立参考算法和数学不变量交叉检查；API状态机可以用明确的状态转换表做预期。

## 2. 一个最小错误怎样被定位

`debugging.py` 故意给出 `broken_mean(values)=sum(values)/(len(values)-1)`。对[2,4,6]，错误结果是6，正确均值是4。为什么错？分母用了样本方差里常见的n-1，但均值定义需要n。名字相似的统计公式不能混用。

第一步建立失败样例：输入[2,4,6]应为4。第二步缩小：单元素[9]应为9，但错误实现除零。第三步定义空输入：没有均值，抛ValueError比返回0更明确。第四步修复分母并加空检查。最后保留三个测试，防止未来修改又引入同类错误。

调试的基本循环是：复现→观察→假设→只改变一个因素→验证。不要一次改十个地方后只知道“现在好了”。也不要把打印所有变量当唯一策略；打印应围绕你正在检验的假设。

## 3. unittest 的最小结构

```python
import unittest
from labs.foundations.debugging import mean

class MeanTests(unittest.TestCase):
    def test_regular(self):
        self.assertEqual(mean([2, 4, 6]), 4)

    def test_empty(self):
        with self.assertRaises(ValueError):
            mean([])
```

继承TestCase让测试框架发现断言与结果；test_开头的方法是独立测试；每个测试应能单独运行，不依赖另一个测试先改变共享状态。`setUp`和`tearDown`用于建立、清理每个测试的资源，F16项目用它们创建内存数据库。

`assertEqual`用于精确相等；`assertAlmostEqual`适合某些浮点数量；数组使用NumPy专门比较函数。近似相等必须选择合理容差，不应为了让测试通过随意放大容差。绝对误差适合接近零的值，相对误差适合尺度变化的值；内核卷会更详细讨论。

## 4. 单元、集成与端到端测试

单元测试聚焦一个小合同，通常快且容易定位；集成测试检查模块边界，例如解析后写数据库；端到端测试经过真实入口，例如启动HTTP服务器再发请求。三者各有价值，不是层级越高越高级。

本卷自动测试不需要外部网络：HTTP服务用纯dispatch函数验证状态码和数据合同，数据库用内存或临时文件。这样测试不会因为服务器无法访问而随机失败。真正socket层的行为留在F16手动本地演练中验证，报告中不能把“dispatch测试通过”说成“所有HTTP传输细节已实测”。

当使用真实模型API时，响应随机且有费用，核心逻辑应先用固定假响应测试，再加少量显式联网集成测试。以后Agent卷将沿用这套边界。

## 5. 边界、反例与性质测试

常见边界包括空集合、单元素、零、负数、重复、最大长度、非法类型、Unicode、缺字段、未知字段、失败后重试。不要机械给每个函数填满同一清单；从合同推导哪些边界有意义。

batches测试遍历count从0到19、size从1到6，检查扁平化后等于原序列。这是有限范围的性质测试，不是穷尽证明，但能覆盖大量尾批组合。你可以再加随机样例，不过要固定随机种子并保留失败输入，否则难以复现。

对softmax，输入统一加常数后结果应不变；对去重保序，第一次出现位置应保留；对幂等操作，执行两次与一次最终状态相同。这些性质常比大量硬编码预期更能揭示设计错误。

## 6. 读 traceback 的方向

traceback列出调用链，最下面通常显示最终异常类型和消息，往上看谁调用了谁。先找属于自己项目的最靠近错误的调用点，再检查它接收到的输入。不要因为栈顶出现某个库就直接认定“库坏了”；库可能只是拒绝了你传入的非法数据。

在关键点放 `breakpoint()` 可进入调试器，观察变量、单步执行和调用栈。它会暂停程序，不能不小心留在自动化测试或后台服务里。短函数用打印和测试就足够；复杂状态机使用调试器更有价值。

日志与调试器也不是互相替代：线上无法随意暂停的服务依赖日志和指标；本地最小复现适合断点。日志中记录request_id、阶段和错误分类，往往比打印整段包含密钥的请求更有效。

## 7. 复杂度作为另一种“正确性边界”

一个函数输出正确，但对十万条记录耗尽内存，也不符合实际需求。时间复杂度描述输入规模增长时工作量如何变化，空间复杂度描述额外存储需求。线性扫描O(n)不代表每条数据固定一秒；它描述增长关系，不是具体硬件计时。

日志项目为了精确排序算p95保存所有有效记录，内存O(n)，排序O(n log n)。它明确写出这个限制，而不是因为读取用生成器就宣称全流程常数内存。若数据很大，要选择流式近似分位数、外部排序或数据库聚合，这是有具体约束的拓展任务。

## 8. 七个练习与答案

**F09-1 红绿修复。** 先为broken_mean写失败测试，再修复。验收：保留空输入与单元素测试。答案见mean参考实现；不要只改预期值迎合错误代码。

**F09-2 失败状态。** 写测试证明Budget超额失败不会修改used。答案：先consume(7)，捕获consume(4)异常，再assertremaining=3。

**F09-3 性质测试。** 对batches多个长度和size验证扁平化不变。验收：一个故意丢尾批的版本应被测试抓住。

**F09-4 测试独立性。** 设计两个测试共享同一列表导致顺序依赖，再改成每个测试创建新对象。答案：隔离fixture；不要通过给测试排序来掩盖共享状态。

**F09-5 数值比较。** 比较0.1+0.2与0.3。验收：解释二进制浮点表示，选择近似断言；同时说明整数计数不该随意用近似比较。

**F09-6 假依赖。** 为一个“请求模型后解析结果”函数传入固定响应的假client。验收：测试不联网且能覆盖非法JSON响应。答案：依赖注入，把网络从核心合同中移出。

**F09-7 测试盲区说明。** 写一段你的验证报告：验证了哪些输入与环境，没验证什么。参考：CPU/NumPy测试通过，没在Windows原生、WSL、Docker和GPU上全部重跑；不能写成全平台保证。

## 掌握门槛

你能先写出失败样例，再定位和修复错误；测试能够独立运行、覆盖关键边界，并且你能诚实解释测试证据的范围。达到这个门槛，才开始修改推理框架和Kernel更稳妥。
