# F05 网络、SSH、HTTP 与 JSON：从一根连接到可验证的 API 请求

你会在本机、WSL、服务器和容器里运行不同程序，也会调用远端模型 API。最常见的困惑不是模型本身，而是“地址是什么”“端口在哪里”“为什么服务器上能访问、本机不能”“收到四百错误究竟算没连上还是连上了”。本章从最小通信模型开始，逐层建立地址、连接、协议、认证与数据合同的理解。

默认实验 `python -m labs.foundations.http_message` 和 `python -m labs.foundations.json_contract` 完全离线。实际网络练习只访问你自己控制的课程服务，并由你显式启动；本章不会自动调用付费 API，也不需要 GPU。

## 第一课：网络连接的是运行中的程序

### 1.1 先从同一台机器上的两个程序想起

一个程序生成请求，另一个程序接收并返回结果。二者需要约定在哪里找到对方、怎样建立通信、怎样划分消息、怎样解释字段，以及遇到失败时怎么办。即使它们都在同一台电脑上，这些问题仍然存在；把服务器放到远端，只是又增加了网络路径与访问控制等因素。

客户端与服务器描述的是一次交互中的角色。客户端主动发起请求，服务器在某个地址等待并处理请求。同一个程序可以在一段关系里当服务器，在另一段关系里当客户端。例如你的 Agent 接收用户任务时像一个服务端，调用模型 API 时又成为客户端。不要把“服务器”只理解成一种更大的物理电脑。

### 1.2 地址、端口与协议各回答一个问题

网络地址帮助确定通信目的地的网络位置，端口帮助操作系统把传输交给对应的服务，协议规定双方如何解释交换的数据。知道某台机器的地址，不等于知道它运行了什么服务；知道一个端口开放，也不等于知道该端口使用 HTTP、SSH 还是其他协议。

可以把地址与端口组合看作一个连接目标，但还需要协议和应用路径才能表达完整请求。浏览器访问某个 HTTP 服务与 SSH 客户端连接同一台主机，可能使用完全不同端口和消息格式。把 HTTP 文本发给 SSH 端口，通常不会因为“网络能到达”就得到有意义的网页响应。

## 第二课：IP 地址、网卡与路由的直觉

### 2.1 一台机器不一定只有一个地址

机器可以有多个网络接口，每个接口可能配置多个地址。物理网卡、回环接口、虚拟网络和容器网络会形成不同视角。因此“服务器的 IP”在复杂环境中不一定是唯一值，你需要确认客户端应该从哪条网络路径访问哪个接口。

IPv4 常写成四个十进制数，每段对应八位，总共三十二位。它不是任意四个整数都合法。IPv6 使用更长的地址空间和不同文本表示。本章实际练习主要用 IPv4 回环，目的是减少无关配置；不要因此认为所有生产地址都可以套用四段数字的解析规则。

### 2.2 本地网络与下一跳

主机根据路由规则决定把数据交给哪个下一跳。目标在直接连接的网络里时，可能通过本地链路直接发送；目标在其他网络时，通常交给网关继续转发。应用一般不需要自己实现每一跳，但排查网络不通时，要知道“发起请求”并不意味着数据能自动越过所有网络边界。

子网前缀表达哪些地址属于一个范围。比如一个二十四位前缀的 IPv4 网络，前三个字节通常共同表示网络部分，剩余部分区分范围内地址。实际可用地址、广播与特定网络规则还需要按环境理解。这里的目标是读懂配置中的范围含义，而不是让你随意修改公司路由。

### 2.3 私有地址与公网地址

某些地址范围用于内部网络，不会按普通公网路由方式在互联网中直接访问。公司局域网、家庭路由和容器网络常使用这类范围。一个内部地址在服务器所在网络可达，不代表你当前电脑所在网络也可达，可能需要 VPN、跳板或其他被授权通道。

NAT 等机制可以转换地址与端口映射，让内部连接通过网关与外部通信。但“内部程序可以访问外网”不自动意味着外部程序可以反向连接内部服务。入站访问还涉及映射、防火墙和监听配置。把这两种方向分清，能解释很多“服务器能下载模型，为什么我却访问不了它”的问题。

## 第三课：回环地址与监听地址

### 3.1 127.0.0.1 永远需要问“谁的自己”

回环地址指当前网络环境中的本机。你在 Windows 浏览器访问它，通常访问 Windows 当前网络视角的本机服务；在远端 SSH 会话里运行 curl 访问它，是远端服务器自己；在具有独立网络命名空间的容器里访问它，通常是容器自身。它不是一个全局代号，不会自动指向“我想访问的模型服务器”。

这也是跨环境排错时必须先确认执行位置的原因。同一条含回环地址的命令，在本机和服务器可能访问两个完全不同的程序。即使端口数字相同，也不代表同一服务。先说清命令在哪台机器和哪个网络环境执行，再讨论地址意义。

### 3.2 0.0.0.0 用于监听时的含义

服务绑定所有 IPv4 接口时，常用零地址作为通配监听地址。它表达的是服务愿意在哪些本地接口接收连接，而不是给远端客户端填写的万能目标地址。客户端通常使用实际可达的 IP 或域名。

绑定范围与实际可访问范围不是同一件事。服务监听所有接口后，防火墙仍可能阻止连接；容器内部监听后，宿主机还可能需要端口发布；服务可以接到请求，也可能因为鉴权而拒绝处理。反过来，绑定回环通常限制直接网络入口，但其他转发机制仍可能建立访问通道。

基础课程默认使用回环地址，让你先在最小环境中学习协议。需要局域网访问时，再明确接口、访问者与数据边界。不要把“我希望另一台自己的电脑访问”直接等价成“对所有网络来源开放且无需认证”。

## 第四课：端口、监听与连接

### 4.1 监听端口属于运行中的服务状态

服务器程序调用相应网络接口，在一个地址和端口上监听。若没有程序监听，客户端不能仅凭知道端口数字就获得服务。配置文件里写了端口，不代表服务已经启动成功；启动程序打印了一行配置，也不代表它已经完成模型加载并开始接收请求。

```bash
ss -ltn
```

这类命令可以观察本机的 TCP 监听状态。列表反映执行命令所在网络环境，容器内外可能不同。某些详细进程信息需要相应权限，不能因为未显示进程名字就断言不存在监听。观察应与服务日志、启动状态和实际请求结合。

### 4.2 端口冲突怎样发生

两个服务试图在冲突的地址与端口组合上监听，后启动者可能失败。若一个服务只绑定特定接口，与另一个绑定所有接口的服务之间，冲突关系还要看具体系统和选项。初学时不要靠反复换随机端口掩盖自己不知道已有服务是谁，应先观察并确认归属。

客户端连接通常也使用自己的临时源端口。一次 TCP 连接需要区分源地址、源端口、目标地址和目标端口等信息，因此许多客户端可以同时连接同一服务器监听端口。服务器的一个监听端口不意味着只能处理一个连接，也不意味着应用层一定支持任意并发。

### 4.3 连上了不等于处理完了

连接建立表示传输层某些步骤成功，不代表 HTTP 请求已被解析，也不代表模型已经生成结果。你可能连接成功后排队很久，或在发送正文时失败，或收到合法 HTTP 错误。排查时需要按阶段记录，而不是把整个过程都叫“连接时间”。

## 第五课：TCP 提供字节流，不替你划分业务消息

### 5.1 可靠有序与应用成功的区别

TCP 为双方提供有序字节流等传输语义，处理分段、确认和重传等机制。应用看到的数据不需要与底层每个网络分组一一对应。但传输可靠不等于业务操作只发生一次，也不等于对方一定会按你的意图处理数据。服务器处理成功后响应丢失，客户端仍可能不知道结果。

你调用一次发送，不保证接收方一次读取就得到恰好同样长度的消息；接收方一次读取也可能包含多个逻辑消息的一部分或全部。应用必须定义消息边界，例如固定长度、长度前缀、分隔符或更高层协议。把一次 recv 当作一条完整 JSON，是许多初学网络程序的典型错误。

### 5.2 一个分片例子

假设要传输文本 `hello\nworld\n`，接收端可能先拿到 `hel`，再拿到 `lo\nwor`，最后拿到 `ld\n`。如果协议规定换行结束一条消息，解析器需要保留尚未完成的尾部，等下一块补齐，才能依次产生 hello 与 world。每块输入的边界不是业务消息边界。

若文本采用 UTF-8，字节块还可能切在汉字编码中间。因此正确的流式处理要同时考虑字节到字符的增量解码，以及字符流到消息的边界识别。F02 的增量解码与这里的消息组装是两个相邻但不同的状态机。

### 5.3 超时与关闭

连接可能在不同阶段超时：无法建立、建立后长期无数据、整体请求超过预算。对端正常关闭与网络突然断开也有不同观察。应用需要决定哪些情况可重试、哪些需要查询已有任务状态，以及如何限制无限等待。一个统一的“网络错误”标签往往不足以支持正确恢复。

HTTP/3 等协议使用不同底层传输机制，本章的 TCP 链条不是所有网络应用的唯一实现。当前学习目标是把常见 HTTP/1.1 与 TCP 场景看清，再理解更复杂协议如何改变部分机制而保留应用合同。

## 第六课：DNS 把名字连接到地址

域名让人和应用使用相对稳定的名称，而不是记住某个具体地址。DNS 查询可以返回相应地址记录等信息，但一个名字可能有多个地址，结果也可能随配置、缓存和时间变化。域名不是一台物理机器永久不变的别名，负载均衡与服务迁移会使关系更复杂。

解析失败发生在建立目标连接之前。若域名无法解析，去修改 HTTP 路径通常没有帮助。若直接使用 IP 可连接而域名失败，应该检查名称解析和相应网络配置；但对 HTTPS，直接替换成 IP 还可能触发证书名称不匹配，因此不能把这种测试当成完整等价请求。

缓存提高效率，也可能让不同机器暂时观察到不同解析结果。排查时记录实际解析到的地址和时间，比只说“这个域名能不能用”更精确。不要在没有理解的情况下全局修改 DNS 或绕过公司网络规则；基础课程只要求你识别这层责任。

## 第七课：TLS 解决传输中的身份与保密问题

HTTPS 在 HTTP 语义之外加入 TLS 等安全传输机制。它通常提供传输加密、完整性保护和对端身份验证。服务器证书中的名称需要与客户端访问目标匹配，信任链需要满足客户端验证规则。TLS 成功不代表应用账号已经登录，API Key 与业务权限仍属于更高层。

证书验证失败可能来自名称不匹配、证书过期、信任配置或中间代理等原因。把验证关闭可以让某次请求继续，但同时改变了身份保证，不能作为默认修复。正确排查应记录具体错误，核对目标名称与环境信任配置，再按授权方式修正。

加密传输也不意味着客户端日志可以随意打印密钥，或者服务端收到数据后永远不会泄露。TLS 保护的是特定传输边界，应用存储、日志、工具调用和权限还需要各自设计。分层理解能够避免把一个安全机制误当成对所有风险的总开关。

## 第八课：把 URL 拆成有意义的部件

```text
http://127.0.0.1:8765/tasks?status=todo&limit=2#local-note
```

scheme 指明使用的协议方案，host 指定主机名称或地址，port 指定端口，path 指向应用资源或路由，query 携带查询参数，fragment 通常由客户端处理，不作为普通 HTTP 请求目标的一部分发送给服务器。课程 `http_message.describe` 会离线拆解这些字段。

查询参数可以出现重复键，例如同一个过滤字段给出多个值。因此 Python 的 parse_qs 常把值保存为列表，而不是假定每个名称只有一个字符串。具体 API 是否允许重复、怎样解释重复，仍由应用合同决定。解析器保存可能性，不等于业务一定接受所有形式。

URL 中某些字符需要百分号编码，路径与查询也有不同语义。不要用简单字符串拼接把任意用户文本直接塞进 URL，而应使用相应编码工具。特别是输入含空格、问号、井号或与号时，未编码内容可能改变原本的结构，而不仅仅成为一个字段值。

课程描述函数拒绝把用户名密码放进 URL，并只接受明确的 HTTP 或 HTTPS 方案。它不发送请求，也不证明目标可达。这是“解析合法性”与“网络实际执行”分离的例子，不能因为 URL 拆解成功就宣布 API 已连接。

## 第九课：HTTP 请求由哪些部分组成

### 9.1 方法与请求目标

HTTP 请求包含方法、请求目标、字段和可选内容等结构。GET 常用于获取资源，POST 常用于提交处理或创建，但真正业务效果由服务实现与协议合同共同决定。不能仅凭方法名就推断服务器绝不产生任何外部变化，也不能把所有 POST 都当成同一种创建操作。

同一个主机与端口可以通过路径区分多个接口，例如健康检查、任务列表和任务创建。收到四零四通常说明已经有 HTTP 响应，只是相应资源或路由未按预期找到。它与“没有任何服务监听端口”发生在不同层，修复动作也应不同。

### 9.2 头部与正文

Content-Type 告诉接收者内容的媒体类型，Authorization 等字段可以传递应用认证信息，Accept 表达客户端希望接收的表示类型。字段名和具体语义遵循协议与 API 合同，不能把任意字段都当作自由备注。重复字段、大小写与合并规则也有协议细节，初学客户端应使用成熟库而不是手工拼接全部报文。

正文可以是 JSON、二进制数据或其他格式。长度若以 Content-Length 表达，单位是字节，不是中文字符个数。先把字符串编码成实际传输字节，再计算长度，才能避免包含非 ASCII 内容时的错误。成熟 HTTP 客户端通常会帮助处理这些细节，但你需要理解它替你做了什么。

### 9.3 一个合成创建请求

```json
{"title":"实现第一个工具","idempotency_key":"practice-1"}
```

这份 JSON 可以成为任务服务的请求正文。title 是业务内容，幂等键用于识别同一业务操作的重试。请求还需要正确方法、路径与内容类型才能被相应接口理解。只把 JSON 发到任意地址，不能让网络自动猜测应该调用哪个业务函数。

## 第十课：HTTP 响应、状态码与错误体

响应包含状态、字段和可选内容。成功状态也需要按具体接口解释：普通读取成功与资源创建成功可能使用不同状态。客户端应按照合同解析返回内容，不应只看状态是二开头就随意假定正文一定包含某个字段。

四百类常表示客户端请求相关问题，五百类常表示服务器处理相关问题，但这些分类仍不足以决定所有重试策略。例如请求限流可能需要等待，参数非法通常需要修正输入，业务冲突需要重新读取状态。盲目对所有非成功状态快速重试，会增加负担并掩盖真正原因。

| 课程常见状态 | 需要进一步检查的内容 |
|---|---|
| 200 | 返回体是否符合成功数据合同 |
| 201 | 新资源身份与后续查询方式 |
| 400 | 语法、字段类型或请求合同哪里不符 |
| 404 | 主机/端口虽有响应，但路径或资源是否正确 |
| 409 | 版本、幂等键或状态冲突的具体原因 |
| 413 | 请求体大小是否超出接口限制 |

错误响应也可能包含结构化 JSON，帮助客户端分类与提示。但如果代理返回 HTML 错误页，客户端直接调用 JSON 解析器就可能只看到解码错误。正确诊断应先记录 HTTP 状态与内容类型，再尝试按预期格式解析，避免把上游故障隐藏在下游语法异常后面。

## 第十一课：JSON 是语法，不是业务保证

JSON 的基本值包括对象、数组、字符串、数值、布尔和 null。对象键使用字符串，字符串使用相应引号与转义规则。Python 的字典展示不是自动合法 JSON，例如单引号、True 与 None 的写法不同。应使用 json.dumps 与 json.loads 等解析器，而不是用简单替换把一种语言文本“改成”另一种。

一个合法 JSON 可以是数字或列表，而你的接口可能要求顶层必须是对象。即使顶层是对象，字段也可能缺失、多余、拼错或类型不符。业务校验应在语法解析之后执行，并给出明确错误。课程 `parse_request` 要求精确字段集合、非空请求 ID 和非负整数 token 数。

```python
import json

value = json.loads('{"request_id":"r1","tokens":12}')
if not isinstance(value, dict):
    raise ValueError("object required")
if set(value) != {"request_id", "tokens"}:
    raise ValueError("unexpected fields")
if not isinstance(value["request_id"], str) or not value["request_id"].strip():
    raise ValueError("nonempty request id required")
if type(value["tokens"]) is not int or value["tokens"] < 0:
    raise ValueError("nonnegative integer tokens required")
```

布尔值在 Python 类型体系中与整数有关系，因此只用一般整数实例检查可能接受 true 对应的布尔对象。数量字段若明确拒绝布尔值，就需要更严格规则。类型提示不能替代这里的运行时验证，因为网络输入来自不受你静态代码约束的外部世界。

是否允许额外字段属于版本策略。严格拒绝有助于暴露拼写错误，忽略未知字段可能有助于某些兼容场景。两种策略都需要明确说明，不能让“实现没有考虑过”成为默认合同。模型工具参数、配置文件和 API 请求都会遇到相同问题。

## 第十二课：一次请求的完整时间线

以常见 HTTPS 客户端为例，先解析 URL 和配置，再进行名称解析，选择地址并建立传输连接，完成 TLS 握手，发送请求字段与内容，等待服务器处理，接收响应并解码，最后验证业务数据。连接复用、缓存和协议版本可能省略或改变某些阶段，所以这是一条帮助理解的基本路线，不是所有请求都会重新走完整套步骤。

每阶段都可能失败。名称解析失败时没有连接到目标；连接被拒绝时通常尚未取得 HTTP 响应；TLS 验证失败时不能把它简化成业务密码错误；HTTP 四百状态表示已经收到应用层响应；JSON 解析失败表示响应内容与预期格式不符；业务验证失败则说明格式可能合法但字段不满足合同。

把这些阶段写成日志字段，可以避免只留下一个“请求失败”的总耗时。对模型 API，还会进一步区分排队、首 token、后续流式输出和完整结束。基础网络理解越清楚，后面性能分析越不容易把传输、框架排队与模型计算混成一个数字。

## 第十三课：curl 命令逐项解释

先在 F16 按教材显式启动自己的课程服务，再运行：

```bash
curl --noproxy '*' --fail-with-body --connect-timeout 3 --max-time 10 \
  http://127.0.0.1:8765/health
```

noproxy 指定此次请求不经代理，星号用引号保护，避免被 Shell 当路径通配符展开。连接超时限制建立连接相关阶段的等待，最大时间限制整体操作。让 HTTP 错误反映为失败状态并保留响应体，有助于脚本同时知道失败与具体原因。实际选项支持应按本机 curl 帮助确认，旧工具不认识选项时，是客户端能力问题，不是服务器接口故障。

代理会改变请求经过的路径。你以为正在直连本机服务，环境中的代理变量却可能使请求走向另一个中间层。排查时先明确是否使用代理，再决定是否对本次局部请求绕过。不要为了一个课程回环请求，未经理解就全局删除公司网络配置。

将响应交给 JSON 格式化工具之前，先确认请求本身成功。否则网络错误、HTML 错误页或空响应可能只表现为 JSON 解析失败。管道状态的规则也会影响脚本最终看见哪个退出值，F03 的知识在这里直接发挥作用。

## 第十四课：SSH 同时解决远端身份与通道

### 14.1 你需要认证服务器，也需要向服务器认证自己

SSH 连接不仅是打开另一个终端。客户端要确认连接的是预期服务器，服务器也要确认你有权使用相应账户。主机密钥指纹用于帮助识别服务器，用户密码或用户密钥用于用户认证，这两套身份不能混为一谈。

首次连接出现主机指纹提示时，应通过可信渠道核对，而不是机械地接受所有内容。已有主机密钥突然变化时，也应先确认是正常更换还是目标错误。删除已知主机记录可以消除某个提示，却不会自动证明新对端真实可信。

### 14.2 公钥与私钥的角色

公钥可以放到授权服务端用于验证，私钥应保留在自己受控位置。私钥不是需要发给管理员的“登录资料”，也不应提交到公开仓库。口令可用于保护私钥文件，但具体账户与密钥管理还要遵循所用环境的规则。课程不要求你公开真实服务器地址或密钥来完成练习。

```bash
ssh USER@HOST
```

这里的用户与主机是占位内容，需要替换为你被授权使用的环境信息。连接成功后先运行身份检查，确认远端机器、用户和目录，再进行文件或服务操作。终端窗口仍在自己的电脑上，不意味着里面的命令仍在本机执行。

### 14.3 传文件与执行命令分开

SSH 会话不自动同步本地文件。需要传输时使用明确的文件传输工具或 Git 工作流，记录源与目标方向。把远端路径写到本机普通文件命令中，可能只是在本机创建一个奇怪名字，而不会自动发到服务器。先确定操作在哪个程序中解释，才能正确理解路径语法。

## 第十五课：本地端口转发的三个视角

```bash
ssh -N -L 8766:127.0.0.1:8765 USER@HOST
```

这个例子让本机的一个端口通过 SSH 通道连接到远端视角中的目标服务。浏览器访问本机回环的八七六六；SSH 客户端把数据通过加密通道送到远端；远端再连接自己的回环八七六五。左边端口属于本地入口，右边目标由远端视角解释，不能把两个数字和地址角色混在一起。

N 选项表示不执行普通远端命令，保持转发用途。转发建立并不自动证明远端服务健康：如果远端八七六五没有监听，浏览器通过转发访问仍会失败。诊断可以先在远端直接请求其回环服务，再检查本地转发是否建立，最后从本机访问入口。

本地端口也可能被占用，选择另一个本地端口不需要同时改变远端服务端口。转发的监听范围和访问者仍需按实际配置确认，基础练习保持本地使用即可。端口转发是一种连接路径安排，不是绕过业务权限的理由；服务自身的认证合同仍然适用。

## 第十六课：tmux 的作用与限制

tmux 管理持久终端会话，使你可以分离连接、稍后重新附加。它能帮助远端学习任务不依赖某一次 SSH 窗口持续打开，但并不自动替你调度 GPU、限制内存或判断公司任务是否繁忙。会话保留与资源管理是不同责任。

```bash
tmux new -s course
tmux ls
tmux attach -t course
```

分离常用先按控制前缀再按对应键的方式，具体按键取决于配置。分离不会等于停止里面运行的程序。重新附加后，先查看已有任务状态，避免因为没看到旧窗口就又启动一份相同模型服务。结束会话前也要确认其中只包含自己的课程任务。

短期实验仍应设置有限输入、有限迭代和明确结束条件。保存日志与命令记录可以帮助你在重新连接后恢复理解，但不要把密钥放进命令历史或公开日志。基础 CPU 实验适合先练习这些操作，再将同样纪律用于 H100。

## 第十七课：重试、超时与幂等

### 17.1 超时只能说明客户端没有按时得到结果

假设客户端请求创建任务，服务器已经保存任务，但响应在返回途中丢失。客户端看到超时，不能据此断言创建没有发生。如果立刻重发一个没有去重机制的创建请求，可能产生重复任务。网络失败带来的不确定性是应用设计必须承担的事实。

### 17.2 幂等键把重试关联到同一业务操作

一个明确的幂等合同可以规定：同一键与相同参数重复提交，返回同一个结果；同一键但参数不同，返回冲突。这样客户端在不知道响应是否丢失时，可以使用同一个键重试，而不是创建新身份。F16 会实际实现并测试这套行为。

幂等不是简单“把错误忽略掉”。服务端需要把业务操作与键的记录放在合适的事务或一致性边界内，否则仍可能在竞争时重复执行或错误接受冲突。客户端也不能每次重试都生成一个新键，否则服务端无法知道它们属于同一操作。

### 17.3 重试预算与退避

可重试错误也需要次数、总时间和等待策略。快速无限重试可能放大服务故障，尤其多个客户端同时这样做时。参数错误通常应该修正输入而不是等待；认证错误通常需要处理凭证或权限；临时限流可能需要按合同等待。先分类，再决定是否重试，远比统一套一个循环可靠。

## 第十八课：五层诊断表

| 层 | 要确认的事实 | 常见证据 |
|---|---|---|
| 执行环境 | 请求从哪台机器/容器发出 | 主机、目录、命令与环境记录 |
| 地址与路径 | 目标是否解析且路由可达 | 实际目标地址与网络配置 |
| 传输与监听 | 端口是否接受连接 | 监听状态、连接错误类型 |
| HTTP 与认证 | 是否收到合法响应，状态是什么 | 状态码、字段、错误体 |
| 数据合同 | 解析后是否满足业务要求 | 类型、必需字段、范围与版本 |

连接拒绝、连接超时、四零四、JSON 解析错误和字段类型错误不应写成同一个结论。每一种观察都说明系统已经走到某个阶段，并在下一责任边界失败。先利用已经成功的部分缩小范围，再检查尚未成立的前提，能让诊断从猜测变成推理。

## 第十九课：十二道练习与参考答案

### 题一：解释回环的视角

分别在本机、远端和普通独立网络容器中解释回环地址。参考答案必须明确“当前网络环境自己”，不能回答成固定的一台机器。再说明为什么远端服务监听回环后，本机直接访问自己的回环通常不会自动抵达远端。

### 题二：监听所有接口与客户端地址

说明零地址用于绑定时的含义，以及客户端通常应该使用什么。答案是监听范围与访问目标不同；客户端使用实际可达地址或域名，防火墙、映射和认证仍影响可访问性。只改绑定参数不保证所有网络问题解决。

### 题三：URL 拆解

运行课程 describe，逐项解释 scheme、host、port、path、query 和 fragment。查询值保存为列表，是因为同名参数可能重复。片段通常由客户端处理，不作为普通请求目标发送。解析成功不能证明网络可达。

### 题四：三种失败的区别

没有监听服务、请求未知路径、提交非法 JSON，分别可能体现为连接失败、HTTP 四零四、HTTP 四百。参考答案要指出各自已成功经过哪些层，下一步检查什么，而不是只背状态名称。

### 题五：正文长度

```python
import json
text = json.dumps({"title": "学习"}, ensure_ascii=False)
raw = text.encode("utf-8")
print(len(text), len(raw))
```

比较字符数与字节数，说明长度字段应根据实际传输字节计算。若启用不同 JSON 转义选项，文本内容与字节数也可能改变，但解析后的业务对象可以相同。这说明表示形式与语义对象是不同层次。

### 题六：业务合同拒绝

为课程 parse_request 提供缺字段、额外字段、空 ID、负数量、布尔数量和顶层列表。参考结果都应拒绝，但原因不同。测试应明确每个例子违反哪条合同，避免只写一个笼统的“坏输入会报错”。

### 题七：分片组装

输入块依次为 `hel`、`lo\nwor`、`ld\n`，手算按换行分隔的输出。答案依次产生 hello 与 world，未完成尾部必须保留。若最后没有换行，协议需要明确尾部算不完整错误还是最后一条记录，不能让实现自行猜测。

### 题八：完整的离线分隔器

```python
def split_records(chunks):
    pending = ""
    records = []
    for chunk in chunks:
        pending += chunk
        while "\n" in pending:
            record, pending = pending.split("\n", 1)
            records.append(record)
    if pending:
        raise ValueError("incomplete final record")
    return records

assert split_records(["hel", "lo\nwor", "ld\n"]) == ["hello", "world"]
```

本例用于已解码文本，尚未处理字节跨字符边界，也没有限制缓冲大小。生产解析器需要明确最大记录长度和错误策略。用一次收到两条记录、一次只收到半条、空块和不完整结束分别验证状态机。

### 题九：端口转发逐段追踪

使用本章八七六六到远端八七六五的示例，用文字说明浏览器连接、本地入口、SSH 通道与远端目标四个位置。答案必须把本地与远端的回环分开，并说明远端服务未启动时转发本身不能创造服务。

### 题十：请求重试

创建请求超时后是否可以换一个新幂等键直接重试？参考答案通常是否，因为新键可能代表新业务操作，无法去重上次已成功但响应丢失的结果。应按接口合同使用原键或查询操作状态，明确处理不确定结果。

### 题十一：tmux 不等于结束程序

在自己的会话里运行一个短 CPU 程序，分离再附加，记录任务是否继续。参考结论是分离改变终端连接状态，不等于向程序发送停止命令。GPU 任务是否占用资源应通过实际进程与设备观察确认，不能只看窗口是否打开。

### 题十二：一份完整 API 诊断记录

提交请求目标的脱敏结构、执行位置、连接与总超时、是否使用代理、HTTP 状态、内容类型、错误分类和最小合成输入。禁止包含真实密钥。参考合格记录应让别人能判断失败发生在哪层，而不必接触你的私人服务凭证或业务数据。

## 第二十课：把一段网络数据逐层拆开

### 20.1 分层是在划清责任，不是在背名词表

可以把一次简单通信分成应用消息、传输、网络寻址和本地链路等责任。HTTP说明请求与响应怎样解释，TCP等传输机制说明字节流怎样在端点间交付，IP层帮助数据跨网络寻找目标，本地链路再负责当前这一跳的实际发送。每一层为上层提供某些能力，同时有自己的失败边界。分层模型的价值是让你知道一个问题应在哪一层寻找证据。

这些层不是每次都对应一个独立程序，也不是说硬件与软件严格一层一个文件夹。操作系统网络栈、驱动、网卡和应用库会共同实现它们。你不需要从第一天就阅读全部内核源码，但应避免把“网卡连上了”“能够解析域名”“TCP连接成功”“HTTP成功”和“业务结果正确”当作同一句话。

例如局域网链路正常，只能说明某些本地传输前提成立；目标网络仍可能没有路由。路由成立，目标端口仍可能没有服务。服务接收连接，应用仍可能返回鉴权失败。鉴权成功，业务请求仍可能字段非法。每个成功层次都缩小了问题范围，却没有替下一层作保证。

### 20.2 TCP序号的手算直觉

假设应用希望传递六个字节，内容是abcdef。为了便于手算，暂时把第一个数据字节标为序号一。发送方可以把前三个字节放在一次传输里，把后三个字节放在另一次传输里；接收方根据序号知道它们在字节流中的位置，而不是根据应用调用send的次数划分消息。确认信息帮助发送方知道哪些数据已经被接收，从而决定是否还需要重传。

真实TCP还包含连接建立时的初始序号、控制位占用和更多细节，本例没有试图复刻全部协议状态。它要说明的是可靠字节流依赖明确的顺序与确认机制，而不是网络保证每个分组永不丢失。某一分组丢失可以通过重传补齐，应用可能只观察到延迟增加，而不一定直接看到“丢了一包”的事件。

接收方按序交付字节，也不保证应用总能在有限时间内得到完整业务结果。对端程序可能永远不发送下一段，连接可能被中断，应用协议也可能没有定义完整结束。传输机制提供一部分可靠性，超时、消息边界和业务完成仍需要更高层设计。你以后阅读流式模型输出时，不能仅凭连接仍开着就认为生成一定在正常推进。

### 20.3 流量控制与拥塞控制不要混为一谈

流量控制关注接收方是否有能力接收更多数据，避免发送方把接收缓冲淹没；拥塞控制关注网络路径承受的负载，避免过度发送使网络整体恶化。二者都可能影响发送速率，但责任不同。客户端读取很慢和网络链路拥塞，可能都表现为吞吐下降，却需要不同诊断。

应用层也有自己的背压与队列。模型服务可能已经接收完整请求，但在等待GPU调度；网络带宽此时并不是主要瓶颈。反过来，模型快速生成大量输出，客户端或中间代理消费慢，也可能影响端到端行为。先区分生成速度、传输速度和消费速度，才能知道增加GPU算力是否真的改善用户等待。

## 第二十一课：HTTP消息边界、连接复用与流式输出

### 21.1 正文长度与传输分块

HTTP/1.1需要让接收方知道一条消息在哪里结束。某些消息使用明确长度，某些使用分块传输编码等机制，具体规则还与方法和状态有关。应用不应自己随意混用长度字段与分块规则；成熟客户端和服务器库负责按协议生成与解析这些结构。你在业务代码中看到的正文内容，通常已经不是原始网络分组或传输分块的完整外观。

必须区分三种“块”：网络传输分段、HTTP传输编码块、应用层事件块。它们的边界可以完全不同。一个模型事件可能跨多个网络读取，也可能与下一个事件一起出现在一次读取中。若应用以SSE等格式传递事件，还需要按该格式的分隔与字段规则解析，不能拿底层read返回一次就当成一个完整事件。

### 21.2 连接复用降低开销但增加状态

每次请求都重新建立连接和TLS握手会产生额外成本。连接复用让多个请求使用已有连接或连接池，减少重复准备。但复用也需要管理连接是否仍有效、服务器何时关闭、并发请求怎样安排和超时怎样计算。你在基准中测“第一次请求”和“稳定复用后的请求”，结果可能不同，应记录测试状态。

连接池不是业务并发上限的同义词。客户端允许多少连接、服务器允许多少并发请求、模型调度器同时处理多少序列，是不同层次参数。一个请求可能在客户端池中排队，也可能在服务器队列中排队，或者正在模型内部计算。只观察总体耗时无法自动区分这些位置，必须结合相应指标。

### 21.3 首字节、首事件与首token

收到响应头或第一个字节，不一定已经得到模型的第一个可见token。流式API可能先发送元数据、心跳或工具调用片段。测量首token延迟时，需要定义什么事件算作token以及计时起点是什么；否则不同工具报告的数字不具有直接可比性。

同样，连接关闭不一定是唯一正常结束信号。应用协议可能用明确终止事件表示完成，随后连接继续复用；连接意外断开也可能发生在终止事件之前。客户端应检查协议完成状态，而不是把“读不到更多字节”一律当成成功。Agent卷会把这类不完整流与正常完成分开建模。

## 第二十二课：代理、反向代理与服务路径

### 22.1 谁代表谁建立下一段连接

客户端代理代客户端向目标建立请求，反向代理常位于服务入口，将请求转给后端服务。它们可能处理TLS、路径转发、限流、认证、缓存或负载均衡。因此你访问的域名与实际执行模型的进程之间，可能存在多个中间组件。某个错误响应可能由中间层生成，而不是由模型框架生成。

诊断时应记录响应状态、相关字段和服务日志，确认请求是否到达目标后端。一个网关返回五百错误，不代表后端一定崩溃；也可能是连接后端失败、上游超时或路径配置错误。另一方面，后端日志出现请求也不保证客户端收到了完整结果，中间传输仍可能失败。

### 22.2 基础URL与接口路径的组合

模型客户端常配置一个基础URL，再由库拼接具体路径。如果基础URL已经包含某段版本路径，而调用方又重复追加，最终可能得到不存在的双重路径。反过来，少了一段前缀也可能访问到错误路由。遇到四零四时，应查看实际请求目标，而不只是检查配置中看起来正确的域名。

不要为了消除四零四就在多个地址间随机尝试并携带密钥。应先根据提供方合同明确基础URL和接口路径，用无敏感信息的结构记录核对。一个HTTP兼容接口可以支持部分协议而非全部协议；能列出模型不自动证明所有生成端点、流式工具调用和参数都受支持。

### 22.3 转发与认证边界

中间代理可能终止TLS再向后端建立新连接，所以端到端保护范围需要按实际部署判断。客户端持有的API密钥也可能只适用于某个网关，而不是后端模型框架本身。不要把不同系统中的凭证混用，或把包含认证字段的请求随意重定向到另一个来源。

对学习项目，先使用自己的回环服务把路径、状态和JSON合同验证清楚，再接入真实供应商。这样真实API失败时，你已经有一个可控基准，能够区分客户端逻辑问题与外部接口差异。离线替身不是替代真实能力测试，而是让协议实现本身可以稳定验收。

## 第二十三课：一个从健康检查到创建任务的手动验收流程

第一步只检查服务是否在预期地址监听，并请求健康接口。健康成功只能证明这条检查路径可用，不能证明数据库写入或模型生成已经全部正常。第二步发送一个最小合法创建请求，记录状态、返回身份和内容。第三步用返回身份查询，确认读到同一资源，而不是只相信创建响应的文字。

第四步使用同一个幂等键与相同参数重复提交，检查资源身份不变。第五步保持键不变但改变参数，检查是否按合同返回冲突。第六步发送非法JSON与合法JSON但非法字段，分别检查语法错误和业务错误。第七步停止服务并重新启动，再查询已保存资源，验证持久化边界。每一步都对应一个不同责任，不能用一次健康检查替代整套流程。

全过程使用合成标题与自己的本地数据库，不需要真实公司数据。若某一步失败，保留准确命令、状态与脱敏响应，再回到对应层定位。不要通过删除所有数据库或重新安装全部依赖来消除症状，因为那会抹掉有价值的失败证据，也无法说明问题为什么出现。

完成后，把请求时间线、服务状态转换和持久数据变化画成一张简短表。你会发现，网络只是把输入送到业务状态机的通道；可靠应用还需要校验、事务、幂等和恢复。F16正是沿这条链建立完整任务服务，后续Agent工具也会复用相同思路。

还要验证请求体大小限制。客户端发送的数据即使语法合法，也可能大到使服务耗尽内存；因此服务应在读取和解析阶段明确限制，而不只是等全部内容进入内存后才发现超限。限制单位必须写清是字节、记录数还是业务字段长度，并给出明确错误响应。反过来，客户端读取响应也需要考虑异常巨大内容，而不是认为服务器永远返回小结果。

大小限制与超时解决不同问题：一个小请求可以处理很久，一个巨大请求也可能很快抵达。可靠接口同时定义输入范围、处理预算与结果合同。为本地服务分别构造“略小于上限”“恰好上限”“超过上限”的合成请求，能检查边界是否一致；不要用真实超大业务数据来试探未知服务容量。把这些限制写入接口文档后，调用者才能在发送前做相应检查。

## 第二十四课：从基础协议走向 Agent 与推理服务

Agent 调用模型时，需要正确维护请求身份、流式分片、超时和重试；推理框架服务需要明确监听地址、队列与输出协议；检索系统需要验证远端数据格式与权限。它们都建立在本章这些基础之上。你不需要先背完全部网络标准，但应能把一次调用拆成可观察的责任层次。

HTTP 语义与消息边界参考 RFC 9110、RFC 9112，SSH 行为参考 OpenSSH 原始手册，具体入口在本卷来源表中。后续 F16 会让你真正实现并运行回环任务服务，把本章的请求、状态、JSON、幂等和持久化连接成完整工程。
