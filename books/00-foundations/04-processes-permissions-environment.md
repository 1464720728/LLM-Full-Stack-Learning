# F04 进程、权限与环境：谁在运行，能访问什么，失败后怎样收尾

一条命令被 Shell 正确解析，只是执行的起点。操作系统随后要安排进程、内存、文件、用户身份和调度。你需要知道程序是否仍在运行、它在等待什么、为什么某个路径不可访问，以及停止它会留下什么状态。本章把这些问题连成一个可以观察和推理的模型。

主实验为 `python -m labs.foundations.permissions` 与 `python -m labs.foundations.process_runner`。默认实验不会改变系统权限，不会终止其他进程，也不会使用 GPU。所有进程操作只针对自己明确启动并记录身份的练习程序。

## 第一课：程序文件与运行实例

### 1.1 同一份代码可以同时有很多次执行

程序是代码与相关资源的静态组织，进程是程序正在运行的一次实例。你可以同时启动同一个 Python 脚本三次，得到三个不同进程。它们读取相同源码，却可能使用不同参数、目录和环境，持有不同内存状态，也可能在不同执行位置。磁盘文件路径相同，不代表运行状态共享。

每个进程都有可观察的身份，例如进程 ID。它还拥有当前工作目录、环境变量、打开的文件描述符和内存地址空间等状态。这些属性共同决定“同一条命令”实际做什么。一个脚本在不同目录读到不同文件，或在不同环境导入不同包，并不需要源码本身发生变化。

进程结束不等于源码删除。源码删除也不一定立刻终止已经运行的进程，因为程序可能已经加载了所需内容。类似地，模型服务启动后把权重加载进内存或显存，磁盘上某份权重之后改变，并不会自动意味着运行中模型立即同步更新；具体行为取决于程序是否重新读取。不要把持久文件与运行时状态混成一层。

### 1.2 内存地址空间的隔离直觉

两个普通进程各自拥有虚拟地址空间。它们内部打印出相同数值的地址，不意味着指向同一物理内存对象。操作系统与硬件把进程视角的地址映射到实际资源，隔离使一个程序不能按普通方式随意读取另一个程序的全部内存。共享内存是需要明确建立的特殊机制，不是“都在一台机器上”就自动共享变量。

这种模型帮助你理解为什么一个子进程修改 Python 列表，父进程的普通列表不会自动变化。线程与进程在共享状态上的区别会在 F11 展开。当前先记住：程序间协作通常要经过明确通道，例如文件、管道、套接字或共享内存，不能靠相同变量名传递数据。

## 第二课：父子进程与继承

### 2.1 启动关系不是对象包含关系

Shell 启动程序时，新的执行通常与父进程建立父子关系。进程表中的父进程 ID 可以帮助你追踪谁启动了谁。父子关系不意味着父进程能通过普通局部变量访问子进程所有对象，也不意味着子进程结束会自动撤销它已经写出的文件。它主要描述创建与等待等操作系统关系。

子进程会继承某些执行上下文，例如当前目录、环境以及被允许继承的文件描述符。继承通常是初始状态，而不是永远双向同步的共享配置。父进程后来修改自己的环境变量，不会自动更新已经运行的子进程；子进程改变自己的目录，也不会让父 Shell 跟着进入相同目录。

### 2.2 为什么脚本中的 cd 不改变调用者

你运行 `bash script.sh`，脚本通常由子 Shell 执行。脚本里 cd 改变子 Shell 的目录，随后它启动的程序可继承这个新目录，但脚本结束后父 Shell 保持自己的原目录。若使用 source 在当前 Shell 中执行脚本，情况不同，因为动作直接发生在当前环境。F03 的语法在这里得到进程层解释。

这条规则也影响环境激活。若一个脚本只是启动另一个 Shell 并在其中激活虚拟环境，那个子 Shell 结束后，你当前终端不一定继续使用被激活环境。明确调用虚拟环境内的 Python 可执行路径，或在当前 Shell 中正确读取激活脚本，才能建立预期的解释器选择。

### 2.3 返回状态与等待

父进程可以等待子进程结束，并取得其退出状态。等待不是自动读取全部业务结果；退出状态只提供一个有限的状态通道，数据仍可能通过标准输出、文件或其他接口传递。父进程若不检查退出状态，就可能把失败子进程留下的部分输出当成成功结果继续使用。

一个进程已经结束但其退出信息尚未被父进程回收时，可能以僵尸状态出现在进程表中。它通常不再像正常运行进程那样执行计算，但仍占用相应管理记录。看到这个术语不要立刻理解成“系统里有一份还在偷偷运行的完整程序”，应先区分执行结束与父进程回收完成这两个阶段。

## 第三课：怎样观察自己的进程

```bash
ps -u "$USER" -o pid,ppid,stat,etime,args
```

这条命令限定查看当前用户的进程，并选择显示进程 ID、父进程 ID、状态、已运行时长和参数。你应该先找到自己刚启动的练习程序，再对照父子关系，而不是把整台服务器的进程列表当作可以随意处理的任务清单。命令行参数可能包含敏感信息，公开截图前应检查内容。

PID 是当前系统中的运行标识，但会被复用。今天看到的某个数字，明天可能对应另一个程序。保存一个旧 PID 后过很久直接发送信号，存在误操作风险。可靠操作应在动作前重新核对用户、命令、启动时间等上下文，或由启动器直接持有自己创建的进程对象与生命周期关系。

进程状态通常包含运行、睡眠、停止等不同情况。睡眠不等于程序坏了，它可能正在等待输入、网络或计时器。CPU 占用低也不等于没有工作，I/O 等待程序可能主要在等外部资源。相反，CPU 占用高只说明正在消耗计算资源，不证明算法正在朝正确目标推进。

已运行时长与 CPU 时间不同。一个程序运行十分钟，其中九分钟等待网络，它的墙钟时间与累计 CPU 时间会很不一样。性能排查应先问延迟花在哪里，而不是只看一个百分比就决定增加 GPU。后面的框架测量课程会继续区分吞吐、排队、计算和端到端延迟。

## 第四课：前台、后台、作业与会话

### 4.1 前台交互的含义

前台作业与当前终端的交互联系紧密，通常能够读取键盘输入，并接收终端产生的相应控制信号。你运行一个持续等待输入的程序后，Shell 提示符不再出现，是因为 Shell 正在等待前台作业，而不是终端必然卡死。程序可能正常计算，也可能等待输入，需要结合预期行为判断。

命令末尾加后台符号可以让 Shell 不必一直等待它完成，但后台并不自动提供可靠服务管理。输出仍可能写到当前终端，输入行为可能受到限制，终端断开后的存活也取决于会话与信号处理。把一个长任务放到后台，不等于已经解决日志、退出状态、重启与资源回收。

### 4.2 作业号与 PID 不同

Shell 的作业管理可以使用它自己的作业编号，操作系统则使用 PID 等标识。作业可能包含管道中的多个进程，所以一个作业不一定只对应一个 PID。你看到 `jobs` 输出的编号时，应知道它属于当前 Shell 的管理视角，不是可以在任意终端通用的系统进程身份。

前台恢复、后台继续和停止状态等操作涉及作业控制。初学练习可以使用自己启动的小型等待程序观察，但不要在公司任务上试探未知快捷键。理解“暂停执行”和“结束进程”也很重要：暂停的进程可能仍保留内存和打开资源，并不等于释放了所有占用。

### 4.3 远端长任务的会话管理

SSH 断开后任务是否继续，取决于它怎样启动、标准流连接、会话与信号行为。tmux 等会话工具能够让你重新连接到持久终端会话，但它不是资源调度器，也不会自动限制显存或防止错误程序无限运行。nohup 改变特定挂断行为，也不等于提供完整重启和健康检查。

本课程的长实验应优先设置明确超时、日志路径和结束条件，并记录自己创建的会话或任务名称。共享服务器的 GPU 实验尤其需要可预测地结束。基础章节不要求你长期占用 GPU；真正需要时，后续课程会给出限定规模的实验。

## 第五课：信号与终止不是同一种停止按钮

### 5.1 正常退出、请求终止与强制结束

程序可以自行完成并正常退出。外部也可以发送信号，请求它中断或终止。终端中的 Ctrl+C 通常向前台进程组发送中断信号，程序可能将其转换为语言层异常或运行清理逻辑。常见终止信号也给程序一定机会完成收尾，但程序是否处理、怎样处理取决于实现。

强制终止会绕过普通用户态清理机会，所以不能把它当成第一选择。一个程序正在写文件、提交事务或管理子进程时，突然结束可能留下临时文件、不完整应用状态或仍在运行的后代。操作系统会回收许多进程资源，但不会自动理解并回滚所有业务副作用。

### 5.2 为什么先确认再发信号

只按模糊命令名批量结束进程很危险，尤其在共享机器上。多个用户可能都运行 Python，甚至同一用户的不同重要任务都叫 Python。正确操作应限定到自己创建、已经核对的具体进程或进程组。不要把“清理一下环境”翻译成对所有同名进程发送强制信号。

优先尝试程序提供的正常关闭机制，或发送可处理的终止请求，等待明确时间，再根据状态决定是否升级。等待不是永远等待，应有上限和记录。对于教学任务，最可靠的方法是从启动时就建立生命周期管理，而不是运行几个小时后再凭进程名猜哪一个属于自己。

### 5.3 进程组与后代

一个外部命令可能继续启动多个子进程，例如构建工具、测试执行器或模型服务。只终止最外层进程，不一定自动结束所有后代。POSIX 环境中可以通过独立进程组或会话组织自己启动的任务，再向该组发信号；但后代若主动脱离原组，仍需要更强的管理机制。

这就是为什么一个 timeout 参数不等于完整沙箱。时间限制、进程树管理、文件权限、网络访问和 CPU/GPU 资源约束是不同责任。课程的最小 subprocess 实验只展示一个固定子程序，不宣称可以安全执行任意未知代码。

## 第六课：用户、组与权限判断

### 6.1 身份先于权限位

操作系统根据进程的用户与组等身份判断访问权限。文件也有所有者与组信息。普通九位权限把读取、写入、执行能力分别分配给所有者、所属组和其他用户。理解权限前，先用 whoami 或相应身份查询确认当前用户，不要因为目录位于自己的主目录下，就假定所有文件一定属于自己。

用户身份与程序文件的名字没有直接等价关系。一个名为“管理员工具”的脚本，不会因此自动拥有管理员能力；一个普通脚本如果被高权限身份运行，也可能具有很大影响。权限来自实际执行身份和系统规则，而不是你给程序起了什么名字。

### 6.2 sudo 不是通用修复按钮

sudo 可以按配置以其他身份执行命令，常见是提升权限，但它还可能影响环境变量、主目录和文件所有权。用 sudo 运行一个原本只需普通用户权限的安装或写文件步骤，可能产生之后普通用户无法修改的文件。眼前成功不一定意味着环境从此更正确。

遇到 Permission denied 时，先定位缺少的是文件读权限、目录穿过权限、可执行权限还是其他限制。只有确实需要管理操作并符合机器规则时才提升权限。课程工程与虚拟环境通常可以放在普通用户可写目录，没必要因为一次路径选错就把整套学习流程变成管理员操作。

### 6.3 权限与数据内容无关

一个文件内容看起来完全无害，也可能因为权限而无法读取；一个可读文件也可能包含不应公开的数据。操作系统访问控制与应用数据保密是相关但不同的层次。公开教材代码不意味着可以把公司的运行日志、API 端点和密钥一起提交。学习时使用合成夹具，既能复现实验，也能保持数据边界清楚。

## 第七课：逐位读懂 rwx 与八进制

每组权限有三位：读为四，写为二，执行为一。一个组内把允许的位相加，得到零到七的一个八进制数字。例如六等于四加二，表示读写但不执行；五等于四加一，表示读与执行；零表示都不允许。

| 八进制数字 | 二进制位 | 符号 | 含义 |
|---:|---|---|---|
| 0 | 000 | --- | 无普通权限位 |
| 4 | 100 | r-- | 读 |
| 5 | 101 | r-x | 读与执行 |
| 6 | 110 | rw- | 读写 |
| 7 | 111 | rwx | 读写执行 |

三个数字从左到右分别对应所有者、组、其他人。六四零表示所有者读写、组只读、其他人无权限，符号为 `rw-r-----`。七五零表示所有者全部、组读执行、其他人无权限。不要把七七七当作“最正确”的权限，它只是把普通权限位广泛开放，可能远超需求。

Python 中 `0o640` 明确表示八进制字面量；直接写 `640` 是十进制数，两者值不同。课程权限实验将模式拆成各个位并检查是否开启，用来帮助你看清八进制表示与二进制位之间的关系。这里没有真的改变系统文件权限，适合先在纸上算对再做受限手动操作。

## 第八课：文件与目录的 rwx 语义不同

### 8.1 普通文件

读权限允许读取内容，写权限允许按相应规则修改内容，执行权限影响作为程序直接执行。一个 Python 源文件没有可执行位，仍可能由已有解释器以读取源码的方式运行；直接执行脚本则还涉及执行权限与 shebang。不要把“python script.py 能运行”与“./script.py 能运行”当成完全相同的路径。

可执行位也不证明文件是有效程序。若文件内容格式错误或指定解释器不存在，仍会失败。文件系统挂载选项等因素也可能影响执行，普通九位权限并不是整个访问控制系统的全部。

### 8.2 目录

目录读权限主要影响列举名称，执行权限常被理解为搜索或穿过目录，写权限影响目录条目的增删等操作。访问一个深层文件需要沿路径穿过多个父目录，因此即使文件本身可读，某个父目录缺少穿过权限也可能导致访问失败。

删除文件主要涉及其父目录的条目修改能力，而不只是文件本身是否可写。这常常让初学者惊讶：一个只读文件可能仍能被有权修改父目录的用户删除。系统还可能使用 sticky bit、ACL、挂载规则或强制访问控制施加额外限制，因此完整判断不能只看一组九位权限。

### 8.3 最小权限的具体含义

最小权限不是抽象口号，而是根据任务划定能力。读取教材通常不需要写系统目录；运行一个统计脚本不需要修改其他用户文件；保存个人实验结果只需写自己的结果目录。接口设计也应反映这些范围，让错误路径尽早被拒绝，而不是给予广泛权限后希望调用者永远不误用。

## 第九课：umask 是按位屏蔽，不是十进制减法

程序创建文件时请求某组初始权限，umask 屏蔽其中不应授予的位。常见普通文件请求六六六，目录请求七七七；在屏蔽零二二时，结果分别为六四四和七五五。某些例子看起来像数字相减，但真正规则是按位运算，不能推广为普通减法。

课程实现使用 `requested & ~mask & 0o777`。按位与保留请求中已经开启、且没有被屏蔽的位。屏蔽不会把原本关闭的位变成开启，也不存在普通算术减法中的借位。对请求六四零、屏蔽零二七，结果仍是六四零，因为被屏蔽的那些位原本就没有授予。

umask 通常影响之后创建的对象，不会自动批量修改已经存在的文件权限。改变 Shell 中的 umask 后，现有文件仍保留自己的模式，除非你明确修改。若你希望验证效果，应分别创建新文件与新目录，观察实际结果，而不是仅查看旧文件然后断言设置无效。

应用也可能主动请求更严格的权限，最终结果不会因为 umask 较宽松就自动增加请求之外的能力。涉及秘密文件时，应该由创建逻辑明确使用合适权限，而不是依赖操作者终端碰巧配置得当。本章只模拟普通权限位，不实现 ACL、特殊位与不同文件系统的全部行为。

## 第十课：环境变量如何影响程序

### 10.1 环境是字符串映射

环境变量通常是一组名称到字符串值的映射。即使内容看起来是数字或布尔值，程序读到后也需要按自己的合同解析。字符串 `"false"` 在 Python 的普通真值判断中仍是非空字符串，不能用 bool 直接把它当作逻辑假。配置解析应明确接受哪些字面形式。

Shell 变量是否进入子进程环境取决于导出与启动方式。前缀赋值可以只作用于某条命令，不必永久改变当前 Shell。你可以通过一个固定 Python 子程序读取某个课程变量，观察继承效果，而不要全量打印所有环境，因为其中可能存在密钥和内部配置。

```bash
COURSE_MODE=demo python -c 'import os; print(os.environ["COURSE_MODE"])'
```

执行结束后，父 Shell 不应被理解为自动永久拥有同样的赋值。这个实验体现的是给一次子进程执行提供环境，而不是修改所有未来会话。

### 10.2 环境变量不是加密保险箱

把 API 密钥放在环境变量里，可以避免直接写进源码或某些命令行参数，但它并不是绝对秘密空间。程序日志、诊断脚本、错误报告和不当环境转发仍可能暴露内容。教学环境检查只报告允许公开的字段，不应为了方便把整个 os.environ 原样输出。

公开仓库中的示例应只展示变量名称和占位值。真实值保存在个人受控环境中，调用真实 API 前再明确配置。离线课程不需要这些密钥，测试也不应因为你的机器恰好配置了密钥就自动联网或花费额度。

### 10.3 配置优先级要可解释

一个程序可能同时接受默认值、配置文件、环境变量和命令行参数。必须规定冲突时谁优先，否则使用者不知道最终设置来自哪里。常见设计让显式命令行覆盖环境或配置，但这不是所有程序统一的法律，应查看具体实现。F10 将构建完整配置解析例子。

环境还会影响语言、编码、线程数和设备可见性等。某个变量被设置不等于所有库都会遵守，也不等于系统资源已被物理隔离。例如隐藏某些 GPU 的变量通常影响相应运行库的设备视图，不是完整权限沙箱。对共享资源，仍需要正确的任务范围与调度约定。

## 第十一课：PATH 与解释器选择

PATH 是寻找可执行文件的目录列表，在 Linux 常用冒号分隔。输入不带路径的命令时，Shell 按规则搜索；输入明确路径时，目标定位更直接。前面目录中的同名程序可能覆盖后面目录中的程序，因此顺序很重要。不要把陌生可写目录随意放在搜索路径最前面。

虚拟环境激活通常通过调整 PATH 等状态，使环境中的 Python 更容易被找到。验证应让 Python 自己输出 sys.executable，而不只是看提示符名称。某些 Shell 还会缓存命令查找结果，修改安装或搜索路径后若行为异常，需要理解并检查实际解析对象。

```bash
command -v python
python -c 'import sys; print(sys.executable); print(sys.prefix); print(sys.base_prefix)'
```

command 查询 Shell 的解析结果，Python 输出自己实际运行的位置和环境前缀。两种证据从不同层观察同一启动过程。若解释器和 pip 不属于同一环境，就会出现安装成功但导入失败；使用当前 Python 的 `-m pip` 能减少这种不一致。

不要为了让某个包导入成功，就无差别向 PYTHONPATH 加入许多绝对目录。那可能让程序偶然导入另一份同名模块，造成更隐蔽的版本混用。先确认工程入口、工作目录与安装方式，必要时用模块路径查询确定实际加载了哪份文件。

## 第十二课：用 subprocess 建立清晰执行合同

课程 `run_child` 固定启动当前 Python，并把用户文本作为一个独立参数传给子程序。它不接受任意可执行文件名，也不把输入拼成 Shell 命令。这样可以聚焦学习参数边界、输出捕获、超时和退出状态。

```python
import subprocess
import sys

result = subprocess.run(
    [sys.executable, "-c",
     "import sys; print(sys.argv[1]); print('diagnostic', file=sys.stderr)",
     "hello; this is one argument"],
    text=True,
    capture_output=True,
    timeout=3,
    check=True,
)
print(result.stdout)
print(result.stderr)
print(result.returncode)
```

列表每个元素是一项参数。默认不使用 Shell，因此文本中的分号只是普通字符，不会分成另一条命令。sys.executable 明确使用当前解释器，避免系统中另一份 python 被意外找到。`-c` 后的短代码由子 Python 解释，最后一个元素则成为这段代码读取的参数。

capture_output 捕获两个输出流，text 让接口按文本处理结果，timeout 设置等待上限，check 让非零状态转换为异常。每个选项承担不同责任：捕获输出不代表检查成功，设置超时不代表限制内存，不使用 Shell 不代表目标程序没有危险功能。可靠执行器需要逐项写出承诺，而不是用某个选项名概括全部安全性。

捕获全部输出还可能占用大量内存。如果允许外部程序无限打印，父进程收集输出会不断增长。真实执行工具应考虑流式读取、输出上限、截断标记和日志存储，而不是只加 capture_output。当前实验输出固定且很小，因此没有实现任意程序的完整资源管理。

## 第十三课：失败、超时与子进程清理

### 13.1 非零退出怎样变成异常

check 为假时，subprocess.run 可以正常返回 CompletedProcess，但 returncode 为非零；调用者需要自行判断。check 为真时，非零会产生 CalledProcessError，便于沿异常路径处理。两种方式都可以正确，关键是不能把失败状态忽略后继续把 stdout 当作可信业务结果。

```python
import subprocess
import sys

result = subprocess.run([sys.executable, "-c", "raise SystemExit(7)"], check=False)
assert result.returncode == 7
try:
    subprocess.run([sys.executable, "-c", "raise SystemExit(7)"], check=True)
except subprocess.CalledProcessError as exc:
    assert exc.returncode == 7
```

这段代码中的七是人为选择的教学状态，不是所有程序对七都有统一含义。一个执行器应保留原始状态和必要诊断，再根据业务规则映射成自己的错误分类，避免把所有失败都压成一个没有信息的字符串。

### 13.2 超时不等于撤销所有效果

程序在超时之前可能已经写文件、发请求或提交部分结果。终止等待不能把这些效果自动撤销。如果任务具有副作用，重试之前需要判断上一次是否已经成功执行到某一步。这个问题会在 Agent 工具的“不确定结果”状态中深入展开，基础 subprocess 也应先建立这层意识。

subprocess 的高层超时处理与任意进程树管理不是同一保证。一个子程序可能启动后代，并让后代继承输出管道或脱离原进程组。若你要管理整项作业，必须从启动时组织会话、资源和清理策略，不能只在最外层异常处理中打印 timeout 就宣布所有占用已经释放。

### 13.3 资源限制应分项记录

一个实验至少可以记录最长运行时间、输入规模、并发数、输出上限和设备范围。CPU、内存、文件数、网络与 GPU 各有不同约束手段。课程基础实验保持小规模，避免把资源问题混进语义学习。进入真实框架实验时，再按章节逐项增加规模并记录实际峰值。

## 第十四课：五类常见故障的因果诊断

**找不到命令。** 首先确认当前 Shell 与机器，再检查命令名、PATH 和实际安装位置。若明确路径能运行而短名称不能，重点在搜索规则；若路径本身不存在，重点在安装或环境选择。不要修改应用源码来解决尚未启动解释器的问题。

**权限不足。** 确认实际用户，沿路径逐层检查目录与目标文件，再考虑执行位、挂载规则和其他访问控制。文件可读但父目录不可穿过，仍可能无法访问。修复应尽量限定到需要的对象与能力，不使用广泛开放权限作为通用答案。

**程序似乎卡住。** 先问预期是计算、等待输入还是服务监听；查看自身日志与资源使用，区分正常慢、外部等待和死锁。没有输出不一定无进展，输出很多也不一定有进展。为小复现增加关键阶段记录，比无差别增加日志更容易定位。

**退出成功但结果错误。** 操作系统只知道程序怎样退出，不知道你的数学或业务目标是否满足。需要测试与验收 oracle 检查输出语义，例如统计总数是否一致、文件是否可重新读取、生成结果是否满足合同。零退出不是正确性的终极证明。

**停止父进程后仍有占用。** 检查是否有后代、其他会话或独立服务继续运行，确认归属再处理。不要因为一次清理不完整就批量结束所有 Python。更好的修复是改进启动器，让它明确记录自己创建的任务和生命周期。

## 第十五课：十二道练习与完整参考答案

### 题一：一份脚本启动两次

解释两个进程共享什么、不共享什么。参考答案：它们可以读取同一源码文件和某些共同外部文件，但普通局部变量与当前执行状态属于各自进程；参数、目录、环境可能不同。若需要共享数据，必须通过明确机制，不能凭相同变量名实现。

### 题二：父子目录

在子 Shell 中进入练习目录，结束后观察父 Shell 当前目录。答案是父目录通常不被子进程修改。再比较 source 的执行方式，说明不同结果来自修改发生在哪个执行环境，而不是 cd 命令忽然失效。

### 题三：权限手算

将七五零写成符号，再将读写、读写、只读三组转成八进制。答案分别为 `rwxr-x---` 与六六四。每组分别按四、二、一组合，不能把三位当成普通十进制位权计算。

### 题四：umask 反例

请求六四零，屏蔽零二七，结果仍为六四零。解释已有关闭位不会因屏蔽发生借位。用课程 apply_umask 验证，再选一个请求七七七、屏蔽零七七的例子，得到七零零，确认你理解按位关系。

### 题五：文件只读却可能可删除

参考答案应指出删除主要修改父目录中的名称关系，还受额外系统规则约束。文件写权限控制内容修改，不等于对目录条目删除的完整控制。不要在真实重要文件上实验，使用自己临时创建的目录和文件。

### 题六：环境中的布尔字符串

```python
def parse_bool(value):
    if value == "true":
        return True
    if value == "false":
        return False
    raise ValueError("expected true or false")

assert parse_bool("false") is False
```

这份合同只接受两个明确小写形式，不自动接受大小写、数字或空字符串。若需要更多形式，应写入合同与测试。不能使用 bool(value)，因为非空字符串 false 本身仍会被视为真。

### 题七：只观察允许公开的环境

```python
import os

allowed = ["COURSE_MODE", "COURSE_DATA_DIR"]
report = {name: os.environ.get(name) for name in allowed}
print(report)
```

这比全量输出环境更符合最小诊断原则。实际报告还应判断路径或模式值是否适合公开；允许列表只是缩小范围，不自动证明每个值都没有敏感性。课程夹具使用合成值即可。

### 题八：参数字面性

把子进程输入设成包含分号、美元符号和星号的普通文本，确认它只作为一项输出。参考实现使用固定可执行文件与参数列表，不启用 Shell。还要解释目标程序自身仍可能把参数解释成特殊选项，因此安全边界不能只停在 Shell 这一层。

### 题九：明确非零失败

运行第十三课的 SystemExit 示例，分别记录 check 为真与假时的行为。答案应包含返回对象与异常两种路径，并保留原始退出状态。只写“都会失败”不足以说明调用者怎样知道失败。

### 题十：固定分析器合同

设计函数只允许运行仓库中的一个固定分析脚本，输入文件必须位于指定课程目录，运行有超时。参考组合是根目录路径验证、固定参数数组、明确 cwd、受控环境、退出状态检查和输出合同。还需注明路径检查不是完整操作系统沙箱，输入文件可能在检查后变化。

### 题十一：最小进程观察记录

启动一个短期自己的练习程序，记录其 PID、父 PID、命令、开始与结束状态。不要依据过期 PID 进行后续操作。参考验收是能够解释谁启动它、谁等待它、它通过什么通道返回结果，以及结束后哪些持久文件仍保留。

### 题十二：故障分类器

为执行工具设计四种结果：正常成功、子程序非零、等待超时、无法启动。答案应分别记录适用字段，如退出状态、诊断、超时上限和启动异常。不要把无法找到可执行文件误报成子程序返回非零，因为此时子程序可能根本没成功启动。

## 第十六课：亲手构造一个可观察的进程执行器

### 16.1 先定义结果，而不是先写try

最小执行器也应该区分启动失败、运行失败、超时与成功。启动失败意味着操作系统没有按要求开始那个程序，例如可执行文件不存在；运行失败意味着程序已经启动，后来以非零状态结束；超时意味着等待超过本执行器允许的上限；成功则仍只表示进程层合同成立，业务输出是否正确需要另行验收。若四种情况都返回空字符串，调用者就无法选择合理恢复策略。

我们先固定子程序集合，而不开放任意命令执行。一个模式打印短结果，一个模式主动返回非零，一个模式等待超过上限。这样的测试替身能够稳定制造边界，不需要依靠真实网络偶然超时，也不需要在服务器上启动巨大任务。执行器接收的是模式选择，不是让调用者把任意Shell文本塞进来。

```python
import subprocess
import sys

SCRIPTS = {
    "ok": "print('done')",
    "fail": "import sys; print('bad input', file=sys.stderr); raise SystemExit(7)",
    "slow": "import time; time.sleep(2)",
}

def observe(mode):
    if mode not in SCRIPTS:
        raise ValueError("unknown fixture mode")
    try:
        result = subprocess.run(
            [sys.executable, "-c", SCRIPTS[mode]],
            capture_output=True, text=True, timeout=0.2, check=False,
        )
    except subprocess.TimeoutExpired:
        return {"status": "timeout", "returncode": None}
    except OSError as exc:
        return {"status": "start_error", "reason": type(exc).__name__}
    return {
        "status": "success" if result.returncode == 0 else "nonzero",
        "returncode": result.returncode,
        "stdout": result.stdout,
        "stderr": result.stderr,
    }
```

这段代码选择check为假，是为了在一个明确分支中把退出状态映射为自己的结果结构。异常分支处理没有正常CompletedProcess的情况，正常返回分支处理已经获得退出状态的情况。你也可以使用check为真再捕获异常，但应保证最终分类含义一致，而不是混用两套行为后漏掉某种失败。

零点二秒只是小型教学上限，不用于证明不同机器的启动性能。高负载机器上，即使正常模式也可能因为启动调度延迟而超时，因此自动验收不应写“正常模式一定小于某个极短毫秒数”的脆弱性能断言。真正关注的是超时分类与清理行为，测试可以选择更宽裕上限或替身控制，而不是依赖偶然时序。

### 16.2 为什么同时捕获两个流

一个子程序可能向标准错误写很多数据。如果父进程只等待标准输出结束，却一直不读取标准错误，后者的管道缓冲可能填满，子进程阻塞在写错误流，父进程又等待子进程结束，形成互相等待。高层communicate及相关接口就是为协调这些输入输出而设计的，不能随意用两个顺序read替代并假定等价。

同时捕获两个流后，也不要试图仅按两个最终字符串的拼接顺序还原真实事件时间线。两个流是独立通道，缓冲与调度会影响观察顺序。若业务需要精确事件顺序，应在协议中加入序号或时间信息，并设计统一采集方式；事后把stdout接在stderr前面并不能证明程序先输出了全部正常数据再输出错误。

对无限输出程序，收集两个完整字符串仍然可能耗尽内存。真实执行器可以逐块读取并施加总量上限，达到上限后明确记录截断和处理策略。这里的固定替身只产生很小输出，所以教学代码不承担任意外部程序的输出资源保障。准确说明范围，能防止后续Agent工具把小例子直接当成生产沙箱。

### 16.3 工作目录与环境要显式传递

subprocess可以指定cwd，让子进程从明确目录开始；也可以指定env，提供明确环境映射。若没有这些参数，通常继承父进程相关状态。继承很方便，但也会让程序行为依赖你启动它的终端。当你需要复现实验时，应记录工作目录与影响结果的关键环境值，而不必公开所有可能敏感变量。

如果提供env字典，通常需要理解它是你交给子进程的环境，而不是自动只覆盖其中一项后保留所有其他项。常见写法先复制当前环境再覆盖少数课程字段，但这会继续传递其他已有值；对于不可信执行，需要按平台和程序需求建立更严格的允许列表。允许列表也不能随意删掉必需系统配置后再把启动失败归咎于程序。

## 第十七课：调度、内存与资源观察的基础模型

### 17.1 进程为什么会轮流获得CPU

一台机器上的可运行任务可能多于当前能够同时执行的硬件线程。操作系统调度器决定哪些任务何时运行，并在需要时切换。你看到多个程序似乎同时推进，不代表每个程序一直独占一个CPU核心。任务在运行、等待和再次就绪之间切换，是多任务系统的正常行为。

上下文切换需要保存和恢复相关执行状态，也可能影响缓存局部性，因此创建越来越多进程并不保证速度越来越快。若任务主要等待I/O，适量并发可以重叠等待；若任务已经把CPU用满，继续增加竞争可能只增加切换与内存压力。F11会通过具体任务比较并发模型，此处先建立资源有限的直觉。

程序墙钟时间包含排队、等待和实际执行。CPU时间更接近处理器为任务执行所花的累计时间，多线程程序的累计CPU时间还可能与单一墙钟时间呈现不同关系。报告性能时必须写清指标定义，不能把某工具显示的时间直接当成另一层的延迟。你后来测量模型吞吐与首token延迟时，会反复用到这种区分。

### 17.2 虚拟内存大小与实际常驻内存

虚拟地址范围描述进程可以使用的地址空间布局，不等于每个地址都已经对应一块实际常驻物理内存。常驻内存、共享页面、内存映射与文件缓存等概念会使不同工具的数字看起来不一致。初学时不要把进程表里最大的一个内存字段直接称为“它独占的真实内存”。

同一共享库或映射文件的页面可能被多个进程共享，简单把每个进程的常驻数字相加可能重复计算。另一方面，一个进程申请内存成功，也不必然保证未来所有访问都不受系统压力影响。发生内存不足时，系统或资源管理层可能采取限制或终止措施，应用需要正确处理失败并保存必要证据。

模型实验尤其容易把CPU内存、GPU显存、磁盘缓存和权重文件大小混在一起。它们属于不同资源。文件在磁盘上有若干字节，不代表加载后的每个张量、临时缓冲和缓存只占同样大小；量化和数据类型转换还会改变布局。基础学习先学会给每个数字标注资源类别与统计口径，再进入容量公式。

### 17.3 文件描述符也会耗尽

进程能同时打开的文件或套接字数量受到限制。忘记关闭文件、反复创建连接或让子进程继承不需要的描述符，可能最终出现“打开文件太多”之类错误。这个问题与磁盘是否还有空间无关：一个资源是存储容量，另一个是打开对象的管理额度。

上下文管理器可以让正常与异常路径都释放文件对象，但并不替代对对象生命周期的设计。若你把所有打开的文件存进全局列表，直到程序结束都不关闭，即使每个文件很小，也可能耗尽描述符。批量处理通常应限制同时打开的数量，处理完及时关闭，而不是一开始把全部输入都打开。

## 第十八课：权限诊断的三个逐层案例

### 18.1 文件可读却无法读取

设目标文件本身允许当前用户读取，但它位于一个当前用户不可穿过的父目录中。路径解析在到达文件前就可能失败。诊断时应把路径拆成每一级目录，逐层确认搜索能力，而不是只对最终文件执行长格式列表后宣布权限正常。若连父目录内容都不能列出，也需要区分缺少列举与缺少穿过能力。

合理修复应考虑目录设计是否正确。也许文件本来就不应该放在那里，也许应由拥有者将需要共享的文件放到适当共享目录，而不是把整个个人目录开放。最小权限不是只改最后三位数字，而是让存储位置和访问关系符合业务。

### 18.2 源码能被解释器运行却不能直接执行

通过Python读取源码时，解释器需要读取脚本文本；直接执行脚本还需要相应执行权限，并依据shebang找到解释器。若shebang指向不存在的位置，或文件换行形式导致解释器路径被错误解析，直接执行可能失败，而显式调用Python仍可成功。两种入口不同，所以观察结果并不矛盾。

解决时先决定你希望支持哪种入口。课程统一使用显式Python模块命令，可以减少shebang与执行位带来的初学混淆。若你要发布独立CLI，再按目标平台处理安装入口与可执行权限，而不是只在自己机器上加一次执行位就假设所有平台都一致。

### 18.3 管理员运行后普通用户无法写结果

假设你曾用高权限运行学习脚本，结果目录中的文件归高权限身份所有。之后普通用户重跑，可能无法覆盖这些文件。此时真正问题是文件所有权与运行身份不一致，不应继续把每次运行都升级为高权限。先确认哪些文件由自己的误操作产生，再按机器规范恢复正确所有权或重新在个人目录创建结果。

这个案例说明，提升权限可能把一次临时成功变成长期环境问题。对课程代码，优先使用个人可写目录、虚拟环境和明确的输出位置，能让权限错误保持局部、可解释和可恢复。共享服务器上涉及系统级对象时，应遵循已有管理流程，而不是把教材练习变成全局配置修改。

### 18.4 区分应用限制与系统限制

一个服务自己声明最多处理两个请求，是应用层并发规则；操作系统限制进程可使用的内存，是系统资源规则；调度平台把任务放进受限资源组，又是另一层管理。它们可以配合，但不会自动互相等价。应用写了并发上限，不代表子进程不能继续创建线程；设置了某个设备可见性变量，也不代表进程在所有接口下都失去其他设备权限。

当你遇到资源不足，应先确定限制来自哪一层。应用可能主动拒绝任务并返回明确错误，运行库可能分配失败，系统可能终止进程，容器管理器可能报告被资源规则处理。这些情况的日志位置与恢复方式不同。只看到进程消失就断言“代码有异常”会漏掉系统层证据；只看到应用报内存不足就立即扩大系统额度，也可能掩盖程序无限缓存的逻辑错误。

对自己的实验建立一张结果表：启动是否成功、开始和结束时间、退出状态、关键输出、是否观察到超时、预期文件是否完整、是否仍有自己创建的后代。表中每项都对应一个实际观察，不用“应该已经结束”替代检查。重复执行时保留本次运行身份，避免把上一次残留文件误当成本次成功产物。

在进一步开发执行工具时，可以把运行身份加入输出文件名或报告字段，再要求结果必须属于当前运行。这样即使某次任务在写新结果前失败，旧报告也不会被误读成新任务成功。这个小设计把进程生命周期与文件生命周期连接起来，也是后续评测系统和Agent执行账本的基础。

为这个运行身份设计一个反例测试：先留下旧结果，再让新运行在输出前失败，检查调用者是否拒绝把旧结果算作本次成功。恢复正常运行后，报告身份应与当前任务一致。这个测试验证业务完成与进程退出之间的连接，而不仅是检查文件是否存在。

## 第十九课：把权限与进程知识接到后续工程

Agent 工具执行器需要知道调用是否真的启动、是否完成、是否产生副作用，以及超时后是否仍有后代占用资源。推理服务需要知道进程在何处运行、使用哪份环境、打开哪些端口与文件。GPU 算子实验也依赖解释器、设备可见性和正确的运行身份。基础系统知识不是这些领域之外的额外负担，而是解释它们实际行为的底座。

本章完成标准是能对自己的一个外部任务建立清晰执行合同，并在失败时按启动、权限、运行、退出和业务验收逐层定位。你不需要现在成为系统管理员，但必须避免以最高权限和批量终止掩盖不理解的问题。下一章将把进程之间的联系扩展到网络，解释地址、端口、连接与协议。
