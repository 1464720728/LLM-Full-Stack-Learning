# F01 从打开电脑到第一个可解释的程序

本章从零建立一个最重要的能力：知道自己正在让哪台机器上的哪个程序，以什么身份、在什么目录、使用什么输入执行什么任务。你以后会同时接触 Windows、WSL、SSH、Docker、Python 虚拟环境、模型服务与 GPU。如果这一层没有分清，后面遇到错误时就只能不断换命令碰运气。本章把这些看似相似的窗口和路径拆开，并带你完成可重复的第一次学习。

本章只需要普通 CPU。无需先配置 CUDA、下载模型权重或开通 API。你拥有的高性能设备会在相应课程发挥作用，但基础环境练习的重点是观察和解释，不是计算规模。

## 第一课：先认识计算机中的几层角色

### 1.1 硬件、操作系统、程序、进程

硬件包括处理器、内存、磁盘和网络设备等。处理器执行机器指令，内存保存正在使用的数据，磁盘提供通常能跨重启保留的存储。GPU 也是处理器的一种，擅长某些大规模并行计算，但它不会替代操作系统管理文件、用户和普通命令。你运行一个简单 Python 脚本时，即使电脑装有很强的 GPU，脚本也可能完全没有使用它。

操作系统管理硬件资源，并向程序提供文件、进程、网络和权限等接口。Windows 与 Linux 是不同操作系统环境，命令、路径规则、可执行文件格式和系统库可能不同。因此“我在电脑上装了 Python”必须进一步说明安装到哪个操作系统环境中。Windows 中的 Python 与 WSL Linux 中的 Python 通常不是同一个解释器，也不会自动共享所有依赖包。

程序是可执行代码及相关资源的集合。进程是程序正在运行的一次实例。磁盘上的 Python 可执行文件可以被启动多次，形成多个进程；这些进程一般有各自的运行状态。你关闭一个终端里的 Python，不会因此删除磁盘上的解释器。反过来，文件仍在磁盘上也不意味着某个先前运行的进程仍然存在。

这几层可以用一个小例子贯穿：你在终端输入运行教材实验的命令；Shell 找到 Python 可执行文件；操作系统创建或替换相应进程；Python 进程读取源码和依赖；CPU 执行相应指令；程序通过操作系统把文本写到终端。任何一层出现问题，症状都可能只是屏幕上显示“失败”，所以我们需要学会识别失败发生在哪一层。

### 1.2 终端与 Shell 不是同一个东西

终端是处理文字输入输出的界面。Shell 是解释命令、启动程序、管理管道和变量等的软件。Windows Terminal 可以同时打开 PowerShell、命令提示符和 WSL 的 Bash 标签页；同一个终端外观并不保证内部运行同一种 Shell。看到相似的黑色窗口，不能就把 Linux 命令直接粘到 PowerShell。

Shell 提示符通常显示一些辅助信息，例如用户名、机器名和当前目录，但这些显示内容可以被自定义。提示符不是可靠的唯一证据。判断位置应运行实际查询命令，例如 Linux 的 `pwd`、`hostname`、`whoami`，或 PowerShell 的 `Get-Location`。你需要把显示线索和程序查询结果结合，而不是仅凭颜色或窗口标题判断环境。

教材代码块一般不包含提示符符号。若资料写成 `$ python demo.py`，开头的美元符号常表示“这是一条 Shell 命令”，不是必须一起输入的字符。类似地，`>>>` 常表示 Python 交互解释器提示符。将这些提示符原样粘入另一种解释环境，可能造成语法错误。复制命令前，先确认代码块使用的是哪种语言或 Shell。

### 1.3 编辑器与解释器也有不同职责

编辑器用于修改文本，解释器用于执行代码。一个文件在编辑器里看起来没有红线，不保证运行正确；编辑器也可能使用与终端不同的 Python 环境。如果编辑器能够识别 NumPy，而终端提示找不到 NumPy，首先核对两个地方选择的解释器，而不是反复重装同一个包。

文件扩展名 `.py` 提示这是 Python 源代码，但扩展名不会神奇地让任何文本都变成合法程序。Python 仍会检查缩进、括号、名称和语法。保存文件时还应注意是否真的保存到你计划运行的路径。有些编辑器中的未保存标签页只是临时内容；终端执行磁盘上的旧文件，就会出现“我明明改了代码，结果怎么没变化”的现象。

## 第二课：为当前执行建立五项身份记录

本课程建议每次遇到陌生环境时，先记录机器、用户、Shell、当前目录和解释器。它们看起来像环境杂事，却直接决定命令的实际含义。机器不同，看到的磁盘和网络不同；用户不同，权限和主目录不同；Shell 不同，变量与引号语法不同；目录不同，相对路径指向不同位置；解释器不同，可用依赖和语言行为可能不同。

Linux 或 WSL 中可以逐条执行：

```bash
hostname
whoami
pwd
printf '%s\n' "$SHELL"
python3 -c 'import sys; print(sys.executable); print(sys.version)'
```

前三条分别查询机器名、当前用户与当前工作目录。第四条展示环境变量 SHELL 的值，但它不一定等于此刻正在运行的全部 Shell 状态，所以应将它当作线索，而非绝对证明。最后一条启动 Python，并让 Python 自己报告可执行文件位置与版本，这比凭命令名称猜测解释器可靠。

PowerShell 中可以先使用：

```powershell
hostname
whoami
Get-Location
$PSVersionTable.PSVersion
py -3 -c "import sys; print(sys.executable); print(sys.version)"
```

这里的变量语法与 Bash 不同。最后一条使用 Windows 的 Python 启动器选择 Python 3；如果你的安装没有提供 `py`，应检查 `python --version` 并使用实际存在的命令，而不是假定所有机器都完全一样。课程要求的是知道自己选择了哪个解释器，不是强迫每个人的可执行文件名称相同。

把输出复制到自己的实验记录中时，应避免公开包含公司主机名、内部路径或用户信息的完整记录。你可以在个人记录保留真实值，在公开求助材料中用结构一致的占位内容替换。这不影响学习，因为真正重要的是相互关系：当前目录属于哪台机器，解释器属于哪个环境，命令是否从同一个根目录执行。

## 第三课：分清 Windows、WSL 与远端 Linux

### 3.1 Windows 本机视角

Windows 原生 Python 运行在 Windows 进程环境中，通常使用盘符路径，例如某个用户目录下的工程。它适合完成本课程的标准库、NumPy、Agent 与检索等许多 CPU 实验。你不必因为后续课程涉及 Linux，就认为现在所有操作都必须先搬到服务器。

Windows 文件系统路径与 Linux 路径并不是简单地把斜杠方向换一下。盘符、大小写规则、权限模型、符号链接和可执行文件形式都可能不同。Python 的 pathlib 可以帮助写可移植路径代码，但不能抹去所有系统差异。课程会尽量让核心实验跨平台，而涉及权限位、信号和 Shell 管道的练习需要使用明确的 Linux 环境。

### 3.2 WSL 视角

WSL 让你在 Windows 中运行 Linux 环境。对学习者最直接的好处是：仍使用熟悉的 Windows 桌面编辑和浏览资料，同时能在 Linux 终端学习路径、权限、进程与工具。你应把 WSL 当作一个需要单独识别用户、目录和依赖的 Linux 环境，而不是“Windows 终端换了一个皮肤”。

Windows 文件可以通过挂载路径被 WSL 访问，但不意味着每种访问方式都有相同的性能和权限表现。初学时，把 Linux 工程副本放在 WSL 自己的用户目录，能减少跨文件系统引起的混淆。Windows 与 WSL 可以分别拥有自己的工程副本和虚拟环境；不要把一个环境创建的 `.venv` 直接复制给另一个环境使用。

### 3.3 SSH 远端视角

SSH 登录远端服务器后，你输入的命令主要在远端执行，当前目录也属于远端文件系统。你本机桌面的某个文件不会自动出现在服务器上，服务器上写出的结果也不会自动下载到桌面。SSH 提供的是远端会话与相关传输能力，不是把所有文件系统无条件合并。

最常见的误解是：在本机安装了一个包，以为远端也能导入；或者在远端运行脚本，却把本机路径作为参数。排查这种问题时，重新执行五项身份检查即可快速定位。不要因为终端窗口仍显示在自己的电脑屏幕上，就认为程序一定在自己的电脑上运行。

这三种环境可以同时存在。你可以在 Windows 编辑资料，在 WSL 学 Linux，在公司服务器 CPU 上运行服务练习，之后再按需要使用 H100。每次跨环境时，重新确认机器、目录、解释器与输入数据，能避免大量看似随机的问题。

## 第四课：安装与验证的正确顺序

### 4.1 先发现已有工具，再决定安装什么

面对一台机器，不应立刻复制一长串安装命令。先查询是否已有 Python 和 Git，记录版本及路径。共享服务器可能已经维护了可用环境；重复安装系统级软件可能引入冲突，也可能超出你的权限。发现现有工具并理解它们，比盲目追求“最新版本”更适合作为第一步。

```bash
python3 --version
git --version
```

这两条命令只报告版本，不会证明所有依赖都存在，也不会证明你已经位于正确目录。它们只是环境证据的一部分。若 Shell 提示找不到命令，可能是软件未安装，也可能是可执行文件目录不在 PATH 中。F04 会讲 PATH 的搜索机制；现在先避免把两种情况当成同一个问题。

Windows 与 WSL 安装步骤应以官方说明为准。本仓库的 [第一次学习](../../docs/START_HERE.md) 提供两条完整起步路线，并链接 Python、Git 与 Microsoft 的原始文档。安装方式会随系统和软件版本变化，因此本章重点建立验证方法，不能仅凭安装器成功结束就断言终端实际使用了预期版本。

### 4.2 先取得仓库并进入工程根目录

Git 仓库保存源文件及其版本历史。本章只使用最基本的克隆操作，Git 对象、分支和冲突将在 F12 详细展开。克隆的意义是把远端工程的一份工作副本放到本地，你随后可以阅读、运行、修改并通过版本差异看清自己的变化。

```bash
git clone https://github.com/1464720728/LLM-Full-Stack-Learning.git
cd LLM-Full-Stack-Learning
```

克隆会在当前目录下创建工程目录，所以执行前先用 pwd 或 Get-Location 确认位置。不要把工程克隆到需要管理员权限的系统目录，也不要随意覆盖已经存在且包含自己学习修改的同名目录。若目录已存在，先判断它是不是已有副本，而不是重复克隆后迷失在多个几乎相同的文件夹中。

确认当前目录里能看到 `requirements-cpu.txt` 后再进行下一小节。Linux 可用 `pwd` 和 `ls requirements-cpu.txt`；PowerShell 可用 `Get-Location` 和 `Get-Item requirements-cpu.txt`。若已有课程副本，进入那个副本即可，不要重复克隆。

### 4.3 为什么先建立虚拟环境

Python 虚拟环境用于把一个工程的解释器入口和依赖安装位置与其他工程区分开。它不是完整虚拟机，也不会自动隔离文件、网络或系统权限。激活虚拟环境主要影响当前 Shell 的命令搜索路径等状态，使 `python` 与 `pip` 更容易指向该环境。

不同工程可能需要不同版本的依赖。如果所有包都装进一个共享环境，升级某个包可能让另一个工程失效。独立环境把这种相互影响缩小到工程范围，也方便记录和重建。不过虚拟环境本身通常不适合作为跨操作系统、跨位置搬运的交付物；更可靠的做法是保留源码和依赖声明，在目标环境重新创建。

Linux 路线：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -c 'import sys; print(sys.executable)'
python -m pip install -r requirements-cpu.txt
```

第一条让所选 Python 运行标准库 venv 模块，创建 `.venv` 目录。第二条在当前 Shell 读取激活脚本。第三条立即验证实际解释器位置，避免只相信提示符前面的环境名称。第四条让同一个 Python 运行 pip，把课程依赖装到这个环境中。

Windows 可以直接调用环境内的可执行文件，而不修改 PowerShell 脚本策略：

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-cpu.txt
.\.venv\Scripts\python.exe -c "import sys; print(sys.executable)"
```

明确路径的写法稍长，却能减少“激活是否成功”的疑问。安装依赖会联网，这是准备环境的动作；后面的课程离线实验本身不因此变成联网实验。要分清依赖获取、程序运行、模型 API 调用三个不同阶段。

### 4.4 为什么强调 python -m pip

单独输入 pip 时，Shell 会按搜索路径寻找一个叫 pip 的程序，它可能属于另一个 Python 安装。`python -m pip` 则让当前选定解释器运行它能找到的 pip 模块，更容易保证安装目标与运行目标一致。它不是任何情况下都能自动修复环境，但能消除一个非常常见的不一致来源。

验证依赖时应使用同一个解释器进行导入。例如安装 NumPy 后执行 `python -c "import numpy; print(numpy.__version__)"`。如果仍失败，检查 sys.executable、安装输出和当前环境；不要马上加 sudo 把包安装到系统 Python，因为那可能只是制造第二个与当前运行无关的安装位置。

## 第五课：认识已经取得的工程目录

工程根目录是包含 README、books、labs、tests、tools 等项目的目录。教材通常要求从这里运行命令，因为 Python 的模块查找和相对文件路径与执行位置有关。进入某个 labs 子目录后再运行同样的顶层模块命令，可能找不到包。这个失败并不代表源码丢失，而是你改变了执行上下文。

| 目录 | 保存的内容 | 初学时怎样使用 |
|---|---|---|
| books | 教材正文与工作簿 | 按先修顺序阅读，跟随例子记录状态 |
| labs | 完整参考实验 | 自己尝试后逐段比较，不把运行成功等同掌握 |
| tests | 自动验收代码 | 查看哪些合同与边界被实际检查 |
| practice | 空白实现题与评分器 | 在个人练习副本中补代码并获得反馈 |
| projects | 跨卷综合工程 | 基础机制掌握后组合成较完整系统 |
| tools | 导航、检查、进度工具 | 查找当前课程和记录学习证据 |

这些目录是教学工程的组织方式，不是 Python 或 Git 强制要求所有项目采用的标准。以后阅读真实框架时，会遇到 src、examples、benchmarks 等不同布局。判断目录责任，应结合 README、入口和调用关系，而不是死记某个文件夹名字一定代表某种组件。

## 第六课：解释一条命令的每个部分

```bash
python -m labs.foundations.environment
```

`python` 是希望 Shell 启动的程序名称。`-m` 是传给 Python 的选项，要求按模块名称运行模块。后面的点分名称表示包与模块路径，而不是普通文件名字符串。Shell 先决定怎样把这一行分成参数并找到 python；Python 再解释 `-m` 与模块名。两层解析各有规则，不能把所有错误都归为 Python 语法问题。

为什么使用模块方式而不是直接执行某个深层文件？模块方式能使包内导入按照工程结构运行，通常更适合教学仓库的组织。直接执行文件也有用途，但它对模块搜索路径与包上下文的影响可能不同。F07 会解释这些区别；现在先按照教材指定方式从仓库根目录运行，不要为了绕过一次错误随意改成另一种入口。

命令执行后，可以观察标准输出、标准错误和退出状态。标准输出常用于正常结果，标准错误常用于诊断，退出状态供其他程序判断成功或失败。终端可能把两种文本都展示在同一个窗口，所以仅凭颜色或排列不能判断它来自哪个流。F03 会通过重定向把它们分开观察。

命令完成并回到提示符，表示这个前台程序已经结束，不一定表示成功。如果程序抛异常后退出，也会回到提示符。要结合输出与退出码判断。反过来，一个服务程序可能一直运行并等待请求，不返回提示符并不一定是卡住。你需要先知道程序预期是一次性任务还是长期服务。

## 第七课：第一次完整实验应该怎样做

先运行课程环境实验。它会展示与解释器、平台、目录和可选工具相关的观察信息。不要只把输出截图保存；请逐项写下自己认为它表示什么，以及它能证明什么、不能证明什么。例如发现系统存在 nvidia-smi 可执行文件，不等于你已经证明某个 GPU 计算成功；发现某包可以被导入，也不等于这个包的所有后端都可用。

接着运行一个更小的路径或数值实验。执行前先写预测，哪怕预测不确定。例如你预计程序会输出当前工作目录还是源码文件所在目录？运行后比较差异，回到代码定位它调用了哪个查询。这样做是为了把“看过输出”变成“理解输出与代码之间的因果关系”。

```bash
python -m labs.foundations.paths
python -m labs.foundations.python_values
```

第三步只改变一个条件。可以改变输入列表中的一个值、改变当前目录、或者明确换用另一个解释器。每次只改一个因素，更容易知道结果变化由什么引起。如果同时换 Python、换目录、改源码、升级依赖，之后即使成功，也难以解释是哪一步解决了问题。

第四步主动制造一个可恢复的小错误。比如把模块名拼错一个字母，观察 ModuleNotFoundError 与 Shell 的“找不到命令”有什么区别。然后恢复拼写，再运行。错误不是学习中的意外噪声，它能帮助你辨认系统边界。关键是把实验限制在自己的副本和目录中，并记录怎样恢复。

第五步关闭终端，重新打开，从头独立完成进入目录、选择解释器、运行实验的过程。这一步能揭露你是否依赖之前遗留的激活状态或临时变量。如果第二次做不出来，不要把它解释成自己记性不好；应把缺失步骤补进操作记录，直到流程可复现。

## 第八课：怎样读取错误而不被长堆栈吓住

### 8.1 先判断错误来自哪一层

Shell 报“command not found”时，程序通常还没被成功启动，应检查命令名和搜索路径。Python 报 SyntaxError 时，解释器已经启动并读到源码，但解析失败。ModuleNotFoundError 表示某次导入找不到模块，可能与环境、包安装或执行目录有关。FileNotFoundError 表示程序运行到了文件操作，而目标路径未按预期找到。

这些名字不是需要死背的英文单词表，而是排查顺序的证据。若解释器根本没启动，修改 Python 函数内部逻辑没有帮助；若解释器已运行到数据库打开阶段，重复安装 Git 也没有关系。先定位层，再选择相关检查，能大幅减少随机尝试。

### 8.2 traceback 应从哪里开始读

Python 堆栈通常显示调用经过的文件与行号，最后一行给出异常类型和简短信息。初学时先看最后一行确认错误类别，再从底部向上寻找属于你当前工程的最近调用位置，打开对应行，确认它实际收到什么输入。不要只复制最后三个英文单词给别人，因为错误位置和调用上下文通常同样重要。

一份有效求助记录应包含完整命令、当前目录、解释器版本与路径、完整异常文本、期望结果和最小复现输入。输入可能包含敏感信息时，制作结构相同的合成样例，而不是直接公开公司日志或密钥。一个小而完整的例子比巨大截图更容易被别人复现，也更容易帮助你自己看清错误。

### 8.3 区分未安装与装错环境

如果提示缺少 NumPy，先用当前解释器执行 `python -m pip show numpy`，再查看 sys.executable。电脑上“某处已经安装”不能保证当前解释器能找到它。若你在 Windows 安装包，却在 WSL 执行程序，两个环境的安装记录不自动互通；若你在系统 Python 安装，却用虚拟环境运行，也可能出现同样现象。

不要把修改系统权限作为通用修复。给目录设置宽松权限、用管理员账户重跑、关闭安全检查，可能让眼前症状消失，却掩盖了路径和环境选择错误。基础学习更应该保留普通用户环境，让错误明确暴露，再按原因修复。

## 第九课：怎样阅读一份陌生源码

第一遍不要从第一行读到最后一行试图理解全部细节。先找入口：命令启动哪个模块，模块最后是否有主入口，主入口调用什么函数。再找输入输出：输入来自参数、文件还是内置夹具；输出是返回值、打印文本、文件还是网络响应。接着追踪一份很小的数据，沿实际调用链观察它如何变化。

第二遍识别状态。哪些值只读，哪些容器会被修改，哪些对象在多次调用之间保留？同一个列表是否同时被历史、缓存和当前请求引用？函数是否读写外部文件？这种状态清单会帮助你理解很多“代码看着没问题，运行却串话”的错误。

第三遍读失败路径。未知输入时抛什么异常？资源不足时是否已经部分修改状态？取消发生时谁负责清理？初学者往往只读正常路径，觉得“这一段就是读文件然后返回”，却没有看到文件不存在、编码错误或读到一半失败时的行为。可靠工程能力来自对正常与失败两类路径同时有解释。

第四遍再回到具体语法。遇到不熟悉的推导式、生成器或上下文管理器，可以先把它展开成普通循环和显式步骤，再比较语义。不要因为一个表达式很短就认为它简单；也不要因为一个函数很长就认为它一定复杂。判断复杂度要看它维护多少状态、承担多少责任和依赖多少隐含前提。

## 第十课：建立自己的学习记录，而不是只收藏答案

一份有用的实验记录至少包括问题、预测、命令、观察、解释与下一步。问题说明你想验证什么；预测使你暴露当前理解；命令与环境使别人能够复现；观察记录真实结果；解释把结果与机制联系起来；下一步指出尚未验证的边界。这个格式不需要很长，但每一栏都应该有具体内容。

例如研究相对路径，可以写：“我预测程序读取的是运行目录下的 data.txt；从另一个目录启动后实际报文件不存在；源码使用普通相对路径而非 __file__ 构造路径；因此路径相对于进程当前目录解析；下一步比较基于源码位置的路径写法。”这段记录比“路径学完了”更能说明你掌握了什么。

学习状态也应有层次。阅读表示你接触过内容；实践表示你运行并修改过；掌握表示你能在没有答案的情况下完成验收并解释失败。自动测试通过只能说明代码对这些检查给出预期行为，不能自动证明代码是你独立完成的，也不能证明你知道为什么正确。

```bash
python tools/course.py record F01 --status practiced --evidence "能独立识别环境并重复运行首个实验"
python tools/course.py next
```

课程进度记录在个人本地目录中，不会因为教材更新就替你认定已经掌握。你可以把遗忘的章节改回阅读或实践状态。学习不是一次性打勾，而是不断提高可独立完成任务的范围。

## 第十一课：六个基础故障的诊断演练

**故障一：找不到 python 命令。** 先确认当前环境是 Windows 还是 Linux，再检查该环境安装的命令名称。Windows 可能提供 py 启动器，Linux 常用 python3。只有确认软件未安装后才按官方说明安装；若已经安装，检查终端是否需要重新打开以及 PATH 是否包含对应位置。验收是能说明最终运行的可执行文件路径，而不是仅仅换一个名称后碰巧成功。

**故障二：明明装了包却不能导入。** 比较安装时与运行时的 sys.executable，使用同一解释器执行 `-m pip` 和导入验证。若发现一个路径位于系统环境、另一个位于 `.venv`，就已找到关键差异。修复应对准目标环境，不必删除所有 Python 安装。

**故障三：修改代码没有效果。** 检查文件是否已保存，终端运行的是否为同一个副本，当前目录是否指向另一个克隆。临时在入口打印源码路径可以提供证据，确认后再去掉诊断输出。若涉及长驻服务，还要确认旧进程是否仍运行并使用旧代码；仅修改磁盘文件不一定自动更新已运行进程。

**故障四：模块存在却报找不到。** 回到仓库根目录，用教材指定的 `python -m` 命令执行。检查是否误把目录名拼错、是否进入了子目录、是否使用了另一个工程副本。不要首先给 sys.path 加一串绝对路径，因为那会让问题依赖你当前机器的布局，掩盖原本应当修正的入口。

**故障五：程序一直不退出。** 先看它是否预期为服务或交互程序。若是一次性实验，检查是否等待输入、等待网络或进入无限循环。使用中断前先理解可能的副作用，避免以为停止显示就等于所有子进程和外部操作都被撤销。进程与信号将在 F04 展开。

**故障六：同一命令在两个终端结果不同。** 比较五项身份记录，再比较环境变量、源码版本和输入文件。两个终端可能分别激活不同环境，也可能处于不同机器或目录。把差异逐项列出后，一次只统一一个条件，直到找到导致结果变化的因素。

## 第十二课：十二道练习与参考答案

### 题一：给一次执行画出职责链

用自己的话解释终端、Shell、Python、操作系统各做什么。参考答案：终端处理文字交互；Shell 解析命令并启动程序；Python 解释并执行 Python 代码；操作系统提供进程、文件、网络和资源管理。答案若把“终端执行所有代码”作为唯一解释，说明还没有区分界面与执行程序。

### 题二：识别三种机器视角

在 Windows、WSL 和 SSH 终端分别记录机器、用户、目录和解释器。参考判断不是要求三个输出必须不同，而是能解释哪些状态独立、哪些资源可能通过挂载或网络共享。即使机器名碰巧相同，也不能据此认定环境相同，应结合路径和解释器位置。

### 题三：解释关闭终端后什么会保留

参考答案：保存到磁盘的源码通常保留；当前 Shell 的临时变量和激活状态通常不会自动出现在新会话；普通前台进程可能随会话结束受到影响；远端长期任务是否保留取决于启动与会话管理方式。不能把“窗口关了”简单等同于“所有文件与程序都删了”。

### 题四：创建并验证独立环境

在工程目录创建 `.venv`，不用猜测而是通过 sys.executable 证明选择正确。完整命令见第四课。验收还包括关闭终端后再次通过激活或明确可执行路径恢复使用同一环境。仅看到提示符带括号不算完成，因为提示符可以被自定义。

### 题五：区分两种找不到

故意把 Python 命令名和模块名各拼错一次。参考答案：前者通常由 Shell 报告无法找到程序，后者由已经启动的 Python 报告模块导入失败。两者发生在不同层，所以修复对象不同。恢复后再次运行正常命令，证明错误制造与恢复过程均可控。

### 题六：确定真实源码副本

若电脑有两个同名工程目录，设计一个不修改业务逻辑的方法确认当前运行哪份。参考方法是打印模块的 `__file__` 或查看当前目录与调用入口，并与编辑器打开路径比较。完成后移除临时输出，避免污染原有机器可读输出合同。

### 题七：解释依赖安装的目标

说明 `python -m pip install ...` 与直接 pip 的差别。参考答案是前者让已选解释器运行其环境中的 pip，后者由 Shell 独立寻找 pip 程序，可能指向不同环境。不能把前者神化为“一定不会有依赖冲突”，它只是减少解释器选择不一致的一类问题。

### 题八：把一个错误缩小成最小复现

从任何一次模块或路径错误中，保留能够稳定复现的最少命令与文件。参考提交应包含当前目录、解释器路径、完整命令、最小输入和异常，而不是一整个个人工程压缩包。最小化过程中若错误消失，应继续寻找被移除的哪个条件是必要原因。

### 题九：读懂一次正常输出

运行环境实验，任选三项输出，分别写出它能证明与不能证明的结论。参考例子：解释器路径能证明当前进程使用的 Python 位置，不能证明另一个终端也使用相同解释器；包版本能证明当前环境安装的版本，不能证明 GPU 后端已成功运行。

### 题十：为第一个实验写完整记录

参考记录结构为“假设—输入—命令—观察—解释—下一例”。验收要求至少一项预测在运行前写出，至少一次主动修改输入，至少解释一个结果变化。复制程序输出而没有自己的推理，不满足本题目标。

### 题十一：跨终端恢复

关闭当前终端，重新进入工程，选择环境，运行两个基础实验。参考成功条件是无需依赖旧终端中的临时状态，且能解释每个恢复步骤。若需要查看笔记，可以查看；本题检验操作可复现，不是要求背下所有命令字符。

### 题十二：制定首周小目标

把“学会 LLM”拆成三个本周可验收任务。参考例子是独立识别执行环境、解释相对路径、写一个有输入输出的小函数。每项都应有可执行证据与失败边界。不要把“看完多少页”作为唯一指标，因为页数不能直接证明理解或操作能力。

本章结束时，你应能在任何一个新终端里快速建立执行身份，找到工程根目录，选择正确解释器，运行一个离线模块，读出失败发生在哪一层，并把流程重复一次。你不必已经理解每个系统内部实现，但不能再把所有窗口、路径和环境混成一个没有边界的“我的电脑”。
