# F07 模块、对象、迭代器与接口：读懂工程里的 Python

> 先修 F06。实验：`python -m labs.foundations.objects`、`python -m labs.foundations.iterators`。目标是读懂真实项目中常见的 `self.step()`、dataclass、生成器和包内导入。

## 1. 从一个文件到一个包

一个 `.py` 文件通常构成一个模块，模块给变量、函数和类提供命名空间。`from .functions import batches` 表示从同一个包里的 functions 模块导入 batches。相对导入依赖包上下文，所以本课程统一从仓库根目录运行 `python -m labs.foundations.cli`，而不是直接运行深层文件路径。

`-m` 让 Python 以模块方式定位并执行目标，保留正确的包关系。直接执行 `python labs/foundations/cli.py` 时，解释器可能不知道这个文件所属包，从而使相对导入失败。不要用到处修改 `sys.path` 的方式掩盖包结构问题；先理解执行入口。

```python
if __name__ == "__main__":
    main()
```

这段判断让模块被导入时只提供定义，被当入口执行时才运行演示。导入模块时无条件发API请求、加载大模型或开启服务，会使测试与复用都很困难。模块顶层应尽量避免昂贵副作用。

## 2. 类把状态与合法操作放在一起

函数适合无状态变换，对象适合拥有长期状态和规则。例如 Budget 拥有 limit 与 used，consume 是修改它的操作。`budget.consume(3)` 可以近似理解为 `Budget.consume(budget,3)`；`self` 是当前实例的约定参数名，不是魔法全局变量。

所以 `self.step()` 表示在当前对象上查找 step 方法并调用。要知道 step 在哪里定义，需要查看当前类、继承的父类或其他属性绑定，不能仅凭名字推测它来自某个库。读真实 Agent 时，先找到对象的构造位置和类定义，再沿继承关系追踪。

`@dataclass` 根据字段定义生成常见方法，如初始化和表示。它减少重复代码，不改变“实例是有状态对象”的本质。`field(default=0, init=False)` 让 used 初始化为0，但不成为外部构造参数。`__post_init__` 在生成的初始化之后检查 limit。

## 3. 不变量比“面向对象术语”更重要

Budget 的不变量是 `0 <= used <= limit`。consume 先检查 amount 类型和范围，再判断剩余额度，最后才修改 used。若先修改再发现超额抛错，异常发生后对象可能已经处于坏状态。

手算 limit=10，依次 consume(3)、consume(4)，used=7，remaining=3。再 consume(4) 应抛错且 used仍为7。测试专门验证“失败不改变已提交状态”。这也是数据库事务、Agent预算扣费和KV分配器的重要设计思路。

property 让 `budget.remaining` 看起来像属性，但每次访问都会根据 limit-used 计算。它不是自动缓存。把一个很昂贵、有副作用的过程隐藏在 property 内会让读者误判代价，因此本例只做简单计算。

## 4. 组合与继承怎么选择

若一个 Agent 拥有 model client、memory store、tool registry，它们通常可以作为独立对象组合进 Agent，而不必让 Agent 继承“模型、内存、工具”三个父类。组合表达“有一个”；继承更适合表达可替换的“是一种”，且子类应保持父类合同。

接口可以先从普通 Python 约定开始：只要对象有 `generate(messages)` 方法，调用方就能使用。后续可以用 Protocol 描述结构化接口，便于静态检查。不要一上来给每个类都写三层抽象基类；抽象应来自真实替换需求。

一个小练习接口：给日志项目注入 `writer.write(report)`，分别实现终端writer和文件writer。统计逻辑不需要知道报告最后写到哪里，这叫把业务逻辑与外部副作用隔开。你以后替换真实模型为假模型做测试，原理相同。

## 5. 迭代器：不是所有输入都应该先变成列表

可迭代对象能提供迭代器，迭代器维护“读到哪里”的状态。`iter(x)` 获得迭代器，`next(it)` 取下一项，结束时抛 StopIteration。for 循环替你处理这个协议。

生成器函数含有 yield。调用它时不会立刻执行整个函数，而是返回生成器；每次 next 执行到下一个 yield 并暂停，保留局部状态。实验 source 产生0²到6²，分成 `[[0,1,4],[9,16,25],[36]]`；消费后再 `list(source)` 得到空列表，因为同一个生成器已经耗尽。

```python
source = (i * i for i in range(7))
chunks = stream_batches(source, 3)
first = next(chunks)
```

此时仅消费了前三项，不是把七项全部算完。这种惰性让你能逐行处理大日志和数据流，而不是把整个文件读入内存。

## 6. 惰性也改变了错误出现的时间

生成器函数的参数校验可能到第一次迭代才执行。例如 `stream_batches(values,0)` 返回生成器后，看起来还没报错，调用 next 或转换list才触发检查。API使用者必须知道错误是在构造时还是消费时产生。

惰性不等于自动内存安全。若你最后调用 `list(generator)`，所有结果仍会驻留内存；若生成器把历史保存在列表里，它也可能越长越大。我们的 stream_batches 只保留当前批次，但下游如果保存每个批次，整体还是 O(n)。内存复杂度要看整条链路，而不是只看一个 yield。

生成器可以在 finally 中清理资源，但未耗尽生成器时的关闭时机需要注意。文件流通常用 with 明确生命周期；不要寄希望于垃圾回收恰好及时释放。

## 7. 装饰器与上下文管理器先认形状

装饰器 `@decorator` 是对被定义对象进行包装或转换的语法。它不是只用于“漂亮地写注释”。例如 `@dataclass` 根据类字段生成方法；后面 `@triton.jit` 会让函数进入另一套编译和调用路径，但二者语法相似并不代表行为相同。

上下文管理器 `with resource as x:` 在进入和退出作用域时执行协议，用于可靠释放文件、事务或锁。异常发生时也应触发退出处理。它解决的是生命周期，不是“让变量只活在缩进里”；Python 的 with 块通常不创建独立变量作用域。

读源码时看到陌生装饰器，首先查它的定义或文档：是否改变函数签名？是否缓存结果？是否把同步函数变成异步？是否在导入时注册？这一习惯会避免误读框架。

## 8. 七个练习与详细答案

**F07-1 追踪 self。** 把 `budget.consume(3)` 改写成显式类调用。答案 `Budget.consume(budget,3)`。再说明两个Budget实例为何不会共享used：used是实例字段。

**F07-2 异常后状态。** limit=5，consume(4)后尝试consume(2)。验收：异常后remaining仍为1；参考实现先验证后修改。

**F07-3 去掉主入口保护。** 解释导入模块时为什么会多打印输出。答案：模块顶层代码在导入时执行；将演示置于 main guard 内。

**F07-4 惰性证明。** 在输入生成器中记录已访问元素，取得第一个批次后检查记录。验收：size=3时只访问0、1、2。测试 `test_iterator_lazy` 展示了完整做法。

**F07-5 耗尽行为。** 对同一个生成器调用两次list。验收：第二次为空；若需要重跑，应重新创建生成器，或明确保存数据。

**F07-6 写一个有限重试迭代器。** 依次yield尝试编号0..max_attempts-1。要求max_attempts正整数，不能无限循环。答案核心是range与参数校验；后续Agent重试还需要错误分类和幂等性，不能只靠循环次数。

**F07-7 接口替换。** 写一个类拥有 `write(report)`，记录收到的报告；将它用于测试日志统计流程。验收：测试无需真实文件和终端。答案使用依赖注入，把可变外部行为传入，而不是在统计函数内部固定调用print。
