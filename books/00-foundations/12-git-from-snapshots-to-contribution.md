# F12 Git 从快照到源码修改：让每次学习都能回退和审阅

> 先修 F02、F06、F09。实验：`python -m labs.foundations.git_model`。真实Git操作只在自己的课程克隆或临时练习仓库进行。

## 1. Git记录的不是“当前文件夹的一切”

工作区是你正在编辑的文件，暂存区记录下一次提交准备包含的内容，提交是一个带父关系和元数据的快照。远端仓库是另一份仓库，不是你每次保存文件就自动同步的网盘。

`git add notes.txt` 把此时该文件的内容放入暂存区。之后继续修改文件，不会自动更新已暂存内容。`git commit` 记录暂存区，而不是无条件把工作区最新内容全部提交。实验先stage v1，再把工作区改成v2，提交得到的仍是v1。

| 观察命令 | 比较对象 |
|---|---|
| `git status --short` | 工作区、暂存区和HEAD的简要状态 |
| `git diff` | 工作区相对暂存区 |
| `git diff --staged` | 暂存区相对HEAD |
| `git show HEAD` | 最近提交的内容与元数据 |

这四个命令比盲目 `git add .` 更值得熟练掌握。提交前看暂存差异，能发现密钥、数据库、缓存或错误文件被加入。

## 2. 用一个小模型理解快照

`git_model.py` 用字典表示工作区和暂存区，用复制后的字典表示提交。它只模拟教学语义，不实现真实Git的blob/tree/commit格式，也不模拟完整增量、删除或合并。哈希使用SHA-256截断，仅用于观察相同内容对应稳定标识，不应称它为真实Git提交SHA。

为什么提交时 `dict(self.index)` 要复制？如果把可变index字典本身保存到commits，后续stage会改变过去提交，这违背历史快照应稳定的合同。这个例子把F06的别名知识和版本控制连接起来。

真实Git提交还包含父提交、作者、时间、提交信息和tree引用；两个相同文件快照的commit也可能因这些元数据不同而有不同ID。不要把“内容一样”直接等同“提交ID一样”。

## 3. 分支是指向提交的名字

分支不是把整个目录复制一份的文件夹。它是指向某个提交的引用，HEAD通常表示你当前附着的分支。新提交让当前分支指针向前移动，其他分支保持原处。

推荐学习流程：

```bash
git status --short
git switch -c study/f12-batching
# 修改自己的练习文件并运行测试
git diff
git add path/to/your/exercise.py
git diff --staged
git commit -m "Add tested batching exercise"
```

`path/to/your/exercise.py` 是占位路径，应替换为实际文件。不要为了复制命令创建一个叫path/to的假结构。提交信息写清改变的行为，方便未来定位“哪次修改引入了尾批丢失”。

切换分支前处理未提交修改：可以提交、明确暂存到stash，或在确认不需要后恢复。不要在不理解的情况下执行hard reset清空工作成果。

## 4. fetch、pull、push各做什么

fetch获取远端对象与引用更新，通常不直接合并进当前分支。pull是在获取后再按配置进行合并或变基等整合。push把本地对象和引用更新发送到远端；未提交的工作区修改不会随push自动上传。

两个分支有祖先关系时，推送某个分支会携带远端缺少而该分支需要的对象。因此你在A提交C，然后把C合入B，先push B，也可能把C对应的对象传到远端；但远端A分支名是否移动是另一个问题。对象是否存在和哪个分支名指向它，必须分开理解。

remote名如origin只是本地别名，不天然等于“官方仓库”。`git remote -v` 查看地址。学习开源项目时，fork远端和upstream远端通常需要明确区分，避免把提交推到错误目的地。

## 5. 合并冲突是信息冲突，不是系统坏了

两条分支修改同一段内容，Git无法自动决定最终结果时会标记冲突。解决冲突不是随便删掉标记，而是理解两个改动的语义，得到一个同时满足需求的版本，再运行测试。

例如A修复空输入，B优化批处理循环。若冲突解决只保留B，可能重新引入空输入错误。验收应包含两边各自的测试。你还应检查冲突范围以外的语义交互：文本没有冲突不代表行为一定兼容。

merge保留分支汇合关系；rebase把提交重放到新基底，通常改变提交ID。已经共享的历史不宜随意重写。这里不要求立即精通所有恢复命令，而是先养成“提交前审阅，合并后测试”的习惯。

## 6. .gitignore、秘密与大文件

`.gitignore`影响未跟踪文件的发现，不会自动把已经跟踪的文件移出历史。把API密钥提交过一次后再加ignore，旧提交中仍可能存在它；这不是“现在文件看不到了”就解决的问题。

课程仓库不应跟踪真实密钥、个人数据库、GPU缓存、大模型权重或公司数据。生成结果和下载数据应有明确目录与忽略规则，必要时用校验和与下载说明复现，而不是把所有产物塞进Git。

Git工作区大小、`.git`对象库大小和某次push传输量不同。一次push取决于远端已有对象和协商压缩；不能简单用`du -sh .`当作上传量。基础课程先理解边界，再学习更精确的对象统计和打包分析。

## 7. 阅读经典开源项目的第一步

在修改vLLM或SGLang前，你应能固定某个commit，记录环境，找到一个小测试并运行，然后只修改一个行为。第一项开源贡献不必是复杂算法：补一个能复现真实边界的测试、修正文档中可验证的命令、改进错误消息，都能训练工程闭环。

阅读顺序建议：README理解用途→安装/开发文档理解环境→测试目录理解合同→入口函数追一次输入→相关实现→历史提交理解设计。不要从仓库第一文件开始通读，也不要以“全部文件都看过”作为学习目标。

官方Pro Git可作为术语参考，课程练习仍以本仓库的小程序为对象，避免将阅读大书当成不动手的理由。

## 8. 七个练习与详细答案

**F12-1 暂存差异。** stage v1后再改成v2，分别查看diff与diff --staged。答案：工作区差异显示v1→v2，暂存差异显示HEAD→v1；commit保存v1。

**F12-2 分支图。** 从同一提交建立两个分支各提交一次，画出父关系。验收：知道分支名是引用，提交之间的父关系不因名字变化而变化。

**F12-3 未提交不会push。** 修改文件但不add/commit，解释push为什么不会上传该修改。答案：push传提交对象与引用，不传任意工作区状态。

**F12-4 合并验收。** 两分支分别修复空输入与尾批，合并后运行两套测试。验收：不仅无冲突标记，还满足两项行为。

**F12-5 忽略规则。** 新建`.practice`输出，确认不会出现在待提交清单。若已跟踪，说明ignore为何无效。答案：跟踪状态与忽略规则是不同机制，需要明确从索引移除并审阅变化。

**F12-6 版本证据。** 记录一个本地提交ID和测试命令，写入自己的学习记录。验收：他人能定位你修改的精确代码，不能只写“最新版”。

**F12-7 小PR说明。** 为一次batches边界修复写两句话：什么输入以前错、现在行为如何、如何验证。参考：输入长度非批次整数倍时尾部丢失；保留尾批并加入0..19长度的性质测试。不要写空泛“优化代码质量”。

## 掌握门槛

你能审阅将要提交的内容，理解本地与远端引用，能在分支上完成有测试的修改并解释差异。达到这里，后续真实框架源码实验就有可回退、可追踪的基础。
