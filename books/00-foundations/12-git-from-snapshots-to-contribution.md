# F12 Git 从快照到源码修改：让每次学习都能回退和审阅

> 先修 F02、F06、F09。实验：`python -m labs.foundations.git_model`。真实Git操作只在自己的课程克隆或临时练习仓库进行。

## 1. Git记录的不是“当前文件夹的一切”

工作区是你正在编辑的文件，暂存区记录下一次提交准备包含的内容，提交是一个带父关系和元数据的快照。远端仓库是另一份仓库，不是你每次保存文件就自动同步的网盘。

`git add notes.txt` 把此时该文件的内容放入暂存区。之后继续修改文件，不会自动更新已暂存内容。`git commit` 记录暂存区，而不是无条件把工作区最新内容全部提交。实验先stage v1，再把工作区改成v2，提交得到的仍是v1。

| 观察命令 | 比较对象 |
|---|---|
| `git status --short` | 工作区、暂存区和HEAD的简要状态 |
| `git diff` | 工作区相对暂存区 |
| `git diff --staged` | 暂存区相对HEAD |
| `git show HEAD` | 最近提交的内容与元数据 |

这四个命令比盲目 `git add .` 更值得熟练掌握。提交前看暂存差异，能发现密钥、数据库、缓存或错误文件被加入。

## 2. 用一个小模型理解快照

`git_model.py` 用字典表示工作区和暂存区，用复制后的字典表示提交。它只模拟教学语义，不实现真实Git的blob/tree/commit格式，也不模拟完整增量、删除或合并。哈希使用SHA-256截断，仅用于观察相同内容对应稳定标识，不应称它为真实Git提交SHA。

为什么提交时 `dict(self.index)` 要复制？如果把可变index字典本身保存到commits，后续stage会改变过去提交，这违背历史快照应稳定的合同。这个例子把F06的别名知识和版本控制连接起来。

真实Git提交还包含父提交、作者、时间、提交信息和tree引用；两个相同文件快照的commit也可能因这些元数据不同而有不同ID。不要把“内容一样”直接等同“提交ID一样”。

## 3. 分支是指向提交的名字

分支不是把整个目录复制一份的文件夹。它是指向某个提交的引用，HEAD通常表示你当前附着的分支。新提交让当前分支指针向前移动，其他分支保持原处。

推荐学习流程：

```bash
git status --short
git switch -c study/f12-batching
# 修改自己的练习文件并运行测试
git diff
git add path/to/your/exercise.py
git diff --staged
git commit -m "Add tested batching exercise"
```

`path/to/your/exercise.py` 是占位路径，应替换为实际文件。不要为了复制命令创建一个叫path/to的假结构。提交信息写清改变的行为，方便未来定位“哪次修改引入了尾批丢失”。

切换分支前处理未提交修改：可以提交、明确暂存到stash，或在确认不需要后恢复。不要在不理解的情况下执行hard reset清空工作成果。

## 4. fetch、pull、push各做什么

fetch获取远端对象与引用更新，通常不直接合并进当前分支。pull是在获取后再按配置进行合并或变基等整合。push把本地对象和引用更新发送到远端；未提交的工作区修改不会随push自动上传。

两个分支有祖先关系时，推送某个分支会携带远端缺少而该分支需要的对象。因此你在A提交C，然后把C合入B，先push B，也可能把C对应的对象传到远端；但远端A分支名是否移动是另一个问题。对象是否存在和哪个分支名指向它，必须分开理解。

remote名如origin只是本地别名，不天然等于“官方仓库”。`git remote -v` 查看地址。学习开源项目时，fork远端和upstream远端通常需要明确区分，避免把提交推到错误目的地。

## 5. 合并冲突是信息冲突，不是系统坏了

两条分支修改同一段内容，Git无法自动决定最终结果时会标记冲突。解决冲突不是随便删掉标记，而是理解两个改动的语义，得到一个同时满足需求的版本，再运行测试。

例如A修复空输入，B优化批处理循环。若冲突解决只保留B，可能重新引入空输入错误。验收应包含两边各自的测试。你还应检查冲突范围以外的语义交互：文本没有冲突不代表行为一定兼容。

merge保留分支汇合关系；rebase把提交重放到新基底，通常改变提交ID。已经共享的历史不宜随意重写。这里不要求立即精通所有恢复命令，而是先养成“提交前审阅，合并后测试”的习惯。

## 6. .gitignore、秘密与大文件

`.gitignore`影响未跟踪文件的发现，不会自动把已经跟踪的文件移出历史。把API密钥提交过一次后再加ignore，旧提交中仍可能存在它；这不是“现在文件看不到了”就解决的问题。

课程仓库不应跟踪真实密钥、个人数据库、GPU缓存、大模型权重或公司数据。生成结果和下载数据应有明确目录与忽略规则，必要时用校验和与下载说明复现，而不是把所有产物塞进Git。

Git工作区大小、`.git`对象库大小和某次push传输量不同。一次push取决于远端已有对象和协商压缩；不能简单用`du -sh .`当作上传量。基础课程先理解边界，再学习更精确的对象统计和打包分析。

## 7. 阅读经典开源项目的第一步

在修改vLLM或SGLang前，你应能固定某个commit，记录环境，找到一个小测试并运行，然后只修改一个行为。第一项开源贡献不必是复杂算法：补一个能复现真实边界的测试、修正文档中可验证的命令、改进错误消息，都能训练工程闭环。

阅读顺序建议：README理解用途→安装/开发文档理解环境→测试目录理解合同→入口函数追一次输入→相关实现→历史提交理解设计。不要从仓库第一文件开始通读，也不要以“全部文件都看过”作为学习目标。

官方Pro Git可作为术语参考，课程练习仍以本仓库的小程序为对象，避免将阅读大书当成不动手的理由。

## 8. 七个练习与详细答案

**F12-1 暂存差异。** stage v1后再改成v2，分别查看diff与diff --staged。答案：工作区差异显示v1→v2，暂存差异显示HEAD→v1；commit保存v1。

**F12-2 分支图。** 从同一提交建立两个分支各提交一次，画出父关系。验收：知道分支名是引用，提交之间的父关系不因名字变化而变化。

**F12-3 未提交不会push。** 修改文件但不add/commit，解释push为什么不会上传该修改。答案：push传提交对象与引用，不传任意工作区状态。

**F12-4 合并验收。** 两分支分别修复空输入与尾批，合并后运行两套测试。验收：不仅无冲突标记，还满足两项行为。

**F12-5 忽略规则。** 新建`.practice`输出，确认不会出现在待提交清单。若已跟踪，说明ignore为何无效。答案：跟踪状态与忽略规则是不同机制，需要明确从索引移除并审阅变化。

**F12-6 版本证据。** 记录一个本地提交ID和测试命令，写入自己的学习记录。验收：他人能定位你修改的精确代码，不能只写“最新版”。

**F12-7 小PR说明。** 为一次batches边界修复写两句话：什么输入以前错、现在行为如何、如何验证。参考：输入长度非批次整数倍时尾部丢失；保留尾批并加入0..19长度的性质测试。不要写空泛“优化代码质量”。

## 9. 第一轮真实实验：把三个区域分别观察出来

前面的模型提供直觉，现在在一个完全独立的练习仓库中验证真实 Git。选择自己的练习父目录，创建一个新的 `git-f12-lab`，确认里面没有重要文件后再初始化。不要在公司工程中运行这些故意冲突与恢复的练习，也不要把本段的练习提交混入课程源码。所有操作只发生在这份独立仓库。

```bash
mkdir git-f12-lab
cd git-f12-lab
git init -b main
git config user.name "Learning Student"
git config user.email "student@example.invalid"
printf 'first\n' > notes.txt
git status --short
git add notes.txt
git diff --staged
git commit -m "Add first learning note"
```

mkdir 创建练习目录，cd 改变当前工作目录，git init 建立仓库元数据。`-b main` 指定初始分支名，避免依赖机器上的默认配置。user.name 与 user.email 在这里是本仓库提交元数据，不是 GitHub 登录凭证；没有 `--global`，所以不会修改你所有工程的身份设置。示例邮件使用保留无效域名，只用于本地教学。

首次创建 notes.txt 后，它尚未被 Git 跟踪，status 短格式通常显示两个问号。add 将当前文件内容纳入暂存区，diff --staged 显示准备提交的新文件。commit 创建提交并移动当前分支引用。保存文件、暂存、提交是三个独立动作，任何一步都不会自动完成下一步。

```bash
printf 'second\n' > notes.txt
git diff
git add notes.txt
printf 'third\n' > notes.txt
git status --short
git diff
git diff --staged
git show HEAD:notes.txt
git show :notes.txt
cat notes.txt
```

现在三个区域分别是 first、second、third。HEAD 指向的提交仍保存 first，索引保存 second，工作文件保存 third。`git show HEAD:notes.txt` 从提交树读取路径，`git show :notes.txt` 从索引读取路径，cat 读取工作区。这三条观察命令把抽象术语变成可直接比较的内容。

短状态的两个位置通常分别表示索引相对 HEAD 的变化，以及工作区相对索引的变化。这个例子两个位置都可能是 M，表示两层都有修改。不要把 MM 当作“修改了两次”的计数，它表示两个比较关系。冲突时状态组合另有含义，未跟踪文件也有特殊显示，因此读到不熟悉组合时应查 status 帮助而不是凭字母猜测。

如果此时 commit，保存的是 second，工作区 third 仍作为未提交修改留下。提交并不会神奇把文件恢复成 second，也不会把 third 自动收入历史。提交后再次看 status 与 diff，你会看到工作区仍相对新 HEAD 有变化。这是学会分批提交与避免误提交的最重要实验之一。

## 10. 索引、对象与提交图：为什么历史可以稳定保存

Git 用内容寻址对象保存版本数据。blob 表示文件内容，tree 表示目录条目及其关联对象，commit 引用一个树并保存父提交和元数据。名称不是必须背诵的考试词，而是解释“文件内容相同但路径不同”“快照相同但提交不同”等现象的结构。Git 不只是保存一个差异文本列表，展示 diff 是在版本之间计算变化的一种视图。

同样内容的普通文件可以关联同一个内容对象，但目录树记录它们分别出现在哪个名字下。提交对象还含作者、提交者、时间、消息和父关系，所以即使树相同，提交标识也可能不同。课程的 Snapshot 小模型只对字典内容做摘要，不能代替真实对象格式。不要把教学模型输出的十位数字称为真实 Git commit SHA。

```bash
git rev-parse HEAD
git cat-file -t HEAD
git cat-file -p HEAD
git ls-tree HEAD
git log --oneline --decorate --graph --all
```

rev-parse 将引用解析为具体对象标识；cat-file 的 type 查询说明对象种类，pretty 输出展示内容结构；ls-tree 查看提交根树中的条目；log 的 graph 用文本布局表达父关系。命令只读取，不修改历史，适合在任何自己的仓库里观察。但输出可能含作者邮箱与提交信息，分享时应考虑隐私。

分支名是一个可移动引用，提交对象本身保持内容不变。创建 study 分支只建立新名字指向某个提交，不复制全部工程；切换分支时 Git 根据目标快照更新工作区与索引。新提交让当前分支引用移动，其他分支引用不自动跟随。HEAD 通常指向当前分支，也可能直接指向某个提交，这就是 detached HEAD。

在 detached HEAD 上仍可创建提交，但若之后切走且没有分支或标签指向它，新提交不容易从常规分支列表找到。若你在阅读某个旧版本时意外做了有价值修改，可以及时创建分支保存引用。不要把 detached 理解成文件只读或仓库损坏，它只是 HEAD 的引用方式不同。

标签通常用于给某个版本起稳定名字，分轻量与带说明等形式。分支适合随开发前进，发布标签一般不应随意移动。学习源码时记录具体提交比只写 main 更可靠，因为 main 会变化；记录版本标签也要确认它所指向的提交。复现实验需要精确版本，而不是“我当时拉了最新版”。

## 11. 恢复动作必须说明要改变哪个区域

恢复命令容易混淆，是因为它们操作的区域不同。取消暂存只改变索引，保留工作区编辑；恢复工作文件会改变磁盘上的内容，可能丢掉未提交修改；移动分支引用又是另一层动作。执行前先用 status、diff、diff --staged 确定当前状态，再选择最小范围操作。

对已经有提交历史的文件，`git restore --staged notes.txt` 通常将索引恢复为 HEAD 版本，让已暂存变化回到未暂存状态，工作文件仍保留。它不是删除你的编辑。若使用 `git restore notes.txt`，则默认按索引恢复工作区，会覆盖当前未暂存内容。两条命令只差一个选项，效果却不同，必须先理解区域关系。

```bash
git diff --staged
git restore --staged notes.txt
git status --short
git diff
```

本段只演示取消暂存，适合在前面练习仓库观察。若要丢弃工作区修改，先保存副本或确认修改确实不需要，再对明确文件操作，不要对整个工程盲目执行。版本控制能保存已记录历史，但没有提交、暂存或其他备份的文字，不一定能靠 Git 恢复。

revert 创建一个新的提交来反向应用某个旧提交的变化，适合在共享历史中保留“做过什么、后来如何撤销”的记录。reset 则可以移动当前引用，并按模式影响索引和工作区，语义更容易造成误操作。学习第一阶段优先用明确文件恢复、分支和 revert，不需要靠 hard reset 解决所有问题。

stash 暂时保存一组工作修改，让你切换任务，但它不是长期版本管理替代品，也不是所有未跟踪文件默认都会包含。使用前看清选项与保存范围，使用后确认恢复结果；stash apply 保留条目，pop 尝试应用后按成功情况处理条目。发生冲突时仍要理解内容，不是再次 pop 就会自动解决。

reflog 记录本地引用近期移动，可以帮助找到刚切走或移动前的提交。它是恢复线索，不是永久云备份；保存期限、垃圾回收和本地仓库状态都会影响可恢复性。发现误操作后先停止继续复杂改写，查看 reflog 并建立保护分支，往往比连续执行更多 reset 更有希望保留证据。

## 12. 合并的祖先关系与冲突的语义

假设 main 在提交 A，创建 study 后得到 B，同时 main 没有新提交。把 study 合回 main 时，可以仅把 main 指针前移到 B，称为快进。没有产生新的合并提交并不意味着修改没有合入，只是现有祖先关系已经能表达完整历史。若两边都从 A 各自产生提交，合并通常需要汇合双方历史。

三方合并会参考共同祖先和两边版本。若甲修改文件前半、乙修改后半，Git 可能自动组合；若同一区域的变化无法自动判断，就留下冲突。自动合并成功只说明文本规则可合并，不代表业务逻辑一定兼容。例如一边改变函数参数，一边新增旧参数调用，文件不同也可能造成运行错误。

冲突标记把两边候选内容展示在工作文件中。解决时需要理解当前分支、被合入分支与共同祖先分别表达什么，编辑出最终正确内容，删除标记，暂存解决后的文件，再完成合并。只选择 ours 或 theirs 可能丢掉另一边需求；这些策略只有在你明确知道整份内容该以哪边为准时才合理。

一个具体例子：一边修复空输入抛 ValueError，另一边优化均值累加但忘了空输入。合并后应同时保留优化和空输入合同。测试必须包含两边的行为，而不是只检查没有 `<<<<<<<`。冲突解决本质上是一次新实现，需要重新审查和验证，不是纯机械清理文本。

rebase 将一串提交重放到新的基础提交之上，通常生成新的提交标识。它让历史看起来更线性，但并不证明逻辑更简单。已经被其他人基于其开发的提交，重写后会给协作带来额外协调。个人尚未共享的学习分支可以在理解后整理；共享分支上的历史修改需要遵守项目协作规则。

cherry-pick 把某个提交引入的变化应用到当前分支，形成新的提交。它适合选择性移植小修复，但新提交并不自动与原提交拥有同一身份；若之后再合并完整分支，要理解重复变化与冲突可能。第一版学习先掌握正常分支合并，再逐步使用选择性移植，避免把历史变成无法解释的复制链。

## 13. 远端不是实时镜像：对象、引用与跟踪分支

remote 是本地配置的一组远端地址与抓取规则，origin 只是常见名字。可以把自己的 fork 叫 origin，把上游叫 upstream，也可以使用其他名称。执行任何推送前，查看 remote 地址和当前分支对应关系，确认目标仓库和引用。GitHub 账号关联、读取权限和写入权限是不同能力，不能从能看仓库就推断所有写操作都可用。

fetch 获取远端新对象并更新远端跟踪引用，如 origin/main。这个名字保存在本地，用来记录最近一次抓取时观察到的远端状态，不是每次读取都实时联网。远端别人刚推了新提交，你本地 origin/main 在下一次 fetch 前可能仍指向旧位置。它与本地 main 也是两个不同引用。

pull 在 fetch 之后整合到当前分支，具体使用 merge、rebase 或仅允许快进取决于选项和配置。初学时分开执行 fetch、查看差异、再选择整合，更容易知道发生了什么。不要在有未整理工作修改时反复 pull，希望远端更新自动解决本地问题；先看状态与分支关系。

push 请求远端更新某个引用，并传输所需对象。未提交工作区文件不属于待推送提交图，所以保存文件后直接 push 不会上传编辑。分支名是否在远端存在、是否允许更新、是否满足快进或保护规则，都是独立检查。认证成功也可能因分支保护或权限范围拒绝写入。

当远端分支包含你本地没有的新提交，普通推送可能因非快进被拒绝。正确起点是 fetch 后查看双方提交，理解是否需要合并或变基，而不是立即强制推送。强制更新可能使其他人提交不再从该分支可达；即使某种保护选项降低误覆盖概率，也不能替代对共享历史的判断。

本地仓库之间也能练习远端机制，不需要联网。一个 bare 仓库只保存仓库数据而没有普通工作区，适合作为教学远端；两个克隆分别模拟两位开发者。这样可以安全观察推送、抓取和冲突，不影响真实 GitHub 分支。完成机制训练后，再把相同概念用于用户授权的真实仓库。

## 14. 十二道练习：完整动作与预期

以下命令在第一轮创建的独立练习仓库中进行。每题开始先确认 `git status --short`；若还有上一题未整理修改，先理解并保存，不要为了继续盲目删除。需要不同初始状态的题目可以另建全新的练习目录，以保持结果清楚。

### 题一：证明提交读取索引

```bash
printf 'v1\n' > snapshot.txt
git add snapshot.txt
printf 'v2\n' > snapshot.txt
git diff --staged -- snapshot.txt
git diff -- snapshot.txt
git commit -m "Record staged snapshot v1"
git show HEAD:snapshot.txt
cat snapshot.txt
```

答案：提交读取内容 v1，工作区仍是 v2。两个 diff 分别观察 HEAD 到索引、索引到工作区，不能混称“文件改动”。完成后将 v2 作为下一次明确提交，或保存后恢复，保持后续题目起点干净。

### 题二：取消暂存但保留编辑

```bash
git add snapshot.txt
git restore --staged snapshot.txt
git diff --staged -- snapshot.txt
git diff -- snapshot.txt
cat snapshot.txt
```

答案：暂存差异为空，未暂存差异仍显示 v1 到 v2，工作文件没有丢失。此题只改变索引，理解这一点后才考虑其他恢复操作。

### 题三：建立清楚的学习分支

```bash
git add snapshot.txt
git commit -m "Update snapshot to v2"
git switch -c study/branch-demo
printf 'branch note\n' > branch.txt
git add branch.txt
git commit -m "Add branch-specific note"
git log --oneline --decorate --graph --all
```

答案：study/branch-demo 指向新提交，main 保持创建分支前的位置，HEAD 附着在 study 分支。文件 branch.txt 属于新提交快照，切回 main 时正常情况下不出现于其快照。

### 题四：快进合并

```bash
git switch main
git merge --ff-only study/branch-demo
git log --oneline --decorate -3
```

答案：main 可以前移到 study 指向的提交，不需要新合并节点。`--ff-only` 明确要求快进，若历史已经分叉则拒绝，避免命令在不同状态下自动采用另一种整合方式。

### 题五：忽略未跟踪生成物

```bash
mkdir generated
printf 'temporary\n' > generated/output.txt
printf 'generated/\n' > .gitignore
git status --short
git check-ignore -v generated/output.txt
```

答案：生成文件被忽略，check-ignore 显示生效规则来源；.gitignore 本身仍需要作为源码规则提交。若文件早已跟踪，新增忽略规则不会自动移除历史，这是另一种状态。

### 题六：查看一个文件的历史

```bash
git log --oneline -- snapshot.txt
git show HEAD:snapshot.txt
git log -p -- snapshot.txt
```

答案：路径前的双横线分隔选项与路径，避免某些名字被误认为引用。log 展示相关提交，带 patch 的形式展示变化；历史文本只是证据，还要结合当时测试与需求解释原因。

### 题七：建立发布观察点

```bash
git tag study-f12-complete
git rev-parse study-f12-complete
git show --stat study-f12-complete
```

答案：标签指向当前版本，之后新提交不会自动移动这个标签。这里是本地学习标签，不会因创建就自动发布到 GitHub；是否推送标签是另外动作。

### 题八：未提交内容不在提交对象中

```bash
printf 'not committed\n' > local-only.txt
git status --short
git ls-tree --name-only HEAD
```

答案：status 能看到本地未跟踪文件，提交树列表没有它。因此 push 当前分支也不会包含这个文件的工作区内容。不要把远端当作未提交草稿的自动备份。

### 题九：审阅暂存的完整范围

```bash
git diff --staged --stat
git diff --staged --name-status
git diff --staged
```

答案：第一条看规模，第二条看路径及增删改，第三条看具体内容。三者互补，只有文件名列表无法发现文件内部密钥，只有大段 diff 又可能忽略新增巨大二进制文件。

### 题十：撤销已共享行为用新历史表达

在独立练习分支创建一条只新增 `revert-demo.txt` 的提交，再反向撤销：

```bash
printf 'demo\n' > revert-demo.txt
git add revert-demo.txt
git commit -m "Add reversible demo"
git revert --no-edit HEAD
git log --oneline -2
```

答案：历史保留原新增提交，并增加一个反向提交，当前快照不再包含该文件。这里演示的是本地练习；真实共享分支仍需按项目流程审阅提交。

### 题十一：定位精确版本

```bash
git rev-parse HEAD
git status --short
python --version
```

答案记录提交标识、工作区是否干净和解释器版本。如果工作区还有修改，仅记录 HEAD 不能完整描述实际运行代码；应补充差异或先形成明确提交。环境与代码版本共同构成复现证据。

### 题十二：写一份可审阅的变更说明

完整参考文本：“输入长度不是批大小整数倍时，旧循环遗漏最后一批。本修改保留不足一批的尾部；使用空输入、单元素、整批和尾批样例，以及长度零到十九的顺序保持检查验证。”这个说明先写触发条件和行为，再写验证，不用“优化体验”代替事实。

如果实际只改文档，就写哪个命令或先修顺序造成误解，以及现在怎样修正；不要宣称没有执行的测试。说明属于协作接口，读者不应必须翻聊天记录才能知道变更目的。

## 15. 一次完整冲突实验与参考解决

另建一个新的临时练习仓库，确保没有任何重要内容。先提交 `answer.txt` 为 base，再从同一提交分出 left 与 right，分别把同一行改为不同内容。回到 left 合并 right，Git 无法自动选定一行时会产生冲突。此实验故意制造失败，出现非零退出是预期现象，不代表练习环境坏了。

```bash
mkdir git-conflict-lab
cd git-conflict-lab
git init -b main
git config user.name "Learning Student"
git config user.email "student@example.invalid"
printf 'base\n' > answer.txt
git add answer.txt
git commit -m "Add common base"
git switch -c left
printf 'left requirement\n' > answer.txt
git commit -am "Apply left requirement"
git switch main
git switch -c right
printf 'right requirement\n' > answer.txt
git commit -am "Apply right requirement"
git switch left
git merge right
```

`commit -am` 会自动暂存已跟踪文件的修改和删除，但不会把任意未跟踪新文件都加入。这里只在已有 answer.txt 上使用，避免初学者误以为它等同 `git add .`。合并失败后运行 status，打开文件查看两边内容，再根据业务需求形成最终答案。

```bash
printf 'left requirement\nright requirement\n' > answer.txt
git add answer.txt
git diff --staged
git commit -m "Combine both requirements"
git log --oneline --graph --all
```

本例的参考解决保留两条独立需求，因此最终两行都存在。真实代码不能总通过简单拼接解决：两个函数定义同名时直接保留两份可能让后者覆盖前者，两个互斥参数也需要重新设计。冲突标记只是提示你必须做语义判断，最终版本仍要运行相关测试。

如果决定放弃这次合并，应在理解当前状态后使用合并中止机制恢复到合并前的状态，并核对原有修改是否保留。不要在冲突过程中继续启动另一次 rebase 或 pull，叠加多个未完成操作会让状态更难解释。一次完成一个明确历史操作，是初学阶段最重要的纪律。

## 16. 从历史定位缺陷：log、blame 与二分查找

log 展示提交序列与图，带路径可缩小范围，带补丁可看到具体变化。blame 把当前文件行关联到最近修改它们的提交，是定位设计背景的入口，不是归责工具。某行最近格式化过，显示的提交可能不是引入逻辑的原始变化，需要继续追踪历史与相关讨论。

当已知某个旧版本正常、新版本失败，而且有稳定复现测试时，可以使用二分定位。每次选择中间版本运行同一个测试，判断好坏，逐步缩小引入范围。它依赖测试可靠与版本能构建；若测试随机失败或环境随版本变化却没处理，结论可能错误。先建立最小稳定反例，再使用历史搜索工具。

不要在自己有未保存编辑的主工作区里随意切换很多历史版本。可以使用独立克隆或 worktree，让阅读与实验和当前修改分开。worktree 共享底层仓库对象，但有不同工作目录与检出状态；它不是完整独立备份，也有分支检出限制。使用前确认路径和分支，避免把两个目录误认成同一份当前状态。

学习开源框架时，先固定提交并运行一个小测试，然后追踪相关函数与历史变化。一个改进错误消息、补充边界测试或修正文档的贡献，能够训练完整闭环；不必一开始修改最复杂调度器。理解别人为什么写出某个约束，通常比随手把它删除让样例通过更有价值。

## 17. 大文件、秘密和可复现数据的存储边界

Git 适合文本源码和相对小的版本数据，不适合把所有模型权重、缓存和运行数据库直接收入普通历史。文件从当前目录删除不代表历史对象立即消失，仓库体积可能继续增长。对于下载数据与模型，保存来源、版本、摘要和获取步骤往往比复制巨大产物更适合教学工程。

Git LFS 使用指针与外部对象存储管理大文件，但需要服务与配额支持；它不是自动无限容量，也不改变敏感数据不该公开的事实。选择 LFS、发布附件或外部数据存储前，先明确使用者如何取得相同版本、如何验证完整性以及是否有许可。当前课程的默认离线夹具应保持小而可审查。

秘密一旦进入共享历史，应按真实暴露情况处理凭证失效与更换，单纯删除当前文件或新增 ignore 不足以消除旧版本中的值。历史清理也涉及协作副本和远端缓存，不能轻率承诺“删掉提交就完全消失”。最有效的日常习惯是提交前审阅暂存内容，并让示例配置只包含占位符。

忽略规则应精确。过宽规则可能把真正源码隐藏，过窄规则可能让缓存和个人状态不断出现在 status。用 check-ignore 查看某个文件为何被忽略，能帮助诊断“明明创建了文件却加不进去”。强制添加之前先理解规则目的，不要把忽略配置当成需要绕开的障碍。

仓库大小、工作区大小与一次推送量不同。工作区包含未跟踪生成物，.git 保存历史对象，推送只发送远端缺少且目标引用需要的对象，并可能打包压缩。不能从目录总大小直接推断网络上传量，也不能从一次小推送推断仓库长期没有大文件问题。分析时应明确你测量的是哪个层次。

## 18. 分阶段工程任务：一次可以让他人复核的小贡献

第一阶段选择一个具体可复现缺陷，例如批处理漏尾、配置零值被覆盖或错误时状态被修改。第二阶段在独立分支写失败测试，确认旧实现真的失败。第三阶段做最小修复，运行相关测试。第四阶段审阅工作区与暂存差异，排除无关格式改动、缓存和秘密。第五阶段形成清楚提交与说明。

第六阶段在另一个干净目录或 worktree 运行说明里的命令，验证别人无需你的终端遗留状态就能复现。第七阶段准备 PR 描述，说明触发条件、结果变化与验证边界。是否向真实上游提交是单独的协作动作，应按用户目标与项目贡献指南进行；本章练习完成本地可审阅成果即可。

验收时请解释提交图中每个节点为何存在，而不是只看“分支合上了”。你能指出起点、失败测试、修复与验证，能说明哪些文件属于提交、哪些只是本地生成物，并能恢复到某个明确版本。这些能力让后续框架和算子修改有可靠历史基础，也使你可以持续扩展课程而不失去已有学习成果。

## 19. 不联网的远端实验：两份克隆看到的世界

在新的练习父目录中，创建一个 bare 仓库，再克隆为 alice 与 bob。bare 仓库没有普通工作文件，扮演远端对象与引用存储；alice、bob 是两个独立工作区。这个实验不需要 GitHub 凭证，也不会修改任何真实远端，因此适合反复观察分布式协作机制。

```bash
mkdir git-remote-lab
cd git-remote-lab
git init --bare --initial-branch=main remote.git
git clone remote.git alice
cd alice
git config user.name "Alice Student"
git config user.email "alice@example.invalid"
printf 'shared base\n' > shared.txt
git add shared.txt
git commit -m "Create shared base"
git push -u origin main
cd ..
git clone remote.git bob
cd bob
git config user.name "Bob Student"
git config user.email "bob@example.invalid"
```

alice 第一次克隆空远端时看到空仓库提示是正常现象。首次提交后 push 创建远端 main，并通过 `-u` 设置当前分支的上游跟踪关系。bob 随后克隆，获得远端已有提交与文件。这里“共享”通过推送和抓取发生，不是两个目录直接共用同一个工作文件。

现在在 alice 新增一条提交并推送，bob 不做 fetch 时仍停留旧视图。bob 的普通 cat 当然不会自动出现 alice 新内容；即使查看 origin/main，它仍可能是上一次抓取记录。执行 fetch 后，origin/main 更新，但 bob 的 main 和工作区通常仍未自动前移。再执行明确快进合并，工作区才体现远端新版本。

```bash
cd ../alice
printf 'alice update\n' >> shared.txt
git commit -am "Add Alice update"
git push
cd ../bob
git show origin/main:shared.txt
git fetch origin
git show origin/main:shared.txt
cat shared.txt
git merge --ff-only origin/main
cat shared.txt
```

手算四个时刻：抓取前 bob 的远端跟踪引用与工作区都旧；抓取后远端跟踪引用新、工作区仍旧；快进后本地 main 新；工作区随之更新。把这四项分别记录，能消除“fetch 明明成功为什么文件没变”的困惑。它按设计只更新获取到的对象和引用，不等于替你选择整合策略。

如果 bob 在抓取前也创建本地提交，历史就可能分叉。此时快进合并拒绝是保护信息，不是必须用强制操作消除的障碍。查看 log 图，确认共同祖先与双方新节点，再选择普通合并或符合协作规则的变基。远端更新与本地修改都可能有价值，工具无法替你判断哪一边应该被丢弃。

## 20. 读懂 diff：一块补丁到底表达什么

diff 展示两个版本之间的变化，不是完整文件。常见补丁头部说明旧路径与新路径，块头显示旧新行号范围，前导减号表示旧版本中被移除的行，前导加号表示新版本中加入的行，空格开头是上下文。行内容本身若以加减号开头，仍要区分补丁标记和实际字符。

块头中的行号描述补丁对应的版本位置，不代表当前编辑器里所有后续改动后的绝对位置。多次修改后上下文可能变化，应用补丁可能需要定位或产生冲突。读补丁时先看函数或段落上下文，再看具体增删，避免只看到一个运算符变化却不知道它影响哪条路径。

```diff
-    return sum(values) / (len(values) - 1)
+    if not values:
+        raise ValueError("empty sample")
+    return sum(values) / len(values)
```

这块补丁同时改变空输入行为和普通输入分母。审查时应要求两个方面的验证，而不是只说“修复一行”。如果新增代码之前还有迭代器转换，则还要考虑输入是否被消费、是否支持 len。补丁范围小不等于语义影响只有一个点。

重命名检测通常是比较内容相似度后形成的展示判断，不是文件对象自带永恒身份。大幅修改并重命名可能显示为删除加新增，也可能被识别为 rename。审查时关注实际内容与用途，不要因为显示成重命名就认为没有逻辑变化。二进制文件的 diff 也可能不展示内部内容，需要单独检查来源和必要性。

行尾变化会让整份文件看起来都改了。Windows 与 Linux 换行、编辑器自动格式化、编码或末尾空白处理都可能造成噪声。先确定项目的文本规范，避免在一个行为修复里混入整个文件的无关换行变更。必要时把格式调整独立成清楚提交，让审查者能区分机械变化与逻辑变化。

`git diff --check` 可以发现某些空白问题和冲突标记相关问题，但它不执行程序，不验证 Python 语法或业务正确性。工具名字里的 check 只是其定义的检查范围，不能替代测试。提交前审阅通常结合差异、静态检查与相关行为验证，每种证据回答不同问题。

## 21. 历史组织：一个提交应该表达什么

一个提交最好表达一个可说明的逻辑变化，并在合理范围内保持可运行。把修复均值、升级全部依赖、重新格式化和新增 Docker 配置塞进同一个提交，会让失败定位与审查困难。拆分不是为了追求很多小数字，而是让每个节点有清楚因果。过度拆成无法单独理解的一行一提交，也可能增加阅读成本。

暂存区允许你从工作区的一批编辑中挑选本次要提交的部分。交互式暂存可以按块选择，但初学时先按明确文件暂存，逐步理解后再使用分块工具。分块后务必查看暂存版本是否仍然自洽：工作区整体测试通过，不代表只提交其中一半后的代码也能运行。真正要交付的是索引里的版本。

提交信息第一句说明具体行为变化，正文可说明原因、兼容性和验证。不要只写 fix 或 update；几周后你无法从这些词定位学习进展。也不必把所有聊天过程写进历史，保留读者评估变更所需信息即可。文档修复同样应指出哪条操作或概念被澄清，而不是泛泛“完善教材”。

amend 可以修改最近提交，通常产生新的提交标识。若提交尚未共享，它适合补上遗漏小改动；若已经共享，修改身份会影响其他人的历史关系。使用前确认是否已推送以及团队规则，不要把 amend 当作每次编辑后自动执行的习惯。历史是否可重写是协作合同，不只是个人偏好。

squash 把多个提交组合成一个较大的逻辑变化，适合整理探索过程；保留多个提交则可能更好表达实现步骤。两者没有普遍优劣，关键是最终历史能支持审阅、定位和回退。课程工程未来扩展时，可以按卷或明确教学功能组织变更，避免把互不相关的大量内容混成无法复核的一团。

## 22. 跟踪状态、删除与移动的几个易错点

删除工作文件后，Git 看到的是工作区相对索引的删除；要将删除纳入提交，需要暂存相应变化。`git rm` 可以同时更新索引并删除工作文件，使用前确认路径。若只想停止跟踪而保留本地生成物，可以使用只操作索引的形式，但这会改变下一次提交中的文件集合，需要审阅并配合忽略规则。

文件从一个路径移动到另一个路径，最终快照只记录新旧路径的内容关系，Git 可以在展示历史时判断相似性。`git mv` 方便执行移动与暂存，但不是唯一能形成正确历史的方式；普通文件系统移动后明确暂存增删也可以。重要的是最终差异与内容符合意图，而不是强迫所有编辑都通过 Git 命令完成。

未跟踪文件不受普通提交历史保护，ignored 文件也只是被状态发现规则忽略，不代表不能被程序读取或不会占磁盘。清理命令可能删除这些文件，因此不能因为“Git 不显示它”就认为删除没有损失。模型下载、个人数据库和练习输出即使不进 Git，也可能有保留价值，应有独立存储与重建策略。

子模块是一种让父仓库记录另一个仓库具体提交的机制，不是普通目录复制。克隆父仓库后，子模块内容可能需要额外初始化，更新也有独立步骤。初学课程不需要随意引入子模块，但阅读大型开源项目时看到它，应理解父提交记录的是版本引用，而不是自动跟随外部 main。复现依赖仍需固定精确版本。

## 23. 开源协作的完整阅读与修改路径

先阅读项目贡献指南，确认开发环境、格式、测试和 PR 模板。它们描述的是该项目具体协作合同，不能假设所有仓库都用相同命令。然后找到一个小而真实的问题，建立失败样例，定位负责该行为的模块，再做最小修改。跳过复现直接大面积重构，很难证明你解决了原问题。

阅读源码时优先追踪一个具体输入。例如数据加载器接到五条记录和批大小二，在哪个函数保存迭代状态，谁丢弃尾批，哪个配置控制行为。把调用链与对象状态记录下来，再查历史说明为什么如此设计。有些看似错误的行为可能是明确选项，如训练时 drop_last；先确认合同再修改。

测试成本要按变化选择。文档命令修复应验证命令可运行；纯解析逻辑应有离线单元测试；涉及 CUDA 内核才需要适当 GPU 验证。用户有 H100 资源，可以安排真实实验，但不应让每个无关文档改动都启动多卡训练。验证应充分且针对风险，不是以资源消耗多少衡量认真程度。

PR 描述应面向不知道聊天背景的审查者。先说什么输入以前产生什么错误，现在怎样变化，再写实现要点与验证。若没有在某个平台运行，明确说明；若只验证小输入，不夸大为生产负载保证。讨论中接受反馈后，更新最终描述，使它反映当前实现，而不是保留已经放弃的初始计划。

第一项贡献不必获得合并才有学习价值。完成可复现问题、独立测试、清楚修复与审阅材料，本身已经训练工程能力。真实上游是否接受，还取决于维护方向、兼容性与已有工作。尊重项目规则，避免为了“贡献记录”提交没有实际价值的噪声改动。

## 24. 恢复演练与掌握检查

在自己的练习仓库中完成一次无损恢复：先提交一个稳定版本，修改文件并暂存，再取消暂存，确认内容仍在；随后把有价值修改提交到独立分支，切回稳定分支，确认两份历史都能通过分支名找回。这比直接练习危险的全局重置更适合建立区域模型。

再完成一次历史撤销：新增一个小文件并提交，用 revert 生成反向提交，查看图中两个节点与当前文件集合。最后用 show 读取旧提交中的文件，证明当前文件消失不等于历史内容立即不存在。这个实验同时解释为什么秘密删除不能靠当前快照完成，以及为什么历史恢复有价值。

如果遇到未知状态，先只读观察：status 说明工作区与索引，log 说明引用与父关系，diff 说明内容变化，reflog 提供近期引用移动线索。只有当你能用一句话说清下一条命令将改变哪个区域、哪些路径和哪些引用时，再执行修改。熟练不是背更多恢复咒语，而是能预测命令后的状态。

本章最终的可交付证据是一份小仓库或分支、一组测试结果和一张你自己画的提交关系图。你应该能回答某个文件当前在哪些版本存在、哪些编辑尚未提交、远端跟踪引用何时更新，以及一次推送会更新哪个分支。掌握这些问题后，学习大型框架代码、维护课程版本和逐步提交算子实现，都有了可追踪的工作基础。

### 补充：忽略模式与目录规则的逐步判断

忽略文件中的模式不是 Python 正则表达式。星号通常匹配名字中的一段，斜线影响路径范围，末尾斜线常用于目录，感叹号可表达重新纳入的例外，但父目录被整体忽略时还有需要理解的遍历规则。初学时先写简单明确的生成目录规则，再用 check-ignore 验证具体路径，不要凭正则经验直接猜复杂模式。

规则可以来自仓库内的 .gitignore、本地排除文件或用户全局配置。某个文件在你机器上不显示，不代表其他学习者也有相同全局规则。影响项目可复现行为的公共生成物规则应随仓库保存，个人编辑器临时文件则可按团队习惯放本地或全局配置。诊断时显示规则来源，比不断追加重复模式更有效。

被忽略的文件仍能被显式强制加入，但执行前应理解为什么它被排除。如果是模型缓存或密钥，绕过规则会破坏存储或隐私边界；如果是确实需要保存的小型测试夹具，可以调整规则让意图清楚。不要让一次 force add 成为以后只有少数人知道的隐含例外。

### 补充：提交身份、认证与签名属于不同层

user.name 和 user.email 是提交记录中的身份元数据，不是登录密码。GitHub 认证决定你能访问哪些远端资源，提交签名则用于提供关于提交来源的额外验证。三者不能互相替代：写了某个名字不会获得该账号权限，能推送也不代表提交一定带有可验证签名。课程练习使用本地示例身份，只为了避免修改用户全局配置。

远端地址可能使用 HTTPS 或 SSH，两种传输有各自认证方式。查看 remote 地址能知道当前使用哪种入口，但不要把凭证直接嵌入公开命令或提交记录。遇到认证失败时，先确认服务、账号、仓库权限与传输方式，再按平台官方流程处理；反复更改 user.email 通常不能解决网络认证问题。

仓库里的 hooks 或自动化配置可能在某些动作时执行代码。阅读陌生仓库的开发脚本前，应理解它做什么，尤其是安装依赖、下载模型、启动服务或修改系统环境的动作。Git 本身记录源码，不代表其中每个脚本都已经由你审查。对本课程实验，优先执行清楚的标准库与离线测试命令，外部资源任务再按具体说明选择。

最后保存一次完整版本证据：提交标识、是否有未提交差异、依赖版本、测试命令、输入摘要和结果。单独一个截图无法重建这些条件，单独一个分支名也可能随未来提交移动。把证据与学习记录关联后，你能够在几个月后重新运行同一算法，并明确判断差异来自代码、输入还是环境变化。

当一次恢复成功后，立即检查文件内容并建立清楚引用，别只因命令退出为零就停止验证；恢复动作的目标是找回正确状态，而不只是让终端不再报错。
