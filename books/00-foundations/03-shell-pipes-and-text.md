# F03 Shell、参数、标准流与管道：把一整条命令拆开理解

你以后会遇到很长的模型启动命令、Docker 命令和评测脚本。如果只会整行复制，一旦路径含空格、环境变量为空、前半段失败或某个参数被误展开，就很难定位。本章先建立命令执行的准确模型，再通过小实验学习引号、参数、输入输出、退出状态和脚本结构。读完后，你应该能把一条长命令还原成“启动哪个程序、交给它哪些参数、数据从哪里来、结果到哪里去”。

本章使用 Bash 语义，操作只限自己的 `.practice/f03`。PowerShell 是另一种语言，不能把本章所有语法原样套过去。离线 Python 对照实验是 `python -m labs.foundations.text_pipeline`，不需要网络或 GPU。

## 第一课：Shell 是一门用于组织程序的语言

### 1.1 输入的一行文字不会原封不动交给程序

考虑 `python train.py --epochs 3`。Shell 首先识别命令结构，把普通词、引用、变量和重定向等按自己的规则处理，然后找到要运行的程序，把参数序列交给它。Python 再解释自己的参数，读取 train.py，脚本还可能进一步用 argparse 解释 epochs。这里至少有 Shell、Python 解释器和应用参数解析三个层次。

因此，一个报错中的“参数不认识”可能来自不同程序。若 Shell 在引号处发现语法错误，目标程序根本没有启动；若 Python 报告解释器选项错误，脚本可能尚未运行；若脚本解析器拒绝某个业务参数，则前两层已经成功。读错误时先确认是谁在说话，才能决定修改哪一层。

Shell 并不自动理解 `--epochs` 是训练轮数。对 Shell 来说，它只是一个普通参数字符串；具体含义由接收程序定义。不同工具即使使用相同选项名，也可能有不同类型和单位。你不能仅凭看到 `--timeout 10` 就断定十是秒，它也可能是毫秒或其他单位，必须查对应程序合同。

### 1.2 命令、选项、选项值与位置参数

常见命令行习惯把带短横线的词作为选项，例如 `-n` 或 `--name`，把紧随其后的词作为选项值，把其余词作为位置参数。但这只是常见约定，不是 Shell 强制所有程序采用的规则。有些选项不带值，有些允许 `--name=value`，有些工具还有子命令。

```bash
python tools/course.py lesson F03
```

Shell 启动 python，并传入三个主要参数：脚本路径、lesson、F03。Python 先把脚本路径作为入口，课程脚本再把 lesson 识别为子命令，F03 识别为对应位置参数。你应该能够按这三个解析阶段画出参数去向，而不是把整行当作一个不可分解的口令。

### 1.3 可执行程序与 Shell 内建命令

有些命令由 Shell 自己实现，例如常见的 cd；有些是独立程序，例如许多系统中的 ls。cd 必须改变当前 Shell 的工作目录，如果只在一个独立子进程里改变目录，子进程结束后父 Shell 的目录不会因此改变。这说明命令是否内建，与它需要修改哪个进程的状态有关。

可以用 `type` 等 Shell 查询工具观察一个名称最终解析为内建、函数、别名或外部程序。不要只凭命令名字推断来源。某人可能定义了同名别名或函数，使你输入的命令先经过额外包装。排查奇怪行为时，确认真正执行的对象，比不断改变参数更有效。

## 第二课：先用一个参数显微镜观察真实输入

最直接的学习方法是让一个程序打印自己收到的参数。Python 的 sys.argv 提供脚本参数列表；在 `python -c` 模式下，第一个元素通常是该模式的标识，其后才是你传入的参数。

```bash
python -c 'import sys; print(repr(sys.argv[1:]))' alpha 'two words' "three words"
```

预期打印三个参数：alpha、two words、three words。单引号和双引号在这个例子中都把空格包在同一个参数里。引号本身通常是 Shell 的分组语法，不会作为那两个参数内容的一部分传入 Python。若你希望参数中真的包含引号字符，需要按相应引用规则明确表达。

再删除第二个参数外面的引号。程序会收到更多参数，因为空格被 Shell 用作词的边界。接收程序并不知道你原本想把哪些词当作一个文件名，它只看到已经解析完成的参数列表。所以“程序怎么把我的路径拆开了”常常发生在程序启动之前，真正需要修复的是 Shell 引用。

参数显微镜比 echo 更适合观察边界，因为 echo 的输出会把多个参数重新显示成一行，可能看不出原来是一项还是两项。repr 则会展示列表与字符串边界。调试任何复杂命令时，都可以先把业务程序替换成这种无副作用观察器，确认参数准确后再恢复真实动作。

## 第三课：三种引用方式各做什么

### 3.1 单引号保留字面内容

在普通 Bash 单引号中，内容按字面保留，变量引用和命令替换不会按通常方式展开。因此你希望把一个正则表达式、固定 JSON 或含美元符号的文本原样交给程序时，单引号常常最清楚。单引号内部不能直接包含另一个未处理的单引号，因为它会结束当前引用范围，需要分段引用或选择其他表达方式。

```bash
label='two words'
printf '<%s>\n' '$label'
```

第二条输出的是美元符号加名字，而不是变量的值。因为 Shell 看到单引号后，把其中内容当作一个字面参数。这个规则非常适合保护不希望被 Shell 解释的文本，但如果你本来就需要变量值，它就不是正确选择。

### 3.2 双引号允许部分展开并保留参数边界

```bash
printf '<%s>\n' "$label"
```

这里变量被替换为 two words，但双引号保留一个参数边界，不会因为值中含空格就拆成两项。双引号也不等于“所有字符都失去特殊意义”：变量展开、命令替换等仍可能发生，反斜杠在特定字符前也有作用。将外部文本放进双引号字符串时，必须理解这层解释。

写脚本时，路径变量通常应该加双引号，例如 `"$file"`。它同时防止展开结果经历不希望的分词和路径名展开。即使你现在的测试文件名没有空格，也应按允许输入的合同写正确，而不是让测试数据的简单性掩盖缺陷。

### 3.3 反斜杠与续行

反斜杠可以使某些字符按字面解释，也常用于把长命令延续到下一物理行。续行反斜杠后面必须按相应语法紧接换行；如果后面多了空格，可能转义的是空格而不是换行，下一行就变成另一条命令。复制网页中的长命令后出现奇怪的“选项被当作命令”，应检查这个位置。

续行只是源码排版，不代表启动多个进程。你可以把一条命令的每个参数写在单独一行，使业务含义更清楚，但最终接收程序看到的仍是一组参数。相反，真正用换行分开的两条命令默认是两个执行动作，其失败与状态传播需要单独处理。

## 第四课：变量、环境变量与展开

### 4.1 赋值语法为什么不能随意加空格

Bash 中常见赋值写作 `name=value`，等号两侧不能像某些编程语言一样任意放空格。`name = value` 可能被解释为运行名为 name 的命令，并给它传入另外两个参数。Shell 的语法和 Python 不同，不能只按视觉相似性迁移规则。

引用变量使用 `$name` 或 `${name}`。花括号能明确变量名边界，例如 `${name}_result` 表示变量值后接后缀，而 `$name_result` 会查找另一个更长的变量名。花括号本身不自动提供引用保护；如果需要把展开结果保留为一个参数，仍应写成 `"${name}_result"`。

### 4.2 Shell 变量与导出的环境

Shell 内部变量不一定自动传给子进程。export 将相应变量纳入之后启动子进程的环境。子进程通常得到环境的一份继承状态；它修改自己的环境，不会反向修改父 Shell 的变量。这个父子关系在 F04 会展开。

```bash
course_label='foundation'
export course_label
python -c 'import os; print(os.environ.get("course_label"))'
```

也可以在单条命令前设置环境赋值，使影响限于该命令的执行环境。常见例子是为排序设置 `LC_ALL=C`。注意这仍是环境配置，不是命令参数，接收程序通过环境查询它，而不是在 sys.argv 中把它当普通选项读取。

### 4.3 空值、未设置与默认值

一个变量可能未设置，也可能已设置为空字符串。这两种状态在某些配置逻辑中意义不同。Shell 提供若干参数展开形式处理默认值与缺失，但初学时不要只记符号，先写出你想要的合同：空字符串算不算有效值？缺失时是否应该立即失败？默认值来自哪里？

如果把空变量未经引用展开到命令中，它甚至可能消失成零个参数；加双引号则保留一个空参数。接收程序看到“没有提供参数”和“提供了空字符串”可能采取不同动作。参数显微镜能够直接观察这种区别，是理解默认配置错误的重要练习。

## 第五课：展开顺序与通配符

### 5.1 星号通常由 Shell 先处理

在常见设置下，未引用的 `*.txt` 会被 Shell 展开为当前目录匹配的路径，然后这些路径作为多个参数交给程序。程序可能根本没有收到星号。若你希望某个工具自己处理模式，需要引用它，例如 find 的 `-name '*.txt'`。

通配符与正则表达式是不同语言。Shell 的星号通常匹配路径名中的一段字符，正则中的星号通常修饰前面的表达式；正则 `.*` 表示任意字符重复，而 Shell 的 `.*` 常涉及点开头的名字。看见相同符号不能推断相同含义，必须问“当前由谁解释这段文本”。

### 5.2 没有匹配时怎么办

不同 Shell 或选项下，无匹配通配符的处理可能不同。Bash 的常见默认行为会保留未匹配模式本身，但启用某些选项后可能变为空或直接报错。脚本若依赖某种行为，应明确设置或避免隐含假设。初学练习可以先用 printf 展示展开结果，再把结果交给会修改文件的命令。

不要在尚未观察展开结果时使用宽泛通配符做删除或覆盖。对于本课程，任何修改都限定在自己的练习目录，并先列出将被处理的具体路径。这样做不是让你永远害怕命令，而是训练“先知道输入集合，再执行动作”的基本工程习惯。

### 5.3 分词与路径名展开会叠加

未引用的变量展开结果可能先被分词，再进行路径名展开。因此一个变量值不仅可能因为空格变成多个参数，其中的星号还可能进一步变成多个文件名。仅仅保证原始命令里没有直接写星号，并不代表没有路径展开；星号可能来自变量内容。

这也是为何不应把一整条命令拼成字符串再期待 Shell 安全、准确地重新解析。复杂启动器更适合使用明确参数数组。Python 的 subprocess 在 `shell=False` 且参数为列表时，能够把每个元素直接作为一个参数传递，避免额外 Shell 解释；F04 将给出完整例子。

## 第六课：三条标准流与文件描述符

### 6.1 输入输出不是只有屏幕这一条路

常见命令行进程启动时有标准输入、标准输出和标准错误三个约定通道。常用文件描述符编号分别为零、一、二。标准输入可以来自键盘、文件或管道；标准输出可以到终端、文件或另一个程序；标准错误通常用于诊断。终端可能把输出与错误都显示在同一个窗口，但它们仍是不同通道。

将正常数据与诊断分开非常重要。假设一个程序承诺在标准输出返回 JSON，却先打印“开始处理了”，下游 JSON 解析器就可能失败。把进度和诊断写到标准错误，机器可读结果留在标准输出，可以让程序更容易组合。日志级别与具体消息结构会在 F10 进一步展开。

```bash
python -c 'import sys; print("result"); print("diagnostic", file=sys.stderr)'
```

先直接运行，两个词都可能出现在终端。再分别重定向，就能观察它们属于不同流。这个实验比只背“stdout 是一、stderr 是二”更有意义，因为你实际验证了同一窗口并不等于同一数据通道。

### 6.2 文件描述符是进程中的引用入口

文件描述符不是文件路径，也不是文件内容。它是进程用来引用某个已打开输入输出对象的标识。不同进程中的同一个数字，不必指向同一个文件；一个进程的多个描述符也可以关联到同一个输出目标。重定向就是在启动或执行命令时重新安排这些连接。

理解这一点后，`2>&1` 就不再只是需要背下的符号。它的意图是让描述符二指向当时描述符一所关联的目标。这里的“当时”很重要，因为重定向按顺序处理，后续改变一的目标不一定会追溯修改二之前复制的连接关系。

## 第七课：重定向的顺序与失败

| 写法 | 主要含义 |
|---|---|
| `command > out.txt` | 标准输出写到文件，通常截断旧内容 |
| `command >> out.txt` | 标准输出追加到文件 |
| `command 2> err.txt` | 标准错误写到另一个文件 |
| `command < input.txt` | 标准输入从文件读取 |
| `command > out.txt 2>&1` | 先改标准输出，再让错误跟随该目标 |

`command > out.txt 2>&1` 与 `command 2>&1 > out.txt` 不同。第一种先让一指向文件，再把二指向此时的一，因此二者都去文件。第二种先把二指向原来的一，通常是终端，然后只把一改到文件，所以错误仍可能显示在终端。你可以用上一课的双输出程序亲手验证。

重定向通常由 Shell 在目标程序真正执行前安排。如果目标文件无法创建，命令可能根本没有成功启动。反过来，Shell 可能已经截断了输出文件，随后程序才因为参数错误退出。因此“程序没有正常运行”并不保证“没有任何文件副作用”。重要输出应使用更稳妥的保存策略，而不是总把最终结果直接作为重定向目标。

还有一个常见陷阱：把同一个文件同时作为输入与截断输出，例如某些形式的 `cat file > file`。Shell 先截断输出，程序再读取时内容已经没了。正确的修改通常需要临时文件、工具自身支持的原地编辑语义，或完整读取后按明确策略替换。不能把“输入输出文件名相同”理解成系统会自动保护旧内容。

## 第八课：管道连接的是数据流，不是命令字符串

### 8.1 两个程序怎样协作

`left | right` 通常把 left 的标准输出连接到 right 的标准输入。Shell 负责建立连接并启动相关进程，数据通过管道传递。right 不会收到字符串形式的“left 命令”，而是读取 left 实际输出的字节。两边可以是完全不同语言编写的程序，只要对输入输出格式达成一致即可协作。

管道常允许生产者与消费者重叠运行，不必等左边把全部结果写完才启动右边。管道缓冲有限，如果右边消费慢，左边写入可能等待，这是一种背压。后面的异步课程会重新讨论同样思想：下游能力有限时，上游不能无限堆积数据而假装系统没有约束。

### 8.2 标准错误默认不一定进入管道

普通管道连接标准输出。左侧程序的标准错误通常仍按其既有连接输出，因此你可能在屏幕看到错误，而右侧读到空数据。若希望把错误也交给下游，需要明确合并，但合并后下游就会同时接到数据和诊断，可能破坏格式合同。不是所有情况都应该“把所有东西合并起来”。

### 8.3 下游提前退出会影响上游

例如右侧只想读取前几行后结束，上游继续写入时可能遇到管道已关闭。这个现象不一定表示上游业务数据错误，而可能是整个组合的预期行为。严格处理管道状态时，需要理解各阶段退出的原因，不能只看到某个非零值就不加区分地重试整个任务。

## 第九课：从日志中构造一条可手算管道

先创建合成日志：

```bash
mkdir -p .practice/f03
printf '%s\n' \
  'INFO request=a tokens=4' \
  'ERROR request=b timeout' \
  'INFO request=c tokens=7' \
  'ERROR request=d timeout' \
  'ERROR request=e invalid_json' > .practice/f03/run.log
```

目标是统计每种错误原因出现次数。先把需求拆成三个转换：筛选错误行、提取原因字段、按原因分组计数。每步都先单独执行并查看中间结果，而不是一次写出长管道后只看末尾。

```bash
rg '^ERROR ' .practice/f03/run.log
rg '^ERROR ' .practice/f03/run.log | awk '{print $3}'
rg '^ERROR ' .practice/f03/run.log | awk '{print $3}' | sort | uniq -c
```

第一步应该得到三行。正则中的行首约束确保不会把仅在消息正文中出现 ERROR 的普通行算进去。第二步按这个合成格式提取第三个空白字段，得到 timeout、timeout、invalid_json。第三步先排序，让相同值相邻，再由 uniq 统计相邻相同值。缺少排序时，相隔较远的相同原因不会自动合并成一组。

这个方案依赖日志格式很简单：原因恰好是第三个空白字段，不含空格，也没有转义或嵌套。如果真实日志改成 JSON，继续按第三列提取就不再可靠。工具链正确性不只由工具本身决定，也依赖输入合同。一个处理小样例成功的命令不能直接推广为任意日志解析器。

课程 Python 对照实现通过生成器筛选行，再使用 Counter 计数，最后排序键以固定输出顺序。预期字典包含 invalid_json 一次和 timeout 两次。两种实现帮助你看到，Shell 管道和 Python 函数组合都在建立清晰的数据转换边界，只是执行与数据表示机制不同。

## 第十课：退出状态是独立于文本的结果通道

### 10.1 零与非零是约定，不是自然语言结论

程序退出时返回一个状态值，Shell 可以根据它决定后续动作。通常零表示成功，非零表示失败或某种特殊结果，但具体数值含义由程序定义。搜索工具没有匹配时可能返回非零，这不一定代表工具崩溃；某些检查器发现差异也可能使用特定非零状态表达正常检测结果。

`$?` 读取上一条命令的退出状态，但你再执行其他命令就可能覆盖它。因此要在需要时立即保存到变量。不要先运行一串诊断命令，再读取 `$?` 并以为它还是最早那条业务命令的结果。状态值与标准输出内容也是分开的：程序可以打印“成功”却非零退出，也可以没有任何输出却零退出。

### 10.2 条件执行

`a && b` 表示 a 成功才执行 b，`a || b` 表示 a 非零时执行 b。它们常用于简单流程控制，但不要把复杂业务逻辑挤成许多混合的短路表达式。尤其 `a && b || c` 中，c 可能因为 b 失败而执行，不仅仅表示 a 失败的分支。需要清晰互斥逻辑时，用显式 if 更容易理解。

```bash
if python -m labs.foundations.text_pipeline; then
    printf '%s\n' 'pipeline check completed'
else
    printf '%s\n' 'pipeline check failed' >&2
    exit 1
fi
```

这里的 then 和 fi 是 Shell 语法。条件位置执行的是命令，判断依据是退出状态，不是像 Python 那样直接计算一个布尔对象。这个语言差别需要明确，否则容易把 `if` 当成所有语言里都完全相同的结构。

### 10.3 管道状态与 pipefail

Bash 默认情况下，管道的整体状态通常由最后一个命令决定。若左侧读取失败，但右侧仍成功处理了空输入，整条管道可能显示成功。启用 pipefail 后，整体状态会更容易暴露管道前面阶段的非零退出，但它仍不代替你理解每个阶段的状态含义。

set -e 也不是“脚本从此绝不漏错”的保证。它在条件、管道和其他语法上下文中有规则与例外。初学者应先为关键操作写明确判断，知道哪些非零是预期结果，再使用这些选项作为辅助。机械复制一行严格模式，却从不检查输入合同和失败恢复，仍可能写出危险或误导的脚本。

## 第十一课：搜索文件与搜索内容

### 11.1 找名字与找文本是不同任务

`rg --files` 适合列出搜索范围中的文件，`rg 'pattern' path` 搜索文件内容，find 可按名称、类型和其他元数据选择路径。没有搜到内容，不等于文件不存在；工具可能按忽略规则跳过某些位置，也可能把文件视为二进制。排查时要确认搜索范围、忽略规则和模式，而不是把空输出当作绝对证据。

```bash
find .practice/f03 -type f -name '*.log'
rg -n 'timeout' .practice/f03
```

第一条把带星号的模式通过单引号原样交给 find，让 find 对遍历到的名字匹配。第二条搜索内容并带行号，便于回到具体位置。行号是当前文件布局下的位置，不是永久身份；文件修改后，旧行号可能指向别的内容，因此源码记录最好同时保留版本与符号名称。

### 11.2 正则表达式从最小集合学起

先掌握字面文本、行首行尾、字符类和重复，再考虑复杂组合。若只是寻找固定字符串，可使用工具提供的固定字符串模式，避免把点号、括号等误当正则语法。模式正确性应通过正例与反例同时验证：不仅确认该匹配的行被找到，还确认看起来相近但不该匹配的行被排除。

正则适合某些文本模式，不是所有嵌套格式的通用解析器。JSON、Python 源码和复杂日志有各自语法，使用理解格式的解析器通常更可靠。一个正则在你目前看到的五条记录上成功，不证明它理解了所有转义和嵌套情况。

### 11.3 文件名不能总按空格或换行拆分

`for f in $(ls ...)` 会把命令输出再次经历替换、分词和可能的路径名展开，遇到含空格或换行的文件名就可能损坏边界。更可靠的方法是使用明确的路径迭代方式，或采用 NUL 分隔并让下游以同样协议读取。NUL 在常见路径名中有特殊限制，因此适合作为这类工具协议的分隔符。

初学者不必立即掌握所有复杂 find 与 xargs 选项，但必须知道问题是什么：文本展示格式不是无歧义的数据传输格式。对批量文件修改，先用能够保留路径边界的工具或 Python Path 迭代实现，往往比写一个高度压缩的 Shell 循环更安全也更易读。

## 第十二课：命令替换、子 Shell 与输入块

### 12.1 命令替换取得的是输出文本

`$(command)` 运行命令并把其输出用于当前命令的一部分。它不是把一个 Python 对象或任意结构直接嵌入 Shell，而是进行文本替换。尾部换行处理、引用方式和后续分词都会影响结果，所以它适合明确的小型文本值，不适合把任意文件清单当成安全数组传输。

如果替换内容来自不可信输入，不应再把它交给 eval 进行二次解释。eval 会让数据重新变成 Shell 代码，使原本只是文本的分号、替换和重定向获得执行含义。多数课程启动器都可以通过参数数组或直接函数调用实现，无需使用 eval。

### 12.2 子 Shell 的状态不自动回传

括号分组通常在子 Shell 环境中执行，里面的 cd 和变量修改不会按一般方式改变外面的父 Shell。这个行为适合临时进入某个目录执行命令，再回到原环境。但若你期待括号中的赋值在后面仍可见，就会产生误解。函数与子 Shell 也不应混为一谈，它们对状态作用域的影响不同。

```bash
original_dir=$PWD
( cd .practice/f03 && pwd )
printf '%s\n' "$PWD"
```

最后输出仍应是外层当前目录。这个实验没有依靠再执行一次 cd 返回，因为外层从来没被子 Shell 改变。理解这种状态边界后，你就能解释为什么某些脚本中“已经 cd 了”却没有影响调用者。

### 12.3 Here document 的引用决定是否展开

Here document 可以把多行文本作为命令输入。结束标记是否引用，会影响内容中的变量和替换是否被 Shell 处理。若你要原样写一段包含美元符号或反引号的代码，引用结束标记通常能避免意外展开。写入仍可能覆盖目标，因此文件路径和内容都要明确。

```bash
cat > .practice/f03/literal.txt <<'DATA'
This line contains $HOME literally.
The text is not a shell command.
DATA
```

这里文件中保留 `$HOME` 字面内容，而不是当前主目录。结束标记需要按语法单独出现，缩进和额外空白可能改变匹配。对于要交付给别人运行的长脚本，直接保存为清晰文件通常比在一条命令中嵌套多层引用更容易审阅。

## 第十三课：从一条命令走向一个可维护脚本

脚本应当有明确输入、输出、工作目录约定、依赖、失败行为和副作用范围。最小脚本也可以遵守这些要求：接受一个日志路径，确认文件可读，调用一个解析程序，将机器可读报告放在标准输出，诊断写到标准错误，失败时返回非零状态。不要让脚本默默依赖你当前终端里某个未记录变量。

脚本第一行常见 shebang 用于告诉系统直接执行时采用哪个解释器。使用 `bash script.sh` 则明确由当前选择的 Bash 读取它。`sh` 不保证支持 Bash 的所有扩展，因此不能把 Bash 数组等语法写进脚本后随意改用 sh 运行。文件是否具有可执行权限与解释器能否读取它也是不同条件，F04 会继续说明。

对复杂数据逻辑，Shell 更适合负责启动与连接，Python 更适合承担结构化解析、合同验证和可测试计算。这个分工不是语言优劣判断，而是让每一层承担擅长的责任。若你发现一行命令需要多层转义才能表达一个 JSON 字段操作，通常值得把它写成一个明确的 Python 函数。

脚本中的错误处理还应考虑是否已经产生副作用。前一步创建了部分输出，后一步失败时是否需要清理？重新运行会覆盖还是追加？同一个任务重复执行会不会产生两份记录？这些问题与后面的幂等、事务和恢复相连，不能仅靠 set -e 自动解决。

## 第十四课：四个完整故障演练

**演练一：含空格的路径。** 创建一个名为 `two words.txt` 的小文件，分别通过未引用和引用的路径读取。用参数显微镜确认接收程序到底看见一项还是两项。修复后再用空字符串、星号字符和中文路径做边界测试，确认修复针对的是参数边界，而不只是某个特定名字。

**演练二：诊断污染 JSON。** 写一个小程序先打印进度，再打印 JSON，把它交给 JSON 解析器。观察失败位置。将进度改到标准错误后，机器输出恢复为单一 JSON。这个练习说明结构化接口的可靠性需要从输出通道设计开始，而不是下游不断尝试跳过前几行。

**演练三：管道前段失败被掩盖。** 让前段读取一个不存在的练习文件，后段只统计输入行数。比较默认管道状态与明确错误检查。观察后段输出零并不证明输入文件合法为空，也可能是上游根本没成功读取。修复应让空数据与读取失败保持不同状态。

**演练四：重定向顺序改变。** 用同时写 stdout 和 stderr 的程序分别运行两种顺序，把文件内容与终端内容记录成表。先预测，再执行。掌握标准是能用描述符连接解释结果，而不是只背“二杠一放最后”。

**演练五：未排序的相邻计数。** 让相同错误原因被其他原因隔开，直接运行 uniq 计数，再加入 sort。解释 uniq 的合同是相邻分组，而不是全局哈希聚合。工具没有出错，是你对工具承担的责任理解错了。

## 第十五课：十二道习题与参考答案

### 题一：写出参数列表

预测 `python -c 'import sys; print(sys.argv[1:])' a 'b c' ""` 的列表。答案是三项：a、b c、空字符串。空字符串仍是一个参数，因为双引号保留了边界。把最后引号删掉后，没有相应文本，也就不再提供同一个空参数。

### 题二：变量引用三种结果

令变量包含两个词和一个星号，分别观察单引号、双引号和无引号展开。参考答案：单引号保留美元符号名称；双引号使用变量值但保留一个参数；无引号可能分词并进一步展开路径。具体无引号结果依赖当前目录内容，因此应在自己创建的固定夹具目录验证。

### 题三：保存退出状态

```bash
python -c 'raise SystemExit(7)'
status=$?
printf 'status=%s\n' "$status"
```

预期保存七。若先运行其他命令再赋值 status，读到的可能是后者状态。答案需要说明状态通道独立于程序有没有打印文本，不能通过查找输出中是否出现“error”来代替退出状态判断。

### 题四：分开两个输出流

```bash
python -c 'import sys; print("data"); print("warning", file=sys.stderr)' \
  > .practice/f03/data.txt 2> .practice/f03/error.txt
```

参考验收：data 文件只有正常结果，error 文件只有诊断。再改变重定向顺序并合并，说明连接如何变化。目录必须事先建立，重定向失败时不要误以为 Python 业务代码已经执行。

### 题五：精确筛选错误行

给日志加入 `INFO message=ERROR`，要求它不被计入错误行。答案使用行首和后续分隔约束，例如 `^ERROR `。只搜索 ERROR 子串会误收。完整验证应包含真正错误行、正文含 ERROR 的普通行、空行及相似前缀。

### 题六：全局错误计数

完整 Shell 参考管道见第九课。解释 sort 与 uniq 的不同责任，并用 timeout、other、timeout 三行构造缺排序的反例。若只测试已经按原因排列的数据，错误实现可能碰巧通过，因此测试夹具必须破坏隐藏的有利条件。

### 题七：用 Python 保留结构化语义

```python
import json

line = '{"message":"a b", "tokens":2}'
record = json.loads(line)
if type(record.get("tokens")) is not int or record["tokens"] < 0:
    raise ValueError("invalid tokens")
print(record["tokens"])
```

此例先解析 JSON 语法，再验证业务字段，不用空格切分猜列位置。字符串包含空格不会破坏解析。答案还应指出合法 JSON 并不保证字段类型正确，布尔值也不应自动作为整数 token 数接受。

### 题八：找文件而不提前展开模式

```bash
find .practice/f03 -type f -name '*.log'
```

引号使模式交给 find。去掉引号后，Shell 可能先用当前目录中的文件展开星号，使 find 接到不同参数。测试时可在当前目录创建一个匹配文件，观察参数变化，而不是只在没有匹配的目录里运行后认为两种写法永远等价。

### 题九：脚本中的工作目录

设计脚本接受显式输入路径，不依赖它自己的所在位置。参考思路是让调用者传入路径，脚本原样作为一个带引用的参数传给解析程序，并在帮助说明中写清相对路径以调用目录为准。若读取随脚本分发的资源，则另建资源定位规则，不要把两类路径混用。

### 题十：避免命令字符串二次解释

```python
import subprocess
import sys

argument = "two words; literal text"
completed = subprocess.run(
    [sys.executable, "-c", "import sys; print(sys.argv[1])", argument],
    text=True, capture_output=True, check=True,
)
assert completed.stdout.strip() == argument
```

分号在这里是一个参数内的普通字符，不会因为其外观像 Shell 控制符就启动另一条命令。原因是参数列表与 shell=False 的执行方式没有让 Shell 二次解析。这个例子是教学说明，不应由此扩大成所有被调用程序对输入都绝对安全；接收程序仍有自己的解析规则。

### 题十一：识别混合短路的陷阱

解释为什么 `a && b || c` 不一定等同于“a 成功执行 b，否则 c”。答案是 a 成功而 b 失败时，c 也可能执行。若需要按 a 的状态选择互斥分支，应使用明确 if，并另外定义 b 失败时怎样处理。把流程画成三种状态比背运算符优先级更容易发现问题。

### 题十二：提交一个可组合日志报告器

要求读取合成日志，输出固定 JSON，诊断独立，空输入合法，错误格式明确失败。参考核心可以使用本卷 text_pipeline 的 error_counts，再由外层 json.dumps 输出。验收应分别测试正常数据、空输入、无错误记录、格式不符合合同、读取失败以及被下游解析器成功接收。必须说明当前简单空白日志格式的限制，不能把它当任意生产日志解析器。

## 第十六课：从空文件构建一个有合同的小脚本

### 16.1 先定义参数语法，再写循环

现在把前面的知识组合起来。目标脚本接受一个输入文件路径，统计文本记录数并输出JSON；路径可以包含空格，缺失或未知参数应明确失败；脚本不修改输入文件，也不自行扫描整个磁盘。这个范围很小，却已经要求你理解参数边界、位置参数、条件判断、输出通道和退出状态。

脚本启动后，Shell使用位置参数保存调用者传入的参数。第一个是美元符号加一，第二个是美元符号加二；参数数量可通过相应特殊参数查询。shift把已经处理的前部参数移走，让后续参数成为新的第一项。这里的移动发生在脚本自己的参数视图中，不会回头修改调用者原来的命令历史。

解析选项时必须先检查是否还有对应值，再读取第二项。否则用户只输入选项名却忘记路径时，脚本可能得到空值，或者在某些严格设置下直接产生难读错误。明确报“这个选项需要一个路径值”，比让下游文件读取报错更贴近真正原因。未知选项也应拒绝，不能默默忽略拼写错误后使用默认配置。

```bash
#!/usr/bin/env bash
input=''
while [ "$#" -gt 0 ]; do
  case "$1" in
    --input)
      if [ "$#" -lt 2 ]; then
        printf '%s\n' '--input requires a path' >&2
        exit 2
      fi
      input=$2
      shift 2
      ;;
    *)
      printf 'unknown argument: %s\n' "$1" >&2
      exit 2
      ;;
  esac
done
if [ -z "$input" ]; then
  printf '%s\n' 'missing --input' >&2
  exit 2
fi
python -c 'import json,sys; from pathlib import Path; text=Path(sys.argv[1]).read_text(encoding="utf-8"); print(json.dumps({"records":len(text.splitlines())}))' "$input"
```

将它保存到自己的练习目录，用bash显式运行。最后的路径参数加双引号，因此即使包含空格，也仍是Python收到的一个参数。Python部分由单引号保护，Shell不会把其中Python语法当作自己的变量展开。程序错误信息由Python写到标准错误，退出状态继续反映失败；脚本的最后命令就是Python调用，因此这里没有随后一条成功打印把失败状态覆盖掉。

### 16.2 逐轮追踪参数解析

调用时提供选项名和一个包含空格的路径，参数数量起初为二。case检查第一项，匹配输入选项；数量足够，于是把第二项内容赋给input；shift二后参数数量变成零，循环结束。接下来检查input是否为空，再启动Python。你应该把每一轮的参数数量、第一项、第二项和input列成表，这与Python循环状态追踪采用同样方法。

若用户输入一个未知选项，程序在启动Python之前就返回状态二，并把错误说明写到标准错误。若文件路径存在但编码错误，则参数解析成功，失败发生在Python读取文本阶段。若文件合法且为空，JSON中的记录数是零，退出成功。这三个结果分别对应参数合同失败、数据读取失败和合法空数据，不能被合并成同一个“没有结果”。

这里没有加入所有可能选项，也没有尝试成为通用命令行解析库。随着参数变多，重复写这种Shell解析会增加维护成本，此时可以把解析迁到Python argparse。先亲手理解简单解析过程，再使用库，才能读懂库替你承担了哪些责任，而不把解析器视为无法解释的黑箱。

### 16.3 为什么转发参数要特别对待

一个包装脚本经常需要把自己的剩余参数交给另一个程序。带双引号的特殊参数集合能逐项保留原始边界，而把所有参数先拼成一个字符串会丢失边界信息。两个原参数分别为“a b”和“c”，与两个原参数分别为“a”和“b c”，若简单用空格拼接，都可能显示为相同文本，之后无法可靠恢复原结构。

因此转发参数的目标应该是保留序列，而不是制造一条看起来像原命令的字符串。Bash数组也遵循同样思路：每个元素对应一个参数，在展开整个数组时使用能够保留逐元素边界的引用形式。Python的subprocess参数列表更直接地体现这种结构。理解这一点，是从复制启动命令走向编写可靠启动器的关键。

### 16.4 测试命令与普通方括号语法

在脚本中看到方括号，不要自动套用Python列表含义。常见单方括号形式本质上是测试命令的一种写法，要求参数与结束符之间有合适空格；双中括号则是Bash提供的条件语法，规则与单方括号并不完全相同。你可以先在课程脚本中使用清晰的基本形式，再查手册理解扩展，而不是把两者随意替换。

字符串比较、整数比较和文件属性测试也有不同操作。对一个字符串使用数值比较可能报错或产生非预期解释；检查文件是否存在与是否为普通可读文件是不同问题。写条件前先说出完整中文合同，例如“参数数量至少为二”或“路径代表一个普通文件”，再选择对应测试，能够避免只凭符号外观猜语义。

## 第十七课：脚本边界中的进程、清理与数据格式

### 17.1 source与启动子Shell

显式启动bash读取脚本时，脚本通常在子进程环境执行。脚本内改变目录或普通变量不会自动改变调用它的父Shell。source则让当前Shell读取并执行文件内容，因而变量、函数和目录等状态可能直接影响当前会话。虚拟环境激活脚本常需要这种当前环境修改能力，这解释了为什么它通常使用source而不是单独启动另一个bash。

source也意味着被读取文件具有在当前会话执行代码的能力，它不是只读配置解析。不要把任何来源不明的文本文件都当作安全数据直接source。对结构化配置，使用专门解析器并验证字段通常能更清楚地区分数据与代码。这条边界与避免eval是同一个原则：尽量不要让本来只想读取的数据获得语言执行能力。

### 17.2 管道中的变量修改

某些Shell管道组件在子Shell环境执行，因此在管道内给变量赋值，不一定能在外层观察到变化。Bash还存在与相关行为有关的选项和上下文，所以可移植脚本不应依赖未经验证的假设。若目标是累计一份数据，使用明确文件输入重定向、合适的循环结构或Python程序，往往比依赖隐含父子执行语义更清晰。

这个问题与前面“cd为什么需要内建”相互呼应：修改发生在哪个进程，决定谁能观察到状态变化。不要把同一个终端窗口里显示的所有命令当成共享一份可变状态。管道中的每个程序有自己的执行上下文，数据流连接不等于所有局部变量也自动共享。

### 17.3 清理必须知道自己创建了什么

脚本临时创建文件后，失败或中断时可能需要清理。可以使用trap等机制注册退出时的处理，但清理命令必须限定到自己创建并记录的具体资源。不要为了方便而删除整个共享目录，也不要在路径变量可能为空时拼出宽泛通配符。清理逻辑本身也是代码，也需要输入合同和测试。

更可靠的结构是先创建专用临时目录，立即保存其路径，所有中间文件都放在其中，退出时只清理这一目录。若清理失败，应保留足够信息供人工判断，而不是隐藏所有错误。对于需要长期保留的结果，要在任务成功后按明确规则移动或替换到正式位置，不能把最终交付与临时垃圾混在一起。

### 17.4 标准输入一次只能承担清楚定义的角色

当你使用Python从标准输入读取源码时，同一个标准输入通常就不能再同时作为业务数据流自由使用。比如把一段Python源码通过输入块交给解释器，又期待脚本的input读取管道中的另一份数据，容易产生角色冲突。解决方法是把源码保存为文件或使用明确的命令参数入口，让标准输入专门用于数据。

同样，一个程序若既从键盘询问交互问题，又希望在管道中处理数据，就需要设计非交互模式。自动化任务不能依赖无人回答的提示，否则看起来会像程序卡住。可靠CLI应让必要信息通过参数、配置或标准输入的明确格式传入，并在缺失时及时失败，而不是无限等待。

### 17.5 排序与编码的环境依赖

文本排序规则可能受locale影响，某些工具的字符分类与大小写处理也依赖语言环境。若你要生成可复现的机器报告，应明确选择排序规则，而不是依赖操作者当前终端设置。为单次命令设置稳定环境比修改整台机器的全局配置更容易控制影响范围。

但“稳定的字节顺序”不一定就是用户期待的自然语言顺序。工程报告、文件清单和用户界面可能需要不同规则。先说明目标，再选择实现，才能避免把某一种排序当作唯一正确答案。这个区分会在检索排名、日志聚合和评测结果比较中继续出现。

### 17.6 给脚本建立行为测试矩阵

不要只测试一次正常输入。对本章的小报告器，至少建立以下情况：路径普通且文件非空，路径含空格，文件合法但为空，缺失选项值，未知选项，路径不存在，内容不是约定编码，以及下游程序解析输出。每个情况都写明预期标准输出、标准错误和退出状态，三个通道分别核对。这样才能发现“报错文字正确但退出零”或“返回非零但仍输出半份JSON”之类接口问题。

测试还应该从不同当前目录启动脚本，确认相对路径合同与帮助说明一致。若你承诺输入相对调用目录，就不能在脚本内部偷偷切到源码目录再解释输入；若你承诺资源相对工程目录，就应显式建立这个根。两种合同分别测试，不把它们混成一个偶然可运行的路径。

最后做一个负向控制：临时去掉路径参数外的双引号，确认含空格测试会失败；把诊断改到标准输出，确认下游JSON解析测试会失败；把失败后的状态错误改成零，确认状态测试会失败。只有测试能抓住你故意制造的目标错误，它才真正提供相关保障。恢复正确实现后再运行全部矩阵，这就是从“我觉得脚本没问题”走向可验证结论的过程。

测试夹具只使用你创建的小文件，并把每次预期保存为可阅读记录。不要把当前目录恰好没有空格、数据恰好已经排序、网络恰好稳定当成程序合同。主动打破这些有利条件，才能判断脚本究竟依赖了哪些没有写出来的前提。

## 第十八课：从 Shell 技巧走向可推导的执行模型

学习到这里，你已经可以用五个问题拆解任意命令：由哪个 Shell 解析，最终程序是哪一个，参数列表是什么，标准流连接到哪里，退出状态怎样影响后续动作。接下来阅读框架部署脚本时，先用这五项把通用执行机制看清，再研究模型名称、并行度和缓存参数等业务含义。

不要把熟练等同于能写更长的一行命令。真正可维护的脚本应该让别人能看清责任边界，并能在某阶段失败时快速定位。对于复杂逻辑，拆成具名步骤、保存必要中间证据和保留完整错误，通常比极度压缩更有价值。
