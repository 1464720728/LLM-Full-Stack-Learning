# F13 Docker 从镜像到服务：知道你的程序究竟住在哪里

> 先修 F04、F05、F10。离线模型实验：`python -m labs.foundations.container_model`。真实Docker步骤是明确的手动拓展，不会在自动测试中拉镜像或启动容器。

## 1. 把四个常混淆的名字拆开

Docker是一套构建与运行容器的工具体系；镜像是一份只读模板；容器是从镜像创建出来的运行实例，通常有自己的可写层、配置和进程；Compose是描述并管理一组服务配置的工具。它们不是同义词。

你可以从同一个镜像启动两个容器，一个监听8001，一个监听8002，它们各自有进程状态和可写层。停止其中一个不会自动停止另一个；删除容器不等于删除原镜像；拉取一个新镜像不等于正在运行的旧容器自动升级。

Docker通常采用客户端与daemon分离的架构。终端中的docker命令是客户端，它向daemon请求创建、运行、查看对象。当前连接哪个daemon很重要：本地Docker Desktop、远端Linux Docker或不同context可能管理不同资源。看到一组容器，不代表你正看公司所有服务器。

## 2. 镜像层与容器可写层

镜像由层和配置等内容组成，层可复用。新镜像和旧镜像可能共享大量层，因此拉两个版本不一定下载两份完全独立的数据。tag是可移动的名字，例如某个nightly标签今天和明天可能指向不同内容；digest标识具体内容，适合复现时固定。

容器运行时对文件的修改通常落在可写层。删除这个容器后，那些未放到持久存储的修改就不再属于新容器。只停止再启动同一个容器，其可写层通常仍在。把stop和rm区分开，才能预测数据是否保留。

离线模型使用image字典、writable字典和volume字典。第一个容器把/app/version改成temporary-v2，把/data/progress写成lesson13；第二个新容器复用原镜像和同一个volume，因此版本回到v1，而progress仍是lesson13。

它是生命周期概念模型，不模拟真实overlay filesystem、权限、copy-on-write粒度和mount优先级。不要把字典查找的性能推断成真实Docker读写速度。

## 3. Volume、bind mount和构建上下文

volume由Docker管理，适合持久数据。bind mount把宿主机某个路径映射到容器路径，适合开发源码或明确的数据目录。容器里的路径可能与宿主机完全不同，所以“/data”必须同时说明位于哪一侧。

bind mount可以只读。读取模型权重或输入数据时，若程序不需要修改它们，可以使用只读挂载，减少误改。运行用户的UID/GID与目录权限也会影响读写，不能把所有permission denied都归咎于Docker。

构建上下文是docker build可发送给构建器的文件范围。若在含巨大权重和密钥的目录直接build，又没有正确.dockerignore，可能把不必要内容送入构建上下文。`.gitignore`与`.dockerignore`解决不同工具的输入筛选，不会自动替代彼此。

## 4. 用课程日志工具构建一个小镜像

本卷提供 `labs/foundations/Dockerfile`，从仓库根目录构建：

```bash
docker build -f labs/foundations/Dockerfile -t llm-course-foundations:local .
docker run --rm llm-course-foundations:local
```

这是明确需要已安装Docker、可获得基础镜像的操作；教材自动验证没有执行它。镜像只复制labs包和foundations子包，不复制整个仓库，不安装GPU依赖，不需要GPU。默认运行日志分析demo，完成后退出；`--rm`只删除这次自动创建的容器，不删除镜像。

Dockerfile中使用Python 3.12系列基础标签以表达兼容范围；正式复现实验应记录构建时解析出的digest，不能把可变标签视为永远相同。课程没有编造一个未核查的digest。

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY labs/__init__.py /app/labs/__init__.py
COPY labs/foundations /app/labs/foundations
USER 10001:10001
ENTRYPOINT ["python", "-m", "labs.foundations.log_project"]
```

JSON数组形式ENTRYPOINT直接描述可执行文件和参数，避免额外Shell层的引号与信号语义。这个小镜像不需要写/app，非root用户足够。若增加输出挂载，要确保挂载目标对该用户可写，而不是直接改回root掩盖权限设计。

## 5. 端口、监听地址和容器网络

端口发布`-p 127.0.0.1:8765:8765`把宿主机回环8765映射到容器8765。冒号左右分别是宿主机和容器视角。容器内服务若只绑定容器的127.0.0.1，普通bridge映射不一定能到达它；生产容器常在容器内绑定0.0.0.0，再由宿主机发布地址控制外部可达性。

本卷任务服务为了本地学习固定绑定127.0.0.1，所以Docker演练选择不监听端口的日志工具。不要为了让示例“看起来完整”把一个未鉴权教学服务默认暴露到所有接口。以后服务卷会明确设计容器内监听与宿主机发布的组合。

`docker network ls`列网络对象；`docker compose ls`列Compose项目；`docker ps`列容器。它们回答不同问题，没有谁是“更完整的全部Docker列表”。

## 6. 容器不是完整虚拟机，也不是万能保险箱

Linux容器共享宿主内核，同时通过命名空间、cgroups和权限等机制组织隔离与资源限制。镜像里的用户空间与宿主内核共同决定行为。容器可以限制CPU和内存，但GPU可见性、显存占用和公司调度规则需要另外处理。

避免给课程实验使用privileged、挂载Docker socket、挂载整个宿主根目录等高权限设置。它们可能让容器获得远超学习所需的控制。不是因为课程代码“应该没问题”就可以忽略权限边界。

Docker组访问在许多部署中相当于很高的主机控制能力，因此不能把加入docker组当作无风险的普通文件权限调整。公司服务器应沿用管理员认可的使用方式；若需要sudo docker，脚本中每条docker调用的权限问题要有明确方案。

## 7. 日志、停止与资源清理

`docker logs 容器名`读取容器标准输出/错误的日志；`docker stop 容器名`请求停止；`docker rm 容器名`删除已停止容器；`docker image ls`查看镜像。清理只指向你明确创建的对象，课程不使用全局prune或批量删除他人资源。

前台启动容器时，当前终端会附着其输出；`-d`表示后台运行并返回容器ID。后台不是“不会占资源”，模型服务即使没有请求也可能持续占显存。用完GPU实验后应停止自己的实例，验证资源释放。

容器重建后依赖不见了，是因为你只在旧容器可写层临时安装。可复现依赖应写进Dockerfile或明确环境文件；容器运行中手动修复可以用于定位问题，但要把最终修复回写到可重建配置。

## 8. 八个练习与参考答案

**F13-1 生命周期预测。** 修改容器内文件，stop/start同一容器与rm后创建新容器分别怎样？答案：前者通常保留可写层，后者从镜像重新开始；volume可独立保留。

**F13-2 tag与digest。** 为什么复现nightly时应记录digest？答案：tag可移动，digest固定内容；本地名字与内容标识不是一一永恒对应。

**F13-3 只读挂载。** 设计一个只读取输入日志的容器调用，输入bind mount为只读。验收：不挂载整个用户目录，不把密钥放进镜像。

**F13-4 构建边界。** 解释为什么只COPY课程需要的包比COPY整个仓库更清楚。答案：缩小输入范围与意外带入内容，但.dockerignore仍用于减少构建上下文传输。

**F13-5 端口视角。** 宿主映射8766:8765时，客户端访问哪个？答案：宿主8766；容器服务监听8765。再解释容器内localhost不是宿主localhost。

**F13-6 故障分类。** 运行失败分别出现镜像不存在、权限拒绝、程序异常。验收：定位拉取/daemon访问/应用执行层，不一律重新安装Docker。

**F13-7 可复现报告。** 构建并运行课程镜像，记录镜像ID、基础digest、命令和输出。验收：不把“构建成功”宣称为所有宿主平台都已验证。

**F13-8 Compose阅读。** 打开提供的compose.yaml，解释service、image、build、command与profiles。答案：profile使练习服务显式选择；up启动的是实例，不是“安装镜像到主机系统”。

## 9. 第一次观察 Docker：先定位控制面，再运行程序

在任何 docker run 之前，先确认客户端连接的服务端。命令行工具存在，只说明客户端可执行文件可被找到；daemon 未运行、权限不足或 context 指向另一台机器，都可能使操作失败。客户端与服务端可以不在同一个操作系统环境里，尤其在 Windows Docker Desktop、WSL 与远端 Linux 混合使用时，更要记录实际视角。

```bash
docker version
docker context show
docker context ls
docker info
docker ps
docker ps -a
```

version 常同时展示客户端和服务端信息，若只有客户端成功而连接服务端失败，应先处理连接层。context show 表示当前上下文，context ls 列出已配置目标，info 展示服务端环境。ps 默认关注运行中的容器，带 -a 包括已停止实例。它们都是观察命令，但输出可能含主机路径与环境信息，分享时只保留诊断所需部分。

Docker context 的切换会改变后续命令控制的对象集合。你在 PC 终端执行命令，不代表实际容器一定运行在 PC；若连接远端 daemon，bind mount 的宿主路径也通常由 daemon 所在机器解释，而不是从客户端电脑自动上传。这个区别能解释“本地明明有文件，容器却挂载不到”的常见问题。

镜像仓库 registry 保存可拉取镜像，daemon 保存本地已有镜像与容器，客户端发出控制请求。三个角色又是不同层次。docker pull 的网络失败可能发生在访问 registry，docker ps 的失败可能发生在客户端到 daemon，容器内部访问 API 的失败则是第三条网络路径。不要把所有网络错误都归为“Docker 断网”。

第一次实验只运行课程日志工具，避免同时引入 GPU、服务端口、模型下载和数据库。这样若失败，可以逐层判断基础镜像获取、构建上下文、Python 导入或应用输出。等这些层清楚后再增加挂载与网络，每次增加一个维度更容易定位原因。

## 10. 镜像、容器、进程的完整生命周期

镜像是创建容器所需的文件系统内容与配置。docker create 建立容器配置和可写层但不一定启动主进程，docker start 启动已有容器，docker run 则把创建和启动组合起来。容器的生命状态与主进程关联：主进程退出后，容器不再运行，但其记录和可写层可以继续存在，直到明确删除。

同一个镜像可以产生多个容器，它们共享只读基础内容，但有独立运行配置与可写层。一个容器安装了额外包，不会自动修改另一个，也不会自动更新原镜像。重建新容器时，那些临时安装不在模板里就消失。调试时可以临时操作，但最终修复必须进入 Dockerfile 或明确依赖声明才能重现。

stop 与 rm 是两个不同动作。stop 请求主进程结束，并按工具设置等待后采取进一步停止动作；rm 删除容器对象及其可写层。restart 是停止再启动同一容器，不等于重新构建镜像。pull 新标签只更新本地镜像引用，也不会让已经运行的实例自动换成新代码。

| 动作 | 镜像 | 容器对象 | 主进程 | 容器可写层 |
|---|---|---|---|---|
| pull | 获取或更新本地引用 | 不创建 | 不启动 | 无新层 |
| run | 使用已有或取得镜像 | 创建 | 启动 | 新建 |
| stop | 保留 | 保留 | 结束 | 保留 |
| start | 保留 | 复用 | 再启动 | 复用 |
| rm | 通常保留 | 删除 | 应已停止或按明确操作处理 | 删除 |

表格描述常见基础路径，挂载卷有独立生命周期，不能混入容器可写层。尤其匿名卷、命名卷与不同删除选项的组合有各自规则，清理前应查看实际 mounts 与命令帮助。不要把“卷通常独立保存”扩张成“任何命令都永远不会删除卷”。

容器内第一进程还承担信号与子进程管理相关责任。使用 exec 形式入口能减少额外 Shell 层对信号转发的影响，但不自动让任意程序正确处理所有信号。长期服务应响应停止请求、停止接收新任务、等待或取消在途工作、保存必要状态，再退出。容器工具只能发送信号，业务清理仍由应用实现。

## 11. 分层文件系统：覆盖不是修改模板

镜像层可以看作一系列文件系统变化的组合，运行时再加容器可写层。读取路径时看到组合后的视图，写入通常落在可写部分。具体实现涉及存储驱动或镜像存储后端，不应把它理解成每次 run 都复制一整份镜像到新目录，也不能把 Python 字典模型当成真实内核实现。

覆盖一个镜像里已有文件，容器看到新内容，原镜像仍保留原版本。删除镜像里的文件，容器视图中可以把它隐藏，但不意味着基础只读层的字节已从本地所有镜像对象中消失。这也是为什么在 Dockerfile 前一层复制秘密、后一层删除，不能安全地认为秘密从镜像历史中完全不存在。

构建缓存按步骤与输入复用结果。把变化很频繁的源码放在安装稳定依赖之前，可能导致后续昂贵步骤经常重跑；把依赖声明先复制并安装，再复制源码，通常更利于缓存。但缓存不是可复现性的替代品：远端依赖或可变标签变化、构建参数不同，都可能改变结果。缓存命中只是复用已有产物。

课程 Dockerfile 不安装额外第三方依赖，因为默认日志项目仅需要标准库。它只复制 labs 的包入口与 foundations 子目录，减少实际镜像内容。构建上下文仍是仓库根目录，仓库当前没有根级 .dockerignore；若你在个人副本加入大权重或私密文件，应先在自己的构建方案中设置排除规则并检查上下文，不能只因 COPY 范围小就忽略发送给构建器的输入边界。

镜像 tag 是方便人的名称，digest 是内容标识。用 python:3.12-slim 表示一个兼容系列，但该标签随上游维护可能指向新内容。固定 digest 有助于复现实验，却也意味着更新修复需要主动计划。记录构建时实际解析结果和日期，比编造一个未核查摘要更诚实，也更便于之后比较环境变化。

## 12. Dockerfile 每个指令的阶段与作用

FROM 选择基础镜像，从而获得用户空间文件、Python 与所需系统库。它不把宿主机内核复制进去。WORKDIR 设置后续工作目录，并影响相对路径与默认运行目录。COPY 从构建上下文复制文件到镜像，而不是从任意宿主路径随意读取。USER 设置后续运行身份；ENTRYPOINT 定义容器默认启动的可执行程序及参数。

课程的两条 COPY 分别建立 labs 包标识与 foundations 内容，目标路径都在 /app。运行时 Python 从 /app 作为工作目录解析模块，能找到 labs.foundations.log_project。若把 WORKDIR 改到别处却不调整模块安装或搜索路径，可能出现 ModuleNotFoundError。镜像构建成功只说明 Dockerfile 步骤完成，不保证默认启动路径一定正确。

USER 使用数字 UID 与 GID，说明进程不以容器 root 身份运行。数字身份与宿主目录所有者权限相交时，可能导致 bind mount 输出不可写。修复应明确谁拥有输出目录、使用什么组权限或运行身份，而不是一遇到错误就把所有路径 chmod 成全员可写。F04 的权限位知识在容器中仍然适用。

ENTRYPOINT 与 CMD 可以共同定义可执行程序和默认参数，具体覆盖行为需要理解。课程只设置 ENTRYPOINT，因此 run 后追加参数会作为该 Python 模块的参数。若想临时运行别的程序，可明确覆盖 entrypoint；不要以为在镜像名后写 bash 就一定替换原入口，它可能只是成为 log_project 的一个无效参数。

```bash
docker run --rm --network none --entrypoint python llm-course-foundations:local -c 'import os,sys; print(os.getcwd()); print(sys.executable)'
```

这条命令明确把入口换成 python，后面的 -c 和代码字符串成为 Python 参数。network none 表明这个观察不需要网络，--rm 让一次性容器退出后删除。它只读取进程目录与解释器路径，不修改挂载，也不访问 GPU。实际运行依赖你已经构建镜像，未构建时应先完成前面步骤。

RUN 在构建阶段执行，ENTRYPOINT 在容器运行时执行，二者时间不同。ENV 写入镜像默认环境，运行时可以覆盖；ARG 通常用于构建参数，不能当成安全秘密存储。把 API key 放入构建参数或层命令可能留下记录，课程应在运行阶段通过合适受控方式提供凭证，而不是烘焙进公开镜像。

## 13. 挂载两侧路径与数据所有权

bind mount 的 source 是 daemon 宿主侧路径，target 是容器内路径。容器程序只看到 target，不知道你在宿主上把目录叫 learning、data 还是别的名字。挂载会覆盖目标位置原本可见的内容，因此把空宿主目录挂到 /app，可能让镜像中的源码在容器视图里消失。它没有删除镜像文件，只是该位置被另一个文件系统视图遮住。

命名卷由 Docker 管理，适合应用长期保存的数据；bind mount 适合明确与宿主共享的源码或输入文件；tmpfs 适合短期内存文件，不用于持久保存。三者生命周期不同，选择时先问数据谁拥有、是否需要跨容器重建保留、谁负责备份与删除。不要只因为某个短选项写起来方便就决定存储结构。

只读挂载限制容器通过该挂载修改输入，适合日志、模型权重和课程数据。输出应放到另一处明确可写目录。把输入与输出分离有助于验证“不改原始数据”的合同，也减少误删除范围。只读挂载不是整体安全沙箱，容器其他权限与网络能力仍需按任务配置。

挂载路径应使用自己创建的专用目录，避免挂载整个用户主目录或服务器根目录。读取一个日志文件不需要访问 SSH 密钥、其他工程或公司数据。配置中出现 Docker socket 挂载时尤其要理解其控制能力，它可能让容器管理宿主上的其他容器资源，远超普通文件共享。

```bash
mkdir -p practice-data
printf '{"request_id":"demo","latency_ms":10,"tokens":3,"status":"ok"}\n' > practice-data/input.jsonl
docker run --rm --network none --mount "type=bind,source=$(pwd)/practice-data,target=/data,readonly" --entrypoint python llm-course-foundations:local -c 'from pathlib import Path; print(Path("/data/input.jsonl").read_text(encoding="utf-8"))'
```

这组命令只在你自己的课程副本创建一个小输入目录。`$(pwd)` 由宿主 Shell 展开为当前绝对路径，双引号保持含空格路径作为一个参数。Python 字符串里的 /data 属于容器视角。若使用 Windows PowerShell，路径与 Shell 展开语法需要采用对应写法，不能逐字符照搬 Bash；本段明确是 Linux 或 WSL Bash 路线。

## 14. 网络的四层观察：监听、容器接口、发布、客户端

服务进程先在容器内某个地址和端口监听，容器网络提供接口与路由，Docker 端口发布把宿主入口关联到容器端口，客户端再连接宿主地址。四层中任意一层不匹配都可能连接失败。先确认进程已启动并监听，再检查容器与宿主映射，最后判断客户端路径，不要一开始就把所有防火墙关闭。

容器里的 127.0.0.1 指向容器自身网络命名空间中的回环。宿主 127.0.0.1 指向宿主，另一容器的 localhost 又是另一份视角。应用配置数据库 host=localhost，在数据库是另一个容器时通常不符合预期。Compose 网络中的服务名可以帮助定位同一项目网络里的其他服务，但仍要确认端口与服务是否就绪。

宿主发布 `127.0.0.1:8766:8765` 表示客户端从宿主回环的八七六六进入，容器服务使用八七六五。左边不写地址时的暴露范围应按 Docker 行为和环境理解，不要默认只对本机开放。教学服务没有认证时，明确限制宿主回环入口是合理默认；真正跨机器访问需要独立设计认证与网络边界。

EXPOSE 是镜像元数据说明，不等于自动把端口发布到宿主。容器内进程监听也不自动意味着外部可达。反过来，发布端口成功也不证明进程已经准备好接收请求。运行状态、监听状态和健康状态是不同概念，诊断时应该分别观察。

本卷任务服务固定本机回环监听，因此课程 Dockerfile 选择一次性日志程序，避免给初学者一个看似可运行却网络语义不匹配的服务容器。若以后改造成容器服务，要显式提供容器内监听配置，并同时限制宿主发布地址；不能只改一端后宣称完整容器部署已经完成。

## 15. Compose 文件逐字段拆解

课程 compose.yaml 的 services 下定义 foundations-log-demo。service 是声明的服务配置，实际运行会产生容器实例；它不等于镜像，也不等于网络对象。profiles 为 practice，表示普通未启用该 profile 的流程不会自动包含它，显式指定服务又有相应启用规则。运行前用 config 查看解析结果，有助于发现路径和变量问题。

```bash
docker compose -f labs/foundations/compose.yaml --profile practice config
docker compose -f labs/foundations/compose.yaml --profile practice run --rm foundations-log-demo
```

build.context 是 ../..，相对于这个 Compose 文件的位置解析，回到仓库根目录；dockerfile 字段再按构建上下文定位课程 Dockerfile。image 给构建结果一个名称。这里没有 command 覆盖，所以沿用镜像入口；如果你增加 command，要理解它与 ENTRYPOINT 的组合，而不是以为会完全替换进程。

network_mode 为 none，表示本次日志演示不需要容器网络；read_only 使容器根文件系统按只读方式运行；cap_drop ALL 去掉额外 Linux capabilities；no-new-privileges 限制通过执行获取新权限；mem_limit 与 cpus 给出小规模资源边界。这些设置服务于具体离线任务，不代表任意应用照抄都能运行。

例如需要写临时文件的程序，在只读根文件系统下可能失败；正确扩展是提供明确 tmpfs 或可写挂载，而不是取消全部限制。需要网络 API 的程序不能使用 none，但应只增加任务真正需要的能力。理解每个字段的目的后，配置才是可维护设计，而不是一份神秘咒语。

Compose 的项目名用于组织相关容器、网络和卷，可能由目录、配置或命令参数决定。两个目录运行相似配置，可能属于不同项目；改变项目名可能创建一组新对象而不是更新旧对象。排查“为什么多了另一套容器”时，应检查项目身份，而不是立即批量删除所有看起来相似的资源。

## 16. 资源限制与共享服务器礼仪的技术基础

容器共享宿主资源，后台运行并不减少占用。CPU 限制影响可用计算配额，内存限制可能使超额进程被终止，磁盘与网络仍有各自瓶颈。docker stats 提供观察线索，但指标含义与采样要结合环境解释。不要把一次低 CPU 截图当作长期没有负载的证明。

GPU 可见性与 GPU 资源控制又是另一层。允许某个容器看到一张 GPU，不等于为它独占分配显存或计算时间；模型加载后即使空闲，也可能持续占用显存。用户的八卡 H100 可以用于需要的实验，但基础 Docker 章节无须默认占 GPU。后续算子与分布式实验应按明确卡数、时长和停止流程运行。

共享服务器上的容器名称应包含自己的任务标识，方便只管理本人实例。停止前先确认容器 id、名称、镜像、创建时间和标签，避免误操作同事任务。不要使用全局 prune 或按模糊字符串批量删除来“清理环境”，因为未运行资源也可能是别人保留的数据或镜像缓存。

日志与卷也消耗存储。一个服务长期输出大量日志，哪怕计算负载很低，也可能填满磁盘。设置适当日志保留、监测数据目录和清理自己的可重建产物，是资源管理的一部分。删除前先区分可重建缓存和唯一实验结果，不能把所有不进 Git 的文件都视为可随时丢弃。

## 17. 四层故障诊断的完整流程

第一层是客户端命令是否存在与语法是否正确。第二层是客户端能否连接目标 daemon，以及是否有授权。第三层是镜像能否取得与构建，包含 registry 网络、基础标签、上下文与 COPY 路径。第四层才是容器应用启动后的 Python 导入、文件权限、配置与业务错误。按层次分流，比遇错就重装 Docker 更有效。

容器立即退出时先看退出状态与日志。一次性日志程序正常完成后退出是预期行为，不应该为了让 docker ps 一直显示它就加无限 sleep。长期服务退出才需要判断是否缺配置、端口冲突或应用异常。理解程序职责后，才能判断容器结束是成功还是失败。

挂载后文件不见时，先检查 target 是否覆盖了镜像内容，再检查 source 属于哪台 daemon 主机。权限拒绝时查看容器运行 UID/GID、宿主目录所有者和模式位、挂载是否只读；不要一律改为 root。只读文件系统错误与普通权限位拒绝是不同线索，应分别解释。

端口连接失败时，先看服务是否运行和监听，再看发布映射，最后检查客户端连接的地址。宿主能访问但远端不能访问，可能是宿主绑定回环或网络策略；容器内能访问自己但宿主不能，可能是发布或监听视角。每次只改一个条件，并记录实际观察，避免把网络配置越改越宽却仍不知道根因。

## 18. 十二道完整实操题：先预测，再观察

本节前几题可以纯 Python 离线完成，后面的 Docker 命令是手动环境练习。执行前确认当前 context、对象名称与磁盘路径。所有命令只涉及自己创建的课程对象；没有 Docker 环境时记录未执行，不把模型实验结果替代真实容器结果。

### 一：可写层不能污染镜像

```python
from labs.foundations.container_model import Container
image = {"/app/version": "v1"}
first = Container(image)
first.write("/app/version", "v2")
second = Container(image)
assert first.read("/app/version") == "v2"
assert second.read("/app/version") == "v1"
assert image["/app/version"] == "v1"
```

答案验证两个实例的可写层独立，原镜像字典未改变。真实存储实现更复杂，但生命周期关系与这个小模型一致；模型不提供性能、权限或内核隔离证据。

### 二：共享卷跨实例保留

```python
from labs.foundations.container_model import Container
image = {"/app/version": "v1"}
volume = {}
first = Container(image, volume=volume)
first.write("/data/progress", "F13")
second = Container(image, volume=volume)
assert second.read("/data/progress") == "F13"
assert first.volume is second.volume
```

共享来自显式传入同一个 volume 对象，不是所有容器默认共用所有文件。换成新的空字典，第二个实例就没有这条进度。

### 三：只停止与新建实例的区别

```python
from labs.foundations.container_model import Container
image = {"/app/version": "v1"}
container = Container(image)
container.write("/app/version", "temporary")
container.running = False
container.running = True
assert container.read("/app/version") == "temporary"
replacement = Container(image)
assert replacement.read("/app/version") == "v1"
```

running 字段只是模型状态，不启动真实进程。它用于手算“同一个对象继续存在”和“创建新对象”的差别，不能作为 docker stop/start 实测。

### 四：查看镜像配置

```bash
docker image inspect llm-course-foundations:local --format '{{json .Config.Entrypoint}}'
docker image inspect llm-course-foundations:local --format '{{.Config.WorkingDir}}'
docker image inspect llm-course-foundations:local --format '{{.Config.User}}'
```

预期分别对应 Python 模块入口、/app 和数字用户。实际值以构建出的镜像为准，若不同，检查你运行的标签是否指向刚构建版本，而不是直接修改教材预期迎合旧镜像。

### 五：用一次性容器观察身份

```bash
docker run --rm --network none --entrypoint python llm-course-foundations:local -c 'import os; print(os.getuid(), os.getgid()); print(os.getcwd())'
```

在该 Linux 镜像中应看到配置的数字身份与工作目录。这里观察的是容器进程身份，不是 Windows 登录账号，也不等于拥有宿主相同用户名的权限解释。

### 六：显式参数传给默认入口

```bash
docker run --rm --network none llm-course-foundations:local --help
```

答案应显示 log_project 的参数帮助，因为镜像已有 ENTRYPOINT，追加参数交给该模块。若你想运行其他程序，需要明确覆盖入口，不能把任意程序名作为尾部参数后期待自动替换。

### 七：检查实际挂载

```bash
docker create --name f13-mount-inspect --network none --mount "type=bind,source=$(pwd)/practice-data,target=/data,readonly" llm-course-foundations:local
docker inspect f13-mount-inspect --format '{{json .Mounts}}'
docker rm f13-mount-inspect
```

这题要求前面已创建 practice-data。create 只建立本题对象，不执行应用；inspect 应显示 source、destination 与只读属性。最后只删除明确命名的练习容器，不影响其他对象。

### 八：只读输入的写入失败

```bash
docker run --rm --network none --mount "type=bind,source=$(pwd)/practice-data,target=/data,readonly" --entrypoint python llm-course-foundations:local -c 'from pathlib import Path; Path("/data/new.txt").write_text("x", encoding="utf-8")'
```

本题预期非零退出，表明通过该挂载写入被拒绝。失败属于练习成功条件，不应为了让命令变绿而取消只读。随后检查宿主目录没有 new.txt，补齐状态验证。

### 九：查看 Compose 解析结果

```bash
docker compose -f labs/foundations/compose.yaml --profile practice config
docker compose -f labs/foundations/compose.yaml config --profiles
```

答案解释构建上下文、入口来源、网络关闭、只读根文件系统与资源上限。config 只解析配置，不证明镜像已经构建或容器已经运行；报告中要区分配置检查与执行验证。

### 十：前台运行并检查退出

```bash

docker inspect f13-exit-demo --format '{{.State.Status}} {{.State.ExitCode}}'

```

课程日志 demo 是一次性工作，正常结束后状态为 exited 且退出码为零。没有 --rm 是为了留下对象供 inspect，观察完成后再明确删除；这与前面一次性自动清理的选择不同。

### 十一：保存可复现镜像证据


记录实际输出、构建命令与日期。某些本地构建镜像没有 registry digest，不能伪造一个；镜像 ID 与可拉取仓库摘要用途也不同。证据应按实际对象类型解释。

```bash
docker ps -a --filter name=f13-
docker image ls llm-course-foundations
```

列表用于观察，不应把结果无条件接到批量删除命令。逐个确认练习容器归属与状态，再删除明确对象。镜像保留可供下次复用，是否删除取决于自己的存储需要，不必每次练习结束都重新下载。

## 19. 分阶段项目：把日志分析器变成可重建运行环境

第一阶段在宿主 Python 环境运行日志 demo，记录输出与退出状态。第二阶段阅读 Dockerfile，逐条预测工作目录、用户、入口和包含文件。第三阶段构建镜像并运行同一 demo，比较业务结果而不是期待所有路径与平台字符串完全相同。第四阶段覆盖入口观察环境，确认你的预测与镜像配置一致。

第五阶段挂载只读输入文件，先用简单 Python 读取证明路径可见，再调用实际日志 CLI 处理。不要同时增加文件、网络、数据库和 GPU，否则错误来源难以区分。第六阶段为输出提供专用可写路径，确认运行用户有权限，并验证原始输入未改变。输出使用 F08 的可靠保存机制，而不是把最终文件原地截断后冒险写入。

第七阶段删除旧容器再创建新容器，观察哪些数据消失、哪些挂载数据保留。第八阶段改变源码后重新构建，确认新镜像确实包含变化；仅修改宿主文件不会自动改变已复制进镜像的源码，除非你使用 bind mount 或明确开发同步机制。这个对照能帮助你区分开发模式和交付模式。

第九阶段使用 Compose 运行同一服务配置，检查 profile、网络和资源限制。第十阶段写验收记录：实际 Docker 客户端与服务端、基础镜像摘要、构建命令、运行命令、输入摘要、结果及未验证平台。Win11、WSL 与 Linux 的路径和 daemon 架构不同，未分别执行就不能写成全部通过。

项目目标是可重建，不是把一个手工修好的容器保存成无法解释的黑盒。若你在容器中临时安装包解决问题，回到 Dockerfile 或依赖文件记录最终方案，再从干净构建验证。这样下一次机器更换、容器删除或同事复现时，环境仍能按说明建立。

## 20. 构建上下文与依赖缓存的更细分析

docker build 命令最后的点表示构建上下文目录，不表示 Dockerfile 必须位于当前目录。`-f` 指定 Dockerfile 位置，而 COPY 的源仍按上下文解释。把 Dockerfile 放进 labs/foundations，不意味着 COPY 可以直接按该文件目录随意读取上级任意路径；上下文是构建器允许看到的输入范围。

构建器可能本地运行，也可能远程运行。上下文中的内容需要按构建机制提供给它，因此包含大量模型缓存会增加传输与扫描成本，也可能暴露不需要的数据。只写少量 COPY 可以减少最终镜像内容，却不应被当成上下文隐私控制的唯一手段。个人扩展项目应明确 .dockerignore，并验证排除规则没有把必需源码一起隐藏。

依赖安装的可复现性由多个因素共同决定：基础镜像内容、包版本、系统库、平台架构、构建参数和外部下载来源。固定 Python 主次版本仍可能允许补丁版本变化；只写库名不锁版本可能随时间安装不同实现。课程基础镜像不额外安装第三方包，降低这个阶段复杂度；后续 GPU 环境则需要更详细版本矩阵。

缓存失效不一定是坏事。源码变化后重新复制是正确行为，依赖声明变化后重新安装也是必要行为。为了速度强行使用旧缓存，可能让你以为正在测试新代码，实际上运行旧产物。构建日志应帮助确认哪些步骤复用、哪些重做，验证时还应检查应用版本或文件摘要，避免标签名相同造成误判。

多阶段构建可以把编译工具与运行环境分开，最终镜像只保留需要的产物。它适合有编译步骤的项目，但基础日志工具没有必要为了“看起来专业”增加多阶段。先理解单阶段输入输出，再在实际存在编译依赖、镜像体积或安全需求时引入，才能解释每一阶段为何存在。

## 21. 容器隔离背后的系统概念

Linux 命名空间让进程看到不同的资源视图，例如进程编号、网络接口和挂载树。cgroups 管理资源使用与限制，权限、capabilities 和安全配置控制能做哪些操作。这些机制共同构成容器运行环境，但容器仍共享宿主内核。镜像里安装某个发行版用户空间，不代表启动了该发行版自己的独立内核。

虚拟机通常提供虚拟硬件并运行独立来宾内核，容器则在同一内核上组织进程视图与资源。Windows 上运行 Linux 容器常涉及额外 Linux 环境，因此你看到的宿主视角可能有多层：Windows、WSL 或 Desktop 的 Linux 层、容器。每一层的路径、网络和资源归属都应分清，不能只说“我电脑上的 /data”。

容器 root 与宿主普通用户的关系取决于部署、用户命名空间和权限配置。即使某种配置减少了宿主权限，也不能把 root 容器当作完全无害；高权限挂载或 daemon 控制接口可能扩大能力。课程采用非 root、有限挂载和明确网络需求，是为了让权限与任务匹配，而不是承诺绝对隔离。

镜像来源也属于工程信任边界。运行别人提供的镜像是在执行其中代码，不能只看名字像某个官方项目就相信。应查看官方发布渠道、固定版本与必要摘要，阅读入口和挂载要求。陌生镜像要求 privileged、host 网络或宿主根目录挂载时，先理解原因与替代方案，不要把这些选项当通用排错开关。

容器本身也不是秘密管理系统。环境变量可能出现在容器配置检查或诊断输出中，镜像层和构建历史可能保存构建时信息，挂载文件则受路径权限影响。选择凭证传递方式时应考虑谁能查看 daemon 和宿主，避免把真实 API key 写进 Dockerfile、Compose 示例或公开命令历史。

## 22. 服务就绪、健康检查与依赖顺序

容器处于 running 只说明主进程仍在，不代表服务已加载模型、完成数据库迁移或准备接收请求。健康检查通过应用定义的探测判断某种可用状态，但探测本身也有范围：返回健康不一定证明所有下游依赖都正常，更不证明性能满足目标。应该把存活与就绪含义分别说明。

Compose 启动依赖顺序也不自动等于业务就绪。数据库容器进程已启动时，应用马上连接仍可能失败。可以使用明确健康条件或应用内有界连接重试，但必须保留总超时与错误信息。无限等待“直到能连上”会让部署永久卡住，且掩盖配置拼错等不可恢复问题。

健康检查不应执行昂贵或有副作用操作。每隔几秒发一个真实大模型请求，会消耗算力和费用；每次探测写数据库，也可能产生噪声。选择轻量、能代表服务状态的检查，并明确失败阈值与恢复策略。基础日志工具是一次性任务，不需要伪造常驻健康接口。

重启策略决定进程失败后是否再次启动，但不能修复应用逻辑错误。一个缺必需配置的容器反复重启，只会持续产生相同失败。先读取退出原因，区分临时故障与确定配置错误，再决定是否重试。对会产生外部写入的任务，自动重启还需要幂等与检查点，否则可能重复处理。

停止服务也需要顺序。先停止接收新任务，再等待或取消已有任务，保存必要状态，关闭资源并退出。强制结束可以作为最后手段，但可能留下不确定外部结果。F11 的取消与 F08 的事务知识在容器服务中同样适用，Docker 不会替应用自动完成业务回滚。

## 23. 性能观察与资源选择

容器通常不是性能问题的唯一来源。CPU 配额、内存限制、存储层、bind mount 所在文件系统、网络路径和应用算法都可能影响速度。Windows 与 WSL 跨文件系统访问的成本可能不同，不能把某次慢读取直接归咎于 Python 或 Docker。先把输入位置与执行位置记录下来，再做受控比较。

测量容器性能时，区分首次镜像拉取、构建、进程启动、模型加载与真正请求处理。把这些全部混成一个总秒数，难以判断优化方向。若目标是用户首次运行体验，总时间有意义；若目标是算子吞吐，就应单独测量对应阶段。指标的定义必须与问题匹配。

内存限制触发终止时，应用可能没有机会打印完整 Python 异常。查看容器状态与宿主资源线索，区分应用主动退出、信号结束与资源不足。不要仅凭最后没有 traceback 就认定程序正常完成。退出码、日志和状态信息需要联合解释，具体数值含义也应结合运行时与操作系统。

基础练习只需要 CPU 和小内存，课程 Compose 的边界适合当前日志 demo，不是所有扩展任务的通用配额。若加入大文件排序或 NumPy 矩阵，应重新估算内存与时间，并记录配置变更理由。资源提高应来自输入规模需求，而不是遇到错误就无限加大上限。

## 24. 最终验收与未执行边界

你应能在纸上预测一个文件分别位于镜像、容器可写层、bind mount 和命名卷时，在 stop、start、rm、重新创建后的命运；能解释宿主与容器端口的对应；能从 Dockerfile 看出构建时与运行时动作；能只管理自己的对象。每个预测至少选一个小实验验证，而不是只记术语定义。

本教材自动化验证运行的是 container_model 与其他离线 Python 合同，不会自动拉取镜像、启动 daemon、连接公司 Docker 或占用 GPU。真实 Docker 步骤需要在你的可用环境手动执行并记录。没有执行的 Win11、WSL、不同架构与 GPU 容器组合，都应保持“未验证”状态，而不是因为配置看起来合理就标记通过。

把最终命令、对象名、输入摘要、镜像标识和输出保存在自己的学习记录。完成后检查没有遗留需要停止的服务或占用 GPU 的实例，保留有价值结果，删除明确可重建的个人练习容器。这样你获得的不只是 Docker 命令熟练度，而是能解释程序究竟运行在哪一层、数据由谁持有、失败时如何恢复的工程能力。

### 补充手算：同名路径不代表同一文件

宿主有 `/home/student/data/input.jsonl`，容器把它挂到 `/data/input.jsonl`。程序记录的路径是容器内路径，宿主编辑器打开的是宿主路径；二者通过挂载关系指向相同内容。若你另在镜像中复制一份 `/app/input.jsonl`，它就是不同文件。修改宿主输入不会自动改变镜像复制版，除非重建或程序读取的是挂载路径。

再考虑两个容器分别挂载同一个宿主目录。它们会共享该目录内容，不能因为可写层独立就推断挂载也独立。一个容器写出 report.json，另一个可能读到它；同时写同一路径则可能互相覆盖，需要应用锁、独立文件名或数据库协调。Docker 存储共享没有自动提供业务事务。

如果把目录以只读方式挂到第一个容器，以可写方式挂到第二个，第二个仍可能修改底层内容，第一个随后读取会看到变化。只读限制的是该挂载视角的写能力，不是把底层数据冻结成不可变快照。需要稳定输入时，应使用明确快照、摘要验证或运行期间不修改的合同。

### 补充手算：数字身份与输出权限

设宿主输出目录属于 UID 一千，权限为七五五；容器进程 UID 一万零一。目录所有者可写，组和其他只有读与进入权限，因此容器通常不能在其中新建文件。即使容器内没有名字叫 student 的用户，数字身份仍参与权限判断。错误来自目录权限与身份不匹配，不是文件编码或镜像层故障。

可以按环境选择合适运行 UID/GID、为专用输出目录设置明确组权限，或使用由应用管理的卷。每种办法都要确认其他需要访问的人或进程仍有正确权限。不要把所有目录改成七七七作为默认答案，因为那会扩大写入范围，也让后续无法解释谁应拥有数据。

只读根文件系统与可写挂载可以同时存在。应用代码放在只读 /app，输入只读挂到 /input，输出可写挂到 /output，短期临时文件放到明确 tmpfs。这样的布局让路径用途一眼可见，错误时也容易判断程序是否写错位置。布局本身不复杂，但需要应用把路径做成清楚配置，而不是到处写当前目录。

### 补充：Compose 变量替换与容器环境不是同一件事

Compose 在解析配置时可能用宿主环境或指定文件替换 `${NAME}`，这是配置生成阶段；environment 或 env_file 则向容器进程提供运行环境。某个变量参与前者，不意味着它自动出现在容器里；某个变量进入容器，也不意味着它决定构建上下文。排查配置时先区分哪一阶段使用了该值。

`docker compose config` 展示解析后的配置，因此可能展开敏感值。把完整输出复制到公共讨论前，应先检查是否包含凭证、内部地址或宿主私有路径。对于课程离线配置，字段较少且无密钥；以后接 API 时，应采用明确秘密处理方式，避免把诊断工具输出直接当作可公开附件。

多个 Compose 文件合并可以实现开发与生产差异，但覆盖规则需要按字段理解，不是任意 YAML 后文件简单替换整个前文件。初学阶段使用一份短配置更容易掌握；确有环境差异时，再用 config 检查最终结果，并测试每个变体。配置文件越多，越需要能解释最终生效值来自哪里。

### 补充：镜像能运行不等于应用已经可移植

镜像包含用户空间依赖，但仍受 CPU 架构、宿主内核能力、设备与运行时配置影响。为某个架构构建的镜像不一定能在另一架构原生运行，仿真又可能改变性能与兼容性。课程使用普通 Python 标准库降低差异，但实际跨平台运行仍需要证据，不能只因为“用了容器”就宣称消除了所有环境问题。

GPU 镜像还涉及宿主驱动、容器运行时与用户空间库之间的兼容关系，模型权重和显存需求也独立存在。基础章节不编造当前硬件上已经验证的版本组合；到相应实验时应读取官方支持资料并在小输入上验证，再扩展规模。先掌握镜像、挂载、权限与进程这些稳定机制，会让后续兼容性排查少很多猜测。

最后为自己的容器实验写一个停止条件：成功输出报告后退出，出现配置错误时非零退出，收到停止请求时结束在途工作并清理。不要为了保持容器“在线”而加入无意义无限循环，也不要把一次性任务包装成长期服务后忘记资源。运行形式应服从任务生命周期；能结束、能重建、能说明数据在哪里，比容器列表里一直显示 running 更有实际价值。

每个新实验先写清输入、输出和停止条件，再增加权限或资源，才能保持运行结果可解释。
