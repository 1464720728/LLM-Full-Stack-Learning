# S11 Prefill/Decode 分离：搬走计算，也搬来了状态协议

先修 S02、S03、S10。PD 分离不是“把两台服务器同时开起来”，而是把同一个请求的两个阶段放到不同执行资源上，并把它们之间的状态、所有权和失败语义设计完整。

## 1. 为什么考虑分离

长 prefill 通常会形成较大的矩阵计算；小批 decode 则常受权重/状态访问与启动开销影响。两种工作在同一资源上混合，可能相互干扰：长 prefill 拉长已在输出请求的间隔，decode 又让 prefill 不能连续占用资源。分离允许分别配置硬件、批次与调度目标。

这只是动机，不是性能保证。分离增加 K/V 传输、两个队列、路由和故障处理，还可能降低每个池的利用率。负载很小或网络很慢时，放在同一引擎中反而更简单、更快。

## 2. 请求状态要如何穿过两端

一个完整生命周期至少包括：前端接收；路由到 P；P 分配并计算状态；D 预留目标空间；传输 K/V 与布局信息；D 确认状态可读；D 从正确位置继续生成；释放 P 端临时所有权；最终释放 D 端状态。

这里有两个不同“完成”：P 的 GPU 已完成计算，与 D 的 GPU 已能读取传输结果。CPU 收到“发送已提交”不等于 DMA/RDMA 复制完成。若 D 提前启动 attention，就可能读旧数据；若 P 提前复用源页，也可能在传输中被覆盖。

可以把传输看成一份带版本和长度的契约：请求ID、模型/adapter身份、token范围、层/头分片布局、源/目标页映射、dtype、完成事件以及错误状态。两个池的 TP 不同，状态布局可能需要重排，不能简单把一段字节复制过去。

## 3. 手算传输是否值得

在 `pd_break_even` 的简化模型里，共置 TTFT=`共置排队+prefill`；分离 TTFT=`prefill+D排队+传输`。设 prefill100 ms、共置排队300 ms、D排队30 ms、状态1GiB、传输建立1ms。

有效带宽1 GB/s时传输约1074.74 ms，分离TTFT约1204.74 ms，比共置400 ms更差；10 GB/s时传输约108.37 ms，分离约238.37 ms；50 GB/s约22.47 ms，分离约152.47 ms。这里省略了P池排队、重排、重叠和首token位置等细节，目的是让每个假设可见。

```bash
python -m labs.serving.experiments --lab pd_transfer
```

传输1GiB不意味着显存只多占1GiB：源和目标在一段时间同时持有，可能还有 staging buffer。计划容量时要考虑重叠峰值，不仅是最终稳态。

## 4. 两个队列和背压

如果 P 远快于 D，P 会不断产生等待 D 的状态。没有背压时，传输队列和待接收状态会持续增长。一个可靠系统需要 admission 机制：在接受更多 prefill 前确认 D 的接收能力，或设置有限队列、超时和拒绝策略。

反过来，如果 P 太慢，D 可能空闲。这正对应“prefill请求上限32、客户端发64”一类问题：后32是否排队取决于前端和调度约束，D何时开始工作取决于前32中哪些已经产生可转移状态，而不是等所有32全部完成才必然启动。真实实现可以按请求/块流式转移，但不能凭名称假定存在。

调节两池比例时，要测各自利用率、队列长度、传输等待和端到端SLO。只看P侧prefill tokens/s变高，可能掩盖D侧更大的积压。

## 5. 前缀缓存与分离相互影响

前缀可能在P端命中，D端却没有；也可能D保留上一轮对话状态，P需要计算新suffix。复用决策会影响传输范围和所有权。一个简单实现可传完整必要KV；更复杂实现需要双方交换已存在块的身份和版本。

缓存身份必须跨设备保持可验证。一份旧权重版本的状态，不能因为token相同就接到新权重引擎里。某些服务支持在线权重更新，更需要给请求/缓存绑定版本。模型名字符串不足以唯一标识实际权重。

删除、取消与超时也要跨端传播。如果前端断开，只取消D而P继续计算，资源可能浪费；如果P失败，D预留空间要归还。重复到达的完成通知必须幂等，避免同一页释放两次。

## 6. 通信与计算重叠的条件

重叠需要确实独立的工作。例如D处理请求A的decode时，可传请求B的状态；P生成后面的块时，前面已经完成的块可先传。但如果某一步必须等待全部状态，重叠空间就有限。网卡、copy engine、GPU HBM带宽还可能与计算争用。

“异步”API仅表示调用者不立即等待；总临界路径是否缩短，要看时间线。如果传输在最末端才启动，即便调用是async，也可能完全落在关键路径。正确实验应记录计算结束、传输开始/结束、D执行开始，而非只在Python函数前后计时。

## 7. 练习与参考解法

1. **破平衡条件。** 设P排队不变且可忽略额外开销，何时分离TTFT更好？答案是共置排队减D排队，大于传输成本。这个条件不包含ITL改善；PD可能TTFT略差却保护decode间隔，所以还要明确优化目标。
2. **状态机设计。** 写 P_CREATED→P_COMPUTED→TRANSFER_SUBMITTED→D_READY→D_RUNNING→DONE 的事件表，并为每步标所有者。参考解法在 TRANSFER_SUBMITTED 仍保留源引用，D_READY后才允许按协议释放；若取消发生在中间，仍等在途访问安全结束。
3. **重复通知。** 用字典记录 transfer_id 和terminal状态，重复D_READY不能重复retain，重复abort不能重复free。加入乱序通知测试，必要时拒绝不合法转换，而不是把任何状态都直接覆盖。
4. **不同TP布局。** P端TP=2、D端TP=4，KV头8。P每rank有4头，D每rank有2头；画出每份头数据的目的rank。若KV头数不整除，不能用本简单模型，需要查实现是否复制或重排。
5. **背压模拟。** 每轮P产生3任务、D完成2，队列初始0，十轮后理论积压10。给队列上限4，设计 admission 拒绝/等待策略；输出每轮接受、完成、积压，验证守恒 `初始+接受-完成=剩余`。
6. **真实源码任务。** 在固定 SGLang 仓库查找 `disaggregation` 与传输 connector；找到接收就绪、取消、超时三条路径。选一个接口写布局说明，记录实际支持的模型状态类型。不要从标准KV支持推断所有混合SSM状态也完整支持。

掌握门槛：能完整说明PD状态交接、失败回收与背压；能算传输下界；能解释PD为什么可能更慢；能把跨节点和PD分离区分开——同节点可以PD，跨节点也可以纯TP而不PD。
