# S08 测量与排队：让性能结论可以被复核

先修 S02、S07、均值和百分位。本章目标是独立设计一个不会把输出长度、到达模型、缓存状态和冷启动混在一起的实验。看懂“tokens/s 很高”远远不够；你需要知道这个值代表什么工作负载，以及改善是否损害了另一个指标。

## 1. 四个时间点与三个常见指标

记录请求提交 `t0`、首个有效输出 `t1`、后续输出时间 `t2...tn`、请求结束 `te`。TTFT=`t1-t0`；端到端延迟=`te-t0`；平均 ITL 在确实逐 token 计时的前提下为 `(tn-t1)/(n-1)`。只有一个输出 token 时，ITL 没有定义，不能填 0 暗示它更快。

手算：到达 2 ms，输出出现在 7、9、12 ms，结束 12 ms。TTFT=5 ms，间隔为 2 和 3，平均 ITL=2.5 ms，端到端=10 ms。`e2e/output_tokens=10/3` 不是同一个 ITL，因为其中含排队和 prefill。

服务端排队时间、prefill 时间、网络时间也不能只靠这三个客户端指标唯一分解。两个系统可以有相同 TTFT，却一个卡在队列、一个卡在 tokenizer。需要服务端 trace 才能归因。

## 2. 吞吐的分子与分母

输出吞吐是输出 token 总量除观察窗口；总 token 吞吐可能把输入与输出都算进去；请求吞吐是完成请求数除时间。三者不可互换。一个模型短答很多，requests/s 很高，不代表它在相同输出任务上更高效。

观察窗口也影响数值。只测稳态中间 30 秒，和包含加载、warmup、最后排空的完整时间，回答不同问题。正式报告应同时说明是否包含预热、是否包括失败请求、是否包括被取消 token、结束时是否 drain 队列。

有效吞吐 goodput 更进一步：只计满足质量与延迟约束的完成工作。若大量请求超时，但剩下的 tokens/s 更高，用户未必受益。你可以同时报告原始吞吐和 SLO 达标率，避免一个标量掩盖取舍。

## 3. 开环与闭环负载

闭环客户端固定并发 C：一个请求完成才发送下一个。系统越慢，客户端发送得越慢，容易低估真实拥塞。开环按预先定义的到达速率发送，不等前一个结束；当到达率超过处理率，队列会增长。

Little 定律在稳定条件下给出 `平均在系统请求数 L = 到达率 λ × 平均停留时间 W`。例如稳定 20 请求/秒、平均 0.5 秒，平均在系统有 10 请求。它不是说所有瞬间都恰好 10，也不适用于无限增长的过载队列直接求稳态。

本卷 replay 使用固定 arrival trace，因此更像离线离散事件的开环回放。参考 HTTP benchmark 是串行闭环小探测，主要检查正确性和响应，不是完整压力测试工具。两种工具不能拿相同图标题假装同一种测量。

## 4. 百分位为何需要样本和定义

均值容易被极端慢请求拉动，p50 描述中位，p95/p99 描述尾部。只有 4 个请求时，p99 非常不稳定，本代码仍可算插值百分位，但数值没有大样本尾部保障。

对于 `[1,2,3,100]`，本函数采用线性插值：p50=2.5，p95=85.45。其他库可能采用 nearest-rank 等定义，所以统计方法也要写进报告。不要把不同定义的小样本百分位差异当性能回归。

建议保留每请求原始记录，在汇总中明确样本数、失败数和缺失字段。只留最终 p95 会让后来无法检查是否有某类长提示集中变慢。含私有内容的请求正文不需要进入公开报告，记录长度、任务类别和匿名 ID 即可。

## 5. 冷启动、缓存与预热

模型加载、权重转换、JIT 编译、autotuning、CUDA Graph 捕获都可能影响前几次请求。缓存命中还可能缩短 prefill。比较两个配置，必须说明各自处于冷或热状态，以及是否使用相同预热流程。

不要简单删除所有慢样本：先判断它是明确排除的初始化阶段，还是稳态偶发编译或缓存未命中。后者本来就是系统行为的一部分。若线上形状经常变化，固定 shape 的热态基准可能过于乐观。

建议分三份结果：启动到 ready；首次合法请求；固定预热后稳定工作负载。对 prefix cache 再分 cold namespace 与 warm namespace，或使用框架支持的缓存清理动作，并记录具体语义。

## 6. 一个可复核的对照实验

运行：

```bash
python -m labs.serving.experiments --lab metrics
python -m labs.serving.replay
```

replay 对三个预算与三种策略形成九组配置，固定 trace，并首先断言所有输出等价。输出中的吞吐明确标为 synthetic，不冒充真实 GPU tokens/s。观察 p95 TTFT 与总完成时间如何变化；选择你关心的目标，解释为什么没有一个策略在所有维度都必胜。

真正 GPU 实验可以沿用相同报告结构，但必须用实际 tokenizer 得到长度，记录模型 revision、框架/驱动/CUDA、GPU SKU、并行参数、后端、上下文上限与缓存状态。一个 H100 PCIe 的结果不能无条件代表 H100 SXM；只写“H100”会丢掉关键条件。

## 7. 练习与参考答案

1. **指标区分。** 请求 A 100 输入、10 输出、1 秒；B 1000 输入、10 输出、1 秒，同时完成，总窗口 1 秒。输出吞吐 20 token/s，总 token 吞吐 1120 token/s，请求吞吐 2 req/s。三个数都可合法，但必须标明名称。
2. **单 token。** 只有一个输出时把 ITL 设置为 None。若画图工具不接受缺失值，应过滤并报告有效样本数，而不是填零参与平均。
3. **闭环偏差。** 模拟服务耗时从 100 ms 变成 1 s，固定并发 1 的到达率从约 10/s 降到 1/s。答案：没有观察到长队列不能证明服务能承受 10/s；客户端自己降载了。
4. **输出长度混杂。** 配置 B 比 A 更快，但平均输出从 100 降为 20。设计验收：同一任务与解码上限，保留输出长度分布和停止原因，必要时用固定生成长度微基准隔离 runtime。不能强迫所有实际任务固定长度而忽略质量，但性能归因应控制长度。
5. **尾部报告。** 对 20 条记录计算 p95，再随机抽 5 条重复计算，观察结果变化。参考答案应说明不确定性来自样本选择，不能宣称 p95 稳定改善。若要置信区间，可 bootstrap 请求级样本，但同一任务多次测量的相关性需要分组处理。
6. **修改 replay。** 增加 SLO：TTFT≤10 ms、平均 ITL≤3 ms，输出达标请求比例。计算分母用所有已提交请求，并单独列失败/取消。未知 ITL 的单 token 请求如何判定需要预先定义，不能看到结果后临时决定。

掌握门槛：能写清一份 benchmark 的负载、计时边界与统计定义；能发现把 chunk 当 token 的错误；能解释高吞吐与低尾延迟的冲突；能给实验设计找出至少三个混杂因素。
