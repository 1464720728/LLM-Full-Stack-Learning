## 1. 第一课：先画时间线，再选择指标

一次请求至少可以记录客户端发起、服务收到、排队开始、获得执行资源、prefill 完成、首个输出生成、首段文本到达、最后输出生成、最后文本到达和应用完成。不同进程的时钟不一定一致，因此跨机器时间不能随意相减。客户端端到端延迟可以用客户端同一个单调时钟测，服务内部阶段则使用同一时钟域的 trace 或明确的时钟对齐方法。

TTFT 通常表示从请求起点到首 token 的延迟，但起点和终点必须写清楚。客户端发起到首段有效文本，包含网络、排队、tokenization、prefill 和输出传输；服务收到到首个模型 token，不包含前面的网络段。两份报告都叫 TTFT，若边界不同，不能直接比较绝对数值。

E2E 是从请求开始到完成的总时间。完成可以指最后正文到达，也可以指终止事件与 usage 收齐，或连接关闭。后几项可能晚于最后 token。测量应保存这些原始时间点，而不是只保存一个含义模糊的 duration；以后才能根据不同问题重新计算，而不用重新跑全部实验。

设请求在二毫秒到达，三个输出 token 分别在七、九、十二毫秒生成，应用在十三毫秒完成。TTFT 为五毫秒，逐 token 间隔为二和三毫秒，平均间隔二点五毫秒，E2E 为十一毫秒。应用完成比最后 token 晚一毫秒，这一毫秒可能是封装与发送完成事件，不能误算成模型又生成了一个 token。

| 事件 | 时间 | 与前一步的关系 | 可用于什么指标 |
|---|---:|---|---|
| 请求开始 | 2 | 定义计时起点 | E2E、TTFT 的起点 |
| 第一个 token | 7 | 等待与首轮计算共五毫秒 | TTFT |
| 第二个 token | 9 | 间隔二毫秒 | ITL |
| 第三个 token | 12 | 间隔三毫秒 | ITL、最后 token 时间 |
| 应用完成 | 13 | 额外完成尾部一毫秒 | 完整 E2E |

单调时钟适合测持续时间，因为它不受普通系统时间校正的同类影响。Python 中可使用 `time.perf_counter()` 测本进程持续时间；把结果记成毫秒时乘一千，并在字段名标单位。不要把秒数放进带 _ms 的字段，也不要把纳秒整数未经转换与毫秒阈值比较。单位错误可以让系统看起来快或慢一千倍。

## 2. 第二课：ITL、TPOT 与平均数究竟平均了什么

ITL 是相邻输出 token 之间的间隔，前提是你确实有逐 token 时间戳。一个请求输出 N 个 token，就有 N减一 个间隔。只有一个 token 时，没有间隔；应记为缺失或不适用，而不是零。零表示观察到瞬时完成的间隔，会在平均和 SLO 中造成错误优势。

很多报告把 TPOT 定义为 `(E2E-TTFT)/(N-1)`。若 E2E 的终点就是最后 token，这与逐 token 间隔的平均值相同；若 E2E 包含最后 token 后的封装、usage 或网络尾部，则两者不同。前面的例子中，按应用完成算出的 TPOT 为三毫秒，而真实两个 token 间隔平均为二点五毫秒。因此报告必须写公式与终点。

不要用 E2E 除以输出 token 数代替平均 decode 间隔。E2E 包含首 token 之前的排队与 prefill，分母又是 N 而不是 N减一。对短输出，这种差别尤其大。若任务主要是只生成一个分类 token，TTFT 和整体完成时间更有意义，强行计算 TPOT 反而制造没有定义的指标。

聚合也有两种常见方式。先算每请求平均 ITL 再对请求求平均，让短请求和长请求权重相同；把所有 token 间隔放在一起求平均，让输出长的请求权重更大。设甲只有一个十毫秒间隔，乙有一百个一毫秒间隔。请求平均为五点五毫秒，全部间隔平均约一点零八九毫秒。它们回答不同问题，不应互相冒充。

```python
def request_metrics(arrival, emitted, finished):
    if finished < arrival or any(t < arrival or t > finished for t in emitted):
        raise ValueError("timestamps outside request lifetime")
    if any(b < a for a, b in zip(emitted, emitted[1:])):
        raise ValueError("emission timestamps must be ordered")
    gaps = [b-a for a,b in zip(emitted, emitted[1:])]
    return {
        "ttft_ms": emitted[0]-arrival if emitted else None,
        "e2e_ms": finished-arrival,
        "mean_itl_ms": sum(gaps)/len(gaps) if gaps else None,
        "completion_tpot_ms": ((finished-emitted[0])/(len(emitted)-1)
                               if len(emitted)>1 else None),
        "last_token_ms": emitted[-1] if emitted else None,
        "gaps_ms": gaps,
    }

m = request_metrics(2, [7, 9, 12], 13)
assert m["ttft_ms"] == 5 and m["e2e_ms"] == 11
assert m["mean_itl_ms"] == 2.5 and m["completion_tpot_ms"] == 3
assert request_metrics(0, [4], 4)["mean_itl_ms"] is None
assert request_metrics(0, [], 2)["ttft_ms"] is None
print(m)
```

这个函数拒绝时间倒序和超出请求生命期的输出，但没有自动判断 emitted 是模型 token 还是文本 chunk。数据含义仍由采集端保证。如果把 SSE 片段时间传进来，数学会照常算出数值，但指标名称应改成片段间隔。类型与数值校验不能替代语义校验，这在性能数据里尤其重要。

## 3. 第三课：吞吐的分子、窗口与失败处理

请求吞吐是完成请求数除以观察时间，输出 token 吞吐是输出 token 数除以观察时间，总 token 吞吐可能把输入与输出都算进去。设甲输入一百、输出十，乙输入一千、输出十，二者在同一个一秒窗口完成。请求吞吐是每秒二请求，输出吞吐是每秒二十 token，总输入加输出吞吐是一千一百二十 token 每秒。三个值都合法，名字必须不同。

输入 token 与输出 token 的计算成本不同。prefill 可以利用较大矩阵并行，decode 通常每个请求每轮产生一个新 token，而且读取已有 KV。把长 prompt 的输入 token 大量加入分子，可能使总 tokens/s 很高，但用户等待的首输出并没有更快。若报告只给一个总数，无法知道系统是在处理哪类工作。

观察窗口可以从第一请求发起到最后请求完成，也可以是稳定负载中间的一段固定时间。前者包含启动/排空效应，后者更接近稳态容量，但必须处理跨窗口请求。你要定义统计的是窗口内完成的请求、窗口内实际产生的 token，还是窗口内到达请求的最终结果。不同口径都可以研究，不能混在一个比值里。

失败请求不能悄悄删除。假设提交一百请求，九十个超时，十个快速完成；只对成功请求计算平均延迟会让服务看起来很快。应同时报告提交数、完成数、成功数、错误数、取消数、超时数，以及仍在运行数。延迟分布可以针对成功请求给出，但旁边必须有成功率，且解释超时如何进入 SLO 判定。

goodput 进一步要求结果满足预先定义的质量与延迟目标。若 SLO 是 TTFT 不超过五十毫秒、平均 token 间隔不超过十毫秒，并且请求正常完成，那么只有满足这些条件的完成工作计入有效吞吐。输出质量也可能成为条件，但不能在看到结果以后随意放宽规则。先定义目标，再做实验，才能避免选择性报告。

| 数量 | 合法分子 | 必须同时说明的条件 |
|---|---|---|
| requests/s | 完成或成功请求数 | 完成定义、失败与窗口 |
| output tokens/s | 实际输出 token 数 | 是否含失败请求已产生部分 |
| total tokens/s | 输入加输出 token 数 | tokenizer、输入是否重复计算 |
| goodput | 满足 SLO 的请求或 token | SLO、未知指标与失败处理 |

缓存命中后有些输入 token 没有重新计算。如果总 token 吞吐把逻辑输入长度全部计入，应该明确这是“服务的逻辑 token 量”，不是“实际计算 token 量”。同样，抢占重算会增加实际计算，却不增加用户逻辑输入。两个口径分别用于业务承载与设备效率分析，不能混用来宣传优化幅度。

## 4. 第四课：百分位是排序位置，不是最慢百分之几的平均

把延迟从小到大排序，p50 描述中间位置，p95 描述靠近尾部的位置。它不是“最慢百分之五请求的平均延迟”，也不是“百分之九十五请求平均耗时”。本仓库 percentile 使用线性插值：位置等于 `(样本数-1)*q`，在相邻排序值之间按小数部分插值。

对一、二、三、一百这四个样本，p50 的位置是一点五，得到二点五；p95 的位置是二点八五，得到三加上九十七乘零点八五，即八十五点四五。样本里没有请求恰好耗时八十五点四五，这不矛盾，因为它是统计定义产生的插值值。另一种 nearest-rank 定义可能直接返回一百，报告应说明采用哪一种。

```python
from labs.serving.analysis import percentile

values = [1, 2, 3, 100]
assert percentile(values, 0.5) == 2.5
assert abs(percentile(values, 0.95) - 85.45) < 1e-12
assert percentile(values, 0.0) == 1
assert percentile(values, 1.0) == 100
print({"n": len(values), "p50": percentile(values, .5),
       "p95": percentile(values, .95)})
```

只有四个请求也能算 p99，但它不能提供可靠的大样本尾部判断。某一个慢请求的出现或缺失就会大幅改变结果。小规模真实探测的主要目标是验证端点、协议和测量流程，不是证明生产 p99 改善。你可以保留该数值，但必须把样本数放在旁边，避免制造看似精确的结论。

多个分组的百分位不能直接平均得到总体百分位。两组请求数量不同、分布不同，平均 p95 可能与合并原始样本后的 p95 相差很大。若需要总体结果，保留原始请求记录或使用能够合并且误差明确的直方图/摘要结构。只留下每批一个 p95，会丢失以后正确聚合所需的信息。

尾部分析还要按输入长度、输出长度、缓存命中与请求类别分组。整体 p95 变好，可能只是长请求比例下降；某类重要任务仍可能更慢。分组不是为了从很多图里挑最好看的一个，而是解释混杂因素。分组规则应该在实验设计时确定，并保留全部组的样本数，避免极小样本产生误导。

### 4.1 重复实验、配对比较与不确定性

同一个配置跑两次得到不同结果并不罕见，原因可能是后台负载、缓存状态、到达随机性或设备频率变化。先保存每轮结果，观察变化量与待比较的优化幅度。如果优化声称只改善百分之一，而重复运行自然波动已经达到百分之十，就不能仅凭一次较好的结果下结论。

配对比较让同一个请求样本在两个配置下都出现，然后计算每个样本的延迟差。这样可以减少任务本身长短差异带来的混杂。若两个配置采用不同输入集合，即使平均输入长度相同，实际难度、缓存共享和输出长度也可能不同。配对并不自动消除顺序效应，因此还应交替或随机化配置顺序，并保持预热规则一致。

bootstrap 可以从请求记录中有放回抽样，重复计算统计量，用于观察样本变化带来的不确定性。但若同一 prompt 重复多次并共享缓存，这些记录并非完全独立；可以按任务或实验轮次分组重采样。统计方法不能创造原本没有的独立证据，四个高度相关请求反复抽样仍然不能变成大量真实用户。

置信区间也不是“真值有这个概率落在区间里”的随意保证。初学阶段可以先把它理解为在明确抽样假设下，量化估计对样本选择的敏感程度。报告应写方法、重采样单位和次数，并避免只保留有利的区间端点。如果尚未学会这些假设，诚实报告多轮原始结果与范围，也比给一个没有说明的精密小数更可靠。

## 5. 第五课：开环与闭环，让负载不再偷偷替系统降压

闭环负载固定在途并发，例如始终保持四个请求，一个结束才发下一个。系统变慢时，新请求发送得也更慢，因此它会自动降低到达率。开环负载按照预先给定的到达时间发送，不等前一个完成；如果服务跟不上，队列会增长。两种方法都常用，但回答的问题不同。

设单个请求服务时间两秒，闭环并发一时每两秒才发一个新请求，几乎看不到服务队列。若真实业务每秒到达一个请求，同一服务每秒只能处理半个，请求会越积越多。不能因为并发一基准中没有排队，就说服务能承受每秒一个请求。客户端的发压方式本身就是实验条件。

固定并发也不等于固定 batch size。某一时刻四个客户端请求可能分别在网络、等待队列、prefill 与 decode 阶段，GPU 本轮未必处理四条序列。反过来，服务端一个请求也可能生成多个候选序列。比较配置时，应同时记录客户端并发、服务活动序列数和每轮 token 数，而不是用一个 batch 字段表示全部。

开环测试也可能被客户端自身限制。如果发送协程排队、CPU 编码太慢或连接池不足，计划到达时间与实际发起时间会偏离。应该记录 planned_arrival 与 actual_send，分别看发压端延迟与服务端延迟。若客户端根本没有按计划发出请求，不能把不足的吞吐归因给服务器，也不能误称已经施加了目标负载。

本仓库 replay 使用固定 arrival trace，在离散事件模型中回放，更接近预先规定到达的开环实验；http_benchmark 是串行闭环小探测，主要验证真实端点与片段时间。它们不能放在同一张图里仅标“并发测试”。工具的名字不保证负载语义，必须读发送循环实际怎么工作。

## 6. 第六课：手写 FIFO 队列，看到等待如何累积

以下程序模拟一个一次只能服务一个请求的 FIFO 服务台。开始时间等于到达时间与上一个完成时间的较大值，完成时间等于开始加服务时间，等待时间等于开始减到达。它不是 LLM 连续批处理模型，但足以清楚说明到达率、服务能力与排队的关系。

```python
def fifo_queue(arrivals, service_times):
    if len(arrivals) != len(service_times):
        raise ValueError("one service time per arrival")
    if any(b < a for a,b in zip(arrivals, arrivals[1:])):
        raise ValueError("arrivals must be ordered")
    ready = 0.0
    rows = []
    for i,(arrival,service) in enumerate(zip(arrivals, service_times)):
        if arrival < 0 or service <= 0:
            raise ValueError("nonnegative arrival and positive service required")
        start = max(arrival, ready)
        finish = start + service
        rows.append({"id": i, "arrival": arrival, "start": start,
                     "finish": finish, "wait": start-arrival,
                     "sojourn": finish-arrival})
        ready = finish
    return rows

rows = fifo_queue([0, 1, 2, 3], [2, 2, 2, 2])
assert [r["wait"] for r in rows] == [0, 1, 2, 3]
assert [r["finish"] for r in rows] == [2, 4, 6, 8]
closed = fifo_queue([0, 2, 4, 6], [2, 2, 2, 2])
assert all(r["wait"] == 0 for r in closed)
print(rows)
```

第一请求零时到达，立即开始，二时完成。第二请求一时到达，但服务台到二时才空闲，所以等一单位；第三请求等二单位；第四请求等三单位。服务时间始终没有变化，用户观察到的总延迟却不断增加。看到 E2E 增长不能直接断言模型 kernel 变慢，队列本身就能解释这个现象。

如果把到达改成零、二、四、六，每个请求恰好在前一个完成时到达，等待为零。这对应闭环并发一的理想发送节奏。两次实验使用完全相同服务时间，却得到不同延迟分布，差别来自负载。性能比较若不固定负载模型，结论可能完全颠倒。

真实 LLM 服务比这个模型复杂：多个请求共享批次，服务速度随输入长度、输出长度、KV 长度和批次变化，prefill 还会影响 decode 间隔。因此不能把单服务台公式直接当作 vLLM 的精确预测。它的教学作用是建立因果方向：输入到达过程与资源服务过程共同决定等待，测量时必须观察两边。

突发也很重要。即使长期平均到达率低于平均服务能力，短时集中到达仍会产生等待。两组业务平均每秒十请求，一组均匀到达，另一组每秒同时发十个，尾延迟可能明显不同。只记录平均 QPS 会丢失这个信息；应保存到达间隔或明确的随机/突发生成规则。

## 7. 第七课：从请求时间求出系统中的平均人数

Little 定律在稳定条件下写作 `L=λW`：平均在系统请求数等于到达率乘平均停留时间。L 包括等待和正在服务的请求，W 包括等待与服务时间。它不是说每个瞬间都有 L 个请求，也不是说过载无限增长时还能套一个不存在的稳态平均。

对前面的有限四请求例子，我们也可以做一个精确面积核对。每个请求从到达到完成期间贡献一条“在系统中”的时间长度，四条停留时间是二、三、四、五，总面积十四。观察窗口从零到八，平均系统人数为十四除八等于一点七五。窗口内四个请求最终都完成，完成率四除八等于零点五，平均停留时间三点五，两者相乘也为一点七五。

这是有限完整窗口的面积恒等式，不能因为算式成立就声称过载过程存在稳定状态。它成立依赖窗口把这四个请求的完整生命期都纳入，没有漏掉窗口开始前已存在或结束后仍未完成的请求。真实稳态采样会有边界请求，需要说明如何处理，或者选择足够长窗口降低边界影响。

```python
rows = [
    {"arrival": 0, "finish": 2},
    {"arrival": 1, "finish": 4},
    {"arrival": 2, "finish": 6},
    {"arrival": 3, "finish": 8},
]
window = 8
area = sum(r["finish"]-r["arrival"] for r in rows)
mean_w = area/len(rows)
rate = len(rows)/window
mean_l = area/window
assert mean_l == rate*mean_w == 1.75
print({"area_request_time": area, "mean_in_system": mean_l,
       "completion_rate": rate, "mean_sojourn": mean_w})
```

这个关系也可以用于检查监控数据是否自洽。若稳定时期报告每秒二十请求、平均停留半秒，平均在系统请求数应在相应口径下接近十。若监控显示一百，可能是并发包含了其他任务、延迟统计只算成功短请求、时间窗口不一致或队列持续增长。它是诊断线索，不是凭三个数字就自动判定哪一个错。

对连续批处理，还要区分“在系统请求数”与“GPU 活动序列数”。等待队列中的请求计入 L，但可能尚未分配 KV；活动序列可能因抢占暂时不执行；一个请求也可能有多个分支。将 Little 定律中的人数替换成物理 batch size 而不检查定义，会得到看似数学化却没有意义的容量结论。

## 8. 第八课：冷启动、缓存与预热要作为实验变量

权重加载、文件缓存、设备初始化、编译、autotuning 和图捕获都可能影响前几次请求。把这些时间计入端到端启动实验是合理的，把它们混进稳态 decode 延迟却不说明则不合理。建议分别记录启动到 ready、首个合法请求和完成固定预热后的工作负载，三个阶段回答不同问题。

预热不能只是“删除最慢的十个样本”。你应在实验开始前定义预热输入、次数和停止条件，并把预热结果单独保存。若线上形状不断变化，稳态中仍可能触发新编译或新 bucket；这些慢请求是实际行为，不应该事后当作预热全部删掉。评估冷形状与热形状的比例，才能理解真实体验。

prefix cache 冷热状态尤其容易混淆。两个配置连续跑相同 prompt，后跑的配置可能受益于已缓存前缀，而不是其调度器更好。可以使用独立服务进程、明确缓存清理接口或不同 namespace 构造对照，但必须记录所用方式及其语义。改变 namespace 可以隔离前缀身份，不等于清空权重缓存或编译缓存。

同样，不要把操作系统文件缓存、tokenizer 缓存、prefix KV cache 和 CUDA Graph 缓存统称为“缓存”。它们存储不同对象、影响不同阶段、拥有不同失效规则。实验表中应分别记录重要缓存状态；一句“warm=true”不足以解释首 token 延迟为什么减少。

控制变量时一次只改变一个核心配置，保持模型 revision、tokenizer、prompt token、输出上限、采样规则和负载相同。随后可以做组合实验研究交互，例如 chunk size 与 token budget 的联合作用。若一次同时换模型、量化、GPU 数和输出长度，即使吞吐翻倍，也无法知道是哪项改动造成。

## 9. 第九课：读懂本仓库 replay 与 HTTP 探测的真实范围

[replay.py](../../labs/serving/replay.py) 对三个预算与三种策略形成九组配置。每组创建新的 Engine，按同一 trace 提交请求，运行到结束，再读取 report。它先收集非缺失 TTFT，计算 p50 与 p95，用总输出 token 除模拟完成时间形成 synthetic 吞吐，最后断言九组输出完全相同。

这里的输出等价断言非常重要：性能比较前先要求逻辑结果保持一致。若某策略通过少生成 token 获得更短完成时间，不能直接当作调度优化。当前参考模型与每请求 RNG 使这种对照可行；真实模型后端可能存在容差或采样差异，需要在实验设计中明确什么算等价，而不是把正确性条件默默取消。

```bash
python -m labs.serving.experiments --lab metrics
python -m labs.serving.replay
```

输出中的 kind 明确写着 synthetic_cost_model_not_real_GPU_benchmark。模拟每轮成本由 Engine 的固定公式产生，没有测 GPU kernel、PCIe、网络或真实 tokenizer。它适合检验调度与指标计算，不能用来证明某个真实框架或显卡更快。把 synthetic 字段保留在导出图表标题和数据列里，避免复制到报告后丢失证据边界。

[http_benchmark.py](../../labs/serving/http_benchmark.py) 的发送循环是串行的。每个请求完成才发送下一个，使用 completions 风格 payload，默认固定短 prompt，也可通过 --prompt-file 读取有界公开输入，读取 SSE 后记录非空 text 事件时间。它把首段正文命名为 ttft_text_ms，把间隔命名为 mean_inter_chunk_ms，只有 usage 提供 completion_tokens 才记录 token 数，没有拿字符数补齐。

同目录的 [concurrent_probe.py](../../labs/serving/concurrent_probe.py) 提供另一种有限封闭负载：最多四个线程、八个请求，并把客户端排队与调用墙钟分开；它仍不是开环到达。S15 展开其完整使用和验证。两种探针要求该 completions 子集的 [DONE] 终止标记，拒绝错误事件或缺标记的截断流，不能只因 HTTP 200 就记成功。

原串行脚本是有边界的小探测工具，不是完整负载发生器。它没有并发调度、开环到达、复杂失败汇总或独立总请求 deadline。urllib 的 timeout 也不自动等同于严格总时长上限；服务持续发字节时行为要结合实际读取路径理解。因此真实共享设备实验还应通过外层受控进程与明确停止条件限制总运行时间，不能把一个 socket 参数当成全部资源约束。

默认 dry-run 不发送请求，显式 execute 才执行。远程端点需要显式 allow-remote，密钥从环境变量读取，不能写进公开报告。使用这个工具时先确认目标服务真的支持该接口；本仓库 mock_server 的教学非流式 token 接口与真实 completions SSE 不是同一协议，不能因为地址都在本机就互换使用。


### 9.1 一条原始记录应该保存哪些字段

最小记录需要 request_id、planned_arrival、actual_send、first_text、last_text、finished、state、input_tokens、output_tokens、token_count_source 和 finish_reason。时间字段应标明时钟域与单位，长度字段应标明来自真实 tokenizer、服务 usage 还是教学输入。若某项没有观测到，保留空值并写原因，不能使用零代替未知。

服务端若能提供 trace，可以追加 tokenize_start/end、queue_enter/leave、prefill_start/end、每轮执行编号、缓存命中 token 和抢占次数。客户端与服务端通过匿名请求 ID 关联，但不要默认两台机器的绝对时间可以直接相减。先在各自时钟域计算阶段持续时间，再研究如何对齐跨机器边界。

为了公开复现，不必保存真实业务正文。可以保存合成数据生成种子、长度分布、模板版本、模型 revision 和公开 fixture。若 prompt 内容会影响缓存共享或输出长度，仅记录长度可能不足，此时应设计可公开的替代工作负载，并承认它与真实业务的差异。保护内容与保留可复现性可以同时做到，不需要把公司数据放进仓库。

数据 schema 一旦确定，应在导出时校验：结束时间不得早于发起，输出数量非负，成功请求的必要字段存在，失败请求保留错误类别。统计脚本读到坏行时明确报告数量与原因，不应静默跳过。否则数据清洗本身就可能选择性删除慢请求，让后续所有图表看起来一致却共同偏离事实。

## 10. 第十课：用完整代码定义 SLO 与缺失值策略

下面用合成记录计算达标率。契约是所有提交请求都进入分母；只有正常完成且 TTFT 达标的请求才可能通过；输出多于一个 token 时还要求平均 ITL 已知且达标；单 token 请求的 ITL 不适用，按预先定义规则豁免这一项。这个规则不是普遍标准，但它明确、可复算。

```python
def slo_summary(rows, ttft_limit, itl_limit):
    passed = []
    for row in rows:
        ok = row["state"] == "finished"
        ok = ok and row["ttft_ms"] is not None and row["ttft_ms"] <= ttft_limit
        if row["output_tokens"] > 1:
            ok = ok and row["mean_itl_ms"] is not None
            ok = ok and row["mean_itl_ms"] <= itl_limit
        passed.append(bool(ok))
    return {
        "submitted": len(rows),
        "passed": sum(passed),
        "pass_rate": sum(passed)/len(rows) if rows else None,
        "good_output_tokens": sum(r["output_tokens"] for r,ok in zip(rows,passed) if ok),
    }

rows = [
    {"state":"finished","ttft_ms":4,"mean_itl_ms":2,"output_tokens":3},
    {"state":"finished","ttft_ms":6,"mean_itl_ms":1,"output_tokens":3},
    {"state":"finished","ttft_ms":3,"mean_itl_ms":None,"output_tokens":1},
    {"state":"error","ttft_ms":2,"mean_itl_ms":1,"output_tokens":2},
]
result = slo_summary(rows, ttft_limit=5, itl_limit=3)
assert result == {"submitted":4,"passed":2,"pass_rate":0.5,"good_output_tokens":4}
print(result)
```

如果业务要求零输出请求也算正常成功，应为它单独定义判定，因为它没有 TTFT。上面程序会让 TTFT 缺失的请求不通过，这符合当前“需要有效生成”的目标。不要把 None 自动替换成零，否则没有任何输出的失败请求反而拥有最好的首 token 延迟。

good_output_tokens 还不是 goodput，必须再除以明确的观察窗口。本例没有真实时间窗口，因此只返回达标 token 数。这个小细节体现了一个原则：缺少必要数据时保留缺失，不能为了凑齐漂亮表格推算一个无依据指标。报告诚实地写“未测”比给一个假精确数字更有价值。

若一个请求平均 ITL 达标但其中一次卡顿很长，用户仍可能体验不好。可以追加每请求最大间隔或间隔 p95 的约束，但应该预先定义，并保留原始间隔。平均数不能代表所有交互体验，长时间停顿对流式阅读和 Agent 工具链都可能特别重要。

## 11. 第十一课：四个容易把结论带偏的故障实验

**现场一：优化后吞吐翻倍，但输出长度减半。** 先比较每请求实际输出 token、finish reason 和任务正确性，再用固定输出长度的微基准隔离 runtime。固定长度微基准不替代真实任务质量评估，只是帮助归因。若优化版更早 EOS，业务可能受益也可能受损，不能直接把总用时减少归功于 kernel。

**现场二：p95 下降，但错误率上升。** 检查统计是否只保留成功请求，超时是否被删除，客户端是否在服务慢时自动降载。恢复全部提交记录，单列成功延迟分布与 SLO 达标率。若失败请求没有终态记录，应先修数据采集，不能用缺失记录证明“它们大概也很快”。

**现场三：GPU 利用率很高，用户仍等待很久。** 区分设备忙于有效 decode、长 prefill、重算还是无效 padding。观察队列、每轮 token 类型、抢占次数、缓存命中和输出进度。高利用率只说明设备某种程度上忙，并不保证用户目标得到满足。把占用率当唯一优化目标，可能让大量长 prefill 挤压交互请求。

**现场四：同样四个请求，第二轮明显更快。** 检查加载、编译、图捕获、prefix cache 和文件缓存状态。用显式冷热分组与固定预热重做，而不是直接把第二轮称为新版本性能。若每次换配置都重启服务，应记录重启是否清除了同样的状态；不同启动路径可能产生不对称的热身条件。

故障报告应提出可被证伪的解释。例如怀疑长度变化，就固定真实输出 token 数后再测；怀疑缓存，就构造冷 namespace 和热 namespace 对照；怀疑客户端瓶颈，就记录计划发送与实际发送差。观察一个相关指标不等于找到原因，只有改变相应条件后结果按预测变化，因果解释才更可信。

## 12. 第十二课：十六道练习、参考答案与实验项目

**练习一，计算完整时间线。** 到达一，输出六、八、十三，完成十五。TTFT 为五，E2E 为十四，ITL 为二和五，平均三点五，按完成时间算 TPOT 为四点五。答案应指出最后 token 后还有两单位尾部，因此两个平均值不同。不能把十四除三当成平均 decode 间隔。

**练习二，只有一个 token。** 到达零、输出四、完成五。TTFT 四，E2E 五，ITL 与 TPOT 不适用。将它们填零会错误拉低整体均值。若 SLO 需要处理单 token，请先规定豁免或其他规则，并在报告中列出这类请求数量。

**练习三，三种吞吐。** 两请求同时占用一秒，输入分别一百和一千，输出各十。请求吞吐二，输出吞吐二十，逻辑总 token 吞吐一千一百二十。若其中一半输入来自缓存，逻辑总 token 数仍不变，但实际重算 token 数不同，不能用同一字段表示。

**练习四，插值百分位。** 对二、四、十、二十求 p50 和 p95。位置分别一点五、二点八五，答案七和十八点五。p95 不是最慢一项二十的固定同义词，而由本章定义决定。若换 nearest-rank，需修改统计标签并重新解释比较。

**练习五，平均的权重。** 甲一个十毫秒间隔，乙一百个一毫秒间隔。每请求平均后再平均为五点五；池化间隔平均为一百一十除一百零一。前者描述典型请求的平均体验，后者描述典型 token 间隔，两者都应注明权重。

**练习六，排队手算。** 到达零、零、三，服务时间二、二、一。第一完成二，第二开始二完成四，第三到达三后等一，开始四完成五。等待为零、二、一，平均一。总停留为二、四、二，平均八除三。用 fifo_queue 验证，不要把第二个请求到达零误写成前一个完成时刻。

**练习七，闭环掩盖过载。** 服务能力每秒半请求，客户端并发一会约每两秒发送一次。若真实到达每秒一请求，长期队列增长。答案应改变发压方法或记录计划到达，不能通过“把并发一改名为低延迟模式”回避实际到达需求。

**练习八，Little 定律。** 稳定每秒二十请求，平均停留半秒，平均系统请求数十。这里十包括等待与执行，不等于 GPU batch 恒为十。若观察到队列持续增长，先承认不满足稳定条件，不能继续把这个平均数当容量承诺。

**练习九，缓存对照。** 两配置连续使用相同 prompt，后者更快。参考解法是分别使用明确冷态与热态实验，保持模型和请求相同，记录缓存清理或 namespace 方式。只交换实验顺序可以发现顺序效应，但不能单独证明所有缓存状态已被控制。

**练习十，失败进入分母。** 提交十请求，八成功且六达标，两超时。达标率应为六除十，成功请求内达标率为六除八，两者可同时报告但名称不同。只报后者会隐藏超时。原始记录应给每个提交 ID 一个最终状态或明确未完成状态。

**练习十一，小样本尾部。** 四请求的 p99 可以计算，但不应据此宣称稳定的生产尾延迟改善。参考答案包括扩大独立样本、重复实验、保留原始记录、报告样本数与变异。若资源有限，就把结论限制为功能探测，不必为了一个漂亮尾部数字长时间占用共享 GPU。

**练习十二，模拟与实测。** replay 得到较高 synthetic_output_tokens_per_s，说明在该固定成本模型和 trace 下完成逻辑输出更快。它不测真实 GPU 带宽、算力或 kernel。正确图标题必须保留模拟性质，真实硬件结果另建数据表并记录环境。

**练习十三，片段时间。** 一个 SSE 文本事件含三个 token，下一事件含一个 token，间隔十毫秒。你只观察到一次片段间隔，无法恢复三个内部 token 间隔。答案是报告 inter-chunk，而不是把十除三或十除四伪造 ITL。服务端逐 token trace 才能提供额外信息。

**练习十四，窗口边界。** 一个请求在窗口前开始，在窗口内结束。若统计完成请求吞吐可计入完成数；若统计窗口内到达请求队列的最终延迟，则不属于该到达 cohort。两个统计对象不同，必须分别定义。不能分子取完成 cohort、分母却使用另一组请求的生命期。

**练习十五，采集端耗时。** 计划每十毫秒发送一次，但 JSON 编码与连接池使实际每三十毫秒才发。服务没有承受目标到达率。参考解法保存计划和实际时间，先排查客户端 CPU、连接与协程调度，再判断服务容量。不能以计划速率作为实际 QPS 写报告。

**练习十六，设计公平比较。** 两配置至少保持模型 revision、tokenizer、输入 token 分布、输出约束、采样、到达 trace、冷热状态与计时口径一致。记录不可避免的差异，并解释其可能方向。输出等价或质量验收应先于性能胜负；否则“更快”可能只是做了更少或不同的工作。

项目第一阶段，给每条请求保存原始时间点、长度、状态和匿名 ID，写上述指标函数，并用手算样本验证。第二阶段运行 replay 九组配置，保留完整 detail，增加 SLO 表，解释预算与策略怎样改变等待和间隔。第三阶段用 FIFO 离散事件程序生成均匀与突发到达，验证平均负载相同不代表尾部相同。

项目第四阶段，在个人电脑或允许使用的单卡环境做最多四请求的真实协议探测，确认计时字段与 token 来源；此阶段不做生产容量结论。第五阶段才安排有明确总时长、并发上限、输出上限和停止条件的真实负载实验。共享 H100 上先单卡短跑，只有研究通信与并行时才扩大设备数，不能为了取得更多样本无限占用公司 GPU。

最终报告应让没有参与实验的人能够复算：列出问题、假设、配置、输入、计时边界、失败规则、原始记录、统计方法、实际结果与未执行范围。结论写成“在这些条件下观察到什么”，不要写成没有条件的“这个框架最快”。掌握这个表达方式，才有资格把性能数据用于选择架构或修改框架。

掌握门槛：能够从原始时间线独立算 TTFT、ITL、TPOT、E2E 与不同吞吐；能说明百分位定义和样本限制；能识别闭环降载、缓存与输出长度混杂；能用队列模型解释等待；能设计不把失败隐藏掉的 SLO 报告。下一章进入 [S09 真实框架源码导航](09-source-reading.md)，把测量发现连接到实际代码路径。
