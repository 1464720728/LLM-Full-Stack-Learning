# S14 服务诊断：从现象到最小复现

先修基础卷Linux/Docker/网络，S01–S13。你应把排障当成建立并排除假设的实验，而不是按顺序尝试所有命令。本章提供一套从客户端到GPU的调查路径，并要求每次修改只有一个明确目的。

## 1. 先定义故障而不是先改参数

“不能用”需要拆成具体症状：连接被拒绝、请求超时、HTTP4xx、HTTP5xx、首token很慢、生成中断、输出乱码、显存OOM、进程退出、单请求结果不稳定。记录发生时刻、请求ID、输入长度、输出上限、并发与最近版本变化。

连接被拒绝通常说明目标地址端口没有可接收连接的服务或被网络路径拒绝；HTTP404说明已经到达一个HTTP服务但路径不匹配；HTTP400通常属于输入契约问题；服务器返回500说明服务端处理失败，但并不自动证明模型Kernel出错。状态码能缩小范围，不能替代服务日志。

最小复现应固定一个请求、一套配置、一段干净日志。把真实私有提示缩成能触发同样问题的无敏感输入，公开issue才有可共享证据。

## 2. 主机、容器与端口

容器内部的127.0.0.1指容器自身；宿主机的127.0.0.1指宿主机。服务在容器内绑定127.0.0.1，通常不能通过普通Docker端口映射从外部访问；容器内可绑定0.0.0.0，再把宿主端口只发布到127.0.0.1，供本机或SSH隧道访问。

本卷脚本采用 `-p 127.0.0.1:18080:8000`，容器服务监听0.0.0.0:8000。这不是把公司服务暴露给公网。若需要LAN访问，应按实际网络管理要求配置，而不是把所有实验都默认开放。

排查命令：

```bash
ss -ltnp
 docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

这里第二行开头的空格对shell无害，但你应能解释每一列。查特定容器日志用它的精确名称，不要用批量stop/remove影响别人。容器退出码、OOMKilled字段、restart次数都可能提供线索；读取范围限定到自己的实验容器。

## 3. 超时来自哪一层

客户端read timeout、反向代理idle timeout、服务请求deadline、harness单步超时、任务总超时、verifier超时是不同计时器。增大客户端timeout不能修复服务端已经取消的请求；增大Agent总步数也不能阻止某次工具执行超时。

对Agent评测尤其要追调用链。EvalScope可能调度Harbor单题执行；Harness控制多轮模型与工具；环境管理器启动Docker；verifier最终打分。每一层都有版本与超时语义。某个参数叫timeout_multiplier，要看它最终作用于哪一个阶段。

在固定EvalScope快照中，Terminal-Bench配置把agent与verifier的超时选项分别处理，并区分某些agent的模型接口归属。因此写“只改了调度器，单题一定完全一样”需要逐层证据，不能从项目关系推断。

## 4. OOM定位按阶段拆

启动时OOM：权重、dtype、量化加载过程、并行分片和图捕获；首请求OOM：shape触发的workspace、编译或缓存配置；并发升高后OOM：状态池、活动请求、临时激活；运行很久后持续增长：资源泄漏、未回收输出、缓存无界或日志堆积。

先采集模型配置、设备总量与当时其他进程占用，再看框架日志的可用KV块与内存预算。如果共享卡已被别人使用，不要把别人的进程杀掉，也不要把利用率提高强抢空间。练习可以换已分配的设备或缩小模型/长度。

OOM之后能否继续使用同一进程取决于错误性质与框架实现。不要把所有CUDA错误都当普通Python内存异常重试。非法访问、通信组失败等可能要求重建Worker或整个服务。

## 5. 性能回归的四层剥离

先用固定输入的单算子测量确定Kernel是否变慢；再用离线模型前向测Runner与模型；再用本地HTTP测服务开销；最后上Agent端到端。若仅Agent变慢，而单次模型延迟不变，可能是工具调用更多、上下文增长、检索变化或重试增加。

请求数量、输入token、输出token、cache-hit、完成原因、错误数都应一起比较。把新版本更长更完整的回答直接判为runtime退化，会误导优化。反过来，丢输出或提前停止可以“加速”，必须用正确性验收挡住。

Profiling要限定窗口。长时间全量trace可能占大量磁盘、CPU并影响被测系统。先用轻量指标找到异常窗口，再抓短trace。GPU计时要同步或使用事件；Python函数返回只代表提交完成时，不能拿它当Kernel耗时。

## 6. 一份能被别人复现的报告

报告应包含：问题摘要；最小输入与期望/实际；版本与commit；模型revision与模板；硬件/拓扑；完整但已去密的启动参数；复现命令；相关日志；最近正常版本；已排除的因素。不要贴API Key、公司端点、私有路径或完整业务数据。

把“观察”“解释”“待验证假设”分开。例如观察是p95TTFT从100升到300；假设是长prefill抢占预算；证据是batch trace中短请求等待更多轮；验证是只改变chunk阈值并保持其他条件。这样的报告能促成可靠修改。

## 7. 练习与解答

1. **端口场景。** HTTP404与connection refused分别说明什么？答案：前者至少有HTTP响应者，重点查路径/服务类型；后者先查监听与网络，不要先改模型参数。
2. **容器映射。** 解释本卷18080:8000映射，两侧分别是哪一个端口。再用SSH本地转发访问远端loopback服务。只操作自己的端口；若占用，选择新端口并同步客户端配置。
3. **故障复现。** 用mock_server发送超长prompt_token_ids或max_tokens=65，预期400，服务应继续健康。验收 `/metrics` bad_request增加，accepted不增加；不能让输入错误把整个进程结束。
4. **性能变量控制。** 两次测试同时改变TP、dtype、cache和模型revision，不能归因。参考解法是回到同一基线每次只改一个变量，必要时做小型因子实验，并对照输出正确性。
5. **评测超时表。** 为一个Agent任务列客户端、模型服务、Agent、环境、verifier的timeout，写清谁触发后谁还在运行。只有验证各层传播后，才可宣称取消完整回收。
6. **写回归issue。** 用S05的活锁故障构造一个报告：预期有限完成、实际反复抢占、最小请求集合、固定seed、事件片段、测试命令和修复解释。参考验收：一个未参与写作的人无需口头补充即可复现；不要只写“跑着卡住了”。

掌握门槛：能从具体症状选第一条检查；能设计最小复现；能区分网络、协议、调度、Kernel与harness问题；能写出可复核的回归报告。
