# S13 容量模型：先算出每个 rank 的账，再启动模型

先修 S03、S10、字节单位与简单代数。容量估算的目的不是给出一个看似精确的“能/不能”，而是发现瓶颈、列明假设，并用小规模测量校准。算术上放得下是必要条件之一，软件支持、临时峰值和通信仍可能让部署失败。

## 1. 六本内存账

权重、KV/递归状态、激活与临时工作区、通信缓冲区、运行时与图捕获、分配器保留/碎片，至少应分开记。权重量化主要改变第一项；KV量化改变第二项；chunked prefill可能改变第三项；TP/EP等并行改变多项的分布而不是统一除一个系数。

8B参数以16bit存储，裸权重约16GB，即约14.90GiB。量化到4bit裸权重约4GB，但还需要scale、zero-point、对齐、可能未量化层与runtime元数据；不能直接把14.90除4当全部显存。对MoE，激活参数少不等于全部专家权重不需要存放，除非采用明确offload或按需加载机制。

设备厂商标注容量、驱动报告、框架可分配容量还可能使用不同单位或保留空间。容量报告统一写GiB或GB，必要时同时显示，避免80GB与80GiB混淆。

## 2. 标准KV的手算

取32层、8个KV头、head_dim128、KV每元素2字节。每token为 `2×32×8×128×2=131072`字节，即128KiB。32768 token约4GiB；131072 token约16GiB；1048576 token约128GiB，均为单请求全层标准KV且未分片的算术值。

如果TP=8且KV头可严格均分，每rank每token16KiB，1M上下文每rank16GiB。这里忽略了权重、workspace等，也假定每层都是相同attention。换成MLA、滑窗、线性注意力或混合SSM，不应继续套这张表；应为每类层写状态公式再求和。

长度上限还可能包括输出预算。输入长度接近max_model_len时，可生成空间减少。某些API报错、某些截断或限制，行为取决于契约。评测中悄悄截断提示会改变任务，不能只把它当容量优化。

## 3. 逐rank而非总和

TP可能分权重和头；PP按层；EP按专家；DP副本独立。LM head、embedding、共享专家、norm和路由器的分片规则可能不同。先写“对象→拥有者→复制/切分→每rank字节”表，再计算最高rank。

例如两个PP stage，一个有较大embedding和输出头，另一个层数更多；平均显存虽然小于容量，第一阶段仍可能OOM。TP头数不整除或KV复制时，某些状态不会线性减少。通信库还可能按world_size分配额外buffer，这也需要加入。

本卷`Capacity`刻意只支持“均匀层、权重均匀分片、KV头整除TP”的模型。遇到不整除直接报错，而不是给一个貌似合理的数字。一个好的估算器应拒绝超出假设的输入。

```bash
python -m labs.serving.experiments --lab memory_capacity
```

阅读输出的assumptions，再看arithmetic_fits；不要反过来只看True就部署。

## 4. 经验校准的最小流程

固定小模型与版本，启动时记录加载后显存；把上下文从512、1024、2048逐级增加，观察KV占用与workspace峰值；把并发从1、2、4增加，检查增长是否符合预期；每步记录请求结束后的逻辑free blocks和设备allocated/reserved。

若理论每增加一个token增加128KiB，而实测分配呈阶梯状，可能因为分页块对齐或框架预分配整个池。预分配时设备显存不会逐请求线性变化，应该从可用块与块字节数推算。不能拿nvidia-smi的平坦曲线否定KV随长度增长。

在共享H100上，从已分配的一张空闲卡做短实验；不需要为了验证基础公式占满八卡。只有要验证TP/EP/通信或单卡放不下的明确课题，才申请多卡时间段。

## 5. 量化与长上下文的不同瓶颈

权重量化腾出空间可能让更多KV可用，但长上下文attention仍可能耗时或需要额外workspace。KV量化减少状态，但引入scale、转换、后端支持与数值误差。CPU offload把某类数据移出GPU，却受CPU容量、PCIe带宽、NUMA、固定页内存等约束。

不关心速度并不自动意味着所有offload方案都可行：实现可能不支持某模型结构或跨节点路径，临时张量仍需在GPU上出现，超时或数据传输错误也会阻断。先验证功能路径，再讨论是否接受慢速。

1M上下文还要考虑tokenizer、请求体、服务前端内存、日志、客户端超时、位置编码配置与模型原生长度。仅修改一个max_model_len参数不能创造模型没有训练或架构支持的能力。

## 6. 练习与答案

1. **单位转换。** 16,000,000,000字节除2^30约14.90GiB；除10^9是16GB。写一个同时输出两种单位的函数，并明确输入单位是字节。
2. **KV公式。** 40层、4KV头、head_dim128、2字节、65536token，KV为`2×40×4×128×2×65536`=5GiB。若两个并发同长度，10GiB；注意prefix共享可能让物理占用不同，但没有共享证据时不要提前减。
3. **复制陷阱。** 2个KV头、TP=8，估算器拒绝。参考答案不是把2/8当0.25头，而是查看实现是否复制头或采用另一布局；明确每rank真实KV头数后才能算。
4. **混合状态。** 24层中12层标准KV、12层固定大小状态，每SSM层每请求1MiB。总状态=12层attention的长度相关项+12MiB固定项。若还有卷积状态或中间checkpoint，应另加，不假设全部固定状态都只有一项。
5. **余量分析。** 可用预算64GiB，权重40、KV16、workspace6、通信1，剩1GiB。即使算术能放下，也很脆弱。提出验证：测峰值、非整块长度、并发上界、图捕获、冷启动，而不是盲目把利用率提到1。
6. **制作部署表。** 为自己的一个具体开源小模型读取config与权重大小，列layers/kv_heads/head_dim/dtype/revision，计算上下文1k/2k/4k和并发1/2的容量。缺字段就保留未知并查实现，不按相近模型猜。再用一张卡短测校准，保存预测与实测差值。

掌握门槛：能从模型shape推KV字节；能识别公式不适用的架构；能按rank算峰值而非平均；能用测量修正模型，明确“算术可行”与“实际可部署”的差别。
