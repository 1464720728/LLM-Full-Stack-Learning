# S04 前缀复用：缓存命中必须先保证语义正确

先修 S03。Agent 会反复携带相同系统提示、工具定义和历史，长对话的前缀复用很有价值。但缓存命中率高不等于正确：把不兼容的状态共享给另一个请求，比缓存未命中严重得多。

## 1. 可复用的是计算状态，不是“意思差不多”

KV 对应特定模型计算下的 token 序列和相关上下文条件。两段语义相似的文本，token 不同，通常不能直接共享 KV。两个看起来完全相同的字符串，也可能因聊天模板、特殊 token、Tokenizer 版本不同而产生不同 token ID。另一个模型版本或 LoRA adapter 对同一 token 序列算出的状态也可能不同。

因此，命中键要反映影响状态的因素：模型权重/版本、token 前缀、adapter、多模态输入或它的稳定标识，以及系统要求的隔离域。不要把用户提供的任意字符串直接当可信模型身份。应用层和服务层应约定谁生成 namespace，谁有权选择它。

我们的键是 `(namespace,完整token前缀)`，避免在入门阶段引入哈希碰撞。生产系统通常使用链式块哈希或 Radix Tree 等压缩结构；省空间与快速查找是后续优化，语义前提不能省略。

## 2. 为什么命中全部提示仍可能要重算

假设缓存已经有 `[1,2,3,4]` 的 KV，新请求提示恰好也是这四个 token。若缓存只保留 K/V，不保留最后位置的 logits，则要生成下一个 token，仍需得到当前最后位置的输出。常见实现会重算最后 token；若复用边界要求整块对齐，可能退回一个完整块。

已核实 vLLM 快照的 `KVCacheManager.get_computed_blocks` 明确说明这个边界。不要把“4 个 token 全在缓存”与“可以零计算直接采样”画等号。另一种系统可以缓存更多输出状态，但那是不同的缓存契约。

我们令最大复用长度为 `floor((prompt_length-1)/block_size)*block_size`。提示长度 5、块大小 2，可复用 4；长度 4，只复用 2。这不是普遍最优策略，而是与本实验“全块 KV、重新产生 logits”的约定一致。

## 3. 缓存条目与活动请求各自持有引用

A 的提示 `[1,2,3,4,5]` 完成 prefill 后，发布前 4 个 token 的两页。缓存各持有一份页引用；A 继续生成时仍拥有自己的引用。A 结束，自己的引用消失，缓存仍可保留两页。B 的提示 `[1,2,3,4,6]` 到来，找到前 4 个 token，自己的表再增加引用，并从 computed=4 开始。

运行：

```bash
python -m labs.serving.experiments --lab prefix
python -m labs.serving.experiments --lab namespace
python -m labs.serving.experiments --lab cache_eviction
```

第一个实验 warm 请求应报告 4 个缓存命中 token。第二个实验改变 adapter namespace，B 应命中 0。第三个实验缓存容量为 1 个条目，淘汰旧条目后空闲页增加；clear 后应全部归还。这里要对照 refs，而不仅看缓存条目数。

## 4. 完整匹配、共同前缀与 Radix Tree

Python 字典只能直接找到完整键。若缓存存 `[1,2,3,4]`，新提示 `[1,2,9]`，仍然可以复用前 2 个 token。因此 `attach` 遍历候选，计算块对齐的共同前缀，选最长匹配。它是容易验证的朴素算法，条目多时很慢。

Radix Tree 将共同前缀共享为树边，边上可存多个 token。插入 `[1,2,3]` 和 `[1,2,9]` 时，公共路径是 `[1,2]`，随后分叉为 3 与 9。查找可能在一条边内部结束，因此需要 split；节点还需要记录状态位置、访问时间和锁/引用信息。树只是索引，实际 KV 仍在状态池中。

SGLang 的固定快照里，`RadixCache.match_prefix`、`insert`、`evict` 可以看到这些职责；`RadixKey.extra_key` 参与逻辑隔离。不要因为名称叫 RadixAttention，就认为它一定是一种改变 attention 数学公式的模型架构；这里主要讨论的是运行时复用机制。

## 5. 淘汰策略为什么影响性能与公平

LRU 淘汰最近最少使用条目，简单但未必最合适。一个长前缀占用很多页、重算又贵；一个短前缀访问频繁、命中收益小。只按最近访问时间排序，忽略大小和重算代价。可以考虑命中次数、长度、上次使用、重算时间、未来复用概率，但每增加一个指标都有记录成本和估计误差。

缓存不能驱逐仍被活动计算使用的数据。我们的缓存 eviction 只释放缓存自己的引用，活动请求引用会保住页面。真实系统如果需要从设备移到 CPU，则还要考虑复制时刻、目标空间、传输完成、恢复成本。一个缓存条目“可淘汰”不表示立即有一整块物理内存可用，因为其他拥有者可能还在。

命中率的分母也要清楚。按请求计算，100 条短请求命中而 1 条巨大请求未命中，可能很好看；按 token 计算却很差。按节省 prefill 时间计算又不同。报告至少注明 request-hit、token-hit 与缓存占用，不能只写一个百分比。

## 6. Agent 场景的缓存友好性

每轮把稳定系统提示、工具 schema 放前面，把变化内容放后面，通常更有利于前缀复用。但不应为了命中率随意重排有语义顺序的消息。JSON 字段排序、工具定义生成、时间戳插入位置、聊天模板版本，都可能影响 token 前缀。

用相同问题发送十次并发请求，未必获得九次命中：如果第一条尚未发布可复用状态，其余九条都可能先开始 prefill。本实现每轮后发布；生产系统发布时间和并发去重策略需看源码。测试 warm-cache 要明确预热请求已经完成，cold-cache 要确认缓存已清空或隔离 namespace。

## 7. 练习与详细答案

1. **算命中上限。** prompt 长 17，block=8，至少重算最后 token，最多命中 16。prompt 长 16 时最多命中 8。解释这两个相差一 token 的请求为什么可能有一整块差距：块对齐与 logits 重算共同导致，不是 tokenizer 失误。
2. **共同前缀。** 缓存 `[1,2,3,4,5,6]`，新提示 `[1,2,3,9,5]`，block=2。最长相同原始前缀为 3，但完整块命中只能是 2。为 `attach` 添加测试，验收不会错误复用第三位置所在整块。
3. **隔离漏洞。** 删掉 namespace 比较，让 adapter A 和 B 命中相同页。当前 Bigram 后端没有 adapter，所以输出可能碰巧一样。答案：测试要检查命中应为 0，或增加 adapter 改变 logits 的后端；不能以碰巧输出相同证明隔离正确。
4. **缓存淘汰仍有活动用户。** A 发布两页，B attach，再 clear cache。验收 A/B 的 tokens 仍存在，refs 从 3 降到 2；之后分别 release，才归零。这个题检验资源所有权，不是淘汰排序。
5. **实现受空间约束的策略。** 把 max_entries 换成 max_cached_pages。参考解法应按唯一物理页统计占用，不能简单把每条前缀的页数相加，因为多个条目可共享页。若选择“逻辑引用页数”作为预算也可以，但必须命名正确，并解释它与真实占用的差异。
6. **前缀缓存研究任务。** 在 SGLang 固定快照中找出 match 的返回对象、节点分裂、锁引用增加与减少、evict 条件。画出“前缀命中→保护节点→执行请求→释放保护”的闭环；用一个中途取消的请求检查是否每条路径都有释放动作。先只写分析笔记，再做独立分支上的最小测试补丁。
