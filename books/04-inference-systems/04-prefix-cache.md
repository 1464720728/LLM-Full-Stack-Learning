# S04 前缀缓存：相同输入什么时候真的能共享状态

上一章建立了页面所有权：页表指向物理块，引用计数决定何时可以回收，共享半满尾页写入前需要复制。本章在它之上增加一个新的拥有者——前缀缓存。它把某些已经算出的历史状态保留下来，使后续请求可以跳过一部分重复计算。

“两个问题开头相同，所以能命中缓存”只是一个很粗的直觉。要把它写成正确系统，你还要回答：比较的是文字还是 token？相同 token 在不同模型、adapter 或位置下能否共享？缓存条目保存什么？请求结束时谁仍持有页面？部分命中怎样附加引用？为什么常常还要重算最后一个 prompt token？淘汰一个条目为何可能没有释放任何物理页？

本章逐行解释 `labs/serving/kv.py` 中的 PrefixCache，并将它与真实框架里的块哈希、radix tree 等设计建立联系。我们使用固定的上游源码快照描述具体接口，不把滚动版本名称当作永远成立的行为保证。所有数值例子都是合成数据，真实 GPU 缓存命中性能没有在本章冒充实测。

## 第一课：缓存的是状态，不是答案

### 1.1 答案缓存与前缀缓存

答案缓存保存某个请求过去得到的完整响应。再次遇到被认为相同的请求时，可以直接返回结果。前缀缓存保存的是模型在处理某段输入后产生的中间状态，后续请求仍需要继续计算并生成自己的输出。

这两个机制的语义不同。答案缓存可能改变随机采样体验，因为直接重放过去结果；KV 前缀缓存只复用符合条件的已有计算状态，理论上可以继续按本次采样配置生成新的结果。能否保持完全相同的浮点轨迹，还要看具体执行路径与后端。

一个共同 system prompt 后面接两个不同问题，完整答案当然不同，但前面的模型状态可能相同。前缀缓存利用的是这个重复子问题。它不会因为 system prompt 相同就把上一个用户的回答直接拿来当作新回答。

### 1.2 为什么只能复用满足因果条件的前缀

标准因果 Transformer 的某个位置只能依赖它之前和当前的输入。若两个请求从开头到位置 k 完全相同，且模型和相关语义相同，这些位置产生的 K/V 可以相同。后面尚未出现的不同问题不应反向改变前面位置。

但是中间一段文字相同，并不一定产生相同 K/V。例如两个请求分别是 `[1,2,8,9]` 与 `[3,4,8,9]`。末尾 token 8、9 相同，但它们的上游 hidden state 已受不同前文影响。不能只按当前块自己的 token 内容复用，而忽略它之前的上下文。

这正是块哈希常需要把前一个块的身份纳入当前块键的原因：缓存身份必须表达完整前缀语义，而不只是局部块看起来一样。课程实现保留完整 token 元组作为键，牺牲空间与查询效率，换来更容易核对的正确性定义。

### 1.3 缓存命中不等于零计算

即使大部分 prompt 已缓存，仍可能需要处理最后一个位置来得到当前请求的下一 token logits，也可能需要处理新增后缀、不同位置或其他未缓存部分。网络处理、模板构造、tokenization、查找和元数据准备也不必为零。

因此报告“命中了九成 prompt”不能直接推导“总响应时间缩短九成”。需要区分避免的模型计算、查找与附加成本、剩余 prefill、排队和 decode。S08 会进一步介绍如何测量，而本章先确保命中的含义本身正确。

## 第二课：缓存身份需要包含什么

### 2.1 文字相同与 token 相同

用户看到同样一句话，不同 tokenizer、聊天模板或特殊标记可能得到不同 token 序列。反过来，两个不同文本表示也可能经某些预处理后得到相同序列。模型执行依据实际 token 与相关输入，不是网页中的表面文字。

因此复现缓存实验时，应保存格式化后的 token ID，而不是只保存原始字符串。若你在一个框架中手动插入 system 标记，在另一个框架中让模板自动插入，两个结果可能并不相同。此时没有命中缓存可能是正确行为，而不是实现失败。

课程 PrefixCache 接收已经编码好的 prompt 元组，它不负责模板或 tokenizer。这个边界让代码简洁，也要求调用方对 token 身份负责。你不能把两套不同词表下同样的整数序列交给同一个 namespace，再期待缓存自动知道它们含义不同。

### 2.2 模型参数与 adapter

K/V 来自模型计算，同样 token 在不同权重下通常产生不同数值。模型权重版本因此是缓存身份的重要部分。名称相同不够：一个模型目录在原地替换了权重，若 namespace 没更新，旧状态可能被错误复用。

Adapter 也可能改变投影或其他计算路径。同一个基础模型搭配不同 adapter，缓存是否兼容必须由实际架构和实现决定，不能默认共用。最保守清楚的学习策略是把 adapter 身份纳入命名空间，并用不同命名空间不命中的测试保护边界。

本课程 namespace 是调用方提供的非空字符串，例如 `model-v1:adapter-none:tenant-demo`。字符串本身没有魔法：它不会自动验证模型文件哈希，也不会自动随权重修改。你需要建立“配置身份如何产生、何时更新、旧缓存如何失效”的上层协议。

### 2.3 位置与注意力语义

RoPE 等位置处理使同一个 token 在不同逻辑位置的 K/V 语义不同。滑动窗口、特殊 mask、前缀位置偏移或其他上下文规则也可能影响可复用状态。缓存键与复用规则必须覆盖这些条件。

本教学缓存只处理从请求开头开始、位置语义一致的普通前缀，不支持把某段历史任意搬到新的位置。若要研究跨位置复用，必须证明需要怎样变换缓存或重新计算，不能只因为 token 元组相同就省略位置条件。

此外，模型运行模式和缓存布局需要兼容。一个 backend 产生的数值格式不一定能被另一个 backend 原样读取；不同 KV dtype、打包方式或缓存组定义可能需要转换或独立池。逻辑身份相同不等于物理表示可以直接混用。

### 2.4 租户与权限边界

缓存共享也有服务边界。一个系统可能允许公开共同提示跨请求共享，却要求不同租户的状态隔离。是否允许共享属于服务的明确策略，不能仅从数学上“这些 token 一样”推出。

本课程把 tenant 放进示例 namespace，是为了让你看见隔离维度。它并没有实现完整认证系统；调用方不能允许不可信客户端随意选择别人的 namespace。身份必须从可信上下文绑定，而不是把用户输入字符串直接当作授权依据。

缓存还可能通过命中时延透露某些前缀是否被处理过。是否需要缓解这种侧信道取决于具体服务威胁模型。这里不夸大一个教学实现的安全能力，但要提醒你：缓存是共享状态，语义正确与访问策略都要单独设计和验证。

## 第三课：课程缓存条目的精确定义

### 3.1 键和值

entries 是一个 OrderedDict。键为 `(namespace, token_prefix_tuple)`，值为这个前缀对应的物理页号元组。键描述状态身份，值描述状态存储在哪里。两者必须匹配；不能只保存 token 前缀却忘记拥有实际页引用。

使用完整 token 元组避免了哈希碰撞处理和链式块身份的教学复杂度。代价是键可能很长，查找可能遍历很多条目；这个实现适合验证语义，不适合直接宣称拥有生产缓存规模下的效率。

OrderedDict 还保存条目的访问顺序。本课程用 move_to_end 把近期使用的条目放到末尾，用 popitem(last=False) 淘汰最旧条目。这是一种按条目计的 LRU 近似，不是按字节、页数或重新计算成本最优的缓存策略。

### 3.2 一条缓存记录也是一个拥有者

publish 新条目时，会对对应物理页 retain。这样原请求结束、释放自己的活动引用后，页面仍因缓存拥有而保留。若 publish 只把页号写进字典却不 retain，原请求结束后页面就可能进入 free，被其他请求覆盖。

这类错误很隐蔽：缓存条目还在，看起来命中率很高，但它指向的物理页已经换了内容。必须把“索引中存在记录”与“记录合法拥有对应资源”一起验证。S03 的 refs 账本会把缓存拥有者也算进去，正是为了检查这个关系。

### 3.3 多个条目可以共享页面

假设一个条目保存前四个 token，另一个保存前八个 token，它们可能引用相同的前面物理页。两个条目各自是一份拥有关系，所以该页会贡献两次缓存引用。淘汰其中一条，只减少对应一次引用。

这意味着缓存条目数、缓存引用总数、缓存独占物理页数是三个不同数量。只看 entries 长度无法知道实际占用多少内存；只把每条目的页数相加，又可能重复计算共享页。正确的容量报告需要说明统计口径。

本课程 refs 方法用 Counter 遍历所有 entries 的页号，得到每页缓存引用次数。它用于所有权校验，不直接把这些重复引用当成不同物理页的字节开销。

## 第四课：publish 如何把已计算前缀变成可复用状态

### 4.1 为什么只发布完整页

课程实现按完整页发布，避免缓存条目引用尚可能继续原地增长的半满尾页。设 block_size 为四，已经计算六个 prompt token，只发布前四个；后两个还在尾页中，不进入本缓存条目。

这不是说半页缓存从理论上永远不可能，而是完整页让身份、有效长度和共享写入规则更简单。要支持半页条目，就必须明确有效长度、后续追加是否触发 COW、条目身份是否随内容变化，以及匹配时如何保持不可变快照。

完整页粒度会浪费某些可复用机会。例如两个五 token prompt 只有最后一项不同，缓存仍能复用前四项；若两个三 token prompt 相同，块大小四的课程缓存不会发布任何条目。粒度选择影响命中收益，也影响管理复杂度。

### 4.2 计算发布长度

publish 先读取请求当前已存的 token，然后计算 `n = min(len(tokens), max_tokens)//block_size*block_size`。min 防止发布超出当前已经存在的状态，也防止把不允许发布的生成后缀混进去；整除再乘块大小，把长度向下对齐到完整页边界。

例子：池里有九个位置，调用方只允许发布前七个，块大小四。min 得到七，对齐后 n 为四。你不能用向上取整把 n 变成八，因为第八项不在本次允许发布范围内；也不能直接用七，因为值对应的是完整页元组。

max_tokens 必须为非负整数。负数在 Python 切片里有特殊意义，如果不验证，可能被错误解释成“去掉末尾若干项”，并返回一个负的命中长度或发布不该发布的内容。资源数量参数不能让语言的切片惯例替代业务合同。

### 4.3 已有条目不重复 retain

如果键已经存在，publish 只更新其最近使用顺序并返回 n，不再增加引用。否则同一请求每轮重复发布同一前缀，会不断增加 refs，而 entries 中只有一条拥有记录，造成计数泄漏。

这个细节说明幂等性不只是重复返回同样结果，还必须保证重复调用不增加不应有的资源责任。测试应多次 publish 同一键，比较 refs 与 entries 数量，确认稳定。

如果新请求用另一组物理页计算出了相同语义前缀，而缓存已经保留旧页，课程实现继续使用旧条目。新请求自己的页面仍按其生命周期释放。缓存不必因为内容重复就保存所有等价物理副本。

### 4.4 新条目发布的顺序

取得对应页号后，先 retain，再把条目写入 entries，最后根据 max_entries 淘汰多余条目。retain 验证全部页面仍然有效，避免把自由页身份发布为可复用缓存。

在当前同步、合法输入的教学路径中，这个顺序容易解释。但如果你把缓存改造成多线程或跨进程服务，还要定义检查、增加引用和发布索引之间的同步边界。不能因为每个函数单独看起来合理，就认为并发交错也自动安全。

## 第五课：attach 为什么不是简单的字典查找

### 5.1 新请求可能只有部分前缀相同

缓存中有 `[1,2,3,4,5,6,7,8]`，新 prompt 为 `[1,2,3,4,9]`，块大小二。完整键不同，但前四个 token 相同，因此可以复用前两页。只做 exact-key lookup 会错过这个机会。

课程实现遍历同 namespace 的条目，从允许长度开始按块递减，寻找共同完整页前缀。它是一个易读的参考算法，不是高效树索引。其价值在于每一步比较都能手算，也不隐藏碰撞和压缩结构。

### 5.2 为什么限制到 prompt 长度减一

attach 的 limit 为 `(len(prompt)-1)//block_size*block_size`。它故意保证至少一个 prompt token 由本次请求重新处理，以得到预测下一 token 的 logits。仅有 K/V 缓存，不一定保存了最后 prompt 位置的最终 hidden state 或 logits。

例如 prompt 长度四、block_size 二，即使缓存有完整四项，limit 也只允许复用两项，还要重算后两项。不是数学上必须重算两项，而是完整页粒度与“至少重算最后一项”共同导致这个结果。

prompt 长度五、块大小二时，limit 为四，可以复用四项，只处理最后一项。prompt 长度一时，limit 为零，不能跳过唯一输入。这个边界特别适合写成测试，因为只测试很长 prompt 往往看不出最后一项的责任。

如果你额外缓存与当前模型、输出模式兼容的末位置 hidden state 或 logits，可以设计另一种协议来减少重算。但那时缓存条目不再只拥有 K/V 页，必须明确额外数据的身份、内存、有效性和采样兼容条件。不能在现有接口中直接把 computed 设成全部 prompt 长度而不给引擎产生首 token 的路径。

### 5.3 逐块回退比较

对某条缓存键，先取其长度与 limit 的较小值 n。若新 prompt 的前 n 项与缓存前 n 项不相同，就把 n 减一个 block_size，再比较。因为 n 始终是完整页倍数，最终结果可以直接转换成页数。

例如块大小二，缓存为 `[1,2,3,4,5,6]`，新 prompt 为 `[1,2,3,9,10,11,12]`。limit 为六，先比较六项不同，再比较四项仍不同，再比较两项相同，命中两项。你不能因为第三项相同就复用三项，因为该实现只支持完整页。

若差异发生在第一项，所有正长度比较最终失败，命中为零。若 namespace 不同，即使 token 全部一样，也不进入比较候选。这保证隔离条件先于内容相似度。

### 5.4 从最长匹配到拥有引用

找出最长 n 后，取缓存页号元组的前 `n//block_size` 项，调用 pool.adopt 附加到新请求空页表。adopt 增加请求自己的引用，缓存原有引用仍然存在。随后更新该缓存条目最近使用顺序，返回 n。

返回值不是凭空的“命中计数”。它必须与新请求实际页表里的载荷前缀一致。Engine 把返回值赋给 computed，因此如果 attach 只返回 n 而没建立映射，后续调度会跳过一段根本没有资源支撑的历史。

若多个条目提供同样长的匹配，本课程选择遍历中遇到的第一个最大值。正确语义要求这些候选都代表相容的相同前缀，所以选择哪组等价物理页不应改变数值；但访问顺序与内存分布可能不同。性能策略可以进一步优化，不能以此破坏身份约束。

## 第六课：用具体页面编号追踪一次冷请求与热请求

设 pool 有六页，block_size 二，缓存最多保存两个条目。A 的 prompt 为 `[1,2,3,4,5]`。先完整处理五个位置，A 页表为 `[0,1,2]`，页零保存一二，页一保存三四，页二保存五。

publish(A, namespace="m", max_tokens=5) 对齐为四，只保存页零和页一。它们 refs 从一变成二：一份属于 A，一份属于缓存。页二仍只有 A 的引用。

A 结束并 release 后，页零和页一各保留一个缓存引用，页二归还 free。此时活动请求为零，但 free 只有四页而不是六页。这是有意缓存，不是泄漏。

现在建立 B，prompt 为 `[1,2,3,4,9]`。limit 为四，匹配前四项，adopt 页零和页一；二者 refs 从一变成二。B 的 computed 为四，只需处理末项九。这个新位置进入 B 自己的新页，不会修改已有完整共享页。

| 时点 | A页表 | B页表 | 缓存页 | 页0/页1引用 |
|---|---|---|---|---|
| A处理后 | [0,1,2] | 无 | 无 | 1 / 1 |
| 发布后 | [0,1,2] | 无 | [0,1] | 2 / 2 |
| A释放后 | 无 | 无 | [0,1] | 1 / 1 |
| B附加后 | 无 | [0,1] | [0,1] | 2 / 2 |
| B释放后 | 无 | 无 | [0,1] | 1 / 1 |
| 缓存清空后 | 无 | 无 | 无 | 0 / 0 |

你可以用下面的完整程序核对：

```python
from labs.serving.kv import PagePool, PrefixCache

p = PagePool(6, 2)
cache = PrefixCache(p, max_entries=2)
p.create("A")
p.append("A", [1, 2, 3, 4, 5])
assert cache.publish("A", "m", 5) == 4
p.check(cache.refs())
p.release("A")
p.check(cache.refs())

p.create("B")
hit = cache.attach("B", "m", (1, 2, 3, 4, 9))
assert hit == 4
assert p.tokens("B") == [1, 2, 3, 4]
p.append("B", [9])
assert p.tokens("B") == [1, 2, 3, 4, 9]
p.check(cache.refs())

p.release("B")
cache.clear()
p.check(cache.refs())
assert len(p.free) == 6
```

注意 check 必须传入 cache.refs。若只统计活动页表，会把合法缓存拥有误判成多余引用。这是系统组合中的常见问题：单个模块的不变量在加入新拥有者后，需要扩大账本范围，而不是把原断言直接删除。

## 第七课：淘汰为什么不一定释放页面

### 7.1 条目删除与物理释放

evict_one 从 entries 中取最旧条目，再对它持有的页 unpin。若某页还被活动请求或其他条目引用，它不会归还 free。因此一次成功淘汰返回 True，只表示一个缓存条目被移除，不保证自由页数立刻增加。

调度器的分配循环因此需要重新检查 needed 与 free，而不是假设淘汰一次就足够。它可能连续淘汰若干条目，直到释放了可用物理页，或已经没有条目可淘汰。

一个手算例子：A 正在使用页零，缓存 C1 和 C2 也各持有页零，refs 三。淘汰 C1 后 refs 二，自由页不变；淘汰 C2 后 refs 一，自由页仍不变；只有 A 结束后才归还。把缓存淘汰的条目数直接当作释放页数，会高估腾出的容量。

### 7.2 LRU 的单位

本实现 max_entries 限制条目个数。一个只保存一页的条目与一个保存一百页的条目，都计为一。若工作负载前缀长度差异很大，条目数上限并不能精确限制物理内存占用。

生产策略可能按页数、字节数、重算代价、访问频率或组合收益来管理缓存。不同策略都有取舍：保留很长但很少复用的前缀，可能排挤多个短而高频的前缀；只看命中次数又可能忽视一次长命中节省的大量计算。

你应先为策略选择一个可解释收益量，再做固定工作负载对照。不要仅因为某个名字听起来先进就替换 LRU；如果连条目和物理页的统计都没区分，新策略很容易优化错误目标。

### 7.3 缓存不应阻止活动工作永久前进

缓存是优化，应在资源紧张时让位给必须推进的请求。若所有自由页都被可淘汰缓存占据，调度器应能释放缓存引用。若缓存规则把所有页永久固定，即使没有活动请求也无法接纳新任务，就把优化变成了可用性障碍。

同时不能为了前进随意删除活动请求所需的状态。正确的共享引用协议使“淘汰缓存拥有”和“保留活动拥有”可以同时成立。这是资源层与调度层合作的关键：调度器提出空间需求，缓存层放弃可放弃的拥有，页池决定哪些物理页真正变自由。

## 第八课：从完整元组到块哈希与 radix tree

### 8.1 为什么完整元组参考很清楚却不够高效

课程匹配会遍历条目并比较多个前缀切片。条目很多、前缀很长时，比较和键存储成本都可能很高。它还可能为多个重叠前缀重复保存大量 token 身份信息。

这并不意味着应该一开始就使用复杂索引。先保留一个最容易证明正确的参考，让后续索引在相同输入上返回等价命中长度和合法页引用。优化目标是降低查找和维护成本，不能改变“哪些状态可以共享”的定义。

### 8.2 块哈希的前缀依赖

一个思路是按固定 token 块计算身份，并把前一个块的身份、当前块 token、模型相关额外信息一起纳入新身份。这样同样局部 token 若处于不同前文，其块身份也不同。

例如前缀 P 的第一块为一二，第二块三四；另一个前缀 Q 第一块九八，第二块同样三四。如果只哈希第二块三四，两者会冲突在语义上；把前一块身份串入后，它们得到不同的链式前缀身份。这里说的冲突不是密码学哈希偶然撞值，而是错误地遗漏了必要输入，导致必然的语义混淆。

真正哈希函数还存在碰撞处理与信任边界问题，具体策略应依据框架实现和威胁模型。课程不凭空声称某种哈希永不碰撞，也不把一个 Python hash 值当作跨进程、跨版本稳定的内容身份。

### 8.3 radix tree 的共享边

Radix tree 把多个键的共同前缀合并到树路径中，边可以保存一段 token，而不必每个节点只放一个 token。查找沿边比较，遇到分歧时停止；插入可能需要把一条长边在共同前缀处拆分。

设已有路径 `[1,2,3,4]`，新序列为 `[1,2,3,9]`。共同部分是一二三，可以把它作为共享边，再分出四与九的两个分支。真实 KV 管理还要考虑块粒度、节点持有的页、锁定引用和淘汰条件，不能把一棵纯字符串 trie 直接等同于生产 RadixCache。

树节点拆分只是修改索引结构，不应无理由复制全部共享 K/V。关键是把逻辑前缀区间与物理载荷拥有关系重新表达清楚。SGLang 固定快照的 RadixKey、TreeNode、match/insert/evict 路径正是源码工作坊中的观察对象。

### 8.4 优化索引的等价性验收

为同一批 namespace 和 token 序列，同时调用慢元组参考与新索引，比较最长可复用完整页长度。随后真正 attach 并检查页池拥有关系，而不是只比较一个命中数字。

必须覆盖前缀完全相同、仅第一块相同、中间分歧、不同 namespace、长度一、恰好整页、比已有键更短、比已有键更长和条目淘汰后的查询。索引代码若只对“新请求比旧请求更长”的常见路径测试，容易漏掉短请求和分支拆分错误。

## 第九课：哪些参数应该进入缓存键，哪些不应该机械加入

设计缓存身份时，两个相反错误都很常见。遗漏真正影响状态的条件，会错误复用；把所有请求字段都放进键，又会让本来可复用的状态失去命中机会。正确方法是问：这个字段会不会改变被缓存的那段计算结果，或者改变它允许被谁读取、以何种布局解释？

### 9.1 temperature、seed 与已经确定的 prompt

在标准生成路径中，temperature 和 seed 作用于从 logits 选择输出 token 的过程，不改变固定 prompt 的前向 K/V。两个请求拥有相同模型和相同 prompt，但采样配置不同，通常仍可以共享 prompt 状态，再各自进行采样。

这里的限定是“被缓存的是已确定 prompt 的状态”。如果比较已经生成的后缀，不同 seed 可能产生不同 token，后续 K/V 自然不同。真正进入状态计算的是最终已知 token 序列，不能因为最初用户问题一样就共享全部生成历史。

因此不要把“请求参数不同”一概等同于“任何缓存都不兼容”，也不要把“temperature 不影响 prompt K/V”误推为“整个响应可以相同”。答案缓存与中间状态缓存的区别在这里再次变得具体。

### 9.2 max_new_tokens 与缓存收益

输出上限通常控制何时停止，并不改变固定 prompt 的前向状态。一个最多输出十项、另一个最多输出一百项的请求，可以具有相同 prompt 前缀。然而它们的未来资源需求和调度时间不同，接纳策略仍可能区别对待。

这说明缓存身份和 admission policy 应当分开。缓存回答“已有状态能否复用”，接纳回答“当前资源是否允许继续服务这个请求”。命中很长前缀可能减少 prefill 工作，但后续长输出仍会增长缓存，不能因为命中就绕过容量约束。

### 9.3 只看模型名字为什么不够

一个模型服务可能在不改公开名字的情况下替换权重、更新 adapter 或改变位置配置。若 namespace 只用可变别名，缓存身份会随时间失去确定含义。更清楚的设计是从经过验证的模型 revision、adapter revision 和相关执行配置产生稳定版本身份。

“稳定版本”不一定要求把所有权重内容每次都重新哈希一遍；实际系统可以在部署时记录不可变版本或可信摘要。关键是修改模型语义时必须切换身份，而不是靠运维人员记住手动清缓存。

切换 namespace 也不等于旧页立刻释放。旧请求可能仍在使用旧版本，旧缓存条目也可能继续占用空间。若支持平滑升级，需要定义旧版本的排空、淘汰和资源回收策略，不能把模型热更新当成单个字符串替换。

### 9.4 执行后端与数值兼容

两个 backend 理论上实现相同注意力，并不自动意味着它们的缓存物理布局相同。即使布局相同，数值 dtype、缩放格式或量化元数据也可能不同。复用必须同时满足语义与表示兼容，或者显式执行经过验证的转换。

转换也有成本和误差。把 BF16 缓存转成某种低精度表示后再供另一个 backend 使用，需要记录 scale、舍入规则和误差边界。不能把“张量形状一致”当作足够证明，因为相同形状的字节可以有不同编码意义。

本课程 namespace 是一个简化责任接口。它让你看到应该隔离的维度，却没有自动推导兼容关系。进入真实框架后，应查明配置如何影响 cache group、block layout 和 backend 选择，而不是仅复制示例 namespace 字符串。

## 第十课：命中指标怎样统计才不误导

### 10.1 请求命中率与 token 命中率

请求命中率可以定义为至少命中一个位置的请求数除以总请求数；token 命中率可以定义为命中的 prompt token 数除以总 prompt token 数。二者回答不同问题。

假设十个请求中九个短请求各命中一项，一个长请求有一千项却完全未命中。请求命中率很高，按 token 计算的复用比例却很低。反过来，只有一个超长请求命中大量位置，也可能显著减少总 prefill 工作，但请求命中率看起来很低。

你应在报告中写出分子和分母，而不是只给一个“缓存命中率百分之九十”。还要说明是否包含短到不足一页的请求、失败请求和重复恢复时的命中。统计口径一变，数字就不再直接可比。

### 10.2 命中 token 不等于避免了相同成本

不同位置的计算成本可能不同，模型结构也不同。一个长历史后的 token 与一个短 prompt 开头的 token，在注意力读历史方面可能有不同开销。单纯命中 token 数是一个容易理解的代理量，不是精确节省时间。

另外，缓存查找、页表附加、元数据搬运和布局准备也有成本。小请求命中很短前缀时，收益可能被管理开销抵消。真实优化应同时观察查找耗时、剩余 prefill、排队与总体延迟，不要把缓存指标与用户体验割裂。

### 10.3 冷启动、热运行与缓存污染

第一次请求通常没有此前同类状态，称为冷路径；重复请求可以观察热路径。但如果热实验之前夹杂大量无关前缀，LRU 可能淘汰目标条目。实验必须记录缓存初始状态与请求顺序，否则重复运行结果不同也许只是缓存内容不同。

为了隔离某个机制，可以先 clear 缓存再运行冷请求，然后立即运行指定热请求。这个受控实验能验证命中语义，但它不代表真实混合负载中的长期收益。第二阶段需要加入不同长度、不同 namespace 和不同复用频率的请求，观察缓存是否被低价值条目占满。

缓存污染不是指数据错误，而是资源被不太可能再次使用的条目占据，挤走更有价值的状态。一个大批量一次性文档任务可能冲掉交互服务常用前缀。是否采用分区、配额或不同淘汰策略，要根据明确工作负载证据决定。

### 10.4 先核对正确性，再讨论收益

比较冷与热结果时，首先确认相同 token 条件下输出语义一致。教学 Bigram 和独立数值参考适合建立这项基线。随后检查命中长度、页面引用、有效长度与剩余工作是否吻合，最后才比较时间。

若热路径更快但输出不同，不能简单把差异解释为“缓存优化的正常随机性”。先固定采样、检查输入身份，再定位 cached 与 uncached 数值何处不同。若真实浮点路径确实不同，也需要量化误差与任务影响，而不是用一句“浮点不确定”停止调查。

## 第十一课：缓存的并发与失效问题

### 11.1 查到条目后，它会不会被淘汰

在单线程课程中，attach 查找、取页、retain 与更新 LRU 按顺序完成。若另一个线程可以在中间淘汰条目，就可能出现“查到页号，但增加引用前页面已经回收”的竞态。

正确并发协议需要让查找与获得拥有关系形成受保护的交接。例如在合适的锁范围内完成，或使用能验证 generation 的原子获取协议。锁的范围与性能需要权衡，但不能只给字典本身加一个线程安全包装，就认为跨字典与页池的多步关系也自动安全。

这个问题可以用确定性交错测试模拟，而不依赖随机 sleep：在查询到候选后插入一个钩子，让另一个操作淘汰并复用页，然后继续 attach。测试应要求系统拒绝过期候选或正确保留原状态，而不是读取被复用的新内容。

### 11.2 发布中的页面何时不可变

如果 publish 保存一个条目后，原请求还可以在同一物理页上继续原地写入，缓存键与载荷就可能不一致。只发布完整页减少了这种风险，因为顺序 append 不会再修改已满的旧页；但代码中其他旁路写入仍可能破坏它。

因此“完整页发布”与“旧页只读约定”需要共同成立。若未来加入原地压缩、KV 量化重编码或缓存布局转换，就要明确它是否保持所有拥有者可见语义，是否需要新版本或复制，以及转换完成前谁可以读取。

### 11.3 失效不是简单删除一个字典键

缓存条目失效意味着不再向新请求提供复用。已经附加该状态的活动请求可能仍有合法引用，需要按自己的生命周期继续或被明确终止。删除缓存键通常只释放缓存那一份拥有，不应突然使活动请求悬空。

模型升级、adapter 更新或租户策略变化时，服务应区分“禁止未来命中”与“撤销已有运行”。两者的业务和资源后果不同。一个支持平滑模型升级的系统可能允许旧请求完成，但新请求只使用新 namespace；一个要求立即撤销某类状态的系统则需要额外取消与清理协议。

本章没有把这些生产协议全部实现进十几行 PrefixCache。它把必要责任展开，是为了让你在修改真实框架时能够提出准确问题，而不是把一个字典删除操作误当作完整生命周期管理。

## 第十二课：十五道练习与完整参考解答

### 练习一：相同后缀能否复用

请求 A 为 `[1,2,8,9]`，B 为 `[3,4,8,9]`，模型相同。能否仅凭后两项相同复用它们的 K/V？不能。它们的上游 hidden state 依赖不同前文；正确缓存身份必须表达前缀上下文，而不只是局部 token 块。

请再构造一个第一块不同、第二块完全相同的例子，并解释只哈希第二块为何会产生必然的语义混淆。答案不应讨论随机哈希碰撞，因为这里根本没有把必要输入放进身份。

### 练习二：发布长度

块大小四，池中已有十一个 token，max_tokens 为九。发布长度是多少？答案八。先取较小值九，再向下对齐完整页得到八。若 max_tokens 为三，结果零；若 max_tokens 为十二，池中只有十一项，对齐后仍是八。

### 练习三：为什么整页 prompt 仍要重算

块大小二，缓存含四项完整 prompt，新请求 prompt 也长四。attach 最大命中多少？答案二，因为课程保留至少一个 prompt token 重新计算，而完整页粒度把可复用长度向下对齐。若 prompt 长五且前四项命中，则可以命中四。

这个答案应同时说明实现限制与可能扩展：缓存最后 hidden state 或 logits 可以设计另一协议，但不能在现有仅有页引用的接口中悄悄跳过首 token 产生所需的计算。

### 练习四：namespace 隔离

先以 namespace A 发布前缀，再用相同 token、namespace B 查询。应返回零，且新请求页表仍为空，原缓存引用不变。参考测试必须检查这三项，而不是只看返回值；错误实现可能返回零却已经错误增加引用。

```python
from labs.serving.kv import PagePool, PrefixCache

p = PagePool(4, 2)
c = PrefixCache(p)
p.create("old")
p.append("old", [1, 2, 3])
c.publish("old", "A", 3)
p.release("old")
before = [page.refs for page in p.pages]
p.create("new")
assert c.attach("new", "B", (1, 2, 9)) == 0
assert p.tables["new"] == []
assert [page.refs for page in p.pages] == before
p.check(c.refs())
```

### 练习五：重复 publish

同一请求同一允许范围发布三次，entries 应只有一项，缓存页 refs 不应每次增加。参考答案：第一次新增条目并 retain，后两次只 move_to_end。用循环保存每次 refs 快照，若持续增长，就是幂等资源管理错误。

### 练习六：部分匹配

块大小二，缓存键为一二三四五六，新 prompt 为一二三九十十一十二。答案命中两项。六项比较失败，四项比较失败，两项成功。第三项相同不足以构成完整页复用，不能返回三。

### 练习七：短于缓存的请求

缓存有八项，新请求只有五项且前五项相同，块大小二。答案最多命中四项。不能把缓存完整八项附加给新请求，也不能让 computed 超过其已知上下文。测试应比较附加后的页表长度与返回命中数，而不仅检查最长键存在。

### 练习八：淘汰不释放页

一个活动请求与两个缓存条目共享一页。先后淘汰两个条目，free_pages 都不增加；活动请求释放后才增加一。参考答案必须列 refs 三、二、一、零的变化。若报告把两次淘汰写成释放两页，统计口径错误。

### 练习九：引用账必须加入缓存

创建并发布前缀，释放原请求后调用 `p.check(c.refs())` 应通过。若调用 `p.check()`，可能因为没有把合法缓存拥有计入而失败。解释这不是应该删除 check，而是组合系统后需要传入完整拥有者账本。

### 练习十：相同内容的不同物理副本

两个请求分别独立计算相同前缀，使用不同物理页。第一个已经 publish；第二个再 publish 同一键时，课程实现不替换旧条目。第二请求结束后，它独占的副本可释放，缓存继续拥有旧页。这个策略避免为同一键保留重复载荷，但也不自动合并活动请求的全部页表。

### 练习十一：温度不同是否必须 miss

相同模型、相同固定 prompt，不同 temperature。参考答案：如果缓存的是普通 prompt K/V，温度通常只影响后续采样，不必仅因此隔离缓存；但具体系统仍可能出于接口或实现约束使用更保守身份。你必须说明缓存对象是什么，不能对任何名为 cache 的机制给同一个答案。

### 练习十二：键存在但页面已复用

故意删掉 publish 中 retain，再释放原请求，让新请求复用物理页。旧 entries 仍指向同一页号，却不再拥有原状态。参考测试应先证明 pool.check 的拥有账失败，再用载荷变化展示为什么“字典里查得到”不足以保证命中正确。

这类故障只能在练习副本中注入，保留基准实现。不要为了演示而修改正式课程代码后忘记恢复。

### 练习十三：请求率与 token 率

十个请求中九个各长两项且命中一项，一个长一千项完全未命中。请求命中率为九成，token 命中率为九除以一千零一十八，约不到百分之一。参考答案要写分母来自全部 prompt token 数，而不是只统计已命中请求的长度。

### 练习十四：实现一个慢匹配 oracle

输入若干 namespace 与 token 元组，不涉及物理页；输出最长可复用完整页长度。完整参考如下。它刻意简单，用来对照更复杂索引，而不是追求性能。

```python
def longest_prefix(entries, namespace, prompt, block_size):
    if type(block_size) is not int or block_size < 1:
        raise ValueError("block size must be positive")
    limit = (len(prompt) - 1) // block_size * block_size
    best = 0
    for entry_namespace, prefix in entries:
        if entry_namespace != namespace:
            continue
        n = min(len(prefix), limit)
        n = n // block_size * block_size
        while n > best:
            if tuple(prompt[:n]) == tuple(prefix[:n]):
                best = n
                break
            n -= block_size
    return best

assert longest_prefix([("m", (1, 2, 3, 4, 5, 6))],
                      "m", (1, 2, 3, 9, 10), 2) == 2
```

本函数还假定 prompt 非空、prefix 表示完整合法前缀。把它作为公共 API 时应补齐这些合同。用于课程合法夹具时，它能独立核对匹配长度，但不能验证页引用，后者仍需 pool 级检查。

### 练习十五：设计一次模型升级

旧模型 namespace 为 v1，新模型为 v2。已有 v1 请求仍运行，新请求必须使用 v2。参考方案是部署身份绑定到请求创建时的可信配置，禁止新请求使用 v1 缓存；旧条目按策略淘汰，但活动 v1 引用保持到完成。若资源不足以同时保留两版，则需要明确排空或停机升级流程，不能把两版 K/V 混用来省空间。

## 第十三课：三个故障工作坊

### 13.1 中间块相同导致错误命中

建立两条第一块不同、第二块相同的 token 序列。先用完整前缀 oracle 得到零共同首块；再实现一个错误的“仅按当前块 token 查找”索引，观察它把第二块当成可共享。

这个工作坊的结果不是随机概率事件，而是缺失上下文身份导致的确定性错误。修复后，当前块身份应携带前缀链或等价信息。验收不仅比较命中长度，还要用真实数值后端证明错误复用会改变后续输出；纯 ID 载荷只能揭示身份映射问题。

### 13.2 LRU 操作顺序写反

缓存最多两项，依次发布 A、B，再访问 A，然后发布 C。正确按访问更新的 LRU 应淘汰 B；若 attach 忘记 move_to_end，可能淘汰 A。把每次 entries 的顺序记录下来，比只观察最终命中率更容易定位。

这个实验还要处理活动引用：淘汰 B 不一定释放它的页。你应把“索引顺序是否正确”和“页资源是否回收”分别列成两张观察表，避免一个错误掩盖另一个。

### 13.3 完整命中后没有首 token

错误实现允许 attach 返回全部 prompt 长度，却没有缓存末位置 logits，也没有安排任何新工作。此时 gap 为零，调度器不能形成 Work，首 token 可能永远不产生。

最小反例是一个 prompt 恰好整页、缓存完全存在、输出上限为一的请求。修复可以遵循课程的至少重算末位置规则，也可以明确增加 logits/hidden-state 缓存协议。两种方案不能混写：只改 computed 而不补输出路径，是状态计数与计算责任脱节。

## 第十四课：完成一份可复核的缓存工程报告

先建立一组小型 workload，包含完全相同提示、共同 system 前缀但不同问题、第一项就不同、不同 namespace、长度不足一页、恰好整页、短于已有前缀和长于已有前缀。每种至少有一个固定样例，记录预期命中长度。

然后执行冷路径，保存页表、refs、entries 和输出。不要只保留 report 中一个 cache_hit_tokens，因为它无法解释页面如何共享。热路径执行后，逐项核对复用页的身份、引用增加、剩余工作和最终输出。

第三阶段限制 max_entries，加入淘汰。报告每次淘汰的条目、它包含的页、哪些页仍被活动请求或其他条目拥有、free 实际增加多少。这个阶段能让你真正理解“删除索引记录”与“释放物理存储”之间的关系。

第四阶段换一个匹配索引，例如简单 trie，但保留慢 oracle 和同一工作集。比较的是语义结果与拥有关系，不应要求内部节点编号完全一样。若优化实现有意选择另一份等价物理副本，报告应说明其合法性依据。

第五阶段才讨论性能。CPU 参考可以记录查找比较次数或运行时间，但不要把它直接外推到 GPU 服务。真实框架实验需要固定模型、权重、模板、token 输入、缓存初始状态、请求顺序与硬件环境，分别报告冷／热路径和混合负载。

最后写清限制：课程采用完整页、从开头开始的普通前缀、显式 namespace、同步页池、按条目 LRU，没有实现完整生产认证、并发缓存交接或跨设备布局转换。限制说明不是让你停止实现，而是让每个升级任务有清楚合同：你知道要新增哪项状态、哪条不变量和哪个失败测试。

## 第十五课：把缓存思想用于真实 Agent 提示组织

Agent 会反复发送系统规则、工具定义、历史消息、检索证据和新的工具观察。你现在可以判断哪些部分可能形成稳定前缀，也能解释为什么一个看起来只增加了短观察的任务，每轮仍可能发生大量重复 prefill。

### 15.1 前缀中的一个变化会影响后面的身份

设输入由三段组成：固定规则五十项、固定工具说明二十项、变化问题十项。如果前七十项每次都相同，可以形成较长共同前缀。若你把每次变化的时间戳放在第一项，后面规则虽然文字一样，整个序列的共同前缀可能从开头就中断。

这不是说永远不能在开头放时间，而是提示组织与复用机会存在具体关系。若业务语义允许，可以把稳定信息保持稳定，把确实需要变化的信息放在适当位置。但不能为了提高命中率随意移动 system、user 或 tool 的角色边界，也不能删去影响任务正确性的当前信息。

一个优化建议必须先保证模型输入语义不被破坏，再讨论缓存收益。把重要约束移到模型可能忽略的位置，只因为缓存数字变好，不是可靠的系统改进。

### 15.2 工具定义的稳定序列化

同一组工具，如果每次以不同顺序序列化，可能产生不同 token 前缀。JSON 对象在业务上可能被认为字段顺序无关，但模型实际看到的是模板编码后的序列；空格、字段排序和描述变更都可能影响 token。

可以建立稳定的序列化流程，减少无意义变化。但“稳定”不意味着把不同工具版本强行当成同一份内容。如果参数 schema 或描述实际改变，模型需要看到新的定义，缓存身份也应随真实 token 改变。

你可以做一个不调用 API 的练习：构造相同工具列表的两种顺序，使用同一个已选 tokenizer 编码，比较最长共同 token 前缀。若本地没有该 tokenizer，先用课程整数序列模拟顺序变化；不要把字节比较结果冒称为真实模型 token 命中率。

### 15.3 检索证据与记忆更新

检索结果每轮可能变化，记忆也可能新增或修正。若把一份可变记忆插在长稳定规则之前，后续共同前缀机会会受到影响。另一方面，记忆位置会影响模型上下文结构与优先级，不能只按缓存效率排序。

合理做法是把提示组织作为一个同时包含正确性、可维护性和效率的设计问题。明确哪些段落是版本化规则，哪些是本轮事实，哪些是用户输入；用固定夹具测试语义，再用真实 token 序列测缓存变化。不要用同一个“优化提示”标签掩盖三个不同目标。

记忆被撤销后，不能继续在新请求的输入中发送旧事实。前缀缓存若仍保存旧 token 状态，并不会自动让新请求使用它；只要新 token 序列不同且身份检查正确，就不会错误命中到不同内容。但若上层错误地复用了旧 prompt token，缓存会忠实加速那个错误输入。因此失效责任不能全部推给 KV 管理器。

### 15.4 内容修改后的可复用边界

假设原序列有十二项，块大小四，修改第九项。前八项仍相同，原则上可以继续复用前两块；从包含第九项的块开始不能复用旧状态。若修改第三项，则第一块已经不同，后面即使局部 token 仍一样，也不能按旧前缀链直接共享。

这使“修改了一个文件就必须清空整个服务缓存”与“只改一个 token 所以只重算一个位置”两种极端说法都不准确。实际可复用边界由完整前缀一致性和块粒度决定。实现可以选择更保守的失效，但要清楚它牺牲了哪些机会。

在一个 Agent 反复阅读相同代码库的场景中，输入组织、文件排序和版本标识共同影响前缀稳定性。你应先保存实际请求序列，再分析变化位置，而不是仅根据“这轮只改了一个文件”推测命中情况。

### 15.5 一个可交付的提示与缓存实验

准备三个语义明确的提示构造器：第一种稳定规则在前、变化任务在后；第二种在最前面插入每轮变化的实验编号；第三种保持内容但打乱工具定义顺序。先在 CPU 上产生 token 序列或明确标记的整数模拟序列，计算各轮共同完整页前缀。

随后在允许的真实 API 或本地服务上，按其实际可观察缓存统计验证。外部 API 是否公开命中 token、是否支持某种缓存策略，必须以该服务当前文档和响应为准；不能把本课程 PrefixCache 的行为直接套给任意厂商。

报告需要把三层证据分开：构造器输出是否语义正确；实际 token 前缀是否稳定；服务是否真的复用并产生收益。只有第一层文本看起来相似，不能推出后两层；只有命中率提高，也不能推出答案质量不受影响。

最后把一次故意错误加入验收：模型版本更换但沿用旧 namespace，或者工具定义改变却继续发送旧序列。说明哪一层应该检测它，以及缺少检测会导致什么结果。这个任务把 Agent 上层上下文管理与推理层缓存连接起来，使你能从请求构造一路追到页面复用，而不是分别记住两个互不相干的名词。

补充一个 Python 层面的实现细节：键使用整数元组而不是可变列表，也是在保护缓存身份的稳定性。列表不能直接作为普通字典键，且它的内容可以在插入后被原地改变；整数元组则能够表达一份固定序列快照。构造元组不代表复制了全部模型数值，它只保存身份所需的 token 序列。值中的页号元组也只是稳定的引用清单，真正载荷仍由页池拥有。读代码时要分别追踪这两类元组：键回答“这是什么状态”，值回答“状态存在哪里”；二者都不可随意修改，但它们并不自动证明底层数据也不可变。只有发布、引用和写入协议共同成立，缓存身份才能始终对应正确载荷。
