# S02 调度器：把多个请求变成每一轮可执行的工作

上一章中，一个请求的状态已经足够复杂：prompt、output、computed、页表和终态必须一致。现在把多个请求放在同一个引擎里，问题不再是“每个请求能不能完成”，而是“它们以什么顺序分享有限资源”。本章从一个纸面队列开始，逐步建立批次、token 预算、分块 prefill、连续批处理、公平性、资源可行性和调度计划的概念。

你应当先完成 S01 的单请求手算。这里沿用 `Request`、`Work` 和 `Engine`，不另造一个无法与代码对应的抽象。所有时间公式都是教学模拟；策略优劣首先以状态正确性、可解释等待和明确目标衡量，真实吞吐与延迟留到有实际设备的实验验证。

## 第一课：调度器到底决定什么

### 1.1 从“谁先用机器”开始

假设只有一台打印机，A 要打印一百页，B 要打印一页。若把 A 的全部一百页印完再处理 B，规则容易理解，B 却要等待很久。若每印若干页就允许其他任务插入，B 可以较早结束，但打印机可能增加切换开销。这个例子帮助理解服务顺序的影响，却不能完全代表 LLM：模型每个请求的历史长度、缓存状态、输出依赖和计算形状还会改变工作成本。

在 LLM 引擎里，调度器不直接决定下一 token 是什么；它决定哪些请求本轮推进、每个推进多少个已知位置、哪些新请求接纳、哪些请求等待或抢占。模型 runner 执行安排好的计算，采样器根据分数选择输出。把这三个决定分开，才能单独修改调度策略而不偷偷改变模型定义。

一个调度器可以完全正确，却不适合某种业务。先到先服务能保证有限任务最终完成，却可能让交互请求首 token 很慢；decode 优先可以维持正在输出的体验，却让新请求等很久。因此“正确”与“优化目标好”是两层验收：先证明没有丢 token、越预算、错用缓存，再讨论对哪类用户更有利。

### 1.2 调度对象不是永远固定大小的请求

请求是长期对象，每轮工作可以很小。A 的 prompt 长十万 token，不能因此每次都把十万位置重新列入工作；它可能已经处理九万九千位置，只剩一千待追赶。B 已经输出了一百 token，也不表示本轮必须计算一百个新位置；正常 decode 通常只处理刚确定的那个末尾 token。

所以调度器应该面向“当前缺口”做决定，而不是只看请求总长度。长度信息仍然重要：它影响缓存需求、attention 工作量和可能的未来成本。但它与本轮安排多少位置不是同一个数字。初学者常把 max model length、batch token budget 和输出上限混用，本课会逐项拆开。

### 1.3 目标函数必须先于参数调整

你希望优化什么？单位时间完成的请求数、输出 token 数、首 token 时间、相邻 token 间隔、尾延迟，还是在某个延迟目标内可承受的到达率？不同目标可能互相冲突。一次性把长 prompt 切得很小，可能改善其他请求的等待，却增加它自己的固定开销。

“更快”不是充分的实验问题。应改写成：“在这份固定到达轨迹和输出长度下，把 chunk 从八改为二，短请求的 TTFT 是否降低，长请求 E2E 增加多少，完成输出是否保持一致？”这样才能设计对照组、记录指标并解释取舍。

本课程先固定模型输出行为，再改变调度参数。BigramBackend 使下一 token 的选择可预测；请求各自持有 RNG，随机采样也不会因为别人先抽了一次而消耗自己的随机流。真实 GPU 中还可能存在批次形状相关的数值变化，S12 会进一步区分逻辑独立性与数值确定性。

## 第二课：五种数量和三个不同队列

### 2.1 客户端并发数

客户端并发数通常指某个客户端或压测器尚未完成的请求数量。它可能包括正在建立连接、已经发送但等待服务端接收、在服务端排队、正在运行和正在接收输出的请求。具体统计起点由工具定义，不能只凭参数名猜测。

发送六十四个并发请求，不意味着某一时刻有六十四条序列进入 GPU，也不意味着服务器会一次性 prefill 六十四份 prompt。服务端可以有自己的限流、等待队列和运行上限。理解这一点，才能解释“客户端已经发了很多，GPU 利用率仍然不高”这种现象：瓶颈可能在前处理、排队政策或资源约束，而不一定在模型算子。

### 2.2 活动序列上限

`max_sequences` 限制本教学引擎同时保留多少个 running 请求。它约束的是活跃请求数，不直接限定每个请求长度。本例若上限为二，三个请求都已经到达，也只有两个能够从 waiting 进入 running。

把上限设置为一可以让调试更清楚：当前只有一份活动状态，日志不会交错。但是它不普遍代表“模型能力完整”。模型能否处理所需上下文，还依赖位置编码、模型配置、缓存空间、backend 支持等。运行序列数与每条序列允许的上下文长度是两个轴。

一个请求占用的缓存可能比另一个请求多几个数量级，因此仅限制请求数并不足以保护内存。两条超长请求可以比几十条短请求更难容纳。真实框架必须同时考虑运行名额和缓存资源；S13 会建立每个 rank 的容量账。

### 2.3 每轮 token 预算

`token_budget` 限制本轮实际处理的输入位置总数。若 A 本轮 prefill 三个 token，B decode 一个 token，则本轮已使用四个位置的预算。这里数的是本轮输入位置，不是最终输出数，也不是 prompt 总长。

把预算设为四，不意味着每个请求各得到四个。预算是共享总量：各请求分配数之和不能超过四。一个常见错误是循环中给每个请求独立使用同一个初始 budget，却没有扣减剩余额度，最终实际安排的总数随着请求数增长。

本课程要求 token_budget 是正整数。浮点数一点五不能作为“允许处理一个半 token”的合法预算；布尔值也不应隐式等于一。类型验证属于资源合同的一部分。若上游 JSON 值未经检查就进入切片长度或循环次数，错误往往在更深处才表现出来，诊断代价更高。

### 2.4 prefill chunk 上限

`chunk_size` 是本教学实现对某个处于 prefill 状态的候选请求本轮分配量的上限。它不等于全批 token_budget。假如 budget 为八，chunk 为三，两个长 prompt 可以各得到三，还剩两个位置给第三个请求或 decode。

如果 budget 本身只有二，chunk 设为八并不能让请求一次处理八个；分配仍受总预算限制。如果请求 gap 只有一，chunk 设为三也不能凭空制造两个有效位置。正确 count 需要同时取多个约束的最小值，而不是只看一个参数。

### 2.5 上下文上限与生成上限

上下文上限约束一个请求能包含多少输入与生成历史；生成上限约束本次最多新增多少 token。它们影响请求是否可接收和最终能运行多久，但不是每一轮的调度额度。一个允许生成一千 token 的请求，仍可每轮只推进一个位置。

明确单位后再读真实框架命令行。类似 max-num-seqs、max-num-batched-tokens、max-model-len 的参数名看起来都包含 max，责任却不同。不能把其中一个调大后断言另外两个限制自动消失，也不能仅通过名字推断所有版本的精确行为；最终要落到已固定源码和实际配置。

### 2.6 接收队列、等待队列与活动集合

前端接收队列可以包含尚未完成预处理的网络请求；调度 waiting 队列包含已经准备好、等待接纳的内部请求；running 集合包含已经接纳并持有活动状态的请求。还有些真实系统会有等待远端 KV、等待语法约束或等待多模态编码的队列。

本课程只显式模拟 pending、waiting、running 三类，以便建立清楚的状态关系。你看到 waiting 为空，不等于整个服务没有请求等候；如果观察的是某个特定组件，还应检查它上游是否积压。不同队列中的等待原因不同，不能全部归因于“GPU 太忙”。

## 第三课：静态批次为什么浪费，连续批处理怎样改变成员

### 3.1 一个三请求例子

设模型一次最多并行处理两条序列。A 需要输出两项，B 需要输出六项，C 已经在等待。为了简化，这里暂时忽略 prefill，假定每一轮 decode 各推进一个 token。

静态批次把 A 与 B 组成一个固定批次，等这个批次所有成员结束后才建立下一批。第二轮 A 完成，第三到第六轮它的位置空着；C 直到 B 完成之后才进入。连续批处理则允许在下一轮边界移除 A、加入 C，让 B 和 C 一起继续。

| 轮次 | 静态批次成员 | 连续批处理成员 |
|---|---|---|
| 1 | A、B | A、B |
| 2 | A、B | A、B |
| 3 | B、空位 | B、C |
| 4 | B、空位 | B、C |
| 5 | B、空位 | 取决于 C 是否结束 |
| 6 | B、空位 | 取决于后续等待请求 |

这张表展示的是成员更新的机会，不是性能倍数。实际每轮耗时会受序列长度、模型形状和后端影响；不能因为有两个成员就假设时间完全相同，也不能把空位比例直接当作总系统可提升比例。

### 3.2 长期状态必须从 batch 中抽离

如果所有生成历史都只存放在固定 batch 的第二行，那么当 A 完成、C 插入、B 位置变化时，就容易把历史错配到新的行。连续批处理要求请求拥有稳定身份，而 batch 中的行号只是当前轮的临时布局。

例如第一轮 A 在扁平数组偏移零，B 在偏移三；第二轮 C 插入后，B 可能在偏移零。B 的请求身份没有改变，它的缓存表和 RNG 也不能因为物理位置变化而重置。Runner 需要明确的映射关系，把本轮张量行重新关联到长期请求。

本课程用 Request 保存长期状态，用 Work 保存本轮计划。这是理解真实框架 scheduler output、input batch 和 request state 的入门钥匙。不同项目的类名可以不同，但“请求身份不等于本轮张量行号”的原则仍然重要。

### 3.3 连续不等于可以修改正在执行的 kernel

一个 GPU kernel 启动后，其输入地址、形状和元数据必须符合启动时的合同。不能因为新请求刚到，就从 CPU 任意修改设备正在读取的页表，并期待 kernel 自动理解新的成员。

通常在调度或执行边界建立新批次。有些框架把 CPU 准备下一批与 GPU 执行当前批重叠，这会增加在途状态和依赖管理，而不是消除边界。连续批处理讲的是迭代之间动态改变成员；异步重叠讲的是不同阶段在时间上并行。两者相关，但不是同义词。

学习时先写同步版本是有原因的：你能清楚看到“安排→执行→回写→下一轮”的顺序，再把其中某些阶段重叠，并为每个新重叠关系补充正确性条件。直接从复杂异步循环开始读，容易把所有 pending 字段都误当成同一层排队。

## 第四课：用 known、computed 和 gap 统一思考

### 4.1 已知序列和已完成计算

定义 known 为当前已知上下文长度，即 prompt 长度加 output 长度；computed 表示已推进到的位置数；gap 等于 known 减 computed。prompt 初到时 known 很大而 computed 为零；每产生一个新输出，known 增加一，而 computed 暂时不变。

前缀缓存命中可以让 computed 的初始值大于零。抢占后重新计算可以让 computed 回退，但 known 不必回退，因为用户已经收到的生成历史仍然存在。这个模型让“初始输入”“正常 decode”“缓存命中”“重算历史”都成为追赶已知序列的不同情况。

注意 known 是信息层面的已知，不是已经算过。一个 token 被采样选出来后，我们知道它的 ID，但它在每层网络中的 K/V 可能还未计算。把“知道这个 token 是什么”与“已经建立它的模型状态”分开，才能解释为什么正常生成后 gap 常为一。

### 4.2 分配量的数学合同

设请求 r 的本轮分配量为 n_r。最基本条件是非负整数，且不超过其 gap。把所有候选请求的 n_r 相加，必须不超过本轮 token_budget。处于 prefill 的请求还受 chunk 上限；此外，安排这些位置所需页面必须可获得。

这些约束只定义“可行”，不定义“最好”。很多不同计划都满足约束。例如 gaps 为五、五，总预算四，可以分四和零，也可以分二和二。前者偏向一个请求较快追上，后者偏向均衡推进。策略是在可行集合中选择计划，而不是跳过可行性检查。

如果某个请求本轮得到零，不能仅凭这个事实说它被永久饥饿。需要观察长期服务机会；但如果一个请求无限期得不到正分配，即使其他请求不断完成，也说明策略可能没有满足你需要的活性要求。

### 4.3 phase 标签并非万能事实

本教学实现用 computed 是否小于原 prompt 长度判定 phase。抢占之后，computed 可能回到零，系统重新处理 prompt，再追赶已生成历史。因此同一个请求会重新经历被标为 prefill 的工作，即使用户之前已经看到过输出。

当某个 chunk 跨过 prompt 末尾，当前实现按该 chunk 起点的 phase 计模拟费用，不在边界强制拆成两份 Work。这是透明的教学选择，不是所有生产调度器的统一语义。阅读结果时应看实际 token 位置与 start/count，而不只看 phase 字符串。

真实框架还可能把 speculative token、结构化输出等待或多模态预算纳入更一般的计数。你应先找到它具体维护了哪些“已知”“已安排”“已完成”“已输出”数量，再建立对应关系，不能只搜索一个叫 prefill 的变量就结束分析。

## 第五课：逐行读本课程的计划构建

核心循环可以压缩成下面这段摘录。它仍然引用实际 Engine 的字段，而不是另造一份含糊伪代码：

```python
budget = self.token_budget
plan = []
for rid in self._order():
    if budget == 0:
        break
    r = self.requests[rid]
    context = r.context
    gap = len(context) - r.computed
    phase = "prefill" if r.computed < len(r.prompt) else "decode"
    count = min(gap, budget, self.chunk_size if phase == "prefill" else 1)
    if count <= 0:
        continue
    while self.pool.needed(rid, count) > len(self.pool.free) and self.cache.evict_one():
        self.event("cache_evicted")
    if self.pool.needed(rid, count) > len(self.pool.free):
        self.event("allocation_blocked", rid=rid)
        continue
    values = context[r.computed:r.computed + count]
    start = r.computed
    self.pool.append(rid, values)
    r.computed += count
    plan.append(Work(rid, start, tuple(values), phase))
    budget -= count
```

### 5.1 budget 是局部剩余额度

第一行从配置复制本轮总额度。每轮都重新开始，不能把上一轮剩余预算永久带到下一轮，否则下一轮的上限会莫名其妙缩小。反过来，也不能在遍历每个请求时重置 budget，那会让每个请求都获得一整份全局额度。

`plan=[]` 创建本轮的新列表。它不是长期保存所有历史工作的大容器；历史观察通过 events 记录。把计划与历史分开，能避免 runner 无意中重复执行过去轮次的 Work。

### 5.2 _order 只决定候选顺序

`_order` 返回当前 running 身份的一个顺序。它不直接分配页面，也不更新 output。这个职责分离让你可以研究 FIFO、decode-first、round-robin 等顺序策略，同时保留同一套预算和资源检查。

若你在 _order 内部又偷偷改变 computed，排序就不再是无副作用的候选选择。这样会让调用两次 _order 产生不同运行进度，测试和日志都更难解释。因此策略函数最好把“排序或选择”与“提交状态变化”分开。

### 5.3 gap 与 count 的检查保护什么

context 是这一刻的已知序列副本，gap 计算尚未处理的位置数。count 同时受到缺口、剩余预算和阶段上限约束。`count<=0` 时跳过，是为了避免形成零长度 Work 或对无进展请求消耗资源。

但这个防护不意味着可以容忍任意负 gap。负 gap 通常说明 computed 已超过 known，是更早的状态错误。当前 check 会检查运行请求的 computed 范围；在更复杂实现中，你可能希望更早地断言，避免错误被一个 continue 暂时隐藏。

### 5.4 资源不足为何先尝试淘汰缓存

前缀缓存持有的是可复用状态，它占用页面但不一定属于活动请求唯一需要的历史。当自由页不够时，可以先释放部分缓存引用，为当前计算腾出空间。淘汰操作如果没有真正释放页面，循环仍可能继续淘汰其他条目，直到可行或没有可淘汰项。

这里不能把所有缓存页都无条件清空，因为有的物理页还被活动请求引用。正确淘汰只释放缓存自己的那份引用；页是否回到 free，取决于总引用计数是否降到零。S03、S04 会用具体页面编号推导这件事。

### 5.5 为什么扣预算必须在成功安排之后

如果在页分配失败前就扣掉预算，该请求没有形成 Work，却占用了本轮额度。后面一个只需一页、原本可运行的请求可能因为预算被浪费而不能执行。这样系统看起来“没有足够预算”，实际却是失败路径错误地消费了预算。

正确顺序是：检查可行性，成功追加资源与元数据，更新 computed，记录 Work，扣减预算。这个顺序仍然需要 append 的失败原子性作为基础。如果 append 写了一半后才失败，调度器不能仅靠把 budget 加回来恢复一致性。

### 5.6 Work 保存 start 的时机

start 在 computed 增加前保存。假如旧 computed 为四、count 为二，本轮工作应从位置四开始，覆盖四和五；更新后 computed 为六。如果更新后才写 start，就会错误记录从六开始，runner 可能使用错误位置编码或读错输入片段。

这类错误往往不会改变 token 数，所以只断言本轮 count 总和合法不够。需要验证每个 Work 的 start 和 token_ids 确实等于对应请求旧上下文的那段切片。状态工作坊将提供逐轮快照，帮助你建立这种更细的测试。

## 第六课：完整手算一个混合批次

先不考虑页不足，关闭前缀缓存。A 的 prompt 长七，B 长二，C 长一；三个请求都已经 running，output 初始为空，computed 都为零。总预算五，chunk 为三，候选顺序固定 A、B、C。

第一轮 A 的 gap 为七，count 为三，剩余预算二；B 的 gap 为二，count 为二，剩余预算零；C 没有工作。A 处理了 prompt 的前三项但没有输出；B 处理完全部 prompt，产生第一个输出。此时 A 的 known/computed 为七/三，B 为三/二，C 为一/零。

第二轮如果仍用 FIFO，A 得到三，剩余二；B 已经进入 decode，只需处理一个末尾 token，剩余一；C 得到一并产生第一个输出。此时 A 仍未处理最后一个 prompt token。这个例子说明 chunk 限制可以给后续请求留机会，但并不保证每个请求每轮都得到相同数量。

第三轮 A 只剩一个 prompt 位置，处理后产生第一个输出；B 和 C 若尚未结束，各得到一个 decode 位置。预算未必用满。剩余预算并不总表示实现低效：当前可行工作可能不足，或者某些请求已经结束。不能为了“填满 batch”把尚未知的未来 token 当成输入。

| 轮次 | A安排 | B安排 | C安排 | 使用总预算 |
|---|---:|---:|---:|---:|
| 1 | 3 | 2 | 0 | 5 |
| 2 | 3 | 1 | 1 | 5 |
| 3 | 1 | 至多1 | 至多1 | 至多3 |

现在改变策略为 round-robin。第一轮起点 A；第二轮起点 B；第三轮起点 C。你必须重新计算每一轮的剩余预算，不能只把上表三列顺序交换，因为前一轮分配会改变下一轮 gap 和 phase。

这一练习的核心不是某个最终数字，而是状态依赖：调度策略改变历史，历史改变候选缺口，候选缺口再影响下一轮计划。一个只对静态 gap 列表排序的函数，还没有模拟完整的生成系统。

## 第七课：分块 prefill 的收益和代价

### 7.1 长 prompt 怎样挡住已开始输出的请求

假设 A 正在 decode，需要本轮一个位置；B 刚进入，prompt 有十六个位置。如果本轮总预算十六，并且 B 排在前面、chunk 不限制，它可以消耗全部预算，A 本轮无法输出下一 token。用户看到的现象是答案已经开始，却中途停顿。

把 B 的 chunk 限为四，可以把剩余预算留给 A 以及其他请求。这不是改变 B 的数学定义，而是把已知输入分多轮处理。只要每块之间状态正确衔接，最终数值语义可以保持；实际浮点执行路径是否完全一致则是另一层验证。

分块的一个代价是增加轮次数。若每轮有固定调度、启动或同步成本，B 本来一轮能完成的工作可能变成四轮。另一个代价是某些矩阵形状变小后效率变化。所以不能仅凭“更公平”就断言任意小 chunk 都最好。

### 7.2 一个透明的代价模型

本课程每轮模拟时间为固定一毫秒，加每个 prefill 位置零点二五毫秒，加每个 decode 位置零点一毫秒。这个公式不是 H100 的拟合结果，只是让你能在纸上看见固定开销与工作量的区别。

单个十二位置 prompt，若 chunk 十二且预算足够，一轮模拟成本四毫秒；若 chunk 三，需要四轮，固定开销变为四毫秒，位置成本仍是三毫秒，总计七毫秒。纯看这个单请求，它的 prefill 完成时间变差了。

但如果一个短请求在中间到达，四轮方案提供更多重新接纳和选择的机会。系统级收益来自对多个请求的等待结构改变，而不是凭空减少了这十二个位置的数学工作。你应同时报告长请求与短请求的指标，避免只挑受益的一方。

### 7.3 chunk 不能代替内存管理

把长 prompt 切成很多块，可以减少某次执行的临时工作量，但已经建立的历史 KV 通常仍要保留。若最终上下文长度太大，缓存总量仍然可能超过预算。chunked prefill 不是让任意长上下文自动装进任意小显存的技巧。

反过来，页池足够容纳完整上下文，也不意味着一次巨大的 prefill 张量不会触发临时工作区峰值。长期缓存与瞬时执行空间不同，所以容量模型要分别记账。S13 会把权重、KV、激活、工作区和 graph 内存分开计算。

### 7.4 调度边界与到达时间

本教学模拟器在 step 开始处理新到达请求。若 B 在一次较长 batch 执行中到达，它要等下一次 ingest 才进入 waiting。这对应一种迭代边界接收的简化模型。生产系统的网络前端可以更早接收，但新请求真正进入设备工作仍受调度边界制约。

因此更大的批次可能减少启动次数，同时延长新请求等待下一次决策的时间。这个权衡不能仅从单轮 token 数推导，需要结合批次实际耗时和到达过程。开放到达负载与固定客户端并发负载也会给出不同现象，S08 会展开。

## 第八课：三种基础策略与可构造的反例

### 8.1 FIFO 的优点和弱点

FIFO 按当前 running 列表顺序分配。它简单、可预测、容易定位问题。对有限固定工作集，先到的请求常能较早完成；当预算小于前面请求的持续需求时，后面的请求却可能等待很久。

设总预算一，A 与 B 都已运行，各需要输出十项。FIFO 每轮先考虑 A，A 的正常 decode 每次都消耗唯一额度。B 虽然已经拥有 running 名额，却可能直到 A 结束才得到第一次工作。这里“已接纳”不代表“得到公平服务”。

在有限十项输出例子中，这属于长时间等待，不是严格无限饥饿。若系统允许前方工作持续增长，或新高优先级工作不断插入，才可能形成更强的饥饿现象。讨论公平性时区分有限最坏等待与无限不服务，有助于把直觉变成可测试命题。

### 8.2 Decode-first 的目标

decode-first 优先 computed 已达到 prompt 长度的请求，倾向保护已经开始输出的交互体验。本课程通过排序键实现：尚未完成 prompt 的请求排到后面。它没有改变总预算，也没有让 decode 免费。

一个反例是大量长输出请求持续占据活跃集合，新长 prompt 总被推迟。已有用户可能觉得输出很流畅，新用户却长期看不到首 token。这并不一定说明策略错误，而是说明它优化了不同指标；是否可接受取决于业务目标和额外公平机制。

生产设计常需要给新请求或 prefill 预留机会，而不是绝对地让 decode 永远压过一切。可以采用配额、年龄提升或显式延迟目标，但每种机制都要重新检查总预算和资源可行性。

### 8.3 Round-robin 的具体含义

本课程 round-robin 旋转候选起点。若 running 为 A、B、C，第一轮从 A 开始，第二轮从 B 开始，第三轮从 C 开始。它并不是把每轮预算平均除以三；每个候选仍按 gap、chunk 和剩余预算分配。

这种策略能减轻总是排在后面的请求长期没有机会的问题，但不等于按计算时间公平。一个长上下文 decode 的 attention 读历史成本可能高于短上下文 decode；同样分配一个 token 不代表得到相同设备时间。

请求完成或新请求加入时，列表长度改变，cursor 通过取模决定起点。测试不能只覆盖固定三成员不变的场景，还要加入成员退出和插入。否则你可能在理想排列下得到轮转，实际动态负载中却总跳过某个请求。

### 8.4 按请求公平、按租户公平与按成本公平

一个租户提交一千条短请求，另一个租户只提交一条长请求。逐请求轮转会给前者更多总体份额，尽管每条请求看似公平。若业务希望租户之间共享资源，就需要先在租户层分配，再在租户内部安排请求。

按 token 公平也可能与按时间公平不同。长上下文、不同模型、不同 adapter、不同多模态输入的单位 token 成本可能不同。建立成本估计后可以使用虚拟服务时间等办法，但估计误差也会影响公平性。

入门时不要急着实现复杂算法。先明确自己的公平单位，写出一个能打破现有策略的负载，再加入最小改进，并保留反例测试。这样你得到的是可解释的设计演进，而不是一组名词和无法验证的“智能调度”。

## 第九课：资源不足时怎样保证系统仍然前进

### 9.1 有预算不等于有可行工作

某轮 token_budget 还有四，但所有候选都需要新增页面，而 free_pages 为零。调度器不能因为 token 预算允许就越过内存限制；也不能建立指向不存在页面的 Work。多资源约束下，可行工作集合可能为空。

先尝试淘汰无必要缓存，是一种优先保持活动请求的选择。如果仍无法推进，当前实现会考虑抢占一个较年轻的活动请求，释放其活动页引用，让较老请求继续。抢占保留输出历史与 RNG，但 computed 回退以便以后重算。

这不是唯一策略。其他系统可能换出 KV、选择不同牺牲者、拒绝新请求或使用更复杂预留。评价策略时既要看短期释放了多少，也要看后续重算成本和用户等待，不能把“成功释放一页”当作完整优化目标。

### 9.2 为什么不能马上重新接纳刚抢占的请求

如果释放 B 后立即按原并发上限重新接纳 B，它又可能占回刚腾出的资源，系统回到同一状态。这样的循环会不断“抢占→接纳→再次无进展”，日志很多，实际工作没有增加。

本实现暂时降低递归重试中的 max_sequences，使本轮在较少活动请求下重新尝试；finally 再恢复原配置。这个局部控制保护了一次明确的前进机会。它不是全局自适应并发算法，而是教学版对无进展重试的约束。

你应寻找一个严格变化的量来解释为什么重试会结束，例如活动页表数量减少，或者某个最老请求获得可行工作。仅凭“循环应该很快找到办法”不构成活性证明。S05 会更详细讨论进展度量和错误恢复。

### 9.3 不可行请求应尽量早拒绝

若单个请求即使独占整个页池也无法满足本课程最坏需要，反复抢占其他请求也不会使它完成。submit 的容量预检避免这种无意义运行。它不保证多个请求同时都能保留完整缓存，只保证单个请求具有本教学设计下的基本可行性。

早期拒绝应给出可解释错误，而不是让请求排队很久后才发现永远不能成功。真实系统还要考虑动态模型内存、不同缓存组和输入结构，不能把教学公式当作普遍 admission guarantee。原则是：明确无法满足的合同尽早报告，不确定的动态资源则由运行策略处理。

## 第十课：自己实现一个可验证的纯计划函数

先把页面和模型都拿掉，只练习预算分配。输入是有序候选列表，每项给出请求身份、gap 和该请求本轮上限；输出是非零分配列表与剩余预算。这个函数不修改输入，因此可以反复调用比较策略。

```python
def allocate(candidates, budget):
    if type(budget) is not int or budget < 1:
        raise ValueError("positive integer budget required")
    result = []
    left = budget
    for rid, gap, cap in candidates:
        if type(gap) is not int or gap < 0:
            raise ValueError("gap must be nonnegative")
        if type(cap) is not int or cap < 1:
            raise ValueError("cap must be positive")
        count = min(gap, cap, left)
        if count:
            result.append((rid, count))
            left -= count
        if left == 0:
            break
    return result, left

plan, left = allocate([("A", 7, 3), ("B", 2, 3), ("C", 1, 3)], 5)
assert plan == [("A", 3), ("B", 2)]
assert left == 0
```

第一项验证让函数合同明确，防止 float 和 bool 混入位置数量。`left` 是局部剩余预算，不修改调用者传来的配置。每个候选的 count 不超过三个上界；追加非零项后扣减剩余量。到零时提前结束，因为后续候选不可能得到正分配。

这个函数故意没有决定候选排序。你可以在调用前旋转列表，或把 decode 放在前面，再用同一分配逻辑观察差异。分配器与排序器分别测试，错误更容易定位：若总数超预算，优先检查分配；若某请求长期得不到机会，优先检查候选顺序与成员更新。

它也没有处理资源不足。在下一阶段，为每项候选加入一个“能否安排”的纯判断，验证不可行候选不会消费 token 额度。但真实页面申请可能修改状态，所以最终还需要把可行性判断和资源提交连接起来，并为失败原子性写回归。这个渐进过程正是从纸面算法走向系统代码的路径。

## 第十一课：十四道练习与参考解答

### 练习一：给参数写单位

客户端同时发出六十四个请求，活动上限八，总 token 预算一千零二十四，chunk 两百五十六。请逐项说明计量对象，不能只写“并发”。

参考答案：六十四是客户端未完成请求数量；八是引擎同时活动序列数量；一千零二十四是某轮所有工作输入位置数之和上限；两百五十六是本教学配置中单个 prefill 候选一轮最多处理的位置数。它们没有构成固定的 `[64,1024]` 模型输入张量，也不能单独确定显存占用。

### 练习二：静态与连续批处理

A 输出两项，B 输出六项，C 输出两项，最多两条活动序列，暂不计 prefill。请列出静态批次与连续批处理成员变化。

参考答案：静态 A/B 批次要等第六轮结束，C 才开始；连续模式在 A 第二轮结束后，下一轮让 C 加入。C 在第三、四轮推进并结束，而 B 继续到第六轮。这个结果证明了更早服务机会，不证明真实 GPU 总耗时恰好按轮数比例减少。

### 练习三：剩余预算

候选 gaps 为八、二、四，prefill cap 为三，预算六。参考答案为三、二、一。解释第三项为何不是三：前两项已经消耗五，剩余仅一。若程序输出三、二、三，它把共享预算错误地当成了每请求额度。

### 练习四：零 gap

候选 A 的 gap 为零、B 的 gap 为二，预算三。参考答案只产生 B 的 Work，剩余一。零 gap 不应建立空工作，也不应消耗预算。进一步检查为什么 A 出现零 gap：它可能等待外部状态，也可能已经需要终结，不能让这种状态长期无说明地停留。

### 练习五：float 与 bool

分别传入 budget 为一点五和 True。参考答案均拒绝。True 在 Python 中可通过一般整数实例判断，但不符合此处资源数量的明确合同；本课程采用 `type(value) is int`。如果你的 API 想允许别的整型对象，应显式定义转换规则，而不是让切片操作偶然决定行为。

### 练习六：构造 FIFO 等待反例

使用 budget 一、两个长输出请求和 prefix cache 关闭。记录第二请求第一次 Work 的迭代号，再换 round-robin。参考答案应展示 FIFO 下第二请求可能长时间等候，round-robin 下更早获得工作。不要只比较最终完成状态，因为两者都完成不能说明等待分布相同。

### 练习七：只改顺序是否应改变输出

用本课程 BigramBackend、温度零、固定请求比较三个策略。参考答案：各请求最终输出应一致，批次组成和模拟时间可以不同。若输出不同，应检查请求上下文、缓存归属、重复采样或停止条件。这个测试不声称真实 GPU 的浮点路径也必然逐 bit 一样。

### 练习八：请求独立随机流

把采样温度设为正，各请求使用固定但不同 seed，改变 token_budget。参考答案：本课程中每请求输出应保持一致，因为其 RNG 状态只由该请求自己的采样消耗。若改成一个全局 RNG，不同调度顺序可能把同一随机数分给不同请求，输出随之改变。

### 练习九：chunk 与固定开销

十二个 prefill 位置，固定开销一、每位置零点二五，分别用 chunk 十二、六、三，预算足够。参考答案模拟 prefill 总代价分别为四、五、七。你必须说明这只分析单请求与透明线性模型，没有计算其他请求的等待收益，也没有包含真实 kernel 形状效应。

### 练习十：失败请求不消费预算

写一个候选 A 不可行、B 可行的分配例子。A 如果失败，本轮预算应完整留给 B。参考方案是在纯计划函数里先调用不改变状态的 feasibility 判断，只有成功选中后才减 left；进入真实页池后，要另行测试分配失败没有修改页面、引用和 computed。

### 练习十一：年龄提升策略

设计 age 表示活动请求连续多少轮没有获得 Work。每轮未服务的 age 加一，已服务的归零；超过阈值后优先考虑。参考答案必须在“实际产生 Work”之后更新 age，不能只因候选被遍历就归零，否则资源不足请求会永远看起来刚获得服务。

完整最小更新函数如下。它只维护账本，不替你决定最优阈值：

```python
def update_ages(active_ids, served_ids, ages):
    served = set(served_ids)
    return {
        rid: 0 if rid in served else ages.get(rid, 0) + 1
        for rid in active_ids
    }

ages = update_ages(["A", "B"], ["A"], {})
assert ages == {"A": 0, "B": 1}
ages = update_ages(["A", "B"], ["A"], ages)
assert ages == {"A": 0, "B": 2}
```

### 练习十二：给计划写性质检查

对 allocate 的结果验证：所有 count 为正整数；总和不超过 budget；每个 count 不超过对应 gap 和 cap；剩余量加已分配量等于初始预算。参考答案应对不同预算和 gap 组合循环检查，而不只测试一个固定三请求例子。

还要保留一个故意错误的分配器作为负向控制，例如每请求都用初始 budget。性质检查必须能抓住它。若测试只检查返回值是列表，就不能证明任何资源约束。

### 练习十三：动态成员的轮转

初始 A、B、C，第二轮后 A 结束，D 加入。请为你实现的轮转策略明确定义下轮从谁开始，并给出测试。参考答案没有唯一自然规则，但规则必须稳定、可解释，不能让成员变化导致某请求永远不被服务。当前课程使用列表和递增 cursor 取模，你应先按这个精确定义推导，再提出自己的替代方案。

### 练习十四：写一份策略比较报告

固定 workload、backend、seed、输出上限，分别运行三策略。报告至少包含每请求输出、首次被调度轮次、TTFT、E2E、平均 ITL、总模拟时间和抢占数。参考答案应先检查输出一致，再讨论指标变化，并明确时间是 synthetic。只贴一个平均值不合格，因为它无法显示某个请求受到的严重损害。

## 第十二课：三种故障注入与最小诊断

第一种故障是在资源检查前扣预算。构造先遇到不可行 A、后遇到可行 B 的场景，观察 batch 中 B 是否被错误饿住。证据应包含 allocation_blocked 和最终 Work 列表，不依赖墙钟运行时间。修复后，同样输入应恢复可行 B 的服务机会。

第二种故障是在每个候选开始时重置 budget。使用三个都需要三位置的请求与总预算四，错误实现可能安排九个位置。检查所有 Work count 之和即可定位。这个错误不会必然引发 Python 异常，因此必须靠不变量测试，而不是等待程序崩溃。

第三种故障是抢占后立即按原名额重新接纳牺牲者。观察重复的 preempted/admitted 事件和 computed 无增长，给出一个有限迭代预算使实验明确失败。修复不是“把迭代上限调大”，而是改变重试中资源状态确实前进的条件。

这些注入应在自己的练习副本中做，保留基准实现和测试。每次只改变一个机制，先写下预期反例，再运行。若同时修改预算、资源和采样，你即使看到结果变坏，也难以判断是哪项假设被破坏。

## 第十三课：为什么相同 token 预算不代表相同计算成本

前面的调度器把每个输入位置当成一个预算单位，这是清楚而实用的基础，但它不是精确的设备时间模型。为了理解限制，需要把一个 Transformer 层的主要工作分成投影、注意力读历史和前馈网络三部分。我们不在这里重新推导整个模型，而只追踪调度器面对的成本差异。

设隐藏维度为 d，本轮有 n 个输入位置。一个稠密线性投影把形状为 n×d 的矩阵乘上 d×d 权重，主要乘加数量与 n×d² 成正比。多个位置一起处理时可以复用相同权重，并形成不同形状的矩阵乘法。GPU 是否高效取决于实际形状、布局和 kernel，不是把 n 乘一个永远不变的常数就能知道。

注意力部分还与历史长度有关。对一个 decode query，若它需要读取 L 个历史 key/value，分数与加权聚合的主要工作随 L 增长。于是两个请求本轮都只安排一个 token，但一个历史长十六，另一个历史长一万，它们的 attention 工作与内存读取量不同。

prefill 中有 n 个新 query，每个 query 的可见历史范围又不同。如果它们是完整 prompt 的一段，可能既看先前已缓存位置，也看本块中不晚于自己的位置。一个简单计数是把每个 query 的可见 key 数相加；这能帮助估算注意力连接数量，但仍不是完整性能预测，因为融合、tile、缓存命中和硬件并行都会改变实际代价。

取一个可手算例子：A 是长度四的完整 prompt，因果连接数为一加二加三加四，等于十。B 是在已有长度一百历史之后新增四个位置，连接数近似为一百零一到一百零四的和，等于四百一十。两者都安排四个新 token，却不是同样的注意力工作量。一个只记录 scheduled_tokens 的图表会隐藏这种差异。

再看内存侧。decode 的多个请求通常读取同一套模型权重，但各自的 KV 历史不同；prefill 增加更多 query 行，可能提高某些矩阵运算的算术强度。算术强度可以粗略理解为每搬运一定字节做了多少计算。它不是越大越自动更快，但能说明为什么同样的 token 数在不同阶段可能遇到不同瓶颈。

因此你在真实服务中观察到“把 budget 翻倍，吞吐没有翻倍”并不奇怪。可能是设备已经接近某类瓶颈，也可能是新批次形状触发不同 kernel，或者临时内存峰值导致抢占增加。调度器只控制一部分条件，不能把所有性能现象归因于一个预算参数。

### 13.1 写一个透明的成本特征记录器

在引入复杂预测模型之前，先为每份 Work 记录可解释特征：本轮 query 数、开始位置、处理后的上下文长度、phase、KV 页数、是否跨页、是否前缀命中。记录特征不等于已经知道它们与耗时的关系，但它为之后的测量建立了依据。

例如 query 数为 count，起始位置为 start。如果采用标准因果可见范围，第 i 个新 query 的可见长度为 start+i+1。一个纯 Python 计数函数可以把这些长度相加，作为本轮注意力连接数的解析代理量：

```python
def causal_pairs(start, count):
    if type(start) is not int or start < 0:
        raise ValueError("start must be nonnegative")
    if type(count) is not int or count < 0:
        raise ValueError("count must be nonnegative")
    return count * start + count * (count + 1) // 2

assert causal_pairs(0, 4) == 10
assert causal_pairs(100, 4) == 410
```

第一项 count×start 计算每个新 query 都能看见的旧历史连接；第二项是块内下三角连接数。这个函数没有计入头数、head dimension、投影、FFN 和硬件实现，因此名称应当是连接计数，不应叫“精确 GPU 耗时”。把估计量命名准确，可以阻止后续报告不知不觉夸大证据。

你可以在练习副本中为 batch 事件附加这个字段，再比较同样 scheduled_tokens 的批次是否具有不同连接数。输出仍然只是解析特征；等真实设备实验记录每轮耗时后，才能研究哪些特征能解释时间变化。

### 13.2 从 token 公平到成本公平

假设 A、B 每轮都得到一个 token，看起来完全轮流。但 A 的历史长、B 的历史短，A 可能消耗更多设备工作。若你的目标是让两个租户获得接近的资源份额，就需要考虑成本，而不仅是 token 数。

一种入门做法是维护每请求或每租户累计的“估计服务量”，优先选择累计量较低的一方。它类似一本虚拟账本：安排工作后按明确成本模型记账。这个模型可以先使用连接数加投影近似，随后用真实测量校准。但模型偏差会影响分配，所以报告必须保留估计公式与实际效果。

不要把“采用了成本模型”当作公平证明。若某类请求的实际成本长期被低估，它仍可能获得过多资源；若模型更新后成本特征失效，旧账本也可能不再合理。正确研究路径是先定义资源份额目标，再在代表性与对抗性负载中检查偏差。

本课程不把复杂成本调度塞进基础 Engine，原因是当前任务首先要让你完整理解可行性与状态。作为扩展，你可以在独立策略中实现估计服务量，保持原始策略作为对照，并检查任何新排序都不会越过预算、资源或停止条件。

## 第十四课：用两份到达轨迹检验自己的结论

固定一批请求在时间零全部到达，称为一次突发工作集，是很容易复现的实验。它适合观察长短任务之间的服务次序、总完成时间和有限最坏等待。所有输入提前存在，最后总会逐渐排空，因此它不能完整模拟持续在线服务。

另一种负载让请求按给定时刻不断到达。如果平均到达工作量大于系统能够完成的工作量，等待队列会持续增长。这时某个策略在前十个请求上表现不错，也不意味着系统可以长期稳定。必须记录队列长度随时间的变化、完成率和拒绝策略。

再区分开放到达与闭环并发。开放到达轨迹不等待上一个请求完成才发送下一个；闭环客户端通常维持固定数量的未完成请求，每完成一个再补一个。闭环负载在服务变慢时会自然降低新请求到达速度，因此可能隐藏队列在真实开放负载下的增长。两者都可以有用，但不能把一个实验结果直接当作另一个模式的结论。

在本课程中，你可以预先填写 arrival_ms 构造确定的开放轨迹。不要把这些时间解释成真实客户端网络测量；它们是仿真输入。通过固定它们，可以确保比较不同策略时经历同一份外部需求，而不是一个策略碰巧遇到更轻负载。

建议建立两组最小轨迹。第一组包含一个长 prompt、两个短 prompt，全部时间零到达；第二组让短请求分别在长 prompt 的几轮处理中间到达。保持每个请求的 prompt 与输出上限相同，只改变到达时刻。这样可以观察 chunk 影响的是初始分配，还是后续接纳机会。

一个完整报告不应该只有“round-robin 更好”。你应写清：在哪组轨迹、哪个请求的哪个指标改善；是否有其他请求变差；总工作是否一致；有没有抢占；队列是否排空；结果是否依赖当前模拟成本公式。这样别人才能复算并提出反例。

还要避免完成请求偏差。如果实验在固定时刻停止，只统计已经完成的请求，最慢的请求会被排除，平均延迟看起来反而很好。报告应同时列出未完成、取消、失败和被拒绝请求。对未完成项不能伪造一个已经观测到的完整延迟，而应保留其状态与已等待时间。

### 14.1 一个分阶段调度研究任务

第一阶段只保存每份请求的到达时刻、prompt 长度、输出上限和身份，不改变 Engine。第二阶段跑三个已有策略，检查输出一致并导出所有事件。第三阶段写分析脚本，把每请求第一次 Work、第一次 token、结束事件关联起来。第四阶段才实现自己的策略。

这样的顺序保证你在修改之前已经拥有可复现基准。若先修改代码再决定要记录什么，很容易只保留支持新策略的指标。先固定验收字段和负载，再做改动，可以减少这种无意选择。

新增策略的最低验收包括四类检查。正确性方面，输出与基准语义一致；资源方面，预算和页池不变量成立；活性方面，有限可行工作集最终完成；性能方面，报告预先指定的指标和代价。四者缺一，都不能称为一个完整的调度改进。

最后写一页“失败的假设”：例如原以为减小 chunk 总能改善短请求，结果当短请求本来就排在前面时没有收益，长请求却增加固定开销。记录这种反例比只展示成功曲线更能提升你修改真实框架的能力，因为它迫使你把结论限定到真实条件。

## 第十五课：从本章走进真实 Scheduler

本卷固定的 vLLM Scheduler 快照把请求当前已知 token 与已计算 token 之间的差额作为重要调度依据，还维护更复杂的运行状态。你现在可以沿着“配置中的上限→Scheduler 保存的上限→每轮局部 token_budget→每请求 num_scheduled_tokens→SchedulerOutput→ModelRunner”逐段阅读，而不必先背完整个仓库。

阅读时为每个变量写单位：请求数、token 位置数、block 数、字节数、轮次数。很多源码误读实际上是单位混淆。看到一个减法，先问两边是否属于同一层计数；看到一个列表，先问它长期保存请求，还是仅属于当前批次。

S09 会建立调用链地图，S17 会围绕固定上游 helper 和真实测试逐段改写。当前章节的任务是把调度的核心问题变成你能独立手算、实现、破坏和修复的机制。做到这一点后，真实源码的复杂性才会表现为更多约束与优化，而不是一堆不可理解的类名。

来源与证据范围见 [本卷固定资料](SOURCES.md)。本章的计划代码直接对应本仓库 Engine；连续批处理、分块 prefill 和资源约束的理论动机由 PagedAttention、Sarathi-Serve 等原始论文提供背景。本文没有移用论文中的性能数字作为本课程或你的硬件测量结果。

最后的口头验收也应落到具体数值。让另一位读者给你三个请求的已知长度、已计算长度和页面状态，你在不知道程序输出的情况下写下候选顺序、每次预算扣减和最终计划；随后交换两个请求的到达时间，再完整推一次。若你只会解释已经打印出来的轨迹，却不能预先预测下一轮，说明你仍在识别术语，还没有掌握调度算法。反过来，如果预测与程序不同，不要先修改答案迁就程序：先核对阶段定义、轮转起点、前缀命中和资源条件，确认究竟是手算漏掉了条件，还是代码违反合同。教材参考实现同样需要接受这种可证伪检查。
