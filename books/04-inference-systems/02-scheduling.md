# S02 调度器：把请求变成每一轮可执行的工作

先修 S01。你现在要学的是“谁在这一轮算多少”，不是“如何把 batch size 设得更大”。完成本章后，应能实现一个调度策略、说明它牺牲了什么，并用对抗负载检验饥饿和吞吐。

## 1. 三种容易混淆的数量

客户端并发数是尚未结束的请求数量；最大活动序列数是引擎同时持有运行状态的上限；每轮 token budget 是一次执行最多计算多少输入位置。它们不是同一个参数。64 个客户端同时提交，活动上限为 8，单轮 token 上限为 1024，不意味着模型收到一个形状固定的 `[64,1024]` 张量。

排队请求还可能经过前端队列、预处理队列、调度等待队列、远端 KV 等待队列。画时间线时必须标明你观察的是哪层。`max_num_seqs=1` 可以用于简化调试，但它不普遍等价于“模型能力完整”；它限制的是调度并发，是否允许完整上下文还受模型、缓存和内存配置影响。

## 2. 静态 batch 与 continuous batching

传统静态批次把一组请求一起运行到结束。设 A 输出 2 个 token，B 输出 10 个 token；A 在第 2 轮完成后，其位置可能一直空着，直到 B 结束才填入 C。连续批处理在迭代边界更新成员：A 完成后 C 可以进来，同时 B 继续 decode。

“连续”并不表示任意时刻把新请求塞进一个已在执行的 Kernel。通常是下一个调度边界重建元数据。CPU/GPU 重叠调度还会允许提前准备后续批次，但仍需管理输入与完成依赖。先理解串行循环，再理解流水化，否则很容易把异步当作“没有顺序约束”。

连续批处理需要把请求状态从 batch 对象中分离。请求的生成历史、随机状态、停止规则和缓存表长期存在；批次只是这一轮的工作清单。我们把长期状态放在 `Request`，把短期工作放在不可变 `Work`。这也是阅读真实框架时值得首先寻找的设计分界。

## 3. 一个统一的追赶模型

对于请求 r，定义 `known = len(prompt)+len(output)`，`computed` 是已经计算的输入位置数。需要追赶的数量是 `known-computed`。提示初到时 gap 很大；每生成一个 token，known 增 1，下一轮通常只追赶一个位置。前缀缓存可以直接让 computed 起点变大；抢占后重算会让 computed 退回但 known 保持。

本参考实现保留 prefill/decode 标签便于教学。真实 vLLM 在已核实快照的 Scheduler 中更一般地按已计算 token 与已知 token 的差额调度，还考虑推测 token 等。不要把教学代码中的两个分支硬套为真实框架必有的两个独立队列。

每轮选择满足约束的一组数量 `n_r`：总和不超过 token budget，各请求不超过它的 gap，页资源足够，序列数与其他资源预算合法。有多模态输入时，还可能有编码器预算；有结构化输出时，可能等待语法状态。单靠一个整数预算不能描述全部限制。

## 4. Chunked Prefill 为什么影响首 token 与已有请求

A 的提示长 12，B 的提示长 2，budget=8。若 A 可以一次占满 budget，B 会被推迟。把 A 的 chunk 限为 4，本轮还能安排 B。另一方面，A 被拆成更多轮，每轮固定启动和调度开销增加，A 自己的 TTFT 可能变差。

把每轮代价写成 `固定开销 + prefill位置代价 + decode位置代价`，你能先验证方向，再到 GPU 测真实曲线。真实代价不是严格线性：GEMM 形状、序列长度、attention backend、CUDA Graph 是否命中都会改变耗时。本实验不把线性式当性能预测器，而把它当可解释的排队模型。

运行下面三个实验，保留 JSON：

```bash
python -m labs.serving.experiments --lab token_budget
python -m labs.serving.experiments --lab chunks
python -m labs.serving.experiments --lab continuous
```

先检查输出 token 是否相同，再比较模拟时间。若改变调度就改变我们的确定性参考模型输出，优先怀疑状态或随机流被错误共享。真实 GPU 中输出改变还可能来自数值路径差异，S12 会专门讨论。

## 5. 读 `step` 的关键顺序

先 ingest，再 admit，再构建计划；对每个候选请求算 gap 与 count；先确认页资源，再 append 元数据；只有实际安排成功才扣 budget。把扣预算放在资源分配前，会让失败请求消耗空预算，导致明明有可运行请求却形成空批次。

构建计划后统一推进时钟，再处理结果。为什么不逐请求累加整轮开销？因为这些请求属于同一批次，共享一次批次启动。在真实实现中，要进一步区分主机提交时间、GPU 开始与结束时间、结果可被 CPU 读取时间。异步 API 返回并不是 GPU 完成。

本实现把异常隔离到单请求：某个后端的 logits 失败，只结束该请求；其他请求仍可产生结果。但真实共享 Kernel 的设备错误可能破坏整个 Worker 上下文，这时不能假装单请求隔离足够。设计错误等级：输入错误、单请求执行错误、批次失败、设备不可恢复错误；恢复动作应匹配等级。

## 6. 三个策略各自的盲点

FIFO 先服务排在前面的请求，容易解释，但长 prefill 可能阻塞短交互。Decode-first 先维持已经开始输出的请求，常用于保护 inter-token latency，但持续到来的 decode 可能推迟新请求首 token。Round-robin 轮转起点，让有限预算下每个活动请求有获得资源的机会；这不自动保证等延迟，因为请求成本不同。

公平性要先定义：按请求轮转，按 token 数，按计算时间，按租户配额，还是按 SLO？同样 100 token，长上下文 decode 与短上下文 decode 的成本可能不同。一个团队提交一万个小请求也可能压倒另一个团队的一条长请求，所以生产公平性常需分层队列。

不要只报告平均延迟。A 改善 10 ms 而 B 恶化 1 s，平均值可能掩盖用户体验。至少保留每请求记录、p50/p95，以及拒绝和失败数量。比较策略时固定到达时间、提示长度、输出长度与随机种子；把生成输出变短造成的“加速”识别出来。

## 7. 练习与解答

1. **预算手算。** 请求 gap 为 7、2、1，chunk=3，budget=5，FIFO 顺序不变。答案：本轮分配 3、2、0；第三个请求虽然只要 1，也不会越过耗尽的预算。下一轮是否改变顺序取决于策略，不应在答案中暗中更改。
2. **制造饥饿。** budget=1，两个长输出请求，FIFO。预测第二请求何时拿到资源。参考：第一个每轮消耗唯一 token，它结束前第二个无法前进；round-robin 应交替服务。验收不仅看都完成，还看每请求第一次被调度的迭代号。
3. **实现年龄提升。** 在 `_order` 中按等待轮数加权。参考解法：每轮未获得 Work 的活动请求 age+1，获服务后归零；排序键先比较是否超过阈值，再执行原策略。不要只以提交年龄排序，否则老请求会永远霸占优先级。为三个到达时间不同的请求写最大等待轮数测试。
4. **区别吞吐与能力。** 把 max_sequences 从 4 改为 1。验收：固定种子下输出相同，但延迟和批次组成改变。若你据此声称实际大模型完全确定，还缺硬件数值稳定性证据；这个实验只验证参考实现的逻辑独立性。
5. **预算扣错故障。** 在页不足前扣 budget，制造一个需要两页但只余一页的请求和另一个可运行请求。正确版本应该安排后者。用事件中 allocation_blocked 和 batch.work 证明，不要靠运行耗时偶然变大判断。
6. **生产拓展题。** 在 S09 的固定 vLLM 快照里找到 token_budget 初始化、被减少的位置与 `num_scheduled_tokens` 生成位置，写一张变量流转表。答案不是某个参数说明页，而是一条“配置→Scheduler 字段→局部预算→输出结构→Runner 输入”的可复现源码路径。

掌握门槛：能手算混合长短请求四轮计划；能实现一种策略并用反例解释它的弱点；能区分客户端并发、运行序列、单轮 token 数；能指出模拟耗时和真实性能之间还缺哪些测量。
