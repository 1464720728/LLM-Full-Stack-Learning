# S15 从个人PC到共享H100：把真实硬件用于明确问题

先修基础卷环境、S08–S14。个人Win11电脑适合每天完成CPU、Python、Agent与小模型练习；Linux服务器CPU/Docker适合源码、服务与测试；H100用于需要CUDA、真实推理或多卡通信证据的课题。课程没有要求为了每个概念都占用八卡，也没有为了避开GPU而只做模拟。

## 1. 三种环境承担不同任务

在Win11上，建议把Linux相关练习放在一个明确的WSL2发行版里，保持课程目录、Python环境和Git工具的一致性。Windows路径与Linux路径不同；Windows Python安装的包不会自动进入WSL Python。先运行基础卷环境检查，再运行本卷CPU实验。

RTX5070Ti与H100的架构、内存、驱动和Kernel支持条件不同。不要因为两者都能运行CUDA，就认为同一个二进制包支持所有新架构，也不要把H100的SM90优化直接当消费卡可用实现。真实支持以当前PyTorch/CUDA/Triton/框架官方安装矩阵和运行探测为准。课程代码的纯CPU部分不依赖这一选择。

服务器上独立创建学习环境和实验容器，不修改正在服务的系统Python、全局库或已有容器。源码学习副本也不等于生产安装目录。环境隔离的价值首先是可复现和可恢复，而不仅是“整洁”。

## 2. 每次GPU实验先写一张实验卡

实验卡包括要回答的问题、设备数量与ID、预计最长时间、模型与revision、输入长度、输出上限、并发、停止条件、预期产物。比如：“一张H100、5分钟内、比较eager与默认图模式，4条固定短请求，每条最多32输出，记录首轮和预热后的延迟。”

这比“开一下大模型看看”更容易安排共享资源。卡空闲不代表你拥有长期独占权；使用公司已分配的设备与时间窗口。脚本限制持续时间与工作量，是课程行为可控的一部分，不是对公司资源管理制度的替代。

## 3. 先准备模型与镜像，不边测边下载

一个具体的单卡起点是 `Qwen/Qwen2.5-0.5B-Instruct`，固定revision为 `7ae557604adf67be50417f59c2c2f167def9a775`。已核查其[固定配置](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/7ae557604adf67be50417f59c2c2f167def9a775/config.json)：24层、hidden 896、14个Q头、2个KV头。它用于小型真实服务与正确性实验，不是本课程自行训练的模型，也不代表任何镜像都自动兼容。权重准备时把该revision和文件摘要写进实验卡；不要使用会漂移的main作为实验身份。

这个模型尤其适合说明“模型能放进多卡”与“分片合法”不同：14个Q头不满足常见均匀TP8头分片条件，不能拿它直接完成八卡实验。两卡也需核查所用backend与框架支持；八卡应另选已核实分片条件的模型，先完成S10/S13容量与通信计算。这里不给出未验证的八卡模型兼容性承诺。

`h100_server.sh`要求三个环境变量：本地已存在且带digest的vLLM镜像、绝对模型目录、明确GPU编号。模型目录需要完整权重、config、tokenizer与生成配置；记下模型来源与revision。脚本不自动挑选大模型，也不自动拉取权重。

```bash
export COURSE_VLLM_IMAGE='vllm/vllm-openai@sha256:替换为你已核验的真实摘要'
export COURSE_MODEL_DIR='/绝对路径/已准备的小模型'
export COURSE_GPU_IDS='0'
bash labs/serving/h100_server.sh
```

上面含占位符，不能原样执行。digest应从实际本地镜像元数据核验，不能从本书猜一个。第一次不加`--run`，只检查将执行的命令；确认当前镜像的`vllm serve --help`支持这些参数，再显式运行：

```bash
bash labs/serving/h100_server.sh --run
```

服务最长约5分钟，绑定到宿主机127.0.0.1:18080，单卡、短上下文、最多4活动序列、eager模式，设置保守显存利用率。这个比例仍不是“最多只使用这些空闲显存”的强隔离保证；它是框架预算参数，启动前必须确认设备分配与模型能放下。

## 4. 第一个真实服务实验

先用自己的本地小模型完成一次普通请求，再运行有限探测：

```bash
python -m labs.serving.http_benchmark --model /model
python -m labs.serving.http_benchmark --model /model --execute --requests 4 --max-tokens 32
```

第一条是dry-run，不发送请求。第二条使用`/v1/completions`流式文本接口，适用于支持该接口的服务；若模型/服务只接受聊天模板，应改适配器并记录变化，不强行把聊天请求塞进纯文本接口。返回model ID若不同于`/model`，先从服务模型列表确认实际ID。

脚本只把非空文本片段用于首文本时间，片段间隔明确标为inter-chunk。它不做高并发压测，不调用付费API，除非你明确指定远端、允许远端且执行。API Key从指定环境变量读取，永远不写到课程Git仓库或报告。

## 5. 三轮单卡实验

第一轮验证长度：固定并发1，输入约256/512/1024，输出固定32，观察TTFT、内存状态与日志，不超过配置上下文上限。输入长度用实际tokenizer计算，重复字符不保证等长token。

第二轮验证并发：固定输入和输出，从1到2到4。记录总吞吐、每请求TTFT与输出长度。不要只用串行小探测推断并发性能，需要编写明确并发负载生成器，并限制总请求数。

第三轮验证缓存：同一个前缀先预热再测suffix，再换namespace或真正清缓存做冷对照。记录token-hit与延迟；如果四条同时发出都未命中，检查第一条是否尚未完成发布，而不是立即断言缓存坏了。

所有硬件结果应保存到自己的实验记录，标明真实运行时间和环境。仓库默认提供的方法和模拟结果不能预先标成“已在H100验证”。本版本没有执行真实H100/5070Ti性能实验。

## 6. 两卡与八卡实验的升级条件

只有单卡流程正确、模型和软件支持清楚，才转两卡。脚本显式要求`--allow-multi-gpu`：

```bash
export COURSE_GPU_IDS='0,1'
bash labs/serving/h100_server.sh --tp 2 --allow-multi-gpu
```

仍先dry-run。多卡实验回答TP分片、通信、数值变化或单卡容量不足的问题；不保证变快。八卡同理用8个已分配编号与`--tp 8`，但小模型可能不支持该TP或效率很差，不能因为脚本允许就认为任何模型都适合。

本脚本是同节点TP教学入口，不是跨节点启动器，也没有启用EP、PP、PD或推测解码。若要研究这些模式，应先完成S10/S11的所有权和通信设计，再使用固定版本官方recipe验证支持条件，另写专门实验卡。

## 7. 练习与解答

1. **环境指纹。** 记录Python、框架、PyTorch、CUDA runtime、驱动、GPU名称与可见设备数量，解释runtime与驱动版本为何不是同一个值。不要把完整环境变量全部导出，里面可能有密钥。
2. **dry-run审阅。** 逐个解释脚本中的`--gpus`、端口映射、只读模型挂载、CPU/内存限制、timeout和cleanup。验收能指出容器内0.0.0.0与宿主loopback映射并不矛盾。
3. **停止演练。** 在自己的测试容器内验证Ctrl+C或timeout后容器结束、端口释放。只使用脚本生成的精确容器名，不运行全局docker清理命令。若退出码124，说明timeout到期，不应把它记录为模型崩溃。
4. **卡号映射。** 选择物理GPU3单卡，容器内框架可能看到cuda:0。解释它是可见设备列表的相对编号；不要误以为用了物理0。用设备UUID记录更稳妥，但本教学脚本只接受数值ID并明确范围。
5. **性能对照。** eager与默认graph模式各测冷启动、首请求、预热后请求。参考报告允许某些小负载没有明显改善；不应为了得到预期结论删样本。正确性、输出长度和采样条件先对齐。
6. **多卡准入。** 写一份两卡实验计划，列出模型TP支持、KV头可分性、每rank内存、通信路径、时间上限和退回单卡条件。没有这些信息时不启动八卡。任务不是回避H100，而是让每次占用都产生清晰学习证据。

掌握门槛：能独立启动和停止有界本地服务；能解释每个资源限制的作用与边界；能采集真实结果而不混入模拟数据；能知道何时一张卡足够、何时多卡不可替代。
