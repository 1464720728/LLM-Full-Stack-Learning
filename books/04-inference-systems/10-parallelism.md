# S10 TP、PP、DP、EP、CP：先切清楚数据，再讨论卡数

先修矩阵乘法、S03、S06。把八张卡的显存相加，只能得到物理容量总数，不能证明一个模型会自动使用它们。分布式设计首先是数学分解与状态所有权，其次才是启动参数。

## 1. 一个矩阵乘法的两种切法

令 X 形状 `[m,k]`、W `[k,n]`，Y=XW。按 W 的输出列切成 W1 `[k,n/2]`、W2 `[k,n/2]`，两卡各得到 Y1/Y2，拼接就是完整 Y；如果下一层能继续使用分片，不必立刻 gather。

按 W 的输入行切，同时把 X 的 k 维切成 X1/X2，则 Y=X1W1+X2W2。两卡各算一个 `[m,n]` 部分和，需要求和归约。若有 bias，应在求和之后加一次，或者采用等价但明确的分配；每卡都加完整 bias 再 all-reduce，会把 bias 加两遍。

手算：X=`[1,2,3,4]`，W 为 4×2，行依次 `[1,0]`、`[0,1]`、`[1,1]`、`[2,0]`。完整结果为 `[12,5]`。按输入切前两行部分是 `[1,2]`，后两行部分是 `[11,3]`，相加恢复。请用 NumPy 写两个分解并与原式比较；这是 TP 的最小数学基础。

## 2. TP 是层内分片，不是任意平均分权重

Tensor Parallel 通常在一层内部按规则切矩阵和 attention 头。它能让一个请求同时使用多个 GPU，但在若干位置需要 collective。增加 TP 可能降低单卡权重和某些计算量，却增加通信、改变 GEMM shape，还可能使小 batch 算子效率下降。

KV 是否均分要看 KV 头与 TP 的关系。GQA 的 KV 头数少，TP 大于可分 KV 头数时，某些实现会复制或采用其他策略；不能永远把 KV 容量除以 TP。Embedding、norm、小参数、某些路由状态也可能复制。容量估算应按具体分片规则逐项计算。

## 3. PP：按层划分与流水线泡泡

Pipeline Parallel 把层划到不同 stage。一个微批先经过 stage0 再stage1，因此单请求依赖仍然存在。多个微批能在流水线上错开：stage1 处理微批 A 时，stage0 处理 B。若只有一个很短 decode 请求，流水线很难填满。

假设两个 stage 各需 1 个时间单位，处理 4 个微批，理想流水线总时间为 2+4-1=5；完全串行是 8。两个 stage 不平衡为 1 和 3，则慢 stage 成为瓶颈，不能继续套等时公式。通信、调度、启动也会增加开销。

PP 的 KV 按层归属 stage，某张卡负责几层就持有相应状态。层数不均匀、embedding/lm_head 较大时，内存也可能不均衡。所谓“平均每卡刚好够”常常低估最重 rank。

## 4. DP 与 EP 的区别

Data Parallel 通常复制模型，给不同副本分配不同请求。它提高整体服务能力，不会让一个请求天然拥有两份副本显存。某些框架的 DP attention 与 EP MoE 会组合，不能只看到 DP=2 就认定整个模型完整复制两遍。

Expert Parallel 把专家分到设备。Router 为 token 选专家，token 激活被分发到对应设备，专家算完再把结果合并回原请求位置。这个过程包含路由索引、token permutation、all-to-all 或等效通信、专家 GEMM、权重合并。

手算两卡、四专家：卡0持专家0/1，卡1持2/3；三个 token 的 top-2 分别是 `{0,2}`、`{2,3}`、`{1,3}`。你要统计每卡发出多少份 token 激活、每专家收到多少份，再按原 token 与路由权重归并。激活分发可能复制 token 到多个专家，但不等于把全部专家权重复制给每个请求。

## 5. SP 与 CP 需要看上下文定义

Sequence Parallel 常用于把某些层的激活按序列维切分，以减少重复的激活存储与计算，并配合 TP 的 collective。Context Parallel 通常针对长上下文，把序列历史或 attention 工作分布到多个设备，需要交换 K/V、块统计或部分结果。具体名称在项目间可能不同，必须查看该实现的通信与布局。

关键问题是：每个 rank 有完整 token 序列吗？有完整 head 吗？持有哪段 K/V？最终结果在哪里归约？写出这些答案比记缩写更有用。对于 softmax attention，分片结果不是简单平均：要合并每片的最大值、指数和与加权值，才能保持归一化正确；相关数值推导见算子卷的 online softmax。

## 6. Collective 与拓扑

All-reduce 把各 rank 的张量求和等聚合后，让每个 rank 得到结果；all-gather 拼接各分片；reduce-scatter 归约后把结果分片保留；all-to-all 让各 rank 向不同目标发送不同片段。点对点 send/recv 则直接表达两个端点之间传输。

本卷 ring 模型估算每 rank 的 all-reduce 发送量约为 `2*(p-1)/p * N`，延迟项约 `2*(p-1)*alpha`，带宽项为发送量除有效带宽。它是特定 ring 算法的理想模型，不是 NCCL 永远使用的唯一算法。

单位特别容易错：100 GB/s 是每秒一千亿字节，100 Gbit/s 只有其八分之一的字节速率；GiB 则是 2 的幂。PCIe、NVLink、跨节点 NIC 的路径也不同。看到八卡互联图时，必须理解某个 rank pair 是否经过额外 hop，而不是只抄一个峰值带宽。

## 7. 实施顺序与验证

先在 CPU 数组中证明分片数学等价；再用两个本地进程做 collective 语义练习；之后才上分配到的两卡；最后需要时尝试八卡。每一步比较完整结果与分片结果，记录最大绝对/相对误差和形状。若一上来就用巨大模型，数学、通信、内存和服务配置会同时成为未知变量。

GPU 上注意 rank/world_size/local_rank 的含义。world_size 是参与某个进程组的 rank 数；local_rank 是本机设备映射；模型可能有多个不同用途的组。错误地把 EP 组拿来执行 TP all-reduce，即使所有进程都启动了，也可能死锁或得到错误结果。

## 8. 练习与解答

1. **TP 手算。** 用上文 X/W，加入 bias `[1,-1]`，正确 Y 为 `[13,4]`。若每分片先加一次 bias 再求和，会得到 `[14,3]`。为这一错误写测试。
2. **DP 容量题。** 两副本各 40 GiB 空闲，某请求需 60 GiB 状态，能否因为总空闲80而运行？常规独立 DP 不能；请求归属于一个副本。需要另一种分片或转移机制，不能靠总和推断。
3. **PP 泡泡。** 4 个等时stage、1微批，填充/排空占比很高；8微批理想步数是 4+8-1=11。答案需说明 stage 等时、忽略通信且能流水的假设；不能把公式直接当 decode latency。
4. **MoE 路由表。** 对上文三个 token 写 token→expert→rank 映射，给每路由权重0.5，专家输出简化为 `expert_id+token_id`，手工归并，再写程序还原原 token 顺序。验收顺序不能按通信到达先后拼接。
5. **通信量。** N=32 MiB、p=8，ring 每 rank 发送56 MiB。若有效50 GB/s，仅带宽项约1.17 ms，再加14次延迟项。不要把32 MiB当32 MB，也不要把总网络字节和单rank字节混算。
6. **源码拓展。** 在固定 vLLM/SGLang 源码中找到一个 column-parallel 与 row-parallel linear，追踪 gather/reduce 条件。写出输入输出shape与 bias处理。没有看到对应实现之前，不根据类名猜是否启用了通信。
