# S05 抢占、取消与故障：让系统在坏情况中仍然前进

推理服务不是一个只会从输入走到输出的直线程序。资源可能不足，用户可能关闭连接，某个请求可能触发模型错误，设备工作可能还在执行时请求已经取消。一个能运行正常样例的框架，距离能可靠处理这些情况还有很大差距。

本章把抢占、取消和失败分开定义，再围绕实际 `Engine` 逐行推导。你会看到，最难的地方通常不是“把状态改成 cancelled”，而是同时保持输出历史、随机数、缓存所有权、在途工作和外部可见结果一致。每种恢复动作都必须回答：哪些事实已经发生，哪些状态可以丢弃重建，哪些动作绝不能重复。

所有实验使用合成请求和 CPU 参考后端。真实 GPU 异步错误的处理需要具体运行时与设备证据，本章会明确给出需要新增的协议，而不会声称同步 Python 示例已经具备完整生产恢复能力。

## 第一课：先区分四个不同动作

### 1.1 等待不是抢占

waiting 请求尚未获得活动运行状态，它只是没有被接纳。抢占则针对已经运行、已经持有某些资源的请求，把它暂时移出活动集合，让其他工作先获得资源。两者的历史不同，恢复责任也不同。

一个等待中的新请求可能没有任何 K/V，也没有输出；一个被抢占请求可能已经向用户发出几十个 token。恢复后者时不能把它当成全新请求，否则用户会看到重复、丢失或内容改变。状态名即使都暂时叫 waiting，也必须保留必要历史字段。

### 1.2 抢占不是取消

抢占通常意味着任务还应继续，只是暂时让出资源。取消意味着上层决定不再继续生成。抢占后保留输出并等待重新接纳；取消后进入终态，不再安排新的模型工作。把两者混为一谈，会让资源优化意外终止用户任务。

本教学引擎中，抢占释放活动页表，将 computed 设回零，保留 prompt、output 和 rng；取消通过统一 _finish 移除队列、释放页引用并记录结束。它们共享部分资源清理动作，但用户可见语义不同。

### 1.3 失败不是正常停止

长度达到上限属于正常 finished；输入合同被拒绝、后端执行抛异常、设备不可恢复错误属于不同失败层。不能为了让所有请求“看起来结束”就把它们统一标成 finished。

用户需要知道已有部分输出是否可信、是否可以重试、是否需要新请求身份。运维需要知道错误属于单请求输入还是整个 worker。评测需要把失败计入分母，而不是悄悄丢掉。清晰终态是系统可观测性的基础，不是报告里的装饰字段。

### 1.4 重试不是恢复的同义词

重试意味着再次执行某个动作；恢复意味着把系统带回一个满足合同的状态，可能包含重试，也可能只清理资源或重新计算缓存。若动作已经产生外部可见效果，盲目重试可能重复效果。

纯模型前向通常可以在相同输入上重算，但采样会消耗随机状态，输出事件可能已经发送，文件写入或工具调用更可能产生外部副作用。因此“网络超时就再来一次”不能作为所有层通用的恢复策略。

## 第二课：建立一个“已经发生什么”的状态账

### 2.1 五类必须区分的进度

第一类是输入已经知道多少：prompt 加生成历史。第二类是缓存已经建立多少：computed。第三类是计划已经安排多少：scheduled。第四类是设备实际完成多少：completed。第五类是外部已经看见多少：emitted。

同步教学引擎把某些阶段合并，使 computed 的推进与本轮工作紧密相连；真实异步框架通常需要更多字段。不能看到一个叫 num_computed_tokens 的字段就假设它在所有版本中精确等于设备已经完成的数量；应看它在哪个阶段更新、是否包含在途预约。

为什么需要这些区别？因为取消或错误可能发生在任意两个阶段之间。已经安排但还未执行的工作可以不再提交；已经提交但未完成的工作可能无法立即停止；已经完成但未发送的结果可以丢弃；已经发送给用户的结果则不能假装从未发生。

### 2.2 输出历史是事实记录

假设请求已经输出 `[4,5]`，客户端已经收到它们。抢占后释放 K/V，不意味着这两个 token 失效。它们仍然是后续生成的条件，也仍然是外部已发生的事实。

因此当前课程保留 output，只把 computed 回退。恢复时重算 prompt 加已有 output 的历史，追赶到当前 context 后才产生下一 token。若你同时清空 output，就把同一用户请求变成了一个新的生成过程；即使最终文字偶然一样，也会造成重复发送或指标错误。

### 2.3 RNG 状态也是运行状态

每请求 rng 在采样后推进。抢占只是丢弃可重建缓存，不应把 rng 重置到初始 seed。否则恢复后下一次采样使用的是已经用过的随机数，而不是原轨迹下一项。

只保存 seed 不足以精确恢复任意中途状态，除非你能按相同规则重放所有已发生的随机消耗。实际采样器、过滤或投机流程可能消耗不同数量的随机数，因此这种重放需要明确合同，不能靠猜“生成了几个 token 就跳过几个随机数”。

本课程抢占发生在同一进程中，rng 对象原样保留，所以不需要序列化。若扩展成持久恢复，应保存兼容的 RNG 状态或设计明确的按请求位置取随机数机制，并记录版本与算法条件。

### 2.4 缓存是可重建状态，但不是无成本状态

K/V 通常可由已知 token 历史与相同模型重新计算，因此释放它不必丢失语义历史。但重算消耗设备时间，也可能影响其他请求等待。把所有请求频繁抢占，会形成吞吐下降甚至抖动。

此外，重建必须使用相同模型、位置、adapter 和输入处理语义。若模型在中途升级，拿新权重重算旧请求历史不一定继续同一个生成过程。恢复配置身份是合同的一部分，而不是“只要 token 一样就行”。

## 第三课：为什么会需要抢占

### 3.1 逐步增长的资源需求

接纳时两个请求都能放下，不代表生成若干轮后它们的缓存增长仍然可同时容纳。每次新 token 可能填满尾页并触发新页申请；如果多个请求在同一轮跨页，自由池可能突然不足。

例如池有四页、每页两项，A、B 各有四项 prompt，刚完成 prefill 就各占两页，总池已满。它们继续生成时需要把新 token 的状态写入额外页。如果两者都保持活动状态，可能谁都无法推进。

这不是模型参数内存变化，而是请求状态增长。只看服务启动时“模型成功加载”不能证明运行时所有长度与并发组合都可行。S13 会把静态权重和动态缓存分开记账。

### 3.2 预留、换出、重算与拒绝

一种策略是在接纳时为最坏输出预留全部缓存，容易保证可行，但可能把大量从未使用的上限空间锁住。另一种策略按实际增长分配，资源紧张时换出或重算。还有服务会限制长度、并发或直接拒绝超出预算的请求。

换出把状态搬到另一个存储层，恢复时搬回；重算释放状态，恢复时重新执行历史。换出有传输与存储成本，重算有计算成本。哪种更好取决于模型、上下文长度、互连、主机内存与工作负载，不能只记一个固定答案。

本课程采用重算式抢占，方便在纯 CPU 元数据模型中验证语义。它没有模拟实际 GPU 到 CPU 的传输，也没有声称对所有模型最优。你应该先理解它必须保持哪些状态，再研究生产框架如何选择策略。

### 3.3 牺牲者选择的代价

抢占最近接纳的请求，可能保护更早等待的用户；抢占最大缓存请求，可能一次释放更多页；抢占重算成本小的请求，可能降低恢复代价。不同目标会给出不同选择。

当前 Engine 选择 running 列表最后一项，保留较老的活动请求。这是透明而有限的策略，便于构造前进证明；它不是基于完整成本模型的最优算法。教材中的简单选择应当作为可比较基线，而不是被包装成生产最佳实践。

## 第四课：逐行解释 _preempt_for_progress

核心代码如下：

```python
def _preempt_for_progress(self):
    if len(self.running) < 2:
        return False
    rid = self.running[-1]
    r = self.requests[rid]
    self.pool.release(rid)
    self.running.remove(rid)
    r.state, r.computed = "waiting", 0
    r.preemptions += 1
    self.waiting.appendleft(rid)
    self.event("preempted", rid=rid)
    return True
```

### 4.1 为什么至少有两个活动请求

如果只有一个请求，抢占它并马上尝试自己，可能只是无意义重算循环。课程 submit 已经预检单个请求在独占整个池时具有基本可行性，因此一个独占请求仍无法前进时，应调查不变量或设计限制，而不是无限抢占自己。

这个判断依赖课程的容量与分配模型。更复杂框架可能支持不同的单请求换出或重新调度策略，但那需要额外状态。不能把当前一条 if 当作所有系统的通用定理。

### 4.2 release 释放的是活动拥有权

pool.release 删除这个请求的页表并减少其页引用。若某些完整前缀页还被缓存拥有，它们仍然保留；所以抢占不一定把该请求历史所涉及的全部物理页都变成自由页。

这也解释了为什么调度器应观察实际 free 数量，而不是假定“抢占了一个长度八的请求，所以必定释放四页”。共享页面和缓存拥有会改变释放量。资源优化必须依据真实拥有关系。

### 4.3 running 与 waiting 同步变化

从 running 移除后，将 state 改为 waiting，并把身份放到 waiting 左端。保留 prompt 与 output，computed 归零，preemptions 加一。appendleft 让它在后续接纳中较早重新获得机会，但本轮还需要防止它立即回到原占用状态。

若只改 state 而忘记移除 running，后续排序可能继续安排它；若只移除 running 而不加入 waiting，任务就被遗忘；若加入两次 waiting，则可能重复接纳。所有集合关系应作为不变量一起检查。

### 4.4 事件记录的是已经完成的状态转移

preempted 事件在关键状态更新后记录，使观察者能把它理解成抢占已经发生。日志时机也需要语义：如果先记录成功，再执行可能失败的释放，日志可能声称一个实际未完成的动作。

真实系统有时会记录 intent 与 completion 两种事件，以便恢复和诊断。当前简单同步实现只保留完成事实；扩展时不要把“准备抢占”与“已经释放资源”写成同一个不加区分的事件名称。

## 第五课：重算为什么不能重复输出

### 5.1 一个完整恢复例子

设 prompt 为 `[1,2,3]`，已输出 `[4,5]`，所以 context 长五。正常运行中 computed 为四，最后已选出的 5 尚未处理。现在抢占，output 保持两项，computed 变成零，活动页表释放。

恢复接纳后，如果没有前缀缓存，computed 仍为零。chunk 为二时，第一份工作处理一二，computed 二；第二份工作处理三四，computed 四；第三份工作处理五，computed 五。前两轮只是恢复已知历史，不产生新输出。

只有第三轮追上完整 context，才采样下一个 token 6，并追加一次输出。最终历史从 `[4,5]` 变成 `[4,5,6]`，而不是再次发出四五六。这个过程解释了 `computed == len(context)` 门槛为什么不能被“每轮工作结束就采样”替代。

### 5.2 前缀缓存可以缩短恢复

如果接纳时命中前两个 prompt token，computed 从二开始，前面的重算工作可以跳过。课程只发布 prompt 前缀，不把整个生成后缀都自动保存为可共享条目，所以恢复仍可能需要追赶已有输出历史。

cache_hit_tokens 在多次接纳中会累加命中次数，它不是去重后的“独一无二被缓存 token 总量”。报告应清楚说明这个计数口径，避免把重复恢复命中误当作输入总长度之外的新内容。

### 5.3 外部输出不能靠事后字符串去重

有人会尝试在客户端发现重复片段后删除它们，来掩盖恢复时重复生成。这个办法不可靠，因为正常语言本来就可能重复单词或句子；你无法仅凭文本判断某片段是合法生成，还是错误重放。

正确协议应在状态层保证不重复发出已经提交的输出，或给输出事件稳定的序号与请求身份，让消费者能够识别重放。文本内容不是事件身份。这个原则与 Agent 工具调用的幂等键相似，但推理输出和外部工具副作用仍有各自具体合同。

## 第六课：取消请求时要处理哪些阶段

### 6.1 取消尚未到达的请求

在模拟器里，请求可以提前登记一个未来 arrival_ms。若此时取消，不能让 finish_ms 减 arrival_ms 得到负延迟。当前 cancel 会把未来到达时刻调整到当前模拟时刻，再终结。

这是为了让本教学指标保持有意义，不是生产网络协议的普遍规则。真实服务中的“请求已经接收但业务计划在未来执行”可能采用不同时间字段。关键是每个时间戳都必须有清楚含义，不能为了避免负数任意覆盖原始审计事实。

### 6.2 取消 waiting 请求

waiting 请求还没有活动页表，_finish 主要把它从等待队列移除，设置 cancelled、finish_ms 和事件。它不应该继续占据接纳顺序，也不应该在下一次 _admit 中被重新加入 running。

测试应取消队首、队中与最后一项，而不只测试唯一等待请求。容器移除逻辑若写错，可能删除了相邻请求或留下重复身份。用不同 rid 和不同 prompt 可以避免错误结果恰好一样而被隐藏。

### 6.3 取消 running 请求

同步课程中，cancel 发生在 step 调用之间，没有正在异步执行的设备工作。它释放活动页表、移除 running 并进入终态。后续 step 不再为其形成 Work。

若你把 cancel 放进另一个线程，与 step 同时操作同一个 Engine，当前代码没有承诺线程安全。不能因为 Python 解释器存在某些运行时锁就假设跨多个容器的状态更新是原子的。要支持并发取消，需要集中事件队列、锁或其他明确同步设计。

### 6.4 取消已经 finished 的请求

已终结请求的第二次 cancel 返回 False，不再释放资源，不改时间，不追加事件。调用者可以把它理解为此次没有新的状态转换。这个幂等行为防止网络重试或重复用户操作造成 double free。

幂等不代表所有错误都应该吞掉。对不存在的 rid，当前实现仍会触发查询错误；它与“存在且已经结束”不同。API 层可以选择如何向客户端编码这两种情况，但内部不应丢失区别。

## 第七课：统一 _finish 为什么重要

### 7.1 终结路径的共同责任

_finish 检查并释放活动页表，移除 running 与 waiting 中的身份，写入 state、finish_ms、error，再记录事件。正常完成、取消与捕获到的后端错误都通过它，减少各分支重复实现清理的机会。

如果普通完成释放资源、错误分支却只写 state，失败请求就会泄漏页。若取消分支释放了页，却仍在 running 中，下一轮可能读到不存在的表。统一终结函数使这些责任集中可审查，但仍需要每种入口的测试。

### 7.2 状态与错误信息

state 表示类别，error 保存简化错误信息。本课程后端异常只保存异常类型名，避免把任意长或敏感内容塞进报告。这是教学选择；生产日志可以有更详细、受控的诊断字段，但不应把内部堆栈和私密输入无条件回传用户。

错误对象也应区分可重试与不可重试条件。输入 token 超词表重试同样输入不会成功；瞬时资源紧张可能稍后成功；设备上下文损坏可能要求重启 worker。一个布尔 success 不能表达所有恢复责任。

### 7.3 清理顺序与异常边界

清理本身也可能发现不变量错误，例如页引用不足。当前代码让这类错误暴露，帮助发现资源管理缺陷，而不是在所有清理异常上静默 pass。把所有异常吞掉会让服务表面继续运行，内部账本却越来越坏。

生产系统可能需要尽最大努力清理多个资源，并聚合报告错误；这不等于假装每项释放都成功。若某资源无法确定是否已释放，应进入明确的故障处理路径，避免再次分配导致数据损坏。

## 第八课：从单请求错误到 worker 故障

### 8.1 输入错误

输入错误发生在模型工作之前，例如非法 token、负预算、格式错误。应尽早拒绝，且不留下活动页和部分请求历史。它通常不要求其他合法请求失败。

本地 mock 服务把某些验证异常转换成 HTTP 错误响应。协议状态与内部异常类型不是一一相同的东西，API 层需要明确映射。不要把所有异常都返回同一个“服务器错误”，否则用户无法判断是否应该修正输入。

### 8.2 单请求后端异常

课程提供一个 Failing 后端：遇到特定首 token 就抛 ValueError，其他请求正常输出。Engine 在处理该请求 logits 时捕获异常，调用 _finish(error)，继续处理同批其他请求。

这个实验检验隔离语义：一个坏请求不能让所有好请求都被无声丢弃，同时坏请求的资源必须释放。它不证明真实 GPU kernel 的所有错误都能局部恢复。Python 函数抛异常与设备运行时错误是不同故障等级。

### 8.3 批次与设备错误

某个共享 kernel 出错，可能影响整个 batch；某些设备错误可能使后续操作无法可信继续。恢复策略要依据具体运行时保证，不能简单把错误归给某一个 rid 然后让其他请求照常使用同一损坏状态。

一个合理的诊断框架先记录失败发生的阶段、涉及 batch、worker 与请求，再决定重试、重算、终止或重启范围。重启本身还会影响已有活动请求的结果交付，需要上层协议处理。S14 会把这种分层诊断展开为实际排障流程。

### 8.4 失败后是否继续使用内存对象

如果某个操作在中间失败，调用方不能未经确认就继续使用已变更的内存状态。需要知道该操作的失败原子性范围，或从可信快照重建。前面 PagePool 的 OutOfPages 保证很明确；任意第三方 backend 抛错则未必有相同保证。

这也是为什么接口合同要写清“失败后状态如何”。只说明成功返回值，无法指导恢复。一个高层 catch 语句只能捕获控制流，不会自动修复被调用函数已经修改的数据。

## 第九课：异步取消为什么需要“延迟释放”

### 9.1 CPU 说停止，不代表设备已经停止读取

考虑一张物理页 P。CPU 已经提交一个 GPU kernel，它稍后会读取 P。此时用户取消请求，CPU 收到消息并从调度队列移除它。这个动作只能保证不再主动安排新工作，不能自动撤销已经提交的设备读取。

如果立刻把 P 放回自由池，另一个请求可能把新 K/V 写进去，而旧 kernel 仍在读取。结果可能是错误数值，也可能是跨请求数据混用。这类错误不一定每次出现，因为它取决于设备与主机的交错时序。

因此“取消完成”的定义需要拆开。对用户的逻辑取消可以已经确认；资源完全可复用则要等待所有在途使用结束。两个事件可以发生在不同时刻，报告和状态机应能表达这个差别。

### 9.2 三种责任不能压成一个布尔值

第一种责任是请求是否仍允许提交新工作。第二种是已经提交的工作是否仍可能读取资源。第三种是结果是否仍允许向用户发出。取消通常让第一和第三变成否，但第二可能暂时仍为是。

一个简单布尔 active 无法完整表达这种组合。如果 active=False 就立即释放，会过早回收；如果 active=True 才能保留资源，又可能继续输出被取消请求的结果。分开记录逻辑状态与在途计数，可以避免这个冲突。

你可以把状态分成 active、cancel_requested、draining、retired 等阶段，但名字不是关键。关键是每个阶段明确允许什么动作：能否新提交、能否发结果、是否仍持有资源、什么完成条件允许回收。

### 9.3 在途引用的思想

一种教学模型是把每个在途设备操作看成临时拥有者。请求本身持有一份 owner 引用，提交工作时再增加一份 in-flight 使用；取消释放请求 owner，但只要 in-flight 尚未归零，页面就不能回收。

操作完成时减少对应在途使用；当逻辑拥有者为零且在途使用为零，资源才能重新进入 free。真实框架可能用事件、stream 顺序或其他机制表达，不一定真的采用相同计数字段；但它们都必须保证旧使用与新复用之间的顺序。

### 9.4 完成消息还要能识别旧代次

物理页号可以复用。旧请求使用页零，释放后新请求也可能使用页零。若某个迟到完成消息只带页号，系统可能把它误认为当前分配的完成事件。

因此给分配附加 generation，让句柄成为“页号加代次”，可以在教学模型中识别过期消息。完成事件还需要独立 ticket，避免同一工作完成通知被处理两次。页身份与工作身份共同保护资源生命周期。

这不是用更长 ID 自动解决并发，而是把需要验证的事实显式编码出来。真正的同步协议仍要保证状态更新本身不会被并发交错破坏。

## 第十课：一个可运行的延迟释放状态机

下面是完整的离散事件练习。它不调用 CUDA，不模拟设备耗时，只演示取消后在途操作尚未完成时，页面为什么仍不可复用。把它保存到自己的练习文件运行，逐行核对后面的状态说明。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Handle:
    page: int
    generation: int

class DeferredPool:
    def __init__(self, pages=1):
        self.free = list(range(pages))
        self.generations = [0] * pages
        self.live = {}
        self.tickets = {}
        self.next_ticket = 1

    def allocate(self):
        if not self.free:
            raise RuntimeError("no reusable page")
        page = self.free.pop(0)
        self.generations[page] += 1
        handle = Handle(page, self.generations[page])
        self.live[handle] = {"owner": True, "inflight": 0}
        return handle

    def submit_use(self, handle):
        state = self.live[handle]
        if not state["owner"]:
            raise RuntimeError("cancelled owner cannot submit new work")
        ticket = self.next_ticket
        self.next_ticket += 1
        self.tickets[ticket] = handle
        state["inflight"] += 1
        return ticket

    def cancel_owner(self, handle):
        state = self.live.get(handle)
        if state is None or not state["owner"]:
            return False
        state["owner"] = False
        self._reclaim_if_idle(handle)
        return True

    def complete(self, ticket):
        if ticket not in self.tickets:
            raise ValueError("unknown or duplicate completion")
        handle = self.tickets.pop(ticket)
        state = self.live[handle]
        state["inflight"] -= 1
        self._reclaim_if_idle(handle)

    def _reclaim_if_idle(self, handle):
        state = self.live[handle]
        if not state["owner"] and state["inflight"] == 0:
            del self.live[handle]
            self.free.append(handle.page)
            self.free.sort()

p = DeferredPool(1)
old = p.allocate()
ticket = p.submit_use(old)
assert p.cancel_owner(old) is True
assert p.free == []
assert p.live[old]["inflight"] == 1
p.complete(ticket)
assert p.free == [0]
new = p.allocate()
assert new.page == old.page
assert new.generation != old.generation
assert old not in p.live
assert p.cancel_owner(old) is False
assert p.cancel_owner(new) is True
assert p.free == [0]
```

### 10.1 Handle 为什么冻结

Handle 由 page 和 generation 组成，并使用 frozen dataclass。它作为字典键表示一次具体分配身份。若插入 live 后还能修改字段，键的含义可能改变，字典查找也会失去稳定性。冻结不是完整安全机制，但它清楚表达身份对象应不可变。

物理页号相同、generation 不同的两个 Handle 不相等，所以新旧分配不会被看成同一条 live 记录。这个设计让迟到的旧句柄查询明确失败或返回“已经不再拥有”，而不是误操作新请求。

### 10.2 allocate 不知道设备工作

allocate 只从当前可复用 free 中取页，增加代次，建立一份逻辑 owner。它不假设页面没有历史使用，因为旧使用的完成责任已经由 free 的维护协议处理。

也就是说，free 不是“用户已经取消的页面”，而是“所有旧拥有和在途使用都已结束、可以安全复用的页面”。这个定义比一个模糊的“空闲”词更强，也更容易写测试。

### 10.3 submit_use 先取得当前拥有状态

提交使用前检查 owner 仍然有效，避免取消后继续安排新工作。然后生成唯一 ticket，把 ticket 映射到当前 Handle，增加 inflight。ticket 是工作身份，不是页身份；同一页可以有多个在途工作，因此不能只用页号作为完成通知键。

若未来支持多个逻辑请求共享同一页，owner 也需要从布尔值扩展为明确计数或拥有集合。本例只研究单个逻辑 owner 与多个在途使用，刻意把范围保持可手算。

### 10.4 cancel_owner 与 complete 各自减少什么

cancel_owner 只撤销逻辑 owner，不假装设备工作已经完成。complete 只处理对应 ticket 的在途使用，不把仍活跃的 owner 一起删除。两者都调用同一个回收判断，保证条件集中一致。

第一次取消返回 True，重复取消返回 False。重复 complete 则报错，因为它表明同一工作完成事件被重复处理；如果静默再减一次计数，就可能提前回收。幂等策略应根据接口责任明确选择，而不是所有重复都一律忽略。

### 10.5 这个模型不能证明什么

它没有真实线程竞争，没有 GPU stream，没有跨进程消息丢失，也没有内存写入可见性。它证明的是一个离散事件顺序下的生命周期关系：取消 owner 后只要有在途使用就不能复用，所有使用完成后才进入 free。

迁移到真实框架时，你需要找到什么事件等价于 submit_use、什么完成条件等价于 complete，以及这些事件是否可能丢失、重复或乱序。代码形式可以完全不同，但资源安全问题不能消失。

## 第十一课：活性与有界重试

### 11.1 为什么“没有崩溃”还不够

一个服务可能永远循环，却没有完成任何请求。日志不断出现分配失败、抢占、重新接纳，看起来程序很忙，但 computed 和 output 都没有增长。这样的系统没有满足活性要求。

正确性通常包括安全与活性两类目标。安全关心坏事不发生，例如不读错页、不重复输出；活性关心好事最终发生，例如有限可行请求能完成、取消最终释放资源。一个永不执行任何工作的小程序可能很难写错输出，但它显然不能算可用推理服务。

### 11.2 找一个能说明前进的量

在正常轮次，可以观察本轮是否安排了至少一个有效位置、某请求 computed 是否增加、是否产生新输出或是否减少了待处理请求。在抢占重试中，可以观察活动请求数量是否严格减少，使一个原本可行的请求获得独占机会。

不是所有状态都单调增加。computed 在重算时会回退，所以不能只用它作为整个系统唯一进展指标。需要结合“已经对外提交的输出事实”“当前恢复阶段”“活动资源集合”建立更完整的论证。

### 11.3 重试预算的职责

max_iterations 给教学 run 一个明确上限，避免逻辑错误造成无限运行。达到上限应报告未完成，而不是伪装成正常结束。预算不是让任意错误最终消失的参数；如果一个最小例子总在相同状态循环，把上限从一万改成一百万只会浪费更多时间。

网络重试也应有次数、时间和退避规则，但必须先确认操作是否适合重试。已经发送的输出事件、已经产生的外部效果和纯可重算状态不能用同一策略处理。

### 11.4 finally 为什么出现在临时并发限制周围

当前 Engine 为避免刚抢占的请求立即重新接纳，会临时改变 max_sequences，递归尝试一步，再在 finally 恢复配置。finally 的作用是无论内部正常返回还是抛异常，都执行恢复。

若只在正常路径恢复，某次错误可能让引擎永久保留较低并发上限，后续表现像性能退化，却很难从请求结果直接发现。临时修改共享配置必须有清楚的恢复边界；更复杂实现也可以用局部参数避免修改全局字段。

## 第十二课：十五道练习与完整参考解答

### 练习一：抢占与取消的字段差异

列出两者对 prompt、output、computed、rng、state、页表和终结时间的处理。参考答案：重算式抢占保留 prompt/output/rng，computed 回退，释放活动表，state 回 waiting，不写正常终结时间；取消进入终态，移除活动/等待身份并记录结束，后续不再生成。两者都可能释放请求页引用，但不能因此合并为同一操作。

### 练习二：恢复手算

prompt 长三、output 已有两项、computed 为四，抢占后无缓存、chunk 二。参考答案恢复工作长度依次为二、二、一；只有最后一次追上五项 context 后才采样新 token。若前两轮也发出输出，就把缓存恢复误写成继续生成。

### 练习三：为什么保留 RNG

用固定 seed 的随机采样请求，记录运行到两项输出时的 rng 状态，再抢占恢复。参考答案：保留对象应接着消费下一份随机数；重新建立同 seed RNG 会回到序列开头。这里没有要求最终随机 token 必然不同，因为某些分布可能偶然选到相同 token；应直接检查随机状态或使用能稳定显露差异的分布。

### 练习四：取消幂等

运行一个请求一步后取消两次，保存第一次后的事件数、finish_ms 和自由页数。第二次应返回 False，三项状态不变。这个测试比只看 state 为 cancelled 更强，因为它检查了重复请求不会产生新的资源副作用。

### 练习五：取消等待中的请求

活动上限一，提交 A 和 B，让 A 运行而 B 等待，再取消 B。参考答案：B 从 waiting 移除，不创建新页表，不在 A 完成后重新接纳。A 应照常完成。给两请求不同 prompt，防止错误删除 A 却被相同输出掩盖。

### 练习六：取消未来请求的时间

登记 arrival_ms 大于当前模拟时钟的请求并立即取消。当前课程应保证报告不出现负的结束耗时，它会调整该请求的到达字段。解释这是一项仿真口径选择，真实审计系统若要保留原计划时间，应另外建立“实际取消时刻”等字段，不能随意丢失业务事实。

### 练习七：后端异常隔离

使用下面完整后端，让首 token 为九的请求失败，其他请求返回固定 logits。坏请求应 error，好请求应 finished，活动页表最终与 running 一致。

```python
from labs.serving.engine import Engine, Request

class FailingBackend:
    vocab_size = 16
    def logits(self, ids):
        if ids[0] == 9:
            raise ValueError("injected request failure")
        return [float(i) for i in range(16)]

e = Engine(backend=FailingBackend(), prefix_entries=0)
e.submit(Request("bad", (9,), 2))
e.submit(Request("good", (1,), 2))
e.run()
assert e.requests["bad"].state == "error"
assert e.requests["good"].state == "finished"
assert e.requests["good"].output == [15, 15]
e.check()
```

参考解释：这个用例只覆盖同步 Python 后端异常，不能证明任意 GPU 设备错误都能让同批其他请求继续可信运行。报告必须保留这条证据边界。

### 练习八：提前释放的反例

在 DeferredPool 中把 cancel_owner 改成无条件立即回收，不管 inflight。参考答案：取消 old 后新请求能够复用同一页，而旧 ticket 仍未完成，生命周期已经违反合同。测试应在旧 complete 前检查新分配是否被错误允许，而不是等待某个随机数据损坏才判失败。

### 练习九：重复完成通知

对同一 ticket 调用 complete 两次。第二次应明确拒绝，不能让 inflight 变负或再次把页加入 free。参考答案要检查 free 中每个页号唯一，而不是只检查长度，因为重复自由页会造成后续重复分配同一物理存储。

### 练习十：旧句柄不能取消新分配

旧 Handle 释放后，同页被新 generation 复用。对旧 Handle 调用 cancel_owner 应返回 False，不能撤销新 owner。这个测试展示物理页号复用与逻辑分配身份不同；如果字典只以 page 为键，迟到旧操作可能作用到新任务。

### 练习十一：两份在途工作

同一 Handle submit_use 两次，再取消 owner。完成第一张 ticket 后页面仍不能复用；完成第二张后才自由。参考答案中的 inflight 依次为二、一、零，owner 始终已经撤销。只用一个“正在执行”布尔值不能可靠表达多个并行使用者的完成关系。

### 练习十二：不能把连接断开当作已撤销计算

客户端关闭连接后，服务器是否一定立即停止 GPU 工作？参考答案是否。网络层观察到断开、取消消息到达引擎、引擎停止安排新工作、在途设备工作完成、资源回收是不同阶段。你需要沿这些阶段记录事件，不能只在前端捕获 BrokenPipeError 就声称资源已经释放。

### 练习十三：构造无进展循环

让抢占后被释放请求立即重新接纳，资源占用恢复原状。参考答案应在有限迭代预算内检测 repeated state：活动集合、页占用和 computed 反复相同。修复需要让重试状态发生可证明变化，而不是只减少日志或延长超时。

### 练习十四：部分输出的报告

一个请求已经输出两项后被取消。报告应保留两项历史、cancelled 状态、实际发出时间和结束时间，不能把它记为零输出正常完成。上层可以决定是否展示或丢弃部分结果，但推理层事实记录不应伪造。

### 练习十五：定义一个恢复检查点

为持久恢复列出最低字段：请求身份、模型/adapter/协议版本、原始已编码输入、已提交输出、停止配置、采样状态、下一事件序号，以及缓存重算或恢复策略。参考答案还要说明 checkpoint 写入失败时不能继续假装它已持久化；内存状态与持久状态的分歧必须有明确处理。

本课程 Engine 不实现这个完整持久恢复协议，所以练习的实现应放在独立项目中。你可以先保存合成请求和标准库 RNG 状态，验证进程重启后与不中断基准一致，再逐步加入缓存、网络和外部观察，不能一次跳到“生产级恢复”。

## 第十三课：三组恢复故障的实验记录

### 13.1 重算过程重复发 token

基线使用已有 output 不变、computed 回退的重算。错误版本在每次重算块后都采样。记录每轮 known、computed、output 与事件序号，第一处分歧会在尚未追上完整历史时出现。

修复后不仅最终列表要正确，输出事件数量和顺序也要正确。如果最终把重复项删掉再比较列表，测试会掩盖客户端曾经收到错误片段的事实。验收必须关注外部可见事件，而不只是最终内存结果。

### 13.2 取消路径漏释放

错误版本只把 state 设成 cancelled，不移除 running 或页表。运行后 check 应发现集合关系不一致，或自由页无法回到基线。分别在 waiting、running、已输出部分结果后取消，确认每条路径都覆盖。

修复应通过统一终结函数完成对应责任，而不是在每个测试末尾手工 clear 池。测试清理不应替被测实现掩盖泄漏，否则实际服务仍会积累问题。

### 13.3 恢复时模型配置变化

用两个不同种子的 TinyAttentionBackend 代表不同权重，前半段在旧后端生成，恢复时偷偷换新后端。即使历史 token 保留，后续分布也不再是同一个模型运行。这个实验展示恢复身份的重要性。

正确行为可以是拒绝不兼容恢复，或者明确把它当成新的模型接续任务并向上层说明；不能继续把结果标成原版本的精确恢复。对真实模型升级也应保持同样的身份原则。

## 第十四课：如何评价一个抢占策略

只统计抢占次数不够。同样一次抢占，可能丢弃十个 token 的缓存，也可能丢弃十万个；恢复计算量、释放物理页数量和用户停顿都不同。一个策略减少抢占次数，却每次选择最昂贵的请求，未必更好。

建议记录每次抢占的请求身份、已知长度、computed、实际释放页数、是否有前缀可复用、恢复到原进度的工作量、期间其他请求完成情况。字段应来自明确事件，而不是事后凭最终状态猜测。

还要观察抖动：同一请求是否短时间内反复被抢占和接纳。频繁重算可能消耗大量算力却不增加外部输出。此时总 GPU 利用率很高也不代表有效吞吐高，必须区分恢复工作与新生成工作。

比较策略时保持相同输入与输出合同。若一个策略通过提前终止困难请求获得更低平均延迟，它改变了完成集合，不能与全部完成的策略只比较同一个均值。拒绝、取消、失败和未完成都要单列。

对于共享 H100，真实恢复实验应有明确规模和截止条件。先在 CPU 离散模型验证状态协议，再用短上下文和少量请求验证实际框架事件。不要用无限长生成把公司设备占满来“自然触发压力”；可以通过小的可控资源配置或测试夹具建立相同机制问题。

本章的结业要求是：你能解释哪些状态可重建、哪些事实不能撤销；能写出取消后的在途资源协议；能用一个最小反例证明错误重试会重复输出；能在报告里把模拟恢复工作、真实设备完成与用户可见结果分开。做到这些，才算把“支持抢占和取消”从两个配置名变成可审查的软件行为。

## 第十五课：取消与结果同时到达时，谁先算数

在同步教学程序中，你通常先调用一步，再调用 cancel，顺序很清楚。真实服务却可能同时收到设备完成消息与用户取消消息。此时不能只说“取消优先”或“结果优先”，必须定义一个能够落实到代码的裁决点。

### 15.1 三种不同时间线

第一种时间线是取消先被引擎处理，结果后来才完成。系统可以丢弃迟到结果，不再向用户发出新 token，但仍等待设备完成后释放资源。这里的“丢弃”是丢弃输出，不是宣称设备从未计算。

第二种时间线是结果已经被引擎接受，但尚未通过网络发送，随后取消到达。服务需要规定这个已准备结果是否仍允许发送。两种选择都可能合理，但客户端体验与状态记录必须一致，不能同一版本在不同路径上随机处理。

第三种时间线是结果已经发送，取消随后到达。已经发出的字节无法从网络和用户记忆中撤回。取消只能阻止后续工作，报告应保留已发部分结果。把输出列表清空并不等于撤销外部事实，只会让内部记录与客户端所见不一致。

### 15.2 线性化点的直观含义

可以把一个并发操作的线性化点理解为“系统正式承认这次操作发生的那个决定时刻”。例如引擎在单一事件循环中按顺序处理消息，把请求状态改为 cancelled 的位置，就是取消在内部状态上的生效点。

在这个点之后，新完成结果若属于已取消请求，就按约定丢弃；在它之前已经提交的输出，保留其事实。事件循环的顺序让并发到达变成可解释的内部顺序，但并不保证真实世界所有观察者同时看见它。

如果采用多线程共享状态，也需要通过锁或原子状态转换建立等价裁决。仅仅先读一次 state、再稍后写 output，中间取消可能已经发生；这种检查与使用之间的窗口需要设计，而不是靠“两个动作间隔很短”忽略。

### 15.3 事件序号与重复交付

给每个请求的输出事件增加单调序号，例如零、一、二，可以让客户端区分新的增量与网络重放。稳定请求身份加序号比文本内容更适合做去重键，因为两个合法连续 token 可能解码成相同文字。

但有序号不等于已经实现 exactly-once。服务端可能在发送后、记录确认前崩溃；客户端可能收到后、保存状态前崩溃。要声明严格交付保证，需要明确持久化、确认和重试协议。很多系统实际提供的是至少一次传递加幂等消费，或者尽力而为流式传递。

本课程没有把完整网络重连协议塞进 Engine。你可以先在纯 Python 队列中模拟“发送成功但确认丢失”，验证消费者按请求身份和序号不会重复应用事件，再考虑真实网络。这样每一步都有可验证合同，而不是只给系统贴一个可靠标签。

### 15.4 mock_server 的能力边界

课程 mock_server 捕获 BrokenPipeError 或 ConnectionResetError，避免客户端断开让演示处理线程直接打印噪声。但它并没有实现一套外部取消端点，也没有异步把断开通知传到正在运行的 Engine。

因为核心运行在锁内同步完成，客户端断开时，模型模拟可能已经全部运行结束。不能把这个异常捕获描述成“支持实时取消 GPU”。想增加真实取消，需要把接收与执行分离，并给运行请求建立可达的控制通道。

这个边界是很好的项目任务：先设计请求登记表与取消消息队列，再让一个唯一引擎循环处理提交、推进和取消。网络线程只负责等待或发送对应请求事件，不能直接同时修改页池。即使还不用 GPU，也能练出真实框架需要的控制结构。

## 第十六课：重试、超时与预算为什么必须分层

### 16.1 连接超时、读取超时与任务截止时间

连接超时限制建立网络连接的等待；读取超时限制某段读取等待；任务截止时间限制整个业务请求允许持续多久。一次流式响应不断产生少量字节，可以没有触发读取超时，却仍超过总任务时间。

设备执行也可能有自己的监控或故障判断，但不能把前端超时直接当作设备已停止。上层超时后需要发出取消或放弃等待，底层仍按资源完成协议清理。没有这一步，客户端早已离开，服务却继续生成大量没人需要的输出。

在课程实验中，应为每层明确计时起点和结束条件。不要把所有 timeout 参数设成相同数字就以为合同一致；它们约束的阶段可能完全不同。

### 16.2 重试会放大负载

一个服务变慢时，如果所有客户端立即重复发送同样请求，新增工作会让服务更慢，触发更多重试。这种反馈不依赖复杂模型，普通队列也会出现。恢复策略必须考虑整体负载，而不只是单个请求“再试一次可能成功”。

退避让重试间隔增长，随机抖动避免大量客户端在完全相同时间一起重试。但它们只缓解时间聚集，不自动解决重复业务任务。若需要避免同一请求被重复执行，还要建立幂等身份与结果处理协议。

对于推理生成，即使重复执行没有外部写入副作用，也会消耗算力和 API 费用，还可能返回不同随机结果。是否允许重试、何时向用户展示结果，应由应用明确决定。

### 16.3 三种预算分别记账

模型调用预算可以限制生成次数或 token 数；调度预算限制某轮安排的工作；恢复预算限制失败后额外尝试或重算。它们不能简单混为一个 max_steps，因为使用者无法判断预算耗尽意味着什么。

一个请求因为多次抢占重算，内部处理的 token 位置总数可能远大于最终 prompt 加 output 长度。如果只统计最终序列长度，就会隐藏恢复开销。相反，向用户展示输出长度时，也不应把重算的内部 token 当作新生成内容。

建议报告分开保留原始输入、已生成输出、重算位置、缓存复用位置和尝试次数。真实 API 的计费口径必须以服务实际响应和文档为准，不能把本课程模拟计数直接解释为费用。

### 16.4 错误分类决定是否重试

参数类型错误应修正输入后再提交；身份或模型版本不兼容应重新建立明确任务；暂时资源不足可以等待或降低负载；可重算执行失败可以在确认状态边界后重试；设备故障可能需要更大范围恢复。

如果代码只有 `except Exception: retry()`，这些情况全部被混在一起。某些错误会永远重复，某些会重复已经发生的效果，某些会把损坏状态带入下一次尝试。分层错误不是为了增加类名，而是为了让恢复动作有真实依据。

## 第十七课：为恢复系统建立一张可审查的责任表

在项目中新增恢复功能之前，先列出每个可变对象的拥有者、修改者、持久化方式和释放条件。例如 output 由引擎追加，客户端只观察；页表由缓存管理更新，runner 按本轮快照读取；RNG 由请求采样消耗；网络事件序号由输出提交逻辑递增。

然后为每条失败边界写明三件事：失败发生前哪些修改已经可见，失败返回后调用方能否重试，重试需要携带什么身份。若某项无法确定，就把它标成不确定状态，不能默认归类为“什么都没发生”。

以模型调用为例，纯前向结果尚未被采样和发送时，重新计算的风险主要是成本与数值路径；采样已经消耗 RNG 后，重新执行需要恢复或保留随机状态；输出已经发送后，再次发送则涉及外部事件去重。相同的函数调用在不同提交阶段，恢复责任不同。

资源释放也要列清楚。取消移除逻辑拥有权，设备完成移除在途使用，缓存淘汰移除缓存拥有权。只有所有合法使用都结束，物理页才可重用。把这些责任集中在同一张表里，能帮助你发现“谁都以为别人会释放”的泄漏，和“两个组件都释放一次”的双重回收。

最后用测试验证责任表，而不是让它停留在设计文档。为每个边界插入一个确定性故障点，执行到那里时中断，再按你的协议恢复。比较不中断基准的最终输出、已提交事件和资源状态，同时记录额外重算工作。

这项验收不是要求所有内部轨迹完全一样。恢复运行可以多出重算事件、等待和抢占计数；必须保持的是你明确承诺的外部结果与资源安全。若契约只保证最终语义而不保证逐 bit 一致，也应在测试和报告里写清楚，不能在失败后临时降低标准。


来源与固定框架对应见 [SOURCES](SOURCES.md) 中 Scheduler、EngineCore 和相关上游测试。进一步的真实源码任务在 [S17](17-source-workbook.md)，复合所有权轨迹在 [S18](18-state-workbook.md)。

还要区分 Python 异常与进程突然消失。正常异常展开时，finally 和上下文管理器通常有机会执行清理；进程被强制终止、机器断电或设备失联时，不能假设同样的代码必定运行。因此跨进程资源不能只依赖某个函数最后一句 release。拥有者身份、租约、心跳或协调服务可以帮助判断资源是否还被合法使用，但超时本身不是旧工作已经停止的证明。尤其在分布式系统中，网络隔离可能让旧 worker 仍继续执行；若新 worker 已被允许接管，迟到旧结果必须通过运行代次或其他隔离令牌拒绝，避免两个拥有者同时提交同一请求的结果。

这个问题可以先用离散事件练习：给请求增加运行代次，重启接管时递增；每份 Work 和结果都携带提交时的代次；处理结果前比较它是否仍属于当前运行。旧代次结果可以记录为迟到观察，但不能修改新运行的输出或释放新运行页面。代次不能替代设备完成等待，却能保护上层状态免受旧消息污染。将这项检查与前面的页面 generation 区分开：前者识别一次请求执行，后者识别一次物理页分配，它们服务于不同生命周期，不能因为都叫版本号就混用。

这些故障应在独立测试实例或离散事件模拟器中注入，并保存每一步状态；共享服务上的真实故障实验必须有明确的运行范围和恢复责任。
