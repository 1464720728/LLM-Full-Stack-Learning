# S05 抢占、取消与故障：让系统在坏情况中仍然前进

先修 S02–S04。一个服务是否可靠，往往取决于资源不足和请求失败时发生什么。只测“两个请求顺利完成”无法证明调度器正确。本章用内存压力、取消、后端异常和重试，检查系统是否泄漏、重复生成、死锁或一直忙却没有进展。

## 1. 资源不足有不同层次

请求进入系统前就可能永远放不下。例如池总共能容纳 8 个输入位置，但单请求提示有 10 个位置，而且没有 offload/滑窗机制；继续排队不会创造容量，应在 admission 前拒绝并解释约束。另一类请求单独可以放下，但与别人一起时不够；可以等待、抢占、减少并发或换执行位置。

还有临时工作区不足：KV 预算看似足够，某个 prefill shape 需要更大的 attention 临时张量，导致实际分配失败。不能只减 KV 上限就认为解决了所有 OOM。模型加载、编译/图捕获、首次请求、稳态 decode 各阶段的内存峰值可能不同。

本教学引擎只管理固定 token 页；在 submit 时检查 `prompt + max_new_tokens - 1` 是否超过全池容量。它是保守的完整请求上界，不代表生产框架必定预留所有未来 token。请求间的竞争在 step 时处理。

## 2. 三种常见应对方式

等待保持已有状态不变，等别人结束后继续；重计算抢占释放某请求的 KV，保留输入与已生成 token，稍后从可用前缀重算；换出把状态转移到 CPU 或其他设备，恢复时拷回。三者有不同代价：等待增加延迟，重计算消耗算力，换出消耗容量和带宽。

简单比较：某请求有 2 GiB 状态，链路有效 20 GB/s，仅单向搬运的理想传输时间约 107 ms，换出再换入至少约 214 ms，再加排队和同步。如果重算只需 50 ms，重算可能更便宜；若重算需 2 s，换出可能更合理。这个判断依赖实际形状与链路，不是固定“CPU offload 更省”或“重算更快”。

抢占谁也有策略。最新请求可能已经花了很大 prefill 成本；最老请求可能快结束，释放它会损失进度；最大状态请求释放最多，但恢复最贵。生产策略常用近似规则，初学实现先保证可终止和可解释，再优化成本。

## 3. 重算不能重复输出

假设提示 `[1,2]`，已输出 `[3,4]`，计算到位置 3，也就是 `[1,2,3]` 的状态。抢占后 computed 退回 0，但 output 仍是 `[3,4]`。恢复过程中，先重算 `[1,2]` 不应再次向客户端输出 3；继续重算 3 也不应再输出 4；只有追赶到完整已知上下文 `[1,2,3,4]` 后，才采样新 token 5。

所以条件必须是“computed 等于当前完整 context 长度”才产生新的输出，而不能写成“prefill 完成就采样”。还要保留每请求 RNG 状态。恢复时重新用同一个 seed 从头初始化 RNG，会重复消费最初随机数，后续采样流与未抢占时不同。

查看 `Engine._preempt_for_progress`：它释放 victim 表，保存 prompt、output 和 rng，将 computed 置零并重新等待。查看 `step` 的 catch-up 注释，再运行：

```bash
python -m labs.serving.experiments --lab preemption
python -m unittest tests.test_serving_core.EngineTests.test_preemption_progress_and_no_duplicate_output -v
```

验收输出 A=`[5,6,7,8]`、B=`[9,10,11,12]`，即使发生抢占也不能多、不能少、不能重复。

## 4. 防止“刚抢占又立即招回来”

如果内存满时抢占 B，下一轮开始又因 max_sequences 还有名额把 B 立即招回来，可能恢复到同一困局。程序看起来一直在调度，计数器增加，实际 token 数不增加，这叫活锁。死锁是完全无法前进；活锁是动作持续发生却没有有用进展。

本实现只在整轮没有计划时，释放较年轻请求，临时降低活动上限，让保留下来的请求先取得进展。这个策略偏保守，并不是高吞吐调度器。它的优点是容易用不变量与有限迭代预算检查。`run(max_iterations=...)` 是测试护栏，超限要抛错而不是无限挂住。

更成熟的设计可以让等待队列区分初次请求与被抢占请求，采用冷却时间、资源保留或预估完成成本。但“加 sleep”不是逻辑修复：它可能降低 CPU 占用，却不保证资源关系发生变化。

## 5. 取消是一条跨组件协议

用户取消后，前端不再需要输出；调度器应阻止后续调度；Runner 可能仍在执行已提交批次；缓存管理器要等安全时刻回收；监控需要区分取消和正常完成。取消信号必须带 request ID，不能只带旧批次行号。

取消通常应幂等：第一次成功改变状态，第二次不重复释放。对已完成请求的迟到取消不应抹掉完成结果。对于排队请求，删除队列项就可能足够；对运行中请求，必须协调在途计算。真实 vLLM EngineCore 已核实代码在模型结果处理前处理 abort 队列，说明结果回写顺序是明确设计的部分。

不要把 HTTP 客户端断开自动等同于 GPU 已停止。反向代理、SDK 和服务端可能分别检测断开；一些系统会继续计算直到某个边界。测“取消释放时间”时，要记录取消发送、服务端接收、请求移除、页可复用四个时刻。

## 6. 错误恢复要保留可诊断性

本实现捕获后端异常后，将请求标为 error，保存异常类型，释放引用，再继续其他请求。它不把完整异常和敏感输入原样发给客户端。线上系统应把详细堆栈放入受控日志，并返回可关联的错误 ID。完全吞异常只会让用户看到空输出，无法分辨模型拒答、长度为零还是执行故障。

需要区分可重试和不可重试。输入 shape 不合法，重复发送不会变合法；瞬时资源拥挤可以排队或退避；GPU illegal memory access 可能使进程不可信，应按设备故障策略重建。不要无限重试，尤其是工具执行或计费请求可能重复产生外部副作用。

## 7. 练习与参考答案

1. **不可行请求。** 池 4 页、每页 2，提示长 6、最大输出 4。需要缓存最多 9 个位置，所以本引擎应拒绝。若输出上限 3，最多 8，可以进入。解释最后输出不计算为何影响上界。
2. **恢复 RNG。** 温度改为 0.8，对比充足页和受压抢占两种配置。参考解法：相同 request seed 但保留独立 RNG 实例，输出序列应一致；抢占恢复不得重新构造 Request。为重计算过程加入禁止新增 emitted_ms 的断言。
3. **取消时刻矩阵。** 分别在 pending、waiting、running、finished 调 cancel，检查终态与 free 页。pending 的模拟到达时刻在本实现被调整到取消时刻以避免负时延，这是一项教学约定，不能直接作为生产事件语义；若改为保留原 arrival，应把预到达取消的 latency 标为未定义。
4. **构造活锁。** 临时删掉抢占后的 max_sequences 限制，使用 preemption 实验，设置迭代上限 100。应能观察反复 preempt/admit。修复后不仅测试完成，还统计每个请求的 generated count 单调增加、抢占次数有限。
5. **后端隔离。** `fault_injection` 中 rid=bad 的 prompt 首位是 9，触发异常；good 应正常结束。若坏请求仍占页，检查 `_finish` 所有出口。验收：error 数 1、finished 数 1、缓存关闭时所有页归还。
6. **设计有限重试。** 写一个最多重试 2 次的后端包装，第一调用抛瞬时异常，第二成功。答案必须说明重试发生在采样前，不能消费 RNG 后再重试；使用明确异常类型，不捕获所有异常当瞬时错误。用计数器断言调用次数，禁止真的 sleep 让测试变慢。

掌握门槛：能解释抢占后 known/computed/output 的关系；能构造并修复活锁；能为取消列出资源回收边界；能把错误分成输入、请求、批次、设备四个等级。
