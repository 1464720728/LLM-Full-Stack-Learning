# S16 综合工程：交付一个能解释、能测试、能诊断的推理系统

本章不是“以后可以做”的项目清单：仓库已经包含可执行参考工程，你需要先复现，再关闭答案独立重做关键模块，最后把同样的方法用到真实框架。完成时应有代码、测试、运行记录、设计解释和失败案例，而不是只有截图。

## 1. 项目A：请求轨迹回放与调度实验台

入口是[`replay.py`](../../labs/serving/replay.py)。它读取固定arrival trace，对不同token预算和调度策略运行同一工作负载，先验证输出等价，再汇总延迟与吞吐。默认trace含短聊天、长文档和后续请求，能够观察混合负载。

```bash
python -m labs.serving.replay
python -m unittest tests.test_serving_projects.ProjectTests.test_replay_outputs_equal -v
```

工程的输入契约是JSON列表，每项含id、prompt整数数组、output上限、arrival模拟毫秒。它不偷偷tokenize字符串，避免长度定义随模型变化。输出显式标注synthetic，包含每请求细节。源代码是一个可读的参考解，不依赖GPU或API。

第一阶段逐个读`compare`：输入校验、配置笛卡尔积、创建Engine、构造Request、run、汇总TTFT、计算输出吞吐、跨配置对照outputs。注意percentile只对有首输出的请求计算，而分母与失败情况还需要报告。第二阶段增加取消事件与SLO goodput，保持原测试通过。第三阶段把arrival改为确定性随机过程或读取真实匿名trace，写清负载分布。

验收标准：总token预算永远不越界；所有终态请求无活动表；固定模型/seed下策略不改变输出；未知ITL不填0；每个失败均保留分类；报告能说明最佳策略依赖哪个目标。

## 2. 项目B：本地服务接口与资源账本

入口是[`mock_server.py`](../../labs/serving/mock_server.py)。在一个终端运行：

```bash
python -m labs.serving.mock_server --port 18081
```

另一个终端运行：

```bash
curl --noproxy '*' -sS http://127.0.0.1:18081/health
curl --noproxy '*' -sS http://127.0.0.1:18081/v1/completions -H 'Content-Type: application/json' -d '{"prompt_token_ids":[1,2,3],"max_tokens":4}'
curl --noproxy '*' -sS http://127.0.0.1:18081/metrics
```

响应应有token_ids `[4,5,6,7]`。接口叫completions只是教学路径，不承诺OpenAI完整兼容：它使用显式prompt_token_ids、不含Tokenizer、不含聊天模板、不提供真正GPU流式生成。一个锁串行保护Engine所有权，避免HTTP线程同时修改页表；它不实现生产连续请求队列。

你要从这里完成一个真实工程升级：把HTTP接收与Engine执行分离。接收线程只校验并入队，单一worker拥有Engine；每请求一个结果队列或future；客户端取消转成一个取消事件；输出线程不直接访问页池。测试并发提交、坏请求、重复取消、服务停止时排空或中断。不要先去掉锁再希望GIL保护复合状态更新。

验收标准：接口输入限制明确；请求ID唯一；后台worker唯一拥有调度状态；断开连接不泄漏请求；历史记录有界；日志不暴露提示/密钥；每次实验可在几分钟内停止并归还资源。

## 3. 项目C：框架源码回归补丁

完成S09后进入[源码工作坊](17-source-workbook.md)。工作坊提供针对固定vLLM快照的新测试文件与安装辅助脚本，目标是验证分块预算和取消幂等，使用真实Scheduler与上游helper；不需要模型权重前向，但测试环境仍需要该版本完整Python依赖及本地模型config。

你的任务顺序是：读测试契约；在独立源码副本复制测试；运行并记录环境；实施一个故意错误的小变异确认测试会失败；撤销变异；实现自己的可解释改动；运行相关回归。变异测试证明测试不是“永远绿”。禁止在正在提供服务的安装目录做这些操作。

真实框架的依赖复杂度本身就是学习内容。CPU标记不代表可以在只装标准库的解释器里运行；测试可能导入torch、平台模块和模型config。没有合适依赖时记录未执行，不把语法检查当成完整通过。

## 4. 项目D：真实硬件证据报告

用S15的一张H100短实验，把项目A中的一个假设拿到真实服务验证，例如小chunk是否改善混合长短请求TTFT，同时是否增加长请求总时间。你需要实际token长度、固定模型revision、镜像digest、图模式、后端、GPU信息、负载和样本数。

可以得出“假设不成立”。例如模拟模型里小chunk改善短请求，但真实Kernel对小shape效率较低，总体更差。这个结果说明模型缺少哪些硬件因素，而不是实验失败。把模拟和实际对照，才是在建立系统工程判断力。

若只有个人PC可用，先完成CPU项目与真实源码测试，再在兼容的本地GPU软件栈做小模型实验；不能把5070Ti数据直接标成H100。H100多卡项目待明确设备窗口时执行，但教学解释与代码不因没占卡而缺省。

## 6. 开源拓展任务如何选

vLLM与SGLang作为主线，先完成固定版本的单请求与调度路径，再学习混合KV管理、PD connector和模型后端。不要同时fork十个框架却每个只读README。FlashInfer/CUTLASS等更底层实现放到算子卷对应任务，带着Runner需要什么布局的问题去读，会比从文件第一行漫游更有效。

EvalScope/Harbor等评测系统作为外部调用链练习：从一个任务出发，记录环境启动、harness选择、模型接口、工具交互、verifier与报告。目标是知道自己改变了一层会影响什么，而不是把某个框架宣称为所有benchmark通用标准。

经典论文如PagedAttention、Orca、DistServe、Sarathi-Serve可以在有代码直觉后阅读。读每篇时写：原瓶颈、关键假设、数据结构、调度策略、实验工作负载、限制条件、今天的源码中哪些思想仍存在。不能把论文峰值加速比当自己的设备保证。

## 7. 综合练习与参考路径

1. **独立重写页池。** 不看kv.py，用单独文件实现create/append/fork/release/check；通过同样边界测试后再比较。验收重点是失败原子性和共享尾页，不是行数少。
2. **新增调度策略。** 实现带等待年龄的decode优先，构造长prefill与持续短请求负载。报告一个改善案例和一个退化案例。只报告赢的图不算完成。
3. **服务并发化。** 按单worker所有权模型改mock_server。参考设计用线程安全Queue收命令，RequestFuture回结果；所有Engine mutation在worker线程，HTTP只读不可变结果快照。
4. **真实源码测试。** 执行工作坊回归，保留原版本通过、故意变异失败、修复后通过三份证据。只给pytest一张绿图不足以证明测试检验了你的机制。
5. **容量预测。** 选一小模型，写预测表再实测。解释误差来自预分配、workspace、图缓存或单位，不能用“框架开销”笼统包掉所有差异。
6. **最终答辩。** 解释一个请求从API到输出的完整路径，然后现场处理：取消、页不足、缓存命中、模型异常、非整块提示五个变化。能够指着代码和测试说明状态转移，才算从“听懂”进入“会做”。
