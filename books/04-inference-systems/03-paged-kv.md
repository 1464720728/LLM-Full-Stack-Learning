# S03 分页 KV：从地址翻译到引用计数

先修 S01–S02、列表与字典、整数除法。本章代码只有 CPU 元数据，但你会真正实现页分配、地址映射、共享、写时复制和回收；这些机制是读懂推理框架缓存组件的基础。

## 1. KV Cache 存了什么

在自回归注意力中，一个历史位置的 K/V 可被后续位置重复使用。若每次都从头计算所有历史投影，会重复大量工作。把各层已经计算的 K/V 留在内存中，新的 query 直接读取它们，就是 KV Cache 的基本思想。

对标准 attention，忽略布局填充，某个请求每 token 的 KV 字节数是 `2 × 层数 × KV头数 × head_dim × 每元素字节数`。2 代表 K 与 V。它不是模型参数量，也不是隐藏维度的简单同义词。GQA 使用更少 KV 头；MLA、滑窗、SSM 和混合层则需要更具体的状态模型，不能无条件套这个公式。

KV 的逻辑坐标是“哪层、哪请求、哪个历史位置、哪个头、哪个通道”。物理实现可把这些维度重排，以适配 Kernel 合并访存和向量化。页管理解决“哪些物理块属于这个逻辑序列”，Kernel 解决“按什么布局读写里面的数值”。只知道 PageTable 还不等于知道 attention Kernel。

## 2. 连续分配为什么浪费

如果给每个请求预留最大上下文 8192，实际只用 100，就有大量预留空间闲置。若按当前长度分配连续区间，增长时可能需要搬家；不同长度请求不断结束，会留下难以拼接的孔洞。

分页把逻辑序列切成固定大小的块，每块独立映射到物理页。例如 block_size=4，序列长度 10，需要三个页。逻辑第 9 个 token（零基位置 8）属于逻辑页 `8//4=2`、页内偏移 `8%4=0`。页表可能是 `[7,2,11]`，所以读取物理页 11 的第 0 行。逻辑相邻不要求物理相邻。

最后一页可能没有填满，这叫内部碎片。长度 10、块大小 4，浪费 2 个 token 槽。很多请求时，块越大通常尾部浪费越大；块越小则页表更长、分配和寻址成本更高。分页不是消灭所有碎片，而是改变空间与管理成本的权衡。

## 3. 手算一座页池

页池有 4 页，每页 2 个位置。A 输入 `[1,2,3]`，占页 0=`[1,2]`、页 1=`[3]`。B 输入 `[8,9]`，占页 2。剩余页 3 空闲。A 再追加 4，只填满页 1，不需要新页；A 再追加 5，才占页 3。

此时 B 结束，页 2 归还；C 可复用物理页 2。A 的逻辑序列并没有移动。你可以用纸画两个结构：`tables={'A':[0,1,3]}` 与 `pages[bid].data`。两者必须同步更新。修改页表不改引用计数，或改引用计数不改页表，都可能潜伏到几百个请求后才出错。

运行：

```bash
python -m labs.serving.experiments --lab cow
python -m labs.serving.experiments --lab allocation_atomic
```

## 4. 引用计数是所有权账本

一页可以被多个请求共享，还可能被前缀缓存持有。它的引用数应等于所有这些拥有者的引用总数。请求结束只删除自己的引用；如果缓存仍然持有，页不会变成 free。反过来，缓存淘汰一个前缀，也不能释放活动请求仍然使用的页。

读 [`kv.py`](../../labs/serving/kv.py) 的 `retain`、`unpin`、`release`。`retain` 要求页面已经有人持有，避免把 free 页从旁边偷偷“复活”。`unpin` 把引用减到 0 时清空数据并放入 free-list。`release` 先移除请求表，再归还它拥有的每个页引用。重复释放必须报错或在上层幂等处理，不能悄悄把计数减成负数。

`PagePool.check` 不相信账本自己宣称正确，它重新遍历全部请求表和缓存条目，计算 expected references，然后逐页对账。这类昂贵检查适合测试和调试，不必每轮生产启用。它能抓到“看起来输出还对，但某页已经泄漏”的错误。

## 5. 写时复制为什么发生在半页

A 已有 `[1,2,3]`，块大小 4；B 从 A fork，二者共享同一页，引用数 2。B 想追加 9，如果直接写共享页，A 会莫名获得 9。正确动作是：为 B 新分配一页，复制原来的 3 个值，把 B 的最后页表项换成新页，减少旧页的 B 引用，再向新页追加 9。

如果共享页已满 `[1,2,3,4]`，B 追加 9 时只需要新建尾页，不必复制满页。因为满页将保持只读，而追加发生在另一个页。这个区别解释了为什么“总是复制所有历史”很慢，也解释了为什么只对未满共享尾页做 COW 是一个合理起点。

真实 KV 复制的数据是张量，可能要异步 GPU copy，并受到流和完成事件约束。本例复制 Python 列表，因此看不到带宽和同步代价。机制相同的部分是所有权转移；不能把列表操作的时间当 GPU copy 成本。

## 6. 分配失败必须是事务

设只剩 1 个空闲页，某次 append 既要复制共享尾页，又要新增两页，合计需 3 页。若先复制一半，再发现不足，必须回滚所有修改，难度很高。更好的入门实现是先计算 needed，确认足够后一次预留全部页，再开始修改。

`needed` 的公式包含两部分：追加后所需总页数减当前页数，再加可能的尾页 COW。`append` 在资源检查前不动原表，失败抛 `OutOfPages`，原 tokens 和 refs 应完全不变。这个性质叫失败原子性。它不需要数据库才能实现；系统内存分配同样需要事务思维。

真实引擎可能不直接预留全部未来生成空间，而按下一轮需要分配；还可能触发缓存淘汰、请求抢占、CPU offload。无论具体策略如何，都要说明“分配失败时哪些状态已经改变、谁负责恢复”。源码里遇到 `None` 返回值，不要只看调用成功路径。

## 7. 页池和 CUDA 内存分配不是一回事

框架往往先在 GPU 上建立大块 KV 存储，再在内部管理 token 页；我们的 free 页归还表示可以被别的请求复用，不一定让 `nvidia-smi` 中的进程显存下降。PyTorch 自身也可能有缓存分配器。因而“请求都结束了，但显存没变小”不能单凭这一点判定泄漏。

检查泄漏应看逻辑可用页、活动引用、缓存保留、内存高水位是否在重复负载后持续增长；必要时再区分 reserved 与 allocated。仅把进程杀掉释放所有显存，并没有定位泄漏根因。

## 8. 练习与答案

1. **地址翻译。** 页表 `[5,2,9]`，block_size=4，逻辑位置 6 和 10 在哪？答案分别是物理页 2 偏移 2、物理页 9 偏移 2。写一个纯函数并测试越界拒绝，不能直接用 Python 负索引允许位置 -1。
2. **碎片计算。** 请求长度 `[1,4,5,8]`，块大小 4，需要 1+1+2+2=6 页，24 槽；有效 18，浪费 6，内部碎片率按分配槽计算是 25%。若除以有效 token 数得到 33.3%，必须明确那是“额外空间相对有效数据”的另一个比例。
3. **COW 手算。** A/B 共享两页，最后页只含 1 个 token，B 追加 5 个 token，块大小 4。需要复制尾页 1 个，加新增 1 个，总计 2 个新物理页；不是 5 页，也不是只 1 页。
4. **故障注入。** 删除 COW 分支后运行 `test_cow_partial_tail_and_release`。预期 A 的 token 被污染。修复后再证明 B 的修改不影响 A、满页仍共享，避免“复制所有页”这种正确却不必要的补丁。
5. **回收压力。** 循环 100 次 create/append/fork/release，结束后空闲页应等于初始总页数。加入随机释放顺序，但固定测试种子。测试失败时打印最小操作序列，而不是整池长日志。
6. **后端接口设计。** 为真实 K/V 提出一个 PageStorage 接口，至少有 allocate、copy、write、read、completion。参考答案应把逻辑引用计数和异步数据完成分开：一个页可有引用但数据尚未就绪，另一个页逻辑释放了但 GPU 仍可能访问。需要事件或 epoch 防止过早复用；只增加一个布尔 `ready` 不足以描述跨流依赖。

掌握门槛：能够独立写出分页地址翻译、失败原子 append、尾页 COW；能画出请求结束但缓存保留时的引用图；能解释为什么显存仪表不下降不一定泄漏。
