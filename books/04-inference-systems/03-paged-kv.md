# S03 分页 KV：从一个 token 的地址到可证明的资源所有权

这一章解决一个具体问题：许多请求的上下文长度不断增长，模型需要保留各自的历史 K/V，怎样让它们在有限内存里增长、共享和释放，而不把别人的历史读进自己的回答？

“分页”不是一个神奇加速词。它首先是一套地址映射与所有权管理方法。只有把逻辑位置、物理页号、页内槽位、引用计数和有效长度全部定义清楚，你才能理解 PagedAttention 为什么需要页表，为什么共享前缀后追加可能必须复制，以及为什么一个分配失败不能留下半张新页表。

本章先用 token ID 代替真实浮点 K/V 作为可手算载荷，直接对应 `labs/serving/kv.py`。这不是数值 attention 实现；S19 再把真实 K/V 数组放进相同所有权结构。两层分开后，你可以先证明“读的是正确位置、不会释放仍在使用的页”，再证明“这些位置中的数值产生正确 logits”。

## 第一课：为什么历史 K/V 需要长期保存

### 1.1 从单次矩阵计算走到持续生成

在普通一次性函数中，输入矩阵经过运算产生结果，临时数组可以在函数结束后释放。自回归生成不同：下一轮 query 仍要读取过去 token 的 key 和 value。过去的 K/V 因而成为跨轮状态，而不只是一次矩阵乘法里的临时值。

设一层 attention 使用两个 KV 头，每个头维度四，已经处理五个 token。一份 K 的形状可以理解为 `[5,2,4]`，一份 V 同样如此。两个数组共五乘二乘四乘二，等于八十个数。如果每个数占两字节，纯载荷为一百六十字节。真实模型有许多层，必须再乘层数；这里故意选很小的数字方便你数清每个轴。

token ID 本身只是一个整数，K/V 是经过 embedding、投影和上游层计算得到的浮点向量。把 token ID 缓存起来，不能代替保存真实 K/V。当前 PagePool 用 ID 作为元数据演示，是为了检查顺序与所有权；不能因为变量叫 kv 就声称它已经节省真实模型的重算。

### 1.2 为什么通常不缓存全部 query

下一轮使用的是新位置自己的 query，过去 query 一般不再用于下一位置的标准自回归 attention。过去 K/V 却会持续被新 query 读取。因此典型 KV cache 保留 K 和 V，而不是把 Q/K/V 三者一律长期保存。

这不是所有网络结构的普遍定律。不同注意力变体、状态空间模型或混合缓存会保存不同状态。阅读真实框架时，应先确认模型结构需要什么，而不是把“每层两个相同形状数组”当作永远适用的假设。S13 的简单容量估算也明确限定了普通均匀 KV 头结构。

### 1.3 增长与未知结束时间

请求开始时，prompt 长度已知，最终输出长度却可能只知道一个上限。按最大可能长度一次分配连续大数组，容易为许多实际很短的请求保留大量未使用空间；按当前长度精确分配，再每次增长时搬到更大数组，又可能反复复制。

还有并发问题。A 占用一段连续空间后释放，中间留下一个洞；B 的新需求可能总字节数不大，却找不到足够长的连续区间。这是理解外部碎片的入口：空闲总量足够，不代表某种连续分配要求能满足。

分页把长期状态拆成固定大小块，请求通过页表把若干不必相邻的物理块串起来。它不消除所有浪费，也不让所有访问免费；它改变了分配和映射的单位，让增长、共享与回收更灵活。

## 第二课：先用书页编号理解逻辑地址和物理地址

### 2.1 三个坐标不能混用

逻辑 token 位置是请求内部的第几个位置；逻辑页号是这个位置属于请求的第几块；物理页号是内存池中实际存放数据的哪一块。页内槽位则是该位置在块里的偏移。

例如 block_size 为四，请求 A 的页表为 `[7,2,9]`。逻辑位置六先做除法：六除四商一余二。逻辑页号一对应页表第二项物理页二，因此真正读取物理页二的槽位二。你不能把位置六直接当物理页六，也不能把逻辑页号一当物理页一。

Python 中 `divmod(position, block_size)` 同时给出商与余数。它把一个长序列的索引拆成“第几页”和“页内第几个”。这个转换是分页寻址最基本的一步；后续 kernel 再复杂，也需要以某种形式完成同样的映射。

### 2.2 一个完整地址表

仍取 block_size 四，A 页表为 `[7,2,9]`，有效长度十。前四个逻辑位置在物理页七，中间四个在物理页二，最后两个在物理页九。物理页九剩下两个槽位无效，不应参与 attention。

| 逻辑位置 | 逻辑页 | 页内槽位 | 物理页 |
|---:|---:|---:|---:|
| 0 | 0 | 0 | 7 |
| 3 | 0 | 3 | 7 |
| 4 | 1 | 0 | 2 |
| 6 | 1 | 2 | 2 |
| 7 | 1 | 3 | 2 |
| 8 | 2 | 0 | 9 |
| 9 | 2 | 1 | 9 |

把页表改成 `[2,9,7]`，请求内部顺序不会自动跟着物理页号排序。正确读取必须沿页表顺序，而不是把页面按编号从小到大拼起来。很多错误的教学实现恰好总按顺序分配物理页，使这个缺陷被掩盖；测试应故意制造非连续、乱序的物理映射。

### 2.3 地址最终如何变成字节偏移

假设每个物理页保存 block_size 个位置，每个位置有 H 个头、每头 D 个数，元素字节数为 b。采用简单连续布局时，一份 K 的某元素偏移可以写成：先到物理页起点，再到页内 token，再到 head，最后到维度。

用整数例子：物理页二，block_size 四，H 为二，D 为三，槽位一，头一，维度二。按 `[page,slot,head,dim]` 行优先布局，元素下标为 `(((2*4+1)*2+1)*3+2)`，等于五十九。若每元素两字节，相对数组首地址的字节偏移是一百一十八。

这个公式依赖具体布局。真实 kernel 可能采用不同的维度顺序、打包方式或向量化布局，不能把本例当作所有框架统一 ABI。学习目的在于训练你从 shape 与 stride 推导地址，而不是记住某一串乘法。

## 第三课：分页节省什么，又付出什么

### 3.1 内部碎片

固定块大小使每个请求最后一页可能没填满。block_size 四，有效长度五，需要两页，总容量八，浪费三个位置。这叫内部碎片：已分配块内部的未使用容量。

长度分别为一、四、五的三个请求，总有效位置十，却分别需要一、一、两页，共十六个槽位，未使用六个。若块大小改为二，它们分别需要一、二、三页，总容量十二，未使用两个。较小块减少尾部浪费，但增加页表条目与管理工作。

不能据此断言块越小越好。GPU 访存、kernel 的 tile 组织、调度元数据、缓存匹配粒度和通信都会受到块大小影响。理论碎片只是选择参数的一个维度，真实性能还需实际验证。

### 3.2 外部碎片与不连续物理块

固定块池可以从任意空闲物理页中组合出请求需要的逻辑页序列，因而不要求整个请求占一段连续大空间。只要有足够数量的块，就可以构造页表。这改变了大块连续分配的困难。

但更底层的设备分配器仍可能有自己的碎片问题。如果页池本身不是一次连续预分配，而是不断申请不同大小设备内存，仍要考虑下层分配行为。课程 PagePool 在启动时建立固定页面对象，主要研究池内分配，不宣称解决整个 GPU 内存分配系统的所有问题。

### 3.3 额外成本

分页读取需要页表查找，可能产生不连续物理访问；共享状态需要引用计数和复制策略；每次增长都要计算需要的新页；缓存淘汰需要维护拥有者。灵活性来自更多明确的元数据和协议，不是凭空消除成本。

为什么仍然值得？因为推理请求长度差异大、生命周期不一致、前缀共享机会多，灵活管理长期 KV 往往比给每个请求预留最大连续数组更合适。这个判断来自工作负载与设计权衡，不能只用一个“分页一定更快”的口号概括。

## 第四课：PagePool 中每个容器的责任

### 4.1 pages：物理页面集合

`self.pages = [Page() for _ in range(pages)]` 创建固定数量的 Page 对象。列表下标就是物理页 ID。每个 Page 有 data 和 refs；data 在本章保存 token 元数据，refs 表示当前合法拥有者数量。

这些 Page 对象不是请求私有的。不同请求可以通过页表引用同一物理页，前缀缓存也可以持有它。正因为数据与请求分离，才有共享和复用的机会；也正因为如此，释放和修改必须遵守所有权规则。

### 4.2 free：当前可分配物理页

free 最初包含全部页 ID。代码使用 heapq 维护它，使分配时优先取较小编号。这主要让教学轨迹容易复现；选择最小页号不是分页正确性的必要条件。

自由页必须满足 refs 等于零，而且 data 已清空。页号不能在 free 中出现两次，否则两次分配可能把同一物理页交给两个互不知情的请求。检查 free 是否包含重复项，是发现双重释放的一种直接方法。

堆不是普通排序列表的同义词。heapq 保证根元素最小，并维护适合高效取最小值的结构，但内部整个列表不一定始终全局排序。不要在调试时看到 free 的显示顺序不是完全升序，就误以为池已损坏；应检查堆语义与唯一性。

### 4.3 tables：请求到逻辑页表的映射

`tables[rid]` 是该请求按逻辑顺序排列的物理页 ID 列表。它只描述映射，不复制物理页面内容。两个 tables 项可以包含相同页号，那表示共享同一个 Page。

`create` 先验证 rid 是非空字符串且尚不存在，然后建立空列表。空页表本身不分配任何物理页。这个设计允许“请求已经拥有一个缓存入口，但尚未处理任何 token”的状态，与接纳后首次计算之前的生命周期一致。

`tokens(rid)` 沿页表顺序把每页 data 展平，是一个易读的慢观察函数。它创建新列表，适合测试和手算，不代表生产 attention 会先把所有页复制成一个连续 token 数组再运行。真实数值参考中的 gather 也有类似的验证用途，而高性能 kernel 通常直接按映射读取。

### 4.4 refs 的计数单位

refs 数的是合法引用，不是页面中 token 数，也不是引用它的 Python 对象数量。一个活动请求页表里的一项贡献一次引用；一个缓存条目持有该页也贡献一次引用。如果两个缓存条目都保存包含该页的前缀，它们各自的拥有关系也必须计入。

所以 refs 可以大于活动请求数。请求全部结束后，页仍可能因缓存拥有而保持正引用。只要账本一致，这不是泄漏。相反，refs 为正但找不到任何活动表或缓存拥有者，才说明存在丢失的引用释放。

## 第五课：先推导 needed，再执行 append

### 5.1 不共享时需要多少新页

设请求已有 size 个有效位置，本次追加 count 个，块大小为 B。追加后所需逻辑页数是向上取整 `ceil((size+count)/B)`。在整数运算中，可以用 `(size+count+B-1)//B`。减去当前页表长度，得到正常增长需要的新页数。

例如 B 为四，当前 size 为三、页表长一，追加一项。新总长度四，所需页数一，差为零：可以填满已有尾页。追加两项时，新长度五，所需页数二，差为一：尾页填一项，再申请一个新页。

空请求追加五项时，size 为零、页表长零，新总页数二，因此申请两页。count 为零时直接返回零，不能因为共享尾页就无端触发复制；没有写入就没有 COW 必要。

### 5.2 为什么共享的半满尾页要额外一页

假设 A、B 共享一个只含三项的尾页，块大小四。B 要追加一项，普通增长公式得到零新页，因为逻辑总长度仍能放进一页。但 B 不能直接修改共享尾页，否则 A 也会看到第四项。

因此需要额外申请一页，把旧尾页有效内容复制过去，再在新页上追加。逻辑页数没有增加，物理页总用量却增加一。这就是 needed 中 copy_tail 项的来源。忽略它，会在逻辑容量看似足够时覆盖别人的状态。

只有三个条件同时满足才需要这项额外页：页表非空；尾页未满；尾页引用数大于一。尾页已满时，新 token 本来就进入新页，不会修改旧共享页；尾页只有自己一个引用时，可以安全原地追加。

### 5.3 组合例子

B 为四，当前长度七，对应两页，尾页三项且被共享。本次追加六项，新总长度十三，需要四个逻辑页，正常增长增加两页；共享半满尾页还要复制一页，总申请三页。

分配之后，旧完整前页仍共享；旧半满尾页被新副本替换；新副本先填入一项变满；剩余五项进入两个新页。若只申请两页，代码会在追加中途发现没有可用页；这时若已经改写尾页和 computed，就很难回滚。

把公式与实际逐 token 填页过程对照，是验证分配算术最可靠的办法。不要只对一个恰好整除的输入测试，因为共享尾页与跨页追加的组合才最容易暴露差一错误。

### 5.4 needed 必须是无副作用查询

调用 needed 应当只告诉你需要多少页，不提前从 free 取页，也不修改 refs。调度器可能为了判断可行性调用它多次。如果一次查询就消费资源，第二次查询的结果会受第一次影响，整个预算逻辑会非常难以推理。

本实现验证 count 为非负整数，再读取页表与页面长度计算结果。你可以连续调用三次，检查 pages、free、tables 完全不变。这类测试保护“查询函数只是观察”的接口合同。

## 第六课：append 为什么要先完整预留

### 6.1 失败原子性的具体含义

本章说 append 失败原子，不是说它在多线程环境中自动安全，也不是说任意硬件故障都能回滚。这里的明确承诺是：当所需自由页不足而抛 OutOfPages 时，原来的页表、页面数据、引用计数和自由页集合都保持原状。

这个范围非常重要。单线程代码也会需要失败原子性，因为异常可能发生在部分状态修改之后。并发安全则还需要锁、原子操作或其他同步协议，两者不能混为一谈。

预留流程先算 count，再比较自由页数量。如果不够，立即抛异常，没有触碰旧数据。只有确认足够，才从堆里一次拿出全部所需页面，把它们设为一个引用，并用迭代器 available 按后续需要消费。

### 6.2 分配之后的状态

新页刚从 free 移出时，refs 设为一，表示接下来将由当前请求使用。在本同步函数内部，它们暂时保存在 reserved 中，还没有全部接到 tables。外部观察者不应在这个中间阶段任意读取不变量；如果要并发访问，就必须给整个修改过程明确同步边界。

这说明“每一行执行后全局不变量都必须成立”不是所有实现的要求。有些操作在事务内部经历暂时状态，只在成功返回或明确失败返回时保证合同。代码审查时要辨认可观察边界，而不是把内部过渡状态误判为已经发布的状态。

### 6.3 复制共享尾页的四步

若尾页未满且共享，取一个 reserved 新页；把旧 tail.data 复制到新页；把当前请求页表最后一项改为新页号；最后释放当前请求对旧页的一个引用。

为什么复制 data 使用 `copy`？因为如果只是让新页 data 指向旧列表，两个 Page 虽然物理 ID 不同，内部载荷仍然共享。随后向新页 append 会继续影响旧页，COW 就只复制了外壳。这个错误必须用“修改新分支后旧分支不变”的测试发现。

为什么只 unpin 一次？当前请求从旧页转移到新页，只失去自己的一份拥有关系；其他请求或缓存仍然持有旧页。把旧页 refs 直接设为零，会把仍在使用的状态错误放回自由池。

### 6.4 逐 token 填页

遍历 values 时，若页表为空或尾页已满，就从 available 取下一页并追加到页表；随后把 token 追加到当前尾页 data。这个顺序保证每个 token 恰好进入一个有效槽位。

最后断言 available 已耗尽，检查 needed 的算术与实际分配路径一致。如果还有预留页没用完，说明公式多算；如果中途迭代器耗尽，说明公式少算。两种情况都应作为实现错误调查，而不是静默把多余页丢掉或临时再申请。

生产实现可能以批量张量拷贝代替 Python 逐 token 循环，但合同没有变化：追加顺序必须保留，旧有效数据不能被改写，所需新页必须完整可得，结果页表必须对应新的逻辑长度。先验证慢而清楚的参考，有助于以后优化时保留正确性判据。

## 第七课：fork、retain、adopt 与 release 的逐行责任

### 7.1 fork 只共享映射，不复制全部历史

`fork(parent,child)` 先确认 parent 存在，再确认 child 是新的合法身份。然后复制父页表列表，增加这些物理页的引用，最后把新列表登记为 child 的页表。

复制页表列表的目的是允许 child 后续替换自己的尾页映射，而不修改 parent 的列表。物理 Page 的内容仍然共享。这种“复制小映射、共享大载荷”的设计，正是 COW 能够节省大量复制工作的基础。

验证顺序也有意义。若先 create(child)，再发现 parent 不存在，会留下一个空 child 表。虽然没有分配物理页，它仍然污染了身份空间和活动表不变量。当前实现先检查所有必要条件，避免这种部分副作用。

### 7.2 retain 为什么先汇总再修改

retain 接收一组页号，先验证每个 ID 是合法范围内的非负整数，再用 Counter 统计重复出现次数。随后检查所有页当前都不是自由页，全部通过后才逐页增加计数。

为什么不能边遍历边加？例如输入包含一个有效页和一个自由页，如果先给有效页加一，再在第二项报错，就泄漏了第一项引用。调用方看到 retain 失败，往往不会知道自己还欠一次 unpin。完整预检避免这种半成功状态。

Counter 的作用是明确处理同一页在输入列表中多次出现的情形。一般请求页表不允许重复同一个物理页，但更底层的引用操作可以按出现次数增加或减少。不同接口的合同不一样，不能因为 retain 能统计重复，就认为 adopt 也应该允许一个请求重复映射同一页。

### 7.3 adopt 的特殊合同

adopt 把一组已经存在的物理页附加给一个空请求页表，常用于前缀缓存命中。它要求目标表为空，防止无意覆盖已有拥有关系；要求页号不重复，防止同一逻辑请求把相同物理块当成两个不同历史块。

它先调用 retain，只有全部引用增加成功后，才把页号列表写入 tables。若 retain 因自由页或非法 ID 失败，目标空表保持不变，其他页计数也不变。这个接口是前缀缓存与活动请求之间的所有权交接点，不能只看它返回了一个长度就认为共享已经成功。

### 7.4 unpin 与 release

unpin 先统计本次要减少的引用数，再检查每页现有 refs 是否足够。通过后逐页减计数；某页降到零时，清空 data 并把页号放回 free。若现有引用不足，应当报错，不能把负数引用当作“已经空了”继续运行。

release 从 tables 移除请求的页表，并对其中所有页 unpin。它表示这个请求不再拥有任何活动页引用，不表示其他拥有者失效。如果前缀缓存仍持有某页，页保持有效；如果没有任何拥有者，它才归还自由池。

重复 release 不是本接口定义的幂等操作，因为第二次已经找不到请求表。请求级 cancel 的幂等性由 Engine 在更上层检查终态实现。把幂等责任放在正确层级，可以避免底层资源错误被“反正重复也没事”的处理隐藏。

## 第八课：完整手算一次共享、分叉、追加与释放

建立四页、每页四槽的池，页号为零到三。A 追加 `[1,2,3]` 后，A 页表为 `[0]`，页零 data 为三项、refs 为一，自由页为一、二、三。

fork A 到 B 后，A 与 B 的页表是两个不同列表，但内容都是 `[0]`。页零 refs 变成二，载荷仍只有一份。此时两个请求读到同样历史是正确共享，不是串话；关键在于未来写入时是否隔离。

B 追加 9。普通逻辑增长无需第二页，但共享半满尾页触发 COW。needed 返回一，从 free 取页一；复制 `[1,2,3]` 到页一；B 页表变成 `[1]`；页零 refs 减为一；随后页一追加 9，变成 `[1,2,3,9]`。

| 时点 | A页表 | B页表 | 页0数据/引用 | 页1数据/引用 |
|---|---|---|---|---|
| A追加后 | [0] | 不存在 | [1,2,3] / 1 | [] / 0 |
| fork后 | [0] | [0] | [1,2,3] / 2 | [] / 0 |
| B追加后 | [0] | [1] | [1,2,3] / 1 | [1,2,3,9] / 1 |
| 释放A后 | 不存在 | [1] | [] / 0 | [1,2,3,9] / 1 |
| 释放B后 | 不存在 | 不存在 | [] / 0 | [] / 0 |

释放 A 不应影响 B，因为 B 已经拥有独立副本。释放 B 后全部页自由。你可以直接运行：

```python
from labs.serving.kv import PagePool

pool = PagePool(4, 4)
pool.create("A")
pool.append("A", [1, 2, 3])
pool.fork("A", "B")
assert pool.tables["A"] is not pool.tables["B"]
pool.append("B", [9])
assert pool.tokens("A") == [1, 2, 3]
assert pool.tokens("B") == [1, 2, 3, 9]
pool.check()
pool.release("A")
assert pool.tokens("B") == [1, 2, 3, 9]
pool.release("B")
pool.check()
assert len(pool.free) == 4
```

把池改成只有一页，会发生什么？fork 本身不申请新页，所以仍能成功；B 追加时需要 COW 页，但没有自由页，OutOfPages 应在任何旧状态改变前抛出。A、B 仍共享原来三项历史，refs 仍为二。这是一个专门验证失败路径的反例。

## 第九课：不变量怎样把“看起来正常”变成可验证正确

### 9.1 逐页核对所有权账

check 首先从所有请求页表统计每个物理页被引用的次数，再加上缓存条目提供的引用次数，得到 expected。随后逐页比较 page.refs 与 expected。它不依赖你“记得调用过 release”，而是从当前可观察结构重新计算账本。

这是一种很有价值的验证思想：存储字段是实现维护的快速结果，独立遍历结构计算的值是慢参考。两者一致并不能证明所有语义正确，但能抓住大量漏加、漏减和重复拥有错误。不能用 page.refs 自己再算出同一个 expected，那会失去独立性。

### 9.2 自由集合与引用的双向关系

`(bid in free) == (page.refs == 0)` 同时要求两个方向：零引用页必须自由；自由页必须零引用。只检查其中一个方向不够。漏回收会违反前者，提前回收会违反后者。

还要求自由页载荷为空，避免读取或调试时把旧请求残留元数据当作有效状态。真实数值池为了性能可能不清零全部浮点数组，改由有效长度和 mask 防止读取无效槽；S19 会明确区分逻辑清空与物理数值残留。

### 9.3 页表内部结构

同一请求页表不能重复同一物理页，否则逻辑历史可能重复读取同一段数据。除了最后一页，前面的页都应满，因为 append 按顺序填充，不允许中间留空洞再追加后页。

这个“中间页满”的不变量依赖当前布局设计。如果未来支持稀疏保留、滑动窗口或不同页组，规则会改变；你应重新定义逻辑位置映射，而不是让旧 check 被无理由关闭。检查失败通常是在提醒设计假设已经变化，不能只为了让测试绿而删掉断言。

### 9.4 状态正确不等于数值正确

所有引用和长度都正确，也可能复制错一行 K/V 或错误解释 head 轴。元数据测试只能证明哪些位置应被访问，不能证明其中浮点数的数学含义。S19 的 full-forward 与 cached-forward 对照补上另一层证据。

相反，某一次数值输出恰好相同，也不能证明所有权正确。如果两请求输入相同，错误共享不会立即改变结果；如果错误槽位恰好是零，越界读取可能被隐藏。因此需要结构不变量和数值反例共同覆盖，不能只选择一种测试风格。

## 第十课：三种容易被随机测试漏掉的失败

### 10.1 复制了页对象，却没有复制载荷

错误实现把新页的 data 直接赋值为旧页的 data。两个 Page 看起来不同，tables 中的物理 ID 也不同，refs 甚至全部正确；但是内部列表仍是同一个对象。B 追加后，A 的数据也发生变化。

如果测试只比较页号是否不同，就会误判通过。正确的负向用例应该保存 A 的内容快照，触发 B 的 COW，再检查 A 内容完全不变；还可以检查两个 data 列表不是同一对象。行为检查比仅检查身份更重要，因为生产载荷可能是张量 view，Python 对象不同却仍共享底层存储。

修复是复制真正需要隔离的载荷，而不只是复制描述它的外层结构。在 NumPy 或 GPU 张量中，需要核对 clone/copy 与 view/切片的实际语义。一个同形状的新包装对象，不一定代表独立内存。

### 10.2 分配不足时已经改了一半

错误实现边追加边取新页，直到 free 空了才抛异常。假设当前尾页还剩一槽，本次追加六项，却只够一张新页。它可能先把尾页填满，再把新页填满，最后才发现仍剩一项无处放。

此时异常返回后，调用方无法把请求当作“此次操作没有发生”。如果 computed 没增加，页面却多了五项，页表内容与进度矛盾；如果 computed 已部分增加，接口又没有报告实际成功数量。后续重试整个六项会重复数据，重试剩余部分则需要知道未公开的内部进度。

你可以设计支持部分成功的 API，但必须把合同改成明确返回已写入数量，并让上层处理；不能把一个声称全成全败的接口实现成偶然部分成功。当前课程选择完整预留，使调用者只需处理成功或完全未修改的 OutOfPages。

### 10.3 非法 retain 导致引用泄漏

输入页号列表中第一项合法、第二项是自由页。若代码一边验证一边增加，第一项被加一后第二项报错。调用方看到失败，认为没有获得任何引用，于是不会释放第一项多出来的拥有权。

这个错误在普通“输入全部合法”的测试中永远看不见。要覆盖它，必须故意让错误发生在列表中间或末尾，并在异常后比较完整快照。类似设计适用于批量删除、批量更新和多资源申请：越是批量操作，越要检查中途失败是否污染已经处理的部分。

当前 retain 先收集 counts，验证全部页面，再执行增加。你应当理解它保护的是异常返回时的状态，不是把所有操作神奇地变成跨线程原子指令。

## 第十一课：从同步 Python 池走向 GPU 页池

### 11.1 逻辑释放与设备完成

Python 参考代码中的 append、tokens 和 release 都同步完成。真实 GPU kernel 启动通常是异步的：CPU 发出命令后可以继续运行，但设备可能还在读取某个页面。此时如果 CPU 把页立即放回 free，另一个请求可能在旧 kernel 读完前覆盖它。

引用计数只知道“软件对象还拥有多少引用”，不自动知道设备指令是否已经完成。生产设计需要把在途设备使用也纳入生命周期，或采用完成事件、流顺序、延迟释放队列等机制。不能把 CPU reference 的释放时机直接照搬到异步环境。

一个最小时间线是：时刻一提交 A 读取页零；时刻二 CPU 收到取消；时刻三把页零分给 B 并写入；时刻四 A 的 kernel 才真正读取。A 可能读到 B 的数据。正确方案应保证页零在所有旧使用完成之前不可重新分配，即使 A 已经逻辑取消。

### 11.2 generation 防止页号复用混淆

物理页 ID 会重复使用。今天页三属于 A，释放后可能属于 B。一个延迟到达的事件如果只写“释放页三”，可能错误作用到新的拥有者。给页面分配附加 generation 或使用包含运行版本的句柄，可以帮助识别过期操作。

例如句柄记为 `(page_id=3,generation=8)`，下一次复用后 generation 为九。旧事件携带八，应被识别为针对过去分配的事件，而不是无条件修改当前页。具体机制因框架而异，但问题本身来自身份复用，不是特定语言独有。

本课程 PagePool 没有实现异步句柄协议，所以不能声称它能处理任意乱序设备完成消息。学习时可以用一个纯 Python 事件队列模拟这个反例，先理解为什么只有物理编号不够，再到真实框架寻找对应生命周期字段。

### 11.3 页数据与页表也有各自的可见性

不仅 K/V 载荷可能在设备上使用，页表本身也可能被复制或读取。CPU 更新页表后，必须确保下一次 kernel 看到与本次输入匹配的版本。若页表更新与数据复制的顺序相反，kernel 可能看到新映射却读到尚未准备好的载荷。

因此真实执行合同需要同时描述：何时分配页面、何时写入 K/V、何时发布页表、哪个流等待哪个事件、何时允许释放旧页。只画“CPU→GPU”一根箭头不足以说明依赖。S06 会把 Work 到设备输入的准备过程进一步拆开。

### 11.4 多层与多种缓存组

实际 Transformer 每层有不同的 K/V 投影，所以不能让所有层共用同一份数值页面内容。实现可以在每页中包含层轴，也可以为不同层或缓存组建立独立数组；关键是模型层身份必须进入寻址语义。

混合模型可能有些层使用普通 KV，有些层使用固定大小递推状态，有些层使用滑动窗口。此时“请求长度每增加一，所有缓存都增加相同字节”的假设不再成立。统一管理器仍可提供抽象接口，但其各组分配规则必须对应真实状态结构。

本章的 PagePool 只有一个同质元数据池，它提供所有权和失败原子性的基础练习。扩展时首先写出每个缓存组的 shape、增长规律、共享条件与释放责任，再决定能否共用同一分配策略。把不同状态强行塞进一个没有语义的“block”名字，会让代码表面统一而实际难以验证。

## 第十二课：十五道逐级练习与完整参考解答

### 练习一：逻辑位置寻址

块大小为四，页表为 `[5,1,7]`，有效长度十一。问位置零、四、十分别落在哪里。答案：位置零在物理页五槽零；位置四在物理页一槽零；位置十在物理页七槽二。位置十一虽然还在已分配尾页容量内，却超出有效长度，不能作为有效历史读取。

完整小函数应同时检查位置范围与页表长度，不能只做 divmod：

```python
def locate(table, block_size, length, position):
    if not 0 <= position < length:
        raise IndexError("position outside valid history")
    logical, slot = divmod(position, block_size)
    return table[logical], slot

assert locate([5, 1, 7], 4, 11, 10) == (7, 2)
```

这里故意没有把完整通用输入验证全部塞进四行示例；作为练习，你应再拒绝非法 block_size 和不够长的 table。核心合同是“已分配容量”不能替代“有效历史长度”。

### 练习二：内部碎片

块大小四，三个请求长度为二、五、八。所需页数分别是一、二、二，总容量二十，有效位置十五，内部未用槽五。块大小二时，页数一、三、四，总容量十六，未用槽一。解释为什么不能仅凭后一组浪费少就宣布它在 GPU 上更快：页表规模、寻址、kernel tile 和缓存粒度也改变了。

### 练习三：无共享追加

已有长度六，块大小四，本次追加一、二、三项，分别需要多少新页？答案依次为零、零、一。已有两页，尾页两项；追加两项恰好填满，追加三项才需要第三页。把“追加非零就一定新建页”写进算法会浪费已有尾部空间。

### 练习四：共享尾页追加

同样已有长度六，但尾页被两个拥有者引用。追加一、二、三项需要多少自由页？答案是一、一、二。前两种都需要 COW 副本，虽然逻辑页数不增加；第三种还要增加一个正常增长页。引用数是否大于一必须参与 needed，不能只看长度。

### 练习五：共享满页

已有长度八，两页都满且被共享，追加一项需要几页？答案一页。旧页不再写入，所以无需复制；新位置进入第三逻辑页。这个例子是对“只要 refs 大于一就复制尾页”的反例，说明 COW 条件必须包含实际写入是否会改变共享页。

### 练习六：零长度追加

共享半满尾页上 append 空列表应该怎样？答案是不改变页表、data、refs 和 free，也不需要新页。写测试前保存四类状态，再执行 append。若算法仅看共享条件就复制，会为一个没有写入的操作消耗资源。

### 练习七：OutOfPages 后完全不变

建立只有一页、块大小四的池，让 A 存三项并 fork 到 B；B 追加一项应失败。参考代码使用快照比较，而不只捕获异常：

```python
from copy import deepcopy
from labs.serving.kv import PagePool, OutOfPages

p = PagePool(1, 4)
p.create("A")
p.append("A", [1, 2, 3])
p.fork("A", "B")
before = deepcopy((p.tables, p.free, [(x.data, x.refs) for x in p.pages]))
try:
    p.append("B", [9])
except OutOfPages:
    pass
else:
    raise AssertionError("expected allocation failure")
after = (p.tables, p.free, [(x.data, x.refs) for x in p.pages])
assert after == before
p.check()
```

deepcopy 在这里用于冻结小型测试状态，不意味着生产系统每次分配都应该深复制整个池。测试可以使用较慢但独立的观察方式，运行时实现则使用更精细的协议。

### 练习八：非法 retain 的中途错误

让页零有一个合法引用，页一自由，调用 retain([0,1])。应报错且页零 refs 仍是一。若错误实现先给页零加一，再发现页一非法，测试会发现额外引用。进一步把非法页放在首位和末位，覆盖不同验证位置。

### 练习九：adopt 的重复物理页

一个空请求表试图 adopt 同一页两次。应被拒绝，并保持原 refs 不变。理由不是重复 ID 看起来不美观，而是当前请求布局要求每个逻辑块对应独立的历史块位置；重复映射会使同一载荷被当成两段历史。若未来要支持有意别名，必须重新定义合同与测试，不能偷偷放开。

### 练习十：缺失 parent 的 fork

调用 fork("missing","child") 后应没有 child 表。参考测试先确认 child 不存在，捕获 KeyError，再次确认。这个题检查的是身份状态的失败原子性，即使没有申请任何物理页，留下错误空表也会破坏更高层生命周期。

### 练习十一：释放顺序

A、B 共享一个完整页，缓存另外持有一份引用。初始 refs 三。依次释放 A、淘汰缓存、释放 B，refs 为二、一、零。只有最后一步才把页放回 free。交换前三种合法拥有者的释放顺序，应得到相同最终资源状态，但每个中间 refs 仍必须对应当前拥有者数。

### 练习十二：故意制造页表与引用不一致

在练习副本中直接把某页 ID 塞进另一个请求表，却不 retain。check 应失败。这个负向用例证明不变量检查能发现“映射存在但引用未记账”的错误。不要在正式实现中靠关闭 check 绕过；应通过合法 fork 或 adopt 建立共享关系。

### 练习十三：页面复用与有效长度

释放一个保存四项的页后，让新请求只写一项。新请求只能读到自己的一项，不得把旧三项残留当历史。本元数据池会清空 data，S19 的数值数组可能保留旧浮点值，因此有效长度测试更重要。相同所有权思想在不同载荷实现中的清理方式可以不同。

### 练习十四：多页 COW

块大小四，A 有七项，fork 到 B，B 追加六项。参考答案：B 需要三张自由页，最终逻辑页数四；A 仍有原七项；两者共享第一个完整页，B 的原半满尾页被复制。请列出实际分配的每个物理页编号，并检查全部中间引用。仅比较最终 token 列表还不够，因为资源泄漏可能不改变内容。

### 练习十五：建立自己的池模型检查器

实现一个独立函数，仅根据 tables 和缓存持有列表重算 expected refs，再检查 free 唯一性与双向关系。不要调用现有 pool.check 作为你的“实现”。参考算法是遍历每个拥有者的页号，对每页计数；对物理池逐项比较；最后验证每请求除尾页外都满。

验收需加入至少三种故意错误：丢一次 retain、多一次 free、共享尾页原地写入。前两种主要由结构账本发现，第三种需要分支内容不干扰测试。由此你会看见一个检查器的能力边界，而不会误以为任何单一断言能够覆盖所有缓存缺陷。

## 第十三课：从数据结构题升级为一个小型资源工程

### 13.1 先写公开接口合同

请为自己的页池实现 create、append、fork、release、tokens 和 check 六个接口。每个接口写明前置条件、成功后状态、异常后状态与返回值。特别说明重复身份、非法 token、空追加、资源不足和重复释放的行为。

合同不需要堆满正式术语，但必须足够具体。例如“append 失败不改变状态”比“append 是安全的”有意义；“release 释放该请求的一份拥有关系，其他引用保留”比“释放内存”准确。写清合同以后，才能判断测试失败说明代码错了，还是两个调用者理解不同。

### 13.2 用操作序列而不是孤立函数测试

单独测试 append、fork、release 都通过，不保证它们组合后正确。一个有价值的序列是：A 追加半页、fork B、B 跨页追加、A 再追加、释放 B、创建 C、C 复用空页、释放 A/C。每一步都检查所有权和各请求内容。

这种序列会同时覆盖共享、分叉、独立增长、物理页复用和释放顺序。你应先在纸上列出预期，再运行程序。若只在每个函数单独创建全新池，很多依赖历史的错误永远不会出现。

可以使用固定随机种子生成更多合法操作序列，但随机测试不是手算反例的替代。手算用例解释为什么错，随机用例帮助探索你没想到的组合。两者结合，比盲目跑一万次却不保存失败序列更有效。

### 13.3 保存最短失败序列

发现错误后，把操作序列缩短到仍能失败的最小版本。例如十几个操作中的问题可能只需要“append 三项→fork→append 一项”就能复现。最小序列更容易看清必要条件，也更适合作为长期回归。

不要把大量无关操作留在测试里，让后来的读者以为它们都是触发条件。另一方面，也不要把关键条件删掉后用更宽松断言让测试继续通过。一个好的回归应明确表达“共享的半满尾页在写入时必须隔离”这样的机制。

### 13.4 资源报告必须能解释

报告至少包含总页数、自由页数、活动请求数、每请求逻辑长度、每请求页表、各页 refs 与缓存拥有关系。只显示“用了多少内存”不足以定位泄漏，因为你无法知道这部分内存属于活动请求、可淘汰缓存还是丢失引用。

在真实部署中不一定公开所有 token 内容，但可以保留安全的计数与身份关联。课程合成数据允许你打印完整页表和载荷，是为了学习。迁移到真实业务时，应根据数据敏感性选择可观测字段，而不改变所有权检查的逻辑目标。

### 13.5 从慢参考到优化实现

你的第一版可以使用 Python 列表和 Counter，重点是正确、清楚、可观察。后续若改成数组、位图、空闲链表或设备端结构，先保留慢参考接口，用同一操作序列对照内容与资源状态。

优化可能改变内部物理页分配顺序，因此测试不应一律要求每次都使用相同页号，除非分配顺序本身属于合同。更稳健的语义检查是：请求读出的逻辑内容一致、引用账正确、空闲容量合理、失败原子性保持。某些专项测试为了手算固定编号，可以单独说明依赖了最小页号分配策略。

### 13.6 结业任务

交付一个包含接口说明、实现、操作轨迹、失败反例和测试报告的小仓库目录。让另一个读者不看实现，只根据合同写一组新的操作序列；你的实现应能正确处理或按合同拒绝。最后口头解释为什么页表复制不等于载荷复制，为什么 refs 为二不等于一定有两个活动请求，以及为什么异步 GPU 释放还需要额外完成条件。

做到这些，说明你已经把分页缓存从“听说它能节省显存”推进到“能实现并验证一套资源管理结构”。S04 会在它上面建立前缀缓存拥有者，S18 会加入更复杂状态组合，S19 会把真实浮点 K/V 和分块注意力放进同一条逻辑链。

## 第十四课：把页池与 Python 内存、设备内存、操作系统分页分开

初学者看到“页”“引用计数”“内存释放”时，很容易把本章与 Python 垃圾回收、操作系统虚拟内存混在一起。它们存在相似思想，但不是同一个管理器。弄清边界，能够避免一些非常顽固的排障误判。

首先，Python 对象是否仍然被引用，是 Python 运行时管理对象生命周期的问题。本章 Page.refs 则是我们自己维护的业务计数。即使把 Page.refs 设为零，Page 对象仍然保留在 self.pages 列表中，没有被 Python 删除。我们只是把这张业务页面标记为可以重新分配。

反过来，一个局部变量不再指向某个页表列表，也不表示业务引用已经正确释放。只要你没有调用相应 unpin，Page.refs 可能仍然是正数。Python 垃圾回收不会自动理解“这个整数页号曾经代表一份 KV 所有权”，更不会替你修复漏掉的业务计数。

其次，GPU tensor 的内存由所用框架和设备分配器管理。一个大张量可以被划成许多逻辑页，页池归还一页只是允许同一大张量中的那段区域重新使用，并不必然触发设备内存 free。外部工具仍看到整个大张量占用显存，是完全可能的。

这解释了为什么不能把“请求结束后显存数字没有下降”直接当成泄漏。需要分别观察活动请求数量、页池自由块、缓存固定块和分配器保留空间。真正泄漏的表现通常是某种资源在等价工作负载重复后无法回到稳定状态，而不只是某个数字没有立刻归零。

第三，操作系统虚拟内存分页由硬件和内核共同管理，涉及进程虚拟地址、物理内存、页表和权限等机制。LLM 的 KV 分块管理借用了地址间接映射与共享思想，但通常是框架自己维护的应用层数据结构。你不能拿操作系统页大小直接当成模型 KV block_size。

本章块大小四表示每块容纳四个 token 位置，不表示四字节，也不表示四个操作系统页。真实一块有多少字节，还要乘头数、维度、元素大小和涉及的层或缓存组。只看一个整数 block_size 而不写单位，是容量估算中常见的千倍误差来源。

再看一个完整单位例子。假设每块十六个 token、八个 KV 头、每头一百二十八维、每个元素两字节、三十二层，K 和 V 各一份。全层载荷为十六乘八乘一百二十八乘二乘三十二再乘二，得到二百零九万七千一百五十二字节，也就是两 MiB。这里假定所有层相同且不分片。

若把八个 KV 头均匀切到四个 rank，每个 rank 两个头，在这个简化假设下每 rank 一块载荷为零点五 MiB。若框架选择复制某些头、模型使用不同缓存结构，或者有额外对齐与元数据，实际值就不同。公式的作用是明确假设并建立初步账本，而不是替代运行时观测。

### 14.1 对齐与 padding 不等于有效数据

为了便于向量化或满足某些 kernel 约束，物理布局可能把维度填充到更合适的大小。有效 head dimension 为六，存储 stride 却按八个元素安排，是可以设计的。此时字节偏移必须使用实际 stride，数学点积却只能使用有效维度或正确处理 padding。

这与尾页未填满类似：容量中的位置不自动都是有效信息。kernel 需要明确的长度或 mask，才能避免把未定义区域参与计算。清零 padding 可以降低某些错误的表现，但不能代替正确的范围合同；因为以后复用时这些位置可能不再是零。

CPU reference 往往使用紧凑数组，让每个 shape 看起来直观；真实后端可能为了性能选择更复杂布局。源码阅读时应同时记录逻辑 shape 与物理 stride，而不是只抄一个张量维度列表。两个实现拥有同样逻辑 shape，也可能有不同寻址规则。

### 14.2 只读共享与可写所有权

共享页面为什么能够安全复用？因为共同拥有者在共享阶段把既有内容视为只读。引用计数只是告诉你有多少拥有者；真正防止串改的是“写入前检查共享并隔离”的规则。若某个旁路函数可以直接修改 page.data，COW 协议就被绕过了。

因此工程接口应尽量减少直接暴露可变底层载荷。读取函数返回副本或只读视图，写入必须经过受控接口。Python 教学代码为了可观察性公开了字段，学习者可以直接检查；这同时意味着它没有通过语言封装强制阻止所有错误写入。测试和调用约定承担了额外责任。

在真实系统中，即使 API 表面只读，设备端错误 kernel 仍可能写错地址。所有权设计不能替代地址正确性检查、数值 oracle 和设备工具，但它能给这些检查提供明确边界：哪些区域本次允许写，哪些区域必须保持不变。

### 14.3 为什么数据一样也不能任意共享

两页当前保存相同 token ID，并不自动说明真实 K/V 一样。它们可能来自不同模型参数、adapter、位置编码、前缀历史或租户语义。PagePool 本身只管理页，它不知道这些模型含义；上层 PrefixCache 必须负责判定哪些状态允许复用。

这说明低层与高层都有不可替代的合同。低层保证“你交给我的引用不会被错误回收”，高层保证“这些引用指向你真正需要的状态”。如果高层给错页，即使低层所有 refs 都正确，模型结果仍然错误。S04 正是从这一责任边界开始建立前缀身份。

最后，请用一句完整话描述一次共享：请求 B 经过语义身份检查，获得与其前缀相容的一组现有页引用，页池增加对应拥有权；之后 B 只读旧内容，若需要修改共享半满尾页则先复制；B 结束时只释放自己的引用。这句话中每个动词都对应代码与测试，缺少任何一项，都可能留下一个静默错误。

来源与实现依据见 [本卷来源](SOURCES.md) 中 PagedAttention 原始论文及固定 KVCacheManager 快照；本章逐行解释直接对应本仓库 [kv.py](../../labs/serving/kv.py)。纸面页数、槽位和字节例子均为透明教学数据，不是实际 GPU 内存占用测量。

还有一个值得亲手验证的边界：页面编号只是池内身份，不携带“更早的历史”或“更近的内容”这样的时间语义。释放页零以后，新的短请求可能先拿到页零，而一个更老的请求仍保留页三。调试时若按物理页号排序后展示请求历史，会把这种正常复用解释错。正确观察器应先选择请求，再沿该请求的逻辑页表遍历；需要展示物理池时，则单独列出每页的拥有者。把这两张视图同时打印，能直观看到一份连续逻辑历史怎样映射到不连续物理块，也能检查同一物理块是否被多个合法拥有者共享。这个观察方法在后续阅读真实框架日志时仍然有用：先确认日志里的编号属于请求、逻辑块还是物理块，再判断它的增减是否异常。
