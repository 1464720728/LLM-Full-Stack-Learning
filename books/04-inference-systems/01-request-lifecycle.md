# S01 一次请求怎样穿过推理系统

先修：能读 Python 函数、类、列表、字典、异常；知道张量和自回归生成。若“进程、HTTP、JSON、模块导入”仍然陌生，先完成[基础卷](../00-foundations/README.md)。本章的目标不是背组件名称，而是在一个请求卡住时，知道应该在哪一层加日志、读哪个状态、验证哪条约束。

## 1. 把“调用模型”拆成可以观察的动作

在网页中输入一句话后，GPU 不会直接收到字符串。客户端先形成协议请求，HTTP 服务解析请求体，校验模型名、输出上限和采样参数。聊天接口还要把角色、工具定义、历史消息套进聊天模板。Tokenizer 把结果变成整数列表。调度器决定请求何时进入一个批次；缓存管理器为状态分配空间；模型执行器准备张量并调用模型；采样器把 logits 变成下一个 token；输出处理器判断停止条件、增量解码、形成流式事件。

这些是职责，不一定是独立进程。小程序可以把它们写在一个线程里；大系统可能把 Tokenizer、调度器、GPU Worker、Detokenizer 分成多个进程。遇到名为 Engine 的类，不要自动认为它包含所有步骤；要看输入、返回值以及它持有什么对象。

一个请求同时有三种身份：业务层的会话或任务 ID，服务层的 request ID，执行层某轮批次中的行号。行号随批次变动，不能长期用它标识请求。缓存也不能只按“当前第 0 行”存，否则上一轮第 0 行退出后，下一轮的新请求会读到旧状态。我们给每个请求一个不可复用的 `rid`，把行号作为短暂映射。

## 2. Prefill 与 Decode 的真正差别

设提示 token 为 `[1,2,3]`，要生成三个 token。模型先处理三个输入位置，最后一个位置的 logits 预测第一个输出 4。此时有了 `[1,2,3]` 的已计算状态，但尚未把 token 4 作为输入处理；第二次前向处理 token 4，预测 5；第三次处理 5，预测 6。

因此，三个输出通常只要求缓存到 `[1,2,3,4,5]`，最后输出的 6 不必再送入模型，除非还要继续生成。这个差一位经常造成 KV 容量、调度计数和停止逻辑的错误。输出了一个 token 不等于为它计算了 KV。阅读框架时，要区分 `output_token_ids`、`num_computed_tokens`、计划执行的 token 数和实际接受的 token 数。

Prefill 可以同时处理多个已知输入位置，因为提示已经给定；Decode 的后续 token 依赖刚刚生成的结果，通常每轮每请求处理一个新位置。这里“通常”很重要：推测解码、某些结构化输出优化会改变一轮处理几个位置，但不会消灭数据依赖。本卷默认关闭推测解码，先把基本语义学准确。

## 3. 手工追踪：从状态到结果

运行：

```bash
python -m labs.serving.experiments --lab lifecycle
```

代码使用一个可精确预测的 16 状态 Bigram 模型：看到 token `i`，贪心选择 `(i+1)%16`。它不具有语言能力。这样我们可以一眼判断错误发生在调度还是模型上。此实验的提示为 `[1,2,3]`，最大输出 3，prefill chunk 为 2。

| 轮次 | 本轮输入 | computed 结束值 | 是否产生新输出 | 已生成列表 |
|---|---|---:|---|---|
| 1 | 1,2 | 2 | 否，提示尚未算完 | 空 |
| 2 | 3 | 3 | 是，预测 4 | 4 |
| 3 | 4 | 4 | 是，预测 5 | 4,5 |
| 4 | 5 | 5 | 是，预测 6 后结束 | 4,5,6 |

实验里的时间是人为设定的代价函数：每轮 1 ms，加每个 prefill 输入 0.25 ms，加每个 decode 输入 0.10 ms。第一轮 1.50，第二轮 1.25，第三和第四轮各 1.10，总计 4.95 ms。首 token 在 2.75 ms 出现。这些数用来验证时间记账，绝不是 H100 性能结果。

## 4. 逐段读 `Request` 与 `Engine`

打开 [`engine.py`](../../labs/serving/engine.py)。`Request.__post_init__` 在入口建立数据不变量：提示不能空，token 必须是非负整数，输出上限必须是非负整数，arrival 和 temperature 必须有限。为什么用 `type(x) is int` 而不只用 `isinstance(x,int)`？Python 的 `bool` 是 `int` 的子类；协议输入 `true` 不应该悄悄变成 token 1。

`context` 返回提示与已生成输出的拼接。它是逻辑序列；`computed` 表示这个序列中有多少位置已经执行过。运行中应满足 `0 <= computed <= len(context)`。`rng` 属于请求，而不是共享在 Engine 上，否则多一个并发请求就会消费随机流，改变别人的采样结果。

`Engine.submit` 只登记请求，不运行模型。`_ingest` 把到达时间已满足的请求从 pending 移到 waiting。`_admit` 才建立缓存表，并尝试匹配前缀。`step` 形成 `Work`，更新本轮计算位置，推进模拟时钟，再获取 logits 和采样。`_finish` 负责释放请求引用并写终态。`run` 是重复调用 `step` 的便利封装，不是另一套调度算法。

实现中缓存页装的是 token ID，代表“这一行 KV 已经计算”的元数据；神经网络 K/V 张量并不住在这些页中。BigramBackend 直接查看最后一个 token；TinyAttentionBackend 会重新计算上下文。这样拆开是为了分别验证缓存生命周期与数值计算。把它叫作“实现了生产级 PagedAttention”是不正确的。

## 5. 为什么要把状态机写清楚

请求可能处于 pending、waiting、running、finished、cancelled、error。状态不是给日志美化用的：只有 running 请求可以占有活动缓存表；finished 不应再次进入等待队列；cancelled 后到来的迟到输出不能再发给用户；error 要归还资源。

本参考实现的取消发生在迭代边界，没有真实 GPU 异步执行。生产系统更复杂：取消时已经提交的 Kernel 未必能立即停止，所以先标记逻辑取消，等计算完成或确认不再访问状态后再回收。过早 free 会产生 use-after-free；过迟 free 会表现为内存泄漏。学习本模型时先证明所有权正确，再研究异步完成事件。

## 6. 从日志提出可证伪的假设

如果没有首 token，依次查：请求是否登记？是否到达？是否入队？是否入选？是否因为空间不足被跳过？prefill 是否全部完成？模型是否抛异常？输出是否已生成但卡在增量解码？这条检查链比“是不是 GPU 太慢”有用。

日志应该有 request ID、阶段、token 数、时刻和简短错误分类，避免输出完整提示、API Key 或用户私有内容。计数器记录量；事件日志记录顺序；追踪跨度记录跨组件延迟。它们回答的问题不同，不能互相代替。一个 `running=1` 的指标不能告诉你是谁，也不能证明这个请求本轮得到计算。

## 7. 练习与参考解法

1. **手算换提示。** 把提示改为 `[14,15]`、输出上限 3、chunk=1。预测输出和前向次数。答案：输出 `[0,1,2]`；两轮 prefill 加两轮 decode，共四轮。最后的 2 尚未被作为输入执行。
2. **零输出。** 构造 `max_new_tokens=0`。验收：输出空、终态 finished、没有活动页。参考实现在 ingest 时直接结束；若先送入模型再丢弃结果，语义虽可能相同，但浪费算力且影响计费统计。
3. **查状态约束。** 故意删掉 `_finish` 中 `pool.release`，运行 `python -m unittest tests.test_serving_core.EngineTests.test_cancel_idempotent -v`。应该失败在页未归还或活动表集合不一致。修复要恢复所有权处理，而不是删断言。
4. **完成和取消的竞争。** 对已经完成的请求调用 cancel。答案应是 False，不能改写原完成时间或多释放一次。使用终态集合做幂等检查；需要审计时可另记“取消请求被忽略”事件。
5. **入口验证。** 给提示 `[True]`、空提示、负输出上限、NaN 温度，各写一个用例。验收：错误在调度之前出现，缓存池不变。详解：越早验证越容易归责；晚到模型 Runner 才崩溃，会把协议错误伪装成后端故障。
6. **接口重构。** 把 Request 的列表直接传给不可信后端，后端追加 token，会发生什么？答案：如果后端拿到内部可变对象，会破坏 computed 和 context 的一致性。这里 `context` 生成新列表；你可进一步用不可变 tuple 定义 Backend 接口。验收是加入一个会修改输入的后端后，请求提示仍不变。

掌握门槛：不看书画出某请求的五次状态变化；解释最后一个输出为什么通常没有 KV；能用事件记录定位“排队、计算、输出处理”中的故障；能说明本实验不是完整推理引擎的三个原因。
