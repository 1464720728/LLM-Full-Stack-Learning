# K01　张量不是表格：从一个地址开始理解布局

先修：基础卷的 Python 列表、函数、NumPy 数组与二进制单位。完成本章后，你应能从形状和步长独立算出任意元素的地址，判断两个张量是否共享存储，并解释为什么“转置”未必搬动数据。这是阅读 CUDA、Triton、Attention、KV Cache 代码的共同起点。

## 1. 存储是一条线，维度是解释方式

纸上的二维矩阵有行有列，显存中的一段分配却是一串字节。形状 `shape=(3,4)` 表示程序把十二个元素解释为三行四列。它不保证物理布局一定是逐行连续；真正决定寻址的是 `stride`，即某个逻辑下标加一时，需要沿存储走过多少元素。另有一个起始偏移 `storage_offset`，让张量视图能够从整段存储的中间开始。

以 float32 为例，每个元素占四字节。设存储起点地址是 1000，连续行优先矩阵形状为 `(3,4)`，元素步长为 `(4,1)`。逻辑元素 `(1,2)` 的元素偏移是 `1*4+2*1=6`，字节地址是 `1000+6*4=1024`。这里四个数不能混为一谈：`3,4` 是形状，`4,1` 是步长，`6` 是元素偏移，`24` 才是字节偏移。很多 Kernel 越界问题来自把其中两种单位混用。

一般的 n 维公式是：

\[
\operatorname{address}(i_0,\dots,i_{n-1})=p+\left(o+\sum_j i_js_j\right)b.
\]

其中 `p` 为底层存储的字节起点，`o` 为起始元素偏移，`s_j` 为元素步长，`b` 为元素字节数。公式本身没有矩阵乘法知识。Kernel 中的所有 `ptr + row*stride_m + col*stride_n` 都是在实现这个公式。

## 2. 一次转置发生了什么

执行 `a=np.arange(12).reshape(3,4)` 后，`a[1,2]=6`。执行 `t=a.T`，得到形状 `(4,3)`、元素步长 `(1,4)` 的视图。此时 `t[2,1]` 的偏移是 `2*1+1*4=6`，仍然读到同一元素。转置只需要交换形状与步长，数据可以完全不移动。`np.shares_memory(a,t)` 能说明它们是否共享存储；只看对象身份 `a is t` 不够。

于是，逻辑上相邻并不等于物理上相邻。对 `t` 固定第一维并沿第二维访问，每次要跳四个元素。一个假定最后一维步长总为一的 Kernel，如果直接接受这个视图，就可能给出数值错误，甚至访问错误的位置。合法设计有两种：入口显式拒绝非连续输入，或把各维步长作为参数并在内部正确寻址。最危险的是文档声称支持任意布局，代码却悄悄按连续布局计算。

`.contiguous()` 一类操作通常会在必要时建立新的连续存储。它可能引入一次完整拷贝。若把这次拷贝藏在计时区间外，你测到的 Kernel 速度就不能代表端到端成本。若新布局本来就连续，则可能不复制，不能把每次调用都当成一样的成本。

## 3. 切片、广播、负步长

`a[:,::2]` 只选择第 0、2 列，形状是 `(3,2)`，元素步长为 `(4,2)`。逻辑上仅有六个元素，底层仍可能保留原来十二个元素的存储。因此 `numel*itemsize` 是逻辑有效载荷，不一定是底层分配大小，也不是进程显存占用。

广播可用步长零表达：一个长度为一的维度被逻辑扩展后，多个下标都读取同一位置。读取很方便，写入则有别名问题：多个输出位置可能映射到同一个地址。如果程序允许这种视图作为写入目标，必须明确是禁止重叠、进行归约，还是以别的语义处理；“最后写的线程赢”通常不是一个可接受的算子定义。

NumPy 支持负步长反向视图，例如 `a[::-1]`。这时起始偏移要移到最后一行，再用负步长往回走。并非所有框架和 GPU Kernel 都支持负步长。你的实现不支持时，应该在入口拒绝，而不是赌调用者不会传进来。

## 4. 从 Python 走到指针代码

阅读 [reference.py](../../labs/kernels/reference.py) 的 `offset`，先别运行。预测 `(index=(2,1), shape=(4,3), strides=(1,4))` 的结果，再用 K01、K02 验证：

```bash
python -m labs.kernels.run --lab 1
python -m labs.kernels.run --lab 2
```

K01 输出连续三维步长 `(12,4,1)` 和偏移 `23`。K02 的转置仍读取 `6`，且共享内存为真。NumPy 输出的 `strides` 单位是字节，本教材 `offset` 的步长单位是元素。看到输出 `(8,32)` 一类数值时，先检查当前数组 dtype 的字节数，不要机械地以为程序错了。

`offset` 做了逻辑越界检查，却没有负责分配存储，也没有保证给定步长与实际分配一致。这体现了接口职责：一个寻址公式可以正确，而使用它的存储描述仍可能错误。生产张量系统通常在更高层维护这些不变量。

## 5. 练习与参考答案

1. **手算。** float16 张量形状 `(2,3,5)`，连续布局，底层起点 2048；求 `(1,2,4)` 的地址。答案：步长 `(15,5,1)`，元素偏移 29，字节地址 2106。验收：全过程显式写出每个单位。
2. **修改。** 在自己的练习文件中给 `offset` 增加 `itemsize` 参数，返回字节偏移。解法：先保留原函数的维度和边界校验，最后只乘一次 `itemsize`；测试 float16 与 float32 同一下标应有二倍关系。
3. **调试。** 某 Kernel 用 `row*N+col` 处理 `a.T`，为什么第一个元素可能正确而后面的错？答案：零偏移不受步长影响，其他元素需要 `(1,4)` 的步长。写一个 `3x4` 的非方阵测试，比方阵更容易暴露错误。
4. **设计。** 一个逐元素只读算子支持广播输入，输出必须连续。写下至少四条契约。参考：输入形状可广播；步长可为零；输出不与输入别名；输出各元素只写一次。若支持原地更新，须重新定义别名和依赖，不能直接复用契约。
5. **实操。** 用 `np.arange(24).reshape(2,3,4)` 建立转置和步长切片，逐点用 `offset` 算地址并和实际值比较。验收不是打印一个值，而是遍历整个合法下标空间；负步长另加起始偏移测试。
6. **性能推理。** 若每次调用都先拷贝一个 1 GiB 视图，再运行 0.1 ms Kernel，能否宣称该算子耗时 0.1 ms？答案：只能宣称内部 Kernel 的那一段设备执行耗时；完整算子必须包括必要拷贝与调度。把这两项分别记录。

掌握门槛：不用查资料解释 shape、stride、offset、dtype、alias 五者关系；用非连续输入主动击穿一段错误寻址代码；说清修复是支持布局还是拒绝布局。
