# K04 GPU访存从零推演：地址集合、缓存、共享内存、Bank与同步

K03解释谁执行代码，本章解释这些执行者怎样取得数据。同一条数学表达式，可以因为数据布局、线程映射和复用方式不同，产生非常不同的访存成本。学习目标不是背“共享内存快、全局内存慢”，而是能列出一组线程访问的字节地址，计算一个明确模型中的传输单元，判断数据是否重复读取，并说明每次同步保护了哪条读写依赖。

本章使用仓库实验四和五作为起点，但正文会把其中每一个数字推出来：

~~~bash
python -m labs.kernels.run --lab 4
python -m labs.kernels.run --lab 5
~~~

这里的sector与bank计算是有声明假设的教学模型，不是完整硬件模拟器。真实请求合并、缓存命中、指令宽度和设备微结构需要在目标机器上进一步观察。先把模型算对，再讨论它能够解释什么、不能解释什么。

## 第一课：先区分地址空间、存储位置和缓存

### 1. “global”不是“每次都直接读取显存芯片”

CUDA中的global memory描述一种设备可访问的全局地址空间。一次global load可能命中某级缓存，也可能需要访问设备的外部内存。因此，看到源码从global指针读取，不能直接断言每个元素都产生一次完整的外部内存访问。

缓存保存近期或符合缓存策略的数据副本，目标是减少重复访问的成本。程序仍使用原来的逻辑地址，缓存系统决定是否能从更近位置提供内容。相比之下，共享内存通常由程序显式分配并通过代码安排写入与读取，其内容和协作时序由程序承担更多责任。

地址空间回答某个对象通过什么规则被访问，物理存储与缓存路径回答请求可能在哪些硬件资源中得到满足。把二者混成一张简单的“快慢排序表”，会导致很多错误推断。例如线程私有的local memory不等于一定存放在片上寄存器里，名字中的local描述可见性，不是速度保证。

### 2. 寄存器、共享内存和全局存储的角色

寄存器通常用于保存线程正在计算的局部值。一个累加器、循环变量和短向量中间结果可能驻留在寄存器中。寄存器资源有限，编译器分配过多值时可能发生溢出到其他存储位置的情况，这叫spill。源码里写一个局部变量，并不保证它永远只占一个廉价寄存器。

共享内存提供同一协作范围内线程可共同访问的存储，常用于复用tile、交换局部结果和实现归约。它不会自动把global数组搬过来，程序必须安排加载；也不会自动判断什么时候可以覆盖旧数据，程序必须建立同步。

设备全局存储通常容量更大，用于模型权重、KV缓存、输入输出和大型中间张量。不同GPU产品使用的外部内存技术可能不同，本章不把所有GPU都称为HBM设备。分析时先说“设备外部内存”或“全局存储”，需要具体带宽与介质时再查实际型号。

### 3. 可见性与生命周期一起看

一个线程的寄存器值通常不能被另一线程直接当作普通内存地址读取。共享内存属于具体block或特定高级协作合同，不能把某个block中的shared数组当作全grid公共数组。global缓冲区则可被多个block访问，但并发读写需要明确同步与内存模型。

共享内存的内容也不会跨任意Kernel调用永久保存。每次工作如何初始化、哪些槽位有效、何时可复用，都要由当前算法保证。把上一次运行留下的值当作默认初始状态，是典型错误。对于尾块，无效槽位通常需要显式填入数学中性值，而不是期待它们“刚好是零”。

## 第二课：从一条线程指令收集地址集合

### 1. 先固定我们分析的单位

假设一个warp中有三十二个有效线程，每个线程从float32数组读取一个元素。每个元素四字节。令线程lane编号从零到三十一，数组基址按教学传输单元对齐。线程lane读取第lane个元素，则它访问的起始字节地址是基址加四乘lane。

我们把三十二个起始地址列出来：零、四、八，一直增加到一百二十四。每个访问覆盖四字节，因此整个集合覆盖零到一百二十七，共一百二十八字节，没有间隙。现在才能讨论这些地址需要触及多少传输单元，而不是先背“连续访问最快”。

如果每个线程读取一个八字节元素，地址间隔和覆盖宽度都变成八；如果只有前十个线程有效，地址集合只有十个访问；如果数据指针偏移四字节，整体集合也随之移动。这些变化都会影响后面的覆盖计算，不能只看线程数量。

### 2. 地址相邻与线程编号相邻是两个条件

合并访问的关键之一是同一相关指令中有效线程访问的地址能否被较少存储事务覆盖。不是要求每个线程在自己的整个循环里连续访问，也不是要求源码中的数组“看起来连续”。必须把同一时刻执行同一条加载指令的线程地址放到一起分析。

例如每个线程循环读取相隔三十二元素的位置：第一轮线程零到三十一分别读零到三十一，第二轮分别读三十二到六十三。每个线程自己的两次读取相隔很远，但每一轮跨线程访问仍然连续。反过来，每个线程自己读取两个相邻元素，也可能因为不同线程起点相隔很远而形成稀疏地址集合。

K03的grid-stride循环正好展示这种区别。一轮中相邻线程负责相邻逻辑元素，轮与轮之间每个线程跨过总线程数。分析访存时以一轮的相关指令集合为单位，不能把单线程轨迹直接当作整个warp的请求形态。

## 第三课：完整推导三十二字节sector模型

### 1. 从区间覆盖而不是经验口诀出发

为了手算，我们把地址线分成连续三十二字节区间，称为sector。零到三十一属于sector零，三十二到六十三属于sector一，依此类推。一个访问从地址a开始、宽度w字节，它覆盖的sector编号从a整除三十二，到a加w减一再整除三十二。

用减一是因为宽度w的访问包含a到a加w减一这w个字节。例如从二十八开始读取四字节，覆盖二十八到三十一，只触及sector零；从三十开始读取四字节，覆盖三十到三十三，则跨越sector零和一。只检查起始地址会漏掉后一种跨界。

多个线程的访问可能触及相同sector，因此要对所有sector编号取并集，而不是简单把每个线程触及数量相加。连续三十二个float32元素覆盖一百二十八字节，在对齐情况下触及四个sector。三十二个线程不等于三十二个sector。

### 2. 对齐与偏移四字节的完整对照

对齐起点下，访问区间整体为零到一百二十七，sector为零、一、二、三。若基址整体偏移四字节，访问区间变成四到一百三十一，触及sector零到四，共五个。有效数据量仍是一百二十八字节，但覆盖的传输粒度增加。

这里不能立即说“性能必然降低百分之二十五”。sector数量只是一个流量模型，真实缓存、请求合并、指令执行和后续复用会影响实际代价。它可以提出一个可验证解释：起点偏移造成额外传输单元；要确认影响，需要在目标设备上测量对应指标和耗时。

如果访问宽度、sector粒度或有效lane集合改变，结果也要重新计算。把四与五背成某种永恒硬件规律没有意义，重要的是你能从地址区间推出它们。

### 3. 跨八个float访问为什么触及更多sector

现在每个线程读取第八乘lane个float。起始字节地址变成三十二乘lane，因此每个线程恰好落在一个新的sector起点。三十二个线程触及三十二个sector，但每个sector只使用其中四字节。有效数据仍是一百二十八字节，覆盖空间却分散到更大范围。

这种模式可能出现在按列读取行宽为八个元素的行优先矩阵，或其他跨步布局中。它不意味着列访问在所有情况下都错误，而是说明线程映射与存储布局不匹配时，单条访问指令利用传输粒度的效率可能下降。

如果这些sector随后被别的线程或后续指令充分复用，端到端浪费可能有所变化。因此，单指令地址分析是第一层证据，整个Kernel的数据复用分析是第二层证据，两层都需要。

## 第四课：把模型写成一个独立可验证的程序

### 1. 完整实现

~~~python
def touched_sectors(addresses, width_bytes=4, sector_bytes=32):
    if width_bytes <= 0 or sector_bytes <= 0:
        raise ValueError('positive widths required')
    result = set()
    for address in addresses:
        if address < 0:
            raise ValueError('negative address')
        first = address // sector_bytes
        last = (address + width_bytes - 1) // sector_bytes
        result.update(range(first, last + 1))
    return result

aligned = [4 * lane for lane in range(32)]
shifted = [4 + 4 * lane for lane in range(32)]
strided = [32 * lane for lane in range(32)]
assert len(touched_sectors(aligned)) == 4
assert len(touched_sectors(shifted)) == 5
assert len(touched_sectors(strided)) == 32
assert touched_sectors([30], width_bytes=4) == {0, 1}
~~~

集合负责去重，range的右端点要加一，因为last本身也在覆盖范围内。输入addresses以字节为单位，width_bytes也是字节，二者单位一致。不要把元素下标直接交给这个函数，除非每个元素恰好一字节。

仓库reference.sectors返回集合大小，核心推导与此一致。它明确称为理想化触及sector模型，不预测完整硬件事务。你可以在自己的练习文件中返回具体集合，这会比只看到数字更容易定位边界错误。

### 2. 为什么要包含跨sector的单次访问测试

如果测试只用四字节对齐的float地址，错误实现可能只计算address整除sector而忽略访问宽度，仍然通过所有样例。加入地址三十、宽度四的反例后，它才会失败。这个测试说明我们验证的是区间覆盖，而不只是常见输入上的一个简化公式。

类似地，重复地址测试能检查集合去重，空地址列表测试能检查零访问结果，负地址测试能检查合同拒绝。每个用例都应对应一个明确可能出错的逻辑，而不是为了增加测试数量随机堆数据。

### 3. 地址模型如何帮助读真实Kernel

打开一个加载表达式，把指针基址暂时设成零，代入一个warp或一个program内各线程/元素的逻辑下标，得到相对字节地址。先看是否越界，再看覆盖了哪些sector，最后看这些数据后面被使用几次。

这套方法能处理行列交换、不同head布局和GEMM加载方向。它不会自动告诉你最终机器指令，因为编译器可能向量化或重排，但能先发现明显的不匹配。若源码地址模型与预期完全不符，就没有必要急着解释复杂硬件指标。

## 第五课：缓存是复用机制，不是无限容量的免费仓库

### 1. 命中、未命中和工作集

缓存命中表示所需数据能在某级缓存中找到；未命中则需要从更远处取得。工作集是某段执行期间反复使用的数据集合。若工作集过大或访问模式不利，旧数据可能在再次使用前被替换出去。

同样的Kernel反复运行时，第一次与后续运行可能有不同缓存状态。输入规模很小时，重复测量可能主要观察缓存内访问；规模增大后才更明显地反映外部内存。性能报告应说明输入大小、重复方式和是否希望测量冷缓存或热缓存情境。

不能因为某个测试的有效带宽超过设备外部内存的标称值，就立即断言测量作弊或硬件超频。也可能是数据命中了缓存，或带宽公式重复计算了逻辑读取量。需要把“逻辑字节数”“实际外部流量”和“某级缓存流量”区分开来。

### 2. 时间局部性与空间局部性

时间局部性是同一数据在相近时间再次使用，空间局部性是访问相邻地址。向量加法通常每个输入元素只使用一次，主要依赖连续访问；矩阵乘法中一个A元素可以参与多个输出列的计算，一个B元素可以参与多个输出行的计算，具有明显复用机会。

缓存可以自动捕捉部分复用，但程序组织仍影响复用是否发生在数据被替换之前。tile把相关计算聚在一起，让同一块数据在较短时间内被多次使用。共享内存则可以把部分复用显式交给程序管理。

不要把缓存和shared看作互相排斥的两种世界。真实算子可能同时利用global缓存、shared tile和寄存器累加，每一层承担不同范围的复用。优化分析应问每个数据块在哪一层被谁使用多少次，而不是只说“用了共享内存所以更快”。

### 3. 只读并不自动等于永远缓存命中

数据没有被修改，只说明其值稳定，不说明缓存容量足够或访问模式有利。模型权重很大，某个权重块读取后可能很久才再次使用；KV缓存也随序列增长，工作集可能不断变大。只读合同有助于优化，但不能替代容量与复用分析。

反过来，可写数据也可能被缓存。关键是写入策略、读写顺序和一致性合同，而不是简单把输入与输出分别贴上“缓存”和“不缓存”标签。初学时先使用官方定义和测量工具，不自行发明缓存行为规则。

## 第六课：共享内存是一份由程序管理的协作数据

### 1. 从两线程交换数据开始

设thread零需要thread一加载的值，thread一也需要thread零加载的值。两者可以各自把global输入放到shared数组自己的槽位，经过适当同步后，再读取对方槽位。这里shared承担跨线程交换，屏障建立生产到消费的顺序。

如果每个线程只是把自己的global值写到shared，再立刻读回自己同一位置，既没有跨线程交换，也没有多次复用，那么这次中转可能只增加工作。shared的价值来自明确的数据流改变，而不是变量声明带上了某个关键字。

在GEMM中，一个线程加载的A元素会被同block中计算不同输出列的线程使用，B元素也会被计算不同行的线程使用。这种多消费者复用才是shared tile的核心收益之一。K06会把具体复用次数算出来。

### 2. shared数组需要谁初始化

共享内存不能默认具有你需要的初值。每个后续会读取的位置，要么在本轮由某个线程写入有效数据，要么被明确写入数学中性值。尾块加载不足时，常见做法是让对应线程写零，而不是跳过写入留下旧内容。

写入责任还需要唯一或有明确合并语义。若两个线程向同一shared位置写不同值，就需要重新检查地址映射；若它们本来要做归约，则应采用正确协作算法，而不是普通竞争store。共享可见性扩大了合作能力，也扩大了错误影响范围。

### 3. shared容量与复用收益同时考虑

tile越大，理论上可能复用更多数据，但也占更多shared容量。一个block占用太多资源，可能减少同SM驻留的其他block。共享存储本身也有访问组织和同步成本，因此不能只根据复用次数判断最终性能。

正确实验先建立数值等价，再记录tile形状、shared字节数、寄存器使用、有效工作比例和耗时。若某个tile更慢，可能是资源限制、bank冲突、尾部浪费或其他因素，需要用证据区分。把“shared很快”当成唯一解释，会阻碍真正的分析。

## 第七课：Bank模型如何从地址推出冲突

### 1. 先声明教学模型

我们采用三十二个bank、每个基本word四字节的简化模型。一个word地址除以三十二取余得到bank号。这里word地址已经把字节地址除以四，不能直接把任意字节地址当作word编号。

多个线程访问同一个word时，可以存在广播式服务情形；访问不同word却落到同一bank时，可能需要分批处理，形成bank冲突。真实硬件对不同访问宽度和指令有更细节的规则，所以我们用它解释基础现象，不把一个模运算当作全部硬件行为。

### 2. 连续word与跨三十二word的完整对照

线程lane访问word地址lane时，bank号依次为零到三十一，每个bank对应一个不同word。在这个模型里没有不同word争用同一个bank。

线程lane访问word地址三十二乘lane时，所有地址对三十二取余都为零。三十二个不同word落到bank零，因此模型给出三十二路冲突。若所有线程都访问word零，则它们虽然也都指向bank零，却是同一个word，属于广播情形，不能按三十二个不同word计算冲突。

这两个例子只差“地址相同”与“bank相同”四个字，却是理解冲突的关键。bank号是地址的某种映射，不是完整地址。相同bank不代表相同数据，正如同一楼层编号规则不代表每个房间都是同一个房间。

### 3. 用集合区分广播与不同word争用

~~~python
def bank_degree(word_addresses, banks=32):
    if banks <= 0:
        raise ValueError('positive bank count required')
    groups = [set() for _ in range(banks)]
    for address in word_addresses:
        groups[address % banks].add(address)
    return max((len(group) for group in groups), default=0)

assert bank_degree(list(range(32))) == 1
assert bank_degree([32*i for i in range(32)]) == 32
assert bank_degree([0]*32) == 1
assert bank_degree([]) == 0
~~~

每个bank里保存的是不同word地址的集合，所以重复读取同一个word不会增加集合大小。返回最大集合大小表示这个简化模型中最拥挤bank需要服务的不同word数。它是用于比较访问模式的指标，不是直接测得的时钟周期数。

## 第八课：二维转置为什么需要Padding或其他布局变换

### 1. 先分析三十二乘三十二shared tile

假设shared数组按行优先存储，每行三十二个word。读取同一列、不同的三十二行时，线程lane的word地址为lane乘三十二加固定列号。对三十二取余，所有线程的bank号都等于固定列号，因此形成严重的不同word同bank映射。

按行读同一tile时则不同。固定行号，线程lane读不同列，地址是固定行乘三十二加lane，bank号随lane变化，覆盖全部bank。于是一个布局可以让行访问好，却让列访问差。转置需要把两种方向连接起来，这就是布局选择的核心矛盾。

### 2. 在每行末尾补一个word

把物理行跨度从三十二改成三十三，而逻辑有效列仍为三十二。读取同一逻辑列时，地址变成lane乘三十三加col。因为三十三对三十二取余为一，bank号等于lane加col再取余，三十二个lane分散到不同bank。

多出来的第一个word不是新的逻辑矩阵元素，它是物理布局中的padding。输出数学shape仍然可以是三十二乘三十二。你在K01已经学过逻辑元素数与存储跨度不同，现在这一区别被用来改善shared访问模式。

padding增加存储占用，也可能影响其他访问宽度或tile策略。它不是对所有矩阵、所有数据类型和所有指令都最优的通用补丁。真实库还可能使用swizzle等更复杂映射，目标仍是让消费者访问模式匹配存储组织。

### 3. 用四bank小模型完整手算

为了纸上可见，把模型缩成四个bank、四行四列。原布局读取列零的word地址为零、四、八、十二，bank全为零。每行补一个word后，地址变成零、五、十、十五，bank分别为零、一、二、三。

选择列二时，原布局地址为二、六、十、十四，bank全为二；补位后地址为二、七、十二、十七，bank为二、三、零、一。你可以看到padding不只修复第一列，而是改变了跨行步长对bank数的模关系。

这份手算比记住“数组第二维加一”更可靠。因为当数据类型宽度、bank模型或读取粒度改变时，你需要重新推导，而不是机械复制某个声明。

## 第九课：寄存器复用、spill与局部数组

### 1. 一个局部数组未必全部驻留寄存器

源码里声明一个线程私有数组，例如float acc[若干元素]，表达的是每个线程拥有自己的逻辑状态。编译器能否把所有元素分配到寄存器，取决于数组大小、访问方式、优化分析和资源压力。动态下标访问也可能影响处理方式。

如果寄存器需求过高，部分值可能溢出到local memory。local在这里强调每线程私有的地址空间，不能误读为“本地所以一定快”。相关访问可能经过缓存和设备外部存储路径，实际代价需要编译报告和分析工具确认。

因此，增加每线程输出tile虽然可能提升数据复用，也可能显著提高寄存器占用并触发spill。一个优化同时改变多个资源因素，需要逐项记录，不能只数global load减少了几次。

### 2. 累加器为什么适合保留在寄存器

矩阵乘法输出元素需要沿K维反复累加。如果每次乘加都把中间结果写回global，再重新读出，会产生大量不必要流量。让线程在局部累加器中保留部分结果，最后一次性写回，可以减少中间读写。

但一个线程负责太多输出元素，就需要更多累加器。每线程寄存器增加可能减少可驻留warp，也可能影响编译器安排。优化目标不是把所有中间量都塞进寄存器，而是在复用、并发和资源限制之间找到合适平衡。

### 3. 观察证据的顺序

先看源码中每个线程保存哪些长期活跃值，再看编译器资源报告与是否出现spill信息，最后结合profiler和实际耗时解释。源码变量数量不等于最终寄存器数量，因为编译器会消除、合并和重用某些值；反过来，复杂表达式也可能产生额外临时状态。

当你改变tile后性能突然下降，检查资源变化比立刻换另一组随机参数更有效。你应提出可证伪解释，例如“较大累加器导致spill增加”，再寻找能支持或否定它的报告，而不是把所有下降都称为GPU调度玄学。

## 第十课：同步、可见性与共享缓冲区复用

### 1. 一个tile至少有生产、消费、复用三个阶段

线程从global加载数据并写shared，是生产；其他线程读取shared参与计算，是消费；下一轮加载覆盖相同shared位置，是复用。生产完成前不能消费，消费完成前不能覆盖。这两条依赖决定了同步应该放在哪里。

如果只有第一条依赖被保护，程序仍可能在下一轮覆盖时出错。一个较快线程已经完成自己的乘加并开始加载新tile，另一个较慢线程还在读旧tile，两者访问同一shared位置，就会混入不同轮次的数据。这个错误在不同设备或输入上可能表现不同。

### 2. 双缓冲改变依赖图，而不是消灭依赖

使用两份shared缓冲区时，可以让一份供当前计算读取，另一份准备下一批数据。这样有机会让数据搬运与计算重叠，但必须记录每份缓冲区当前属于哪一轮、是否已经准备好、是否还有消费者使用。

缓冲区交替使用时，生产者不能因为“这是另一份”就立即覆盖；两轮之后它仍会回到同一份，需要确认上一次消费完成。高级异步拷贝和屏障机制提供更细粒度工具，但算法仍然维护相同的所有权和阶段关系。

### 3. 不要用额外同步掩盖错误地址

如果错误来自两个线程写同一个本不该共享的槽位，增加屏障可能改变表现，却不一定修复数学语义。先验证每个阶段的地址映射和写入所有者，再验证阶段之间的顺序。地址错与时间错经常同时存在，分层排查能够避免误修。

一个有效测试可以先用CPU模拟shared数组并按阶段执行，验证每阶段最终内容；再在GPU上验证同步实现。CPU阶段模型不能证明设备内存语义，但能先排除纯算法与地址错误，把后续调试范围缩小。

## 第十一课：向量化加载与对齐的合同

### 1. 一次加载多个元素意味着更宽的访问

把四个float标量读取合成某种宽加载，可能减少指令数量或改善访问效率，但它要求指针、范围和布局满足该路径的合同。底层分配对齐，不代表经过切片后的逻辑起点也满足同样对齐。

假设原起点按十六字节对齐，向后偏移一个float后起点加四，不再是同样的十六字节对齐位置。即使剩余元素数量很多，也不能未经检查把这个视图当成原来的宽向量布局。K01的storage_offset现在直接影响指令合法性与性能。

### 2. 尾部不能被宽访问悄悄越过

长度十的数组若每次处理四个元素，前两组覆盖八个元素，最后只剩两个。把最后两个也用不受保护的四元素读取，可能访问到不属于数组的内存。即使最后只写回两个结果，越界读取仍然发生。

可以使用适当的掩码加载、标量尾部处理或明确要求长度满足对齐倍数的接口。不同方案有不同复杂度和性能，关键是不能把尾部合法性寄托在分配器“通常多给一点空间”上。实际分配可访问范围与逻辑合同都需要尊重。

### 3. 编译器可能自动向量化，也可能没有

源码写成四次标量load，不保证最终一定四条独立机器指令；写了某种向量类型，也不保证在所有条件下达到期望的加载方式。编译器会根据类型、对齐、别名和目标进行处理。要确认机器行为，需要观察相应编译产物或工具证据。

学习阶段先写清合同与正确地址，再观察编译器如何实现。不要为了追求一条漂亮指令而牺牲可解释的边界处理。后续K15会教你区分源码、IR、PTX和最终设备指令。

## 第十二课：三种访存故障的完整诊断

### 故障一：数值正确但跨步输入显著变慢

先确认算子是否真的支持该stride，数值通过只说明此次输入符合参考。然后列出同一warp的地址集合，比较连续与跨步版本触及的sector数量。再检查是否增加了隐式连续复制，以及计时范围是否包含复制。

如果地址模型预测更分散，但实际耗时差异不大，可能有缓存复用、问题规模太小或其他瓶颈。不要强行让数据服从预设结论，应该记录模型预测与观测差异，再设计更能区分原因的实验。

### 故障二：shared转置版本比直接访问更慢

检查是否只改变了中转位置，却没有增加复用或改善global地址模式；检查shared列访问是否产生bank冲突；检查额外同步和shared容量是否降低并发机会。一个“用了shared”的实现可以同时增加多项成本，因此变慢并不奇怪。

用小模型先计算bank映射，再加入padding或另一种布局，确认数学结果不变。然后只改变这一项重新测量，避免同时改变tile、线程数和数据类型，使结果无法归因。

### 故障三：第二轮tile计算偶尔混入下一轮数据

在代码中标出每个shared槽位最后一次被读取的位置，以及下一轮第一次被写入的位置。若缺少消费完成到覆盖开始的依赖，就可能发生混用。添加正确范围的阶段同步后，还要保留故障注入版本作为负向验证。

不要仅用一次随机输入判断问题消失。可以使用每轮tile数值差异明显的数据，例如不同轮次乘上不同量级，让混入错误更容易观察；同时覆盖尾块和不同K长度。数值设计可以帮助把时间错误转成可辨识的结果差异。

## 第十三课：十二道练习与完整参考答案

### 练习一：计算对齐连续访问

三十二线程各读四字节，起始地址为四乘lane，sector大小三十二。答案是四个sector，编号零到三。完整解应写出最后一个访问覆盖一百二十四到一百二十七，而不是只看最后起始地址。有效数据量为一百二十八字节。

### 练习二：计算偏移后的覆盖

所有起始地址整体加四后，整体覆盖四到一百三十一，共五个sector。多出的sector只包含尾部部分有效数据。不能直接把五比四当作精确耗时比例，因为模型尚未包含缓存、请求执行和其他瓶颈。

### 练习三：检查跨边界单次访问

~~~python
assert touched_sectors([28], 4, 32) == {0}
assert touched_sectors([30], 4, 32) == {0, 1}
assert touched_sectors([31], 2, 32) == {0, 1}
~~~

这组测试专门验证访问宽度参与计算。若实现只收集起始sector，后两项会失败。题目完整答案还应说明区间右端点为何是起点加宽度减一，而不是起点加宽度。

### 练习四：对比四线程小模型

设sector八字节、每线程读两字节，四线程连续地址零、二、四、六只触及一个sector；若地址改成零、八、十六、二十四，则触及四个。这个缩小模型保留了分散访问的结构，便于纸上演算，但不能把它当作实际GPU sector规格。

### 练习五：证明广播不等于不同word冲突

输入三十二个word零，bank_degree为一；输入零、三十二、六十四等三十二个不同word，结果三十二。参考解释必须指出集合去重按完整word地址进行，bank映射只决定分组，不能代替数据身份。

### 练习六：推导padding

在四bank模型中，行跨度四导致列访问bank号固定；行跨度五使bank号随lane增加一。推广到三十二bank、三十三word跨度得到同样结构。答案不能只写“第二维加一”，还要写出地址对bank数取余的推导，并指出它依赖当前word宽度模型。

### 练习七：实现带padding的打包器

~~~python
def pack_rows(matrix, pitch):
    rows = len(matrix)
    cols = len(matrix[0]) if rows else 0
    if any(len(row) != cols for row in matrix) or pitch < cols:
        raise ValueError('rectangular matrix and sufficient pitch required')
    storage = [None] * (rows * pitch)
    for r in range(rows):
        for c in range(cols):
            storage[r * pitch + c] = matrix[r][c]
    return storage

packed = pack_rows([[0, 1], [10, 11]], 3)
assert packed == [0, 1, None, 10, 11, None]
~~~

None表示padding槽位不属于逻辑数据，消费者不得把它当作有效元素参与数学运算。实际GPU程序可能把padding初始化为某个中性值，但逻辑边界仍要明确。打包改变的是物理行跨度，不改变逻辑列数。

### 练习八：画出共享缓冲区阶段

参考答案按顺序列出global读取、shared写入、生产完成同步、shared读取计算、消费完成同步、下一轮覆盖。解释第一屏障防止读未完成数据，第二屏障防止覆盖仍被读取的数据。只写两个同步函数名不算完成。

### 练习九：判断shared是否带来复用

若每个线程只把一个输入写shared再读回一次，且没有交换和其他布局收益，不能仅凭shared声明推断更快。若一个加载值被同block十六个输出计算复用，则存在减少重复global请求的机会。实际收益还要扣除shared访问、同步和资源成本。

### 练习十：解释local memory名称

完整答案应说明它通常表达线程私有的访问空间，而非保证片上低延迟存储。大局部数组或寄存器压力可能导致相关存储访问，需看编译与性能证据。不能把源码局部变量、寄存器和local memory三者直接画等号。

### 练习十一：设计一次能归因的性能对比

保持数学操作、输入dtype、shape和测量范围相同，只改变shared行跨度，比较原布局与padding布局。先通过同一数值oracle，再记录耗时与相关访存指标。若同时换tile和线程数，结果就不能单独归因于bank冲突改善。

### 练习十二：写出宽加载的边界合同

参考答案包含逻辑首地址对齐要求、每次加载宽度、元素类型、长度尾部处理、是否允许跨行、输入步长约束和输出别名规则。一个宽加载优化只有在这些条件满足时才属于合法候选，不能以某次没有崩溃替代合同验证。

## 第十四课：小项目——从地址生成器到访存解释报告

项目第一阶段输入线程数、元素宽度、起点偏移和元素stride，输出每个线程的字节区间与触及sector集合。第二阶段输入shared的word地址，输出每个bank对应的不同word集合。第三阶段为行访问、列访问、转置和padding生成数据，验证模型结果。

第四阶段选一个现有CUDA或Triton加载表达式，按同样方法建立地址表。先只讨论相对地址，不直接读取任意真实内存。第五阶段在可用GPU环境中运行有界正确性与性能实验，把模型预测与实际结果并列，而不是只保留符合预期的数据。

报告至少包含一个预测正确的案例和一个模型不足以解释的现象。后者可能来自缓存、指令生成、资源占用或测量范围。能够明确模型边界，比把所有现象都归结成一句“合并访问更快”更接近真正掌握。

## 第十五课：把访存分析接到后续算子

Softmax需要先读一行求最大值，再求指数和，最后归一化，是否保留中间值影响读取与存储次数。GEMM需要让A和B在多个输出间复用，tile决定复用范围与shared/register代价。Attention需要避免把巨大的分数矩阵反复写入外部存储，在线状态则保留必要统计量。

这些算法的数学定义不同，但本章提供统一分析入口：每个阶段读哪些地址，写哪些地址，数据在何处被复用，谁拥有输出，阶段间有什么依赖。接下来的归约、矩阵乘法和在线注意力，将把这些问题与具体公式一起推导，而不是把性能当作公式之外的附加标签。

## 工作坊一：完整拆解一个分块转置Kernel

### 1. 直接转置的两个访存方向

输入为行优先矩阵，若相邻线程沿输入同一行读取，它们的global load地址连续。转置输出要求原来的行列交换，直接把这些线程的结果写到输出同一列时，store地址却可能跨很大步长。反过来，让输出连续，又可能使输入分散。问题来自生产者与消费者需要不同的轴排列。

共享tile提供一个中间交换点：先按有利于输入的线程映射加载，写入shared；同步后由另一种线程映射读取shared，再按有利于输出的方向写回。数学上还是同一个转置，变化的是哪一个线程负责把某个值送到输出。

下面给出一个固定tile边长三十二、每block使用三十二乘八线程的教学Kernel。每个线程处理四个相隔八行的位置，所有线程仍在同一个block内协作。它是完整的设备算法，host分配、launch和错误检查沿用K03流程；当前环境没有编译或运行这段GPU代码。

~~~cpp
template <int TILE = 32, int ROWS_PER_BLOCK = 8>
__global__ void transpose_tiled(const float* input,
                                float* output,
                                int height, int width) {
    static_assert(TILE % ROWS_PER_BLOCK == 0, "whole row groups required");
    __shared__ float tile[TILE][TILE + 1];

    int input_col = blockIdx.x * TILE + threadIdx.x;
    int input_row = blockIdx.y * TILE + threadIdx.y;

    for (int j = 0; j < TILE; j += ROWS_PER_BLOCK) {
        int row = input_row + j;
        tile[threadIdx.y + j][threadIdx.x] =
            (row < height && input_col < width)
            ? input[row * width + input_col] : 0.0f;
    }
    __syncthreads();

    int output_col = blockIdx.y * TILE + threadIdx.x;
    int output_row = blockIdx.x * TILE + threadIdx.y;

    for (int j = 0; j < TILE; j += ROWS_PER_BLOCK) {
        int row = output_row + j;
        if (row < width && output_col < height) {
            output[row * height + output_col] =
                tile[threadIdx.x][threadIdx.y + j];
        }
    }
}
~~~

launch必须使用与模板相配的block形状三十二乘八，grid按输入宽度和高度分别向上取整为tile数。模板参数ROWS_PER_BLOCK并不会自动强迫实际launch满足约定，所以包装器应固定配置或进行验证。只看函数里static_assert，不能推出运行时blockDim一定正确。

### 2. 从输入加载看每个线程负责什么

threadIdx.x选择tile内列号，threadIdx.y选择第一组行号。循环j依次为零、八、十六、二十四，因此同一个线程覆盖四个tile内行。一个block总共二百五十六线程，每个线程四次加载，覆盖一千零二十四个tile槽位，恰好等于三十二乘三十二。

每轮中，一个warp的x从零到三十一、y固定，因此读取同一输入行的连续三十二列。边界条件同时检查输入行和列。无效位置写零，使shared每个槽位都有本轮明确值；虽然合法输出的读取映射应对应合法输入，显式初始化仍使教学状态更容易检查。

第一次同步保证所有加载写shared完成后，任何线程才进入转置读取阶段。这里没有下一轮覆盖同一tile的循环，所以不需要在函数末尾再为同一block内的后续复用建立第二个阶段屏障；若把一个block改成循环处理多个tile，就要重新分析复用边界。

### 3. 输出阶段为什么交换block坐标

转置后的输出高度是原width，输出宽度是原height。输入位于块行by、块列bx的tile，转置后位于输出块行bx、块列by。因此output_row使用blockIdx.x，output_col使用blockIdx.y。只交换shared读取下标，却不交换输出块坐标，会在多tile矩阵上得到错误拼接。

输出地址使用row乘原height，因为原height现在是输出的列数。这也是常见错误点：程序员记住输入的row乘width公式，却忘记转置以后矩阵shape已经交换。非方阵测试能直接暴露这种错误，方阵可能掩盖部分问题。

shared读取采用tile的第一下标为threadIdx.x，第二下标为threadIdx.y加j。它与加载阶段的下标顺序互换。于是一个线程可能消费另一个线程生产的值，shared和同步正是为了合法完成这种交换。

### 4. 追踪一个非对称元素

输入为三行五列，值定义为一百乘行加列。原位置行二、列四的值为二百零四。加载阶段由thread坐标x四、y二、j零把它放到tile[二][四]。输出阶段需要把它写到行四、列二，由thread坐标x二、y四、j零读取tile[二][四]完成。

生产线程和消费线程不同，但它们通过共享槽位和屏障建立明确关系。输出地址为四乘三加二，等于十四，是输出五行三列的最后一个元素。输入地址为二乘五加四，也等于十四，在这个特定末元素例子里偏移碰巧相同；因此还应追踪原行一列三，输入偏移八、输出行三列一偏移十，避免被巧合掩盖。

### 5. padding怎样作用于这个读取模式

输出阶段某个warp里x依次变化，y加j固定，因此它读取shared同一逻辑列的不同行。若物理行跨度为三十二word，所有lane映射到同一bank；改成三十三后，bank号随x变化，符合前文模型的分散关系。

加载阶段按shared行连续写，增加一个padding槽位并没有把有效三十二列拆散。这样同一个物理布局同时服务加载阶段的行访问和输出阶段的列访问。这个例子展示padding的具体用途，而不是只在数组声明里神秘地加一个数字。

### 6. 完整验收集合

至少验证一乘一、三乘五、三十二乘三十二、三十三乘十七以及多个tile组成的非方阵。每个输出都与CPU转置结果比较，输入使用可追踪编号。尾部形状检查无效线程是否仍参与同步，跨tile形状检查block坐标交换，非方阵检查输出行跨度。

再制造三个错误版本：删除输出块坐标交换、把输出地址乘数误写成原width、把shared读取下标改回加载顺序。每个错误都应被某个指定用例击穿。只有这样的负向控制，才能证明测试真正覆盖了转置机制。

## 工作坊二：用最大公约数理解规则Bank冲突

### 1. 规律来自模运算

在三十二bank、四字节word模型中，线程lane访问地址base加lane乘stride。bank号等于这个表达式对三十二取余。随着lane增加一，bank号每次前进stride模三十二。它会在某个循环长度后回到起点。

若stride与三十二互质，例如一、三、五或三十三，完整三十二个lane会遍历全部bank。若stride为二，只访问其中十六个bank，每个bank可能接收两个不同word；若stride为四，只访问八个bank；若stride为十六，只访问两个bank；若stride为三十二，只访问一个bank。

在这个受限模型、完整三十二lane且地址不同的条件下，最大冲突程度与stride和三十二的最大公约数相关。这个结论帮助你快速预测规则模式，但不能覆盖广播、部分lane、跨word宽访问和所有真实指令细节。先明确条件，再使用数学捷径。

### 2. 缩成八bank验证公式

取八个bank和八个lane，stride为三时地址模八依次为零、三、六、一、四、七、二、五，全部不同；stride为二时依次为零、二、四、六、零、二、四、六，每个使用bank出现两次；stride为四时只在零和四之间交替。

你可以把这组序列直接打印，再与bank_degree比较。这样最大公约数不是需要盲信的新公式，而是对已观察模循环的总结。遇到不满足条件的访问模式，返回集合枚举法仍然能够正确计算教学模型。

### 3. 部分lane与访问宽度会改变问题

若只有前五个lane有效，完整warp的循环规律不再直接给出实际冲突程度。某个bank在完整三十二lane中会被访问四次，但有效子集中可能只有一次。掩码改变了参与集合，因此分析必须使用实际有效地址。

若每个线程读取两个相邻word，也要把一条指令的访问宽度及硬件处理方式纳入。不能把每线程起始word简单代入标量模型后就得出完整结论。学习阶段可以先把宽访问拆成word集合观察覆盖，再查对应指令的具体服务规则。

## 工作坊三：逻辑流量、实际流量和融合的收益

### 1. 向量加法的最小数据量

长度n的float32向量加法，读取a和b各四n字节，写出c四n字节，逻辑有效流量为十二n字节。这是假定每个输入元素使用一次、输出写一次的数学数据量模型，不包含缓存写策略、额外元数据或其他实际传输细节。

若测得设备执行时间为t秒，可以计算十二n除以t作为某种有效带宽指标。必须注明它按逻辑流量计算。如果缓存命中使实际外部流量更少，这个数字不能直接当作外部内存控制器真实带宽。

### 2. 两个逐元素算子分开与融合

设先计算tmp等于a加b，再计算out等于tmp乘scale。分开时第一步读a和b、写tmp，第二步读tmp、写out，并读取或使用scale。忽略小标量scale的流量，逻辑数组流量为二十n字节：两个输入读取八n，加tmp写读八n，再加out写四n。

若融合为out等于a加b的结果再乘scale，中间tmp可以只作为线程局部值，不必写入全局数组。逻辑数组流量回到十二n字节，还可能减少一次launch。但融合也可能增加寄存器压力、限制调度或改变编译效果，因此理论减少流量不等于所有输入下都达到固定比例加速。

重要的是中间值是否需要被其他消费者使用。如果tmp同时还要交给另一个算子，完全消除其存储可能改变整个计算图需求。优化必须看完整消费者关系，不能只盯着两个相邻源码表达式。

### 3. 一个完整的流量表

| 路径 | 读取a | 读取b | 写tmp | 读tmp | 写out | 合计 |
|---|---:|---:|---:|---:|---:|---:|
| 分开两个算子 | 4n | 4n | 4n | 4n | 4n | 20n |
| 融合单个算子 | 4n | 4n | 0 | 0 | 4n | 12n |

这张表故意不写某张GPU的速度，因为它描述算法层面的必要数据活动。你可以先用它提出“融合可能减少中间流量”的假设，再测量实际设备时间和资源变化。若输入很小，launch开销可能占主要部分；若计算复杂，算术与资源限制可能更重要。

### 4. 缓存复用与显式融合并不完全等价

分开两个Kernel时，tmp可能仍留在某级缓存，所以第二步未必从最远外部存储重新读取；但它仍有一个显式全局张量、相关写入与读取指令，以及跨Kernel调度边界。融合则从程序结构上消除这份中间数组，而不只是希望缓存命中。

因此，理论流量表和实际缓存行为可以同时为真。报告中应说明你比较的是逻辑读写次数、分配峰值、设备时间还是某级内存流量，避免把不同层次的指标互相替代。

## 工作坊四：建立一份真正可用的访存实验记录

### 1. 每个实验先写预测

例如：“把行跨度从三十二word改成三十三word，在当前标量bank模型中，列读取从所有lane集中同一bank变成分散；数学输出不变；实际GPU耗时是否改善仍待测。”这句话同时包含可手算结论、正确性要求和未验证性能，不会把三者混在一起。

再写控制变量：输入shape、dtype、线程配置、工作量、计时范围和设备保持相同，只改变shared布局。如果你同时改变tile、循环展开和数据类型，就需要承认实验无法单独归因于padding。

### 2. 保存能解释失败的数据

出现错误时，保存最小输入、第一处不匹配下标、预期值、实际值和相关地址公式。对于布局问题，第一处错误位置往往比整体最大误差更有用。最大误差告诉你偏差有多大，位置和映射告诉你可能读错了哪里。

对于性能问题，保存多次测量的分布，而不只挑最小数字；记录是否包含编译、预热、分配和复制。不要把首次JIT时间与后续缓存运行混在同一个平均值里，再试图用访存模型解释全部差异。

### 3. 给每个结论写适用范围

“这个三乘五输入转置正确”是具体观察；“本算法对所有合法矩阵转置正确”还需要索引证明与系统边界测试；“这个配置在H100上更快”需要该设备与测量证据；“所有NVIDIA卡都更快”则是更强且通常没有得到支持的推广。

这样的写法不会削弱学习成果，反而让你知道下一步缺什么证据。真正深入理解算子，就是能把数学证明、地址证明、资源模型和硬件实测分别说清，再解释它们如何相互支持。

## 最终迁移检查

拿到一个新的Kernel，先不要调参数。写出每条主要加载的线程地址集合，标记元素与字节单位，找出复用范围，列出shared生产消费阶段，再检查输出唯一所有者。若能对一个具体tile完成这些步骤，你就拥有了理解新算子访存结构的通用方法；若只能复述“合并访存、共享内存、缓存命中”几个名词，还需要回到本章的小矩阵继续逐项演算。

## 补充工作坊：从Padding继续理解一个可手算的Swizzle

### 1. 为什么需要另一种布局办法

padding通过增加物理行跨度改变bank映射，直观且容易实现，但也增加存储占用。另一类办法是保持元素数量不变，却重新排列每行内部的物理列，使逻辑行列访问都能分散。真实库中的swizzle形式很多，下面只构造一个八行八列、八bank模型里的完整例子，不声称直接对应某条硬件指令布局。

令逻辑位置为行r、列c，二者都在零到七。物理行仍是r，物理列改成c与r的按位异或。最终word地址为r乘八，加上c异或r。异或运算对每个位分别比较，相同得零，不同得一。因为r与c都只需三个bit表示，异或结果也在零到七。

### 2. 先证明没有丢失或重叠

对固定r，映射c变成c异或r是一种置换，因为再与同一个r异或一次会恢复c。也就是说，每个逻辑列对应唯一物理列，不同逻辑列不会重合，全部八列都能覆盖。不同逻辑行又分别拥有不同的八word区域，因此整个六十四元素映射是双射。

这种证明比打印一个正确输出更强：它解释为什么布局打包不会覆盖掉另一个逻辑元素。之后仍需验证消费者采用相同映射，否则数据虽然被完整保存，读取却可能解释错位置。生产者和消费者必须共享同一布局合同。

### 3. 行与列的bank号分别怎样变化

bank号是word地址对八取余，因此等于c异或r。固定行r、让列c遍历零到七，异或映射遍历所有八个bank；固定列c、让行r遍历零到七，也同样遍历全部bank。于是这个小模型的行访问和列访问都避免不同word集中同bank。

以列三为例，r从零到七时，bank号依次为三、二、一、零、七、六、五、四。它不是按自然顺序零到七递增，但仍然每个bank恰好一次。访存目标常常是分散和复用，不要求bank编号必须有某种漂亮顺序。

~~~python
def swizzled_offset(row, col):
    if not 0 <= row < 8 or not 0 <= col < 8:
        raise IndexError('eight by eight layout required')
    return row * 8 + (col ^ row)

all_offsets = [swizzled_offset(r, c)
               for r in range(8) for c in range(8)]
assert sorted(all_offsets) == list(range(64))
for r in range(8):
    assert len({swizzled_offset(r, c) % 8 for c in range(8)}) == 8
for c in range(8):
    assert len({swizzled_offset(r, c) % 8 for r in range(8)}) == 8

storage = [None] * 64
for r in range(8):
    for c in range(8):
        storage[swizzled_offset(r, c)] = 100*r + c
for r in range(8):
    for c in range(8):
        assert storage[swizzled_offset(r, c)] == 100*r + c
~~~

第一组断言验证全局双射，第二组与第三组分别验证每行和每列的bank分散，最后验证实际打包与读取一致。四种性质不是同一件事，所以分别写出更容易定位错误。

### 4. 为什么不能把这个公式直接套进任意Kernel

实际GPU具有不同的bank数量、访问宽度、线程分组和指令布局要求。一个线程可能一次访问多个word，矩阵指令可能规定特定的片段组织，异步拷贝也可能有自己的布局约束。这个八bank标量模型证明的是一个数学排列的性质，不是任意设备上的性能保证。

而且swizzle增加了地址变换。编译器能否高效实现、是否与global到shared加载路径兼容、是否影响向量化，都需要进一步分析。padding和swizzle各自有空间、计算和兼容性取舍，不能把后者因为名字更高级就视为必然更快。

阅读CUTLASS或Triton布局代码时，可以先用本例建立三个问题：逻辑元素被映射到哪个物理槽位，映射是否一一对应，某组实际消费者访问哪些bank。即使真实公式复杂得多，这三个问题仍然成立。先用小尺寸枚举，再理解代数表达，往往比一开始盯着长模板名更有效。

### 5. 一道完整迁移题

把逻辑矩阵值设为一百乘行加列，先用普通行优先打包，再用本例swizzle打包。比较两份物理数组会发现排列不同；按各自正确描述读取，逻辑矩阵却完全相同。接着故意用普通行优先公式读取swizzle存储，找出第一处错误位置，解释错误来自布局合同不一致，而不是数值算术。

最后在报告中写明：你已经证明八乘八模型中的双射与bank分散，尚未证明某个真实GPU指令使用相同布局，也尚未测得速度收益。这种精确区分能让你把一个有用toy model真正迁移到源码阅读，而不是停留在“我知道swizzle这个名字”。

### 6. 从物理位置反解逻辑位置

一个布局若只会正向映射，调试时仍然不方便。对本例给定物理word偏移p，先用p整除八得到物理行r，再用p对八取余得到物理列q。因为q等于c异或r，所以逻辑列c等于q异或r。异或同一个值两次恢复原值，这给出了明确逆映射。

例如物理偏移二十九，行号为三、物理列号为五，因此逻辑列是五异或三，等于六。该位置应保存逻辑行三列六的值三百零六。你可以在打包后的storage中查这个位置，再与逻辑矩阵对照。反解能够把一个错误物理地址转换成可读的行列身份，帮助判断是行号、列号还是布局变换出了错。

真实框架中的布局调试也受益于这种能力。即使生产实现没有显式逆函数，测试工具仍可在小尺寸上建立从物理位置回到逻辑元素的表。它既能检查遗漏和重复，也能把数值错误定位到具体数据来源，而不是只留下一个没有上下文的巨大地址。

请把正向与逆向映射的往返断言同时加入小项目，确保每个合法逻辑元素和每个有效物理槽位都能恢复原身份。
