# K11　量化算子：值的编码、缩放、打包与累加

先修浮点、整数范围、GEMM。目标是区分量化算法与 Kernel 编码，亲手实现可检查的 INT8 GEMM 和 INT4 打包，理解为何 E2M1、INT4、MXFP4、NVFP4 不能互换。

## 1. 一个量化张量不是一串小整数那么简单

对称整数近似常写成 `x≈s*q`，q 为有限范围整数，s 为 scale。非对称形式还包含 zero point，例如 `x≈s*(q-z)`。按 tensor、按行、按列、按组设置 scale，会改变误差和元数据布局，也影响 GEMM 中何时可以把 scale 提出归约。

本卷 INT8 参考按 A 的每行、B 的每列量化。对于 A 行 i 和 B 列 j，scale 与 K 无关，因此 `C[i,j]≈sa[i]*sb[j]*sum_k qa[i,k]*qb[k,j]`。这允许先做整数点积再缩放。若 scale 沿 K 分组，就不能把所有组的 scale 合成一个常数乘在最终整数和上，需要逐组正确组合。

## 2. 舍入、裁剪与零行

本例使用范围 `[-127,127]` 的对称 INT8，scale 为该行绝对最大值除以 127，零行的 scale 设为 1。q=`round(x/scale)` 后裁剪范围。零行采用有限 scale 避免除零；它的反量化仍是全零。

若数值未被裁剪，最近舍入误差不超过 scale/2。这个界是逐元素量化误差界，不是整个 GEMM 输出误差界：点积会累积许多误差项，某些相消结果还可能出现很大的相对误差。不能看到每个权重量化误差小就直接承诺模型端到端无损。

整数乘加必须在足够宽的类型中累加。本例显式把 q 转为 int32 后再做矩阵乘法，避免 NumPy 的 int8 运算在窄类型中溢出。硬件也有明确的输入与累加格式组合，不能用 W8A8 四个字符代替完整数值契约。

## 3. 四位打包不等于四位算术

有符号 INT4 的常见二补码范围是 -8 到 7。一个字节可保存两个 nibble：低四位放第一个数，高四位放第二个数。编码时取 `q & 15`；解码时若四位代码≥8，就减 16 进行符号扩展。奇数个元素需要补齐半字节，并单独保存逻辑元素个数，否则最后一个 padding 会被误当数据。

打包减少存储和带宽，不意味着 Python 或所有 GPU 指令都能直接用这种布局乘法。Kernel 可能先解包、反量化再计算，也可能使用硬件支持的低位矩阵路径。两者的性能和误差条件不同。

```bash
python -m labs.kernels.run --lab 17
python -m labs.kernels.run --lab 18
python -m labs.kernels.run --lab 19
python -m labs.kernels.run --lab 20
```

K18 遍历全部十六种 INT4 值进行无损打包回读。K19 的 E2M1 正幅值为 `0,.5,1,1.5,2,3,4,6`，带符号后仍不是 -8..7 的均匀整数网格。代码 7 在 E2M1 中是 6，而在有符号 INT4 中是 7。仅知道“每个值四位”不足以解释含义。

## 4. Block scaling 还增加一层契约

MXFP4、NVFP4 等体系将低位数值与分块缩放格式组合。理解它们时至少核对：低位元素编码、块大小、块 scale 的类型、是否另有全局 scale、舍入和饱和规则、矩阵指令期待的布局。不要把具体标准的名称当作所有四位浮点的通称。

本卷只实现 E2M1 值表和整数缩放参考，不声称实现完整 MXFP4/NVFP4 序列化或硬件 GEMM。想扩展时，先从公开格式文档逐字段写编码/解码测试，再验证与真实库兼容。把一个 float 数组随意分组、除一个 scale、舍入到最近 E2M1 值，可以用来理解原理，但只有满足全部格式契约才能使用相应标准名称。

## 5. 为什么不同 GPU 后端不同

低精度支持包含多个层次：能存储字节、能解包模拟、能用专门矩阵指令高效算、框架后端是否实现、模型量化方案是否匹配。H100 能运行某种四位权重反量化 Kernel，不等于它有与某款 Blackwell 相同的原生四位矩阵吞吐路径。框架的 Marlin、Triton、CUTLASS 等后端还可能面向不同格式和 shape。

性能比较必须写清 W/A 类型、scale 粒度、累加精度、是否包括量化/解包、batch 与矩阵形状。只写“INT4 比 FP16 快”没有足够含义。

## 6. 练习与参考答案

1. **手算。** x=`[-1,0,.5,1]`，INT8 scale=1/127，q 是什么？答案大致 `[-127,0,64,127]`，具体中点行为取决于舍入规则；反量化 .5 项存在约 .00394 的误差。
2. **打包。** INT4 `[-1,2]` 如何装入字节？答案低 nibble 为 15，高 nibble 为 2，字节为 `0x2F`。解包低位得到 15 后减 16，恢复 -1。
3. **溢出。** 16 项全为 127 的整数点积是多少？答案 258064，显然不能存在 int8 中；实验在 cast 前后比较，解释错误来自累加类型而非量化本身。
4. **分组。** 将 K 分为两组、每组 scale 不同，推导正确 GEMM 反量化。答案分别计算各组整数和乘各自 scale 乘积，再相加；不能先合并整数和再乘一个平均 scale。
5. **误差测试。** 增加一个非常大的离群值，观察按行量化其余小数的误差。参考：scale 被离群值拉大，分辨率下降；按组可改善但增加元数据和算子复杂度。
6. **源码任务。** 在真实量化后端找到 scale 张量形状、权重 packing、累加 dtype 三处证据。验收给出特定模型层尺寸的映射，不以量化名字猜实现。若没有真实 GPU，完成静态阅读与 CPU 编解码，GPU性能留作明确未验证项。
