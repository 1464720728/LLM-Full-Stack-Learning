# K17　Warp 分工、Persistent Kernel 与 MegaKernel

先修 K06、K13、K16。本章把单算子的分工扩大到设备侧任务执行。重点是依赖、资源和正确性；这些技术不能靠把 Kernel 写大就自动获得收益。

## 1. 三个独立问题

Warp Specialization 将不同 Warp 或 Warpgroup 分配给不同角色，例如数据生产者、矩阵消费者、后处理者。Persistent Kernel 让一组较长驻留的工作单元不断取得任务，复用执行环境。MegaKernel 将更大的计算子图组织在同一个 Kernel 中，可能覆盖多个算子、层或更大范围。

它们常被组合，但不是同义词。一个普通 GEMM 可以有 Warp 分工；一个 Persistent Kernel 可以只处理同类小任务；一个融合算子也不必有动态任务队列。读论文时先问融合范围、驻留时间、调度位置三件事，不用一个标签推导全部实现。

## 2. 生产者—消费者协议

设两个共享缓冲区，消费者计算 A 时，生产者加载 B。每个缓冲区需要状态和代际信息：EMPTY 表示可写，LOADING 表示传输未完成，READY 表示可读，COMPUTING 表示仍被消费。循环复用时，简单布尔 ready 可能混淆不同轮次；阶段位或计数器用于区分代际。

生产者发起异步搬运，不等于数据已经完成；消费者发起异步矩阵运算，也不等于它已不再读取操作数。因此“发起”“可见”“完成”“可复用”是四个不同时间点。屏障或完成机制应与真实硬件操作对应，而不是随便在代码里多放几个同步调用。

可以先在 CPU 写状态机，故意模拟生产者过快或消费者过慢，验证不会覆盖或读取空缓冲。这个模型不证明 GPU 内存序正确，但能检查高层协议。随后阅读 CUTLASS 的 pipeline 类，将状态机转移映射到具体 barrier 操作。

## 3. 为什么专职搬运可能有帮助

不同角色可以保持不同的指令流与资源需求，减少同一批线程来回切换搬运/计算逻辑，并利用异步硬件使工作重叠。另一方面，专职角色也占用线程与寄存器，角色不平衡可能让部分 Warp 空等，更多缓冲区也消耗 Shared Memory。

Hopper WGMMA 需要特定 Warpgroup 协作，真实分工必须尊重该粒度。一个教学图画出“Warp0 load，Warp1–3 compute”，只能表达概念，不代表合法 WGMMA 启动。计算参与线程、搬运发起线程、屏障参与计数必须分别核对。

## 4. Persistent 的任务获取

传统 Grid 一次性把任务映射到许多 Block。Persistent 设计让数量较少的 Block 驻留并循环获取任务，可能通过原子计数器或预先安排的队列。它能在不规则工作中改善负载均衡，也能复用某些状态，但引入任务分配开销和终止协议。

队列中的“任务已领取”与“任务已完成”要区分。依赖任务只能在数据真正完成并满足可见性条件后放行。若一个工作单元领取了无法满足依赖的任务并一直自旋，可能阻塞本应完成依赖的其他工作。正确系统需要避免这种资源占用与依赖等待的循环。

## 5. MegaKernel 的机会与风险

融合多个算子可以减少启动、全局中间结果写回和粗粒度边界，并在数据依赖允许时更早启动后续 Tile。机会来自计算图的具体结构，不是“所有操作塞进一个函数”本身。

风险包括寄存器/Shared Memory 压力、代码体积与指令缓存、复杂同步、动态 shape、模型结构变化，以及难以复用已经高度优化的独立库 Kernel。大 batch GEMM 本已充分利用矩阵硬件时，重新写成大融合程序未必更快。多 GPU 情况还要协调通信完成与数据可见性。

不要根据某个模型、batch=1 的结果，宣称整套推理框架可被全面替代。有效评估应同时看正确性、支持范围、编译成本、调试成本、真实端到端收益和维护负担。

## 6. 阅读真实实现的方法

第一遍只找 worker 循环、任务描述、队列、依赖计数、结束标志。第二遍找缓冲区所有权与代际，画出数据生产和消费关系。第三遍才跟进每个任务的 GEMM/Norm/Attention Kernel 细节。这样可避免一开始被数千行指令和模板淹没。

官方 CUTLASS 的 Warp-specialized GEMM 是较好的中间台阶：它的融合范围仍清晰，但已经有真实异步流水线与架构约束。关于更大范围 MegaKernel，应固定所读项目 commit，区分论文设计与仓库中实际可运行配置。

## 7. 练习与参考答案

1. **概念分类。** 一 Kernel 循环处理一千个独立向量，是 MegaKernel 吗？答案可能是 Persistent 工作处理，但是否叫 MegaKernel 取决于所融合计算范围；术语不是严格统一标准，应描述机制。
2. **协议。** 为什么“搬运指令发出”不能把 buffer 标为 READY？答案传输异步尚未完成，消费者可能读到旧数据；必须等正确的完成条件。
3. **死锁。** 所有驻留 Block 等待一个尚未驻留 Block 的结果，会怎样？答案可能永远无法释放资源让依赖者运行；避免未约束的全局自旋屏障。
4. **性能。** 将生产者 Warp 数翻倍一定更快吗？答案不一定；若计算是瓶颈，多生产者只增加资源竞争。先用流水线模型定位 L/C，再测真实资源。
5. **设计任务。** 写两缓冲区、五任务的状态机测试，模拟任意合法交错。参考不变量：每个任务恰好一次；READY 必须来自完成的写；COMPUTING 时不可覆盖；终止时无遗留任务。
6. **源码拓展。** 找一个 CUTLASS Warp-specialized 主循环，列出 producer acquire/commit、consumer wait/release 的对应动作。验收解释一次完整代际循环，不能只抄方法名。

掌握门槛：能从依赖与资源解释为何分工可能加速，也能给出会死锁或更慢的具体反例；阅读大 Kernel 时先定位运行时协议。
