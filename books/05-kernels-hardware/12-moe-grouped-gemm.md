# K12　MoE 算子：路由之后，数据怎样交给专家

先修模型卷 MoE、K06 GEMM 和索引基础。本章关注执行层：token 被分配到多个专家后，怎样打包、计算、还原并累加回原位置。

## 1. 不规则工作从路由产生

稠密 MLP 通常让所有 token 乘同一组权重。MoE 的 router 为每个 token 选择一个或几个专家。即使每个专家内部都是常见 GEMM，专家收到的 token 数也可能不同，有的为空，有的非常多。于是矩阵乘法的 M 维变成了每个专家不同的动态值。

设四个 token，每个选两个专家，共八次 assignment。assignment 不等于八个不同 token：同一个 token 可在多个专家出现。如果路由异常或教学输入允许重复专家，同一个 token 在同一专家里还可能出现多次。正确还原需要按 assignment 的门控权重累加，不能简单赋值覆盖。

## 2. 先构造明确的索引表

对每个 assignment 保存 `(token_id, slot_id, expert_id, gate)`。按 expert_id 分组，形成每个专家的输入 token 列表。对专家 e，取 `X[token_ids]` 与 `W[e]` 做矩阵乘法，得到局部输出；乘对应 gate；最后把局部结果 scatter-add 回原 token。

为了让打包与解包可逆，必须保留原 token 的对应关系。只把向量按专家排序、却丢掉排序逆映射，就无法恢复输出顺序。稳定排序还可帮助复现调试，但并不独自保证整个浮点计算 bitwise 确定。

`grouped_experts` 使用 `np.nonzero(ids==expert)` 找出 token/slot，`np.add.at` 完成带重复索引的累加。为什么不用 `out[token]+=result`？NumPy 的高级索引更新在重复索引时不等价于逐项累加，可能丢失贡献。这个细节非常适合作为从数学进入实际代码的练习。

## 3. 手算一个有重复路由的例子

token x=`[3,4]`，两个 assignment 都指向专家 1，专家权重为 `2I`，gate 为 .4 与 .6。专家各次输出都是 `[6,8]`，最终结果 `.4*[6,8]+.6*[6,8]=[6,8]`。若用覆盖写，可能只留下 `[3.6,4.8]`；若忘记 gate，则得到 `[12,16]`。只测 top-1、唯一索引会掩盖这两个 bug。

```bash
python -m labs.kernels.run --lab 21
```

输出 counts 的和应为所有 assignment 数，最终输出行数仍等于 token 数。这两个尺寸不变量帮助你从复杂 dispatch 代码里确认数据有没有丢失或重复。

## 4. Grouped GEMM 与 padding

为每个专家单独启动一次小 GEMM，启动与调度开销可能很明显。Grouped GEMM 把多组矩阵问题放入同一执行组织中，让工作单元处理不同专家的 Tile。它不等于把所有专家权重拼成一个普通大矩阵直接相乘，后者可能计算大量不需要的交叉项。

另一种做法把每个专家 token 数补齐到某个 Tile 大小。这样布局与矩阵路径更规整，但增加 padding 工作。若某专家只有一个 token、Tile 要求很多行，浪费会明显。应统计实际 token 分布、padding 比例和长尾，而不是只看平均每专家 token 数。

Capacity 限制、丢弃或重路由会改变语义。一个执行器不能为了方便，未经定义就把超出容量的 token 静默丢掉。训练负载均衡损失与推理运行时如何调度也属于不同层级：前者影响路由分布，后者处理当前这次分布。

## 5. 从单 GPU 到 EP

当专家分布在多个 GPU，dispatch 还要通过 All-to-All 或其他通信把 token 送到专家所在设备，再把结果送回。此时 token 索引、源 rank、专家本地编号与 gate 都须正确对应。通信与计算可以按块重叠，但依赖关系不能省略：计算只能消费已到达的数据，输出归并只能读已完成的结果。

本卷 CPU 实现只验证本地数学与索引，不模拟 NCCL 的真实拥塞和内存可见性。学习顺序是：先验证路由与归并→再用单 GPU 不同专家数量→再用两 GPU 验证 dispatch/return→最后才扩展八 GPU 性能。无必要时不要直接启动八卡。

## 6. 练习与参考答案

1. **尺寸。** T=5、top-k=2、E=3，共多少 assignment？答案 10；各专家 count 之和为 10，但不保证平均或每专家非空。
2. **手算。** x=`[1,2]`，专家为 I 与 2I，gate=.25/.75，输出？答案 `[1.75,3.5]`。测试本卷已有这个数值。
3. **故障。** 把 `np.add.at` 改成普通高级索引 `+=`，用重复路由测试。答案可能丢失重复贡献；参考修复为真正的 scatter-add 或先对重复索引归约。
4. **padding 实现。** 每专家补齐到 4 的倍数，同时保留有效数。参考：padding 行输入零，输出只按有效 assignment 归并；统计有效/总行比例，不能把 padding 算入真实吞吐 token 数。
5. **gate 规范。** 是否必须先归一化 top-k gate？答案取决于模型定义；执行器应实现模型给出的语义，而不是认为“概率应该加一”就擅自处理。设计两种模式并写清差异。
6. **工程任务。** 给 grouped executor 加日志：token数、assignment数、每专家计数、最大/平均负载、padding比例和输出校验。验收包含空专家、全部token同专家、重复assignment和非法专家ID；非法输入应失败而非读错权重。

掌握门槛：独立实现 dispatch、专家计算、加权归并，并用索引不变量检查；阅读真实 MoE 后端时能识别 packing、grouped GEMM、通信与 combine 的职责。
