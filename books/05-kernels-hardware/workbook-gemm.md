# 工作簿 W2：从三重循环到 CUDA/Triton GEMM

本工作簿承接 K06，要求你亲手实现、跟踪并修改一个矩阵乘法。目标是读到真实 GEMM 时能识别每个层级负责什么。实验从 CPU 开始，只有设备验证和性能阶段才用 GPU。

## 阶段一：把形状和归约写成契约

A 为 `[M,K]`，B 为 `[K,N]`，输出 `[M,N]`。先只支持连续二维浮点输入，不支持广播、不支持转置标志、不原地更新。检查 A 与 B 的 K 相同，并说明空维度如何处理。教学 NumPy参考允许某些空形状自然得到零输出，但设备包装选择非空矩阵，这是明确的支持范围差别。

把输出 `C[i,j]` 的归约过程写成三重循环。不要一开始用 `np.matmul` 实现自己的 oracle，那只能验证接口调用。先用整数小数据确保可以逐项追踪，再用浮点随机数据检查数值。

本工作簿使用 A=`[[1,2,3],[4,5,6]]`，B=`[[1,0],[0,1],[1,1]]`。分别计算四个 C 元素。C[0,0]=1+0+3=4，C[0,1]=0+2+3=5，C[1,0]=4+0+6=10，C[1,1]=0+5+6=11。每个输出有三个乘法，但共享许多输入值；这就是后续复用的来源。

## 阶段二：地址表比代码更先出现

为 A、B、C 写行优先地址公式：A 偏移 `i*K+k`，B 偏移 `k*N+j`，C 偏移 `i*N+j`。在纸上列出计算 C[1,1] 访问的 A 偏移3、4、5以及B偏移1、3、5。你应该能从展平数组中独立找回对应值。

现在故意写错 B 索引为 `j*K+k`。它把 B 当成转置后的连续布局读取。对某些特殊数据，错误可能不明显；本例错误结果为 `[[1,6],[4,15]]`，与正确矩阵差异清楚。运行：

```bash
python -m labs.kernels.workbook gemm
```

输出同时展示正确和错误结果。注意错误不是“矩阵乘法公式不对”，而是公式中的 B[k,j] 被映射到了错误地址。GPU 算子的大量 bug 就发生在这种数学与布局的接口。

## 阶段三：只切 K，观察累加器

先保持输出整个2×2矩阵，每次只读两个K位置。第一轮 k=0,1，A块为 `[[1,2],[4,5]]`，B块为单位阵，贡献就是 `[[1,2],[4,5]]`。第二轮只剩 k=2，补齐A块为 `[[3,0],[6,0]]`，B块为 `[[1,1],[0,0]]`，贡献 `[[3,3],[6,6]]`。两轮相加得到最终结果。

这里有三个需要记住的状态：当前 K 起点、这一轮真实有效 K 数、已经累计的 C Tile。补齐零是因为乘法归约的加法单位元为零；若填充未初始化值，会把无意义乘积加进结果。对于其他算子，正确补齐值不一定是零，这点已经在 Softmax 工作簿见过。

你应先实现一个返回每轮 trace 的 CPU 函数，打印本轮 A/B、贡献和累加器。再把 trace 关闭用于测试。调试信息与算法核心分离，避免未来大输入打印占满内存。

## 阶段四：再切 M 和 N

把输出划成 BM×BN Tile，外层循环按 i/j 选择 Tile，内层按 BK 遍历归约。此时三个块尺寸可以不同。选择 M=3、N=5、K=7、BM=2、BN=3、BK=4，主动让每个方向都有尾部。

列出每个输出 Tile 的逻辑范围：第一个是行0..1、列0..2，第二个是行0..1、列3..4，第三个是行2、列0..2，第四个是行2、列3..4。每个合法 C 元素恰好属于一个 Tile；每个 Tile 内的 K 循环覆盖0..6一次。这两个证明分别解决输出不重叠和归约不遗漏。

NumPy 切片会自然截断尾部，CUDA/Triton 通常需要显式 mask。别让 Python 自动处理边界的便利掩盖你对设备地址的责任。给自己的 CPU 实现加一个“显式补齐”版本，再与自然切片版本比较，有助于提前发现 padding 设计错误。

## 阶段五：一个线程先负责一个输出

在 CUDA naive 版本中，row 与 col 从二维 Grid/Block 算出，合法线程沿K循环累加一个标量。这个版本不需要 Block 内数据交换，因此边界线程可直接返回，不会影响后续屏障——前提是函数确实没有任何要求全体参与的屏障。

把同一个早退技巧直接复制到 tiled 版本就不安全了，因为 tiled 版本有 `__syncthreads()`。这说明“某段模板代码常见”不是证明；必须结合后续控制流和协作范围分析。

建议你自己先写 naive 版本，并与仓库 `matmul<T>` 比较，而不是把 tiled 版本删掉一些语句就当 naive。两个实现的分工不同：naive 每线程独立读全K，tiled 每线程只负责加载一小部分共享数据，却消费其他线程加载的值。

## 阶段六：逐句走过 CUDA Tiled GEMM

`sa[T][T]` 与 `sb[T][T]` 是 Block 共享数组，不是每个线程一份。`threadIdx.x` 选择 Tile 内列，`threadIdx.y` 选择 Tile 内行。全局 row 与 col 加上 Block 对应的输出起点。

每轮令 ak=`p+threadIdx.x`，bk=`p+threadIdx.y`。线程把 A[row,ak] 放入 sa[ty,tx]，把 B[bk,col] 放入 sb[ty,tx]。虽然两次写入共享数组使用相同局部下标，它们从全局读取的维度角色不同：A沿K横向移动，B沿K纵向移动。把这两个加载公式写反，会造成难以发现的转置错误。

第一次屏障后，每个线程做 `sum += sa[ty][j]*sb[j][tx]`。固定输出 row/col，j沿当前K块移动，正好恢复 GEMM公式。此时 sa一行被同一输出行的多列线程复用，sb一列被多行线程复用。你可以数一下同一个共享值被几个输出消费，而不是笼统说“减少访存”。

第二次屏障保护复用：任何线程都不能开始下一轮写共享数组，直到所有线程读完当前轮。某些 Warp 先完成与另一些后完成是正常的，不能用“线程大致同时跑”代替同步。

最后只对合法 row/col 写 C。无效输出线程仍然参与了前面的共享加载、计算和同步；它们的额外计算是尾部成本。更高级实现可以减少浪费，但第一版正确性优先。

## 阶段七：从线程表达转到 Triton 块表达

Triton版本的 rows 是长度BM向量，cols是长度BN向量，k是长度BK向量。`rows[:,None]*K+k[None,:]` 利用广播生成BM×BK地址矩阵。`k[:,None]*N+cols[None,:]`生成BK×BN地址矩阵。初学时建议在 NumPy 中用相同广播表达式打印偏移表，确认每一格对应正确元素。

两个load各有二维mask：A要求row<M且k<K，B要求k<K且col<N。`tl.dot`执行块矩阵乘加。累加器shape是BM×BN，在每轮K迭代中更新。最终输出mask要求row<M且col<N。三个mask分别保护不同张量，不能只在最终store做边界检查就认为输入也安全。

包装函数把BM/BN/BK设为16/16/32，易于阅读与小规模验证。修改为更大值前，先理解它对布局、编译器资源和输入精度的影响。并非所有shape和dtype组合都支持任意Tile；编译失败时记录配置，而不是一口气改许多常量直到“能跑”。

## 阶段八：精度不是测试后的附注

`tl.dot`的输入精度模式影响实际计算路径。教材使用明确的float32输入和IEEE模式，便于建立起点。若为了性能切换其他模式，应同时记录绝对误差、相对误差和输入分布。考虑结果接近零的点积：真实结果由大正负项相消得到，绝对误差很小也可能有巨大相对误差。

验证可以使用 `abs(err)<=atol+rtol*abs(ref)`，但阈值应基于当前规模和数值契约。不要遇到失败就不断放宽到PASS。先检查错误是否集中于尾部、整行、某一列或所有元素；结构化错误通常是索引问题，随机小幅差异才可能是舍入。

测试矩阵至少包含单位阵、全零、可手算整数、随机浮点、非方阵、三个维度都不整除、极小K。单位阵有利于看出布局，但仅测单位阵可能掩盖一部分乘加路径；多种数据互补。

## 阶段九：加一个真实功能，而不是只改参数

选择加入bias。bias形状为N，输出每列加对应值。CPU公式为 `A@B+bias[None,:]`；CUDA输出前按col读取；Triton在epilogue广播加载。验收检查bias全零、不同列不同值、N尾部。这个扩展迫使你同时修改包装契约、地址、mask和测试，远比把Tile从16改成32更能证明理解。

再选择加入 `alpha AB+beta C0`。若beta=0，是否仍需读取C0？数学上不需要；接口可以允许C0省略，但这会增加分支和契约。第一版可以要求C0始终存在并合法，再做优化。切勿让一个本应不读取的输入仍在Kernel中越界，只因最终乘零就认为安全。

## 阶段十：一次有边界的计时

本卷提供短基准：

```bash
CUDA_VISIBLE_DEVICES=0 python -m labs.kernels.benchmark \
  --run --op matmul --size 256 --repeats 20
```

它先检查数值，报告首次调用墙钟时间，再用GPU Event测稳定重复。它只接受有界尺寸和重复次数，输出说明不包含Host到Device拷贝，也不是服务端到端延迟。运行时的内存分配、缓存和其他租户仍可能影响结果，因此不能把单次结果当作硬件能力上限。

先测256再测512，不要直接在共享卡上用最大矩阵长时间压力跑。若自己的实现比库慢很多，这是正常学习阶段。用数据流解释差距：库可能有更好的Tile、Tensor Core、流水线、布局与调度。你现在具备的是能读懂这些优化在改变什么的基础。

## 加练：区分布局改变、数学转置与转置标志

实际库接口常允许转置标志。假设存储中保存B的转置，逻辑计算仍希望得到AB。你可以改变寻址而不真正复制数据，也可以提前转置成连续布局后调用原Kernel。这两种路径的数学结果相同，但内存开销和执行性能可能不同。请分别实现CPU参考：一种传入形状与stride解释视图，一种显式复制。比较输出时必须相同，计时时必须写明是否包含复制。

用A形状2×3、逻辑B形状3×5做实验。非方阵能让错误的K/N立即暴露。画出物理存储与逻辑访问表，说明转置标志改变的是哪一个下标公式。如果你只是把M与N交换，却没有处理A/B的含义，得到的就不是同一个矩阵乘法。

再研究拆K。把K分成两个区间，分别计算partial C，再相加。数学上仍等价，但多了中间输出与最终归约，也改变浮点加法顺序。它可能改善某些小M/N、大K问题的并行度，却不保证更快。CPU先验证两partial之和，再写设备实验，记录额外内存与launch。不得只报告局部GEMM时间而遗漏归约阶段。

最后故意制造一个“全部值都正确但写入有竞争”的设计：两个Block计算同一个C Tile并都直接写回。对于完全相同的计算，结果可能每次都一样，但这不证明设计合理；如果后续加入bias、累加或不同partial，竞争就会改变结果。正确性需要工作所有权证明，不能仅靠数值相等。请用Tile编号枚举验证每个输出只拥有一个最终写入者，或明确采用哪种合法归约协议。
