# K02 为读懂算子学习 C++：从一行变量到可编译的内存视图工程

本章接着K01的地址模型讲语言。你不需要先读完一本C++百科全书，但不能只记住“星号是指针、模板能优化”就去读CUDA和CUTLASS。我们会从一个可编译程序开始，把类型、对象、表达式、函数、指针、引用、容器、生命周期、模板和构建过程连接起来。每个概念都回答同一组具体问题：这段代码创建了什么，数据在哪里，谁能修改它，什么时候失效，错误会在哪个阶段出现。

本章所有终端命令从课程仓库根目录执行。每个带main的完整C++例子应保存为一个独立的.cpp文件，例如hello.cpp、matrix_view.cpp；不要把它们顺次拼成一个文件，否则会重复定义程序入口。没有main的代码块是辅助片段：变量操作与循环放进main函数体，普通函数、模板和类型定义放在main之前，所需include放在文件最前。文中“沿用前文头文件”表示把相关头文件声明保留在当前源文件里，编译器不会自动记住你之前编译过的另一份文件。每次换完整例子，也要在构建命令中同时换成对应的源文件名与输出文件名。

## 第一课：先得到一个完整的编译运行闭环

### 1. 源文件、可执行文件和运行结果是三个对象

先从仓库根目录创建练习目录；本章不要求切换当前目录。

~~~bash
mkdir -p .practice/cpp build/kernel-labs
~~~

把下面内容保存为`.practice/cpp/hello.cpp`。文件名后缀帮助工具识别语言，但后缀本身不会自动把文字变成机器指令。练习源码放在.practice/cpp，生成的可执行文件放在build/kernel-labs，两个目录承担不同职责。

~~~cpp
#include <iostream>

int main() {
    int count = 3;
    std::cout << "count=" << count << '\n';
    return 0;
}
~~~

第一行把标准库输入输出声明提供给编译器。main是程序入口函数，返回类型int表示它最终给操作系统一个整数退出状态。花括号圈定函数体，count声明创建一个整数对象并初始化为三。std::cout表示标准输出流，连续的左移形状符号在这里是流插入运算，把字符串、整数和换行送到输出。return零表示这个程序主动报告成功，最后的右花括号结束函数。

编译与运行是两个独立步骤：

~~~bash
g++ -std=c++17 -Wall -Wextra -pedantic .practice/cpp/hello.cpp -o build/kernel-labs/hello
./build/kernel-labs/hello
~~~

目录已在保存源文件前创建。这里第一条让编译驱动处理源文件并生成目标可执行文件；-o后面的路径是输出文件名，不是输入。只有编译成功后，才执行第二条启动生成的程序；如果编译报错，先修正，不要继续运行可能残留的旧产物。修改.practice/cpp/hello.cpp以后，如果只执行第二条，你运行的仍是旧二进制。很多“我明明改了代码输出怎么没变”的问题来自忘记重新编译，或运行了另一个目录里同名的旧文件。

终端显示的文字不是程序本身，也不是编译产物。你可以有同一个源文件生成不同优化等级的二进制，也可以让同一个二进制处理不同输入并打印不同结果。把这三层分开，后面研究编译器缓存、JIT和CUDA运行时才不会混乱。

### 2. 先读第一条有意义的诊断

删掉count声明后，编译器会说找不到相关名字。删掉iostream头文件，可能出现cout未声明等信息。漏掉分号后，下一行也可能被连带报告为语法错误。初学时不要从最后一行“编译失败”开始猜原因，而应从第一条指向源文件位置的诊断往前检查。

编译器通常会报告文件、行号、列号和错误说明。行号指向的是它发现问题的位置，不一定是你最早写错的位置。例如上一行漏掉引号，解析器可能在下一行才无法继续。阅读诊断时要把出错行与前后几行一起看，再构造最小例子确认。

我们使用警告参数，是为了尽早暴露可疑但未必非法的写法。警告不是数学正确性的证明：编译器可以接受一个维度写错的矩阵乘法，也可以对一个逻辑正确但风格可疑的程序发出警告。你仍需要测试和手算oracle。把构建诊断当作第一道检查，而不是最后一道结论。

## 第二课：类型决定值的范围、运算方式和存储解释

### 1. 声明不是给变量贴一个注释

Python中名字可以先绑定整数再绑定列表；C++中一个普通变量的静态类型在声明时已经确定。声明int count等于三，意味着count按int的规则存储和运算。声明float x等于三，意味着用浮点格式表示这个值。类型会影响可调用的运算、转换规则、对象大小和函数匹配。

整数类型用于表示离散计数和下标，但不同整数类型的范围不同。C++标准并不要求所有平台的int永远都是三十二位。写教学程序时可以打印sizeof；需要明确位宽的接口可以在可用条件下使用cstdint中的固定宽度类型。涉及模型文件、通信协议或二进制布局时，不能把本机默认类型宽度当作跨平台合同。

浮点数用于近似表示实数。float和double通常提供不同精度与范围，但“更多字节”并不自动解决所有数值问题。后面的归约章节会展示运算顺序如何影响结果。本章先记住：类型参与解释存储，也参与决定算术在哪种精度下执行，转换发生在何处非常关键。

### 2. 字面量与隐式转换会改变计算

表达式五除以二，如果两个操作数都是整数，结果采用整数除法，得到二。把其中一个写成浮点数，例如五点零除以二，就会按浮点算术得到二点五。如果你先做整数除法，再把结果赋给double变量，丢掉的小数不会自动回来。

~~~cpp
double wrong = 5 / 2;
double right = 5.0 / 2;
~~~

wrong得到的是二，因为右侧先算完整数结果；right得到二点五，因为右侧已经采用浮点规则。这与量化算子中“先用窄类型累加再转宽类型”是同一类错误：后面的转换不能修复前面已经发生的信息丢失或溢出。

静态转换可以明确表达意图，例如static_cast<double>(count)。它不是任意值都安全的保证。把一个巨大浮点数转成较窄整数，需要先确认范围和语义；把带符号负数转换为无符号类型，也不会自动拒绝输入。代码可编译与转换符合业务合同是两件事。

### 3. 有符号与无符号混用为何需要小心

std::vector的size通常返回无符号大小类型。循环下标如果使用int，与size比较时可能发生类型转换。尤其当下标意外变成负数，转成无符号后会成为很大的值，比较结果可能与你预想不同。编译器警告能提示一些混用情况，但不能替你判断正确业务范围。

最简单的初学策略是让表示容器索引和长度的变量采用合适的大小类型，同时在从外部整数转换前显式检查非负与上界。不要把所有int机械替换成size_t，因为某些算法确实需要负方向步长或负索引差值。类型选择应该跟随含义：数量通常非负，差值和方向可能为负。

GPU算子中还要考虑下标乘积。即使每个维度都能放进三十二位整数，多个维度相乘可能超出范围。分配字节数、元素偏移和网格尺寸计算都要考虑中间结果的类型，而不是只看最终变量够不够宽。需要宽类型时，应在乘法之前转换相关操作数。

## 第三课：表达式、赋值和控制流怎样改变程序状态

### 1. 赋值与比较不是同一操作

单个等号表示给已有对象赋新值，两个等号表示比较值是否相等。C++允许许多赋值表达式参与更大的表达式，因此在条件里误写单等号可能产生难以理解的行为。初学时应把状态更新与条件判断写清楚，不依赖紧凑但容易误读的表达式。

加等于会读取左侧旧值，加上右侧，再存回。自增运算可以放在变量前或后，它们对表达式结果的含义不同。普通for循环的更新位置只需要推进下标，使用前置自增通常足够。不要为了少写一行把多次自增和数组访问混在同一个复杂表达式里，先确保顺序和依赖可解释。

短路逻辑也很重要。逻辑与在左侧为假时不会继续求右侧，逻辑或在左侧为真时不会继续求右侧。这使“先检查指针非空，再访问指向内容”成为可能。但代码正确依赖运算符确实是短路逻辑运算，而不是位运算符；单个与号和两个与号不能混用。

### 2. 用状态表读一个循环

~~~cpp
int total = 0;
for (int i = 0; i < 4; ++i) {
    total += i;
}
~~~

for括号里依次是初始化、继续条件和每轮后的更新。第一次先令i为零，再检查零小于四；成立则执行循环体，total仍是零；随后i加一。第二次检查一小于四，total变一；第三次加二得到三；第四次加三得到六；更新到四后条件为假，退出。

循环变量i的作用域在这段for语句内部，循环结束后不能把它当作仍然存在的外部变量。total在外层声明，所以循环结束后仍可读取。作用域描述名字在源码哪些位置可见，生命周期描述对象何时存在，两者密切相关但不是完全同义，后面会用动态存储说明区别。

把这个循环改成矩阵遍历，需要同时检查两层边界。外层行从零到rows减一，内层列从零到cols减一，底层偏移为row乘stride_row加col乘stride_col。你已经在K01证明过地址公式，现在控制流决定访问哪些逻辑下标。

### 3. continue、break和return退出的范围不同

continue结束当前这一轮循环体，进入下一轮；break退出最近一层循环；return退出整个函数。嵌套循环里用break只会退出内层，这经常与初学者“整个搜索已经结束”的想法不同。若要从搜索函数直接返回找到的结果，可以使用return，但还要定义未找到时返回什么。

CUDA中某些线程提前return还可能影响后续同步是否能由所有需要参与的线程到达。因此，CPU里看似自然的提前退出，在GPU协作代码中需要重新检查。现在先建立控制流的精确范围，K03和K04再把它连接到线程组同步。

## 第四课：函数不仅有输入和输出，还有修改权限

### 1. 先写一个最普通的值传递函数

~~~cpp
float square(float x) {
    return x * x;
}
~~~

函数名square前面的float是返回值类型，括号里的float x声明一个参数。调用square时，实参值用于初始化函数内部的参数对象。函数内部重新给x赋值，不会改变调用者原来的普通标量变量，因为它修改的是参数副本。

把函数声明和定义分开时，声明告诉编译器名字、参数类型和返回类型，定义则提供函数体。一个函数可以先声明后使用，只要链接时能够找到正确的定义。只声明却没有提供定义，可能在编译每个源文件时都通过，最终链接时才报找不到符号。

返回值应表达计算结果，输出流应表达可观察日志。一个函数打印了某个数，不代表调用者拿到了那个数。这个原则与Python相同，但C++返回类型会让部分遗漏更早被诊断。对于没有结果的操作，使用void表示不返回普通值。

### 2. 值传递容器可能复制整份数据

假设函数参数写成std::vector<float> x。普通传入一个已有vector时，可能需要复制容器内容，函数修改副本不会影响原容器。对于几百万元素，这个成本很大。你必须先明确函数是否需要独立副本，再选择传递方式，不能只因为代码短就默认按值传大对象。

写成std::vector<float>& x表示引用传递，函数通过另一个名字访问调用者的同一容器。修改x里的元素会被调用者观察到。写成const std::vector<float>& x表示只通过这个引用进行只读访问，避免常规复制，同时限制通过该参数修改内容。

引用不等于拥有对象。它没有自动延长所有对象生命周期的普遍能力，也不能替代资源管理。一个函数把引用保存到长期存在的结构里时，必须保证被引用对象活得足够久。只在一次函数调用期间读取，与跨调用长期保存，是不同的合同。

### 3. 完整比较三种接口

~~~cpp
#include <cassert>
#include <vector>

void change_copy(std::vector<float> x) {
    x[0] = 99.0f;
}

void change_original(std::vector<float>& x) {
    x[0] = 99.0f;
}

float read_first(const std::vector<float>& x) {
    return x.at(0);
}

int main() {
    std::vector<float> data{1.0f, 2.0f};
    change_copy(data);
    assert(data[0] == 1.0f);
    change_original(data);
    assert(data[0] == 99.0f);
    assert(read_first(data) == 99.0f);
}
~~~

第一条断言说明副本修改没有传播；第二条说明引用修改传播；第三条说明只读引用仍然读取同一容器的当前值。at会检查范围，而方括号访问要求调用者已经保证下标合法。选择哪种访问方式，与接口处于调试、教学还是高性能内核阶段有关，但边界责任不能消失。

## 第五课：指针把K01的地址公式写进语言

### 1. 星号和取地址符号要结合上下文读

声明float x等于三创建一个浮点对象；表达式&x取得它的地址；声明float* p等于&x创建一个指针对象，保存该地址；表达式*p访问p指向的浮点对象。星号在声明中参与类型，在表达式中表示解引用，在两个数之间又可以表示乘法。同一个字符不能脱离语法位置机械翻译。

~~~cpp
float x = 3.0f;
float* p = &x;
*p = 7.0f;
~~~

最后一行不是把指针改成七，而是把指向对象的值改成七。执行后x为七，p仍指向x。如果写p等于另一个合法float对象地址，才是在改变指针对象本身的值。区分“指针变量存什么”和“指针所指对象存什么”，是读C++的关键门槛。

空指针用nullptr表达，它不指向可解引用的对象。可以把它作为“当前没有缓冲区”的状态，但不能读取或写入其指向内容。检查空指针只能排除一种无效情况，非空指针也可能已经悬空或超出有效对象范围，所以“p不等于空”不是完整安全证明。

### 2. 指针加法以指向类型为单位

对float* p执行p加三，地址移动三个float元素的跨度。常见环境中float占四字节，因此移动十二字节；更严谨的说法是移动三乘sizeof(float)字节。对unsigned char* q执行q加三，则按三字节移动，因为字符类型的大小单位就是字节。

这解释了为什么CUDA代码里a加row乘K加col不再额外乘四。a的类型已经让指针算术以元素为单位。若你把来自NumPy的字节步长直接传进这种公式，又会把字节数当成元素数，最终地址偏移被放大。跨语言接口必须把步长单位约定清楚。

指针算术也不是在整个地址空间里随意加整数都合法。它有对象和数组范围的规则；形成数组末尾后一位置的指针可用于比较和迭代，但不能解引用。不要把“某次运行没有崩溃”当作越界合法的证据，未定义行为可能随优化、输入和编译器改变表现。

### 3. 裸指针没有自动携带长度和形状

一个float*通常只提供地址和静态元素类型。它不会知道数组有十二个元素，也不会知道逻辑shape是三乘四。函数接收指针时，需要另外传入长度、形状或其他描述信息。数组访问是否越界因此往往依赖函数合同和调用者验证。

如果函数只拿到p和n，合法读取通常是零到n减一。如果它要处理二维非连续矩阵，还需要行列长度和两个步长。少传元数据不会神奇地让实现变简单，只会迫使它假定某个固定布局。固定假设可以接受，但要在接口中明确体现。

K01的TensorView把这些元数据放在一个对象里；C++也可以用struct或class实现同样设计。GPU内核可能把它们拆成独立参数，以方便编译器处理。无论打包还是拆开，必须维护的是同一组逻辑关系。

## 第六课：const、引用和别名怎样表达读写合同

### 1. 从右往左辨认常见const组合

const float* p表示p指向的float通过这个指针不可修改，但p本身可以改指向别处。float* const p表示p这个指针变量不能重新指向别处，但可以通过它修改float对象。const float* const p则同时限制两者。实际阅读时，可以先问const修饰的是被指对象还是指针对象，避免只凭它在行中的位置猜测。

const是通过某个接口表达的限制，不等于全局没有其他别名修改同一块存储。你可以有一个只读指针和另一个可写指针指向同一数组。后者修改后，前者读取会看到新值。多线程程序仍然需要同步和数据竞争规则，不能因为输入参数写了const就认为线程安全已经解决。

把const当作接口说明的一部分很有帮助：一个归约输入通常可以是const float*，输出是float*；一个原地更新算子输入输出可能是同一可写指针。看到这些类型时，应进一步检查函数体是否与声明的意图一致，以及调用者是否可能传入重叠区域。

### 2. 引用像别名，但不是可重新绑定的普通指针

一个float&引用初始化后，就作为已有对象的另一个名字使用。给引用赋值会修改被引用对象，不会把引用改绑到另一个对象。指针则可以重新保存另一个地址。这个区别在函数参数中很实用：引用表达“这里必须有一个对象”，指针常用于“可能为空”或显式数组访问，但这只是常见设计习惯，不是万能规则。

引用也有失效风险。容器重新分配后，指向旧元素的引用可能失效；返回局部对象的引用也会悬空。不要因为引用语法没有显式星号，就忽略它背后的对象生命周期。语言帮你减少了一些写法复杂度，没有消除资源的时间边界。

### 3. 别名会影响原地计算

考虑两个长度相同的输入指针a和b，输出c。如果合同允许c等于a，逐元素c[i]等于a[i]加b[i]通常可以安全原地执行，因为每个输出只依赖同位置输入。但如果输出是前缀和或转置，写入某个位置可能破坏后续读取，原地支持就需要重新设计。

更复杂的情况是部分重叠，例如c从a的下一元素开始。即使表达式仍然是逐元素加法，顺序执行也可能先覆盖后面要读的a元素。GPU并行执行会使依赖更难控制。因此，“支持in-place”不能只通过测试c和a完全相同的一种情况就推出支持任意重叠。

优化中可能出现restrict一类非别名承诺。它们告诉编译器某些访问关系受到限制，从而允许更积极优化。错误地作出承诺会让程序失去正确性保证；它不是给代码免费加速的注释。先证明调用合同满足，再使用相关语言扩展或接口约束。

## 第七课：数组、vector和array的存储所有权

### 1. 固定长度数组与动态长度容器

C++原生数组的元素数量通常在类型或声明中固定，数组名在很多表达式中会转换为指向首元素的指针。转换后长度信息不会跟着普通指针一起传递。std::array把固定长度和元素类型组合成一个标准库对象，提供size等接口，适合编译时已知的小数组。

std::vector管理动态数量的连续元素。创建vector<float> a(n)会建立n个float元素；reserve只预留容量，不等于把逻辑size改成n。对仅reserve后仍size为零的vector直接用下标写入，并不因为底层可能有容量就成为合法元素访问。size是已有元素数量，capacity是无需重新分配最多可以容纳的数量，二者必须区分。

在数值程序里，vector适合保存CPU参考数据、接收GPU拷回结果和管理临时缓冲区。它的data方法返回连续数据区的指针，方便传给只接受裸指针的接口。但指针是否继续有效，取决于vector后续是否重新分配或销毁。

### 2. push_back和resize可能使旧指针失效

当vector容量不足时，增加元素可能分配更大存储，把元素移过去，再释放旧存储。此前保存的data指针、元素引用和迭代器可能失效。你不能拿到指针以后不断扩容，再把旧指针传给计算函数。

正确模式是在需要稳定数据地址的阶段先确定大小并完成分配，然后取得指针，避免在该指针使用期间发生会重新分配的操作。若必须调整大小，就在调整之后重新取得指针。更复杂的异步GPU使用还要考虑设备是否仍在读取与CPU对象变更之间的顺序。

这与分页缓存的设计相关：如果一个系统承诺页内地址稳定，就不能在读者仍持有地址时随意移动底层存储。你现在看到的vector失效规则，是更大系统中稳定句柄、间接寻址和引用计数设计的一个小尺度版本。

### 3. at与下标访问分别承担什么

vector的at进行范围检查，非法下标会抛异常；operator[]通常不进行同样的动态检查，调用者必须保证合法。教学程序先用at帮助定位错误，经过明确边界验证的性能路径再考虑下标访问。不能把删除检查当作算法优化的主要成果，更不能删掉检查后没有其他边界证明。

GPU设备代码是否支持某些标准库容器和异常处理，取决于具体编译与设备语言支持，不应把CPU vector代码直接搬进Kernel。常见做法是在host侧管理容器，把底层设备缓冲区指针和必要元数据传给device函数。K03会明确区分这两个执行世界。

## 第八课：对象生命周期、作用域和RAII

### 1. 局部对象为什么不能把内部地址随意返回

函数内创建局部vector，离开函数时vector对象被销毁，其拥有的存储被释放。若函数只返回vector.data()，调用者得到的地址不再指向活着的合法数组。地址数值可能看起来没变，短时间读取也可能碰巧出现旧内容，但程序已经没有正确性保证。

返回整个vector则不同。语言的返回值与移动机制可以把结果对象交给调用者管理，使底层存储继续由活着的对象拥有。你不需要为了避免“复制很慢”就返回悬空指针；现代C++有专门的对象返回与转移机制，先写正确所有权，再分析真实复制是否发生。

类似地，返回局部普通变量的引用也是错误设计。返回值复制的是值，返回引用或指针交出的是对某个对象的访问通道。这个对象在函数结束后是否仍存在，是两种接口的根本区别。

### 2. 动态分配把释放责任变成显式任务

使用new分配对象，需要匹配正确释放；使用new[]分配数组，需要匹配delete[]。混用释放形式、释放两次或释放后继续访问都可能导致未定义行为。初学时理解这些规则很重要，但日常CPU容器管理应优先使用vector、array和合适的智能指针，减少手动资源错误。

资源并不只有内存。文件句柄、互斥锁、CUDA事件和设备缓冲区都有获取与释放过程。每当你在函数中途可能返回或抛异常时，都要问已获取的资源会不会被遗漏释放。把清理代码写在函数末尾，只覆盖了正常走到末尾的路径。

### 3. RAII把资源责任绑定到对象

RAII的核心是让一个对象在构造时建立资源所有权，在析构时释放资源。对象离开作用域时，正常返回或异常展开都会触发适当析构，从而减少散落在各错误分支里的手动清理。名字看起来抽象，但vector就是你已经使用过的实例。

一个拥有独占资源的类还必须考虑复制。默认浅复制一个裸指针，会让两个对象以为自己拥有同一资源，析构时可能重复释放。常见设计是禁止复制，提供移动，把所有权从一个对象转交给另一个对象。移动后的对象仍须处于可析构的合法状态，例如内部指针设为空。

RAII不等于自动解决异步使用。一个CUDA缓冲区包装器在析构时调用释放函数，仍然需要遵守该API与未完成GPU任务之间的合同。词法作用域结束证明host对象要销毁，不证明所有设备消费者已经完成。这个时间关系将在K13继续展开。

## 第九课：struct、class和一个完整的MatrixView

### 1. 先把相关字段放到一起

struct可以把指针、行数、列数和步长组合成一个描述。它让函数参数更容易保持一致，避免到处传一长串整数并写错顺序。class与struct都能定义成员函数；默认访问权限不同，但不需要把它们想象成两套完全不同的语言机制。

下面的MatrixView不拥有存储。它的析构不会释放data，因为分配责任属于外面的vector或其他所有者。这个选择必须写进名字和文档；否则读者可能误以为创建视图等于复制矩阵，或者销毁视图会自动释放底层数据。

~~~cpp
#include <cassert>
#include <cstddef>
#include <stdexcept>
#include <vector>

struct MatrixView {
    float* data;
    std::size_t rows;
    std::size_t cols;
    std::ptrdiff_t row_stride;
    std::ptrdiff_t col_stride;

    float& at(std::size_t row, std::size_t col) const {
        if (row >= rows || col >= cols) {
            throw std::out_of_range("matrix index");
        }
        const auto offset =
            static_cast<std::ptrdiff_t>(row) * row_stride +
            static_cast<std::ptrdiff_t>(col) * col_stride;
        return data[offset];
    }

    MatrixView transpose() const {
        return {data, cols, rows, col_stride, row_stride};
    }
};

int main() {
    std::vector<float> values(12);
    for (std::size_t i = 0; i < values.size(); ++i) {
        values[i] = static_cast<float>(i);
    }
    MatrixView a{values.data(), 3, 4, 4, 1};
    MatrixView t = a.transpose();
    assert(a.at(1, 2) == 6.0f);
    assert(t.at(2, 1) == 6.0f);
    t.at(2, 1) = 99.0f;
    assert(a.at(1, 2) == 99.0f);
}
~~~

rows和cols用大小类型，步长使用可表示负值的差值类型。at先检查逻辑下标，再把下标转换为适合与有符号步长相乘的类型，最后计算偏移。返回float&允许调用者通过该访问修改底层元素，而不是拿到一个副本。

成员函数末尾的const表示它不修改这个视图对象的普通成员，但它仍然可以通过data指针返回可修改的底层float引用。这是浅层描述只读与深层数据只读的区别。如果你要定义真正只读视图，应使用const float*并返回const float&，而不是只在成员函数后面加const就认为数据不可修改。

这个简化视图检查逻辑范围，但没有保存底层分配长度，因此无法验证所有步长对应的物理访问都合法。K01的Python版本做了额外范围计算；若在C++扩展中需要同样保证，就应加入存储跨度元数据。不能因为代码用了at这个名字，就误以为所有内存错误都已经自动被检查。

## 第十课：模板、constexpr和编译期信息

### 1. 为什么Kernel代码会把数字写进尖括号

函数模板让编译器根据类型或编译期常量生成具体实例。最简单的类型模板可以为float与double复用同一种算法，非类型模板参数可以把tile大小等整数作为编译期信息。

~~~cpp
template <typename T>
T add_values(T a, T b) {
    return a + b;
}

template <int Tile>
int full_tiles(int n) {
    static_assert(Tile > 0, "Tile must be positive");
    return n / Tile;
}
~~~

调用add_values<float>选择float实例；调用full_tiles<16>把十六作为模板参数。static_assert在编译期检查条件，若Tile不是正数，相关实例不能成功构建。这与运行时if检查不同：前者验证某个编译生成的程序是否合法，后者验证该程序一次执行的输入是否合法。

在CUDA中，模板常用于固定共享内存数组形状、循环次数或某种类型组合。编译器有机会据此展开循环、去掉分支和选择特定指令。但模板不是自动提速保证。如果生成大量组合，构建时间、二进制大小和缓存占用也会增加；一个固定tile还可能不适合所有输入。

### 2. constexpr与普通const的区别从用途理解

constexpr声明强调其初始化可以满足常量表达式要求，适合用于某些编译期场景。const只表达对象不可通过该名字修改，并不保证值在编译期已知。例如从命令行读取的数可以保存为const，但它仍要等程序运行后才能知道。

不要把“不可修改”和“编译时已知”混为一谈。一个Kernel的输入长度可能在运行中固定不变，却仍是每次launch传入的运行时参数；一个tile大小可能作为模板或Triton constexpr参与代码特化。它们对优化和缓存的影响不同。

本卷CUDA的matmul<16>把共享内存tile的边长固定为十六；矩阵M、N、K则作为运行时参数传入，决定最后一个tile有多少元素有效。编译期tile与运行时问题规模共同构成实现，不能只记住其中一个。

### 3. 阅读长模板时先恢复“职责参数”

真实CUTLASS代码可能把元素类型、布局、tile形状、架构标签、主循环策略和epilogue策略组合成很长的类型。第一遍不要从每个辅助类型的定义一路追到最底层，而应先建立一张表：这个参数决定数值解释，那个决定地址排列，另一个决定工作块尺寸，还有一个决定数据搬运与计算如何协作。

随后选一个具体实例，把参数值代入表，再追它最终实例化到哪个核心循环。抽象模板只有落到具体类型与常量组合时，才容易与硬件执行对应。你不需要第一遍掌握全部元编程技巧，但必须能识别哪些参数会改变数学定义、哪些改变布局、哪些只改变调度。

## 第十一课：lambda、auto和常见现代C++写法

### 1. auto不是“没有类型”

auto让编译器从初始化表达式推导类型，推导完成后变量仍然有明确静态类型。它能减少冗长类型名，但也可能隐藏引用和复制的差别。使用auto接收一个返回引用的表达式时，默认推导方式未必保留引用；需要auto&时应该明确写出。

因此，看到auto不要跳过类型推理。先看右侧表达式返回什么，再看声明中有没有引用或const修饰。阅读数值内核周围的代码，类型决定累加精度、指针单位与是否发生复制，不能因为语法简短就不问这些问题。

### 2. lambda是一个可携带上下文的小函数对象

K01的C++布局程序使用lambda，把二维索引转换为vector位置。方括号是捕获列表，括号是参数，花括号是函数体。捕获决定lambda如何访问外部变量：按值保存副本，或按引用访问原对象。它不是在任何时候都能安全读取所有外部变量的魔法函数。

~~~cpp
const auto at = [&values, cols](int row, int col) {
    return values.at(row * cols + col);
};
~~~

这里values按引用捕获，cols按值捕获。lambda不复制整个vector，但要求它在调用期间仍活着；cols的当前数值被保存，外部之后修改cols不会改变这份捕获。若把lambda从函数返回并在原values销毁后再调用，引用捕获就会悬空。

### 3. 代码短不等于更好读

对于初学者，复杂嵌套lambda、隐式转换和模板推导叠在一起会增加认知负担。教学实现可以先写显式类型和普通函数，等数据流清晰后再使用便利语法。生产代码里的现代写法通常服务复用、泛型与资源管理，但理解时仍应把它们还原为对象、参数、捕获和调用。

本章的目标不是禁止简写，而是让你知道简写省略了什么。能够把一个lambda改写成带字段的函数对象，能够把auto还原为具体类型，才能在报错很长时抓住真正的类型不匹配。

## 第十二课：编译、链接和运行各自负责什么

### 1. 一个源文件也会经过多个阶段

预处理处理include和宏等指令；编译把语言语义转成目标表示；汇编生成目标文件中的机器代码；链接把目标文件与所需库组合起来并解决符号引用。g++命令往往把这些步骤串起来，所以初学者容易误以为它们是一件不可拆分的事情。

只编译不链接可以使用-c生成目标文件。多个源文件分别产生目标文件后，再进行链接。头文件通常提供声明与适合放在头文件中的定义，不是把所有代码复制进头文件就能解决构建问题。重复定义、缺少定义和声明不匹配各有不同诊断。

CUDA编译在这些CPU步骤之外，还要处理device代码、设备目标和相应运行时支持。理解普通C++编译链能让你区分“host编译器报语法错”和“device代码没有适合目标架构的产物”，避免每次都去重新安装驱动。

### 2. 三种常见错误的最小分类

找不到头文件通常发生在预处理或编译入口，检查文件是否存在、include路径是否正确、需要的开发包是否安装。undefined reference通常发生在链接阶段，说明声明可以看见，但最终没有找到匹配定义，或相应库没有正确参与链接。

启动时找不到共享库属于加载问题；程序启动后访问非法内存属于运行问题；输出数值错误属于逻辑或数值问题。最后一类可能完全没有编译器诊断，因此必须依靠测试与手算。把错误分类清楚后再改环境，能避免无关的重装和版本混乱。

### 3. 优化等级改变执行方式，不能改变合法程序的目标语义

-O0偏向少优化，便于初学调试；-O2等等级启用更多优化。优化后某些变量可能被消除、循环被展开，调试器中逐行对应关系也会变化。不要因为调试器找不到某个源码变量，就认为变量从来没有参与数学计算。

如果程序在不同优化等级下输出显著不同，可能是浮点规则允许的差异，也可能暴露了未定义行为、未初始化变量或错误别名承诺。先用明确合同和小输入定位，不能简单得出“优化器不可靠”的结论。后面的K15会继续解释中间表示和具体优化如何工作。

## 第十三课：错误检查、异常与完整清理路径

### 1. 异常是一条控制流路径

vector.at越界会抛异常。如果没有适当处理，程序可能终止并输出诊断。抛异常不等于普通return，调用栈会展开，沿途已构造的适当局部对象会析构，这正是RAII能处理错误路径的重要原因。

异常也不是所有环境都支持的通用机制。GPU设备代码、某些性能库或项目编译选项可能有不同限制。阅读框架时要确认错误是通过异常、返回码、状态对象还是断言传播，不要把一种方式的处理习惯套给另一种。

### 2. 返回码必须被检查

CUDA运行时常返回错误码，代码需要检查是否成功，并在失败时记录哪个调用、哪一行和错误内容。本卷教学程序使用宏缩短重复检查，但宏不是异常安全资源管理器。若前面已经分配部分资源，中间失败直接return，示例可能依赖进程退出回收资源，而成熟库需要更严格的清理策略。

学习时应能说清示例的边界：短程序用于展示API顺序，不代表它已经是可嵌入长期服务器的资源包装库。将其改造成RAII设备缓冲区类，是合理的进阶项目，但必须同时处理复制、移动、析构错误策略和异步使用合同。

### 3. sanitizer能发现什么，不能证明什么

在支持的CPU编译器环境中，地址检查器和未定义行为检查器可以发现一些越界、释放后使用和非法算术等问题。它们会改变程序的运行开销和内存布局，因此不应把带检查器的性能数字当成生产性能。它们也不能自动证明矩阵索引符合你的数学定义。

教学中优先制造受控的小错误，例如对长度三的vector使用at访问下标三，或让一个错误地址公式读错合法位置。需要演示裸内存错误时，使用独立短程序和检查器，避免在共享服务或真实数据上试验。目标是理解诊断，不是把崩溃当作学习成果。

## 第十四课：十二道练习与完整答案

### 练习一：判断整数除法的执行顺序

题目：double a等于七除以二，double b等于static_cast<double>(七)除以二，分别是多少？答案是三与三点五。a右侧先完成整数除法，赋给double时只把整数三转换成浮点三；b在除法之前改变操作数类型，因此保留小数。验收还要自己构造九除以四的例子，说明转换位置为何重要。

### 练习二：编译一个完整的类型观察程序

~~~cpp
#include <iostream>
int main() {
    std::cout << sizeof(int) << ' '
              << sizeof(float) << ' '
              << sizeof(double) << '\n';
    std::cout << 7 / 2 << ' ' << 7.0 / 2 << '\n';
}
~~~

参考解释应区分本机观察与语言保证。第一行打印当前环境各类型对象大小，不能据一次观察断言所有平台相同；第二行展示整数与浮点除法。程序没有需要GPU的部分，因此不应因为服务器有H100就占用设备运行。

### 练习三：把值传递改成只读引用

~~~cpp
#include <vector>
float sum_values(const std::vector<float>& values) {
    float total = 0.0f;
    for (float value : values) {
        total += value;
    }
    return total;
}
~~~

答案使用const引用避免常规容器复制，并明确函数不通过参数修改输入。范围for按元素依次读取，局部value在这里是一个标量副本。若目标是精确研究浮点归约顺序，还需要记录元素顺序与累加类型；本题只训练参数与所有权。

### 练习四：写出指针步长的实际单位

题目：float* p指向一个数组首元素，p加三与p[三]分别表示什么？前者形成指向第四个float元素的位置，后者读取或作为左值访问该元素；移动字节数为三乘sizeof(float)。p[三]与*(p加三)在相关语义下对应。合法性还要求数组实际至少有四个元素，单凭类型不能证明。

### 练习五：修复悬空返回

~~~cpp
#include <vector>
std::vector<float> make_values() {
    return std::vector<float>{1.0f, 2.0f, 3.0f};
}
~~~

这就是完整修复方式之一：返回拥有存储的容器。调用者把结果保存在活着的vector中，再在需要时取得data指针。不要返回函数内部临时vector的data，也不要用static全局容器偷偷改变所有权和线程语义来掩盖问题。

### 练习六：证明reserve不等于resize

~~~cpp
#include <cassert>
#include <vector>
int main() {
    std::vector<float> x;
    x.reserve(10);
    assert(x.size() == 0);
    assert(x.capacity() >= 10);
    x.resize(10);
    assert(x.size() == 10);
    x.at(9) = 3.0f;
}
~~~

完整答案指出reserve后没有十个已构造的逻辑元素，resize后才有。容量可能大于请求值，因此不应断言capacity恰好等于十。这个细节训练你区分接口承诺与某次实现观察。

### 练习七：给MatrixView增加只读版本

~~~cpp
struct ConstMatrixView {
    const float* data;
    std::size_t rows, cols;
    std::ptrdiff_t row_stride, col_stride;
    const float& at(std::size_t row, std::size_t col) const {
        if (row >= rows || col >= cols)
            throw std::out_of_range("matrix index");
        return data[static_cast<std::ptrdiff_t>(row) * row_stride +
                    static_cast<std::ptrdiff_t>(col) * col_stride];
    }
};
~~~

这段定义沿用前文头文件。关键变化是data指向const float，at返回const引用，因此不能通过该接口赋新值。但其他持有可写指针的代码仍可能修改同一存储，不能把它宣传成全局不可变或线程安全。

### 练习八：实现固定tile的向上取整计数

~~~cpp
template <int Tile>
int tile_count(int n) {
    static_assert(Tile > 0, "positive tile required");
    if (n < 0) throw std::invalid_argument("negative size");
    return n / Tile + (n % Tile != 0);
}
~~~

参考实现避免直接写n加Tile减一可能产生的加法溢出形式。对n为零、一、十六、十七，Tile为十六时结果分别零、一、一、二。注意这仍使用int表示n，若输入超出int范围，调用前转换与接口设计还需要处理，不能把一个局部修复当作无限范围支持。

### 练习九：识别lambda捕获生命周期

题目：函数内创建vector，然后返回一个按引用捕获该vector的lambda，调用者稍后执行它，是否安全？答案是不安全，因为局部vector已销毁。修复可以让lambda按值持有需要的数据副本，或持有明确共享所有权的对象，或改变接口保证lambda不逃出原作用域。选择取决于是否允许复制与需要共享修改，不能只把捕获符号改一下而不分析语义。

### 练习十：区分三种错误阶段

删除vector头文件属于编译入口问题；声明一个外部函数却没有提供定义通常导致链接错误；运行一个合法编译程序后矩阵结果错，属于运行逻辑问题。完整练习要求各自保留最小源文件、完整构建命令和第一条有效诊断，说明为何另一阶段的修复无关。例如链接错误不会因为重启GPU驱动而自动消失。

### 练习十一：建立子矩阵视图

~~~cpp
MatrixView submatrix(MatrixView a,
                     std::size_t row0, std::size_t col0,
                     std::size_t rows, std::size_t cols) {
    if (row0 > a.rows || col0 > a.cols ||
        rows > a.rows - row0 || cols > a.cols - col0)
        throw std::out_of_range("submatrix");
    const auto shift =
        static_cast<std::ptrdiff_t>(row0) * a.row_stride +
        static_cast<std::ptrdiff_t>(col0) * a.col_stride;
    return {a.data + shift, rows, cols, a.row_stride, a.col_stride};
}
~~~

范围检查用减法形式避免先计算row0加rows时的无符号溢出。该简单版本对空子矩阵的指针形成仍要求调用者给出合法的底层描述；生产通用视图可以专门处理空范围并携带存储边界。答案必须说明它不复制数据、不拥有存储，以及父所有者必须活着。

为布局程序列出vector对象、data指针、MatrixView、转置视图和输出值。参考答案：vector拥有CPU数据；data指针不拥有；两个视图都不拥有且共享同一数据；按值返回的标量不再依赖原存储。再标出哪些操作可能使指针失效，例如vector销毁和导致重新分配的扩容。能够写出这张表，比只背RAII缩写更接近真实工程能力。

## 第十六课：把资源管理写成一个完整而小的C++类型

### 1. 先用CPU数组理解独占所有权

为了看清资源转移，我们用一个CPU缓冲区类演示。实际项目中优先使用标准库容器；这里手写的目的，是让你知道未来CUDA缓冲区包装器必须承担哪些责任，而不是建议在所有项目中替换vector。

~~~cpp
#include <cassert>
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <utility>

class FloatBuffer {
public:
    explicit FloatBuffer(std::size_t count)
        : count_(count), data_(count ? new float[count]{} : nullptr) {}

    FloatBuffer(const FloatBuffer&) = delete;
    FloatBuffer& operator=(const FloatBuffer&) = delete;

    FloatBuffer(FloatBuffer&& other) noexcept
        : count_(std::exchange(other.count_, 0)),
          data_(std::move(other.data_)) {}

    FloatBuffer& operator=(FloatBuffer&& other) noexcept {
        if (this != &other) {
            data_ = std::move(other.data_);
            count_ = std::exchange(other.count_, 0);
        }
        return *this;
    }

    std::size_t size() const noexcept { return count_; }
    float* data() noexcept { return data_.get(); }
    const float* data() const noexcept { return data_.get(); }

    float& at(std::size_t index) {
        if (index >= count_) throw std::out_of_range("buffer index");
        return data_[index];
    }

private:
    std::size_t count_;
    std::unique_ptr<float[]> data_;
};

int main() {
    FloatBuffer first(3);
    first.at(1) = 7.0f;
    FloatBuffer second(std::move(first));
    assert(first.size() == 0);
    assert(first.data() == nullptr);
    assert(second.size() == 3);
    assert(second.at(1) == 7.0f);
    FloatBuffer third(2);
    third = std::move(second);
    assert(second.size() == 0);
    assert(third.at(1) == 7.0f);
}
~~~

构造函数前的explicit避免某些意外隐式转换，让创建缓冲区这件事保持显式。冒号后是成员初始化列表，它直接初始化成员；不是先默认创建所有成员，再在函数体里赋值。count下划线与data下划线只是命名习惯，用来区分成员与参数，没有特殊语言魔法。

new float[count]后面的空花括号要求值初始化，这里使元素初值为零。没有初始化的浮点数组可能含有未确定值，读取它们不能作为合法随机数据使用。我们的测试先设置第二个元素为七，同时其他元素已有明确初始状态，因此不会把未初始化内容混进验证。

unique_ptr<float[]>表示拥有一个动态数组的独占智能指针。方括号形式让默认删除策略与数组分配相匹配。这个对象销毁时释放资源，因此FloatBuffer没有再手写delete，也不应该重复释放同一指针。资源管理交给标准库成员，外层类负责维护自己的接口不变量。

### 2. 为什么明确禁止复制

复制构造与复制赋值被标记为delete，意味着尝试复制这个类型会在编译期失败。这里的设计选择是一个缓冲区只有一个所有者，不提供隐式深复制。你仍然可以以后增加一个名字明确的clone方法，但它应当让调用者知道发生了分配和数据复制。

如果只是把裸指针作为成员而允许默认复制，两个对象会保存相同地址，却可能在析构时都尝试释放。独占智能指针已经禁止这种复制，这个外层类再次显式声明，是为了让接口意图清楚。阅读生产代码时，看到delete不是“作者没实现”，也可能是故意禁止某种危险操作。

共享所有权是另一种设计，不能简单认为比独占更高级。shared_ptr会维护共享生命周期，但并不自动使底层数据访问线程安全，也不自动解决GPU异步事件。选择共享还是独占，应根据真实所有者关系，而不是为了让编译错误消失。

### 3. 移动究竟移动了什么

移动构造用std::move表达允许从other转移资源。它不是一条把几百万浮点元素逐个搬到新地址的内存复制指令。在这个例子里，unique_ptr把所拥有的指针转交给新对象，原指针变空；数据本体的位置可以保持不变。

std::exchange把other的count替换为零，并把旧值返回给新对象。这样移动后的旧对象同时满足size为零、data为空的接口约定。只移动指针却保留旧count，会让对象仍声称有三个元素，但没有对应存储，at检查便可能错误放行。因此资源转移还要维护元数据一致性。

noexcept声明这条操作承诺不抛异常，它会影响标准库在某些场景下能否放心使用移动。不要对可能抛异常的操作随意加noexcept；若承诺被违反，行为可能直接终止程序。这里使用的成员操作适合该承诺，但换成更复杂资源包装器时需要重新分析。

### 4. 移动赋值与移动构造不是同一场景

构造新对象时，目标还没有旧资源；赋值给已有对象时，目标可能已经拥有另一块资源。例子中third先拥有两个元素，随后接收second的三个元素。unique_ptr移动赋值会处理third原有资源，再接管新资源；外层更新count保持一致。

自我移动检查避免this和other是同一对象时破坏状态。不同类型对自移动的合法保证可能不同，教学类明确处理这个情况更容易解释。返回*this使赋值表达式具有常见的链式使用语义，但实际数值代码中不需要为了简短而把多个所有权转移写成难读的一行。

注意at只提供可写版本，而data提供可写和只读重载。const对象调用只读data版本。函数重载根据对象和参数的类型选择接口，这解释了为什么相同名字可以有不同修改权限。你以后在框架Tensor、Storage和Allocator类中会频繁看到这种设计。

### 5. 从CPU类迁移到CUDA类时新增了什么责任

把new替换为设备分配API、把默认删除替换为设备释放API，只解决了一部分问题。你还必须检查分配返回码、记录或约定所属设备、决定析构失败如何处理、定义是否允许在未完成GPU任务时释放，以及是否通过流有序分配器管理生命周期。

析构函数通常不适合随意抛出新异常，尤其当它在处理另一个异常的栈展开过程中执行时。生产资源类往往把显式close的错误报告与析构兜底清理分开，或采用项目规定的错误记录策略。具体选择要与框架约定一致，本章不把一个CPU示范包装成完整CUDA资源库。

这个迁移分析很有价值：你已经知道哪部分属于普通C++所有权，哪部分来自GPU异步执行。遇到长类定义时，可以先找资源字段、构造、析构、复制与移动，再看执行事件与设备上下文，按职责逐层拆开。

## 第十七课：把一个大报错还原成一条短调用链

### 1. 模板报错里的“实例化位置”是什么意思

假设一个模板函数里调用对象的size方法，但你传入普通int。模板定义本身可能在早期解析时没有立即触发该类型错误；当编译器为int生成具体实例时，才发现int没有size。诊断可能同时显示模板内部错误行与调用它的实例化位置。

读这类报错时，先找最具体的错误，例如某类型没有某成员、参数不能转换或某个static_assert失败；再沿实例化链回到你实际选择的模板参数。不要逐行从最外层几百字类型名开始猜。具体类型、失败操作和调用地点三者组成最小问题。

对于CUTLASS等大量模板组合的代码，错误可能来自不兼容的元素类型、布局或tile策略。先把你改变的参数与原可工作实例对照，确认哪个合同被破坏，再追辅助类型。一次只改一个维度，能让实例化错误更容易归因。

### 4. 在地址乘法之前做范围验证

最后补一个会在大张量里实际出现的问题：计算rows乘cols乘元素字节数时，每一项看起来都不大，乘积却可能超出所用整数类型范围。对于有符号整数，溢出不能被当作可靠的回绕算法；无符号整数有定义的模运算行为，但回绕后的较小分配大小仍然不符合你要保存整个矩阵的业务要求。

正确检查应发生在乘法之前。假设最大可表示值是limit，准备计算a乘b，且二者非负。若a不为零并且b大于limit整除a，就应拒绝该请求。这个检查避免为了判断是否溢出而先执行已经有问题的乘法。后续再乘itemsize时，还需要对中间结果重复检查。

这里的数学并不复杂，但接口层容易遗漏。一个矩阵形状在逻辑上合法，不代表当前平台有足够地址范围或内存完成分配；分配成功也不代表内核内部仍用较窄下标就能正确访问全部元素。host检查、参数类型和device地址计算必须采用一致范围合同。

把这个案例加入小项目：不实际分配巨大数组，只测试尺寸计算函数会拒绝超范围乘积。这样既能验证错误路径，又不会占用大量共享资源。它也训练你区分“测试边界逻辑”和“真的申请极端资源”，后者并不是前者的必要条件。
