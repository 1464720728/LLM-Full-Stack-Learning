# K02　为读 Kernel 学 C++：值、地址、生命周期与编译

先修 K01。目标不是先成为完整的 C++ 专家，而是能读懂 Kernel 周围的类型、指针、容器、函数和资源管理，并能把一段小程序编译、运行、定位错误。

## 1. 变量、对象与指针不是同一个东西

`float x=3;` 创建一个值为 3 的浮点对象。`float* p=&x;` 创建一个指针对象，其值表示 x 的地址；`*p` 访问指向的对象。`p+1` 增加的是一个 `float` 元素的跨度，通常为四字节，而不是一个字节。这解释了为何 C++ 中 `a + row*K + col` 不需要再乘 `sizeof(float)`。若 API 接受 `void*` 加字节数，则又切换了单位。

一个 `float*` 不携带数组长度。Python 的列表通常能在越界时抛异常，C++ 的裸数组下标没有这种普遍保证。越界可能读到碰巧可访问的内存，导致程序继续输出貌似合理的数。这比立即崩溃更危险。教学程序用 `std::vector::at` 验证下标，进入性能代码后才在有证明的边界下使用裸指针。

`const float* p` 表示不能通过 p 修改被指向的浮点值；它不表示所有其他别名都不能修改那块存储。`float* const p` 表示指针变量自身不能改指向，但可以修改对象。阅读 CUDA 函数参数时，`const` 是理解读写集合的重要线索，然而它不自动证明线程安全。

## 2. 生命周期：地址有效也有时间范围

函数内创建的局部数组离开作用域后不再是合法访问对象。把它的地址返回给调用者，就是悬空指针。动态分配把释放责任交给程序，忘记释放会泄漏，释放两次会出错，释放后仍使用则是 use-after-free。C++ 的 RAII 思想把资源生命周期绑定到对象：构造时获取，析构时释放。`std::vector` 管理 CPU 存储就是一个常见例子。

GPU 增加了异步性。CPU 函数返回，并不等于 GPU 已完成读取。假如你把缓冲区交给一个 Stream 上的 Kernel，随后另一个位置释放或复用缓冲区，需要遵守相应 API 的执行与同步保证。不能简单把 CPU 词法作用域当成 GPU 工作完成的证明。这也是推理框架必须有自己的内存生命周期管理的原因。

教学 CUDA 程序逐项调用 `cudaFree`，便于观察生命周期。更成熟的 C++ 项目会使用 RAII 包装，使错误路径也能释放资源。学习顺序是先知道责任是什么，再把责任封装起来，而不是一开始就被智能指针和复杂模板掩盖。

## 3. 函数、引用、模板

`void scale(std::vector<float>& x)` 中的 `&` 是引用，函数修改原容器而不是复制一份。`const std::vector<float>& x` 用于只读访问，既避免复制，又表达意图。引用不等于拥有对象，它的生命周期仍不能超过所引用对象。

`template<int T>` 允许编译器为不同常量 T 生成不同实例。我们的 CUDA GEMM 使用 `matmul<16>`，共享内存数组的尺寸在编译时已知。它与运行时变量 `int tile=16` 的差别是：前者可参与静态数组尺寸、循环展开与代码特化，后者的值要等执行时才能获知。模板本身不保证更快；过多实例也会增加构建时间和二进制体积。

你在 CUTLASS 中会见到长串类型参数。先追四件事：数据类型、布局、Tile 形状、调度策略。不要试图第一遍就阅读全部元编程辅助类。模板最终仍须落到“哪段内存由谁读取、执行什么指令、何时同步”。

## 4. 编译、链接、运行分开排错

源文件经过编译器产生目标代码，链接器解决跨文件符号和库依赖，加载器在运行时建立进程环境。语法错误与找不到头文件发生在编译阶段；`undefined reference` 常是链接阶段；缺少动态库或执行中崩溃则属于运行阶段。不要看到所有报错都去重装驱动。

从仓库根目录执行：

```bash
mkdir -p build/kernel-labs
g++ -std=c++17 -Wall -Wextra -Werror \
  labs/kernels/cuda/layout.cpp -o build/kernel-labs/layout
./build/kernel-labs/layout
```

你应看到偏移 6、值 6，以及 `sizeof(float)`。`-Wall -Wextra` 开启一组警告，`-Werror` 让这些警告变成构建失败。它适合小型受控教学代码，但不能不经评估地强加到一个庞大的第三方项目。

阅读 [layout.cpp](../../labs/kernels/cuda/layout.cpp)：`std::vector<float> a(rows*cols)` 分配数据；循环初始化；lambda 捕获 `a` 并实现逻辑二维索引；`assert` 检查预期；`data()` 提供原始指针。注意转置 lambda 用的是 `col*cols+row`：其形参是转置后的逻辑行列，存储仍按原矩阵索引解释。

## 5. 从可读到可靠

调试时优先缩小尺寸、开启编译器警告、构造能手算的数据。对于 CPU C++ 可以在受支持的编译器环境使用地址和未定义行为检查器：`-fsanitize=address,undefined -g`。它们可发现部分内存问题，但不是数学正确性证明。GPU 的检查工具另有边界，不能把 CPU sanitizer 的成功等同于 CUDA 正确。

不要在练习中故意运行会破坏系统的任意地址写入。学习越界无需去访问真实私有数据：可以编写一个逻辑错误的二维索引，让单元测试指出结果不对；或在隔离的短程序中使用 sanitizer 展示报告。

## 6. 练习与参考答案

1. **地址步长。** `float* p` 与 `unsigned char* q` 指向同一地址，`p+3` 和 `q+3` 分别移动多少字节？答案通常为 12 和 3；以 `sizeof(float)` 实测，不把平台假设藏起来。
2. **阅读。** 把 `layout.cpp` 的转置索引改成 `row*rows+col`，先预测哪些位置碰巧正确，再用全部下标验收。答案：新表达式是在假定转置已物理连续，视图语义下错误；应恢复交换步长的寻址。
3. **改造。** 写 `MatrixView`，保存 `float* data`、rows、cols、两个元素步长和 `at`。参考解法：构造函数只保存描述，访问函数检查逻辑边界再求偏移；不拥有底层数据，析构不得释放它。
4. **资源。** 解释为什么函数返回局部 `std::vector` 的 `data()` 不合法，而返回整个 vector 合法。答案：前者留下指向已销毁对象的地址；后者按 C++ 返回值规则把容器对象交给调用者，其存储生命周期由新对象管理。
5. **构建排错。** 删除 `#include <vector>`、把函数只声明不定义、把可执行文件路径写错，各属于哪一阶段？答案依次是编译、链接、启动；记录最小复现与第一条有效诊断，不只截最后一行。
6. **工程任务。** 为 `MatrixView` 加转置和子矩阵视图。验收：不复制数据，修改原数组可在视图观察到；子矩阵越界立即抛错；写明视图不得比所有者活得久。扩展思考：若希望长期保留视图，必须怎样管理共享所有权？

掌握门槛：能独立编译此程序、添加一个带测试的函数，并解释每个指针的所有者、有效范围和读写权限。无需先掌握完整 C++ 标准库。
