# K14　性能工程：先提出可证伪的解释，再优化

先修前述算法与计时。目标：用字节、FLOP、延迟和资源占用建立性能模型，设计可信基准，知道什么时候该读时间线、什么时候该读 Kernel 指标。

## 1. Roofline 是约束，不是预测魔法

设计算量 F、必须搬运的数据量 B、峰值计算吞吐 P、可用带宽 W。理想耗时至少为 `max(F/P,B/W)`，算术强度为 `F/B`。强度低时更容易受带宽约束，强度高时才可能接近计算上限。这里的峰值要匹配数据类型、稀疏条件和硬件指令，带宽也要匹配实际路径，不能任意拿厂商最大数字相除。

举一个明确标注为合成的设备：P=10¹² FLOP/s，W=10¹¹ byte/s。任务 F=2×10⁹、B=10⁹，则计算下界为 2 ms、搬运下界为 10 ms，整体至少 10 ms。即使计算吞吐翻倍，也无法突破搬运约束；如果把实际流量减半，理想下界才可能降到 5 ms。真实系统还有启动和占用等开销。

```bash
python -m labs.kernels.run --lab 23
```

该实验的硬件参数是人为数字，不是对 H100 或 5070 Ti 的测量。它训练你先核对单位：GB 与 GiB、byte 与 bit、FLOP 与 FMA 都不能混用。

## 2. 为什么小 batch 解码常像访存问题

矩阵乘法的 M 很小时，一份权重对应的复用次数较少；读取大量权重，却只为少量 token 产生输出。batch 增大可让多个 token 复用权重，算术强度上升。但增大 batch 也增加排队与每步工作，可能影响单请求延迟。吞吐最优与延迟最优是不同目标。

MoE 还要考虑激活专家数、专家内 token 分布与通信；长上下文注意力还要读取 KV。不能只用“模型总参数×每元素字节数”解释所有阶段。把 prefill、decode、路由、通信、采样拆开，先画数据路径再计算主要成本。

## 3. Occupancy 不是越高越好

Occupancy 常用来描述驻留活跃 Warp 数相对于上限的比例。提高它可能帮助隐藏延迟，但也可能为了减少寄存器而增加重复计算或溢出。一个每 Warp 做更多有效工作、占用较低的 Kernel，仍可能比高占用版本快。

寄存器、Shared Memory、线程数与硬件块数上限共同约束驻留。调参时只改变一个主要因素，记录编译器资源报告，再看执行指标。否则你把 Tile、Warp 数、精度和融合同时改了，即使变快，也很难解释原因。

## 4. 基准的六个陷阱

第一，异步计时没同步；第二，第一次 JIT 被当成常规性能；第三，参考与优化使用不同精度或不同形状；第四，只测整除尺寸；第五，拷贝、分配或 padding 在某一侧被隐藏；第六，共享 GPU 的干扰被当成算法效果。

应记录中位数和分布，不能只挑最好一次。极短 Kernel 的计时开销可能接近实际耗时，可重复多次摊薄，但要保证重复方式没有改变语义或缓存条件。真实业务与合成热缓存基准可以分别报告，不能拿后者直接宣称端到端加速。

## 5. Nsight Systems 与 Nsight Compute

前者更适合看系统时间线：CPU 提交、GPU Kernel、Memcpy、多个 Stream、空隙、同步与通信。后者更适合深入某个 Kernel：吞吐、访存、资源、指令和瓶颈线索。初学者常直接抓海量 Kernel 指标，却没发现绝大部分时间在 CPU 排队或重复编译。

在共享服务器上先选择一个短小、可复现的目标，不要长时间对公司任务全局采样。性能工具可能改变执行时间和并发行为；把 profiler 下的时间与普通运行时间区别记录。WSL2 的工具支持也依版本与功能而定，核查官方限制后再使用。

## 6. 优化记录是一份实验报告

每次优化写：问题和基线、假设、唯一主要改动、正确性测试、性能结果、误差范围、解释与剩余疑问。例如“将 transpose Shared Memory 行宽从 32 改为 33，假设减少列读取冲突；对输出做完全相等验证；对固定 shape 多次计时；再用指标检查冲突是否下降”。即使结果没有提升，也得到有价值的反证。

## 7. 练习与参考答案

1. **单位。** 128 MiB 数据以 64 GB/s 传输的理想时间？答案 `128*2^20/(64*10^9)` 秒，约 2.097 ms；写出单位后再换算。
2. **下界。** 一个任务计算需 4 ms、搬运需 7 ms，能否把 11 ms 当最优下界？答案若可完全重叠，roofline 下界为 7 ms；实际可能介于更复杂范围，不能自动承诺重叠。
3. **定位。** Kernel 自身占总请求 10%，把它加速两倍，端到端最大改善多少？答案原时间1变为.95，加速约1.0526倍；这体现 Amdahl 约束。
4. **基准设计。** 为 add 写比较表，包括大小、dtype、有效字节、是否包含分配。答案读两输入写一输出，float32 的理想有效载荷为 12N byte；真实流量受缓存等影响。
5. **调试任务。** 某优化只在 1024×1024 快，1031×997 慢且偶发错。参考：先停止性能结论，解决尾部 mask；正确后再检查 padding 工作与 Tile 利用率。
6. **项目任务。** 为自己的一个 Kernel 建立不少于六个 shape 的正确性/性能矩阵。验收允许某些 shape 回退到库函数；明确选择规则，比无条件替换所有输入更可靠。

掌握门槛：每个性能结论都有工作负载、数值契约、环境与测量方式；能用一个反例推翻自己的假设，不把“快了”当成已经理解。
