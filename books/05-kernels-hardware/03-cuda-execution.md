# K03 CUDA怎样执行一段代码：从Host调用到Thread、Block、Warp与SM

本章的核心问题不是“GPU有多少核”，而是你写的一条数组计算究竟由哪些执行者完成、它们如何编号、谁可以相互等待、结果何时能被CPU观察。先完成K01寻址与K02C++，再进入本章。只会记住thread、block、grid三个词，仍然写不出可靠Kernel；必须把它们与具体下标、内存和时间关系连接起来。

本章先用CPU模拟验证工作分配，再阅读完整CUDA程序。没有GPU时可以完成前半部分，真实设备编译与运行留到你自己的WSL/Linux或H100环境。仓库中已有的CUDA代码并未在当前编写环境编译或运行，这个事实不因正文扩写而改变。

## 第一课：CPU与GPU不是同一个执行位置

### 1. Host负责组织，Device执行被提交的工作

一个普通Python或C++程序首先是操作系统中的CPU进程。它读取命令行、创建对象、加载库、选择设备、申请内存，并向GPU提交工作。CUDA通常把CPU一侧称为host，把GPU一侧称为device。这两个词描述执行位置与接口角色，不是“高级部分”和“低级部分”的价值排序。

假设任务是把两个长度一千零三个的数组相加。CPU需要准备输入，确保GPU能够访问对应存储，启动加法Kernel，再在合适时刻取得结果。GPU执行的是许多逻辑线程共同承担的数组运算。CPU端调用一个launch表达式，不代表CPU自己逐个执行了Kernel里的加法。

同一个源文件可以包含host函数和device函数。编译工具链会按照标记和调用关系处理不同部分。看到一个.cu文件，不应认为里面所有代码都运行在GPU；main、vector初始化、打印和许多运行时调用仍在CPU执行。反过来，Kernel函数体中的threadIdx等名字具有设备执行语义，不能拿普通CPU循环的直觉直接替代。

### 2. 两边的指针数值不提供万能访问权限

host上的普通vector数据通常是CPU存储；设备分配得到的缓冲区供GPU使用。某些平台和内存机制提供统一虚拟寻址、托管内存或特定共享访问能力，但不能据此认为任何CPU指针都能直接让GPU读取，也不能认为CPU可以随便解引用所有设备指针。

初学采用明确路径：host容器保存输入，设备分配保存GPU输入输出，通过API按指定方向复制。这个流程看起来多几步，却把所有权和数据所在位置说清楚。以后学习统一内存或零复制时，再比较它们改变了哪一步、需要什么平台条件和会发生什么迁移。

指针在程序里可能都打印成十六进制数字，但地址值相似不代表访问权限相同。调试时要记录分配API、设备号、字节数和生命周期，而不是只看地址是否非零。一个合法设备指针在设备零上有效，也不自动意味着另一个设备可以在没有适当访问配置的情况下使用它。

## 第二课：Kernel是一段被许多逻辑线程执行的函数

### 1. 先看最小加法函数

~~~cpp
__global__ void add(const float* a,
                    const float* b,
                    float* c,
                    int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}
~~~

global标记说明这是可从host提交执行的设备Kernel入口。返回类型是void，结果通常通过输出缓冲区写回，而不是像普通CPU函数那样返回一个数组对象。a与b通过const指针读取，c通过可写指针输出，n告诉Kernel有多少个逻辑元素。

函数体不是被自动改写成一个for循环；它会由本次launch创建的许多逻辑线程执行。每个线程执行相同的源代码，但内建的线程与块编号不同，因此算出不同i。对各线程分别代入编号，你就能知道它们读取和写入哪个位置。

本例没有共享输出位置：每个合法i只由一个线程负责，数学运算仅依赖同位置的a与b。因此不需要线程之间先交换数据，也不需要在加法后设置全局屏障。这是最适合入门的并行问题，因为工作之间独立，正确性主要取决于覆盖与边界。

### 2. launch里的两个数字各表示什么

host侧可以写add<<<grid_size, block_size>>>(...)。第一个配置参数指定本次grid包含多少个block，第二个指定每个block包含多少个thread。假设grid为三、block为四，总共创建十二个逻辑线程，分成三个组，每组四个。

blockIdx.x取零、一、二；threadIdx.x在每个block内部都取零、一、二、三；blockDim.x为四。代入公式，block零负责i零到三，block一负责四到七，block二负责八到十一。threadIdx不是整个grid的全局唯一编号，所以不能只用threadIdx.x作为全局数组下标。

每个block里都会有一个thread零。若错误代码把c[threadIdx.x]作为输出，三个block会重复写同样的四个位置，后面八个位置没有被写到。这个错误不需要理解复杂硬件就能发现，只需把编号表完整列出。

## 第三课：用手算证明覆盖恰好一次

### 1. 为什么要向上取整

若输入长度n为十，block大小为四，需要三个block才能覆盖所有元素。十整除四得到二，只能创建八个线程，漏掉下标八和九。向上取整得到三，创建十二个线程，其中最后两个线程没有合法元素。

常见公式是n加block减一再整除block，但涉及大整数时要考虑加法溢出。数学上等价的写法是n整除block，加上余数不为零时的一。host包装器应先保证block为正，n非负，再计算网格大小。零长度输入通常直接返回空结果而不必启动无意义工作。

### 2. 线程覆盖表

| block号 | block内thread号 | 全局i | n=10时的行为 |
|---:|---:|---:|---|
| 0 | 0,1,2,3 | 0,1,2,3 | 读取并写入 |
| 1 | 0,1,2,3 | 4,5,6,7 | 读取并写入 |
| 2 | 0,1,2,3 | 8,9,10,11 | 前两个有效，后两个不访问 |

最后两个线程仍然存在，它们执行到边界判断后跳过数组访问。不能把“没有有效输出元素”理解成“线程没有启动”。这一区别在计时、资源使用和同步中都会出现。

证明唯一性可以从除法商与余数出发。对任意合法i，除以block大小得到唯一的block号与thread号。只要grid数量足够大，这一对编号就存在；不同i不可能得到同一对商余数。因此，每个合法元素恰好由一个逻辑线程处理。

### 3. 边界判断必须保护实际内存访问

把if写在读取之后没有用。错误代码先执行a[i]，再判断i是否小于n，最后才决定是否写输出，仍然可能发生越界读取。正确版本把所有可能越界的读取与写入都放在有效条件控制下，或使用有明确掩码语义的加载指令。

对于矩阵运算，边界可能有多个轴。行号合法但列号越界仍然非法；归约维尾部不足时，需要给无效输入填入数学上中性的值，而不只是跳过最终store。K06会展示GEMM为什么需要同时保护A、B加载与C写回。

## 第四课：grid-stride循环让工作量与线程总数解耦

### 1. 一个线程可以处理多个元素

如果我们只启动八个线程，却要处理十九个元素，可以让每个线程先处理自己的初始i，再每次跨过总线程数继续处理后面的元素。总跨度是blockDim.x乘gridDim.x。线程零依次处理零、八、十六；线程一处理一、九、十七；线程二处理二、十、十八；其余线程各处理两个。

~~~cpp
__global__ void add_grid_stride(const float* a,
                               const float* b,
                               float* c,
                               int n) {
    int start = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = start; i < n; i += stride) {
        c[i] = a[i] + b[i];
    }
}
~~~

这里grid-stride是工作分配策略，不是张量存储stride。前者决定同一线程下一次处理哪个逻辑元素，后者决定逻辑下标对应哪个物理地址。两个词都叫stride，但单位和作用层次不同。当前输入是连续数组，所以逻辑i恰好直接用于元素地址；如果输入非连续，还需要再应用K01的存储映射。

### 2. 完整十九元素轨迹

~~~text
thread 0: 0, 8, 16
thread 1: 1, 9, 17
thread 2: 2, 10, 18
thread 3: 3, 11
thread 4: 4, 12
thread 5: 5, 13
thread 6: 6, 14
thread 7: 7, 15
~~~

把所有列表合并排序，应该恰好得到零到十八，既不重复也不缺失。仓库实验三就是对这一性质进行CPU模拟。它验证的是映射算法，不是GPU调度速度，也不需要真实线程并行运行。

~~~bash
python -m labs.kernels.run --lab 3
~~~

唯一性证明仍然来自除法：任意元素i对总线程数取余，决定负责它的线程初始编号；商决定该线程循环的第几轮。这样，即使grid比覆盖全部元素需要的大小更小，仍能完整处理输入。

### 3. 为什么这种循环有用，但不是永远最佳

grid-stride循环允许根据设备资源选择有限数量的block，让每个线程处理多个元素，也便于用很小的launch检查算法。它保持一轮中相邻线程访问相邻元素的模式，通常有利于连续访问。但具体性能仍受block大小、寄存器使用、数据规模和内存行为影响。

不是所有算子都能直接改成这套模板。线程之间有协作、每个block负责一个归约或tile时，工作单位可能不再是单个元素。你应先定义哪个输出块归哪个block，再考虑block在多个工作块之间循环，而不是把任何代码外面套一层grid-stride就宣称完成优化。

## 第五课：二维与三维编号如何映射回一条线

### 1. dim3提供的是坐标，不是自动矩阵语义

CUDA允许用dim3描述多维grid和block。x、y、z只是编号轴，CUDA不会自动知道x代表列还是行。你可以约定x映射列、y映射行，但必须让地址公式与launch保持一致。

对二维矩阵，常见写法是row等于blockIdx.y乘blockDim.y加threadIdx.y，col等于blockIdx.x乘blockDim.x加threadIdx.x。如果输入采用行优先连续布局，地址为row乘列数加col。先得到逻辑行列，再计算存储地址，这两步在概念上要分开。

~~~cpp
__global__ void add_matrix(const float* a, const float* b,
                          float* c, int rows, int cols) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < rows && col < cols) {
        int offset = row * cols + col;
        c[offset] = a[offset] + b[offset];
    }
}
~~~

假设矩阵三行五列，block为四列两行，则grid需要两列两行block。右侧block的部分线程列号超出五，底部block的部分线程行号超出三。每个轴都要独立做向上取整和有效性检查。

### 2. block内部的线性线程顺序

多维block内部可以按x变化最快、然后y、再z的方式得到线性线程编号。二维时是threadIdx.y乘blockDim.x加threadIdx.x。这个编号关系在讨论warp里哪些线程访问哪些地址时很有用。

例如block为十六乘十六，共二百五十六个线程。线性编号零到三十一覆盖y为零的一整行十六个线程，以及y为一的一整行十六个线程。不能简单把“一个warp”想成二维block里的一整行，因为一行只有十六个线程，而warp的组织单位不同。

另一方面，把block设成三十二乘八时，最初三十二个线性线程恰好对应同一行的三十二列。这可能改变访存和协作方式，但也会改变其他资源与tile设计。理解映射后再比较性能，避免只凭“方形block更自然”作决定。

### 3. 三维只是再加一层编号

在批量或体数据计算中，可以让z表示批次或深度。此时全局逻辑坐标由三个block坐标与三个thread坐标组成，再通过实际张量stride换成地址。若某个轴只是方便工作分配，而不直接对应存储轴，也完全可以，但需要明确转换关系。

常见错误是把grid的维度数量与张量维度数量强行绑定。一个四维张量可以展平成一维grid处理，也可以把若干轴合并成二维grid。选择哪种组织方式取决于工作单元与访存，不是由张量rank机械决定。

## 第六课：block、warp和SM分别是什么层次

### 1. block是程序员组织协作的单位

同一个block内的线程可以使用该block的共享内存，并通过相应block级同步机制协调。block的大小由launch决定，受到设备与内核资源限制。一个block并不是一块永久固定的物理硬件，也不等于一个SM。

普通CUDA执行模型下，不同block应能以任意合适顺序独立执行，程序不应依赖block零先于block一完成。设备可能同时执行多个block，也可能因为资源限制分批执行。写算法时假设整个grid的所有线程同时驻留，会导致错误的全局等待设计。

### 2. SM是执行资源，warp是调度相关的线程组织

SM是GPU中的流式多处理器，包含执行和存储资源。一个kernel launch产生的block由系统安排到可用资源上执行。一个SM可以驻留多少block或warp，受到线程数、寄存器、共享内存以及架构限制共同影响，不是只看block数量。

在这里讨论的NVIDIA CUDA执行模型中，warp由三十二个线程组成，是理解指令执行与分支行为的重要单位。block内线程按线性编号分组，最后不足一组时也要按相应有效线程处理。不要把一个warp等同于一个C++数组，也不要把一个逻辑线程等同于一条永久独占的物理计算核心。

GPU通过在不同就绪warp之间安排指令执行来隐藏某些等待。这个解释说明为什么更多可运行工作有时有帮助，但并不推出“线程越多永远越快”。如果每个线程消耗大量寄存器，或每个block占很多共享内存，可驻留的工作反而可能减少。

### 3. 用资源装箱理解occupancy

把一个SM的寄存器、共享内存和线程槽位想成几种不同容量的资源池。一个block需要同时满足所有资源条件才能驻留。如果线程数量允许放四个block，但共享内存只够放一个，那么最终不能按线程数量得出四个block的结论。

occupancy通常描述某种驻留warp比例，是一个资源利用指标，不等同于实际算力利用率，也不等同于性能。一个拥有足够数据复用、每个warp做很多有效计算的kernel，可能在较低occupancy下表现很好；一个高occupancy却不断等待不规则访存的kernel，也可能很慢。

本章不要求记住每个型号的具体资源上限。你应该学会在实际设备上读取能力、结合编译报告查看寄存器与共享内存，再解释限制来自哪一项。K14会把这个推理与性能测量连接起来。

## 第七课：SIMT、分支与有效线程集合

### 1. 同一段代码不意味着所有线程永远做相同动作

在加法例子中，每个线程执行同样函数，但if条件取决于自己的i。尾部线程条件为假，因此不做数组访问。对一个warp而言，不同线程可能走不同分支，系统需要按相应执行语义处理这些有效线程集合。

分支分歧的成本取决于具体代码、编译结果和硬件行为，不能用一句“有if就慢”概括。边界检查本身是正确性需要，删掉它可能让程序越界；优化应该考虑如何组织尺寸和工作减少无效计算，同时保留必要保护。

如果所有线程都执行同一分支，分支并不一定造成你想象的额外串行化。若两个分支分别进行不同的大量工作，则需要分析哪些线程在哪段有效。先画出每个线程的条件与工作量，再讨论性能，比背诵“避免分支”更可靠。

### 2. 不要依赖未经同步的隐式步调

旧代码或口头解释常把warp内线程描述成永远严格锁步。现代CUDA编程应遵守明确的同步与内存语义，不能把未写出的执行步调当作通用保证。线程间通过共享数据协作时，要使用适当的同步原语或具有明确合作合同的warp操作。

即使某段代码在一个设备上反复输出正确，也不能据此证明缺少同步是合法的。编译器可以重排、保留寄存器值，硬件执行也有自己的调度细节。只有算法依赖关系与同步合同建立起来，才能把观察提升为正确性论证。

### 3. 原子操作解决冲突更新，不自动建立全部算法顺序

若多个线程需要对同一计数器加一，普通读加写可能丢失更新，因为两个线程都可能读到同一个旧值。原子加法使特定更新按其语义不可被拆开竞争，但它不自动意味着所有其他数组写入已经按你想要的顺序对所有线程可见。

对于归约，原子累加是一种可能实现，但浮点相加顺序可能随执行交错变化。若任务要求确定性或高性能，需要进一步设计。现在先把原子理解为解决某种共享更新的工具，而不是放在任意数据竞争处就能修复整个算法的万能按钮。

## 第八课：同步屏障必须与参与线程集合匹配

### 1. block级屏障做什么

当一个block的线程合作把数据写入共享内存，然后其他线程读取这些数据时，需要确保生产阶段完成后再进入消费阶段。block级同步屏障让需要参与的线程在某个阶段边界汇合，并提供相应内存可见性保证。它不是让整个grid所有block都等待的普通全局屏障。

典型模式是每个线程加载一部分数据，所有参与线程同步，然后每个线程读取可能由别人加载的值。没有同步时，某个消费者可能先执行到读取，生产者还没写完。代码中的加法本身可以完全正确，结果仍会因为阶段顺序错误而不稳定。

### 2. 条件分支中的屏障为什么危险

如果只有部分线程进入包含block级屏障的分支，而其他需要参与的线程永远不会到达对应同步，就可能违反同步要求。常见错误是在尾部线程发现越界后直接return，剩余线程随后执行全block同步。对于需要共享协作的内核，尾部线程通常应继续参与阶段同步，只是加载中性值并禁止无效输出。

这并不表示任何提前return都错误。前面的独立逐元素加法没有后续block协作，越界线程提前退出可以是合法设计。判断依据是该线程是否属于后续同步和共享依赖的参与集合，而不是机械禁止某个关键字。

### 3. 两次同步可能各有不同责任

分块矩阵乘法加载共享tile后需要一次同步，保证计算前数据齐备；完成当前tile消费后还需要同步，避免部分线程开始覆盖下一轮tile，而其他线程仍在读取上一轮。两次同步位置看起来相似，保护的却是不同阶段边界。

若只保留第一次同步，程序可能在小尺寸或特定调度下碰巧正确，但在其他形状上出现间歇错误。调试时要画出“写共享内存—读共享内存—再次写”的时间关系，而不是只数函数体里有几个同步调用。每一个屏障都应能对应一条明确依赖。

## 第九课：完整host流程逐行解释

### 1. 分配与复制的单位是字节

~~~cpp
std::vector<float> a(n, 1.0f);
std::vector<float> b(n, 2.0f);
std::vector<float> c(n);

float* da = nullptr;
float* db = nullptr;
float* dc = nullptr;

cudaMalloc(&da, n * sizeof(float));
cudaMalloc(&db, n * sizeof(float));
cudaMalloc(&dc, n * sizeof(float));
cudaMemcpy(da, a.data(), n * sizeof(float), cudaMemcpyHostToDevice);
cudaMemcpy(db, b.data(), n * sizeof(float), cudaMemcpyHostToDevice);
~~~

前三行创建host容器，分别保存输入一、输入二和输出空间。da等是host程序中的指针变量，用来保存设备分配返回的地址；指针变量本身在CPU程序里，不意味着它指向的数据也在CPU内存。

cudaMalloc需要更新这些指针变量，因此传入它们的地址。分配大小以字节表示，所以是元素数乘sizeof(float)。cudaMemcpy也接收字节数，并明确复制方向。不要把Kernel里的元素偏移单位与分配API的字节单位混用。

这段为了突出流程省略了返回码检查，不能直接当成最终可靠程序。仓库basics.cu对相关运行时调用使用CUDA_OK检查。阅读时应把数据流与错误流都标出来：正常情况下地址如何产生，失败情况下程序如何停止和报告。

### 2. 提交、检查和取得结果

~~~cpp
add<<<grid_size, block_size>>>(da, db, dc, n);
cudaGetLastError();
cudaMemcpy(c.data(), dc, n * sizeof(float), cudaMemcpyDeviceToHost);
~~~

launch把工作提交给设备执行。紧接着检查launch相关错误，可以较早发现配置或提交问题；但设备执行中的某些错误要到同步或后续相关API调用时才暴露。因此只检查launch后一处返回码不足以说明内核执行完成且成功。

把结果拷回host并在CPU验证，需要遵守相应拷贝和流语义。对于教学程序使用的普通同步拷回路径，程序在合适时机得到可读取的host结果；如果改成异步拷贝，就必须额外保证读取前完成。API名字、方向、内存类型和流配置共同决定行为，不能只看“Memcpy”几个字推断全部时序。

随后逐元素检查c是否等于三。这个验证在输入全一加全二时方便，但它不能暴露所有索引错误，因为所有正确输出都相同。真正的布局验收还应该加入递增或非对称数据，确认每个输出来自对应输入。

### 3. 释放与错误路径

完成设备最后使用后，释放da、db、dc。长期运行的服务必须确保所有成功分配都在正常和错误路径正确释放。短教学程序中某些失败直接结束进程，不等于已经提供可复用库级资源管理。K02的RAII分析可以用来改进这些host包装代码。

释放之后指针变量可能仍保存旧数值，除非你主动更新它；旧数值不能再作为合法访问凭证。把指针设空可以帮助减少误用，但多个别名不会自动一起变空。真正的保证来自所有权和最后使用关系，而不是某一个变量的外观。

## 第十课：把仓库的三个CUDA实验读成一条递进路线

### 1. 向量加法验证独立工作分配

仓库basics.cu使用一千零三个元素，启动八个block、每块一百二十八线程。总线程数一千零二十四，大于元素数二十一。grid-stride循环保护越界并允许将来使用更小grid时继续覆盖全部元素。

先手算block七、thread一百零六的i：七乘一百二十八加一百零六，得到一千零二。它负责最后一个合法元素。再把thread号增加一，得到一千零三，已不小于n，因此不访问。这个边界对照比只说“有mask所以安全”更具体。

### 2. 归约引入block内协作

reduce_sum把每个线程负责的输入放入共享数组。尾部无效线程写零，因为零是求和的中性值。第一次同步后，线程合作执行树形加法，每一轮把部分元素合并，最终thread零把当前block的和写到partial。

host再把八个partial求和，得到整个输入和。这是两阶段归约，不是一个全grid同步的单阶段魔法。理解中间partial的shape、所有者和使用时机，才能进一步写更大规模的多阶段归约。

### 3. GEMM引入二维tile和重复阶段

matmul模板为每个block分配一个输出tile，线程协作加载A和B的子块到shared memory。每轮沿归约维推进一个tile，加载后同步，计算若干乘加，再同步保护下一轮覆盖。最后只把合法行列输出写回。

本章先识别执行结构，不急于推导全部矩阵算术。K06会逐项解释为什么A加载使用threadIdx.x选择归约位置，而B加载使用threadIdx.y选择归约位置，以及共享tile怎样被多个线程复用。现在应能把代码划成加载、同步、计算、同步、写回五个阶段。

## 第十一课：为什么不能在普通Kernel里随意做全局屏障

### 1. 一个看似合理的等待会死锁

假设每个block先完成工作，再给全局计数器加一，然后等待计数器等于总block数。你可能希望这等价于全grid屏障。但如果设备资源只能同时驻留部分block，已驻留block在等待中占着资源，尚未开始的block无法获得资源，也就永远不能增加计数器。

这个问题与计数器是否原子无关。原子可以保证计数更新不丢失，却无法让尚未被调度的block在没有资源时执行。错误来自把逻辑上创建的所有block误认为物理上同时驻留。

### 2. 正确拆分阶段的基本办法

对于普通教学任务，可以把全局依赖拆成多个Kernel launch。同一流中前一个Kernel的相关工作完成后，后一个Kernel按流顺序执行，从而形成设备范围的阶段边界。第一阶段写partial，第二阶段读取partial，是归约常见设计。

CUDA也有特定协作启动和更高级同步机制，但它们有相应能力、启动方式和驻留条件，不能把普通launch直接当作满足这些合同。本课程先建立独立block的可靠思维，再在高级章节研究更强机制。

### 3. 把依赖图画出来再选择执行结构

如果输出B依赖所有A块的结果，就需要一个明确的全局阶段边界；如果每个B块只依赖自己block里的A数据，block级同步可能足够；如果各输出独立，则不需要相互等待。先写依赖范围，才能选择正确同步范围。

这条原则同样适用于后面的分布式通信：某个数据依赖只在一个warp、一块SM共享工作、一个GPU或多个rank之间发生，决定了必须使用哪一级机制。使用比需要更强的同步可能浪费性能，使用更弱的同步则会破坏正确性。

## 第十二课：三种故障的完整定位过程

### 故障一：最后几个元素没有被计算

先把n设成十、block设成四，打印或模拟grid计算。若grid采用普通整除得到二，就只覆盖八个元素。修复向上取整后仍需保留i小于n判断，否则新增尾部线程会越界。回归测试覆盖n为零、一、block减一、block、block加一和多个block加尾数。

不要只把n改成整除block来“修复”测试，那只是隐藏边界。真实模型的序列长度、batch和特征尺寸不保证永远落在某个舒服的倍数上。一个可靠算子应支持其合同范围内的尾部，或在入口明确拒绝不支持形状。

### 故障二：改变block数后输出重复或缺失

检查全局i是否包含blockIdx乘blockDim，grid-stride的跨度是否包含gridDim。若循环每次只加blockDim，不同block的线程可能走到同一后续元素。用十九元素、两block、每块四线程列出完整轨迹，重复位置会立即出现。

修复后把所有线程工作列表合并，分别检查排序结果等于零到n减一，以及元素数量等于唯一元素数量。前一个检查覆盖完整性，后一个检查唯一性。单独检查输出值有时会被相同输入掩盖，因此CPU映射测试很有价值。

### 故障三：归约在某些长度上挂住或出现随机错误

先检查是否有尾部线程在屏障之前return，再检查所有循环迭代的同步条件是否对参与线程一致。若线程数不是算法假定的二的幂，树形归约可能遗漏元素或读到无效位置。共享数组大小与实际blockDim不一致也会造成越界。

解决方法不是随意增加更多屏障，而是逐阶段明确参与集合、共享数组有效范围和每个线程的生产消费责任。对于当前固定一百二十八线程教学实现，包装器应保持该约束；若要通用化线程数，必须同时改共享存储、归约算法和测试。

## 第十三课：十二道练习与完整参考解

### 练习一：枚举线程编号

题目：grid为二，block为四，写出所有block与thread组合以及全局i。答案依次为block零内i零、一、二、三，block一内i四、五、六、七。证明方式是代入i等于block号乘四加thread号，而不是仅凭图形猜测。再指出每个block都存在thread零，所以threadIdx不能单独作为全局编号。

### 练习二：实现不会漏尾部的网格计算

~~~python
def ceil_div_nonnegative(n, block):
    if type(n) is not int or n < 0:
        raise ValueError('nonnegative n required')
    if type(block) is not int or block <= 0:
        raise ValueError('positive block required')
    return n // block + (n % block != 0)

assert [ceil_div_nonnegative(n, 4) for n in (0, 1, 3, 4, 5, 10)] == [0, 1, 1, 1, 2, 3]
~~~

这是CPU参考计算，不是CUDA代码。它拒绝bool，避免把True悄悄当作线程数一。零长度返回零，调用者可据此直接返回空结果。若某API不接受零grid，就不能把这个零直接传给launch。

### 练习三：完整验证grid-stride覆盖

~~~python
def assignments(n, blocks, threads):
    if n < 0 or blocks <= 0 or threads <= 0:
        raise ValueError('invalid shape')
    width = blocks * threads
    return [list(range(t, n, width)) for t in range(width)]

work = assignments(19, 2, 4)
flat = [i for items in work for i in items]
assert sorted(flat) == list(range(19))
assert len(flat) == len(set(flat))
assert work[2] == [2, 10, 18]
~~~

参考解把每个线程的初始全局编号作为range起点，总线程数作为步长。改变blocks与threads后数学结果仍应覆盖全部元素。这里没有模拟warp调度和内存速度，因此不能用它预测GPU耗时。

### 练习四：构造错误跨度的反例

~~~python
bad = [[i for i in range(t, 19, 4)] for t in range(8)]
flat = [i for items in bad for i in items]
assert len(flat) > len(set(flat))
~~~

错误版本跨度只有每块线程数四，而初始编号已经包含两个block的八个线程。线程零会访问四，而线程四也从四开始，发生重叠。这个反例明确指向公式缺少gridDim，不是笼统地说“并发出问题”。

### 练习五：手算二维尾块

题目：矩阵三行五列，block四列两行，grid是多少？答案x方向二、y方向二。右下block中，thread坐标零、零对应全局行二列四，是合法最后元素；thread一、零对应行二列五越界；thread零、一对应行三列四越界。有效性必须同时检查行和列。

### 练习六：计算一个warp覆盖的二维线程

题目：block为十六乘十六，线性编号三十一对应哪个thread坐标？答案x为十五、y为一，因为三十一整除十六得一、余十五。编号三十二对应x零、y二。由此说明第一个三十二线程组跨越两行，而不是占一整行。

### 练习七：判断提前return是否合法

独立向量加法中，越界线程return后没有任何共享协作，通常符合本例设计；共享归约中，若剩余线程稍后需要全block屏障，越界线程不能简单退出，应写入零并参与同步。答案必须指出依赖范围和参与集合，不能只回答“return安全”或“不安全”。

### 练习八：修复重复写同一位置

错误Kernel让所有线程把结果写到c[零]。如果目标是逐元素输出，修复为每个线程写自己的合法i；如果目标是总和，则需要明确归约算法，不能把store改成一个普通加等于就结束。多个线程的读改写会竞争，且浮点顺序还涉及确定性。

### 练习九：解释两阶段归约的数据形状

假设八个block各写一个partial，第一阶段输出长度八，不是长度n。第二阶段读取这八个数并合并成一个标量。第一阶段每个partial只由对应block的指定线程写一次，其他线程不重复store；第二阶段开始前必须有明确执行顺序。完整答案同时包含shape、写入所有者和阶段边界。

### 练习十：给加法程序设计非对称数据

~~~python
a = [100*i + 1 for i in range(10)]
b = [-3*i for i in range(10)]
expected = [a[i] + b[i] for i in range(10)]
assert expected == [97*i + 1 for i in range(10)]
~~~

GPU结果应逐元素与expected比较。这样若某线程读了邻居位置，结果通常会变化。全一加全二适合最初检查能否跑通，不足以独立验证所有索引映射；两类用例可以同时保留，各自承担不同作用。

### 练习十一：分类错误发生位置

非法launch配置可能在提交检查时暴露；设备执行越界可能在后续同步点才报告；正确执行但输出数学值错误需要数值oracle发现；host拷贝方向或字节数写错属于数据准备与传输问题。完整练习为每类写一条最小输入与观察点，不把所有错误都归因于“GPU不支持”。

### 练习十二：说明为什么普通全局等待可能死锁

答案必须包含资源驻留条件：等待的block占据可用资源，尚未执行的block无法启动，因此计数器永远到不了总数。原子计数不解决调度资源问题。修复之一是拆成同一流中的两个Kernel，把阶段依赖交给明确的执行边界；特定协作机制则需满足额外合同。

## 第十四课：一个从CPU映射到真实GPU的分阶段项目

第一阶段写一个CPU线程分配模拟器，输入n、grid和block，输出每个线程负责的下标列表。验收覆盖空输入、比线程数短、恰好整除和有尾部的情况。输出中必须能识别缺失和重复，而不只是打印“完成”。

第二阶段将数学运算加入模拟器，每个线程根据自己的列表计算输出。使用非对称输入，并记录每个输出的写入次数。第三阶段把相同下标公式放入CUDA加法Kernel，保留CPU参考作为独立oracle。第四阶段再增加二维矩阵接口和stride参数，确认逻辑映射与存储映射没有混淆。

真实GPU阶段只使用小数组和单设备。先确认当前终端是哪台机器、可见设备集合和编译目标，不在共享H100上启动长期循环。记录驱动、工具链、实际设备能力和完整命令。一个短正确性实验不需要占满八卡，也不需要下载大模型。

项目最终报告应包含线程工作表、唯一性与覆盖证明、GPU验证输出、三个故障反例，以及“哪些结论来自CPU模拟、哪些来自真实设备”的区分。如果当前没有GPU，前两阶段仍可完整交付，后两阶段保留明确未执行记录，不能把代码存在改写成实测成功。

## 第十五课：读到生产代码时的下一层问题

本章的一个线程处理一个元素，是最简单的任务分配。高性能算子可能让一个线程持有多个寄存器元素，一个warp合作一个tile，一个block处理多块工作，或者不同warp承担加载与计算职责。它们并没有推翻本章，而是在明确工作单位之后增加复用和流水线。

阅读复杂Kernel时，先找逻辑输出由谁拥有，再找每个线程如何得到自己的坐标，随后找它读取哪些输入、使用哪些共享数据、在哪些位置等待。最后才分析tile大小、warp数量和硬件指令。若第一步都说不清，直接调num_warps或block大小通常只会制造更多难以解释的结果。

当你能够独立推导十九元素的grid-stride轨迹、二维尾块地址和两次共享同步的不同责任，并能把这些关系指回basics.cu的具体代码行，就已经具备继续学习访存与归约的执行模型。接下来的章节会在这个模型上逐步增加数据搬运和数值算法。

## 操作工作坊一：从终端命令到一次可核对的设备执行

### 1. 先区分驱动、工具链和Python包

运行nvidia-smi用于观察驱动所能报告的设备信息；运行nvcc的版本查询用于观察当前命令路径选中的CUDA编译工具链；在Python环境里查看torch版本则观察另一个软件层。这三个版本不必具有同一个字符串，也不能用其中一个存在证明另外两个已经正确安装。

尤其不要把nvidia-smi界面中的CUDA版本字段直接当成当前nvcc版本。驱动能够支持某一范围的CUDA运行能力，与当前环境是否安装某个Toolkit编译器不是同一个事实。一个环境可能能运行某些预编译GPU程序，却没有nvcc；也可能安装了编译器，却没有可用GPU设备。

本章需要的设备阶段能力是：能编译当前CUDA源码，生成适合目标设备的产物，加载运行时并访问所选GPU。逐项核对比一次性重装所有软件更有效。公司服务器已有环境时，优先使用已有隔离环境和管理规范，不因为教程出现一个命令就修改系统驱动。

~~~bash
nvidia-smi
nvcc --version
python -m labs.kernels.inspect_environment
~~~

最后一条默认只做软件与环境观察，不主动初始化GPU；需要设备能力查询时，按本卷环境章节使用显式GPU选项。这样你能在普通CPU终端先确认解释器与工具路径，而不会把所有课程检查都变成设备操作。

### 2. 编译目标为什么必须匹配实际设备

CUDA编译器需要知道为哪类设备生成代码。H100对应的普通架构目标与消费级Blackwell不是同一个目标；工具链是否认识某个目标，还取决于所安装版本。不要把别人给B200的命令原样复制到H100，再把错误归结为“同样是NVIDIA所以应该能跑”。

对于本章使用普通CUDA C++的教学程序，可以在确认H100环境与工具链支持后采用相应sm_90目标。这里没有使用只属于某个更专门架构变体的高级指令，因此也不需要随意添加专门后缀。真正使用架构特定功能时，K16会要求重新核对能力与目标合同。

~~~bash
mkdir -p build/kernel-labs
nvcc -std=c++17 -O2 -lineinfo -arch=sm_90 labs/kernels/cuda/basics.cu -o build/kernel-labs/cuda-basics
CUDA_VISIBLE_DEVICES=0 ./build/kernel-labs/cuda-basics
~~~

这条编译命令明确是H100路线示例，当前编写环境未执行。-std选择C++语言标准，-O2选择优化级别，-lineinfo保留有助于工具关联源码的行信息，-arch选择目标，-o选择输出。不要把lineinfo误认为已经开启完整设备调试，它只是诊断支持的一部分。

环境变量CUDA_VISIBLE_DEVICES限制进程看到的设备集合。若只暴露一张物理卡，程序内部的设备零指向该可见集合中的第一张，而不一定是机器上的物理编号零。先确认管理员或任务调度系统分配给你的设备，再设置可见集合，不能为了教程方便擅自换到正在运行公司任务的卡。

### 3. 第一次运行应该观察哪些输出

仓库程序先查询设备数量，再选择可见设备零，打印设备名字和计算能力。随后验证向量加法、分块归约与小矩阵乘法。最终PASS仅代表这些输入和这些误差条件通过，不代表该GPU所有算子、所有形状或全部CUDA功能都被验证。

如果输出SKIP表示没有可用设备，就记录未执行，而不是把退出码零当成GPU数值验证通过。可选实验选择友好跳过，是为了不阻塞CPU学习路径；学习记录必须保留状态差别。后面的统一报告也是按照这个原则区分passed与not_executed。

第一次运行不要立刻增加百万级尺寸、循环次数或多卡数量。先修改一组能手算的小输入，确认输出确实随输入改变，再加入一个尾块形状和一个错误配置。这样得到的是对程序行为的理解，而不是只拥有一条“某命令成功”的记录。

## 操作工作坊二：逐轮手算共享内存归约

### 1. 用八个线程替代一百二十八个线程

为了在纸上看清过程，设一个block有八个线程，输入为一、二、三、四、五、六、七、八。每个线程先把自己的输入写入共享数组相同下标，第一次同步后共享数组完整为这八个值。我们暂时只讨论精确整数和，不混入浮点舍入问题。

第一轮stride为四，thread零把位置四加到位置零，得到六；thread一把位置五加到位置一，得到八；thread二得到十；thread三得到十二。其他线程本轮不更新前半区。同步之后，前四个位置保存两项之和。

第二轮stride为二，thread零把位置二的十加到位置零的六，得到十六；thread一把位置三的十二加到位置一的八，得到二十。第三轮stride为一，thread零把二十加到十六，得到三十六。最后只有thread零负责把三十六写到这个block的partial位置。

| 阶段 | 有效更新线程 | 前部共享数据的含义 |
|---|---|---|
| 加载后 | 全部八个 | 每格一个原始输入 |
| stride=4后 | 0至3 | 每格包含两个指定输入 |
| stride=2后 | 0至1 | 每格包含四个输入 |
| stride=1后 | 0 | 包含全部八个输入 |

这个树形结构把串行七次依赖更新重新组织为三轮协作，但总加法次数仍是七次。并行化减少的是依赖深度，不是凭空消除数学所需的所有加法。理解“工作量”和“关键路径”不同，后面分析并行算法才不会只看源码循环层数。

### 2. 每轮同步保护的具体读写关系

第一轮中thread零写位置零，第二轮thread零要读取位置二，而位置二由thread二在上一轮写入。因此必须保证上一轮相关写入完成后再进入下一轮。同步不是为了让所有线程“整齐好看”，而是保护跨线程生产与消费关系。

某些线程在后面轮次不再执行加法，但仍可能属于屏障的参与集合。不能因为thread四不再更新前部数据，就提前退出整个Kernel；它在某个实现中仍需要到达相应同步点。优化warp级尾部时，也必须遵守所用原语和参与掩码的合同，不能仅凭“剩下都在一个warp”删除所有保证。

当输入长度小于线程数时，无效线程加载零。这样树形结构仍然合并固定数量的槽位，但多余槽位不改变总和。例如只有六个有效元素时，共享数组是前六个输入加两个零，结果就是六项和。若无效槽位保持未初始化值，输出可能随旧内存内容变化。

### 3. 非二的幂线程数为什么不能直接套公式

若线程数为六，简单地从stride等于六除以二开始，再不断整除二，会经过三和一两轮。第一轮前三个位置分别合并后面三个；第二轮只把位置一加到位置零，位置二中的一部分结果可能被遗漏。算法的正确性依赖线程数满足特定结构条件。

解决可以是使用补零到二的幂的逻辑结构、采用能处理任意长度的归约算法，或在包装器限制合法线程数。三种方案都合理，但必须与共享数组大小、加载分配和测试一致。只把launch里的线程数改成一个新数字，不代表归约算法自动变通用。

本卷固定一百二十八线程的示范选择了容易验证的情况。你在改造它时，先用CPU列表模拟每轮共享数组变化，证明每个原输入最终贡献恰好一次，再把相同结构搬到设备。这个顺序能把算法遗漏与设备同步问题分开排查。

## 操作工作坊三：执行顺序、内存可见性和结果观察

### 1. 一次丢失更新的完整交错

设共享计数器初值为零，两个线程都执行普通的“读取、加一、写回”。线程A读到零，线程B也读到零；A计算一，B也计算一；A写回一，B随后也写回一。最后结果是一，而任务要求的两次增加应得到二。

问题不是整数加法算错，而是一次逻辑更新被拆成多个可交错步骤。原子加可以给这类更新提供相应原子语义，使两次增加都被保留。但如果计数器用于宣布另一块数据已经准备好，还必须分析数据写入与计数观察之间的内存顺序和作用范围，不能只把加法变成原子就宣称整个发布协议正确。

这也是为什么初学Kernel最好从每个输出唯一所有者开始。独立写入让你先掌握寻址和覆盖，再逐步进入共享协作。复杂并发协议应当建立在明确的不变量和官方内存模型上，而不是靠不断运行看是否“暂时没错”。

### 2. CPU函数返回不代表GPU任务结束

launch提交通常具有异步性质，host可以继续执行后续代码。若你在launch前后用CPU时钟立即取差值，测到的可能主要是提交开销，而不是Kernel完整执行时间。若随后读取尚未完成的异步结果，也可能违反接口使用要求。

正确性检查需要一个能保证目标工作完成的观察点，例如适当的同步或满足语义的结果拷回。性能测量则需要明确是测设备执行、提交延迟还是端到端路径。三者都可以有价值，但不能把其中一个数字换名成另一个。

后面的K13会研究不同stream之间的事件依赖。当前只使用一个清楚的顺序执行路径，先保证“输入准备完成—Kernel使用输入—结果完成—CPU验证”的关系成立。初学阶段减少同时变化的执行维度，有助于定位问题。

### 3. 为什么设备错误可能在后一个API上报

设备工作是异步提交的，某个执行错误可能直到host后来调用同步相关接口时才被发现。因此报错显示在结果拷贝处，并不必然说明拷贝参数本身就是根因。需要回看此前提交的Kernel、配置和输入。

一个有效调试方法是把任务缩小，在可疑Kernel后增加明确同步与错误检查，以缩短错误发生和被观察之间的距离。这样做用于定位，不代表最终性能路径必须保留每个全设备同步。找到错误后，再依据正确依赖恢复合理异步结构。

记录完整错误码、调用位置、输入shape和launch配置，比只保存“CUDA error”最后一行更有用。地址错误、无效配置、设备产物不兼容和内存不足属于不同类别，各自需要不同证据。

## 操作工作坊四：三份从错误到正确的修改报告

### 报告一：把所有输入改成整除尺寸为何不算修复

原程序在n为一千零三个时失败，改成一千零二十四后成功。这个观察说明错误可能与尾部相关，但它没有证明程序已经正确。若接口合同允许任意正长度，修改测试输入只是绕开失败，不是满足合同。

正确报告应记录原失败输入、预期最后合法下标、实际覆盖或访问的最后位置，然后定位是grid向下取整、缺少加载保护还是共享尾部没有填零。修复之后保留原失败输入作为回归，并增加几个相邻长度，防止只针对一个常数作补丁。

### 报告二：增加同步后结果变对，也需要解释原因

若在某个位置加入同步后随机错误消失，这是一条有价值的线索，但仍需说明同步保护了哪条依赖。可能是生产者尚未写完共享tile，可能是消费者还在使用旧tile时下一轮覆盖，也可能是host提前读取结果。不同层次需要不同同步范围。

把所有位置都加全设备同步虽然可能掩盖一些竞态，却会改变调度和性能，也可能仍没有修复真正的所有权错误。报告应列出生产写入、消费读取、复用覆盖三个事件，说明哪两个事件之间缺少顺序，以及选择的同步原语为什么足够。

### 报告三：换block大小后更快，不等于找到了普遍最优

同一Kernel在某个输入上用一百二十八线程比二百五十六更快，可能与寄存器、内存访问、有效线程比例或调度有关。要得出可迁移解释，需要比较多个尺寸、记录编译资源和测量范围，而不是把一个常数写成所有设备的最佳实践。

正确性合同也要重新检查。例如固定shared数组只有一百二十八元素时，直接改成二百五十六线程可能越界。性能实验应该在已证明正确的配置集合中进行。把失败配置的异常快数字纳入比较，会让错误实现看起来像“优化成功”。

## 追加的四道迁移题

**迁移题一：一个线程持有两个输出。** 让总线程数为八、输入长度为十六，每个线程处理初始i和i加八。参考判断：覆盖恰好一次，但相邻两轮的数据仍需分别满足边界；如果长度改成十三，第二轮只有线程零到四有效。用统一grid-stride公式比手写两次重复代码更容易扩展。

**迁移题二：每个block处理一整行。** 二维softmax可以让block号选择行，线程在列维分工。此时grid大小主要由行数决定，不再等于总元素数除以线程数。参考解释必须指出工作单位从元素变成行，归约与归一化需要block内协作，不能直接复用独立加法的提前退出方式。

**迁移题三：为什么只有thread零写partial。** 一个block归约结束后，最终总和位于约定位置。若所有线程写同一个partial地址，即使写入相同数值，也引入没有必要的重复写入与潜在竞争语义；指定一个拥有者让输出责任清楚。若每个线程保存不同局部和，则必须先完成合并，不能任选一个线程的值当总和。

**迁移题四：把launch与数学规模分别命名。** 用problem_size表示元素总数，block_threads表示每块线程数，grid_blocks表示块数，element_stride表示张量存储步长，grid_stride表示线程循环跨度。参考答案要求在公式旁标注单位，说明修改block_threads不会自动改变数学问题，修改element_stride则改变输入地址解释。清楚命名不是装饰，它直接减少跨层混淆。

## 最终验收

不看代码，解释一次host调用从分配、复制、launch、执行、完成观察到释放的全过程；对任意小n和合法grid/block，写出所有线程工作列表并证明恰好覆盖；对二维尾块给出合法与非法线程坐标；对共享归约指出每次同步保护的依赖；最后区分block协作、warp组织与SM资源。若这些问题仍只能回答几个英文缩写，应回到具体十个或十九个元素的轨迹重新演算。

### 资源调度手算补充：为什么block数不等于同时执行数

为了单独理解调度，设一个虚构设备只有两个SM，某个Kernel受资源限制使每个SM同一时刻最多驻留两个block。一次launch创建九个block。逻辑上九个block都属于同一个grid，但初始最多只有四个block驻留，剩余工作要等待资源释放。这个数值例子不是任何真实H100资源规格，只用于把逻辑数量与物理驻留分开。

若所有block执行时间恰好相同、调度无开销且资源完全均衡，可以粗略想象先处理四个，再处理四个，最后处理一个。最后一批只有一个block，另一部分资源闲置，这种尾部效应可能降低整体利用率。但真实设备执行可能交错推进，block时间也未必相同，所以这种批次图只是解释模型，不是精确时间预测。

如果其中一个block因为处理更多有效元素而运行更久，其他block完成后资源可以继续接收后续工作。你不能从block编号推断它什么时候开始，更不能让block八假定block零已经写好某个全局结果。编号服务地址分配，不构成时间顺序保证。

现在考虑每个block增加共享内存tile，使每个SM只能驻留一个block。虽然单个block可能因复用更多数据而更快，整个grid可同时驻留的block数却从四降到二。最终性能可能变好也可能变差，要比较单块工作效率和全局并发机会，不能只看其中一项。K06的tile优化与K14的资源测量正是在分析这种取舍。

再考虑把工作改成少量persistent block，每个block完成一个任务后领取下一个。这样可能改善某些负载不均衡，但需要额外任务队列、领取成本与同步设计，也可能牺牲其他调度灵活性。你现在不需要实现它，只要理解高级策略仍然围绕同样的问题：有限执行资源怎样承担更多逻辑工作。

这份手算还解释了为何“把grid设得极大”不是通用提速方法。过多细碎block会增加调度和边界开销；过少block则可能无法提供足够并发；每个block的资源占用又限制驻留。合理配置来自问题尺寸、工作量、数据复用和硬件资源共同决定，绝不能只凭一个参数越大越好来选择。

请把虚构设备的SM数改成三个、每个SM驻留上限改成两个、grid改成十三，先计算最多同时驻留六个block，再讨论最后剩余一个block时的尾部。随后说明如果block执行时间不等，该简化批次图会失去哪项假设。能明确写出模型假设和失效条件，才是把调度直觉转成工程分析的起点。

最后记录你选择的工作单位究竟是单个元素、一整行还是一个矩阵块，并说明改变这个单位以后，地址公式、同步范围和输出所有者分别需要怎样调整。这份记录将成为下一章访存分析的输入。
