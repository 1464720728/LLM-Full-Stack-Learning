# K03　CUDA 的执行组织：从一个线程到整个 Grid

先修 K01、K02。目标：手动设计不会遗漏或重复写入的索引映射，解释 Thread、Warp、Block、SM 的关系，读懂第一个完整 CUDA 程序。

## 1. 程序实例与硬件资源

一个 CUDA Kernel 是设备上运行的函数。启动语法 `kernel<<<grid,block>>>(...)` 指定要创建多少线程块，每块包含多少线程。`threadIdx` 给出块内坐标，`blockIdx` 给出块坐标。它们描述逻辑工作组织；程序员通常不直接指定某块必须在哪个 SM 上执行。

同一 Thread Block 的线程可以通过 Shared Memory 交换数据并使用块级屏障。通常一个 Block 驻留在一个 SM 上；一个 SM 可以同时容纳多个 Block，受线程数、寄存器、共享内存等限制。Grid 中的 Block 数可以远大于 GPU 的 SM 数，硬件会分批安排。于是 “GPU 有 132 个 SM，就只能启动 132 个 Block” 是错误的；SM 数也不能代替实际设备查询。

在 NVIDIA CUDA 的基本执行模型中，一个 Warp 有 32 个线程。Warp 调度器以 Warp 为重要调度单位；每个线程仍拥有自己的寄存器状态与逻辑索引。不同 Warp 能执行不同的指令阶段，同一 Warp 遇到不同分支时可能需要分别执行不同路径。现代架构的线程调度细节更复杂，但不能因此忽略显式同步与活跃线程掩码。

## 2. 一维映射与尾部

长度 N 的向量可用 `i=blockIdx.x*blockDim.x+threadIdx.x` 定位。假设 N=19、每块 8 线程，则需要 `ceil(19/8)=3` 块。第三块的线程下标覆盖 16 到 23，只有 16、17、18 有效，剩余线程必须被边界判断保护。若写成 `i<=N`，就会访问第 19 个下标；数组合法范围是 0 到 18。

Grid-stride loop 让线程继续处理相隔整个 Grid 线程数的元素：

```cpp
for (int i=blockIdx.x*blockDim.x+threadIdx.x;
     i<n; i+=blockDim.x*gridDim.x) {
    c[i]=a[i]+b[i];
}
```

N=19、2 块、每块 4 线程时，总步长为 8。线程 0 处理 0、8、16；线程 1 处理 1、9、17；线程 2 处理 2、10、18；后续线程处理两个或更少元素。每个合法下标除以 8 的余数唯一，所以既不重叠也不遗漏。这个数学论证比观察一次输出正确更强。

## 3. 屏障不是“暂停一下”

`__syncthreads()` 在 Block 范围内协调线程到达，并提供相应的共享内存可见性保证。若一部分线程提前 return，剩余线程又必须经过屏障，就可能形成非法同步或挂起。因此处理尾部时，常见模式是无效线程加载零但仍参与屏障，而不是立刻返回。

Block 间没有普通 `__syncthreads()` 能覆盖的全局屏障。一个 Kernel 内用自旋等待“所有 Block 都到达”，可能由于部分 Block 尚未获得驻留资源而死锁：正在驻留的 Block 占满资源并等待尚未运行的 Block。先把多阶段计算拆成同一 Stream 上的多个 Kernel，是容易推理的全局阶段边界。Cooperative Groups 等机制有额外条件，不是随手替换一个函数名就能使用。

## 4. 主机与设备一起完成任务

完整流程包括：选择设备、分配显存、复制输入、启动 Kernel、检查启动错误、等待或读取结果、验证、释放资源。[basics.cu](../../labs/kernels/cuda/basics.cu) 给出完整实现。它有向量加法、块归约和带尾部保护的 tiled GEMM，默认只用可见的第 0 张 GPU，数据规模很小。

CPU 部分先完成：

```bash
python -m labs.kernels.run --lab 3
```

K03 的 `exactly_once` 应为真。GPU 环境准备好后，先用 `nvidia-smi` 和框架设备查询确定当前分配给你的 GPU。以下以 H100 的一般目标 `sm_90` 示范，实际架构必须按机器选择：


这里的 `0` 只是示例设备编号；在共享服务器上改成已经分配给你的设备。RTX 5070 Ti 的目标不能照抄 `sm_90`，见 K16。若 Toolkit 不识别目标架构，先核对工具链支持矩阵，不能靠改成一个“能编译的旧编号”来证明兼容。

`cudaGetLastError` 能捕获启动配置等错误，但异步执行错误可能在后续同步或复制时才报告。因为本例用设备到主机复制取得结果，相关错误会在复制步骤暴露。生产调试中要结合调用位置与同步边界，不能误以为报错的复制操作一定是根因。

## 5. 练习与参考答案

1. **索引证明。** N=37、Grid=3、Block=4，列出线程 0、5、11 的任务。答案分别为 `{0,12,24,36}`、`{5,17,29}`、`{11,23,35}`；用取余证明唯一性。
2. **尾部故障。** 移除向量加法的 `i<n`，为什么 N=1024 可能掩盖错误、N=1003 更容易发现？答案：整除尺寸没有尾部线程；不整除时多出的线程访问越界。验收测试须同时包含 0、1、块边界前后与不规则大小。
3. **屏障判断。** `if(i>=n) return; __syncthreads();` 是否安全？参考答案：对于部分线程有效、部分无效的同一 Block，这种控制流不应当作为安全写法；让所有线程参与屏障并将无效输入置零。
4. **二维实操。** 写二维 Grid 映射矩阵元素，验证 `19x17` 每个位置写一次。参考：x 维映射列、y 维映射行；每个维度分别向上取整并检查 `row<m && col<n`。
5. **归约阅读。** 解释本例为何要求 Block 固定为 128。答案：共享数组尺寸与二分归约假设共同限制它；改变 launch 的 Block 大小却不改实现，会让索引或归约树不匹配。
6. **错误定位。** 构造一个维度不匹配的调用，先在 Host 入口拒绝；再说明为何不能只靠 GPU 运行后发现。答案：错误契约可能引发越界且异步报错位置不直观；入口检查使问题定位到调用者。
