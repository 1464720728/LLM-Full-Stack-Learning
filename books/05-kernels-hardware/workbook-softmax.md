# 工作簿 W1：从空白文件写出可靠的 Softmax

这是 K05、K08、K09 的逐步实作课程。请按阶段完成，每个阶段先预测、再运行、最后解释。不要先把参考文件复制到自己的实现中，否则你只能证明复制成功，不能证明理解。建议在个人 PC 的 CPU 上完成阶段一到五，再在个人 GPU 或分配给你的 H100 上完成设备阶段。全程不需要模型权重、API 或持续占用服务器。

## 阶段一：先写接口，不急着写公式

在练习目录建立 `softmax_work.py`。第一版只接受二维浮点数组，逐行计算，无 mask。你要写下输入 `[M,N]`、输出 `[M,N]`、N 必须大于零、输入必须有限、输出不修改输入。为什么要写这些看似平凡的条件？因为代码对 N=0、NaN、非连续视图、全掩码行的行为并不会由“Softmax”这个名字自动决定。没有约定，之后测试失败时你无法分清是实现错还是调用者提出了尚未支持的情况。

先写一个 `check_inputs` 函数：转为 NumPy 数组；检查 rank；检查列数；检查有效值；在失败时抛 `ValueError` 并说明原因。不要把二维要求写成只检查 `len(x)>0`：三维张量也可能有长度。不要把 dtype 判断与数学值判断混为一谈：整数数组可以转换为浮点计算，但最终是否允许它是接口选择，应明确。

验收：二维正常输入通过，一维输入被拒绝，形状 `(2,0)` 被拒绝，包含 NaN 的输入被拒绝。此时还没有 Softmax 计算，但你已经完成了一个可维护算子的边界。

## 阶段二：用循环写最笨但透明的版本

第一版不要向量化。对每一行，先循环找最大值；第二次循环计算指数并求分母；第三次循环除以分母。用 Python `math.exp` 和普通列表即可。三遍循环重复读取数据，性能并不好，但每个中间量都可打印，你能看到每一步对数学公式的实现。

输入 `[0,ln2,ln3]` 时，最大值是 ln3，平移后的指数为 `[1/3,2/3,1]`，分母为2，输出 `[1/6,1/3,1/2]`。若你直接记住输出而不解释分母为何变成2，就还没有把稳定变换与原定义联系起来。将最大值取为零时，原指数为 `[1,2,3]`，分母为6，最终比例相同。公共缩放改变分子分母的绝对量，不改变比值。

把每一行加上常数 c=1000 再运行。正确稳定版本保持结果；直接指数版本可能溢出。这个实验不是让你相信“减最大值就是经验技巧”，而是看到代数等价如何避免有限表示范围的问题。

练习记录中保存三列：你手算的中间量、程序打印的中间量、两者差异。别只保存一张最终输出截图。未来读一个复杂 GPU 实现时，你仍然需要这种中间不变量。

## 阶段三：从循环变成 NumPy 广播

先计算 `m=x.max(axis=1,keepdims=True)`。M=2、N=3 时，m 的形状应为 `(2,1)`，不是 `(2,)`。为什么？因为 `x-m` 应让每行减自己的最大值。当 `(2,3)` 减 `(2,)` 时，NumPy 从最后维对齐，2 与3不匹配；某些方阵形状会让错误广播恰好成功，却沿错误方向操作。

接着计算 e 与分母。分母仍保留 `(M,1)`，这样每行除自己的和。写出每个变量形状：x `(M,N)`、m `(M,1)`、e `(M,N)`、d `(M,1)`、y `(M,N)`。这张表不是可选装饰，它是后面 Triton 布局推理的预演。

至少测一个非方阵 `2x3` 和一个方阵 `3x3`。非方阵有利于发现轴错误，方阵有利于发现“尺寸刚好能广播但含义错了”的情况。给每行加不同常数，验证每行结果独立。

参考解法在 `reference.py` 的 `stable_softmax`，但先不要看掩码分支。你应能用两三行向量表达式重现前面的三遍循环，并对所有已通过的小例子比较。

## 阶段四：加入 Mask，明确全无效行

mask 的形状可以与输入一致，或者按 NumPy 规则广播。第一版建议只接受完全同形状，这样减少一个未知因素。mask 应转换为布尔值：若直接把整数 0/1 数组当作 NumPy 下标，它可能执行整数高级索引，而不是布尔选择。参考实现显式转 `dtype=bool`，正是为了避免这个细节。

对无效项，数学上希望它对分子分母贡献零。把分数设为负无穷，指数成为零。假设输入 `[-3,-2,-1]`，只允许前两项，正确概率应在这两项之间归一化，第三项为零。若把第三项替换成零，它反而比前两项更大，可能夺走最多概率。

全无效行需特别约定。本课程参考输出全零。实现先求最大值，再把非有限的行最大值替换为零作为安全计算基准；无效指数仍明确为零；最后用 `np.divide(...,where=d>0,out=zeros)` 避免零除。这个过程不是在改变有效行结果，而是在为特殊输入建立确定行为。

现在运行：

```bash
python -m labs.kernels.workbook softmax
```

你会看到输入 `[1000,1001,1002]` 被补齐到四项时，第四项为负无穷，指数为零。随后工作簿故意把 `[-3,-2,-1]` 的补齐项设为零，合法三项的概率和只剩约0.3561。这个数字直接证明 padding 已经偷走概率；如果测试只检查“所有输出在0到1之间”，根本抓不住错误。

## 阶段五：编写真正能抓错的测试

测试至少覆盖五类不变量。其一，有效行概率和为一；其二，每项非负；其三，整行加常数不改变结果；其四，掩码位置严格为零；其五，全掩码行遵守约定。还应比较一个独立写法的 oracle。不要让测试从被测函数内部取分母再检查结果，这可能同时复用错误。

边界 shape 包括 `1x1`、`2x3`、`3x31`、`17x257`。单元素行输出一；宽度31和257主动触及二次幂补齐；M=17说明行数也不必整除某个习惯块大小。随机数据要固定种子，但数值检查使用合理容差而非依赖具体机器的最后一位。

故障注入是一种检验测试质量的方法。把减最大值删掉，大数输入测试应失败；把 mask 填充值改为零，mask 测试应失败；把 `axis=-1` 改成 `axis=0`，非方阵或逐行平移测试应失败；把分母改为所有元素总和，行和测试应失败。每次只注入一个错误，确认报错与预期一致，然后恢复。

## 阶段六：把行交给 CUDA Block

看 `cuda/numerical.cu` 的 `row_softmax`。一个 Block 负责一行，固定128线程。行宽131时，线程0处理列0与128，线程1处理1与129，线程2处理2与130，其他线程只处理一个位置。每线程先得到局部最大值，然后写到 `scratch[t]`；Block 在 Shared Memory 上做树形最大值归约。

为什么不用“每线程一个元素”直接发131个线程？可以设计其他映射，但本课程选择固定二次幂线程数以简化归约树，同时用跨步循环支持任意行宽。这区分了逻辑元素数 N 与执行线程数128。它们不必相等。

所有线程从 `scratch[0]` 读出最大值后，程序有一个额外屏障，再复用 scratch 保存局部指数和。这个屏障容易被忽略：如果一个快线程已经开始覆盖 scratch[0]，另一个慢线程还没读取最大值，就可能读到分母阶段的数据。第一次归约末尾的屏障只保证归约完成，不自动保证所有线程都已经把结果读取到自己的寄存器。

随后每线程计算自己负责的指数，暂存到输出 y，再对局部和做 Block 归约，最后把 y 除以总分母。这里输出缓冲被用作临时存储，增加显存读写，但让实现直观。高性能实现可能将更多值保留在寄存器或采用其他映射；先得到可证明正确版本，再讨论复用。

Host 代码将3行、每行131个数拷入 GPU，调用 Kernel，再与 double 稳定公式比较。使用1000附近的大值，是为了验证稳定性，而不只是随机输入。编译命令按真实设备选择架构：

```bash
nvcc -O2 -lineinfo -arch=sm_90 labs/kernels/cuda/numerical.cu \
  -o build/kernel-labs/cuda_numerical
CUDA_VISIBLE_DEVICES=0 ./build/kernel-labs/cuda_numerical
```

这是 H100 示例，5070Ti 不照抄目标。GPU 不可用时，完成静态寻址与同步分析，并诚实标记未运行。

## 阶段七：同一算法的 Triton 表达

Triton `_row_softmax` 把一行作为块级值读取，逻辑块长度取不小于 N 的二次幂。编译器处理块内归约映射，你不需要像 CUDA 版本手写 scratch 和每一步屏障。省略这些代码不等于硬件不需要协作，而是抽象层把它交给编译器。

逐行解释五件事：row 确定哪一行；col 是这行的逻辑列索引集合；load mask 阻止越界；负无穷使 padding 在最大值/指数计算中不参与；store mask 阻止写出真实行范围。`tl.max(x,0)` 和 `tl.sum(p,0)` 的0是本地块张量的轴，而不是原始输入矩阵的全局行轴。因为一个 Program 只持有一行，它的块张量是一维。

包装函数要求连续二维 float32，输出也连续。如果传入转置视图，不应悄悄运行；本例会拒绝。要扩展非连续布局，需要增加输入行步长与列步长，正确计算地址，而不是把 shape 从包装函数传过去就算完成。

## 阶段八：从正确到有限性能实验

先用 `gpu_check --run` 通过数值测试，再讨论计时。Softmax 的完整基准可作为你的练习扩展：分配输入在计时外，暖机三次，用设备 Event 测若干重复，报告行宽与行数。不要在第一次 JIT 时就宣布“比 PyTorch 慢1000倍”，也不要把只有单个热缓存小矩阵的结果推广到所有形状。

对于宽度很大的一行，块内资源会增加；对于大量很短行，一行一个 Program 可能又有其他开销。观察不同区域，比只调一个代表性 shape 更能培养判断力。性能未提高也可以通过本工作簿：第一目标是正确、可解释、可维护，不是击败库。

交付自己的循环版本、NumPy版本、测试、CUDA/Triton读码笔记、一次故障注入记录和真实运行状态。至少完成一个扩展：非连续输入、mask、反向传播、宽行分阶段四选一。选择 mask 时必须处理全无效行；选择反向时必须验证 `p*(g-sum(pg))`；选择非连续时必须用转置或切片主动验收；选择宽行时必须写明多阶段状态。

口头验收有四问：为什么减最大值不改变结果；为什么 padding 不能填零；为什么 CUDA 复用 scratch 前需要同步；为什么 Triton 的块内轴0不是整个矩阵的axis0。四问都能从自己的代码回答，才算完成，而不是只得到一行 PASS。

## 加练：不要让测试被“看起来正常”欺骗

准备三份输出：一份正确Softmax、一份每行除以整个矩阵分母、一份把掩码填零。它们可能都没有NaN、都在0到1之间、形状都正确，因此表面检查完全通过。你要为每份错误输出找一个最小反例。第二种用两行相同输入时，每行和只有约一半；第三种用负logits和一个被屏蔽位置时，无效位置仍吸收概率。把反例写成自动测试，比在日志中看到“结果不太对”更有工程价值。

再考虑dtype。假设输入float16，若最大值与指数仍以低精度处理，某些差异可能被舍入；累加分母时小项也可能丢失。你可以在CPU上先用float64建立oracle，再分别模拟较低精度的中间步骤，观察误差在哪里出现。不要仅把最终输出astype成低精度就声称模拟了整个低精度Kernel：中间运算类型与舍入时机同样重要。

最后加入梯度。给输出设置一个固定上游梯度g，定义标量损失为sum(p*g)。用有限差分检查每个输入分量，再对照公式 `p*(g-sum(p*g))`。如果g全为1，损失是概率和，理论上为常数，梯度接近零。这是一个很好用的结构测试，但不能只测它，因为一些错误实现也可能恰好输出零梯度。再加一个不同元素的g，才能观察真正的雅可比作用。

完成这些加练后，你的作品已经包含输入契约、前向、mask、padding、数值稳定、布局、反向和故障测试。下一次遇到新的归一化算子，应该复用的是这套推导与验收方法，而不是把Softmax代码换几个函数名。
