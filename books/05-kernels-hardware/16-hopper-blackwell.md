# K16　H100 与你的 5070 Ti：同样写 CUDA，不同的硬件契约

先修执行组织、访存和编译。本章不让你背一张越来越过期的峰值表，而是教你识别设备能力、阅读硬件文档，并把代码路径与真实设备对应起来。资料核查日期：2026-11-01。

## 1. 产品名、架构名、Compute Capability 分开

NVIDIA 官方 CUDA GPU 表将 H100/H200 列为 capability 9.0，B200 为 10.0，B300 为 10.3，GeForce RTX5070Ti 为 12.0。这里的编号描述指令和编程能力分类，不是“12.0 在所有方面都包含 10.3 的超集”，也不是 CUDA Toolkit 版本号。

| 设备 | 官方表中的 CC | 学习意义 |
|---|---:|---|
| H100 / H200 | 9.0 | Hopper 路线；学习 WGMMA、TMA 等需核对具体指令目标 |
| B200 | 10.0 | 数据中心 Blackwell 路线，不与消费级路径自动等价 |
| B300 | 10.3 | 另一个明确目标，不能简单套用旧 SKU 容量或指令假设 |
| RTX5070Ti | 12.0 | 个人可随时练习的 Blackwell 消费级设备，适合大量单卡基础算子实验 |

表来自 [NVIDIA CUDA GPU Compute Capability](https://developer.nvidia.com/cuda/gpus)。容量、带宽、SM 数、互连与功耗还取决于具体产品。你在运行时应查询实际设备，而不是把网上某款 SXM/PCIe/整机参数混在一起。

## 2. Hopper 的两个重要协作接口

TMA 为张量数据搬运提供专门机制，允许以描述符表达某些多维传输。WGMMA 以 Warpgroup 协作执行特定矩阵乘加；一个 Warpgroup 包含四个 Warp，即 128 个线程。使用它时，线程参与、操作数布局、异步完成与同步都有严格要求。

“一个 Warp 搬运、另外三个 Warp 算矩阵乘法”可以是抽象分工示意，却不能直接当作 H100 WGMMA 的合法实现。真实 CUTLASS Hopper 路径常以生产者与消费者 Warpgroup 组织流水线；其中实际发起某项搬运的线程可以更少，不能从抽象角色数推断所有线程都做同样工作。

学习次序是：先读普通 Shared Memory GEMM，理解缓冲区读写→再读异步搬运→再读 mbarrier/phase 等同步协议→最后看 TMA 与 WGMMA 的组合。跳过前面三步，只记两个缩写，很难定位真实 Kernel 的死锁或错误结果。

## 3. 数据中心 Blackwell 与消费级 Blackwell

某些 Blackwell 数据中心矩阵路径使用 TMEM 与新矩阵指令组织。不能因为 5070 Ti 也叫 Blackwell，就假定它可运行相同 SM100 专用 Kernel。编译目标、具体指令和官方支持矩阵是依据，产品家族名称只是起点。

这也说明你的两类硬件分工很好：个人 PC 用于大量短小单卡正确性练习、Triton基础、布局、归约与中小 GEMM；H100 用于 Hopper 专用源码/指令、较大模型或必要的多 GPU 通信实验。不是回避 H100，而是让每次使用都有明确需要验证的问题。

## 4. Windows、WSL2、驱动和 Toolkit

WSL2 是 Windows 上的 Linux 环境。NVIDIA 官方指南强调：在 Windows 主机安装支持 WSL 的驱动，WSL 内使用映射的 CUDA 驱动接口，不应在 WSL 内再安装 Linux NVIDIA 显示驱动覆盖它。编译 CUDA 代码需要合适 Toolkit；仅运行某些预构建框架包时，依赖关系又有所不同。

不要复制一个带驱动的 Linux 整套安装命令到 WSL。先读当前官方 WSL-Ubuntu 安装说明，确认软件包是否包含驱动。具体版本会更新，本课程采用能力检查而非硬编码一个永久有效的版本号。

初始诊断：在 Windows 查看驱动和 GPU，在 WSL 查看 `uname -a` 与 `nvidia-smi`；在实际 Python 环境打印 `torch.cuda.is_available()`、设备名称、capability、显存总量与 torch 版本；需要编译时再检查 `nvcc --version`。这些命令分别回答不同问题，成功一个不代表其他全部成功。

## 5. 共享 H100 的实验纪律

默认只用已分配的一张 GPU，设置 `CUDA_VISIBLE_DEVICES`，保持实验数据和迭代次数有界。先用 CPU oracle 验证公式，再运行几十个小 shape 的 GPU 正确性；只有通信实验才显式用两卡。八卡实验应当有拓扑与并行问题需要回答，不能为了“更专业”直接占满。

本课程 GPU 检查数据很小，不下载模型，不启动长期服务，不做自动性能压力测试。真实模型与框架实验见推理系统卷。若需要持续 profiling，先安排可用时间段并保存计划，确保能正常退出和释放自己创建的资源。不要使用清空全部容器或终止所有 Python 进程的粗暴清理方式。

## 6. 练习与参考答案

1. **分类。** `sm_90`、CUDA 13.x、H100、80 GB 分别描述什么？答案目标能力编号、软件工具链版本、产品、容量规格；后者还须核对具体 SKU。
2. **兼容性。** H100 专用 WGMMA 代码能否仅改编译参数成 `sm_120` 就必然运行？答案不能；需核对指令支持和替代路径。编译通过也还要验证数值与同步。
3. **设备记录。** 在两台环境分别保存设备/软件清单。验收显示实际查询结果，不填教材示例值；公司敏感主机名与内部路径不上传公开仓库。
4. **WSL 排错。** WSL 中看得到 GPU，但 nvcc 不存在，是否说明驱动坏了？答案不说明，运行驱动接口与编译 Toolkit 是不同组件；根据任务决定是否需要安装 Toolkit。
5. **实验选择。** 向量加法、Hopper TMA 主循环、双 GPU AllReduce 各放哪里？参考：个人GPU即可、H100、两张获分配GPU；先做CPU验证，避免不必要占用。
6. **源码任务。** 找到一个 CUTLASS 示例的目标架构和调度策略，写出为何适合或不适合你的设备。验收要求真实文件/符号证据，不能以示例标题中的 Blackwell 一词替代判断。

掌握门槛：面对“某 Kernel 不支持某 GPU”能逐项核对格式、指令、编译目标、软件后端和内存要求；不把一切归因于显存不足。
