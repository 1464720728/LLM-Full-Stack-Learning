# K13　Stream、Event 与 CUDA Graph：时间关系也是程序的一部分

先修 K03 主机/设备执行、基础卷并发。目标：从依赖关系理解异步执行，避免测到错误时间，知道 Graph 缓存的是什么，以及它与 Kernel Fusion 的不同。

## 1. Host 返回不代表设备完成

CPU 发起 GPU 工作后，可以继续执行下一条主机语句。一个 Python 函数返回输出张量，可能只是返回已分配内存的句柄，而设备计算仍在队列中。若立刻用 CPU 时钟包住 launch，测到的可能主要是提交时间，而非 GPU 实际执行时间。

同一 Stream 内的相关工作有顺序关系，便于表达“复制输入→运行 Kernel→读取结果”。不同 Stream 可表达独立工作，但是否实际并行，取决于资源、依赖和硬件执行能力。创建十个 Stream 不会让一张 GPU 的算力自动增加十倍。

默认 Stream 在不同模式与库使用习惯下有细节差异。初学时不要依赖模糊的“默认会同步”印象；显式梳理生产者、消费者和所用 Stream，并以当前官方 API 语义为准。

## 2. Event 表达完成边界

Event 可以记录某个 Stream 到达的位置。另一个 Stream 等待该 Event 后再消费数据，就建立了明确依赖。它比对整个设备做同步更细粒度，也更容易保持不相关工作重叠。

例如 A Stream 生成 buffer，B Stream 要使用它：先在 A 中记录 event，再让 B wait event。若只是 CPU 先调用 A 的函数、再调用 B 的函数，不能自动推断两个不同 Stream 间的数据依赖已经建立。内存分配与释放也要服从这个时间关系。

双缓冲流水线包含另一条反向依赖：生产者不能覆盖消费者尚未读完的 buffer。因此至少需要表达“数据就绪”和“buffer 可复用”两种状态。只通知前者会产生覆盖竞争，只通知后者又会读到尚未完成的数据。

## 3. 有限流水线的填充与排空

每个 Tile 搬运需要 L，计算需要 C，假设两个独立执行资源、双缓冲、零同步开销。处理 N 个 Tile 的理想时间为：

\[
T=L+C+(N-1)\max(L,C).
\]

N=3、L=4、C=8 时，串行为 36，流水线为 28。第一块要先装载，最后一块要完成计算，因此不能直接写 `N*max(L,C)=24`，那忽略了填充/排空。

```bash
python -m labs.kernels.run --lab 22
```

真实流水线还有启动、屏障、资源争用、缓冲区容量和可重叠程度；公式是理想下界模型，不能被当作 H100 实测加速。

## 4. CUDA Graph 缓存执行图

CUDA Graph 把一组设备操作及依赖组织成可重复提交的图。它可减少 CPU 一次次提交许多小操作的开销，尤其当计算图反复执行时。Graph 本身并不意味着所有算子合并成一个 Kernel；GPU 仍可能执行许多 Kernel 节点。

Kernel Fusion 改变计算和中间数据组织，可能减少 HBM 读写与启动次数；Graph 更关注提交和执行依赖复用。二者可以结合，但不能用一个术语代替另一个。MegaKernel 则进一步把更大任务调度与计算放到设备程序内部，见 K17。

Graph 捕获与重放需要满足相关 API 的约束。动态 shape、动态内存地址、CPU 分支和不支持捕获的操作可能需要额外管理。一个常见方式是固定 shape bucket 与稳定缓冲区，再把本次数据复制到既定位置；但桶的 padding 会有成本，也不是所有请求都能无条件复用同一图。

## 5. 如何测量才回答你的问题

若问题是“用户等待多久”，计时要涵盖相关 CPU 工作、排队、必要传输与最终同步。若问题是“某个 Kernel 设备执行多久”，可使用正确记录在相关 Stream 上的 GPU Event，配合暖机与重复。若问题是“流水线吞吐”，应计时一批稳定工作而非单个操作。

暖机可能包括 JIT、CUDA context、缓存与库初始化。不要把所有冷启动都丢弃不报告：服务刚启动时用户会经历它；只是稳态比较应与冷启动分开。多租户服务器上，别人的工作也可能影响测量，记录共享条件并使用短、有界实验。

## 6. 练习与参考答案

1. **时间线。** 搬运 L=8、计算 C=4、N=3，理想时间？答案同样 28；瓶颈变为搬运，消费者更常等待。画出各 Tile 开始结束时间。
2. **依赖判断。** 两个 Stream 分别写同一输出数组不同区域，是否必须互相等待？答案若区域严格不重叠且无其他数据依赖，可以独立；若读取对方结果或释放共同存储，就需相应关系。
3. **故障。** 测 `start=time(); launch(); end=time()` 为什么可能得到极小值？答案测到提交而非完成；增加适当设备同步或 Event，并说明测量范围改变。
4. **Graph 选择。** 一次性的长 GEMM 与重复的小算子链，哪个更可能从减少提交开销获益？参考后者更可能，但须实测；长 GEMM 设备时间占主导时，提交优化比例较小。
5. **双缓冲设计。** 写两个 buffer 的状态机：EMPTY→LOADING→READY→COMPUTING→EMPTY。验收给每次转移定义谁发起、谁等待；不能只用一个“ready”布尔值掩盖复用阶段。
6. **实战扩展。** 在可用 GPU 环境用 PyTorch Stream/Event 比较串行与两 Stream 独立向量任务，限制每轮数据量与重复次数。答案允许“没有变快”，但报告必须解释资源/开销假设，并保证正确同步。

掌握门槛：能以数据依赖而不是调用顺序推理异步程序；能区分提交时间、设备时间和端到端延迟；不会把 Graph 说成大融合 Kernel。
