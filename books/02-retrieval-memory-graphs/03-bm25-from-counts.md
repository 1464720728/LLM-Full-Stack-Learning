# R03 从词频到 BM25：亲手实现可解释检索

先修：R02、字典与 Counter、对数和分数。目标是从文档计数推导一条实际排序，逐项核对分数，并能修改实现而知道改变了哪个假设。使用标准库，不下载模型。

## 小课一：先做一个能解释每一分的检索器

向量检索听起来更现代，但关键词检索仍然是理解检索系统的重要起点。它把一个问题拆成可观察的词项，让你知道某篇资料为什么被选中。对于错误码、函数名、产品型号、版本号和稀有专有名词，精确词项还具有直接价值。学习 BM25 的目标不是宣布它胜过所有语义模型，而是掌握一个有清楚假设、可逐项解释且容易作为基线的排名方法。

假设你搜索“cache keys”。文档甲写了两次 cache、一次 keys；文档乙只写了一次 cache；文档丙完全没有这两个词。最朴素的规则会把匹配次数相加，得到三、一、零。但马上出现两个问题。第一，重复一千次 cache 的垃圾文档是否应该获得一千倍优势？第二，一个非常常见的词与一个少见的专业词，是否应该贡献相同的分数？BM25 的核心设计正是对这些问题给出有结构的处理。

还有第三个问题：一篇一万字的长文更容易偶然包含查询词，不能仅因为它长就永远胜过短而直接的答案。另一方面，长文也可能提供完整解释，不能把所有长文都判为差。长度归一化需要可调强度，而不是简单除以文档长度。理解这三个问题以后，再看词频饱和、逆文档频率和长度因子，就能知道每项公式在补什么缺口。

本章先固定一个具体 BM25 变体：查询词去重，IDF 使用带一的平滑正值形式，文档长度按课程词法 tokenizer 的词项数计算。其他库可能使用不同的 IDF、查询词频处理和字段规则。读实现时必须逐项核对，不能只看到类名 BM25 就假设所有数值一致。我们不会把课程的可解释实现说成所有生产引擎的逐行复刻。

## 小课二：文档、词项、词频和文档频率分别是什么

设语料有三条文档：d1 是 `cache cache keys`，d2 是 `cache values`，d3 是 `index data updates`。这里刻意用空格分隔的英文，避免中文分词选择干扰第一次手算。文档总数 N 是三。d1 的词项序列长度为三，d2 为二，d3 为三。语料平均文档长度是 `(3+2+3)/3=8/3`。

词频 tf 关心一个词在一篇文档里出现几次。cache 在 d1 中的 tf 是二，在 d2 中是一，在 d3 中是零。文档频率 df 则关心有多少篇文档包含它，而不关心每篇重复多少次。因此 cache 的 df 是二，keys 的 df 是一。把这两个计数混淆，是第一次写检索器时最常见的错误之一。

| 词项 | d1 的词频 | d2 的词频 | d3 的词频 | 文档频率 |
|---|---:|---:|---:|---:|
| cache | 2 | 1 | 0 | 2 |
| keys | 1 | 0 | 0 | 1 |
| values | 0 | 1 | 0 | 1 |
| index | 0 | 0 | 1 | 1 |
| data | 0 | 0 | 1 | 1 |
| updates | 0 | 0 | 1 | 1 |

这张表可以按行看，也可以按列看。按列看，你得到每篇文档的词频字典；按行看，你得到一个词对应的文档列表与词频，也就是倒排结构。算法公式不要求你必须采用哪种存储布局，但查询效率会受到布局影响。课程实现先用文档词频字典遍历，便于观察；稍后再写一个倒排版本与它核对。

```python
from collections import Counter
texts = ["cache cache keys", "cache values", "index data updates"]
term_frequencies = [Counter(text.split()) for text in texts]
lengths = [sum(counts.values()) for counts in term_frequencies]
document_frequencies = Counter(
    term for counts in term_frequencies for term in counts)
assert term_frequencies[0]["cache"] == 2
assert document_frequencies["cache"] == 2
assert lengths == [3, 2, 3]
```

`for term in counts` 遍历字典的键，所以每篇文档中的 cache 只向 df 贡献一次。若你把它改成遍历原始 token 序列，d1 会贡献两次，cache 的所谓 df 就错误地变成三。这种错误不会导致程序崩溃，却会改变全部相关分数，属于静默逻辑错误。为 df 写一个“同文档内重复词不改变文档频率”的测试，比只测最后排序更容易定位它。

## 小课三：为什么常见词应该少贡献一些信息

假设一百篇文档都包含“系统”，只有两篇包含“前缀去重”。当你看到某篇文档含“系统”时，并没有缩小多少候选范围；看到“前缀去重”时，候选范围大幅缩小。这是逆文档频率的直觉：在当前语料中越普遍的词，单独区分文档的能力通常越弱。

注意这里的“信息”是针对检索区分能力的直觉，不是在证明每个罕见词都语义重要。一个随机乱码也可能只出现一次，却不是正确答案。IDF 只是一个排名因素，不是语言理解或事实判断。拼写错误和数据噪声甚至会获得很高 IDF，因此预处理和查询解释仍然重要。

课程使用的公式是：

$$
\operatorname{IDF}(t)=\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right).
$$

N 表示当前索引文档数，df(t) 表示包含词 t 的文档数，零点五是平滑项，ln 是自然对数。自然对数把乘法尺度压缩为更温和的数值变化；你不需要先掌握全部概率检索推导，先理解它随着 df 增加而减小。加一的形式使合法统计范围内的 IDF 保持正值，避免某些未加一变体对非常常见词产生负分。

对三文档例子，cache 的 df 为二，分数为 `ln(1+1.5/2.5)=ln(1.6)`，约零点四七。keys 的 df 为一，分数为 `ln(1+2.5/1.5)=ln(8/3)`，约零点九八。因此在其他条件相同的情况下，keys 的一次出现比 cache 的一次出现贡献更多。你可以用 Python 的 `math.log1p(x)` 计算 ln(1+x)，它直接表达了公式中的结构。

为什么不简单使用 N/df？当 df 为零时会除零；即使排除零，比例也可能过于陡峭。平滑避免某些边界奇异，对数压缩比例。不同检索模型对这些问题有不同处理，课程只承诺这套明确公式。若你要对齐外部引擎，必须核对它的平滑、对数底数、字段统计和删除文档处理，不能把小数差异都归咎于浮点精度。

## 小课四：词频为什么需要饱和

如果一个词出现一次，文档可能只是偶然提及；出现几次，主题相关性可能更强；出现一千次，不应自然获得一千倍相关性。词频饱和用一个逐渐变平的函数表达这种“边际收益递减”。先忽略长度因素，把因子写成 `f*(k1+1)/(f+k1)`，其中 f 是词频，k1 是正参数。

当 f 为零时，因子为零，未出现的词不贡献分数。当 f 为一且长度因子恰好等于 k1 时，因子为一。当 f 越来越大，分子分母都由 f 主导，因子趋近于 k1+1，而不是无限增加。这就是饱和上限。理解这个极限，可以不用画复杂图也知道重复词的优势会逐渐变小。

取 k1 为一点二，f 为一时因子一，f 为二时约一点三七五，f 为十时约一点九六四，极限为二点二。由一增加到二提升约零点三七五，由九增加到十则提升小得多。请自己计算相邻差值，看到“收益递减”在数字上是什么，而不是只记一个形容词。

k1 越小，越快接近只判断是否出现的行为；k1 越大，在有限词频范围内更接近线性增长。严格地说，k1 趋近零时，对任何正 f，因子趋近一；这类似把多次出现压成一次存在信号。课程代码要求 k1 大于零，不直接使用零，但你可以用很小的正数观察趋势。参数方向的理解比盲目记住常用默认值更有用。

饱和并不意味着重复词完全没有影响。若你重复一个词，也会增加文档总长度，长度归一化同时变化。因此研究 k1 时最好先把长度视为固定控制量，理解函数本身；再在真实文档上观察两种效应共同作用。一次实验同时改词频、总长度、平均长度和文档数，很难判断分数变化来自哪一项。

## 小课五：长度归一化不是简单惩罚长文

BM25 把文档长度与语料平均长度比较。设当前文档长度为 dl，平均长度为 avgdl，长度调整项为 `1-b+b*dl/avgdl`。参数 b 在零到一之间。b 为零时完全忽略长度；b 为一时使用完整的相对长度；中间值在不归一化与完整归一化之间插值。

当 dl 等于 avgdl 时，长度项等于一，不论 b 取何值。短文的比值小于一，长度项通常小于一；长文比值大于一，长度项大于一。这个项乘在 k1 上进入分母，所以在词频相同情况下，长文的单词贡献下降，短文上升。这里比较的是相同词频，而不是说长文最终总分必然更低；长文可能包含更多查询词。

三文档例子里 avgdl 为八分之三的倒数，即八除以三。d1 长度三，比平均稍长，比例九除以八；d2 长度二，比例四分之三。取 b 为零点七五、k1 为一点二，d1 的归一化常数为一点三一二五，d2 为零点九七五。你可以把这两个值看成词频饱和分母中“要克服的背景量”：同样出现一次，较短的 d2 获得更大的词频因子。

为什么不是直接除以 dl？那样会过度奖励极短文档，并把绝对长度与任务效果硬绑定。BM25 使用相对平均长度和可调 b，给系统留出控制归一化强度的空间。不过这并不证明某个 b 对你的资料最优。代码、表格、短问答和长报告具有不同长度分布，应通过固定评测集比较，而不是照抄一个数字就认为完成调优。

切块会改变 dl 与 avgdl。原本一篇长文切成十块后，N 也从文档数变成片段数，词项 df 随之变化。因此“只改切块大小”实际上可能同时改变 BM25 的多个统计量。比较切块策略时，要把索引单位明确写成文档或片段，并保存统计快照。否则你可能把排名改善误归因为边界更好，而实际上主要来自长度分布变化。

## 小课六：把三个因素组合成完整公式

现在把 IDF、词频饱和和长度归一化组合。对查询中每个去重词项 t，计算一项分数，再相加：

$$
\operatorname{score}(q,d)=\sum_{t\in\operatorname{unique}(q)}
\operatorname{IDF}(t)
\frac{f(t,d)(k_1+1)}{f(t,d)+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)}.
$$

q 是查询，d 是文档，f(t,d) 是 t 在 d 中的次数，|d| 是文档词项长度。这个式子不是一个概率输出。它给同一查询下的候选提供可比较的相关性分数；不应直接把一题的二点三分与另一题的一点八分解释成前者更可靠。查询词数量和稀有程度不同，分数尺度也会变化。

查询去重是本实现的显式选择。查询“cache cache keys”与“cache keys”会得到同样分数。某些变体会考虑查询词频，特别是较长查询或其他检索设定；如果你要加这项，必须修改公式与测试。不要在 tokenizer 中悄悄去重文档词项，因为文档词频正是饱和项需要的信息。

若查询词不在文档中，f 为零，它的贡献就是零。课程直接跳过这种词，以避免不必要运算。若整个语料为空，N 和平均长度都没有正常意义，课程返回空结果而不是试图计算除法。若文档存在但都没有有效词项，也应明确处理平均长度为零的情况。这些边界不是特殊到可以忽略的小事，空文件和只含标点的资料在真实摄入中很常见。

## 小课七：完整手算一次排名

查询为 cache keys，使用前三条文档。d1 的 cache 词频是二，归一化常数一点三一二五，因此词频因子是 `4.4/3.3125`，约一点三二八三。乘以 cache 的 IDF 零点四七，得到约零点六二四三。d1 的 keys 词频是一，因子为 `2.2/2.3125`，约零点九五一四；乘以 keys 的 IDF 零点九八，得到约零点九三三一。总分约一点五五七四。

对 d2，只有 cache 出现。归一化常数零点九七五，因子为 `2.2/1.975`，约一点一一三九，乘以零点四七得到约零点五二三五。keys 不出现，贡献零。d3 两个词都不出现，总分零。最终顺序是 d1、d2；课程只返回正且有限的分数，因此 d3 不进入结果。

| 文档 | cache 贡献 | keys 贡献 | 总分 |
|---|---:|---:|---:|
| d1 | 0.6243067 | 0.9331132 | 1.5574199 |
| d2 | 0.5235483 | 0 | 0.5235483 |
| d3 | 0 | 0 | 0 |

请特别观察：d1 的 cache 出现两次，贡献并不是 d2 的两倍。词频饱和与长度因素一起使比值约为一点一九二。d1 更大的总优势主要还来自 keys 这个更少见的查询词。能解释每项贡献，你就能回答为什么第一名获胜，而不是只说“算法算出来更相关”。

如果查询改成 cache，d1 仍排在 d2 前面，但差距变小。若把 d1 后面追加大量不含 cache 的词，保持 cache 词频二，长度惩罚可能让 d2 反超。这个反例很适合验证长度归一化确实生效。要注意追加内容也会改变 avgdl，所以完整手算时必须重新计算平均长度，不能沿用旧值。

## 小课八：从空白文件写出完整的评分器

下面的程序只依赖标准库，使用空格 tokenizer 保持与手算完全一致。它不是为了替换仓库的实现，而是一个可以独立检查的参考。先把它保存到自己的练习文件，逐个打印 tf、df、lengths 和平均长度，再执行最后的断言。不要从一开始就把所有中间值藏在一个巨大的 search 函数里。

```python
from collections import Counter
import math

class ExplainableBM25:
    def __init__(self, documents, k1=1.2, b=0.75):
        if not math.isfinite(k1) or k1 <= 0:
            raise ValueError("k1 must be finite and positive")
        if not math.isfinite(b) or not 0 <= b <= 1:
            raise ValueError("b must be finite and in [0,1]")
        self.documents = list(documents)
        self.k1 = float(k1)
        self.b = float(b)
        self.tf = [Counter(text.lower().split()) for text in self.documents]
        self.lengths = [sum(counts.values()) for counts in self.tf]
        self.n = len(self.documents)
        self.avgdl = sum(self.lengths) / self.n if self.n else 0.0
        self.df = Counter(term for counts in self.tf for term in counts)

    def idf(self, term):
        if self.n == 0:
            return 0.0
        frequency = self.df.get(term, 0)
        return math.log1p((self.n - frequency + 0.5) / (frequency + 0.5))

    def explain(self, query, document_index):
        if not 0 <= document_index < self.n:
            raise IndexError("document index outside corpus")
        if self.avgdl == 0:
            return {}
        result = {}
        length = self.lengths[document_index]
        norm = self.k1 * (1 - self.b + self.b * length / self.avgdl)
        for term in sorted(set(query.lower().split())):
            frequency = self.tf[document_index].get(term, 0)
            if frequency == 0:
                continue
            term_idf = self.idf(term)
            factor = frequency * (self.k1 + 1) / (frequency + norm)
            result[term] = {"tf": frequency, "df": self.df[term],
                            "idf": term_idf, "norm": norm,
                            "factor": factor, "score": term_idf * factor}
        return result

    def search(self, query, k=5):
        if type(k) is not int or k < 0:
            raise ValueError("k must be a nonnegative integer")
        candidates = []
        for index in range(self.n):
            details = self.explain(query, index)
            score = math.fsum(part["score"] for part in details.values())
            if score > 0:
                candidates.append((index, score, details))
        candidates.sort(key=lambda item: (-item[1], item[0]))
        return candidates[:k]

index = ExplainableBM25([
    "cache cache keys", "cache values", "index data updates"])
hits = index.search("cache keys")
assert [item[0] for item in hits] == [0, 1]
assert math.isclose(hits[0][1], 1.5574199428240533)
assert math.isclose(hits[1][1], 0.5235483465015789)
assert index.search("missing") == []
assert index.search("cache", k=0) == []
assert ExplainableBM25([]).search("cache") == []
```

构造函数复制 documents，是为了固定这次索引所依据的文档列表。如果外部随后 append 一条新记录，索引不会一半看新列表、一半仍使用旧统计。字符串本身不可变，所以浅复制列表足以避免列表结构共享；如果文档对象包含可变正文或 metadata，还需要更明确的快照策略。不要把“用了 list”理解成所有嵌套数据都深复制了。

`explain` 返回字典而不只返回一个数，是教学与调试的重要设计。你可以看到每个词的 tf、df、IDF、归一化常数和最终贡献。若分数与手算不一致，逐列比较就能缩小问题范围。只保留最终总分会把多种错误叠在一起，有时两个错误甚至互相抵消，使一个样例看起来正确。

`math.fsum` 对浮点列表求和，帮助减少求和过程的舍入误差；它并不修复错误公式。这里数值很小，普通 sum 通常也足够接近，但区分“公式错”和“浮点末位不同”是重要习惯。测试使用 isclose 而不是把十几位小数字符串写死。容差应足够发现算法错误，不能大到让长度归一化完全失效仍然通过。

`search` 最后返回的是索引位置、分数与解释。真实系统通常应返回稳定文档或片段 ID，而不是列表位置，因为重建顺序可能变化。这个参考为了手算方便保留位置；仓库 `Hit` 则绑定 `Chunk`，并以 chunk_id 破同分。你应理解这两种接口的目的，而不是把示例中的零、一当成生产身份方案。

## 小课九：逐行对照仓库实现的数据流

现在打开 `labs/knowledge/retrieval.py`。构造函数 `self.tf = [Counter(tokenize(c.text)) for c in chunks]` 与上节参考的逻辑相同，区别是使用课程 tokenizer，并接受带身份的 Chunk 对象。一个列表推导式可以展开成三个步骤：遍历每个块，取正文并分词，为词项序列建立 Counter，再把 Counter 加入列表。读不懂推导式时，先在自己的文件里改写为显式 for 循环，行为不应改变。

`self.lengths` 对每个 Counter 的值求和，保留重复词的次数；`self.df` 则遍历 Counter 的键，每篇只计一次。这两行看起来相似，语义却不同。把 `.values()` 放错位置不会总是报错，但会改变统计的对象。你可以为一个全由 cache 重复十次的文档打印两者：长度十，cache 的文档贡献仍然一。

`contributions` 遍历 `sorted(set(tokenize(query)))`。set 去重查询词，sorted 固定遍历顺序。字典结果以词项为键，方便解释。对 f 为零或 avgdl 为零的情况直接 continue，因此没有贡献项与贡献零在这里等价。若你想显示所有查询词，包括未命中的词，应在展示层补零，而不必让核心评分器保存许多无用项。

`search` 对每篇文档的贡献求和，然后交给 `_rank`。后者过滤非正分与非有限值，并使用负分数和 chunk_id 排序。过滤非有限值是一层防护，但不能替代对所有参数和统计状态的正确验证。若你在新增代码中允许 NaN 进入 k1，仅靠过滤可能让检索静默返回空，用户不知道配置错误。因此课程外部接口或扩展实现应尽早拒绝非有限参数，而不是把空结果当成合法答案。

这里还有一个工程取舍：课程每次 `hybrid` 先取当前可见 chunks，再建立 BM25 对象。这样统计只使用当前调用者能见的资料，且更新后自然读到当前版本；代价是重复建索引。生产系统会缓存或维护长期索引，但必须同时解决权限统计、版本失效和并发一致性。不能只复制“预先建一次索引”的优化，却丢掉原本由每次重建提供的正确性保证。

## 小课十：把扫描评分改成倒排评分

扫描版本对每个文档查看所有查询词，便于理解，但大语料中会访问许多不相关文档。倒排版本把每个词映射到包含它的文档与词频。查询时只遍历查询词的 postings，为命中的文档累加分数。它改变的是计算访问顺序，不应改变同一公式的结果。

```python
from collections import defaultdict

class InvertedBM25(ExplainableBM25):
    def __init__(self, documents, k1=1.2, b=0.75):
        super().__init__(documents, k1, b)
        self.postings = defaultdict(dict)
        for index, counts in enumerate(self.tf):
            for term, frequency in counts.items():
                self.postings[term][index] = frequency

    def search(self, query, k=5):
        if type(k) is not int or k < 0:
            raise ValueError("k must be a nonnegative integer")
        if not self.avgdl or k == 0:
            return []
        totals = defaultdict(float)
        for term in sorted(set(query.lower().split())):
            term_idf = self.idf(term)
            for index, frequency in self.postings.get(term, {}).items():
                norm = self.k1 * (1-self.b + self.b*self.lengths[index]/self.avgdl)
                totals[index] += term_idf * frequency * (self.k1+1)/(frequency+norm)
        ranked = sorted(totals.items(), key=lambda pair: (-pair[1], pair[0]))
        return [(index, score, self.explain(query, index))
                for index, score in ranked[:k] if score > 0]

for query in ["cache", "keys", "cache keys", "missing", "cache cache"]:
    scan = ExplainableBM25(texts).search(query)
    inverted = InvertedBM25(texts).search(query)
    assert [r[0] for r in scan] == [r[0] for r in inverted]
    assert all(math.isclose(a[1], b[1]) for a, b in zip(scan, inverted))
```

注意这里把最终解释仍交给 `explain`，这是为了复用展示逻辑，不代表生产查询必须重复计算解释。你可以把解释作为可选调试模式，让正常查询只返回分数和身份。性能优化应当先测瓶颈，再决定是否保存额外中间结果；不要一开始就为了避免几个加法写出难以审查的缓存层。

复杂度也要按实际访问量描述。扫描通常与文档数和查询词数相关；倒排访问的主要数量是查询词 postings 长度之和。如果查询词在所有文档都出现，倒排仍可能接近遍历全部语料，并没有魔法。稀有词更容易缩小候选范围，这也解释了为什么错误码和特定函数名适合词项检索。

若只需要前 k 个结果，可以用堆维护当前候选，避免对大量候选做完整排序。进一步的生产检索会使用更复杂的跳跃和上界剪枝，但你必须先证明被跳过的候选不可能进入当前 top-k。把一些文档随机不算分叫“优化”并不成立。对于学习第一阶段，完整排序更容易核对，等正确性基线稳固以后再优化数据结构。

## 小课十一：新增、删除和更新会影响哪些统计量

增加一篇文档，至少会改变 N、总长度与 avgdl，还可能改变若干词的 df。即使某篇旧文档正文不变，它的分数也可能改变，因为 IDF 和平均长度是语料级统计。这不是缓存错误，而是模型定义的正常结果。若你缓存旧查询分数，却只更新新文档自身，就会混用新旧统计。

删除一篇文档也不只是把它从结果列表中去掉。正确的语料快照应当明确该文档是否还参与 N、df 与 avgdl。有些生产引擎在内部存在删除标记和段合并，统计更新时机可能与物理清理不同；对齐具体引擎时要查看其真实行为。课程参考通过当前可见列表重新构建统计，语义简单且容易验证，但不能因此推断所有生产索引的更新都是立即同样完成。

替换文档时，先减去旧文档对统计的贡献，再加入新文档，看似容易；但失败发生在中间会怎样？如果旧 postings 已删、新 postings 未写，查询会暂时看不到文档；如果新旧同时存在，重复计数会污染 df。你需要事务、不可变快照或其他一致性机制。R08 会进一步解释为什么一个“先删后加”的普通 Python 函数不自动等于原子更新。

最可靠的学习办法是保留全量重建作为 oracle。每次随机新增、删除或修改一条小文档后，用增量实现的统计与全量重建逐项比较。比较 N、每篇长度、总长度、词项 df 和多个查询的分数。只比较最终第一名可能漏掉大量统计错误，因为排名可能暂时没有被改变。

## 小课十二：权限过滤放在哪里，会改变什么

课程 `hybrid` 先调用 `store.visible(ctx)`，再计算 BM25。这意味着一个用户的词频统计只来自他能看见的资料。这样做使教学系统的隐私边界容易理解：不可见资料不仅不出现在结果中，也不参与这次查询的 IDF、向量或上下文构建。代价是不同用户可能对同一公开文档得到不同分数，因为可见语料不同。

如果生产系统使用全局统计再过滤结果，并不意味着它一定错误，但它具有不同的合同。你需要分析全局统计是否允许暴露语料存在信息，过滤时机是否会让 top-k 被私有文档占满，以及用户是否能通过排名变化推断隐藏内容。具体策略取决于服务边界和需求，不能把一个通用性能建议不加分析地搬进多租户系统。

一个简单反例：全局前五名全是当前用户无权访问的私有资料，第六名是公开的正确答案。若先取全局五名再过滤，返回空；若先过滤再排名，公开答案能排第一。这个例子说明后过滤可能伤害召回。你可以扩大候选池缓解，却不能用固定倍数保证所有权限分布下都充分。最小正确性要求仍然是最终结果不得越权。

在课程中，把 tenant、actor 或 group 作为模型可以随意修改的查询参数是错误设计。身份由运行时或服务认证层注入，模型只选择查询文本和允许的检索选项。BM25 本身不懂用户身份；是构建它的上游负责提供正确可见集合。这个职责分离有助于你换检索算法时保留同一授权边界。

## 小课十三：分词规则改变的不是外观，而是整个统计空间

同样的原文，采用不同 tokenizer，会得到不同的词项序列、文档长度、词频和文档频率。中文逐字分词会把“前缀缓存”拆成四个字；词级分词可能把它看成一个或两个词；子词模型又可能采用另一种分段。BM25 公式本身没有告诉你哪种分词最适合当前任务，它只接受前面已经确定的词项。

课程 tokenizer 将英文连续字母数字下划线作为一个词，因此 `max_num_seqs` 会作为一个整体；连字符则会分开相邻片段。这对某些代码标识符有利，对另一些版本字符串可能不够理想。你应该用真实任务中的查询样式建立测试，例如下划线、连字符、大小写、数字点号、路径斜杠和中文夹英文。只测试普通英文句子，会让技术检索中的重要问题一直隐藏。

大小写归一化也是一种选择。把 Cache 与 cache 视为同词通常有帮助，但某些编程语言的标识符大小写具有语义区别。可以同时保留原始字段和归一化字段，或者对自然语言与代码使用不同分析器。不要在没有任务分析的情况下统一调用 lower，然后声称精确匹配完全保留了代码语义。

停用词是另一项容易被过度简化的处理。删除非常常见的功能词可以减少索引和噪声，但否定词、比较词和条件词可能对技术问答至关重要。例如“支持”和“不支持”只差一个字；若把“不”当无意义常用词删掉，词项检索更难区分相反陈述。BM25 本身通过低 IDF 已经降低常见词权重，不意味着你一定要先删除所有高频词。

词干化或词形归一可以把 updates、updated 与 update 联系起来，但也可能把不同含义过度合并。对中文，同义词表、专业词典和缩写扩展也有类似取舍。每增加一条规范化规则，都要保留原始查询和转换后的查询，以便解释为什么某份资料被召回。否则用户搜索某个精确标识符时，系统可能悄悄改写成另一个概念，而你只能看到最终错误排名。

最稳妥的实验顺序是先固定文档与标签，比较 tokenizer，再比较 BM25 参数。若分词、切块、k1、b 和候选数同时改变，即使效果提升，也不知道哪项起作用。一次改变一个机制并记录逐题差异，是建立理解的方法；找到有效组合后，再进行更系统的参数搜索，而不是从一开始随机堆选项。

## 小课十四：词袋模型看不见哪些关系

BM25 通常把文档看成词项计数，忽略大部分词序。因此“系统支持功能甲”与“系统不支持功能甲”可能共享大量词，得到很相近的分数；“A 依赖 B”与“B 依赖 A”也可能有相同词集合。这个限制来自表示本身，不是把 k1 调小就能彻底解决的。你需要额外结构、短语特征、重排器或后续语义验证。

一个简单的短语加分可以检查查询是否作为连续字符串出现在正文中，但它仍不是完整语言理解。空格、标点、词形变化、同义表达和跨句关系都会影响连续匹配。课程 `lexical_rerank` 使用透明的覆盖率与短语加分，明确称为启发式重排，不把它伪装成神经 cross-encoder。学习时应该能够说出它能识别什么、不能识别什么。

字段也很重要。标题中出现某个术语，通常与正文里偶然提及具有不同意义；函数签名、文件路径和说明正文也可能需要不同权重。一个最简单的字段化方案是分别为标题和正文建立 BM25 分数，再按固定权重相加。然而两个字段的长度分布和统计不同，权重不是天然可比的概率。你需要在评测集上检查是否过度奖励标题堆关键词。

```python
def fielded_search(query, titles, bodies, title_weight=2.0, body_weight=1.0):
    if len(titles) != len(bodies):
        raise ValueError("aligned title/body lists required")
    title_index = ExplainableBM25(titles)
    body_index = ExplainableBM25(bodies)
    results = []
    for position in range(len(titles)):
        title_score = sum(x["score"] for x in title_index.explain(query, position).values())
        body_score = sum(x["score"] for x in body_index.explain(query, position).values())
        score = title_weight * title_score + body_weight * body_score
        if score > 0:
            results.append((position, score, title_score, body_score))
    return sorted(results, key=lambda row: (-row[1], row[0]))
```

这个函数是一个明确的教学字段融合方案，不等同于所有名为 BM25F 的实现。它对两个字段分别计算统计，再线性加权。若你阅读一个真正的字段化检索算法，应该核对字段归一化是在词频汇总之前还是之后发生，以及各字段是否共享 IDF。数学运算顺序改变，最终模型也会改变，不能仅凭名字相近就说等价。

对于否定与关系方向问题，你可以把 BM25 当作第一阶段召回：先找到主题相关的候选，再让更强的重排或证据验证检查逻辑。这个分工比要求 BM25 同时完成全部语言推理更合理。与此同时，后续模型也可能错误，因此仍需保留能击穿系统的反例集，而不是把“接了大模型”当成所有词序问题已经解决。

## 小课十五：怎样证明优化版本没有偷偷改变语义

一个有价值的等价性测试不只使用三个固定文档。可以生成许多小词袋语料，比较扫描与倒排版本的文档顺序和分数。生成词表要足够小，使重复词、缺失词和同分经常出现；如果每个文档都由完全不同的随机长字符串组成，测试很可能只覆盖大量零命中情况。

```python
import random

def check_equivalence(seed=13, trials=80):
    rng = random.Random(seed)
    vocabulary = ["a", "b", "c", "d", "e"]
    for _ in range(trials):
        documents = [" ".join(rng.choice(vocabulary) for _ in range(rng.randrange(9)))
                     for _ in range(rng.randrange(1, 9))]
        query = " ".join(rng.choice(vocabulary + ["missing"])
                         for _ in range(rng.randrange(5)))
        k1 = rng.choice([0.2, 1.2, 3.0])
        b = rng.choice([0.0, 0.5, 1.0])
        a = ExplainableBM25(documents, k1, b).search(query, k=20)
        c = InvertedBM25(documents, k1, b).search(query, k=20)
        assert [x[0] for x in a] == [x[0] for x in c]
        assert len(a) == len(c)
        for left, right in zip(a, c):
            assert math.isclose(left[1], right[1], rel_tol=1e-12, abs_tol=1e-12)

check_equivalence()
```

固定 seed 的目的是让失败可重现，不是保证生产服务所有浮点行为确定。这里使用 Python 小规模标准库计算，适合精确追踪。测试失败时，应打印导致失败的语料、查询与参数，而不是只记录第几次 trial。这样你才能把随机发现的故障缩减为一个人能读懂的最小例子。

还需要负向控制：故意把 df 写错，确认测试能发现；故意删除长度项，确认手算样例或专门长度测试失败；故意不去重查询词，确认重复查询测试失败。一个测试在正确代码上通过，只证明没有发现问题；它能击穿你关心的错误实现，才更能说明测试与目标行为有关。

等价性测试也有边界。如果两个实现复制了同一个错误公式，它们可能完美一致。因此要同时保留独立手算 oracle、数学不变量和实现间对照。三者从不同方向提供证据：手算检查公式落地，不变量检查性质，对照检查优化过程。不要把大量随机一致性结果当成所有语义正确性的替代品。

## 小课十六：十二道练习的完整解答

**第一题：区分 tf 与 df。** 在一篇文档里把 cache 重复一百次，对 cache 的 tf 和 df 分别有什么影响？答案：这篇文档中的 tf 增加到一百，语料中包含 cache 的文档数量并不因此增加。文档长度会增加，avgdl 也可能改变。若你只说“分数增加”，没有分开这些统计，就还没抓住题目核心。

**第二题：重算 IDF。** 三篇文档里，某词出现在全部三篇，课程 IDF 是多少？答案是 `ln(1+0.5/3.5)=ln(8/7)`，约零点一三三五，仍然为正。它比只出现在一篇时的约零点九八小很多。不能套用不加一的变体得到负值后说课程实现错了，先核对你正在使用哪条公式。

**第三题：未出现查询词。** 词在任何文档中都没出现，它的 IDF 形式上可能较大，是否会使所有文档获得高分？不会，因为每篇文档的 tf 都为零，贡献为零。IDF 只是在匹配发生时给权重，不会凭空创造匹配。这道题用来防止只看公式某一个因子而忘记完整乘积。

**第四题：查询重复。** 查询从“cache keys”改成“cache cache keys”，课程分数是否改变？不改变，因为查询词先经过 set 去重。完整测试是比较两次每篇文档的贡献字典与总分，而不只是比较第一名。若以后引入查询词频权重，应同时修改文档说明和测试，明确这是一项模型变化。

**第五题：b 为零。** 把 b 设置为零，长度归一化常数变成什么？答案是 k1，与文档长度无关。因此若两篇文档某词词频相同，且使用同一 IDF，该词贡献相同。但不同文档仍可能含有不同数量的其他查询词，最终总分不必相同。这个区别可以避免把局部性质扩大成全局结论。

**第六题：k1 很小。** 对正词频，k1 趋近零时词频因子趋近一；零词频仍为零。这意味着出现次数的重要性被压缩，越来越接近是否出现。请用一点二、零点二、零点零二三个值计算词频一与十的差距。预期差距逐渐缩小，而不是所有分数简单按比例下降。

**第七题：完整手算。** 用本章 d1、d2、d3 和查询 cache keys，答案为 d1 约一点五五七四，d2 约零点五二三五，d3 为零。答题时必须列出 N、df、avgdl、各文档 norm 与每个词贡献。只提交最后三个数，无法判断你是否理解了公式，还是复制了程序输出。

**第八题：空文档。** 语料中加入一篇空文档后，旧文档分数会不会改变？会，因为 N 增加、avgdl 下降，某些 IDF 和长度比例改变。空文档自身不贡献任何词项。是否允许空文档进入索引是摄入策略问题；若选择排除，必须在统计之前排除，并在文档数定义中说明。

**第九题：仅同分排序错误。** 两个实现分数完全相同，却返回不同顺序，是否一定算法错？如果接口要求确定的 ID 破同分，那么其中一个违反接口；若接口未规定同分顺序，可能都合法。课程选择明确稳定顺序，便于测试和重放。不要用随机 seed 代替一个本应确定的 tie-break 规则。

**第十题：权限后过滤。** 全局前五名都不可见，第六名可见，先 top-five 再过滤会返回什么？答案是空；先过滤再排名可以返回第六名。完整解释要指出这是候选截断与授权顺序相互作用，而不是 BM25 公式本身理解权限失败。模型层与数据访问层承担不同职责。

**第十一题：分数能否直接融合。** BM25 第一名得五分，余弦第一名得零点八，是否说明 BM25 更确信？不能。两种分数的尺度和含义不同，直接相加会隐含不受控权重。下一章组会用排名融合或经过验证的分数归一方法处理，不能先把数值大小当概率比较。

**第十二题：优化验收。** 你把扫描版本改成倒排版本，怎样证明没有改变结果？答案包括手算样例一致、多个随机小语料一致、空输入与重复词等边界一致，以及故意错误实现会被测试击穿。还应记录实际运行时间与访问候选数；结果正确不自动说明更快，更快也不自动说明正确。

## 小课十七：三个受控实验，分别观察一个参数

第一个实验研究词频饱和。固定一批长度相同的文档，用无关填充词保持总长度不变，让查询词出现一、二、四、八次。这样 N、avgdl 和每篇 dl 都固定；若查询词出现在每篇里，df 也固定。你看到的分数差异主要来自词频因子。若不做这些控制，重复查询词会同时改变长度，使曲线难以解释。

第二个实验研究长度归一化。每篇文档都只包含一次目标词，但加入不同数量的无关词。分别设置 b 为零、零点五、一。b 为零时，目标词贡献不随文档长度改变；b 大于零时，较长文档通常获得较低贡献。注意每一套语料仍有自己的平均长度，因此你比较的是同一语料中不同文档，而不是随意拿两个不同索引中的分数做绝对比较。

第三个实验研究 IDF。在保持一篇目标文档不变的同时，逐步加入包含或不包含目标词的新文档。两种加入方式对 N 和 df 的影响不同，IDF 变化方向也可能不同。加入不含目标词的文档，会让目标词在更大的语料中相对稀少；加入含目标词的文档，会增加它的普遍程度。这个实验说明分数是相对于语料的量，不是文档自身永久固定的属性。

每个实验都应记录控制变量与变化变量。表格至少包含 N、df、dl、avgdl、k1、b、IDF、词频因子和最终分数。若你只画分数折线，没有这些中间量，读者无法判断曲线是否真的验证了你的解释。对于初学者，十行完整数据比一张看起来专业却缺少条件的图更有价值。

一个重要的反例是“重复整篇文档”。把语料中每条文档都复制一次，N 和各词 df 同时翻倍，平均长度不变。由于公式中还有平滑常数，IDF 不一定逐位保持相同；即使排名常常相近，也不能未经计算就宣称完全不变。你应学会区分直觉上的近似、数学上的严格不变量和有限数据下的实验观察。

## 小课十八：构建解释报告，而不是只打印排序列表

一个可用的解释报告应先显示查询经过了什么处理，再显示语料统计，最后显示每个候选的词项贡献。用户输入“CACHE keys”后，报告应告诉你归一化为 cache 与 keys；若查询词去重，也应显示去重结果。这样当查询意外包含标点或大小写时，你不必靠猜测 tokenizer 的行为。

对每个候选，显示稳定身份、正文摘要、文档长度、匹配词项、每词 tf/df/IDF 与贡献、总分和同分规则。摘要只是便于人阅读，不应参与评分除非你明确选择使用摘要索引。报告中最好保留原文定位，让你发现匹配词是否位于例子、反例、引用或真正结论中。词项命中没有能力区分这些角色，但人可以利用报告定位限制。

```python
import json

def explain_report(index, query, k=3):
    ranked = index.search(query, k)
    return {
        "query": query,
        "query_terms": sorted(set(query.lower().split())),
        "corpus_documents": index.n,
        "average_document_length": index.avgdl,
        "parameters": {"k1": index.k1, "b": index.b},
        "ranking": [
            {"position": position, "score": score,
             "length": index.lengths[position],
             "text": index.documents[position], "terms": details}
            for position, score, details in ranked
        ],
    }

print(json.dumps(explain_report(index, "cache keys"), indent=2))
```

这份 JSON 可以成为实验记录，但不能被直接当作对最终用户的全部回答。开发者需要详细数值，普通用户可能只需要相关段落和清楚来源。把内部解释与产品输出分开，能让系统既可调试又不过度暴露细节。真实服务还要检查报告是否包含用户无权访问的正文或全局统计；调试入口也属于访问控制范围。

当一个候选排名意外上升，沿报告逐项问：是不是查询被拆错？是不是某个稀有词贡献过大？是不是切块变短使长度项降低？是不是新文档改变了 df？是不是字段加权过强？这比一句“BM25 不理解语义”更有帮助，因为很多问题其实来自具体配置或数据状态，能够通过局部修正改善。

## 小课十九：从词项检索进入混合系统时，保留什么

后续加入 dense embedding 后，不要删除词项基线和解释报告。它们能帮助你识别模型召回与关键词召回各自擅长的问题。对于精确错误码，词项检索可能直接命中；对于同义改写，向量检索可能补充候选；对于两者都失败的问题，可能是语料没有答案或问题需要多跳，而不是简单地再增加一种检索器。

混合系统的第一步通常是让不同检索器各自产生候选，再融合，而不是立即把任意分数相加。分数相加需要明确尺度与权重；排名融合则使用名次减少尺度不一致问题，但会丢弃部分原始分数信息。你将会在 R05 完整手算两种思路。当前要保留每个候选来自哪个检索器、各自排名和分数，否则融合后很难解释改善来自哪条路径。

还要防止重复片段投票。如果同一段证据因切块重叠出现多个 ID，词项检索和向量检索都可能返回它们，融合后看起来得到多路支持，实际上只是同一来源的重复。是否按 chunk、段落、文档或独立来源去重，取决于问题与评价目标。这个选择应写进实验，而不是等最终答案重复三遍以后才临时清理。

保留 BM25 也有工程诊断价值。当新 embedding 模型上线后质量下降，词项基线若完全正常，可能帮助你缩小到编码、归一化、索引或模型版本问题；若两条路径同时失败，摄入、权限或资料覆盖更值得先检查。独立基线不是落后的负担，而是让系统变化可解释的一种参照。

## 小课二十：小项目——一份可解释的技术笔记搜索台

项目输入是一个 JSONL 文件，每行包含 id、title、body 和 revision。第一阶段只读取纯文本字段，拒绝重复 id，建立本章扫描版 BM25。提供一个命令行 query 参数，输出前三条命中及每词贡献。为便于复现，固定词法规则与参数，并把它们写进结果元数据。

第二阶段加入倒排版，将同一数据和查询同时交给扫描与倒排两条路径，检查结果一致。不要让两个路径共享最终评分函数，否则独立性会减弱；可以共享已验证的 tokenizer 与数据模型，但分数计算最好各自实现一次，再由手算样例约束。记录每次访问的文档或 postings 数量，说明优化减少的是哪种工作。

第三阶段加入资料更新。最简单的正确版本可以完整重建索引，不必立即做复杂增量结构。更新某篇正文后，再运行旧查询，检查解释报告中的 N、df、长度和版本。保存旧报告，比较哪些候选的分数受到影响。你应该能够解释“没修改的文档为什么分数也变了”，而不是误把它当作随机性。

第四阶段加入一组失败问题：同义词、否定句、关系方向、精确代码标识符、无答案、长文中的短答案。标注哪些是当前词袋表示的固有限制，哪些可以通过 tokenizer、字段或切块改善。这个分类会直接决定下一步应该学向量、重排、多跳还是数据清洗。不要在所有失败下面统一写“换更强模型”。

项目验收物包括一份小语料、十二个问题、手算样例、两种实现、至少六个边界测试、逐题报告以及失败分类。完成以后，你可以把课程 CorpusStore 的可见快照接入搜索台，复用权限与版本语义。此时你已经亲手掌握从数据统计到排名解释的完整链条，后续阅读生产检索器源码就有了可以对照的具体对象。

## 补充案例：一次看似合理却错误的评分缓存

某开发者发现每次查询都重新计算 IDF，于是把 `idf(term)` 的结果缓存在一个全局字典里。第一次在三篇文档上查询 cache，缓存得到约零点四七。随后摄入了十篇全都包含 cache 的新文档，但缓存仍然返回旧值。程序没有异常，候选列表也可能仍然看起来相关，却已经不再实现当前语料定义的 BM25。

错误原因是缓存键只有 term，而函数结果还依赖 N、df 以及统计所对应的权限范围。正确缓存要绑定索引快照或统计版本；若不同用户使用不同可见语料，还要绑定相应范围。你也可以在更新时彻底清空小索引的缓存。关键是先列出函数的全部依赖，再决定缓存键，而不是看到函数参数只有一个词，就以为它是只依赖这个词的纯函数。

同样的问题会出现在预先计算的文档长度归一化常数。某篇旧文档的 dl 没变，但新增文档改变 avgdl，旧 norm 就需要更新或绑定旧快照。若你想避免重算，可以维护不可变索引版本，让一批查询始终使用同一组统计，再在新索引完整准备好后切换。这样换取的是额外内存和版本管理，而不是免费消除依赖。

请设计一个测试：先建立三篇语料并查询，再加入新文档，分别运行全量重建与带缓存版本，比较每个词的 IDF。若只比较第一名，错误可能被掩盖；若比较统计值，则能直接定位缓存失效缺失。修复后，再重复同一个快照上的查询，确认缓存确实可复用。正确性与性能收益都需要证据，不能只完成其中一项。

## 补充案例：查询中的代码符号被吞掉

用户搜索参数 `--max-num-seqs`，普通词法处理可能把它拆成 max、num、seqs。这样能召回自然语言解释，却也可能命中所有分别含这些常见片段的文档。若用户是在查某个精确命令行选项，这种召回可能过宽；如果用户忘了连字符，只写自然语言，则完全精确匹配又可能漏掉答案。

一种清楚的设计是并行建立两类字段：原始标识符字段保留完整参数串，普通文本字段采用词法分词。查询解析器识别明显代码标记后，同时查询两类字段，并在报告中保留各自命中原因。这不是靠随意加大一个词的权重解决问题，而是承认技术标识符与自然语言具有不同结构。小项目可以先用固定规则实现，再用包含下划线、连字符和点号的测试集检查误报与漏报。

最终验收不只是目标文档是否被找到，还包括是否错误命中形似而语义不同的标识符。比如参数名、函数名和日志字段可能共享片段，却属于不同接口。把这些近似反例加入评测，能防止一个只在理想查询上表现良好的搜索台被误认为适合实际代码阅读。

## 源码落实与运行复核

### 源码阅读路线

`BM25.__init__` 中第一步将每个 chunk 词元化，得到一个 Counter。`self.lengths` 对 Counter 的 values 求和，所以词出现两次算两个词元。`self.df` 遍历 Counter 的键，所以每文档每词只算一次。请亲手打印二者，确保能从数据结构看出数学含义。

`contributions` 返回字典而不是立即只返回一个总分，这是调试设计。你可以看到某篇文档是因为哪些词得分，检查意外命中是否由常见词、数字或分词造成。`search` 再对贡献求和，并交给 `_rank`。排序先按负分数，再按 chunk ID，给同分结果一个稳定次序。稳定排序不等于检索更准确，但让回归测试和差异分析更可复现。

未知查询词没有文档词频，因此虽然平滑 IDF 可以算出一个数，最终贡献仍为零。空索引和平均长度为零必须显式处理，否则会出现除零。代码对空材料返回空结果；对负 k 拒绝，而不是让 Python 的负切片产生意外语义。

### 倒排索引与本实验的规模边界

当前实现为了透明，扫描全部文档并逐文档计算贡献。若有百万个片段，扫描成本会变得明显。倒排索引把“词→包含该词的文档与词频”存起来，查询只访问相关词的 posting lists。它改变执行方式，不要求改变评分公式。

一个简单倒排表可以是 `postings[term][doc_id]=tf`。文档长度保存在另一张表，df 等于 posting list 中不同文档数。查询时对出现过查询词的文档累加贡献，再取 top-k。更新与删除时，不仅要修改正文，还要更新 postings、df、总长度与 N。若漏减 df，分数会悄悄漂移，不一定抛异常。

权限也会影响统计口径。本实验先取可见文档，再构建 BM25，因此普通用户与管理员的 N、df、avgdl 可能不同。同一公开文档对两个用户的分数不同是合理的。生产引擎可能用全局统计加受限候选过滤，需要评估是否泄露不应暴露的语料统计以及是否影响排序公平性。

## 完整代码作业：JSONL 搜索台与参数对照

本作业把前面的 ExplainableBM25 变成一个实际可用的小搜索入口。输入文件每行一个对象，包含稳定 id 与 text；输出包含文档 ID、总分与每个词的贡献。解析失败要指出行号，重复 ID 要拒绝，不能用列表位置冒充业务身份。所有数据使用虚构文本，文件位于临时目录，不需要模型或网络。

```python
import json
from pathlib import Path
from tempfile import TemporaryDirectory


def load_jsonl_documents(path):
    records, seen = [], set()
    with Path(path).open(encoding="utf-8") as source:
        for line_number, line in enumerate(source, 1):
            if not line.strip():
                continue
            try:
                row = json.loads(line)
            except json.JSONDecodeError as error:
                raise ValueError(f"invalid JSON on line {line_number}") from error
            if not isinstance(row, dict) or set(row) != {"id", "text"}:
                raise ValueError(f"invalid fields on line {line_number}")
            if not isinstance(row["id"], str) or not row["id"] or not isinstance(row["text"], str):
                raise ValueError(f"invalid values on line {line_number}")
            if row["id"] in seen:
                raise ValueError(f"duplicate id on line {line_number}")
            seen.add(row["id"])
            records.append(row)
    return records


def search_jsonl(path, query, k=3, k1=1.2, b=0.75):
    records = load_jsonl_documents(path)
    scorer = ExplainableBM25([row["text"] for row in records], k1=k1, b=b)
    return [{"id": records[index]["id"], "score": score, "terms": details}
            for index, score, details in scorer.search(query, k)]

with TemporaryDirectory() as directory:
    path = Path(directory) / "notes.jsonl"
    records = [{"id": "cache-guide", "text": "cache cache keys"},
               {"id": "value-guide", "text": "cache values"},
               {"id": "update-guide", "text": "index data updates"}]
    path.write_text("\n".join(json.dumps(row) for row in records) + "\n", encoding="utf-8")
    answer = search_jsonl(path, "cache keys")
    assert [row["id"] for row in answer] == ["cache-guide", "value-guide"]
    assert math.isclose(answer[0]["score"], 1.5574199428240533)
    assert math.isclose(sum(part["score"] for part in answer[0]["terms"].values()), answer[0]["score"])
```

解析函数先验证对象结构，再验证值类型，最后检查重复身份。空行跳过，但错误 JSON 不静默忽略，因为那会让用户以为全部资料已摄入。异常链保留原解析错误供调试，用户层可以只显示安全行号。搜索函数把稳定 ID 与内部索引位置分离，重建文档顺序后仍能正确指认来源。

第一个完整代码题就是把此函数保存到自己的练习模块，增加 argparse 参数 path、query、k1、b、k，输出 JSON。主逻辑已经完整给出，命令行只负责解析与调用，不应该把评分公式再复制一份。验收用三文档金标、未知词、空文件、重复 ID 与坏 JSON 五种输入，分别检查排名、空结果与明确异常。

第二个代码题是倒排等价性。直接运行本章 `check_equivalence`，它用固定随机种子生成语料，对比 ExplainableBM25 与 InvertedBM25 的 ID、分数与顺序。然后故意把 df 改成 tf 总和，测试应失败；恢复后通过。这个故障证明测试能发现实际统计错误，不只是对同一实现重复调用。

第三个代码题是参数控制实验。固定 documents 与 query，只改变 b 为零、零点五、一，记录每篇长度、归一化因子与分数；再固定 b 改 k1。不要同时换 tokenizer 或语料，否则无法归因。下面返回结构化参数表，你可以把它保存成 JSON 或 Markdown。

```python
def parameter_table(documents, query, settings):
    rows = []
    for k1, b in settings:
        model = ExplainableBM25(documents, k1=k1, b=b)
        for index, score, details in model.search(query, len(documents)):
            rows.append({"k1": k1, "b": b, "document": index,
                         "length": model.lengths[index], "score": score,
                         "contributions": details})
    return rows

comparison = parameter_table(["cache", "cache filler filler filler"], "cache",
                             [(1.2, 0.0), (1.2, 1.0)])
zero_b = [row for row in comparison if row["b"] == 0.0]
full_b = [row for row in comparison if row["b"] == 1.0]
assert math.isclose(zero_b[0]["score"], zero_b[1]["score"])
assert full_b[0]["document"] == 0 and full_b[0]["score"] > full_b[1]["score"]
```

b 为零时长度归一化关闭，两篇 tf 相同，所以贡献相同；b 为一时长文归一化因子更大，短文排前。这个断言只证明公式按定义工作，不证明 b 一对真实任务最好。真实超参选择需要独立开发集与测试集，不能拿这两篇专门构造文档当普适结论。

最后提交一份解释报告：某查询为什么第一篇比第二篇高，每个词贡献多少，参数变化影响哪一项，哪种问题词袋模型无法区分。报告应引用你实际运行的 JSON 输出，而不是手写一组没有执行的分数。至此，小项目有完整参考函数、可运行数据与断言，不再只是四阶段任务要求。

### 停用词与稀有词的最后两个反例

停用词表可以减少常见无信息词，但在技术资料里某些短词或否定词非常关键。若把 not、no 或版本前缀删除，两个相反句子可能变成相同词袋。课程基线不依赖复杂停用词表，便于观察统计；引入过滤时应针对任务评测，保留否定与精确标识符反例，不能照搬通用语言列表。

稀有词 IDF 高也不代表它重要。一个随机拼写错误只出现一次，可能得到很高权重；用户查询同样错误时它会排前，但这未必是正确资料。IDF 衡量的是集合中的稀有程度，不是来源权威或事实价值。拼写纠正、字段权重与质量过滤属于额外机制，应分别验证，不能让高分自动变成可信答案。

不同 BM25 变体的 IDF 可能允许负值，而本卷使用带一项的正值形式。看到别的库分数为负，不要立即断言 bug；先查公式与是否进行分数变换。反过来，也不能因为变体存在就忽略实现错误。把同一 N、df 与 tf 代入明确公式手算，才知道差异是否合理。

更新语料后平均长度与文档频率都会变化，即使某篇文档正文没改，它的分数也可能改变。缓存单文档分数而不绑定语料统计版本会出错；缓存分词结果则可在正文与 tokenizer 不变时复用。缓存对象粒度不同，失效条件也不同，这是把公式理解迁移到工程的最后一步。

将这些反例加入 JSONL 搜索台：一条否定、一条拼写错误、一个精确错误码、一次新增长文。保存更新前后解释报告，逐词说明变化来自 IDF、tf 还是长度项。完整答案应引用实际中间量，而不是只写排名变了。

每次改变统计规则都重新运行手算金标与倒排等价测试，确保优化没有悄悄改变评分契约。
