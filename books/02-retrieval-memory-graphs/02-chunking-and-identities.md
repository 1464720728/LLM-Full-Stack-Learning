# R02 切块、字符区间、身份与摄入契约

先修：R01、Python 字符串切片、JSON、哈希的基本用途。你将写出不丢字、不死循环、能够追溯原文的切块器，并解释为什么“每段 500 token”不是一个完整的摄入方案。实验只需 CPU。

## 小课一：同一段文字有多种长度，先确定你在数什么

打开一个文本文件，你看到的是字符；硬盘保存的是字节；模型接口限制的通常是 token；切块器可能按句子或段落工作。这四种单位没有普遍固定的换算比例。把它们都叫“长度”，会让代码在中文、表情、空白或代码段出现时产生难以定位的错误。我们先从最容易观察的 Python 字符串开始。

`len("中文")` 是二，因为 Python 字符串按 Unicode 码点组成；`len("中文".encode("utf-8"))` 是六，因为这两个字符在 UTF-8 中各占三个字节。字符串中的一个视觉符号还可能由多个码点组成，例如某些组合重音和表情序列。因此“用户看到的一个字形”也不总等于 `len` 中的一。课程偏移契约明确采用 Python 字符索引，不声称它是视觉字形索引。

```python
text = "A中文🙂"
print(len(text))
print(len(text.encode("utf-8")))
for index, character in enumerate(text):
    print(index, repr(character), len(character.encode("utf-8")))
```

这段程序会显示四个 Python 字符，总共十一个 UTF-8 字节。A 占一字节，两个汉字各三字节，表情占四字节。若外部服务报告的是字节偏移，你不能直接把它交给 `text[start:end]`；若报告的是模型 token 偏移，也不能直接用来切 Python 字符串。转换必须依据相同原文和相同编码器完成，而且需要处理边界是否落在字符内部。

本课程的词法 tokenizer 又采用另一种单位：英文连续字母数字下划线组成词项，中文逐字成为词项。它用于透明地演示检索，不是某个大模型的 tokenizer。“KV cache”在这里大致有两个词项，不意味着真实模型也一定消耗两个 token。上下文预算若以模型 token 计算，需要使用目标模型对应的编码方式，或依赖供应商给出的实际计数；字符预算只是本地可观察的保守工程约束之一。

从现在开始，变量名也体现单位。使用 `max_chars`、`max_bytes`、`max_tokens`，不要全部写成 `max_length` 却在不同函数里换含义。输出元数据也应写明 offset 的单位和原文版本。这个习惯看似啰嗦，却会在跨 Python、数据库、网络接口和模型服务时减少大量隐蔽错误。

## 小课二：为什么不能直接把整本文档交给模型

如果资料只有两句话，直接放进上下文往往最简单。切块不是必须先做的仪式。它主要解决几类实际约束：文档太长，无法整体放入预算；问题只需要其中一小段，整篇输入会增加无关信息；不同部分权限或版本不同；检索器需要更细的匹配单位；引用需要定位到具体内容。你应先说明自己要解决哪一个问题，再选择切块规则。

切得太粗时，一段相关文字会与大量无关内容共用一个向量或词频统计。检索器可能因为无关部分而降低匹配，模型也需要从噪声中寻找条件。切得太细时，定义、对象、否定词和条件可能分开，单独片段不足以解释意思。不存在一个对所有资料永远最优的固定字符数，切块粒度要结合资料结构、问题类型和下游模型约束评价。

想象原文“在版本二中，只有启用共享前缀时，两个请求才能复用缓存页。”。若第一块只有“在版本二中”，第二块只有“只有启用共享前缀时”，第三块只有“两个请求才能复用缓存页”，任何一块都不完整。最危险的不是完全查不到，而是只取到第三块，回答忽略了版本与启用条件。切块质量应当包含语义条件是否保留，而不只是每块长度是否漂亮。

另一个例子是表格。表头写着“GPU 型号”“显存”“测试精度”，某一行只剩数字。若解析器把表头和行分开，检索到数字也不知道它们对应什么。代码段也类似：函数签名、变量定义和使用处分开以后，短片段可能看起来可执行但缺少上下文。对于结构化资料，保留结构常常比盲目按字数均匀切割更重要。

课程采用字符窗口加适当边界选择，目的在于让你完整理解偏移、覆盖与前进条件。它不是通用文档理解算法。后面讨论标题增强、父子块、句子边界与表格时，你会知道它们分别补哪一类缺口。不要把“使用递归切块器”当成质量已经解决的证据，仍然要实际检查切出的内容。

## 小课三：用左闭右开区间写一个不会含糊的切片合同

设原文为字符串 T，片段由 start、end、text 三项组成。我们要求 `0 <= start < end <= len(T)`，并要求片段正文严格等于 `T[start:end]`。这两个条件让身份和引用可以回到原文核对。左闭右开还有一个方便性质：片段长度恰好等于 end-start，不需要额外加一。

先用纯英文字符避免数错。T 为 `abcdefghij`，窗口四，重叠一。第一片是 `[0,4)`，内容 abcd；下一片从三开始，是 `[3,7)`，内容 defg；第三片从六开始，是 `[6,10)`，内容 ghij。d 和 g 分别出现在相邻两块中，这就是重叠。所有原文位置都至少被覆盖一次，没有位置跳过。

```python
def fixed_windows(text, size, overlap):
    if type(size) is not int or size <= 0:
        raise ValueError("size must be a positive integer")
    if type(overlap) is not int or not 0 <= overlap < size:
        raise ValueError("overlap must be an integer in [0, size)")
    result = []
    start = 0
    while start < len(text):
        end = min(start + size, len(text))
        result.append((start, end, text[start:end]))
        if end == len(text):
            break
        start = end - overlap
    return result

assert fixed_windows("abcdefghij", 4, 1) == [
    (0, 4, "abcd"), (3, 7, "defg"), (6, 10, "ghij")]
assert fixed_windows("", 4, 1) == []
```

逐行看循环的终止逻辑。`end` 先限制到原文长度，防止最后窗口越过末尾。输出片段以后，如果已经覆盖到文末，就立即退出，而不是再制造一个几乎全部重叠的尾片。否则新 start 等于 end 减 overlap。因为 overlap 小于 size，固定窗口至少前进一个字符；这个严格前进条件是防止死循环的核心。

若 overlap 等于 size，第一块结束后 start 会回到原值，程序重复输出同一片段；若 overlap 大于 size，start 甚至可能后退。因此参数约束不只是为了美观，它对应循环是否能终止的证明。不要只测试常见值四和一，还要测试零、负值、相等、布尔值和长度不足一块的文本。Python 的 True 可以作为整数一参与运算，但这里我们明确把它拒绝，因为它不符合用户输入“整数窗口大小”的语义。

本节的固定窗口程序比课程 `chunk_text` 更基础，适合作为独立参考。后者会在窗口后半段寻找换行或句末，尽量减少明显断句。你可以用固定窗口验证覆盖性质，再验证带边界算法是否仍满足同样的不变量。一个更聪明的边界策略若破坏了前进或偏移正确性，就不能算改进。

## 小课四：完整追踪课程边界选择，而不是把它当黑盒

阅读 `text.py` 中 `chunk_text` 时，先找 `lower`。它不是随机常数，而是边界搜索的最早位置。代码把它设置为 start 加上窗口一半与 overlap 加一中的较大者。前半个条件避免只因为很靠前的标点就把块切得过短；后半个条件确保选择边界后，即使减去 overlap，下一轮仍然前进。

候选边界通过 `rfind` 从窗口后部寻找换行、中文句号、英文句点后空格和分号后空格。`rfind` 返回最后一次出现的位置，找不到返回负一。多个候选取最大值，相当于选窗口中更靠后的可用边界。然后 end 设置为 boundary 加一，使主要分隔符被包含在当前片段里。对于长度超过一个字符的分隔串，这不是把整个分隔串都吞进本片，而是课程实现明确选择的字符边界行为。

这段实现为什么使用原文切片而不先 `split` 再拼回？因为 split 和 join 可能改变空白、换行或标点，导致重建文本不再逐字等于原文。若你最终要提供精确引用，保留原文的字符位置有明显好处。你可以为检索建立规范化文本，但应同时保留原文及映射关系，不能把规范化后的坐标冒充原始坐标。

自己选择一个包含两个句号的二十字符字符串，打印每轮 start、预选 end、lower、各个 rfind 结果、最终 end 和下轮 start。不要只看最后返回几块。若你不理解为什么某个句号没有被选中，检查它是不是位于 lower 之前，而不是先修改算法。观察中间值能把“切块效果怪”变成一个具体条件判断。

边界策略仍有局限。英文缩写、数字小数点、代码中的点号和没有标点的长段落，都可能让简单规则失效。解决方式不是声称规则理解了自然语言，而是建立资料类型与预期行为的测试集。对代码可以按语法结构，对表格可以按表头和行，对普通段落可以按句子，再为超长结构添加受限回退。每一种额外规则都应说明何时启用、何时退回基本窗口。

## 小课五：用覆盖矩阵证明没有丢字

只检查每块长度不超过上限，不能证明整个文档都被保留。错误实现可能每隔一段跳过一个字符，所有块长度仍然合法。另一个错误可能把尾部丢掉，也会得到看起来整齐的块。我们需要直接检查每个原文位置被哪些片段覆盖。

```python
def coverage_counts(text, spans):
    counts = [0] * len(text)
    previous_start = -1
    for start, end, piece in spans:
        assert 0 <= start < end <= len(text)
        assert start > previous_start
        assert piece == text[start:end]
        for position in range(start, end):
            counts[position] += 1
        previous_start = start
    return counts

spans = fixed_windows("abcdefghij", 4, 1)
counts = coverage_counts("abcdefghij", spans)
assert counts == [1, 1, 1, 2, 1, 1, 2, 1, 1, 1]
assert all(count >= 1 for count in counts)
```

这里的 counts 长度等于原文长度，每个位置保存覆盖次数。中间的二表示重叠，而不是错误。若出现零，意味着有字符没有进入任何片段；若前进断言失败，说明片段顺序或循环状态有问题。对空字符串，空列表中的 `all` 为真，因此还要按接口约定单独检查空输入返回空片段，这样才不会让空数据遮住逻辑错误。

覆盖检查也能帮助解释重叠成本。固定窗口大小为 w、重叠为 o 时，大部分步骤前进 w-o 个字符。文档很长、边界效应可忽略时，存入索引的总字符量大约被放大为 w/(w-o) 倍。例如窗口四百、重叠一百，放大约为四分之三的倒数，也就是一点三三倍。这个估算不是所有结构切块器的严格公式，但能让你看到重叠并非免费。

重叠还会影响评价。同一句证据出现在三块中，检索器可能返回三个几乎相同的结果，看起来命中很多，实际上只覆盖一个信息点。如果评价按 chunk ID 计数而未区分文档或证据单位，重复块可能被错误地奖励。后面 R05 的去重和 MMR，以及 R06 的上下文打包，会继续处理这个问题。这里先在实验记录中保存“独立证据覆盖”与“返回片段数”的区别。

## 小课六：一个稳定 ID 需要回答哪些问题

文件名不是可靠的唯一身份。不同目录里可能有同名文件，文件可能改名，同一个 URL 内容可能更新，不同租户可能都上传 report.pdf。若用文件名作为全局主键，更新或权限很容易串到另一份资料。通常需要把业务文档身份与内容版本分开：doc_id 表示你认为是同一份长期存在的文档，revision 表示它某次内容和元数据快照。

片段身份还需要绑定它属于哪个版本、从哪里切出、采用什么规则。课程中的 digest 对多个字段先做确定的 JSON 序列化，再计算 SHA-256。确定的序列化很重要：简单字符串拼接可能产生歧义，例如字段对 `("ab","c")` 与 `("a","bc")` 都拼成 abc。带结构的序列化保留字段边界，能避免这种人为碰撞。

哈希不是证明资料真实的签名。任何人都能对错误内容计算哈希；相同哈希最多帮助你识别相同输入或检查数据是否改变。它也不是权限机制，知道 chunk_id 不代表可以读对应内容。系统仍需在查询这个 ID 时验证租户、当前版本和访问许可。否则你只是把可猜的数字 ID 换成难猜的字符串，却没有建立授权边界。

内容哈希也不总适合直接作为业务文档身份。两个不同来源可能包含相同文字，但它们的来源可信度、发布时间和访问权限不同。若你把它们去重成一个没有来源区分的对象，回答可能引用错误出处，甚至把一个租户的数据暴露给另一个租户。可以对相同正文做底层存储去重，但上层来源记录和授权关系仍应独立存在。

课程 fingerprint 包含标题、正文、来源、授权集合、切块参数和 tokenizer 版本。这样正文没变但权限变了，也会产生新版本。你可以选择另一种生产设计，例如内容版本与权限版本分开；但要明确哪些缓存和引用依赖哪一个版本。最糟糕的是没有设计，却在不同组件里各自猜测“只要正文一样就什么都能复用”。

## 小课七：解析、清洗和切块必须有独立的责任边界

从 PDF、网页或办公文档提取正文时，第一阶段是解析：把文件结构转成可处理的内容。第二阶段可能是清洗：去掉重复页眉、规范空白或处理编码。第三阶段才是切块。把这三件事塞进一个没有中间产物的函数，会让你很难定位信息究竟在哪里丢失。第一次接入一种新格式时，应该保存小样本的解析结果与结构标记，并人工比对原文。

清洗不一定越多越好。把所有换行删掉，可能把代码和列表连成一句；把重复文本全部去掉，可能删掉表格中有意义的相同值；把所有标点移除，可能改变负数、小数、版本号和路径。好的清洗规则有明确目的、适用资料类型以及反例测试。不能因为一个正则表达式让文本更“干净”，就假设它保留了语义。

一个实用做法是保留原始文本和规范化文本两份视图。检索使用规范化视图降低格式噪声，引用回到原始视图显示。两份视图之间需要位置映射，或者至少以稳定段落 ID 联系。若规范化涉及删除和合并，单纯加一个固定偏移通常不够。不要在没有映射的情况下，把规范化后的 start/end 写回原始文档，因为后半部分的位置可能全部错位。

对于网页，还需要区分主要内容与导航、广告和评论。用户问页面作者的结论时，评论区的一句反对意见不是同一主体的声明。提取器应保留内容角色和来源位置，而不是把所有可见文字拼成一个没有作者信息的字符串。对于代码仓库，README、注释、测试和实际实现也有不同证据地位；这些差别会影响后续回答的措辞。

首次项目建议先支持 UTF-8 纯文本和明确字段的 JSONL。你可以把复杂格式解析留在独立适配层，但不能在核心切块器里假装已经处理了 PDF 表格和 OCR。等纯文本路径的身份、版本、权限和测试稳定以后，再增加一种真实格式，并保留相同的下游契约。这种分层使新增解析器不会迫使你重写全部检索逻辑。

## 小课八：标题、父子块和相邻块扩展如何改变表示

有时一个小段落只写“默认启用”，离开上级标题就不知道启用什么。给片段添加标题路径，例如“缓存／前缀共享／默认行为”，可以让检索表示获得更多语境。但这段增强文本不是原文连续切片，不能继续声称整个增强字符串都对应原文的 `[start,end)`。正确做法是分别保存原始片段和检索用文本，并标明哪些内容来自结构元数据。

父子块策略把检索单位和送给模型的单位分开。你可以用较短的子块提高匹配定位，命中后返回其较大的父段落，以保留上下文。这不是凭空增加召回，而是在匹配精度与上下文完整性之间做组合。父块仍然受权限和预算限制，不能因为子块可见就假设跨越权限边界的整个父文档都可见。

相邻块扩展是另一种方法：命中块 i 后，额外取 i-1 和 i+1。它适合补回前后条件，但也容易带入无关内容或重复材料。必须使用同一文档版本的邻接关系，不能让当前块与旧版本邻块拼在一起。若切块规则改变，块编号可能完全重排，因此相邻关系不能只靠一个长期不变的序号推断。

比较这些策略时，用同一组问题观察三种量：正确证据是否被召回，完整条件是否进入上下文，最终上下文消耗多少。一个策略可能提高答案完整性，却使上下文翻倍；另一个策略可能节省输入，却让跨段条件丢失。你需要记录这种取舍，而不是用“更智能的切块”作为无法检验的评价。

还有一个常见误解：使用模型判断语义边界就一定更好。模型确实可能识别主题变化，但它也增加调用成本、非确定性和版本依赖。你仍需保存边界结果、模型版本以及可重建的原文偏移。对于大量结构清楚的技术文档，确定的标题和段落规则常常是一个很有竞争力的基线，应该先通过实测再决定是否引入模型。

## 小课九：从一份文档到可重建摄入记录

一份可重建的摄入记录至少需要原始业务身份、来源描述、原文或其可验证定位、内容版本、解析器标识、清洗规则标识、切块参数、tokenizer 标识、访问范围和生成时间。并不是每个字段都必须放进同一张表，但下游必须能回答“这个索引条目是根据哪一份资料、哪一套规则产生的”。如果只能回答“上周跑了一个脚本”，后续调试会很困难。

下面给出一个不依赖数据库的最小构建函数。它把正文切成块，并为整个配置生成指纹。实际仓库中的 CorpusStore 还会负责事务、版本计数和授权，这里只专注理解转换产物。

```python
import hashlib
import json


def stable_hash(value):
    payload = json.dumps(value, ensure_ascii=False, sort_keys=True,
                         separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(payload).hexdigest()


def make_chunks(tenant, doc_id, revision, text, size=8, overlap=2):
    config = {"algorithm": "fixed-window-v1", "size": size,
              "overlap": overlap, "offset_unit": "python-unicode-index"}
    configuration_id = stable_hash(config)
    result = []
    for start, end, piece in fixed_windows(text, size, overlap):
        identity = [tenant, doc_id, revision, configuration_id, start, end, piece]
        result.append({"chunk_id": stable_hash(identity), "tenant": tenant,
                       "doc_id": doc_id, "revision": revision,
                       "start": start, "end": end, "text": piece,
                       "configuration_id": configuration_id})
    return result

first = make_chunks("course", "example", 1, "abcdefghijklmnop")
again = make_chunks("course", "example", 1, "abcdefghijklmnop")
assert first == again
changed = make_chunks("course", "example", 2, "abcdefghijklmnop")
assert {c["chunk_id"] for c in first}.isdisjoint(c["chunk_id"] for c in changed)
```

稳定哈希函数显式排序字典键，保证同样配置不会因为构造字典的先后次序改变序列化结果。身份列表则使用固定字段顺序，每个位置都有明确语义。这里 revision 改变以后，即使文字相同，chunk_id 也改变。这体现了一个选择：引用绑定到某个版本，而不是只绑定到一串文字。生产系统可以采用不同 ID 方案，但必须保留同样明确的版本关系。

不要因为用了 SHA-256 就省略输入验证。空 tenant、错误 revision、非法窗口大小依然是坏输入；哈希会忠实地给坏输入一个看似专业的长字符串。类型和语义检查负责拒绝不合法状态，哈希负责稳定标识合法输入，两者不能互相替代。真正的数据库路径还应把这些构建结果与文档当前版本的更新放入同一事务，避免只写一半。

重试摄入时，完全相同的输入可以复用旧结果，这叫幂等行为。若正文相同但权限、来源或切块参数改变，是否仍算相同请求，要由指纹合同决定。课程把这些字段纳入指纹，因而会产生新版本。理解这个决定后，你就能解释为什么“重复运行同一个摄入命令没有增加版本”和“只修改权限却增加版本”并不矛盾。

## 小课十：三种真实故障的完整定位路径

**故障一：中文引用总是错位。** 先检查存入数据库的 offset 单位，再检查显示层使用什么单位。若解析器给 UTF-8 字节偏移，而 Python 显示层按字符切片，中文前半段以后会越来越偏。最小复现用 `A中文B`，分别打印字节与字符位置。修复是统一单位或保留明确映射，不能随意减去一个“经验偏移”。英文样本全部正常不能证明这个路径正确。

**故障二：某些长文摄入永远不结束。** 打印相邻两轮 start，若不严格增加，就检查 overlap 与边界选择。固定窗口中 overlap 等于 size 会原地循环；带句子边界的实现若选到了 overlap 范围内的过早标点，也可能不前进。修复要建立并断言严格前进，而不是简单给循环加一万次上限。上限可以保护资源，但不能让错误切块被当成成功结果。

**故障三：改了切块参数，旧引用指向不同文本。** 检查 chunk_id 是否仅由 doc_id 和块序号生成。窗口大小改变以后，第零块的内容可能不同，但 ID 没变。缓存和旧回答就会把不同片段误认为同一个对象。修复是在身份或版本中绑定切块配置，重新建立相关索引，并让旧引用明确失效。不要偷偷用新内容覆盖旧 ID 而继续声称引用可追溯。

每个故障都应保留一个最小测试。测试名称说明失效行为，例如 `unicode_offsets_are_character_based`、`boundary_always_advances`、`config_change_invalidates_chunk_identity`。它们不只是防止当前 bug 再次出现，也把系统合同写成可执行说明。以后换成一个第三方切块库时，仍然可以用这些测试判断适配层是否维持了你需要的行为。

## 小课十一：十二道分级练习和答案

**题一：字符与字节。** 计算 `A中文🙂` 的 Python 长度与 UTF-8 字节长度。答案分别是四与十一。逐项展开为一、三、三、四字节，不能用“中文通常三倍”直接乘整个字符串。若换成组合字形，应进一步区分码点数与视觉字符数。

**题二：手算窗口。** 原文十个字符、size 四、overlap 一，写出所有区间。答案是 `[0,4)`、`[3,7)`、`[6,10)`。每块长度四，d 与 g 各重复一次。最后一块已经到文末，立即停止，不再生成 `[9,10)`。这个停止规则避免一个几乎完全重复的额外尾片。

**题三：零重叠。** 同样原文，size 四、overlap 零。答案 `[0,4)`、`[4,8)`、`[8,10)`。最后一块长度二是正常尾块，不应丢弃，也不应伪造两个字符把它补满。索引和引用只能保存真实原文，padding 若用于模型计算，应在另一个层面明确标记。

**题四：非法参数。** size 为零、overlap 为负、overlap 等于 size、size 为 True 应怎样处理？本节参考合同全部抛 ValueError。关键不是错误类型名字，而是必须在进入循环前拒绝，不能输出部分片段后才失败，也不能依赖最终超时才发现参数错。

**题五：覆盖而非拼接。** 为什么有重叠时不能直接断言所有片段拼起来等于原文？因为重叠文字被重复拼入。正确答案是检查每块精确切片、start 严格前进和每个原文位置至少覆盖一次。若要重建原文，应根据偏移合并覆盖区间，而不是盲目 join。

**题六：规范化偏移。** 原文 `A  B` 中有两个空格，规范化成 `A B`。规范化文本中 B 的位置是二，原文中是三。答案说明删除空白改变了后续坐标，因此必须保存映射或将引用绑定到原始段落。一个固定全局偏移不能处理多处不规则清洗。

**题七：身份拼接歧义。** 为什么 `hash(a+b)` 不能安全表达两个独立字段？完整反例是 `a="ab",b="c"` 与 `a="a",b="bc"` 得到相同拼接文本。使用带字段边界的结构序列化再哈希。这里讨论的是输入编码歧义，不是破解哈希函数。

**题八：相同正文不同来源。** 两个文档文字相同但权限不同，能否只保留一个授权记录？不能。可以设计底层内容去重，但每个来源身份、租户和授权关系仍需独立。否则一方公开的内容状态可能错误影响另一方私有资料的访问策略或引用出处。

**题九：配置改变。** 把 size 从八改成六，为什么需要使相关索引或片段版本失效？因为边界、词频、向量输入和引用偏移都可能改变。只重算向量而保留旧 chunk 身份，会让多个组件对同一 ID 持有不同文本。应将配置变化纳入版本迁移，并重新验证引用。

**题十：标题增强。** 给正文前拼上章节标题后，能否仍说整个字符串是原文的连续切片？不能。应保留 `source_text` 与 `retrieval_text` 两个字段，前者用于精确引用，后者可以含标题路径。回答显示时分别标明标题元数据与引文，不把拼接内容伪装成原文连续句子。

**题十一：父子块权限。** 子块可见是否意味着整个父文档都可见？不一定。若父文档内部有独立权限区段，扩展必须再次过滤。最小反例是一份合并报告里第一节公开、第二节私有；命中第一节不能自动把第二节一起送给模型。

**题十二：重试与更新。** 完全相同输入重试应复用还是新增版本？课程选择复用；只修改授权集合应新增还是复用？课程选择新增，因为授权进入指纹。答案应说明这是明确设计合同，而不是所有系统的唯一合法选择。不同设计只要保持身份、缓存、引用与权限一致，也可以成立。

## 补充实验：删除一个字符后，为什么后面的块会一起改变

取原文 `甲乙丙丁戊己庚辛壬癸`，使用四字符窗口和一字符重叠。现在在开头删除甲，再运行相同算法。虽然剩余九个字符各自没有被改写，它们在原文中的位置整体移动，窗口分组也随之改变。一个仅按“第几个块”命名的系统会把旧第零块和新第零块混为一谈；一个绑定内容、配置和版本的系统会明确区分它们。

这也解释了为什么增量摄入不是简单地找出“变动的几个字”就能结束。编辑可能改变段落边界、标题范围、后续偏移和重叠关系。实际系统可以使用结构化段落身份、内容定义切块或更细的依赖信息减少重算，但这些优化需要证明保留了正确的来源映射。初学阶段先完整重建小文档，再与增量实现比较，是更可靠的验证顺序。

请把编辑前后的所有区间列成两列，并写出每一对内容是否相同、身份是否相同、旧引用是否仍可用于当前回答。参考判断是：即使某段文字碰巧相同，它也属于不同的文档快照；系统可以复用底层计算结果，却不能因此跳过当前权限和版本检查。计算复用与证据有效性是两个责任。

再做反向操作：删除文档后重新用相同 doc_id 摄入完全相同正文。课程存储层使用持久版本计数避免版本号回到一，因此旧 chunk_id 不会复活。这个问题会在 R08 用事务和 ABA 例子完整展开。本章先通过这个具体操作理解稳定身份的目标：可重复构建相同快照，同时避免不同生命周期被误认成同一个快照。

实验记录最后还要写明哪些观察来自实际运行，哪些只是预期。比如“参数改变后应重建索引”是设计要求；只有实际比较身份集合、检查查询结果和验证旧引用以后，才能记录这次迁移通过。把要求与证据分开，能避免代码尚未实现却在报告中提前写成成功。

### 摄入并不只是“读文件再 embed”

摄入包括解析、标准化、结构识别、身份分配、切块、元数据验证、访问权限、索引生成、发布。每一步都可能失败。PDF 解析可能把两列交错；表格可能丢列标题；OCR 可能把 0 识别成 O；HTML 可能带菜单、脚注或恶意文字。向量模型能正常返回数值，不表示原文解析正确。

本卷采用纯文本固定输入，避开复杂文件格式并明确保留这层边界。要添加 PDF，应先做“原页—抽取文本—切块”抽样检查，再做检索。解析器版本也应进入摄入指纹，否则换了解析算法却复用旧向量，系统会误认为内容未变化。

`ingest` 先生成所有 Span，再开启数据库写事务。这样切块参数错误不会产生半份文档。指纹包括正文、标题、来源、权限、切块参数和 tokenizer 版本。重试同一输入返回原 revision，改变权限也会生成新 revision。这比“只看正文哈希”的幂等设计更完整。

## 综合工作坊：结构切块也必须保持原文坐标

固定窗口容易实现，但真实 Markdown 有标题、段落与代码块。结构切块的目标不是看到空行就任意拼接，而是让片段保留完整语义单位，同时仍能回到原文精确区间。若先 strip 每段再拼接，前后空白改变，原 offset 就不再成立。一个可靠基线先识别区间，再用原文切片生成内容，不重新构造所谓原文。

下面实现按空行识别段落的教学扫描器。它不解析完整 Markdown，也不理解代码围栏，只说明“结构边界与精确坐标”怎样连接。遇到超长段落仍需要固定窗口回退，后续可以加入标题与代码块状态。不要把这个小函数称为生产文档解析器。

```python
from dataclasses import dataclass
import re

@dataclass(frozen=True)
class ParagraphSpan:
    start: int
    end: int
    text: str


def paragraph_spans(text):
    spans = []
    start = 0
    for boundary in re.finditer(r"\n[ \t]*\n", text):
        end = boundary.start()
        if end > start:
            spans.append(ParagraphSpan(start, end, text[start:end]))
        start = boundary.end()
    if start < len(text):
        spans.append(ParagraphSpan(start, len(text), text[start:]))
    return spans

sample = "  第一段。\n仍是第一段。\n\n第二段含🙂。\n\n最后一段"
paragraphs = paragraph_spans(sample)
assert len(paragraphs) == 3
assert all(sample[span.start:span.end] == span.text for span in paragraphs)
assert paragraphs[0].text.startswith("  ")
```

扫描器把空行分隔符排除在段落正文之外，因此段落集合不覆盖所有字符；这不是 bug，而是明确选择。若应用要求全文字符无遗漏，就需要把分隔符归入相邻块或保留单独结构记录。固定窗口的“每个字符至少覆盖一次”与段落提取的“每段精确可定位”是不同契约，不能把一个测试原样套到所有切块器。

第一段前面两个空格被保留，说明没有 strip 改动原文。emoji 的 Python 字符坐标与 UTF8 字节坐标不同，source[start:end] 只在同一个 Python 字符串坐标系内成立。若下游读取原文件字节，需要显式转换或保存字节偏移，不能把字符 offset 直接用于 seek。

### 结构与长度同时受限时的完整决策

假设段落长度分别八十、一百、四百，目标最大一百八十。前两段连同分隔符可能超过一百八十，不能只加正文长度；第三段单独超长，需要回退切分。决定是否合并时应计算最终实际片段区间长度，而不是去掉分隔符后的文本长度。合并为原文连续区间，引用仍能精确回查。

如果在每个片段前加标题路径，搜索文本与来源文本已经不同。可以保存 source_span 与 search_text 两个字段：前者精确原文，后者用于检索增强。生成引用时回到 source_span，不能把人工补的标题当原文引用。标题也有版本依赖，文档结构变化后搜索文本与索引需要更新。

代码块尤其需要谨慎。空行可能出现在函数内部，按段落拆会截断上下文；长代码块也可能超过预算，需要按函数或行窗口切，但保存语言与起止行。解析器应有状态区分普通段落与围栏，异常未闭合围栏要明确处理。不要通过删掉所有代码块来避免难题，因为用户学习代码时恰好需要这些内容。

### Unicode 与换行的回归矩阵

为切块器准备中文、英文、emoji、组合字符、Windows 换行、连续空行、无空白长串与末尾换行八类输入。测试每个片段边界合法、文本等于源切片、循环终止、最大长度符合契约、重叠不导致倒退。某些输入允许不覆盖分隔符，必须在测试中明确，不把所有差异都当错误。

组合字符例如一个字母加组合重音，在 Python 中可能是两个码点，却在人眼中显示一个字符。按码点切可能把它们分开。课程固定窗口没有完整字素簇处理，应诚实说明。若产品需要用户可见字符边界，可以使用专门 Unicode 分割库并固定版本，但仍保留源坐标映射。用户看到的一个字与程序 len 一不是天然等价。

Windows 的回车换行是两个字符。若解析阶段统一成换行，之后 offset 属于规范化文本，不再直接对应原始字节。保存规范化版本与原文映射，或明确引用展示的是规范化文本。最危险的是一边改变文本，一边继续使用旧偏移而不记录坐标系。

### 身份稳定性与内容去重的不同实验

相同文档版本、相同区间与文本应生成相同 chunk ID，重试不制造重复对象；正文改动或版本改变应生成不同身份，旧引用不能复活。内容哈希可以让相同文本共享底层存储，但业务身份仍需包含来源与代际。两份不同文档写同一句话，不意味着引用可以互换，来源可信度与权限可能不同。

构造两个租户、同 doc_id、同正文，要求 chunk ID 不同；同租户不同 doc_id 同正文，也应不同；同逻辑文档 purge 后重建同正文，版本递增使 ID 不同。这个矩阵直接检验哈希输入是否覆盖身份边界。不要只测试正文改一个字哈希不同，那是最容易的一种情况。

再测试配置改变。max_chars、overlap、tokenizer 或解析规则变化可能改变片段集合与检索统计，应体现在摄入指纹或构建代际中。配置字符串应规范序列化，不能简单拼接导致歧义。版本信息不是装饰，它是判断缓存、向量、图边与引用是否仍匹配的依据。

### 完整练习答案如何自查

如果你的结构切块实现声称精确引用，任选一个片段，用保存的 start/end 从保存的源版本重新切片，必须逐字符相等。若声称全文覆盖，生成 coverage 数组检查每个位置至少一次；若允许结构分隔符不覆盖，列出允许缺口类型。若声称稳定身份，重跑与重启后比较 ID；若声称增量更新，插入文首一字观察哪些窗口变化并解释原因。

这些测试相互独立，全部通过才说明你宣称的契约成立。片段看起来合理不证明 offset 正确，ID 稳定不证明权限正确，覆盖完整不证明语义边界好。把每个性质单独检查，才能在后续换解析器或切块策略时知道究竟改善了什么、损失了什么。

如果引入模型 tokenizer，记录具体 tokenizer 身份与输入模板，先编码整段再设计 token 窗口，并保存 token 区间到原文字节或字符的映射。不同 tokenizer 对中文、代码与 emoji 的拆分不同，不能用字符数乘一个固定常数当精确预算。字符窗口仍可作为简单基线，但报告必须使用正确名称。

切块策略的最终选择要在任务标签上比较：关键条件是否与主句同块、相关来源召回是否改善、重复内容是否增加、引用是否完整。单纯让所有块长度接近目标值，不证明它们适合回答问题。
