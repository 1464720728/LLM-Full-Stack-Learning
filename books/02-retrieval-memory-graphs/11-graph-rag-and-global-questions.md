# R11 图检索与 GraphRAG：局部证据、全局主题与派生摘要

先修：R10、检索评价、摘要概念。目标是判断什么时候需要图结构，什么时候普通检索足够，并能设计可验证的图增强问答实验。

## 1. “某个答案在哪里”与“整个语料在说什么”

问题“缓存如何更新”往往可以由少量具体段落回答；问题“这个项目最主要的技术风险有哪些”可能需要跨许多文档归纳。普通 top-k 检索偏向与查询词最接近的局部材料，不一定覆盖整个语料的主题分布。

图结构可以把实体、关系、文档和社区组织起来，帮助进行局部扩展或全局摘要。Microsoft 的 GraphRAG 项目与论文特别关注从实体关系图生成社区层级与摘要，再服务局部或全局查询。这个具体方法比“用了知识图谱的 RAG”更有专门含义；课程的 BFS 证据图没有实现其社区检测和全部查询策略，不能混称为等价实现。

全局问题并不意味着图一定最好。分层文档摘要、主题聚类、地图—归约式摘要或结构化元数据聚合也可能合适。应先定义问题类型、证据覆盖与计算预算，再决定是否承担图抽取、消歧和维护成本。

## 2. 局部图扩展怎样与文本检索协作

一种透明流程是：文本检索找到种子片段；从片段识别实体；在允许关系和预算内扩展邻居；取回每条边的原始证据；去重后交给回答器。图主要帮助找相关但不一定词面相似的材料，最终仍需要原文支持陈述。

例如用户问“某 Agent 的数据更新依赖什么”。文本检索先找到 Agent，图扩展找到 retrieval、index、corpus，再读取它们的更新策略。路径可以告诉系统下一步去哪找，但不能仅凭 uses 链推出所有更新规则都适用于 Agent。

扩展半径越大，覆盖通常越广，但噪声与成本也可能增加。高连接度节点如“系统”“模型”会把几乎所有东西连接起来，应考虑实体类型、边类型、来源强度和业务范围。图密度大不是质量高的证明。

## 3. 社区与摘要需要两套来源

一个社区是图算法按某种结构目标划分的节点集合，不必等于业务主题。算法可能按连接强度聚类，结果受抽取误差、高度节点和参数影响。不能把社区名称当成自动发现的客观真理。

对社区生成摘要时，至少记录两种 provenance：摘要来自哪些节点/边/片段，以及它采用哪个摘要模型、提示词和版本。如果底层边变化，知道依赖才能重新生成受影响摘要。如果摘要生成规则变化，则所有同规则摘要可能需要重建或标记混用状态。

摘要可以丢信息。某社区里有十份材料支持某结论、一份明确提出例外，摘要若只保留多数意见，会改变事实范围。全局回答要特别保留争议、时间范围、缺失覆盖和来源分布，不应该把流畅综合当成全面代表。

## 4. 设计一个不用 GPU 的全局实验

准备 12 份虚构资料，按缓存、调度、Agent 三类主题各四份。每类包含一条主要结论、一条例外和一份重复材料。先使用普通 top-k 检索回答“主要风险和例外是什么”，再做按主题分层摘要，最后用手工确认的关系图辅助扩展。

为答案定义覆盖清单，而不是一个参考段落：是否提到三类风险；是否保留每类例外；是否错误计算重复文档为独立来源；是否引用了对应原文；是否添加不存在的风险。这样可以看出方法改善的是覆盖还是仅仅答案长度。

这个实验可以先用人工摘要或固定抽取结果，验证组织结构，不必马上调用几十次模型。接入模型后再测抽取错误与摘要错误如何影响最终回答。GPU 不应成为理解这种系统的前置门槛，API 足以开展小规模实验。

## 5. 图上的权限不是删掉几个节点那么简单

节点可以由多个来源共同证明。一个实体名公开，但某条关系私有；某条关系公开，另一条关系仅组内可见。若将权限简单挂在节点上，可能过度隐藏公开知识或意外公开私有关系。因此 provenance 与权限经常需要到断言或边层级。

社区摘要还可能混入不同权限范围的事实。生成后若把它当成普通公开文档，会泄露原本受限的内容。安全方案可以在授权范围内生成不同摘要，或为摘要记录依赖集合并在读取时验证全部依赖授权。只过滤摘要标题不够。

本卷图查询永远以 Context 为入口，取当前可见来源支持的边。虽然简单，但这个入口契约应保留到真实图数据库。若后续换 Neo4j 或另一图引擎，不能因为数据库已有用户账户就默认业务租户隔离自动完成。

## 6. 评价图的每一层

实体抽取可以测实体识别的准确与召回；实体链接可以测同名消歧；关系抽取测 subject/predicate/object 与证据是否正确；路径检索测目标路径或支持集是否被找回；摘要测事实覆盖与支持；最终问答再测任务成功。只测最终一个平均分，很难知道该修哪一层。

如果关系抽取 precision 不高，扩大图可能放大错误传播。若正确路径存在但检索不到，是遍历策略或预算问题；若路径找到了却答案过度推断，是生成和规则问题。组件级指标帮助定位，但最终仍应回到用户任务，而不能只追求漂亮图统计。

部署成本也要拆开。离线抽取可能昂贵但可复用；日常更新小量文档时，是否要重建整张图；社区变化会波及多少摘要；在线查询是否需要多次模型汇总。把所有费用平均到一个 query 之前，要明确更新频率与使用频率。

## 7. 练习与完整参考答案

**练习 1：选择方法。** “错误码 E123 的含义”优先精确词法检索；“模块 A 依赖哪些组件”适合结构化图关系加原文；“全部项目会议的共同风险”可能需要全局聚合。参考答案必须包含为何另一方法不一定划算，而不是把 GraphRAG 当万能升级。

**练习 2：实现有证据的邻居扩展。** 完整参考函数：

```python
def expand_once(graph, context, seeds, allowed_predicates, max_edges=20):
    if max_edges < 0:
        raise ValueError("nonnegative budget")
    selected = []
    seed_set = set(seeds)
    for edge in graph.visible_edges(context):
        if edge.subject in seed_set and edge.predicate in allowed_predicates:
            selected.append(edge)
    return sorted(selected, key=lambda edge: edge.edge_id)[:max_edges]
```

它不跨越权限，不自动断言传递关系；多个扩展轮次还需要全局 visited 和总预算。

**练习 3：社区摘要失效。** 摘要 S 依赖 chunk a,b,c，b 被撤权。参考处理：S 不再能原样对该调用者显示；重新在可见集合生成，或拒绝使用该摘要。不能只从引用列表删掉 b 而保留由 b 推出的正文。

**练习 4：重复来源。** 三篇转载同一公告是否算三票证据？不应。参考记录 original_source_id，将转载视为传播路径而非独立验证。若确实是不同独立实测，才可作为多个观测来源。

**练习 5：设计图消融。** 比较 text-only、text+1hop、text+2hop、text+community 四种，固定语料和模型。记录证据覆盖、错误关系使用率、延迟和更新成本。参考结论可以是某些类型提升而精确查找无收益；需要按问题类型报告，不能只给全局平均。

**掌握门槛：** 能说明自己的系统实现了哪种“GraphRAG”，明确图的来源和摘要依赖，能证明权限与更新传播正确。进一步研读 [GraphRAG 论文](https://arxiv.org/abs/2404.16130) 与 [项目文档](https://microsoft.github.io/graphrag/)；阅读时分别标注离线索引、在线查询和维护步骤。
