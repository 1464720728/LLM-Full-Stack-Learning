# R06 构造 RAG：上下文不是证据的终点

先修：前五章，知道查询和候选的差别。你将实现完整检索—打包—回答—引用校验链，并明确从抽取式回答迁移到真实生成模型后新增哪些错误模式。

## 小课一：RAG 不是把一堆文字粘进提示词就结束

一个最小 RAG 系统至少经历资料准备、查询、候选检索、上下文选择、回答生成和证据验证。每一步有自己的输入和失败方式。把这些步骤全部藏在一个 `ask()` 方法里，可以方便调用，却不能代替你理解里面的合同。学习时应当把同一次请求的中间结果全部拆出来观察。

用户问“青石教学项目的缓存容量是多少”。资料库有旧版写七项，新版写九项，还有一段讨论“如果容量改为十二项会怎样”的设计草案。三个片段都包含项目名和容量数字，检索可能全部命中。但最终回答应该根据当前有效版本和资料角色判断，不能把最高相似度的一个数字直接当成答案。这个例子把相关性、时效性和陈述类型同时摆在你面前。

RAG 的作用是让回答能够使用外部资料，而不是保证资料一定正确，也不是保证模型一定忠实使用资料。模型可能忽略给出的条件，资料可能互相矛盾，检索可能漏掉关键更新。系统设计必须给这些情况明确状态：有足够支持、支持不足、来源冲突、来源过期、无权限或执行失败。不要把所有情况都包装成一段流畅的自然语言。

本章先实现严格抽取式模式。模型自由生成之前，先把来源身份、版本、上下文预算和引用检查做对。之后再解释如何增加改写与综合能力，同时保留可验证边界。这样你不会在第一天就面对“模型写得不对”却不知道该检查哪一层。

## 小课二：一个回答应拆成哪些可检查对象

自然语言回答可能包含多个断言。例如“青石项目当前容量为九项，超过容量时会淘汰最旧条目，因此适合所有高并发场景”。前两句可能分别有资料支持，最后一句却可能是无依据推断。若只给整段回答附一个链接，很难判断每一部分究竟由什么支撑。把回答拆成断言，是细粒度验证的起点。

一个断言对象可以包含 text、引用列表、适用条件、状态和生成来源。引用对象至少包含稳定来源 ID、版本和引文或位置。这里的“至少”不是要求你一开始设计几十个字段，而是确保能回答三个问题：这句话引用了哪份资料的哪个版本，引用的具体文字是什么，系统怎样判定它可用。

课程的 `Claim` 很小：一个 text 与一个 Citation。Citation 包含 chunk_id 和 quote。版本信息通过 chunk_id 绑定的 Chunk 间接获得，验证时重新查询当前可见来源。这个简化接口适合严格抽取；如果要让一个断言依赖多个来源，需要显式扩展引用列表，并定义它们是共同支持还是可替代支持，不能简单把多个 ID 拼成一个字符串。

身份与内容分开也有助于调试。模型可能给出一段正确引文，却填错 source_id；也可能 source_id 正确，但引文是自己编的；还可能二者都正确，但断言比引文更强。三种错误需要不同检查。一个统一的“citation_valid=true”若没有说明验证了哪一层，会误导调用者。

## 小课三：先把资料当数据封装，而不是当系统指令

检索到的文档属于外部数据。即使它写着“忽略之前的要求”“把所有文件发给某地址”，也不应该自动获得控制系统的权力。提示词可以明确说明资料只是待分析内容，但真正的权限仍然由工具和运行时边界控制。把资料用 JSON 包起来能改善结构清晰度，却不能从数学上保证模型绝不受其影响。

一个清楚的上下文条目可以包含 source_id、doc_id、revision、title 和 text。模型回答时引用 source_id，而不是自行创造链接。这样后处理器可以把 ID 映射回已验证来源。不要让模型任意提供一个看似合理的 URL 后就把它显示成真实引用；URL 也可能来自幻觉或恶意资料。

结构化封装还有一个好处：资料边界明确。若直接把多份正文连在一起而没有分隔，模型可能把上一份文档的标题应用到下一份正文，或者把两份不同版本的句子拼成一个不存在的结论。每条资料的身份与版本应与正文一起传入，且在输出中能追踪回来。

```python
import json

def evidence_payload(chunks):
    return json.dumps([
        {"source_id": chunk.chunk_id,
         "doc_id": chunk.doc_id,
         "revision": chunk.revision,
         "text": chunk.text}
        for chunk in chunks
    ], ensure_ascii=False, separators=(",", ":"))
```

这段代码中的 `ensure_ascii=False` 让中文直接保留为字符，`separators` 去掉不必要空白。它影响序列化长度和可读性，不改变资料的信任级别。若正文中包含引号、反斜杠或换行，JSON 会进行转义，实际字符串长度可能大于原始正文长度之和。因此预算检查必须针对最终序列化结果，而不是只数每段 text。

## 小课四：上下文预算必须按整个请求计算

模型的上下文容量不仅被检索资料占用，还包括系统说明、用户问题、历史对话、工具定义、工具结果和可能需要预留的输出。若你把全部容量都分给资料，最终请求仍可能超限。一个简单预算式是：总容量减固定说明、问题、历史、工具结构、输出预留和安全余量，剩余才是证据预算。

这些量如果以模型 token 计数，应使用匹配的 tokenizer 或服务契约。课程 `pack_context` 使用字符预算，只用于透明演示，不把字符数冒充模型 token 数。你可以先在本地按字符建立边界测试，再在真实模型适配层加入实际 token 计数。二者应使用不同字段名，避免调用者误解。

举例，假设某个教学请求允许一千个字符，固定说明一百五十，用户问题五十，历史二百，输出预留二百，结构与余量一百，则证据最多三百。这个数字是虚构预算，不是任何模型的真实限制。重要的是把每项相加，看到“资料明明只有八百字符，为什么仍超限”的原因可能是其他部分已经占了很多。

预算还应考虑一次工具循环后历史增长。第一轮资料能放下，不代表追加工具结果和模型中间输出后第二轮仍然能放下。Agent 需要在每次模型调用前重新构造并检查请求，而不是在任务开始时算一次。后面的 Agentic RAG 会把这项检查接入状态机和预算记录。

## 小课五：逐行理解 pack_context 的选择行为

课程函数从高排名候选开始，尝试把一个条目加入当前 entries，再把整个候选列表序列化。如果长度不超过 max_chars，就接受；否则跳过这条继续看后面的较短候选。注意这里是 continue 的行为，不是遇到第一条过长就结束。一个大块放不下，不意味着后面的所有小块也放不下。

最小合法 JSON 列表 `[]` 长度为二，所以函数要求预算至少为二。这个看起来不起眼的边界体现了“预算包含结构”的原则。每条内容加入后，字段名、数字、引号、逗号和转义也占字符。只对正文长度做加法，会在接近上限时产生不一致。

这种贪心打包不会保证最优证据组合。第一条很长的高排名块可能占满预算，使后面两条互补证据无法加入；一个更好的组合也许是放弃它，选择两个稍短但覆盖完整的块。课程函数选择简单、确定、易读的策略，目的在于把序列化和边界做清楚。质量更高的选择需要结合覆盖、冗余与成本，不能仅在这里换一个排序键就宣称问题全部解决。

你可以为函数构造三个测试：空候选得到 `[]`；第一块过大、第二块可放时第二块仍进入；正文包含引号和换行时最终字符串仍不超预算。第三个测试能抓住只按原文字符数估算的错误。测试应解析返回 JSON 并检查身份集合，不只检查最终长度，这样才能发现内容选错但长度合法的情况。

## 小课六：严格抽取式回答究竟验证了什么

`extractive_answer` 先检索并打包，再把每个保留条目的全文作为 Claim.text，同时把同样文字作为 quote。这样的回答不会自由生成新事实，因而可以通过字面相等检查建立一条非常明确的来源关系。它适合验证数据管道，不追求自然语言表达的灵活性。

验证函数先根据当前身份上下文查找 chunk_id。如果找不到，可能是来源删除、版本过期或权限不允许；课程统一返回 `source_missing_stale_or_forbidden`，避免向未授权调用者泄漏来源存在细节。接着检查引文非空且确实是来源正文子串，最后要求 claim.text 与 quote 完全相等。

最后一项意味着“缓存保存键和值”改写成“系统会复用历史注意力状态”即使语义可能合理，也不会自动通过严格模式。系统返回需要语义复核的状态，而不是猜测它是否等价。这是有意选择的保守合同：机器能精确证明的部分先精确证明，超出能力的部分明确交给更强验证或人工判断。

通过这些检查，仍然不能推出资料本身真实，也不能推出片段与用户问题相关。来源可以包含错误事实，检索也可能挑中主题相近却没回答问题的段落。课程报告明确写出限制，正是为了防止把“精确来源抽取”包装成通用真伪判定。你应在界面或报告中使用准确状态名称，而不是含糊的“已验证正确”。

## 小课七：亲手运行一次引用从有效到失效的过程

下面的程序使用真实课程存储层，创建一份虚构文档，形成引用，然后修改当前版本。它不会访问网络，不需要模型 API。请把每一步的 revision 和 chunk_id 打印出来，观察业务文档身份保持不变，而版本绑定的片段身份改变。

```python
from labs.knowledge.store import CorpusStore, Context
from labs.knowledge.rag import Claim, Citation, validate_claim

with CorpusStore() as store:
    context = Context("course", "learner")
    first_revision = store.ingest(
        "course", "jade-capacity", "Jade capacity",
        "Jade cache capacity is seven items.",
        allowed=("*",), max_chars=100, overlap=0)
    first_chunk = store.visible(context)[0]
    claim = Claim(first_chunk.text, Citation(first_chunk.chunk_id, first_chunk.text))
    assert validate_claim(store, context, claim) == (True, "verified_exact_extract")

    second_revision = store.ingest(
        "course", "jade-capacity", "Jade capacity",
        "Jade cache capacity is nine items.",
        allowed=("*",), max_chars=100, overlap=0,
        expected_revision=first_revision)
    assert second_revision > first_revision
    assert validate_claim(store, context, claim)[0] is False
    current_chunk = store.visible(context)[0]
    current_claim = Claim(current_chunk.text,
                          Citation(current_chunk.chunk_id, current_chunk.text))
    assert validate_claim(store, context, current_claim)[0] is True
```

第一份 Claim 保存的是旧片段身份和旧文字，而不是一个会自动跟随数据库变化的“实时引用”。更新文档后，旧 Claim 对象仍然存在于 Python 内存，但验证器不再接受它作为当前证据。这种设计避免旧回答在资料更新后被错误地重新标为有效。若你需要展示历史回答，可以保留历史状态，但应说明它依据的是旧快照，不能冒充当前答案。

`expected_revision` 是乐观并发检查：调用者声明自己基于哪个版本进行更新。若另一个写入者已经先更新，当前操作应报告冲突，而不是覆盖别人刚写的内容。R08 会完整展开事务与 ABA；本章先看到它怎样影响引用。一个可靠 RAG 系统的正确性不只在模型输出那一刻，还依赖证据的生命周期。

接着把第二次摄入的 allowed 改成空元组，表示默认拒绝所有读取。正文即使没有变化，旧引用也不应继续被当前用户使用。再把文档删除，观察同样的拒绝结果。版本和权限都可能使来源失效，因此引用验证不能只检查某段文字是否曾经在数据库中出现过。

## 小课八：引文存在不等于断言被支持

设来源写着“在教学输入上，算法 A 的输出与参考实现接近”。回答写“算法 A 在所有模型和所有 GPU 上都正确”。引文真实存在，但回答把有限测试推广成普遍保证。这个错误涉及量词范围：教学输入与所有输入、一个环境与所有环境不是同一命题。验证支持关系时必须注意这类范围变化。

再看否定。来源写“尚未在 H100 上执行”，回答写“已经在 H100 上执行”。关键词几乎完全相同，词项检索和向量相似度都可能很高，但逻辑相反。数字也类似：来源写容量九项，回答写十九项；来源写最多九项，回答写至少九项。仅检查共同词汇无法发现这些差别。

时间与主体也会改变含义。来源说旧版本支持某功能，回答说当前版本支持；来源说用户甲偏好短答案，回答说用户乙偏好短答案；来源是一个假设示例，回答把它写成实际观测。你应为这些维度建立测试集，而不是只准备几道简单的同义改写题来评价“faithfulness”。

可以把每个断言拆成主体、关系、对象、条件、时间和确定程度。不是要求所有自然语言都必须机械填满六个槽，而是用这张检查表帮助自己发现遗漏。引用支持的范围应该覆盖回答断言的范围，回答不能在没有额外证据时更强。适度保留“在该资料所述条件下”之类限定，是表达证据边界的方式，不是可有可无的措辞。

语义验证器可以辅助判断，但也可能误判。若使用另一个模型做评审，应固定输入、版本和判定规则，记录其依据，并对关键类别人工抽查。不能把“由模型二检查模型一”当作严格证明。对于高价值事实或复杂推理，保留原文和中间证据链，让人能够复核，比只返回一个自信分数更可靠。

## 小课九：支持、充分和真实是三种不同评价

回答的一句话可能被某段资料支持，却不足以完整回答用户问题。用户问“比较 A 和 B 的区别”，回答只准确描述 A，这段描述是 faithful，但答案不完整。相反，一个回答可能覆盖了所有问题点，却包含来源没有支持的推断。评价应该分别看证据忠实性、问题覆盖和答案正确性。

来源真实又是另一层。严格抽取一份虚构文档可以完全忠实，但若用户以为它是现实资料，答案仍然误导。因此课程 fixtures 明确是教学合成数据，不能拿其中的数字当实际产品规格。真实项目需要记录来源类型、发布主体和时间，并根据任务选择是否进行交叉核对。

证据充分性还依赖任务。例如“定义 KV cache”可能一段教材足够；“确定当前服务器显存不足原因”需要运行时观测；“比较两个框架当前支持情况”需要对应版本代码或正式文档。系统应能说明缺的是哪类证据，而不是统一用“我不知道”结束。一个有用的拒答可以指出下一步应收集什么。

评价表可以为每题记录：必要问题点是否覆盖，引用是否当前可见，引文是否精确，断言是否被支持，来源可信度是否满足任务要求，以及系统是否清楚表达未知。不要急于把全部维度加权成一个总分。先观察各维度的失败分布，才能知道该修资料、检索、生成还是验证。

## 小课十：冲突资料应怎样进入回答

资料冲突可能来自版本差异、条件不同、主体不同、测量误差或真正意见分歧。第一步不是让模型投票选多数，而是检查冲突是否只是条件未对齐。例如一份资料讨论 CPU 参考实现，另一份讨论 GPU 优化实现，它们的性能数字不同并不构成逻辑矛盾。把条件展开后，可能两者都正确。

若同一对象同一条件下存在不同陈述，应保留冲突状态并列出来源。不要因为某份资料排名更高，就自动把另一份删除；相关性分数没有来源权威性的含义。也不要简单按发布时间选最新，除非任务与来源关系支持这种版本规则。一个较新的转载可能复制了更旧信息，时间戳本身不足以判断真伪。

对课程项目，你可以设计明确的版本优先规则：同一 doc_id 只使用当前 revision；不同 doc_id 的相互冲突内容则标为需要复核。这是一个可实现的合同。若要支持 supersedes 关系或权威来源优先，需要把关系作为数据维护，并检查证据，不要只让模型在提示词里猜哪份更可靠。

冲突回答可以采用结构化形式：共同点、分歧点、各自适用条件、目前无法确定的部分和建议验证步骤。这样的回答可能比一个强行单一结论更有用。关键是所有明确事实仍然分别绑定引用，未知部分不能被装饰成已确认事实。

## 小课十一：长回答的引用如何保持细粒度

一篇长回答通常包含背景、事实、推导、建议和未知事项。它们的证据要求不同。背景事实可能需要来源，推导应展示前提与步骤，建议需要说明依据和条件，未知事项则应明确未得到证实。给整篇文章结尾放三个链接，无法清楚对应哪一句由哪条资料支持。

可以先生成一个断言计划，把每个要点与候选证据绑定，再生成自然语言段落。这样模型在写作前就知道哪些内容有支持、哪些缺证据。生成后仍需再次检查，因为表述可能在改写过程中扩大范围。计划阶段的绑定不是最终文本自动正确的保证。

引用位置应尽量靠近它支持的断言。如果一个段落有三个不同来源的事实，可以拆成几句分别引用，或者明确哪些引用支持哪一部分。不要用一个来源标记覆盖整个包含大量推断的段落，使读者误以为每句话都能在原文找到。课程的严格 Claim 结构正是细粒度引用的起点。

对于多来源综合推导，保存中间结论也很重要。来源 A 说明 X 依赖 Y，来源 B 说明 Y 的某个限制，你可以据此提出 X 可能受到相应影响，但还要检查依赖方式和适用条件。逻辑连接不应隐藏在一句“由此可见”后面。多跳章节会进一步把这些依赖写成可检查图。

## 小课十二：摘要也是派生数据，需要来源版本

为了节省上下文，系统可能先把长文摘要成短文，再检索摘要。摘要不是原始资料的替代身份，它是由某组来源和某个模型或规则生成的派生产物。来源更新、删除或撤权后，摘要可能需要重新生成或失效。若只更新原文索引却继续使用旧摘要，回答仍可能携带过期信息。

摘要还可能丢掉条件。原文写“只有在启用某配置时，容量上限为九项”，摘要变成“容量上限为九项”，字数更短但语义更强。对技术资料，数字、否定、版本与限定条件往往是摘要最不能丢的部分。你可以使用结构化摘要字段保留这些信息，并建立针对条件丢失的回归样例。

验证摘要时可以保存每条摘要断言的来源 ID 和引文位置，而不只是把整份原文列表挂在摘要后面。这样某条来源失效时，可以知道哪些摘要断言受影响。这个依赖管理思路将在 GraphRAG 社区摘要中变得更重要，因为一份高层摘要可能依赖很多底层文档，失效传播不能靠人工猜测。

## 小课十三：给生成结果建立一个可执行的输出合同

模型返回“看起来像 JSON”的文本，不等于它满足业务合同。JSON 解析只能证明语法成立，不能证明字段齐全、类型正确、引用有效或断言有支持。一个严格的边界应依次完成大小限制、解析、结构检查、语义检查和来源检查。把这些步骤分开，错误信息才有可操作性。

下面给出一个完整的严格抽取提案验证器。它允许模型或测试替身提出若干条断言，但最终接受与否由运行时决定。这里选择整批拒绝：只要一条不合法，就不把整个报告标为成功。你也可以设计部分接受，但必须明确保留每条状态，不能把失败条目悄悄丢掉后声称所有提案都通过。

```python
import json
from labs.knowledge.rag import Claim, Citation, validate_claim


def validate_proposal(raw, store, context, max_characters=6000, max_claims=6):
    if not isinstance(raw, str) or len(raw) > max_characters:
        return {"accepted": False, "reason": "invalid_or_oversized_text"}
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        return {"accepted": False, "reason": "invalid_json"}
    if not isinstance(data, dict) or set(data) != {"claims"}:
        return {"accepted": False, "reason": "unexpected_top_level_schema"}
    rows = data["claims"]
    if not isinstance(rows, list) or len(rows) > max_claims:
        return {"accepted": False, "reason": "invalid_claim_list"}
    accepted = []
    for row in rows:
        if not isinstance(row, dict) or set(row) != {"text", "source_id", "quote"}:
            return {"accepted": False, "reason": "invalid_claim_schema"}
        if any(not isinstance(row[key], str) or not row[key].strip() for key in row):
            return {"accepted": False, "reason": "invalid_claim_field"}
        claim = Claim(row["text"], Citation(row["source_id"], row["quote"]))
        ok, reason = validate_claim(store, context, claim)
        if not ok:
            return {"accepted": False, "reason": reason}
        accepted.append(row)
    return {"accepted": True, "abstain": not accepted, "claims": accepted,
            "validation": "current visible exact extracts only"}
```

首先检查原始字符串大小，是为了避免一个异常输出占用过多解析资源。随后检查顶层只有 claims，防止调用者误把模型额外返回的字段当作控制指令。每条断言只允许三个字符串字段，再交给当前来源验证。这个过程没有执行模型返回的任何 Python、SQL 或文件路径，模型输出始终是待检查数据。

空 claims 在这个合同里表示合法拒答，区别于 JSON 解析失败。两者都没有可显示断言，但原因不同：前者是模型明确没有提出支持内容，后者是输出不符合协议。运行记录应保留这种区别，否则你可能把格式错误计为谨慎拒答，错误评价系统行为。

若将来支持语义改写，不要直接删除 `claim.text == quote` 的检查后仍保留同一个 verified 状态名。你需要新增语义支持检查，并改变状态体系，例如“来源已核对，语义支持待复核”或“经特定验证器判定支持”。验证强度变化必须在接口和教材中可见，而不是悄悄放宽条件。

## 小课十四：模型提案、工具执行与最终呈现的边界

生成模型可以帮助选择证据、组织语言和提出待检查的断言，但它不应决定自己拥有什么权限。租户与用户身份由可信运行时传入，模型不能在输出里把 actor 改成管理员。检索工具可以接受 query 和有限的 k，身份上下文由宿主绑定。这个设计在 Agent 卷工具执行器与本卷 CorpusStore 之间形成清楚的职责分工。

最终呈现也不应直接信任模型提供的标题、URL 或版本号。模型可以引用 source_id，显示层再从已核对的来源对象读取标题与位置。这样即使模型把一个来源描述成“官方最新说明”，显示层也不会自动采用这个未经证实的说法。来源 metadata 本身也需要可信摄入，不能把模型抽取值直接提升成认证身份。

工具结果属于观察，模型最终文本属于提案，验证器输出属于系统判断。三者分别保存有助于调试。例如工具确实返回了容量九项，模型写成七项，验证器拒绝；这说明检索成功、生成失败、验证成功。若只记录最终“请求失败”，你会误以为整条系统都坏了，无法知道哪部分正在发挥保护作用。

接入真实模型时，先使用四五条虚构资料完成这个闭环，再增加复杂数据。API Key 放在环境变量或适当密钥管理中，不能写进课程文件或日志。这里的重点不是增加无关防护清单，而是确保学习实验不会把验证系统的输入输出与凭证混在一起。真实调用的耗费与失败状态也应被记录，而不是由模型自行声称调用完成。

## 小课十五：检索后的撤权与版本变化

一次 RAG 请求不是瞬间完成的。检索、重排、生成和验证之间可能经过数秒甚至更长时间。在这段时间里，文档可能被更新、删除或撤权。因此“检索时可见”不能自动推出“回答发送时仍可见”。课程在最终引用验证时重新读取当前状态，就是为了解决这类时间窗口的一部分问题。

不过，最后一次检查之后仍然可能发生状态变化。分布式系统很难用一句“再检查一次”保证整个网络发送过程与权限修改绝对原子。实际系统需要定义授权观察点、快照有效期、撤权传播目标和缓存策略。教学实现采用当前读取的明确检查，不宣称已经解决所有跨进程竞态。

如果资料已经发送给外部模型，之后撤权无法让过去的网络传输从未发生。因此数据出口授权必须在发送前完成，最终验证则负责防止过期内容继续呈现。两道检查解决不同时间点的问题，不能互相替代。你应在架构图上标出资料何时离开本地边界，而不只标出最终回答箭头。

对本地学习项目，可以用测试替身在检索后、验证前修改资料，稳定重现这个窗口。避免使用不可靠的 sleep 竞争测试；直接在可控步骤之间执行更新，结果应明确拒绝旧引用。这样的确定性故障注入能让你真正理解生命周期，而不是只在文档里写一句“注意并发”。

## 小课十六：十二道分级练习及完整参考答案

**题一：来源可用性。** 引文能在历史数据库中找到，是否可以用于当前回答？不一定。还要检查当前版本、租户和权限。课程验证器只接受当前可见片段，旧对象仍在内存不代表继续有效。历史展示可以有另一套明确合同，但不能与当前问答混用。

**题二：字面支持。** 引文写“仅 CPU 执行”，回答写“GPU 已验证”，字符串相似度很高是否足够？不够，否定和对象改变导致逻辑相反。参考答案应指出来源存在检查无法验证语义支持，严格抽取会因 text 与 quote 不同而拒绝；语义模式需要额外检查。

**题三：预算。** 总容量一千字符，固定说明一百五十、问题五十、历史二百、输出二百、结构余量一百，证据预算为多少？答案三百。字符不是模型 token，真实接口需按自己的计数合同重新计算。答题时写出所有项，不能只从总数减去资料长度。

**题四：JSON 转义。** 正文中有引号和换行，为什么正文长度之和不能直接代表上下文长度？序列化增加字段名、括号、逗号和转义字符。完整验收是对最终 JSON 字符串检查长度并解析身份集合，而不是只统计 text 字段。

**题五：大块放不下。** 第一条候选太长，第二条较短，课程打包器会结束还是继续？继续尝试后面的候选。答案需要指出这种行为有利于利用剩余预算，但仍不保证最优覆盖。若改成 break，必须用这个例子证明结果会不同。

**题六：严格抽取改写。** 原文“容量为九项”，回答“最多保存九条”，能否自动通过当前验证器？不能，因为它们不是完全相同字符串。即使人工认为语义等价，也需要另一个验证合同。不要把保守拒绝当成代码不理解中文的偶然错误，它是明确设计边界。

**题七：未知引用。** 模型给出一个格式正确但不存在的 source_id，应怎样处理？拒绝提案或该断言，并记录来源不可用状态。不能因为引文内容看起来合理就自动创建一个来源记录，也不能从任意 URL 临时补证据而不记录新的检索步骤。

**题八：冲突。** 两份资料分别写容量七与九，应选排名更高的一份吗？先检查版本、条件、来源角色和替代关系。同一 doc_id 使用当前版本，不同来源真实冲突则保留冲突并复核。排名分数不是权威度，不能代替来源判断。

**题九：摘要条件丢失。** 原文“启用共享时容量九项”，摘要“容量九项”，问题在哪里？摘要把有条件命题扩大成无条件命题。应保留条件字段或精确支持片段，并在摘要验证集中加入这种反例。字数减少不等于信息保真。

**题十：无输出。** 空 claims 与 JSON 解析失败是否都算拒答？不是。前者在合同里是明确拒答，后者是协议错误。评测与日志要区分，否则格式错误可能被误算为系统谨慎，掩盖可靠性问题。

**题十一：撤权窗口。** 检索后文档撤权，最终验证应该怎样？拒绝旧引用。测试可以在两个可控步骤间直接更新权限，不需要靠随机时序。答案还应说明发送给外部模型之前的出口授权与最终验证是不同责任。

**题十二：整段引用。** 一段回答有三个不同事实，只在末尾放一个来源是否充分？未必。应按断言或紧密相关句群绑定来源，明确哪些是事实、推导和未知。一个来源存在不能覆盖段落中所有未经支持的扩展结论。

## 小课十七：把引用扩成精确跨度，解决重复句子的歧义

只保存 quote 字符串有时不足以唯一定位。同一段文档可能重复出现“默认关闭”，一次描述功能甲，一次描述功能乙。字符串子串检查都能通过，但读者不知道引用的是哪一处。可以增加片段内部的 start、end，并要求 quote 等于来源正文对应切片。这样引用既有内容，也有精确位置。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SpanCitation:
    source_id: str
    start: int
    end: int
    quote: str


def validate_span_citation(store, context, citation):
    source = store.get_visible_chunk(context, citation.source_id)
    if source is None:
        return False, "source_unavailable"
    if type(citation.start) is not int or type(citation.end) is not int:
        return False, "invalid_offset_type"
    if not 0 <= citation.start < citation.end <= len(source.text):
        return False, "invalid_offset_range"
    if not citation.quote.strip():
        return False, "empty_quote"
    if source.text[citation.start:citation.end] != citation.quote:
        return False, "quote_offset_mismatch"
    return True, "verified_exact_span"
```

偏移单位仍然是 Python 字符索引，与 R02 的切块合同一致。若想回到完整文档的位置，可以在同一版本下用 chunk.start 加上片段内偏移，但要确认 chunk.text 确实是原文精确切片。若检索文本经过标题增强或规范化，不能直接把增强文本偏移加回原文。这个跨层映射必须遵守同一数据合同。

类型检查使用 `type(...) is int`，明确拒绝布尔值。因为 True 在 Python 中可当一使用，但它不是一个合理的引用偏移输入。范围检查放在切片之前，避免 Python 切片对越界的宽容行为掩盖错误。例如 end 超过长度时，切片会自动截断，不一定抛异常；如果你依赖异常来判断范围，就会漏掉不合法引用。

跨度引用也不能证明语义支持。模型可以准确引用“默认关闭”但把它用于错误功能。精确定位减少歧义，让验证与人工复核更容易，却没有自动完成主体、条件和关系判断。每增加一种结构化字段，都要清楚它消除了哪类不确定性、还保留哪些问题。

## 小课十八：证据预算可以作为一个小型选择问题

贪心打包便于实现，但你可以用小规模穷举验证它是否错过更好的组合。设只有六个候选，每个候选有成本和覆盖信息点集合，枚举所有子集并筛掉超预算的组合，选择覆盖最多的一个。六个候选只有六十四种子集，CPU 很容易完成。这个慢 oracle 有助于理解选择目标，不适合直接扩展到上千候选。

```python
from itertools import combinations

def exhaustive_pack(candidates, budget):
    best = (set(), 0, [])
    for size in range(len(candidates)+1):
        for group in combinations(candidates, size):
            cost = sum(item["cost"] for item in group)
            if cost > budget:
                continue
            covered = set().union(*(item["covers"] for item in group)) if group else set()
            ids = sorted(item["id"] for item in group)
            if (len(covered), -cost, tuple(ids)) > (len(best[0]), -best[1], tuple(best[2])):
                best = (covered, cost, ids)
    return {"covered": sorted(best[0]), "cost": best[1], "ids": best[2]}

candidates = [
    {"id":"A", "cost":8, "covers":{"hardware"}},
    {"id":"B", "cost":4, "covers":{"hardware","version"}},
    {"id":"C", "cost":4, "covers":{"mechanism","validation"}},
]
assert exhaustive_pack(candidates, 8)["ids"] == ["B","C"]
```

这里的成本是人为给定数值，不是完整 JSON token 预算；真正接入时应使用实际序列化成本，并考虑组合结构开销。覆盖标签也是人工 oracle，不是部署时天然可得的信息。你应该把它作为诊断工具：看看一个排名贪心策略在相同候选与预算下距离理想选择有多远，再决定是否需要更复杂的选择器。

还要注意优化目标。只最大化覆盖数量，可能把重要性不同的信息点当成同等价值；只最小化成本，可能选很短但难理解的片段；只最大化相关性总分，可能重复同一事实。实际系统可以采用带权覆盖、最低支持要求和冗余限制，但每个权重都应有任务依据。把复杂度加进去之前，先写出你真正希望优化什么。

## 小课十九：怎样用干预实验判断模型是否真的使用了证据

仅观察回答正确，无法证明模型依赖了检索资料。你可以设计受控干预：保持问题与提示结构相同，只改变虚构资料中的一个关键事实。第一次容量七项，第二次九项，第三次删除容量信息。一个依赖当前证据的系统应分别回答七、九，以及支持不足，而不是始终返回预训练中常见的某个数字。

这个实验必须使用明确的虚构场景，避免故意给真实用户灌输错误资料。它的目的在于测试系统对证据变化的敏感性，不是证明模型总会相信任何文本。对于真实知识冲突，系统还需要来源判断；对于这类合成实验，标准答案由实验设计明确给出，便于隔离机制。

另一个干预是删除检索步骤，直接让模型回答相同问题。若两种设置结果一样，并不能立刻说 RAG 没作用；也可能题目太常识化，模型本来就知道。应使用新造事实、版本更新和带条件的问题，观察引用与回答是否跟随资料。评价设计必须让你想检验的机制有机会影响结果。

还可以只交换 source_id 与正文的配对，验证系统是否能发现身份错配；只修改版本，验证旧引用是否失效；保留正文但撤权，验证访问边界。每个干预只改变一个因素，能让失败原因更清楚。把所有故障一次混入同一请求，虽然看起来“压力很大”，却不利于初学者理解哪个检查真正起作用。

## 小课二十：一个完整的 RAG 验收矩阵

建立至少四类题：可直接回答、需要多条证据、资料冲突、当前资料无答案。每类再加入格式和生命周期变体，例如来源文本含引号、引用跨度重复、文档更新、权限撤销、模型返回坏 JSON。你不需要一开始拥有几百题，但每一题必须有明确预期与失败原因。

对可直接回答题，检查检索是否找到正确片段、打包是否保留条件、输出是否绑定当前引用。对多证据题，检查必要来源是否全部覆盖，而不是只要求有一个相关块。对冲突题，检查系统是否说明差异与条件，避免强行合并。对无答案题，检查是否拒答或提出需要的额外信息，而不是拿主题相关片段凑答案。

输出状态也要分层记录：检索失败、上下文不足、格式错误、来源过期、语义不支持、合法拒答和接受回答。一个失败类别对应不同修复方向。统计时不能把所有失败统一删掉，只计算成功请求的质量；那会让最不可靠的系统通过大量失败来隐藏难题。

若使用真实生成 API，保存足够重建请求的非敏感配置、模型身份、输入资料 ID、实际输出和验证结果。服务不提供确定性时，可对固定题重复运行，分别报告每次结果与聚合，而不是只挑最好一次。检索通常可以较确定地重放，但生成波动与工具环境变化需要单独分析。

## 小课二十一：引用渲染是最后一段真实代码

很多系统在验证阶段正确，最后显示时却把来源映射错了。比如把 source_id 列表按字母排序后，仍沿用原来的数字脚注编号；或者合并重复引用时，把一个句子指向另一个版本。渲染层也应有测试，不能认为它只是排版，与事实无关。

一个安全的简单策略是先为已接受的来源建立固定映射，再根据映射生成脚注。每条断言保留自己的 source_id，不直接保存临时显示编号。显示编号只在本次回答内有效，长期记录仍使用稳定身份。若引用不可用，显示明确状态，不要悄悄删掉脚注后留下看似无条件的事实句。

读者点击引用后应能看到足够上下文，而不是仅看到孤立短句。可以显示标题、版本、原始位置与前后少量文字，同时保持权限检查。上下文帮助读者判断否定、假设和条件，但展示更多内容也受授权与预算约束。这里再次体现：引用的目标是可复核，不是装饰一个链接。

## 小课二十二：从严格模式升级到综合写作的步骤

第一步保持抽取式输出，完成所有身份、预算、版本和权限测试。第二步允许把多个独立抽取组成列表，但不改写内容。第三步允许有限格式转换，例如把同样数值整理成表格，并验证每个单元格来源。第四步才允许自然语言改写与跨来源综合，同时引入语义支持评价与人工抽查。

这种分阶段升级让每一种新能力有可观察的增量。若一开始就让模型写长篇综合报告，失败可能来自任何层，很难区分。反过来，严格模式已经通过的检查也不能因为加入更强模型就删除；它们仍然保护最基础的来源合同。表达能力增加，应伴随新的验证，而不是替换掉已有验证。

综合写作中可以明确区分“来源直接陈述”“根据多个来源推导”“建议进一步验证”。这些标签不应滥用成冗长免责声明，而应在确实存在不同证据地位时帮助读者理解。一个清楚的工程回答能够给出结论，也能够指出结论依赖什么条件。用户最终需要的是可靠地解决问题，而不只是看到一段很像专家写的文字。

## 故障工作坊一：一个正确数字为什么仍然不能通过

让资料写“青石项目当前容量九项”，模型提案也写同样文字，但 source_id 填成另一份文档。许多只检查答案数字的测试会通过，因为九这个数字正确；严格引用验证应该失败，因为提案把正确事实归给了错误来源。这个案例说明答案正确性和引用正确性是两个独立维度，不能只测试其中一个。

定位时先读取模型原始提案，确认 text 与 source_id 的配对；再根据当前 Context 查询该来源；最后比较 quote 是否存在。不要先搜索全库找到任何含九的文档来“修复”引用，否则你改变了模型实际提出的证据链。若产品允许自动补证据，应把它作为新的检索与验证步骤记录，而不是悄悄改写历史。

参考验收包括三个状态：文字正确但来源错，来源正确但引文错，两者都正确。只有最后一种符合当前抽取合同。再加入第四种：来源与引文都正确，但资料已经过期。它仍应失败。完成这四个对照，你会理解为什么一个简单的答案字符串比对无法替代知识系统验收。

## 故障工作坊二：截断把一句话变成相反意思

原文是“并非所有请求都共享同一缓存；只有满足相同前缀与配置条件的请求才可复用”。如果为了节省预算截取中间片段“所有请求都共享同一缓存”，它在字面上确实是原文连续子串，却失去了前面的否定。子串验证因此会通过，但用它作无条件断言会误导。

这个案例提醒你：严格抽取并不自动等于语义保真，尤其是随意选择短跨度时。课程基础回答提取完整片段，仍然需要合理切块；若加入句子级提取，应保留否定与条件的完整范围。可以用句法或模型辅助，但必须对这类反例做检查，并在无法确定时展示更大的原文上下文。

修复思路不是简单禁止所有短引文，而是把引用选择与断言支持共同评价。显示层可以展示引文前后上下文，验证器可以要求提案说明适用条件，人工评测可以标注“字面存在但语义截断”。这比把所有通过 substring 检查的结果统一标成正确更准确。

## 故障工作坊三：模型输入正确，最后报告却错了

假设检索、生成和验证都使用当前容量九项，渲染器却从旧缓存读取标题或摘要，把最终页面显示为容量七项。模型本身并没有犯错，错误发生在输出拼装或缓存层。若日志只保留模型响应，你会看到“模型输出正确”而无法解释用户看到的错误。

因此最终可见报告也应有版本与验收。记录被接受的 Claim、渲染使用的来源映射，以及最终返回结构。在测试中可以把旧摘要缓存预先放入，再执行新版本回答，确认渲染层不会把旧字段覆盖当前断言。不要把展示代码排除在系统正确性之外；用户接触到的是最终产物，而不是内部某个已经通过检查的对象。

这个故障还说明缓存依赖必须明确。答案缓存可能依赖问题、用户权限、资料版本、模型版本、提示模板和验证规则。若缓存键只包含问题文本，同一个问题在资料更新或不同用户下可能返回错误结果。小项目最初可以不做答案缓存，先保持清楚正确的流程；增加缓存时再逐项设计失效规则与回归测试。

## 本章作品的最终验收

交付一个可以在 CPU 上运行的证据回答程序，包含摄入、查询、打包、提案解析、引用验证和结构化报告。至少测试正常回答、无答案、坏 JSON、未知来源、错误引文、版本更新、权限撤销、预算不足和语义截断反例。对严格模式不能自动解决的语义问题，报告应明确说明边界，而不是伪造成功状态。

再写一份逐阶段实验记录，说明每个错误最早在哪一层出现、由哪一条检查发现、修复后哪个回归测试通过。完成这些以后，你掌握的是一套可审查的证据工程流程。后续加入更强模型、更复杂检索和更长任务时，可以沿同样的责任边界扩展，不必重新把全部系统变成一个无法解释的提示词黑盒。

验收时还应保存一次从问题到报告的人工对照表：第一列是用户要求，第二列是需要成立的事实，第三列是证据的完整句子，第四列是片段身份与版本，第五列是最终实际输出。这个表不是把模型的理由抄下来，而是由学习者逐项核对程序产物。若某一列为空，就说明链上存在缺口；不能用其他列写得很漂亮来抵消它。尤其要检查被省略的单位、否定、条件与时间，因为数字本身正确的答案仍可能表达错误的业务事实。做完这张表再运行自动测试，你会知道测试究竟覆盖了哪一段，而不是把绿色结果误解成所有语义都已获证。

## 源码落实与运行复核

### 一次完整的代码追踪

从 `answer_report(store,ctx,query)` 开始。它调用 `extractive_answer`；后者先调用 hybrid，hybrid 内部先取得 `store.visible(ctx)`，因此无权文档不会参与分数统计。候选进入 `pack_context`，输出 JSON 字符串，再解码成结构化条目。每个条目产生一个 Claim，引用 ID 和原文被放到 Citation 中。

返回报告前再次执行 `validate_claim`。这个复核用于防止检索与输出之间发生版本或权限变化。注意它不能完全消除并发竞态：如果校验后马上撤权、随后才发送，仍存在时间窗口。真实服务要定义授权时刻与一致性语义，必要时在统一快照或事务中取证据。课程不是跨系统分布式一致性的完整实现。

若没有合格证据，结果 `abstain=true`。这与 API 调用失败不同。一个是任务层没有足够证据，一个是系统层服务不可用。日志、重试和用户反馈应分别处理，否则系统可能把网络错误伪装成“资料没有答案”。

### 加入真实模型前的契约

把模型接口定义成“输入问题和证据列表，输出结构化 claims”。每条 claim 包含 text、source_id、quote；如果没有足够证据，应允许 no_answer，而不能强迫模型总生成一个结论。对响应做 schema 校验，拒绝不存在的 ID、空引文或超出限制的大输出。

把模型的新增能力分开评估：语句自然程度、证据覆盖、回答正确性、引文支持率、拒答合理性。不要只评价“回答像不像专家”。同一个问题可以重复多次观察波动，但每次都保存本次证据版本和模型配置，才能区分检索变化与生成随机性。

本卷离线代码不发起外部调用，不消耗 API 费用；Agent 工程卷负责模型适配器。连接方式是提供已授权的 evidence data，再接收结构化 claim。不要让模型返回字符串形式的 SQL 或任意文件路径并直接执行。

## 综合工作坊：流式草稿与最终发布是两种状态

模型流式输出时，用户可能在引用检查前就看到半句答案。若前半句说“容量为七”，后续才发现来源过期，撤回文字并不能保证用户没有据此行动。系统应定义草稿与已验证结果的展示语义：可以先显示生成中状态或受限草稿，但不能把未校验内容标成已证实答案。高要求场景可先缓冲结构化输出，完成校验后一次发布。

引用解析也不能在任意 token 边界执行。JSON 可能尚未闭合，source_id 可能只输出一半，文本中的转义可能未完成。增量解析可以帮助界面，但最终仍需完整 schema 与来源检查。不要因为流中出现一个合法 ID 就提前认定整段后续文本受它支持，模型可能继续添加不同断言。

下面的纯函数模拟一个发布闸门。所有候选先校验，任一项失败就返回未发布与错误列表；全部通过才返回完整结果。它使用本卷真实 validate_claim，因此只支持严格抽取，不是生成式蕴含验证器。

```python
def prepare_publication(store, context, claims):
    accepted, failures = [], []
    for position, claim in enumerate(claims):
        ok, reason = validate_claim(store, context, claim)
        if not ok:
            failures.append({"position": position, "reason": reason})
        else:
            chunk = store.get_visible_chunk(context, claim.citation.chunk_id)
            accepted.append({"text": claim.text, "source_id": chunk.chunk_id,
                             "doc_id": chunk.doc_id, "revision": chunk.revision})
    if failures:
        return {"published": False, "claims": [], "failures": failures}
    return {"published": True, "claims": accepted, "failures": []}

from labs.knowledge.store import CorpusStore, Context
from labs.knowledge.rag import Claim, Citation, validate_claim

with CorpusStore() as publication_store:
    publication_store.ingest("publication", "d", "D", "Capacity is seven.", allowed=("*",))
    publication_context = Context("publication", "learner")
    source = publication_store.visible(publication_context)[0]
    valid = Claim(source.text, Citation(source.chunk_id, source.text))
    invalid = Claim("Capacity is nine.", Citation(source.chunk_id, "Capacity is nine."))
    assert prepare_publication(publication_store, publication_context, [valid])["published"]
    rejected = prepare_publication(publication_store, publication_context, [valid, invalid])
    assert rejected["published"] is False and rejected["claims"] == []
```

这个策略是整份回答原子发布。另一种策略允许部分发布，但必须逐断言标明成功与缺口，不能把失败项悄悄删掉后仍声称完整回答。选择取决于任务与产品要求，两者都需要明确状态。示例函数没有数据库快照锁，校验后到实际展示之间仍可能变化，因此它证明的是一次校验过程，不是无限期有效承诺。

### 断言级引用为什么比段落级引用更精确

一段话可能包含容量、更新方式、恢复能力三个断言。段落末尾一个来源只支持容量，读者容易误以为全部得到支持。把答案拆成最小可判断断言，每条附对应来源，能明确支持范围。不是要求每个词都一个引用，而是对独立事实分别建立证据关系。

跨来源综合要保留推断步骤。来源 A 说明组件依赖，来源 B 说明被依赖组件的更新策略，最多支持某条依赖线索；若要推出服务停机，还需要调用与容错证据。引用两篇真实文档不能自动使新增因果结论成立。R10 的路径审查在这里重新出现，图与文本都遵守同样逻辑边界。

引文越短不一定越好。只摘“支持热更新”可能从“不支持热更新”中截出相反意思；只摘“九”可能漏掉单位与条件。可以要求引文覆盖完整句子或必要上下文，并人工检查否定范围。精确子串是来源位置检查，不能替代语义支持判断，教材必须把两者分开说明。

### 回答评价的三种对照输入

第一种对照交换证据事实：容量七改九，答案应随证据改变。第二种删除唯一支持来源，答案应拒答或标缺口。第三种加入高相关但不支持的干扰文档，答案不应被诱导扩大结论。三个对照分别检查忠实性、证据必要性与抗干扰，不需要大量数据就能发现常见 RAG 伪成功。

再加入权限对照：管理员与普通用户同问，结果依据各自可见集合，不共享私有缓存。加入版本对照：同一来源更新后旧引用失效。加入渲染对照：内部 JSON 正确时最终文本仍应保持数字、单位、否定和来源。端到端评价必须覆盖实际用户输出，不能停在模型响应对象。

生成式重述可以用人工断言标签或受控判别器辅助，但判别器也可能出错。不要把另一个模型的分数当绝对真理；在已知负例上评估它的漏报与误报，尤其条件省略与细微否定。高影响任务可以采用更保守的抽取与人工复核，能力选择应由需求决定。

### 预算、顺序与证据完整性的联动

上下文预算不足时，系统可能只放入支持主结论的段落，漏掉后面的例外。排序看似合理，却改变证据范围。解决不只是增加 token 上限，可以按断言组打包主句与条件、去重重复来源、保留必要相邻段落，或在无法容纳完整支持时不回答该槽位。上下文选择本身是一项推理与约束问题。

证据顺序也影响模型注意。把最相关来源放前面通常有帮助，但不能依赖某种固定排序保证正确。评测时打乱等价证据顺序，观察结论是否稳定；把冲突来源放不同位置，检查模型是否总偏向最后一条。顺序敏感性是生成层行为，不应误诊为检索召回变化。

最终作品应保存实际传给模型的证据载荷及其来源清单，在受控权限下可重放。若只保存检索 top-k 而不保存打包结果，就不知道模型真正看到什么。若日志包含私有原文，日志本身也要遵守访问与保留策略。可观测性与数据治理需要同时设计，而不是事后把所有内容都打印出来。

发布后的答案缓存仍是带依赖的历史产物。再次展示时要说明使用的快照或复核当前来源，不能因为第一次校验通过就永久有效。尤其权限撤销后，缓存文本可能仍包含受限事实；删除引用标签并不能消除正文泄露。把报告身份、来源版本与授权策略连接起来，才能让验证贯穿完整使用周期。
