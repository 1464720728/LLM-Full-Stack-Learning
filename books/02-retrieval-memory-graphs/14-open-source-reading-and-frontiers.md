# R14 从自写系统走向真实开源项目与前沿工作

先修：能够运行并解释 R13 两个项目。此章提供的是带任务、定位方法和验收物的源码研读路线，不是收藏链接清单。链接核查日为 2026-11-01；指向 main 或在线文档的内容可能继续变化，课程不把它们冒充固定版本。

## 1. 读源码前先建立问题

面对一个几十万行仓库，直接从第一个文件开始看，很快会失去方向。先把问题限定成可追踪行为，例如“相同文档重复摄入为什么不会重复建立索引”“过滤条件在哪里进入检索器”“检查点与长期记忆如何分开”“一个图关系失效会影响哪些摘要”。有了问题，入口、状态和输出才有明确边界。

每次阅读形成四份记录：调用链；关键数据结构；不变量与异常；本地复现用例。只画架构图不够，必须找一条具体输入走过真实函数。看不懂的语言机制先回基础卷补齐，例如生成器、装饰器、协议、泛型、上下文管理器，不要把它们统称为“框架魔法”。

固定版本的方法是记录仓库 URL 与实际 checkout 的 commit SHA。`git rev-parse HEAD` 给出你正在阅读的版本。课程未实测的版本不写成已验证；在线文档里的 latest 也不是可复现实验标识。后面 API 或路径变化时，先在固定提交用 `rg` 搜索符号，而不是盲目把旧教程命令套到新版本。

## 2. 路线一：Haystack，理解组件与检索边界

入口是 [BM25 Retriever](https://github.com/deepset-ai/haystack/blob/main/haystack/components/retrievers/in_memory/bm25_retriever.py) 与 [Document Store 概念](https://docs.haystack.deepset.ai/docs/document-store)。阅读时回答：Retriever 自己保存倒排统计吗，还是把检索工作委托给 store；过滤条件如何合并；返回对象包含哪些字段；top_k 在哪一层生效。

第一项任务：用本卷三个 cat/dog/fish 文档建立同规模实验，找到 Haystack 当前固定版本所用 BM25 变体与 tokenizer。不要预设分数必须和本卷相同；先解释公式、分词、长度和查询词处理差异，再比较排名。如果数值不一致但原因明确，这是成功的源码分析。

第二项任务：给一个文档添加受限元数据，分别测试初始化过滤与运行时过滤。写一个回归用例，确保合并策略没有把更严格的权限放宽。元数据过滤只是一种实现工具，调用者身份仍需要应用层确定。

第三项任务：建立摄入与查询两个 pipeline，故意连接错误类型的组件，观察框架在哪个阶段拒绝。将本卷手写函数接口与框架组件契约做对照，理解框架减少了什么样板代码，又引入哪些配置与序列化复杂度。

交付物是一页调用链说明、一个固定版本环境记录、三组对比输入输出和一个失败测试。不要把安装成功截图当作完成。

## 3. 路线二：LlamaIndex，理解文档生命周期

入口是 [IngestionPipeline 源码](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/ingestion/pipeline.py) 与 [摄入文档](https://github.com/run-llama/llama_index/blob/main/docs/src/content/docs/framework/module_guides/loading/ingestion_pipeline/index.md)。重点跟踪 document、node、docstore、vector store、变换缓存之间的身份映射。

第一项任务：阅读重复文档检测与更新路径。列出哪些字段参与 hash，哪些状态需要持久化。再做“正文相同但元数据不同”“正文更新”“源文档删除”“同一 source_id 重试”四种实验，观察 docstore 与 vector store 是否一致。

第二项任务：插入一个自己的确定性变换，例如给段落补章节路径，但保持原始引用字段。比较变换前后 hash 与缓存命中，说明什么时候需要失效缓存。不要把源文本悄悄修改后继续声称原始 offset 正确。

第三项任务：实现一个小适配器，把本卷 CorpusStore 导出的可见 chunks 转成该框架的节点对象。保持 tenant、doc_id、revision、source span 字段。再把框架返回对象映射回 Claim，继续使用本卷引用检查。这个任务训练你在保留语义契约的前提下替换框架，而不是重写一遍不可验证应用。

交付物是数据模型对照表、四个生命周期测试、适配器代码和两个实际 bug/边界发现。若固定版本不提供你以为有的策略，就明确记录差异，不能编造参数。

## 4. 路线三：LangGraph，理解持久工作流与长期记忆

从 [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) 和 [Memory](https://docs.langchain.com/oss/python/concepts/memory) 开始。官方文档区分按 thread 保存图状态的 checkpointer 与跨 thread 的 store。这个区分正好对应本卷的“任务恢复状态”和“可复用知识”。

第一项任务：构造只有 search→validate→answer 的最小图。先使用内存 checkpointer，在同一进程暂停与恢复；再关闭进程，观察它不能提供真正磁盘持久性。换成当前版本支持的持久后端，再进行相同实验。记录模型调用和副作用是否重复。

第二项任务：用两个 thread_id 模拟两次会话，共享一个受控 owner 的长期 store，同时让短期消息互相隔离。再换另一个 owner，确认长期记忆不串线。不能只靠不同 thread_id 代替所有用户权限边界。

第三项任务：在记忆写入前设置人工确认点。对恢复路径进行故障注入，检查确认前后的操作会不会重放。把写入改成带幂等键或 CAS 的操作，并解释为何某些步骤必须可重试。不要把“框架支持 checkpoint”理解成任何外部副作用都会自动 exactly-once。

交付物是一段可重启的最小应用、两个会话隔离测试、一条副作用恢复轨迹，以及你能解释的状态更新规则。完成后再研究多 Agent 或更复杂动态图，避免直接陷入大量节点与 prompt。

## 5. 路线四：Faiss 与 Sentence Transformers，真正理解检索性能

[Faiss 索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) 可用于选择 Flat、IVF、HNSW 或量化方案；[Sentence Transformers 重排示例](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) 展示编码与交叉重排的职责。

先做 CPU 的 1000–10000 条规模实验，数据使用公开授权或自建虚构材料。建立精确 Flat ground truth，再测近似索引的 Recall@k、构建耗时、搜索延迟和内存。单次计时噪声很大，应预热、重复、报告中位数或分位数，固定线程数与输入批量。不要在共享服务器上无界开启全部 CPU 线程。

对 embedding 模型建立任务级相关性标签，不能只测 ANN 近邻召回。对 reranker 测候选池大小 N 与最终 k：N 太小可能召回不足，太大可能增加延迟而收益有限。使用显卡时先单卡小 batch，明确一次实验时长与退出条件；本路线没有必须占满 8×H100 的理由。

交付物是一张两种召回指标的对照表、索引参数曲线、同分 tie-break 说明和模型版本记录。某次近似索引更慢也应如实解释，可能小规模下管理开销占主导。

## 6. 路线五：Microsoft GraphRAG，读清索引与查询

入口为 [GraphRAG 文档](https://microsoft.github.io/graphrag/) 与 [原论文](https://arxiv.org/abs/2404.16130)。先区分实体关系抽取、社区组织、摘要生成、局部查询和全局查询。阅读源码时追踪数据表之间的 ID 和来源关系，而不只看最终回答函数。

第一项任务：用 12 份虚构文档做最小摄入，人工检查实体与关系抽取，标出同名、否定、条件和例外四类错误。第二项任务：比较局部事实问答与全局主题问答，分别定义验收标准。第三项任务：修改一份底层文档，追踪需要重建的派生对象以及费用。

真实模型调用可能产生成本，先阅读固定版本的配置与 dry-run 能力，明确调用预算。课程不提供会自动调用外部模型的大规模默认脚本，也不声称本次已执行该框架的 API 索引任务。这里的扩展是有具体输入、输出与验收的训练，不是把核心内容留到以后。

## 7. 追踪前沿时的判断框架

遇到新的记忆或检索论文，先标出它改变哪一层：表示、索引、查询策略、上下文选择、记忆写入、验证或评测。然后查基线是否同模型、同预算、同语料，是否只比较最弱的 naive RAG，是否统计更新与摄入成本，是否有权限、时效和冲突场景。

区分“能复现论文配置”和“适合你的任务”。某方法在长文档全局摘要上有效，不等于在错误码查找上有收益；某记忆算法在合成偏好任务上准确，不等于可以自动保存真实用户长期事实。把前沿结果转成自己小系统上的可检验假设，再决定是否深入。

## 8. 练习与参考交付

**练习 1：固定源码版本。** 在任一上述项目 clone 后运行 `git rev-parse HEAD`，写入自己的实验记录。参考结果应是真实 40 位 commit，而不是把日期或 release 名误当 SHA。课程没有预填未经执行的 SHA。

**练习 2：比较接口。** 把本卷 Context/Chunk/Hit/Claim 与选定框架对象逐项映射。参考表至少包含身份、版本、权限、原文、分数类型和来源字段；找不到对应字段时说明由适配器保存，不能直接丢掉。

**练习 3：一个真正修改。** 选择缓存指纹、过滤合并或重复文档处理的一处行为，先写失败测试，再改小范围代码，再跑相关现有测试。参考交付是可 review 的 diff 和原因，不是简单把参数从 5 改成 10。

**练习 4：读一篇新论文。** 用上述七层分类画出它的改动，列出一个最小可复现实验和可能失败的反例。参考答案必须包含预算与评价条件，不接受只有摘要翻译。

**练习 5：迁移回个人系统。** 选一个有证据收益的组件替换本卷接口，并保留所有 ACL、旧引用、删除、TTL 与冲突测试。验收是原有语义测试继续通过，再增加真实检索质量评估。框架换了，正确性契约不能丢。

**掌握门槛：** 能沿一条真实输入追踪到数据结构与索引调用；能写失败测试定位源码行为；能有依据地采用、拒绝或简化一个新方法。熟悉项目名字只是起点，这些交付才是技能证据。
