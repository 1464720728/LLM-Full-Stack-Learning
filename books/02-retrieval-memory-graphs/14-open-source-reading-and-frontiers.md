# R14 从自写系统走向真实开源项目与前沿工作

先修：能够运行并解释 R13 两个项目。此章提供的是带任务、定位方法和验收物的源码研读路线，不是收藏链接清单。链接核查日为 2026-11-01；指向 main 或在线文档的内容可能继续变化，课程不把它们冒充固定版本。

## 小课一：读源码前先建立问题

面对一个几十万行仓库，直接从第一个文件开始看，很快会失去方向。先把问题限定成可追踪行为，例如“相同文档重复摄入为什么不会重复建立索引”“过滤条件在哪里进入检索器”“检查点与长期记忆如何分开”“一个图关系失效会影响哪些摘要”。有了问题，入口、状态和输出才有明确边界。

每次阅读形成四份记录：调用链；关键数据结构；不变量与异常；本地复现用例。只画架构图不够，必须找一条具体输入走过真实函数。看不懂的语言机制先回基础卷补齐，例如生成器、装饰器、协议、泛型、上下文管理器，不要把它们统称为“框架魔法”。

固定版本的方法是记录仓库 URL 与实际 checkout 的 commit SHA。`git rev-parse HEAD` 给出你正在阅读的版本。课程未实测的版本不写成已验证；在线文档里的 latest 也不是可复现实验标识。后面 API 或路径变化时，先在固定提交用 `rg` 搜索符号，而不是盲目把旧教程命令套到新版本。


### 第一轮阅读的逐步操作

先把自己能运行的三文档例子准备好，写出查询、预期相关文档与不相关文档。再打开公开 API 文档，确认构造参数和返回字段。只记录当前实验需要的参数，不一次阅读所有插件。运行示例后保存对象类型、内容、ID、metadata 与 score，逐项映射到本卷 Chunk 与 Hit。缺少字段时写明，不假设框架自动保留版本与授权。

然后搜索公开入口函数的定义，阅读前后几十行，找实际委托给谁。若调用 document_store.bm25_retrieval，就继续到该方法，不在包装器里寻找公式。把 query 如何分词、filters 如何组合、top_k 在哪里截断画成短调用链。每到一层，记录输入是否变化，尤其默认值、分数缩放与空结果处理。

最后构造一个负例，证明你理解了行为。例如把查询词改成单字符，观察 tokenizer 是否保留；把同一词重复两次，观察查询词频是否影响；给受限元数据，观察过滤发生在候选构造还是结果之后。不要根据课程实现猜框架一定相同，源码分析的价值就在于发现并解释差异。

阅读完成后关闭源码，口头解释一次调用。如果只能复述类名而不能说出数据在哪里存、分数在哪里算、过滤在哪里生效，说明还停留在 API 表面。回到最小例子，增加一条日志或断点，直到每一步都有实际观察。

## 小课二：路线一：Haystack，理解组件与检索边界

入口是 [BM25 Retriever](https://github.com/deepset-ai/haystack/blob/main/haystack/components/retrievers/in_memory/bm25_retriever.py) 与 [Document Store 概念](https://docs.haystack.deepset.ai/docs/document-store)。阅读时回答：Retriever 自己保存倒排统计吗，还是把检索工作委托给 store；过滤条件如何合并；返回对象包含哪些字段；top_k 在哪一层生效。

第一项任务：用本卷三个 cat/dog/fish 文档建立同规模实验，找到 Haystack 当前固定版本所用 BM25 变体与 tokenizer。不要预设分数必须和本卷相同；先解释公式、分词、长度和查询词处理差异，再比较排名。如果数值不一致但原因明确，这是成功的源码分析。

第二项任务：给一个文档添加受限元数据，分别测试初始化过滤与运行时过滤。写一个回归用例，确保合并策略没有把更严格的权限放宽。元数据过滤只是一种实现工具，调用者身份仍需要应用层确定。

第三项任务：建立摄入与查询两个 pipeline，故意连接错误类型的组件，观察框架在哪个阶段拒绝。将本卷手写函数接口与框架组件契约做对照，理解框架减少了什么样板代码，又引入哪些配置与序列化复杂度。

交付物是一页调用链说明、一个固定版本环境记录、三组对比输入输出和一个失败测试。不要把安装成功截图当作完成。


### Haystack 对照实验的完整验收逻辑

先固定三份文本，分别含 cache 两次、cache 一次与完全不同词。记录课程 BM25 的 tf、df、长度与分数，再在所选固定版本框架中运行相同文本。差异可能来自分词模式、BM25 变体、IDF 常数或归一化，不能只说框架更高级。找到每个差异对应的源码行或配置，再修改单一因素观察排名是否按预期变化。

过滤实验使用两个租户和一个类别字段。初始化过滤锁定租户，运行时过滤指定类别，预期结果是二者交集。若框架允许不同合并策略，应显式选择适合授权的策略，并在应用层保留不可放宽的租户条件。用户查询参数不能覆盖可信过滤，这是比某个具体参数名更稳定的原则。

组件管线实验可以故意把输出字段名接错，观察错误发生在构建、验证还是运行。再给类型正确但语义错误的字段，例如把文档 ID 当内容，框架类型检查可能通过，答案仍错误。这个对照说明框架契约只能覆盖它知道的结构，业务来源与权限仍需要你自己测试。

若准备修改源码，选择一个可限定行为，例如补充过滤合并测试或为空查询增加明确错误。先阅读项目贡献规则与已有测试风格，再写失败测试。不要为了课堂实验直接改远程 main，使用自己的分支或隔离 checkout；提交前检查 diff 只含目标变化与必要测试。

## 小课三：路线二：LlamaIndex，理解文档生命周期

入口是 [IngestionPipeline 源码](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/ingestion/pipeline.py) 与 [摄入文档](https://github.com/run-llama/llama_index/blob/main/docs/src/content/docs/framework/module_guides/loading/ingestion_pipeline/index.md)。重点跟踪 document、node、docstore、vector store、变换缓存之间的身份映射。

第一项任务：阅读重复文档检测与更新路径。列出哪些字段参与 hash，哪些状态需要持久化。再做“正文相同但元数据不同”“正文更新”“源文档删除”“同一 source_id 重试”四种实验，观察 docstore 与 vector store 是否一致。

第二项任务：插入一个自己的确定性变换，例如给段落补章节路径，但保持原始引用字段。比较变换前后 hash 与缓存命中，说明什么时候需要失效缓存。不要把源文本悄悄修改后继续声称原始 offset 正确。

第三项任务：实现一个小适配器，把本卷 CorpusStore 导出的可见 chunks 转成该框架的节点对象。保持 tenant、doc_id、revision、source span 字段。再把框架返回对象映射回 Claim，继续使用本卷引用检查。这个任务训练你在保留语义契约的前提下替换框架，而不是重写一遍不可验证应用。

交付物是数据模型对照表、四个生命周期测试、适配器代码和两个实际 bug/边界发现。若固定版本不提供你以为有的策略，就明确记录差异，不能编造参数。


### LlamaIndex 摄入账本的四个对象

Document 通常表示输入资料，Node 表示变换或切块后的检索单位，docstore 保存文档相关状态，vector store 保存向量与对应身份。名称在不同版本可能有细节变化，但你应追踪从源身份到派生节点再到向量 ID 的映射。只要有一层丢失源版本，更新删除就可能不完整。

先用纯文本与确定性切块，避免模型调用掩盖生命周期。第一次摄入后记录节点 ID 与缓存键；完全相同输入重跑，观察哪些变换复用；正文改一个词，观察哪些节点与向量重建；只改 metadata，观察指纹与缓存是否变化。预期不应由你对库的想象决定，而应由文档契约与实际源码共同解释。

删除实验更重要。移除源文档后，检查 docstore、node 列表、vector store 与查询结果，不只看其中一个。某些策略需要显式删除或特定管理配置，若默认没有自动同步，明确写出。库没有承诺的能力不能通过教程措辞补出来；应用需要增加清单、任务状态或补偿流程。

自定义变换应保存原始来源映射。给每段前面加章节标题会改变搜索文本，但引用 offset 若仍指原正文，必须有映射说明。可以把 search_text 与 source_text 分开，检索用增强文本，引用回原片段。这个模式能提高上下文信息而不伪造原文，是一个适合初学者完成的真实代码任务。

## 小课四：路线三：LangGraph，理解持久工作流与长期记忆

从 [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) 和 [Memory](https://docs.langchain.com/oss/python/concepts/memory) 开始。官方文档区分按 thread 保存图状态的 checkpointer 与跨 thread 的 store。这个区分正好对应本卷的“任务恢复状态”和“可复用知识”。

第一项任务：构造只有 search→validate→answer 的最小图。先使用内存 checkpointer，在同一进程暂停与恢复；再关闭进程，观察它不能提供真正磁盘持久性。换成当前版本支持的持久后端，再进行相同实验。记录模型调用和副作用是否重复。

第二项任务：用两个 thread_id 模拟两次会话，共享一个受控 owner 的长期 store，同时让短期消息互相隔离。再换另一个 owner，确认长期记忆不串线。不能只靠不同 thread_id 代替所有用户权限边界。

第三项任务：在记忆写入前设置人工确认点。对恢复路径进行故障注入，检查确认前后的操作会不会重放。把写入改成带幂等键或 CAS 的操作，并解释为何某些步骤必须可重试。不要把“框架支持 checkpoint”理解成任何外部副作用都会自动 exactly-once。

交付物是一段可重启的最小应用、两个会话隔离测试、一条副作用恢复轨迹，以及你能解释的状态更新规则。完成后再研究多 Agent 或更复杂动态图，避免直接陷入大量节点与 prompt。


### LangGraph 恢复实验的状态时间线

先用两个节点，一个执行只读搜索，一个验证引用。暂停点放在搜索结果提交之后，记录 checkpoint 中到底保存了 query、来源 ID、正文还是全部消息。恢复时检查搜索是否重复，以及最终验证是否重新读取当前来源。框架能恢复状态，不代表外部文档在暂停期间没有变化。

接着加入一条带副作用的记忆写入，在提交前、提交后但回执前、回执后分别模拟中断。三种位置有不同恢复语义，不能只测最容易的最后一种。业务写入与检查点不在同一事务时，必须使用幂等键、CAS 与执行回执；框架的节点重放可能重新执行函数，外部副作用需要应用设计。

两个 thread_id 用于区分两次运行，但不是用户权限证明。相同 owner 可以跨 thread 共享长期偏好，另一个 owner 必须隔离；如果仅换 thread 就共享了全部 store，需要检查命名空间与认证。把 thread、user、tenant、project 四个身份列成表，明确各自作用，避免一个字符串承担所有边界。

最后把内存后端换成持久后端，真正关闭进程再恢复。记录版本、后端配置与实际测试结果，不能因为类名包含 Saver 就假设磁盘持久化。官方持久化文档明确区分检查点与长期 store；具体后端与安装依赖以固定版本为准，课程不在未安装环境中编造运行成功。

## 小课五：路线四：Faiss 与 Sentence Transformers，真正理解检索性能

[Faiss 索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) 可用于选择 Flat、IVF、HNSW 或量化方案；[Sentence Transformers 重排示例](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) 展示编码与交叉重排的职责。

先做 CPU 的 1000–10000 条规模实验，数据使用公开授权或自建虚构材料。建立精确 Flat ground truth，再测近似索引的 Recall@k、构建耗时、搜索延迟和内存。单次计时噪声很大，应预热、重复、报告中位数或分位数，固定线程数与输入批量。不要在共享服务器上无界开启全部 CPU 线程。

对 embedding 模型建立任务级相关性标签，不能只测 ANN 近邻召回。对 reranker 测候选池大小 N 与最终 k：N 太小可能召回不足，太大可能增加延迟而收益有限。使用显卡时先单卡小 batch，明确一次实验时长与退出条件；本路线没有必须占满 8×H100 的理由。

交付物是一张两种召回指标的对照表、索引参数曲线、同分 tie-break 说明和模型版本记录。某次近似索引更慢也应如实解释，可能小规模下管理开销占主导。


### Faiss 与编码器实验如何避免指标混淆

先使用固定随机种子生成小矩阵，规范化文档与查询，建立 Flat 精确基线。再建立近似索引，比较返回 ID 与精确 top-k 的交集比例。这个实验隔离索引近似误差，不需要文本语义，也不需要下载模型。记录构建时间、搜索批量、线程数与重复次数，别用一次微秒计时下结论。

第二步换成真实文本 embedding，但保留相同 ANN 比较。第三步增加人工相关性标签，测 Recall、MRR 与 nDCG。这样能区分近似索引漏邻居、编码器语义排序差与问题标签不完整。若 ANN Recall 很高而问答差，应回编码与资料，不要继续调 efSearch 期待解决语义问题。

重排实验固定候选池，分别用原排序、词法教学重排与真实 cross-encoder。真实模型处理查询与文档对，不能把本卷 lexical_rerank 当同等实现。先确认模型训练所用任务、输入模板与最大长度，再观察候选 N 对延迟和质量的影响。正确证据没进候选池时，重排无法创造它。

个人显卡可以承担适度编码与重排批量实验，具体依赖与显存需求要按所选模型核查；H100适合需要更大批量或训练的有界实验。先单设备与小数据，避免占满共享服务器。性能报告必须写实际硬件、精度、批量与同步方式，否则数字无法比较。

## 小课六：路线五：Microsoft GraphRAG，读清索引与查询

入口为 [GraphRAG 文档](https://microsoft.github.io/graphrag/) 与 [原论文](https://arxiv.org/abs/2404.16130)。先区分实体关系抽取、社区组织、摘要生成、局部查询和全局查询。阅读源码时追踪数据表之间的 ID 和来源关系，而不只看最终回答函数。

第一项任务：用 12 份虚构文档做最小摄入，人工检查实体与关系抽取，标出同名、否定、条件和例外四类错误。第二项任务：比较局部事实问答与全局主题问答，分别定义验收标准。第三项任务：修改一份底层文档，追踪需要重建的派生对象以及费用。

真实模型调用可能产生成本，先阅读固定版本的配置与 dry-run 能力，明确调用预算。课程不提供会自动调用外部模型的大规模默认脚本，也不声称本次已执行该框架的 API 索引任务。这里的扩展是有具体输入、输出与验收的训练，不是把核心内容留到以后。


### GraphRAG 的源码任务要沿产物依赖走

从十二份虚构文档开始，先确认文本单元如何保留源身份，再看实体描述与关系如何聚合。挑一条同名实体，观察系统是否误合并；挑一条否定关系，检查是否抽成肯定；挑一条例外，检查社区报告是否保留。每个问题都回到原文，不只评价最终报告读起来顺不顺。

社区阶段记录成员、层级与生成配置。算法标签可能随重建改变，不把整数编号当永久主题身份。报告阶段追踪依赖来源与摘要配置，查询阶段分别观察局部邻域材料与全局 map/reduce 结果。把这些产物画成依赖图，修改一份来源后沿图标记需要重建的对象。

比较普通文本检索、人工主题分层、局部图扩展与社区报告，在相同问题与预算下测覆盖和支持。人工分层是组织上限，帮助判断自动社区是否值得；不使用图的基线也可能表现很好。若复杂方案只让答案变长却没有增加正确槽位，应该如实报告。

真实索引调用可能包括多轮抽取和摘要，因此先估算调用数与费用，设置并发和失败处理。默认离线代码验证不能替代这一真实运行。没有执行就标未执行，完成后保存实际模型、配置、日志与中间产物，才构成可复现源码研究。

## 小课七：追踪前沿时的判断框架

遇到新的记忆或检索论文，先标出它改变哪一层：表示、索引、查询策略、上下文选择、记忆写入、验证或评测。然后查基线是否同模型、同预算、同语料，是否只比较最弱的 naive RAG，是否统计更新与摄入成本，是否有权限、时效和冲突场景。

区分“能复现论文配置”和“适合你的任务”。某方法在长文档全局摘要上有效，不等于在错误码查找上有收益；某记忆算法在合成偏好任务上准确，不等于可以自动保存真实用户长期事实。把前沿结果转成自己小系统上的可检验假设，再决定是否深入。



### 把前沿主张写成可证伪假设

不要把“改进记忆”当一个可直接验证的结论。改写为具体假设，例如在有临时偏好与更正的任务中，新写入策略降低错误永久保存率，同时不降低明确保存召回；或在两跳依赖问题中，图扩展提高必需证据覆盖，在相同调用预算下仍有收益。明确输入、比较对象、指标与失败条件，实验才有方向。

然后设计最小反例。若方法依赖摘要，加入少数例外与来源撤回；若依赖图，加入同名实体与错误桥边；若依赖多轮搜索，加入无答案与重复查询；若依赖记忆，加入范围变化与遗忘重建。反例不是故意刁难，而是检查方法的核心假设在哪些条件下失效。

论文结果与工程保证要分开。平均准确率提高不代表授权安全，静态基准通过不代表删除一致，长对话任务成功不代表自动个人画像可靠。你可以认可论文在其设置下的贡献，同时保留应用需要补齐的契约。成熟判断不是全盘追捧或全盘否定，而是知道证据支持到哪里。

最终做一个小复现再决定深入。如果关键机制在你的数据上没有改善，保存失败分析；如果改善明显，继续扩大样本并检查成本与维护。不要因为论文很新就跳过强基线，也不要因为自己的小实现简单就默认不值得比较。

## 小课八：建立一个不会迷路的源码阅读记录

阅读记录不是抄文件树。选一条行为，例如输入三份文档后搜索 cache，写下入口函数、输入对象、存储调用、评分函数、输出对象与异常。每个节点附实际文件位置与固定 commit，记录你已经验证的事实和仍是猜测的部分。看到一个类名不理解时，先查它的构造与调用，不必立即读所有方法。

把静态阅读与动态运行交替进行。先预测某个函数的输入输出，再用最小脚本调用或断点观察；实际不符时沿调用链追踪。只看源码容易忽略默认配置与插件注册，只跑示例又容易把框架当黑盒。两种证据结合，才能知道行为由哪一层决定。

```python
import json
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class ReadingRecord:
    project: str
    revision: str
    question: str
    entrypoint: str
    observed_input: str
    observed_output: str
    invariant: str
    verification: str

record = ReadingRecord(
    "course-reference", "local-working-tree", "Where is access checked?",
    "CorpusStore.visible", "Context with no ops group", "restricted document absent",
    "Only current authorized chunks enter retrieval", "offline fixture executed")
encoded = json.dumps(asdict(record), ensure_ascii=False, indent=2)
assert json.loads(encoded)["verification"] == "offline fixture executed"
```

示例 revision 写 local-working-tree，诚实表示未绑定提交；真实开源阅读应填实际 SHA。不要为了表格完整编造四十位字符串。verification 区分源码阅读、运行确认、测试确认、未执行，未来回看时才知道哪些结论需要复查。记录格式可以简单，但证据状态必须清楚。

## 小课九：固定版本与环境，才能解释接口变化

仓库分支名 main 会移动，文档 latest 会更新，包版本也可能与源码 checkout 不一致。记录 `git rev-parse HEAD`、实际安装包版本、Python 版本、依赖锁与运行命令。若用 editable 安装，确认导入路径指向你的 checkout，而不是系统里另一份同名包。很多“改代码没生效”其实是 Python 导入了别的环境。

```bash
git rev-parse HEAD
python --version
python -m pip --version
python -m pip freeze
```

这些命令只读取环境，不自动升级依赖。不要在共享服务器全局环境随意 pip install 最新包；为每个源码项目使用独立虚拟环境，避免一个项目升级破坏另一个。Windows 与 Linux 的路径、可选二进制依赖可能不同，报告应注明实际系统，而不是把一台机器成功推断为所有平台成功。

对源码实验，先运行项目规定的最小测试，再改一处行为。若基线本来失败，记录原因，不能把后续失败都归给自己的改动。测试选择应与修改相关，之后按项目要求运行必要检查；不需要无界重复所有大型集成。真实 API、模型下载与 GPU 测试应显式启用，默认离线基线保持可复现。

## 小课十：从公开 API 追到真正执行层

框架公开接口往往只是包装：Retriever.run 可能委托 DocumentStore，Pipeline 负责参数路由，组件装饰器负责 schema，底层索引负责评分。沿调用链时每一层问三件事：新增了什么默认值，改变了什么数据，在哪里执行实际计算。不要把包装器里没有 BM25 公式误判为项目没实现检索。

使用 `rg` 搜符号定义与调用，先找 def 或 class，再找同名方法的具体实现。协议与抽象基类可能定义接口，真正对象由配置或工厂创建。阅读构造函数和依赖注入能确定运行时类型。遇到装饰器，检查它是否修改函数签名、注册组件或包装返回值，不必把所有魔法都当不可理解。

动态观察可以在小脚本中打印 type、模块路径与关键字段，或使用调试器逐步进入。避免在大数据或真实 API 上逐行停顿，先用三份虚构文档。日志只输出必要结构，不打印密钥与私有正文。最小输入使你能手算预期，源码中的每次变换才有参照。

## 小课十一：写一个会失败的行为测试

一个有价值的源码修改从具体触发开始。例如初始化过滤要求 tenant A，运行时过滤只指定 category，错误合并策略可能覆盖 tenant 条件。先写最小测试证明受限文档被返回，再修改合并逻辑，最后确认合法结果仍存在。不能只改参数后观察答案似乎更好，这样难以证明解决了什么。

失败测试应断言外部行为与关键不变量，不机械复制实现步骤。若测试只检查某个内部函数被调用一次，重构可能让它失败却不影响行为；若测试只检查输出非空，权限泄露也可能通过。对过滤、版本、删除、重复文档和恢复，写正反成对例子最有效。

提交 diff 时解释触发、原行为、新行为与验证。不要把大量无关格式化混入小修复，也不要在不了解项目约定时重写整个模块。小而清楚的改动更容易审查，也更适合训练你理解真实调用链。源码阅读的目标是能预测并修改行为，不是累计看过多少文件。

## 小课十二：把论文公式翻译成最小程序

读论文先找对象与符号。查询、文档、向量、排名、图节点、记忆槽分别是什么，矩阵形状如何，优化目标的分母与范围是什么。把每个符号写成一个小数组或字典，用两三条样本手算。若连最小例子都无法对应，直接复现大实验通常只会得到一堆无法解释的日志。

再找方法相对基线改变哪一层。新的检索策略可能只改 query rewriting，新的记忆方法可能改写入选择，新的 GraphRAG 可能改社区或查询规划。不要因为论文标题包含 Agent 就假设它解决所有 Agent 可靠性问题。把变化映射到本卷数据流，明确需要替换的接口与保持的不变量。

最小程序应先验证数学关系，再讨论质量。例如新融合公式先在三条排名上手算，确认权重与归一化；新记忆评分先检查时间边界与范围；新图扩展先用一个环和一个同名实体。大规模指标无法替代这些基本正确性检查，尤其论文代码也可能存在与文字不同的默认行为。

## 小课十三：前沿评价的八个问题

第一，比较是否使用同一基础模型；第二，总调用与 token 预算是否相近；第三，语料与标注是否一致；第四，是否包含强关键词、混合检索与重排基线；第五，是否统计摄入与更新成本；第六，是否测不可回答、权限、时效与冲突；第七，是否有重复试验或不确定性；第八，结论是否超出数据集范围。八个问题帮助你把新方法转成可检验主张。

如果一种方法多调用模型十次，提升可能来自更多计算而非特定结构；如果基线没有重排，改善可能只是更好候选选择；如果语料静态，不能推断增量更新可靠；如果记忆任务只用合成无冲突偏好，不能推断真实长期画像安全。指出这些限制不是否定研究，而是准确理解证据支持到哪里。

复现实验可以先做受控消融：固定其他层，只替换论文关键机制，记录成功与失败类别。若资源有限，选择最能区分假设的小数据，而不是缩小所有东西后得到无意义结果。你的 Win11 机器适合逻辑与小规模索引，Linux CPU 适合批量数据处理，H100用于确有训练或大模型计算需要的有限实验，不必为了显得前沿占满八卡。

## 小课十四：十二道源码与论文练习的完整答案

**练习一，记录版本。** 在实际 checkout 执行 git rev-parse HEAD，把输出原样保存，再记录包版本与导入路径。没有运行就写未固定，不编造 SHA。分支名与日期不能代替提交身份。

**练习二，找到 BM25 真正执行层。** 本次重新读取 Haystack 在线源码得到的具体链是：`haystack/components/retrievers/in_memory/bm25_retriever.py` 中 `InMemoryBM25Retriever.run` 先调用 `apply_filter_policy`、解析 `top_k` 与 `scale_score`，再委托 `self.document_store.bm25_retrieval`。接着进入 [`haystack/document_stores/in_memory/document_store.py`](https://github.com/deepset-ai/haystack/blob/main/haystack/document_stores/in_memory/document_store.py) 的 `InMemoryDocumentStore.bm25_retrieval`：组合内容与调用方过滤，调用 `filter_documents`，把候选交给 `bm25_algorithm_inst`，再排序、截断并生成带分数的 Document。`_dispatch_bm25` 将配置映射到 `_score_bm25okapi`、`_score_bm25l` 或 `_score_bm25plus`；`_tokenize_bm25` 负责小写和 NFC 规范化后的词元处理。写入路径 `write_documents` 更新 `_bm25_attr`、`_freq_vocab_for_idf` 与 `_avg_doc_len`。因此公式不在 Retriever 包装层，统计也不由每次查询重新从候选全文建立。上述是 2026-11-01 在线源码阅读证据，未安装运行；你的 checkout 仍须记录 SHA 后逐符号复核。

**练习三，解释分数不一致。** 同一三文档语料在课程与框架分数不同，检查 tokenizer、BM25 变体、IDF、查询重复词、长度归一化与是否缩放。先解释差异，再比较排名与标签，不要求所有实现数字相同。

**练习四，过滤合并。** 初始 tenant 限制与运行时 category 条件应按产品契约组合，不能无意覆盖授权范围。完整验收含合法匹配、同类别另一租户、当前租户错误类别三条，要求只返回第一条。框架过滤是工具，认证仍由应用负责。

**练习五，摄入四变体。** 以下给出应用要求的参考状态表，初始资料为 d1、revision=1、正文“缓存容量四页”、权限 tenant A、派生节点 n1。它是我们希望适配器维持的合同，不能被写成未运行的 LlamaIndex 版本已经提供这些行为。你的实验需在另一列填实际观察；不满足时由适配层补齐或明确拒绝采用。

| 变体 | 文档与节点的期望 | 向量与缓存的期望 | 必须成立的断言 |
|---|---|---|---|
| 完全相同正文、元数据与摄入配置重试 | d1/r1 与已有节点身份保持，不生成重复可见节点 | 已有兼容向量可复用；变换缓存可命中 | 可见节点 ID 集合与重试前相等，数量不增加 |
| 正文改成“缓存容量八页” | 当前版本推进，旧正文节点退出当前可见集合；保留历史可审计身份 | 对改变的搜索文本重算向量；依赖旧内容的答案缓存失效 | 当前检索不返回“四页”，旧 r1 引用不能冒充当前有效证据 |
| 正文相同、权限由 A 改为 B | 权限元数据版本更新；A 失去可见性，B 按合同获得访问 | 若权限不进入编码文本，向量数值可复用；权限与答案缓存必须更新 | A 的查询为空，B 可查到；不能因 embedding 缓存命中跳过授权更新 |
| 删除来源 d1 | 当前文档与派生节点不可检索，删除版本或墓碑保留防旧任务复活 | 对应向量删除或可靠过滤；派生摘要与答案缓存失效 | 搜索不返回 d1，旧引用失效；迟到 r1 摄入任务不能恢复当前资料 |

这里元数据更新特意区分“向量是否需要重算”与“权限是否必须更新”。若元数据也被拼进 embedding 输入，编码指纹改变就需要重算；若只是可信过滤字段，数值可能保持，但授权状态仍必须更新。测试应分别读取节点 ID、版本、向量身份和查询可见性，而不是只用最终答案是否包含某个词判断。

**练习六，offset 保真。** 自定义变换给文本加标题后，原始 offset 不能继续指向新字符串同位置。保留源映射或明确新文本坐标系，并使引用回原文可验证。不能把变换后文本称为原文精确摘录。

**练习七，内存检查点。** 同进程恢复成功不证明重启持久化。关闭进程后内存 saver 丢失是预期；持久后端需要独立实验。长期 store 与 thread 状态不同，两个 owner 的长期数据仍要隔离。

**练习八，ANN 与语义召回。** Flat 精确近邻作为 ANN 金标，相关性标签作为语义金标。两张指标表分别报告，不能用高 ANN Recall 证明问答正确。查询与文档规范化方式必须一致。

**练习九，重排上限。** 正确证据不在候选池，cross-encoder 无法恢复。先测候选 Recall，再测重排 nDCG 与最终支持。扩大候选池同时增加成本，固定预算比较才能判断收益。

**练习十，GraphRAG 更新。** 修改一份原文，追踪实体关系、社区、报告、向量与答案缓存依赖。实际未重建的对象标未验证，不能因为一次 query 成功就声称增量一致。R11 的依赖失效函数提供最小参考契约。

**练习十一，论文消融。** 把新方法映射到一层接口，固定模型、语料、预算，比较有无该机制。报告至少一个改善与一个失败反例，说明是否有额外计算或数据泄漏。只翻译摘要不算完成。

**练习十二，迁移回个人系统。** 用适配器替换一个组件，保留 ACL、旧引用、CAS、删除重建、TTL 与未知 usage 测试。先证明语义契约不退化，再评估质量与性能。框架名字改变不应抹掉已验证边界。

## 小课十五：形成可持续的源码研究作品集

每个项目保留一个小问题、一条调用链、一个最小复现、一个可审查 diff、一份测试证据和一段结论。作品不必很大，但应让别人能重现。连续完成五个这样的任务，比收藏五十个仓库更能训练代码级能力。你会逐渐发现相同模式在不同框架重复出现：身份映射、缓存指纹、过滤、状态提交、错误分类与来源传播。

阅读前沿保持一份假设清单：方法声称改善什么，你的任务是否有同样瓶颈，最小实验怎样区分它与简单替代方案，成本与维护如何变化。通过实验后再纳入个人系统，失败也保存原因。拒绝一个不适合当前任务的方法，是有证据的工程判断，不是落后。

本章的官方入口在二零二六年十一月一日重新核查，包括 Haystack 检索器、LlamaIndex 摄入、LangGraph 持久化、Sentence Transformers 检索重排与 GraphRAG 文档。网页与 main 仍会变化，具体实验必须记录实际安装与提交。本次教材不声称已下载运行所有外部框架，也不把未执行的 API 或 GPU 结果写成成功。

### 完整的小改动练习：不可放宽的授权过滤

为了把源码阅读变成可执行技能，先独立实现一个过滤组合器。可信条件来自运行器，不可信附加条件来自用户查询。两者应取交集，而不是用字典 update 让后者覆盖前者。下面用最小等值条件表达，避免依赖某个框架版本；接入真实框架时再转换为其过滤 AST。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Equals:
    field: str
    value: str


def matches(row, conditions):
    return all(row.get(condition.field) == condition.value for condition in conditions)


def authorized_filter(rows, trusted_conditions, requested_conditions):
    conditions = tuple(trusted_conditions) + tuple(requested_conditions)
    return [row for row in rows if matches(row, conditions)]

rows = [
    {"id": "a", "tenant": "A", "category": "guide"},
    {"id": "b", "tenant": "B", "category": "guide"},
    {"id": "c", "tenant": "A", "category": "notes"},
]
trusted = [Equals("tenant", "A")]
assert [row["id"] for row in authorized_filter(rows, trusted, [Equals("category", "guide")])] == ["a"]
assert authorized_filter(rows, trusted, [Equals("tenant", "B")]) == []
assert trusted == [Equals("tenant", "A")]
```

第二个断言故意请求另一租户，两个相互矛盾条件使结果为空，不能覆盖可信租户。第三个断言证明组合没有修改原列表。真实系统的权限条件可能更复杂，但不可放宽的交集语义仍适用。若框架提供 replace 或 merge 策略，你需要找到它们实际怎样处理同名字段与布尔条件，不能只看参数名字猜测。

把这个练习迁移到 Haystack 或其他框架时，先写一个适配函数，把 Equals 列表转换为框架过滤结构，再用同样三条资料测试。你的交付是适配代码、固定版本与实际输出，而不是声称某个在线文档永远保持同一 JSON 格式。这样既有完整参考逻辑，也保留版本变化的诚实边界。

### 完整的小改动练习：来源字段不能在适配中丢失

外部框架返回文档对象时，你需要把它转换回课程证据结构。最低要求是稳定来源 ID、逻辑文档 ID、revision、原文与分数类型。若 metadata 缺少版本，不能默认填一，因为那会让更新后的来源伪装成初版。应拒绝或标为无法满足当前引用契约，让摄入适配器补齐字段。

```python
def normalize_external_result(result):
    metadata = result.get("metadata", {})
    required = {"chunk_id", "doc_id", "revision"}
    if not required <= set(metadata):
        raise ValueError("missing provenance metadata")
    if type(metadata["revision"]) is not int or metadata["revision"] < 1:
        raise ValueError("invalid revision")
    content = result.get("content")
    if not isinstance(content, str):
        raise ValueError("content required")
    return {"source_id": metadata["chunk_id"], "doc_id": metadata["doc_id"],
            "revision": metadata["revision"], "text": content,
            "score": result.get("score"), "score_type": result.get("score_type", "unspecified")}

external = {"content": "fictional source", "score": 0.8, "score_type": "cosine",
            "metadata": {"chunk_id": "c1", "doc_id": "d1", "revision": 2}}
assert normalize_external_result(external)["revision"] == 2
try:
    normalize_external_result({"content": "lost metadata"})
except ValueError:
    pass
else:
    raise AssertionError("provenance silently invented")
```

这个适配器不检查当前授权，调用者仍需通过 CorpusStore 或可信来源服务复核。score 为 unspecified 时不能当概率解释，也不能与 BM25 直接相加。适配的目标不是让所有对象勉强塞进同一字典，而是保持语义与暴露缺失。必要字段缺失时明确失败，比填默认值制造假确定性更可靠。

### 一篇论文的完整阅读报告模板

报告开头用一句话说明具体问题与方法改变的层，例如“通过按缺口选择下一查询，改善多跳证据获取”。随后写输入输出与关键公式，给一个两文档手算例子。再列与基线不同的唯一机制、实验模型与预算、数据范围、评价指标、主要结果和已知失败。最后写你自己的最小复现与反例，不需要逐段翻译论文。

如果论文代码与公式不一致，先确认版本、默认配置与实验脚本，再提出问题。可能是符号简化、实现优化、文档过时或真实缺陷，不能看到一处差异就断言作者错误。用最小输入比较行为，记录具体差异与证据。研究阅读同样需要校准，不把怀疑写成事实。

复现失败时记录环境、数据处理、随机种子、模型版本与预算。没有拿到完全相同商业模型或数据时，说明是近似复现，不伪造原结果。你的目标是理解机制与适用条件，诚实的负结果也能指导个人工程选择。

每条路线至少完成一个真实改动或故障复现，再进入下一条。若发现 Python 基础不足，回基础卷补生成器、装饰器、上下文管理器或异步，不必把暂时看不懂归因于自己不适合。框架代码由普通数据结构、函数与状态组成，复杂性可以逐层拆开。持续积累可运行小实验，会比只看高层架构图更快形成深入理解。
