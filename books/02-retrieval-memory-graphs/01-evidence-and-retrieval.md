# R01 从“找一段文字”到可验证的知识系统

本章先修是 Python 的列表、字典、函数、文件，以及“调用模型并不等于调用数据库”的认识。全部实验在普通 CPU 上完成，不需要模型 API、显卡或联网。完成后，你应能给一个问答错误定位到语料、检索、上下文、生成或引用，而不再笼统地说“模型不够聪明”。

本章不假设你已经知道“检索”“相关”“证据”是什么意思，而是用同一个小系统把它们拆开。请创建一张实验记录表，列出输入、预期输出、实际输出和解释。读到一个函数时，先用纸写它接受什么、返回什么，再看实现。这样你学习的不是某个库的调用顺序，而是可以迁移到不同框架的推理过程。

## 小课一：先说清用户究竟缺少什么信息

假设你的资料库有三份课程笔记。第一份讲“KV cache 保存已经计算过的 key 和 value”；第二份讲“更长的上下文通常需要更多 KV 存储”；第三份讲“某个教学程序在 CPU 上模拟分页”。用户问：“我的服务为什么会显存不足？”这不是一句包含关键词的字符串那么简单。它背后有一个信息需求：用户想知道当前故障的原因，以及怎样验证和处理原因。仅返回一段出现“显存”的文档，未必满足这个需求。

把信息需求写成可判断的形式，是开发检索系统的第一步。这里至少缺少模型大小、数据类型、当前上下文长度、同时运行的请求数、显存中还放了什么、错误发生在哪个阶段。资料库可能只能解释概念，不能观察用户机器。你应该把“能够解释容量因素”与“能够确认这次故障原因”拆成两个能力。没有运行时数据时，系统可以列出候选原因和检查方法，却不能把一般规律写成已经确认的现场结论。

再看一个更窄的问题：“课程笔记中，KV cache 保存哪两个量？”这个问题有清楚的答案范围，第一份资料足够支撑。两种问题都含“KV”，但所需的证据结构完全不同。前者需要多项现场观测与机制解释，后者需要一条直接定义。这就是为什么实际查询系统不能仅凭词命中数量决定“已经回答完成”。命中是候选材料，完成是相对于任务要求的判断。

开发时可以把一个需求写成四个字段：主题是什么，问的属性是什么，适用条件是什么，希望输出什么形式。对于“比较两个版本的分页行为”，主题是分页系统，属性是共享或分配行为，条件是明确的两个版本，输出可能是差异表。若漏掉版本条件，检索到另一版本的资料即使主题高度相关，也可能回答错误。以后看到检索器只接受一个 query 字符串，不要忘了：字符串之外仍然有这些任务约束。

你不必一开始就用模型提取这四个字段。手工写十个问题并标注它们，往往比马上实现复杂查询规划更有帮助。你会看到哪些问题能用单条证据回答，哪些问题要求多条证据共同满足，哪些问题在当前资料范围内根本不可回答。这个小标注集会成为后续评测的种子，而不是做完系统后才临时挑选好看的演示问题。

## 小课二：一个字符串经过系统时会变成哪些对象

初学者容易把“文档”看成一个字符串，但系统中至少存在原始文件、解析后的正文、切出的片段、索引条目、检索命中、上下文材料和回答断言。它们可以共享部分内容，却不是同一个对象。原始 PDF 有页码和排版，解析正文可能只有文字；片段有字符起止位置；索引条目包含词项或向量；命中对象附带排名分数；回答断言需要引用。这些转换如果没有记录，最后就很难证明某句话从哪里来。

举一个极小例子。原文是“缓存保存历史键和值。缓存可减少重复计算。”。假设切成两块，第一块是字符区间 `[0,11)`，第二块从后面开始。区间使用左闭右开约定：包含 start，不包含 end。因此长度应当满足 `len(text[start:end]) == end-start`。你可以直接在 Python 中打印每个字符的序号验证，而不是凭视觉数标点。字符偏移不是 UTF-8 字节偏移；一个中文字符通常占多个字节，不能把两者混用。

索引条目随后可能保存“缓”“存”“保”“存”等词项，也可能保存一个几十或几百维的浮点向量。索引不是原文的同义词。仅保留向量后，你不能从任意向量精确恢复原文；仅保留词频也丢失了原词序。因而一个可以给出可核对引用的系统通常仍需保存或定位原始正文。向量库中存了 metadata，并不自动保证这些 metadata 包含正确的版本、来源和偏移。

一次命中可以表示为“片段 C，分数 0.63”。这里的 0.63 只在所选算法、数据预处理和候选集合下有意义。它不是“这段话有百分之六十三的概率为真”，也不是“模型会有百分之六十三的把握回答正确”。如果你将分数显示成置信度，却没有做相应标定，就给用户制造了一个没有依据的概率解释。

回答断言又是另一层。例如“缓存必然使显存下降”这句话即使引用了“缓存减少重复计算”，仍然没有得到支持，因为减少计算与减少存储不是同一属性。把命中原文交给生成模型，不能自动补上这个逻辑缺口。后面的 R06 将把来源存在、引用精确、断言被支持和来源真实分开验证；本章先建立这些对象之间的边界。

## 小课三：用一份可以手工检查的数据开始

不要第一次实验就导入几千篇网页。先用四条虚构记录，确保你能把每条内容完整读完。小数据不是因为真实系统简单，而是因为第一次调试时你需要知道“正确结果应该是什么”。如果你都不知道语料里有哪些句子，就无法判断检索错在算法、数据还是自己的预期。

```python
records = [
    {"id": "d1", "text": "kv cache stores keys and values"},
    {"id": "d2", "text": "long context increases kv storage"},
    {"id": "d3", "text": "a cpu simulator is not a gpu benchmark"},
    {"id": "d4", "text": "cache invalidation follows document revisions"},
]

query = "kv cache"
query_terms = set(query.lower().split())
scored = []
for record in records:
    document_terms = set(record["text"].lower().split())
    score = len(query_terms & document_terms)
    if score > 0:
        scored.append((score, record["id"], record["text"]))
scored.sort(key=lambda row: (-row[0], row[1]))
print(scored)
```

逐行读这段程序。`records` 是列表，列表里的每一项是一个字典；字典用 id 和 text 两个键区分身份与内容。查询先变成小写，再按空白切开，最后放进集合。集合去掉重复词，所以查询写两次 cache 不会获得两次权重。这个选择并非所有检索算法都必须采用，而是我们此刻明确规定的行为。

循环每次处理一条记录。`query_terms & document_terms` 是集合交集：只保留两边都有的词。`len` 数交集元素个数。d1 同时包含 kv 和 cache，得二分；d2 只有 kv，得一分；d4 只有 cache，也得一分；d3 得零分而被过滤。排序键中负号让较高分数排在前面，第二项 id 则规定同分时的顺序。没有这一项也能得到某种顺序，但若数据来源顺序变化，你的演示输出可能跟着变化。

现在改查询为“keys values”。d1 得二分，其余为零。再改为“history memory”。即使你凭语义觉得 d1 相关，程序仍然返回空。原因很明确：它只比较字面词项，没有任何同义词知识。你不能因为函数名叫 search 就假设它理解了语言，也不能把空结果直接解释成“世界上没有这类知识”。它只说明在当前表示和当前规则下没有正分候选。

这个最小检索器虽然粗糙，却已经有可以讨论的接口契约：输入是一个字符串和一组记录；输出是按得分与身份排序的正分候选；大小写被忽略；重复查询词被去重；词序被忽略；零分项不返回；同分顺序稳定。请把这些写成测试，而不是让它们隐藏在实现里。下一章和 BM25 章节会逐步替换其中的部件，但这个“先明确行为，再写算法”的方法不变。

## 小课四：相关性不是一个永远固定的标签

同一条资料对不同问题的相关程度不同。“长上下文增加 KV 存储”对“为什么上下文变长后显存紧张”高度相关，对“KV cache 保存什么”只是间接背景，对“如何配置某个版本的命令行参数”可能完全不足。相关性依赖问题与任务，不是文档自身永远携带的属性。

实际标注还常常有多个级别。例如三级表示直接包含所需答案，二级表示能支持关键解释，一级表示主题相关但不能回答，零级表示无关。这种分级比简单的相关或不相关更适合比较一个排在前面的完整答案和一篇只提到关键词的背景材料。不过，级别必须先写清定义，否则两个标注者可能把“主题相关”与“回答充分”混为一谈。

设问题是“缓存什么情况下必须失效”。d4 直接提到文档版本变化，可能是三级；d1 只讲缓存内容，可能是一级；d2 讲存储开销，可能为零级。若你的标签定义仅看是否出现 cache，d1 与 d4 就会被当成同等相关，评测可能奖励一个事实上没有回答问题的检索器。建立评测集时，最重要的不是一次收集多少题，而是标签是否对应真实任务需要。

相关性还包含条件约束。某文档对旧版系统准确，对新版系统失效；某文档适用于 CUDA 张量，对 CPU 模拟器不适用；某操作说明要求管理员权限，而用户只有普通账户。你可以把条件写成过滤字段，也可以在重排或回答时检查，但不能在任何层都忽略它。高语义相似度无法补偿版本、硬件或权限不匹配。

当一个问题需要两条证据组合时，“每条单独都不完整”不等于“都无关”。例如 A 说明模块 X 依赖 Y，B 说明 Y 需要某配置，组合起来才能解释 X 的限制。此时你需要标注答案所需的证据集合，而不只是一个唯一正确文档。后面的多跳检索和图章节会继续这个例子。当前先记住：把所有任务压成“有没有命中一个标准 ID”会丢失一部分重要能力。

## 小课五：从线性扫描走向索引，究竟省了什么

上面的程序每次查询都遍历全部记录，并对每条正文重新切词。若有 N 条文档，每条平均 L 个词，那么一次查询至少要重新读大约 N×L 个词。N 很小时这样最清楚；N 很大时，你会反复做与当前查询无关的工作。

索引的基本思想是把一部分重复工作提前完成。倒排索引为每个词保存“哪些文档包含它”。例如 kv 对应 d1、d2，cache 对应 d1、d4。查询 kv cache 时，可以直接找这两个词的列表，不必重新扫描 d3 的全部文本。这里提前建索引消耗了时间和额外存储，换来查询时更少的工作。不是所有优化都免费，也不是用了索引就不需要更新和一致性管理。

```python
from collections import defaultdict

postings = defaultdict(set)
for record in records:
    for term in set(record["text"].lower().split()):
        postings[term].add(record["id"])

candidates = set()
for term in query_terms:
    candidates.update(postings.get(term, set()))
print(sorted(candidates))
```

`defaultdict(set)` 的意思是：当首次访问某个不存在的键时，为它创建一个空集合。每个文档内部先去重，所以同一个词出现五次也只把文档 ID 加入一次。这样的列表能回答“有没有出现”，却不能直接回答“出现几次”。BM25 需要词频，因此后面会把集合扩成保存词频的映射。你应根据算法需求决定存什么，而不是看到“倒排索引”就认为只有一种固定结构。

最后的候选集合是各词命中文档的并集，表示满足任意一个词即可。若改成交集，就表示必须包含所有查询词。这两种策略各有用途：并集保留更多可能相关的候选，交集可能更精确但容易漏掉不使用同样措辞的材料。特别是第一个词不存在时，交集会变空；正确实现不能把“还没初始化集合”和“已经确定无候选”混为一谈。

建立索引以后，再修改原文，会发生什么？如果只改 records 而不改 postings，系统就出现两个版本的事实：正文说一个内容，索引仍按旧内容查找。你可能检索到已经不含查询词的文档，也可能漏掉刚加入的新词。这不是“模型幻觉”，而是数据系统的一致性问题。到 R08 我们会用版本与事务处理它；现在先通过一次手工修改观察这个故障。

## 小课六：检索命中、回答支持与事实真实性要分别检查

考虑一份虚构资料写着“教学设备 Z 有一千张显卡”。检索器可以正确命中它，引用器可以精确复制原文，生成模型也可以忠实总结。整条技术链都按输入工作，但原始资料可能是错误的。因而“引用真实存在”不能等同于“引用的事实真实”。建立来源层级、观察资料发布主体和上下文，是另外一项工作。

再考虑一个反向例子：资料准确写着“某实验只运行了 CPU”。回答却写“已经在 H100 验证通过”，并附上这份资料的链接。链接能打开，文档主题相关，但断言不被支持。这种问题不能靠检查 URL 是否存在解决。你必须比较断言与证据具体说了什么，包括否定词、数值、条件、时间和范围。

把验证拆成四问非常有用。第一，当前调用者是否允许读这条来源？第二，这条来源是否仍是当前有效版本？第三，引文是否确实存在于来源中？第四，回答断言是否由这段引文支持？若还需要判断现实世界真伪，再增加来源可靠性和交叉验证。每一问都可能独立失败，错误报告应指出是哪一层，而不是统一返回“回答质量差”。

课程初期采用严格抽取式回答，就是为了先把前三层与最简单的第四层做清楚。回答断言必须等于引文原文，不进行自由改写。这种模式表达能力有限，却容易检查。它并不保证原文真实，也不保证挑出的句子充分回答了问题。我们明确保留这个边界，避免把一个可以机械验证的子问题夸大成通用事实验证器。

当你以后接入模型做综合回答，仍然保留这些层。模型可以提出一个候选断言和一组引用，系统再检查来源权限、版本、引文位置以及支持关系。对于无法可靠自动判断的语义支持，可以保留待复核状态或要求用户查看原文。最重要的是不要把所有检查都外包给一次“请确保答案正确”的提示词，因为提示词不能替代数据身份和权限状态。

## 小课七：用失败树定位问题，而不是一出错就换模型

一个回答错误，至少可能来自六个位置。资料库没有所需内容，是资料覆盖问题；内容有但解析丢失，是摄入问题；切块把关键条件拆散，是切块问题；相关块未进入候选集，是召回问题；进入候选却没放进上下文，是排序或预算问题；证据完整但回答扭曲了含义，是生成或验证问题。它们都可能表现成“最终回答不对”，但修复手段完全不同。

诊断时按数据流检查。先在原始资料中确认答案确实存在，再看解析正文是否保留，再看切块列表和偏移，再看召回候选，再看排序和打包结果，最后才看模型输入与输出。这个顺序能减少盲目调参。如果正确段落根本没进入模型上下文，修改 temperature 通常不能解决真正的问题；如果已经进入，却被回答忽略，扩大向量库候选数也可能只是增加噪声。

你可以为一次请求记录一条 trace：query、身份上下文、索引版本、候选 ID 与分数、被保留的片段、实际序列化上下文、最终引用 ID、停止原因。trace 不应默认包含密钥或全部私有正文；开发环境用虚构数据时可以记录更多内容，真实环境需要按数据治理规则决定。记录不是为了“什么都存”，而是为了让关键转换可重建。

给每个阶段设置一个小断言也很有效。切块后检查每个片段等于原文对应切片；候选返回前检查可见性；打包后检查实际预算；回答前检查引用当前有效。这样故障会在靠近根因的位置暴露。若只在最后检查字符串里有没有答案词，一些严重错误可能被最终偶然正确的文字遮住。

例如问“缓存保存什么”，模型不依赖资料也可能凭预训练回答正确。这个结果不能证明检索系统工作。为了验证检索链，你应使用虚构而有明确定义的事实，例如“课程项目代号青石的缓存上限为七项”，然后在资料里修改为九项，观察回答是否跟随当前版本。如果模型仍答七项，你就得到了一个很有诊断价值的反例。

## 小课八：把实验结果变成可以比较的证据

假设系统甲对十个问题答对八个，系统乙也答对八个。这个总数没有告诉你它们是不是在同八个问题上成功，也没有告诉你错误有多严重。甲可能漏掉两道冷门定义，乙可能把两条无权限资料返回给用户。仅比较一个平均数会掩盖这种差别。设计实验时先保留逐题结果，再汇总，不能只保存最终百分比。

为每题建立一行数据：问题 ID、资料快照、允许的来源、需要的证据、检索结果、回答状态、错误类别。问题 ID 必须稳定，否则你无法把改动前后同一道题对齐。资料快照也必须一致，否则一个系统多拿到了一篇新资料，另一个没有，你就不能把结果差异全归因于检索算法。

第一次基准不必很大，可以只有十二题，但要覆盖不同机制。三题直接定义，三题同义表达，两题需要两个证据，一题无答案，一题旧版与新版冲突，一题权限隔离，一题资料中包含诱导系统越权的文字。这些不是把所有测试混成一个分数，而是让你明确当前系统的责任范围。每次修改后看哪类问题改善、哪类退步，才能知道优化是否符合目标。

对于本章最小词项检索器，你可以先定义检索成功为“期望的文档进入前三”。这只是一个清楚的阶段指标，不是最终答案质量。到了 R05，我们会把排序位置、多个相关资料、分级相关性以及逐题差值都纳入评价。现在不需要背所有指标名字，但要学会为每个数字写出分子、分母和适用范围。

还要区分检索质量与索引近似误差。若一个近似向量索引返回了精确向量搜索的同样邻居，说明近似算法没有额外损失这些近邻；若这些邻居本身与问题不相关，语义检索仍然失败。一个指标测的是“有没有找到算法定义下的最近点”，另一个测的是“有没有找到任务需要的证据”。这两个问题有不同的标准答案，不能使用同一个 recall 名称就认为它们完全相同。

## 小课九：一个从输入到回答的最小工程

下面把检索结果变成可引用的数据，不接外部模型。这个程序刻意让回答保持抽取式，以便你逐行检查所有变化。请先运行，再修改一条记录的内容，最后增加一个查不到答案的问题。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Record:
    id: str
    revision: int
    text: str

@dataclass(frozen=True)
class Extract:
    text: str
    source_id: str
    source_revision: int


def retrieve(query, corpus, k=2):
    terms = set(query.lower().split())
    pairs = []
    for record in corpus:
        overlap = terms & set(record.text.lower().split())
        if overlap:
            pairs.append((len(overlap), record))
    pairs.sort(key=lambda item: (-item[0], item[1].id))
    return [record for _, record in pairs[:k]]


def answer(query, corpus):
    hits = retrieve(query, corpus)
    extracts = [Extract(hit.text, hit.id, hit.revision) for hit in hits]
    return {"abstain": not extracts, "claims": extracts}


def validate(extract, corpus):
    current = {record.id: record for record in corpus}
    source = current.get(extract.source_id)
    return (source is not None
            and source.revision == extract.source_revision
            and source.text == extract.text)


corpus = [
    Record("alpha", 1, "jade cache capacity is seven"),
    Record("beta", 1, "jade cache stores keys and values"),
]
report = answer("jade capacity", corpus)
assert not report["abstain"]
assert all(validate(claim, corpus) for claim in report["claims"])
old_claim = report["claims"][0]
updated = [Record("alpha", 2, "jade cache capacity is nine"), corpus[1]]
assert not validate(old_claim, updated)
assert answer("unrelated zebra", corpus)["abstain"]
print(report)
```

两个数据类让“来源记录”和“回答抽取”拥有不同类型。`frozen=True` 阻止正常属性赋值，帮助你避免在构造回答后随手改写来源对象；它不是数据库事务，也不是安全隔离机制。`revision` 保存版本，目的是让验证器能发现“同一个来源 ID 已经换了正文”。如果只比较 ID，旧回答会在更新后继续被当作当前证据。

`retrieve` 中的 `pairs` 保存分数与记录，排序以后才去掉分数。这说明排序所需的临时信息可以与最终接口返回内容不同。`answer` 不会生成新的事实，它只是将命中的正文连同身份包装成 Extract。`validate` 每次依据传入的当前语料构建映射，因此它会读到修订后的记录，而不是永远相信旧的对象引用。

最后四个断言分别验证正常回答、引用有效性、修订后旧引用失效，以及无候选时拒答。注意“查询命中 alpha 但也可能命中 beta”这一点：当前检索器没有理解 capacity 是问题核心，只按词项交集评分。我们没有隐瞒这个弱点，而是把它保留为后续排序改进的明确起点。你能指出它的限制，说明你已经开始区分代码真正完成的工作与自己希望它完成的工作。

把这个小工程与本仓库的 `CorpusStore`、`Hit`、`Claim` 对照，你会发现后者增加了租户、权限、切片、事务和更严格的生命周期。不要一开始逐字复制大实现；先独立写出本节版本，再逐项加入需求。每加一项都保留旧测试，并增加能让旧实现失败的新测试，才能看见复杂度为何产生。

## 小课十：十二道练习与完整参考判断

**练习一：区分三个层次。** 对“这篇文档与问题相关”“这句话被引文支持”“这句话在现实中正确”分别举例。参考答案：一篇讲缓存的文档可以与显存问题相关，却没有提供当前机器的观测；“资料写了容量七项”可由原文支持；设备真实容量是否七项还需要可信规格或观测。三个判断的输入不同，不能通过换一个措辞合并成同一个布尔值。

**练习二：逐项计算交集分数。** 用本章四条记录查询“kv storage”。参考答案：d2 同时含 kv 和 storage，得二分；d1 只含 kv，得一分；d3、d4 为零且不返回。若实现返回 d4，先检查是否把“包含 cache”误当作“包含所有缓存相关词”。当前程序没有同义词扩展，因此不能用语义直觉替它补规则。

**练习三：加入确定的同分规则。** 为什么不能只写 `sort(reverse=True)`？参考答案：如果列表元素包含 Record 对象，同分比较可能试图比较不支持排序的对象；即使字符串元组能排序，也可能把正文文本作为隐含次序。应写 `key=lambda item: (-item[0], item[1].id)`，明确以高分优先、ID 升序破同分。比较规则属于接口的一部分，值得单独测试。

**练习四：实现只含全部查询词的检索。** 完整参考条件是 `if terms and terms.issubset(document_terms)`。`terms` 的非空检查避免空集合被认为是每个文档的子集而返回全部记录。若你希望空查询返回全部，则应另写明确接口，而不是偶然依赖集合数学。把“kv cache”和“kv absent”作为正反测试，前者命中 d1，后者返回空。

**练习五：证明线性扫描和倒排候选等价。** 对词项并集规则，把扫描得到的正分文档 ID 集合，与所有查询词倒排表的并集比较。参考实现如下；它验证候选集合，不验证排序分数。倒排表只保存文档 ID 时无法独立复现词频评分，不能用这个测试宣称完整 BM25 等价。

```python
def scan_ids(query_terms, records):
    return {r["id"] for r in records
            if query_terms & set(r["text"].lower().split())}

def index_ids(query_terms, postings):
    result = set()
    for term in query_terms:
        result |= postings.get(term, set())
    return result

assert scan_ids({"kv", "cache"}, records) == index_ids({"kv", "cache"}, postings)
```

**练习六：制造索引过期。** 建完 postings 后，把 d1 的正文改成“不含原词的另一段”。参考答案：旧索引仍可能用 kv 找到 d1。完整修复需要删除这条文档旧词项的成员关系，再加入新词项，或重建小语料的全部索引。仅把新词项加入旧列表不会清除已经不存在的旧词，因此不算正确更新。

**练习七：拒答究竟说明什么。** 当查询没有候选，回答应该写“没有找到当前资料中的支持”，还是“这个事实不存在”？参考答案是前者。系统的搜索空间和检索算法都有边界。你可以在报告中记录 `no_candidate_under_current_index`，但不能把有限检索失败升级为世界知识的否定结论。

**练习八：设计一条可以识别预训练猜答的测试。** 参考答案是在虚构资料中定义“青石项目容量七项”，查询后将当前版本改成九项，再查询。评估回答是否跟随更新，并要求引用当前版本。使用“地球有几颗天然卫星”这类模型可能本来知道的问题，难以证明答案确实依赖检索。

**练习九：找出最早失败阶段。** 原文有答案，解析正文没有，检索为空。参考答案是摄入或解析阶段最早丢失了信息。当前证据不支持首先更换 embedding 模型。先检查解析输出、页面布局和字符编码，再决定是否需要重新切块和重建索引。一次修改多个阶段会让你无法知道真正起作用的是哪一个。

**练习十：为多证据问题写标注。** 问题要知道 X 的限制，资料 A 说明 X 依赖 Y，资料 B 说明 Y 的限制。参考答案应记录必要证据集合 `{A,B}`，不能只标 A 为唯一相关。你可以另外记录两条边各自支持什么中间结论。检索到 A 但没有 B，表示发现了连接关系，尚未形成完整支持链。

**练习十一：写一份最小 trace。** 参考字段是请求 ID、查询、身份范围、资料版本、候选 ID、各阶段排除原因、上下文 ID、最终引用和停止原因。正文是否写入日志由实际数据规则决定；本课程虚构数据可以完整打印。API key 不属于调试检索质量所需的信息，不应为了方便把整个请求头原样记录。

**练习十二：解释版本检查。** 删除验证器的 `source.revision == extract.source_revision` 后，会发生什么？若正文比较仍严格相等，某些正文变化仍会被发现；但正文相同而来源条件、权限或发布状态变化的情况可能被遗漏。版本号绑定的不只是文字表面，还可以绑定整个证据记录的语义。不能因为某个例子还能失败，就认为删掉版本检查永远没有影响。

## 源码落实与运行复核

### 阅读代码时先找数据结构

打开 `labs/knowledge/store.py`，先阅读 `Context` 和 `Chunk`，不要立即追踪 SQL。`Context` 携带租户、用户和组；`Chunk` 携带片段 ID、文档 ID、版本、来源、字符区间和原文。`frozen=True` 使 dataclass 实例不能随意改字段，帮助我们把某次检索到的片段当成快照。它并不让数据库不可变，也不解决进程间的并发问题。

然后打开 `retrieval.py` 中的 `Hit`。`score` 是排序依据，而不是事实概率。BM25 分数、余弦相似度和 RRF 分数各自有不同定义，不能因为都叫 score 就相加。再打开 `rag.py`：`Claim` 与 `Citation` 是不同对象，后者指向片段并保存引文。这个拆分允许检测“来源真的有，但回答歪曲了它”。

`answer_report` 是本卷的严格抽取式回答器：只返回当前可见来源里的原文字段，不让一个生成模型自由改写。这是刻意缩小能力边界以检查证据流，不能把它宣传成完整智能问答。它能告诉你检索是否工作；它不能充分理解中文否定、跨句推理或自然语言意图。

### 故障定位方法

出现“回答不对”时，按以下顺序抓取中间产物。先打印文档是否进入数据库，再打印当前用户可见的 chunk 数量，再打印查询词元，再打印全部候选分数和 top-k，再打印真正交给回答器的上下文，最后检查陈述与引文。任何前一层为空，都不应优先调模型温度。

如果检索能找到证据而答案没有使用，检查上下文打包是否超限、重复片段是否挤占空间、回答器是否遵守引用契约。如果某次更新后旧答案仍出现，检查检索索引、缓存、图边、摘要和历史答案是否都记录来源版本。单看数据库最新行不足以证明整个系统已更新。

日志应保留可复查 ID 和版本；敏感文本不应无条件进入通用日志。课程可以打印虚构原文，实际部署时要区分调试日志与业务数据访问权限。

## 综合工作坊：把一次回答拆成可核对的证据表

现在不要再增加检索算法，先完成一个更严格的小作品：给一份答案逐条标注它需要哪些来源。用户问“Jade 如何更新，失败后怎样恢复”，答案有两个独立断言。更新断言需要构建与切换机制，恢复断言需要旧代际保留策略。两条都出现 Jade 这个名字，不代表同一篇介绍足够支持它们。把问题拆成断言槽位，是从“找到相关文本”走向“回答完成”的关键。

建立一张表，每行包含 slot、claim、source_id、quote、status。status 区分未找到来源、来源不可用、引文不匹配、引文存在但语义待审、已通过当前教学规则。不要用一个布尔 correct 压缩所有失败，否则用户只能看到失败，却不知道需要补资料还是修引用。表格也帮助你发现一段回答实际包含三个断言，却只给一个引用的情况。

下面使用完全虚构的事实标签，展示结构验证。它不自动理解自然语言，而是将人工确认的“哪个来源支持哪个槽位”作为金标。这样能先验证证据流，再把语义判断单独替换和评测。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class EvidenceRow:
    source_id: str
    revision: int
    text: str
    slots: frozenset[str]


def inspect_answer(required, proposals, visible_sources):
    inspected = []
    covered = set()
    for proposal in proposals:
        slot = proposal["slot"]
        source = visible_sources.get(proposal["source_id"])
        if slot not in required:
            status = "outside_task"
        elif source is None:
            status = "unavailable_source"
        elif not proposal["quote"] or proposal["quote"] not in source.text:
            status = "quote_mismatch"
        elif slot not in source.slots:
            status = "unsupported_slot"
        elif proposal["claim"] != proposal["quote"]:
            status = "rewrite_requires_review"
        else:
            status = "supported_extract"
            covered.add(slot)
        inspected.append({**proposal, "status": status})
    return {"rows": inspected, "missing": sorted(set(required) - covered)}

sources = {
    "u": EvidenceRow("u", 1, "Jade builds before switching.", frozenset({"update"})),
    "r": EvidenceRow("r", 1, "Jade retains the old generation.", frozenset({"recovery"})),
}
proposals = [
    {"slot": "update", "claim": sources["u"].text, "source_id": "u", "quote": sources["u"].text},
    {"slot": "recovery", "claim": sources["r"].text, "source_id": "r", "quote": sources["r"].text},
]
checked = inspect_answer({"update", "recovery"}, proposals, sources)
assert checked["missing"] == []
assert inspect_answer({"update", "recovery"}, proposals, {"u": sources["u"]})["missing"] == ["recovery"]
```

逐行解释这个程序。visible_sources 不是所有资料，而是当前身份已经获授权的集合；get 返回 None 时，统一不可用，不泄露某份私有资料是否存在。引文检查先要求非空再检查子串，防止空字符串在任何文本中都成立。slots 是人工金标，用来区别相关和足够支持；claim 等于 quote 则把生成自由缩小为精确抽取。covered 只在所有条件通过后增加，最终缺口是所需集合减已覆盖集合。

现在做三个控制变量实验。第一，把恢复断言的 source_id 改成 u，引文仍用恢复句，结果 quote_mismatch；第二，把 quote 也改成 u 的更新句，形式匹配但 slot 不支持，结果 unsupported_slot；第三，保留正确 r 引文却把 claim 改成“任何故障都可自动恢复”，结果 rewrite_requires_review。三个错误都可能在普通“有引用”检查中混过去，但原因与修复不同。

这个工作坊的完整答案不是要求你相信程序理解语义。恰恰相反，人工 slots 暴露了语义标签来自哪里。之后接入模型支持判断器时，保留同样负例，测它能否识别范围扩大、否定丢失与错误来源。结构验证继续由代码承担，不应因为模型更强就删除。

### 证据替换实验：判断回答是否真的依赖资料

把唯一更新来源从“构建后切换”改成“验证后切换”，保持其他字段与问题不变。正确的抽取回答应随原文变化；若最终答案完全不变，可能来自硬编码、旧缓存或模型背景知识。再删除恢复来源，完整状态应变成缺 recovery。最后加入一份只提 Jade 名字但没有机制的文档，不应自动补齐缺口。

这种实验比观察一次正确答案更强，因为它检查输入证据变化是否产生预期输出变化。一个系统偶然答对可能是猜中，能对受控证据变化做正确响应才说明数据链在工作。你也可以交换两个来源 ID，故意让引用错位，检验系统是否只关心答案文字而忽略 provenance。

实验记录应写四列：改变了哪个输入、预期哪个状态变化、实际输出、原因。不要在看到结果后修改预期使它看起来正确。预期来自任务与证据契约，测试结果用来检验实现。对于语义不确定的例子，可以明确标人工待审，而不是强行归入通过。

### 新手调试顺序的最终练习

假设答案为空。先检查资料存在与当前可见集合，再检查词元与候选，再检查上下文预算，最后检查引用。若候选为空，回答器再复杂也无济于事；若候选有而上下文空，可能是预算连元数据都容不下；若上下文有而报告空，可能是来源在生成前更新。沿链定位一次，就比随机改五个参数更有效。

假设答案不空却错误。先逐条拆断言，找对应来源与条件，确认错误首次发生在原文、抽取、检索、上下文、生成还是渲染。源文档本身错误时，引用系统可能完全按设计工作，但仍不能保证事实真实；这需要资料治理与来源判断。准确区分系统忠实于错误来源和系统歪曲正确来源，才能采取正确修复。

完成本章后，你应能用自己的话解释：检索分数是排序信号，相关性取决于任务，引用是可追溯指针，支持是来源与断言的关系，真实性还依赖世界与来源。五者分别建模，后面复杂技术才有清楚位置。否则再多框架与模型也只会把同一个含糊错误包装得更漂亮。

最后区分两类拒答。第一类是资料库里没有支持当前问题的证据，系统应说明缺口；第二类是资料可能存在但当前身份不可用，系统可以统一报告无法获得可用来源，不透露受限对象细节。不要通过不同错误文字让人探测私有资料是否存在，也不要把权限失败解释成世界上不存在这个事实。

一个反例是普通用户查询内部项目代号，系统说“该项目存在但你无权访问”。如果项目存在本身也是受限信息，这句话已经泄露。课程 get_visible_chunk 将不存在、旧版与不可见合为不可用，正是让读路径保持保守语义。管理诊断可以更详细，但应有独立授权，不能让模型随意调用管理接口。

另一个反例是公开资料明确说某功能尚未支持，系统因为查询高度相关而回答支持。这里不是资料缺失，而是支持判断方向错误。修复需要保留否定与条件，不能通过多搜几篇同主题介绍掩盖。把缺证据与读错证据分开，你才能为每种失败选择正确的下一步。

练习时请为这两类各写一个最小输入和预期状态，要求程序输出不同内部原因但遵守对外信息边界。这个作业把检索、授权与回答语义连接起来，避免初学者把所有空结果都当同一种问题。
