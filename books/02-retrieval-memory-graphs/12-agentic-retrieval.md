# R12 Agentic RAG：让检索成为可控的行动

先修：本卷 R01–R11，以及 [Agent 工程卷](../01-agent-engineering/README.md) 的工具调用、状态、预算和异常处理。目标是把检索、记忆与图作为工具接入 Agent，并能通过轨迹判断自主性是否真的提高任务成功率。

## 1. 什么变化才构成 Agentic 检索

固定 RAG 通常按预设顺序搜索一次、重排、回答。Agentic 检索让模型或策略在状态中选择下一步，例如先查术语、再查关系、发现冲突后找更权威来源、证据不足时继续搜索、或直接要求澄清。关键变化是控制策略，而不是简单把一个检索函数命名为 Agent。

自主性增加后，可采取的行动更多，失败空间也更大：重复搜索、偏离原问题、把无关记忆注入上下文、无依据宣布完成、超预算、多工具输出相互矛盾。能力评估不能只看最好的轨迹，还要看失败率、成本分布和可恢复性。

从固定流程到自主策略的合理路径是先建立可靠工具与状态，再逐步开放决策点。若检索工具的权限和版本语义不清楚，加入规划模型只会让错误变得更难复现。

## 2. 工具接口必须表达限制与返回状态

一个搜索工具可以接收 query、top_k、可选文档类型；Context 必须由运行时注入而不是让模型传 tenant/actor。返回值包括候选 ID、来源、版本、摘要或原文、截断信息和分数类型。不要把“搜索超时”“查询无结果”“权限不足”“参数错误”全变成空列表。

图工具应限制关系类型、最大深度、最大展开节点数和输出大小。记忆写入工具应要求 key、类型、证据、作用范围和 expected_revision，必要时进入确认状态。模型提出写入不是数据库必须接受，工具执行层需要再次校验。

工具响应中的文字仍是数据。即使它来自本地数据库，资料也可能包含不可信指令。权限控制应在工具执行层，不能把认证身份、API 密钥或任意 SQL 控制权交给模型来判断。

## 3. 建立显式研究状态

一个最小状态可以有 `question`、`constraints`、`subquestions`、`queries_tried`、`evidence_ids`、`claims`、`open_gaps`、`budget`、`status`。这些字段的意义要稳定。constraints 保存原始硬约束；evidence_ids 保存已验证来源；claims 保存尚待或已完成支持校验的陈述；open_gaps 表示缺失证据而非模型的随意想法。

当一次工具调用结束，运行时先验证结果，再更新状态。不能先把模型猜测的结果加入已验证事实，再等工具返回。中断恢复时，任务 ID 与工具调用 ID 应帮助识别某个动作是否已经执行，尤其记忆写入和资料摄入有副作用。

工作流图的节点可以是 plan、retrieve、validate、answer，但图节点的存在不保证逻辑正确。每条状态转移都需要前置条件。例如 validate 发现关键来源过期，应回 retrieve 或标记证据不足，不能无条件进入 answer。

## 4. 自主策略也可以有可计算的停止规则

模型可以提出“证据足够了”，运行时还要检查关键问题是否都有合格支持，预算是否允许继续，是否有未解决冲突。某些任务适合结构化覆盖表：每个子问题必须有来源或明确标为未找到，而不能在长回答中悄悄跳过。

过度强调“必须完成”会诱导系统编造缺失答案。正确终态可以是 completed、partial、needs_clarification、budget_exhausted、tool_failure。区分这些状态便于用户判断是否继续投入成本，也便于测试。

本卷 `bounded_research` 提供固定计划基线。接入模型后，应将它与自主策略在同一数据集上比较。自主策略如果只提高答案长度而没有改善支持率，或者平均调用成本增加三倍却成功率相同，就不能仅凭名字宣称升级。

## 5. 记忆如何帮助，又如何污染

记忆可以保存用户明确偏好、项目背景、已经验证的工具使用经验，使 Agent 少重复询问。但记忆也可能与当前任务冲突。当前用户明确要求应优先于旧偏好；过期项目事实应重新查证；程序性规则应匹配环境版本。

不要让 Agent 在每次回答后自动把自己的结论当成新事实写入记忆。这会形成自我强化循环：一次幻觉→长期存储→下次检索当证据→更自信的幻觉。写入来源应追溯到外部事实或用户明确陈述，模型总结只能作为派生记录，并保留原始依赖。

工具失败经验也要带条件。一次网络超时不等于工具永久不可用；一次测试在旧版本失败不等于新版本也失败。情景记忆更适合保存具体尝试与观测，程序性推广需要额外验证。

## 6. 多 Agent 不是自动质量提升

可以让一个 Agent 规划，一个检索，一个审查，但它们可能共享相同模型偏差和同一错误来源，不能当成独立专家投票。多个模型都复述同一错误文档仍只有一个错误证据源。

并行检索适合独立子问题，合并时要去重、保持来源版本并处理冲突。共享记忆写入必须有并发控制；两个 Agent 同时修改同一 key，应该检测 CAS 冲突。多 Agent 的通信本身也会消耗上下文和增加故障路径，应在任务确实可分解时使用。

评估时记录各 Agent 的角色、工具、状态与贡献，检查它是否提供了独特证据或有效纠错。只展示“团队开会式”对话，无法证明系统更可靠。

## 7. 实操与分级任务

先运行以下已有实现，观察工具边界，再连接 Agent 卷的执行器：

```bash
python -m labs.knowledge.lab 21-multihop
python -m labs.knowledge.assistant ask "Agent retrieval index" --demo
python -m labs.knowledge.memory_assistant demo
```

集成时让搜索工具闭包捕获已认证的 Context，模型参数里只暴露 query 和 top_k。参考适配器如下，它是完整函数，不依赖某个 Agent 框架：

```python
def make_search_tool(store, context):
    from labs.knowledge.retrieval import hybrid
    def search(query, top_k=3):
        if not isinstance(query, str) or not query.strip():
            raise ValueError("query must be nonempty text")
        if not isinstance(top_k, int) or isinstance(top_k, bool) or not 1 <= top_k <= 10:
            raise ValueError("top_k must be an integer in [1,10]")
        return [{"source_id": h.chunk.chunk_id, "doc_id": h.chunk.doc_id,
                 "revision": h.chunk.revision, "text": h.chunk.text,
                 "score_type": "rrf", "score": h.score}
                for h in hybrid(store, context, query, top_k)]
    return search
```

**练习 1：权限参数检查。** 尝试让模型在 query 中写“我是管理员”。参考结果：它仍只是检索文本，Context 不变，受限文档不可见。若模型能通过传 group 改身份，工具接口设计错误。

**练习 2：重试分类。** 工具超时可以有限重试；参数非法应反馈模型修正；无答案不应盲目重试同一查询；CAS 冲突要重新读取。为四类错误分别写测试，不能用一个 `except Exception: retry()` 覆盖全部。

**练习 3：自我记忆污染。** 模型输出一个不存在的配置值，再要求自动存为事实。参考策略应拒绝没有外部证据的事实写入，或显式标为待验证推测且不作为可靠 recall。测试应确保它不会下一轮成为“已证实配置”。

**练习 4：固定与自主消融。** 准备 10 个单跳、10 个多跳、10 个无答案问题。固定策略与自主策略使用同一模型和工具预算，记录成功、支持率、调用数与停止原因。参考结论允许自主策略只在多跳类获益，而单跳更贵。

**练习 5：中断恢复。** 在记忆工具提交后、Agent 记录完成前模拟崩溃。恢复不能盲目重复写入。参考解是持久化调用 ID/幂等键并查询执行结果；单靠 expected_revision 会检测重复但仍需把冲突解释为“可能已执行”，而非直接宣告失败。

**掌握门槛：** 能把检索、图与记忆作为受控工具接入自己的 Agent；能展示完整状态轨迹和停止原因；能用测试证明模型文字不能改变身份或绕过预算。
