# 怎样从“看懂了”走到“能独立做”

## 一课中的六个动作

**先写问题。** 例如“多个请求为什么可以共享一个 KV 页，却不能同时向同一个物理位置追加不同内容？”比“学习 KV cache”更容易判断自己是否学会。教材章节给你机制，你要把机制变成可检验的问题。

**预测结果。** 在运行示例之前写下输入形状、输出形状、两个具体数值、可能抛出的错误，以及自己还无法推断的部分。预测错误有价值：它定位了你真正不理解的地方。直接复制命令看到成功只说明程序跑过。

**手工跟踪。** 对短程序逐行画出变量、对象引用或状态表。对矩阵程序先跟踪一个输出元素；对 Agent 跟踪一次模型请求、一个工具调用和一条持久化事件；对调度器跟踪一个请求从等待到完成所拥有的资源。第一遍不要从“整个系统”同时看起。

**运行并改动。** 至少改变一个边界：空输入、长度 1、非整块长度、取消、重复事件、超时、文档撤销、错误权限、乱序流式片段。问题不只是代码能不能输出，而是原来成立的性质是否仍然成立。

**解释失败。** 保存一条最小失败输入，说明错误发生在哪个不变量。注意力输出错了，可能是 mask 方向、缩放、softmax 轴、布局或缓存位置；不能把所有情况都归成“精度问题”。Agent 重复执行写操作，可能是重试范围和持久化时机，而不是模型不听话。

**脱离答案复现。** 关掉参考实现，从接口和测试开始写一个小版本。第二天再做一次改变，检验自己保留了什么理解。参考答案不是评分标准的全部：只要满足行为、不变量和边界，你自己的实现可以完全不同。

## 四种熟练度不要混为一谈

| 层级 | 证据 | 自测方法 |
|---|---|---|
| 能描述 | 能解释名词和因果关系 | 不看书讲清输入、输出、状态和适用条件 |
| 能实现 | 从空文件实现最小机制 | 给定接口和测试，不看答案写出可运行版本 |
| 能诊断 | 在陌生错误中定位失败原因 | 处理故意植入的错误，提出最小反例和修复证据 |
| 能迁移 | 在真实项目中识别并修改同类机制 | 找到上游模块，添加回归测试，解释兼容性和成本 |

课程的“掌握”至少要求能实现和能诊断。成为专家还需要持续遇到新约束、维护真实系统并积累判断；本工程把这条路径拆成可做的任务，而不是用一个结业勾选代替工程经验。

## 怎样读一段不熟悉的代码

第一遍只找入口和接口。谁调用这个函数？传入的是文本、token IDs、Tensor 还是请求对象？函数返回结果还是修改共享状态？异常由谁处理？在一个小表格里记录函数名、输入、输出、副作用和调用者。

第二遍跟一条具体输入走到底。不要从文件第一行逐字读完整个仓库。以 vLLM 请求为例，从请求接收追到 token 形成，再找调度决策、KV 分配、模型执行、采样和输出；每次只检查这条路径实际触及的分支。第三遍再主动选择取消、缓存命中、长度变化或抢占，比较路径差异。

第三遍识别不变量。页面引用计数不能为负；同一调用 ID 的结果必须匹配调用；检索结果必须在调用者可访问范围内；Tensor 的 stride 不等于 shape；异步操作提交不等于完成。把不变量变成断言或测试，你才有依据修改代码。

第四遍做一个有限修改。例如增加一条明确日志、修正一个输入边界、给模拟调度器换一个策略、给检索器添加可解释分数。不要在第一次阅读后立即重写整个框架。一个能通过回归测试并解释代价的小修改，比一份漂亮但未经验证的重构计划更有价值。

## 练习分层

每章的题目通常包含计算、阅读、实现、排错和扩展。计算题要求写中间步骤，阅读题要求指出代码对应的机制，实现题要求换输入仍正确，排错题要求先给最小反例，扩展题要求设计实验和比较条件。综合项目把这些能力合起来。

如果一道题卡住，先确定卡在哪一层。不会算矩阵乘法就回到基础卷；不知道 list 与 ndarray 的广播差异就做小数组实验；不理解数据依赖就画读写表；找不到源码入口就从一个运行堆栈入手。跳过先修知识只会让后续每一步都依赖复制。

使用提示时分三级：先看题目的性质或接口提示，再看伪代码，最后看完整实现。看完答案后立即合上，并修改题目一个条件再做。比如参考答案使用固定长度，你改成可变长度；使用单一请求，你改成交错两个请求；只考虑正常结束，你加入异常与恢复。

## 怎样记录一次实验

```text
章节 / 实验 ID：
问题：
假设：
环境：Python、依赖、CPU/GPU、相关版本
输入：形状、数据来源、seed、请求数、边界条件
命令：可复现的完整命令，密钥只写环境变量名
预期：数值、性质、时间趋势或错误类型
观察：实际输出、差值、日志位置
解释：支持了哪个判断，排除了哪个判断
限制：没有测试什么，哪一结论只在 toy 条件成立
下一次：最小的追加实验
```

对于性能实验，记录 warmup、重复次数、是否同步、并发、batch、输入长度和输出长度，区分编译耗时与稳定运行耗时。不要把 CPU 事件模拟的时间写成 GPU 实测毫秒。对于模型 API，记录模型标识、协议、采样参数、工具版本与停止条件；不要把一次成功回答当成可靠性证明。

## 什么情况下可以进入下一章

你能用自己的话解释本章核心机制；至少一项实现不依赖复制；完成一个边界测试；能解释一项故意错误；知道简化实现与真实系统的至少两点差别。满足后写一段证据并把章节记录为 `mastered`。证据可以很短，但应该具体，例如“补上取消路径后引用计数归零，并用两请求共享前缀的测试验证”，比“已读完”有用得多。

暂时不懂一个前沿细节并不阻止所有学习。课程地图把长期原理与依赖特定硬件的细节分开：先完成 CPU 机制，再带着具体问题去 GPU 或上游源码。扩展任务也是本版课程的一部分，但每个任务的环境和前提要满足，不能用“计划做”记成“已验证”。
