# 环境分层：把学习问题放到合适的机器上

学习环境建议使用 Python 3.12：基础 CLI 与参考库仍检查 3.10 兼容，正文中的 TaskGroup／异常组示例要求 3.11 及以上。各章的可选 PyTorch、Triton 与上游框架还需满足各自依赖要求，不能从 Python 版本推断 GPU 支持。

## 1. 先识别资源，再决定实验

课程面对三类环境：Win11 PC（可用 RTX 5070 Ti）、Linux 服务器 CPU／Docker、共享 8×H100。它们不是难度等级，也不是必须逐级买设备。检索评测、状态恢复和协议测试本来就适合 CPU；Hopper 的 TMA／WGMMA 则需要匹配硬件及工具链。把“能在强卡上跑”当成“应该在强卡上跑”，会增加排队与环境噪声。

在任何机器上先运行：

```bash
python tools/course.py doctor
```

这个检查只报告环境与工具位置，不加载 CUDA。需要 GPU 时，再单独运行 `nvidia-smi`，观察真实设备、驱动和显存状态。卡的名称不等于软件兼容性：还要看 PyTorch 构建、CUDA 工具链、Triton 版本、目标计算能力和具体算子是否支持。

## 2. CPU 基础环境

课程导航仅需 Python 标准库。大多数数值实验使用 NumPy；无需预先下载模型权重、向量数据库镜像或安装整套推理框架。最小环境见 `requirements-cpu.txt`。

从用户工作目录创建虚拟环境，不修改系统 Python。每台机器独立建立环境，不在 Windows 和 Linux 之间复制 `.venv`。保存环境记录时：

```bash
python tools/course.py doctor
python -m pip freeze
```

前者是简明报告，后者记录实际安装包。课程的宽版本要求表示兼容目标；实际可复现结果依赖你的环境快照。初版已执行的版本另列在验证报告中。

## 3. 本地 RTX 路线

可以用本地卡完成小型 Tensor 运算、CUDA／Triton 基础、attention 数值验证和小型训练。先确认 GPU 软件栈，再开始 K 卷相关实验。不要把数据中心 Blackwell 的资源配置、TMEM 用法或支持范围直接套到消费级 RTX；同一大架构名称下的芯片仍有差别。

WSL2 的 CUDA 驱动由 Windows 驱动映射提供。安装 Toolkit 与安装驱动是不同事情，WSL 里不要再安装会覆盖映射的 Linux NVIDIA 显示驱动。具体兼容路径参见 [NVIDIA CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/)。本工程不固定一个未经该机器验证的“万能 CUDA 版本”。

安装 PyTorch 前看 [官方安装选择器](https://pytorch.org/get-started/locally/)，安装后分别检查：是否可导入 PyTorch、`torch.cuda.is_available()`、设备名称与能力、一个小 Tensor 运算、课程自己的参考对照。只有最后两步成功，才有证据说明你的栈能运行该实验。`nvcc --version` 与 `nvidia-smi` 中显示的 CUDA 字段含义不同：前者是编译工具，后者反映驱动支持能力，不应直接要求两者字符串完全一致。

把第一个 Kernel 限制为很小输入，检查不整除 tile 的长度。先证明正确，再扩大规模做性能分析。一次小输入成功不能证明所有 shape、dtype 和布局都支持。

## 4. Linux CPU 与 Docker

Linux 操作、文件权限、SSH、进程、日志、容器、HTTP、SQLite 和分布式逻辑可以长期放在服务器 CPU 上练习。容器隔离不是虚拟机：它共享宿主内核；默认写进容器层的数据与 bind mount、volume 的持久化语义不同。基础卷会先用小服务演示，再讨论 GPU 容器。

使用个人工作目录和唯一容器名。停止自己启动的容器，确认名字后再清理；不要执行会影响其他用户的全局 prune。示例服务默认监听 `127.0.0.1`。需要从 PC 访问服务器服务时，可以通过 SSH 本地端口转发学习网络关系，不必先开放公共监听。

```bash
ssh -L 18080:127.0.0.1:8080 YOUR_USER@YOUR_SERVER
```

这是一条供你按自己的服务器替换占位符的命令。连接存在时，本机 `127.0.0.1:18080` 被转发到服务器的 `127.0.0.1:8080`。两个 `127.0.0.1` 各自属于所在的机器，不能把它们想成全世界同一台主机。密钥配置和端口选择见基础卷。

## 5. 共享 H100 的实验顺序

第一批只用一张卡：确认数值、学习 profiler、观察小型框架运行。第二批在资源允许时使用两张卡验证通信和并行。只有明确要观察八卡拓扑或执行对应多卡任务时才占八张卡。把同类实验集中成一次短的运行窗口，先在 CPU 上准备输入、脚本和判断标准，避免占卡后才开始写代码。

建议每次记录：使用哪张卡、预计时长、最大 batch／序列长度／迭代数、输出位置、停止条件。GPU 内存空闲不代表没人会使用；设备分配仍按所在环境的约定。课程不会自行选择“看起来最空”的设备并启动长期任务。

Linux 上可以先限定可见设备，再运行小实验：

```bash
CUDA_VISIBLE_DEVICES=0 python -m labs.kernels.gpu_check
```

这里的 `0` 应替换为已分配给你的设备。程序内可见设备会重新编号；外部的物理卡 3 映射成程序内 `cuda:0` 很常见。不要因此误以为用了另一张卡。

对于长时间运行的命令，可使用工程提供的 `tools/run_experiment.py` 记录启动、退出和超时。它是进程控制工具，不是硬件级资源隔离器；不能限制任意程序的显存，也不能替代集群调度系统。模型显存、内核输入和并发上限仍要在具体程序里设置。

## 6. API 环境

离线 Harness 使用脚本化模型，先测试状态、恢复和工具行为。进入真实 API 阶段再使用自己的端点、密钥和模型标识。API key 放环境变量或本地忽略的 `.env`，不要写入代码、教材截图或 Git 提交。普通 `os.environ` 不会自动读取 `.env`，是否加载由你的程序决定。

一个开发迭代先用单任务、小步数、小输出，检查请求结构与费用，再扩展到评测集。记录 token 使用与重试次数。超时不一定意味着服务端没有处理请求，尤其是外部写操作不能因网络错误无条件重做。Agent 卷会详细设计幂等与恢复。

Chat Completions、Responses、Messages 是协议，不是密钥类型。模型名和支持的字段由具体服务决定；不把任何供应商的私有 `reasoning_effort`、工具字段或流式格式当成通用标准。本版在适配器层明确验证支持范围。

## 7. 三种验证状态

| 状态 | 可以据此说什么 | 不能据此说什么 |
|---|---|---|
| 本地 CPU 测试通过 | 在报告列出的 Python／NumPy 环境满足测试的性质 | 所有系统、GPU、真实模型都已通过 |
| 可选 GPU 脚本存在且语法可解析 | 提供可执行入口与参考对照，依赖满足后可试验 | 已取得某个加速倍数或全部架构都支持 |
| 真实 API／GPU 实际运行并记录结果 | 对该版本、输入和环境有运行证据 | 自动推广到其他版本、负载或硬件 |

逐项保留边界会让你更快定位问题。它不是降低课程目标，而是把“我知道”“我实现了”“我测过了”变成三种可追溯证据。
