# 逐章深写的验收标准

这次修订回应一个具体问题：初版虽然主题多、代码能运行，但大量主章节只有一两千汉字，读者必须自行补全术语、推导和代码之间的关系。课程的目标读者不能承担这些隐含前提，因此正文必须承担完整教学责任。

## 一个概念怎样才算讲完

一个概念第一次出现时，先给出它解决的问题与一个具体场景，再解释所依赖的词义。随后完成通俗解释与严格说明，说明输入、输出、状态、单位、适用条件和不变量。公式中的每一个符号都应有含义；代码中新的语法或重要操作都应能追溯到已教内容。

例如讲 KV cache，不能停在“缓存过去的 key/value，以空间换时间”。读者应能从 token 和投影矩阵算出 K/V，指出每层、每头、每位置的数据，手算一次 prefill 与两次 decode，解释为什么旧 K/V 可以复用、哪些情况下不能复用，并核算实际缓存字节。再逐行跟踪对应实现，改变输入或掩码，观察一致性测试如何发现错误。

## 每章应当提供的学习材料

1. 明确的先修说明，并为本章新名词提供可理解的定义。
2. 由简单问题到完整机制的多节讲解；各节说明前一节留下了什么问题。
3. 通俗解释和严谨解释。比喻需要说明适用边界，不能用比喻替代机制。
4. 多个完整计算或执行案例。给出初值、中间状态、最终结果与验证方法。
5. 能独立运行的代码，以及关键行、变量、分支和数据变化的解释。
6. 对设计选择的解释：为什么需要这一步，省略或换一种写法会怎样。
7. 有明确触发输入的错误案例、观察方法、定位过程和修复依据。
8. 从预测、手算、补写、修改到独立实现的分级练习。
9. 完整参考答案。代码题的答案不能只有“参考某函数”或一个算法名字。
10. 将本章机制接入更大工程的渐进任务，以及明确的验收条件。

这些要求不意味着每章机械套用同样标题。Linux 操作课需要呈现终端状态，数学课需要展开计算，状态机课需要追踪事件与持久化，GPU 课需要对应线程、地址、类型与同步。材料形式应服务于具体机制。

## 避免知识跳步

“先安装依赖”“构建索引”“执行前向”“更新状态”都可能隐藏多个新手尚不会的动作。写作时逐个追问：依赖装进哪个解释器，索引存什么，前向的每个张量是什么形状，状态更新发生在外部操作前还是后？如果答案没有在本章或明确的先修章节出现，就存在需要修补的断层。

指向源码的链接是补充材料。核心教学必须把关键实现放在正文里解释；要求读者自己在一个长文件中猜测入口，不能算逐行讲解。大型真实仓库的导读应提供版本、文件、符号、输入输出、调用关系和可验证的修改任务。

习题答案也需要检查跳步。“使用 RRF 合并”“添加幂等键”“按行归约”都只是方向。完整答案应至少给出数据结构、计算或控制过程、边界处理、预期结果及失败用例。无需每题重新讲一次所有先修，但必须让读者能核对自己的推理。

## 数量检查的作用与限制

`depth_baseline_v1.json` 保存初版提交的主章节长度。`DEPTH_TARGETS.json` 规定此次逐章深写的最低篇幅，`tools/check_depth.py` 统计去掉 fenced code block 后的中文汉字，并生成逐章对照。正文、标题、表格与答案均会计入，因此这些数字不等于纯叙述段落字数。

篇幅检查用于发现某一章仍只增加了几段话，不证明讲解正确或完整。长段落同样可能含糊；测试通过只能证明被测程序行为。人工审查还要检查：是否真正展开计算、是否解释关键代码、答案能否复现、是否反复使用同一段空泛提醒、是否把正文责任转给外部链接。

重复段落检查只提供审稿线索：合理的共同定义可以重复，整段无关提醒反复出现则应删除并换成本章具体解释。不能以添加重复段落、扩大代码块或罗列题目而不解答的方式达到篇幅。

## 代码、来源与硬件证据

正文涉及的实际接口必须与仓库代码一致。已有行为修复应保留，新增可执行示例要以其数学不变量或外部可观察行为验证。没有改变代码行为的文字修订无需制造新的测试数量。

易变化的框架行为、协议和硬件要求引用一手来源；固定版本的源码研究保留提交标识。新实现的正确性、官方实现支持情况、真实设备性能是不同证据，分别记录。GPU、真实 API、Docker 或上游完整环境没有运行，就保留未执行说明。

## 发布门槛

逐章深写、人工内容审查、文档链接检查和相关程序验收完成后统一发布。保留稳定课程 ID、原有项目入口和历史版本。更新日志应描述实质教学变化，不把字数增长本身当作学习成果。
