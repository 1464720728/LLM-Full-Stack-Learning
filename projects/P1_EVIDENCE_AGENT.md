# P1：从工具循环到可恢复的证据 Agent

先修：A 卷工具、事件、持久化与评测；R 卷版本化语料库、混合检索、权限和引用。CPU 即可，不联网，不消耗模型额度。实现入口 [evidence_agent.py](evidence_agent.py)，验收入口 [test_projects.py](../tests/test_projects.py)。

## 1. 要解决的具体问题

用户询问 KV cache。知识库有一份所有演示读者可见的文档、一份仅作者可见的文档，还有另一租户的同题文档。系统需要检索可见证据，向模型返回结构化工具结果，生成答案，并在交付时确认引用仍然有效。执行中可能中断，文档也可能在检索之后被撤销。

这里至少有四个独立的正确性问题。检索器不能把不可见文档交给模型；Harness 不能把模型编造的身份参数当成权限；恢复执行不能随意重复已经完成的工具；引用在交付时需要仍指向当前可访问的版本。任何一个条件失败，都不能靠语言模型“尽量小心”来补救。

本项目用精确摘录代替自由生成，目的是把证据校验变成可以严格判断的测试。它不会证明摘录是真实知识，也不会证明每个摘录都最相关。等控制链正确后，再替换为真实模型并增加语义评测。

## 2. 先运行，再预测下一次变化

```bash
python -m projects.evidence_agent
```

默认输出应满足这些性质：运行 `finished`；两次模型调用；一次工具调用；最终答案被接受；引用只来自普通读者可见的 KV 文档。输出还包含 `run_started`、`model_requested`、`model_completed`、`tool_completed` 等事件。

不要只对照某个长哈希。哈希是 chunk 身份的一部分，内容、版本或切块策略改变后可以变化。更重要的不变量是：最终 `chunk_id` 能从当前用户的可见语料中定位；摘录是该 chunk 的原文；返回的版本没有被删除或替换。

请先预测：若把演示文档的授权从 `('*',)` 改成 `('user:owner',)`，普通读者的最终结果应如何变化？正确结果是没有证据并拒答，而不是检索器偷偷扩大权限来找到答案。

## 3. 数据结构如何连接

`Context('demo', 'reader')` 代表由宿主确定的租户和身份。它不是用户 prompt 里的文字，也不是模型可以自由填写的工具参数。`make_harness` 内部定义 `search` 函数；这个函数通过 Python 闭包使用宿主传入的 context。工具 schema 只允许 `query`，并拒绝额外字段。

因此，模型输出 `{"query":"KV","actor":"owner"}` 会在参数校验阶段失败。这里的约束来自程序结构：模型无法通过合法参数选一个新身份。真实系统中，Context 必须来自认证会话，而不能把客户端自行发送的 actor 字符串直接当真。本项目是本地受信任调用，不包含登录系统。

检索函数调用 `hybrid(corpus, context, query, k=3)`。R 卷实现先取得当前 context 可见的 chunk，再做词项统计和打分。这样不仅最终文本不会泄漏，词项频率和候选分数也不会混进不可访问语料。真实大索引通常需要带过滤条件的索引和足够召回量；小语料实现选择先构造可见集合，强调语义清楚。

工具结果包含 `chunk_id`、`doc_id`、`revision` 和 `text`。这些字段给模型生成引用提供依据，但模型输出仍需要检查，不能把“工具曾经返回过”当成最终权限保证。

## 4. 一步步跟踪 Harness

`harness.new` 创建状态并保存初始快照。第一次 `step` 先增加模型调用计数并持久化，再调用模型。这种顺序承认网络请求存在不确定性：如果进程在发出请求后崩溃，不能把它当成没有发生并无限免费重试。测试替身按持久化的调用索引返回计划，不依赖隐藏的内存游标。

第一次模型返回 `ToolCall('search-1', 'search_evidence', arguments)`。Harness 把调用保存在 `pending`，下一步才执行工具。工具调用 ID 使结果能对应到某一次明确的请求，而不是“最近一个同名工具”。

第二次 `step` 验证参数、检索语料，并先把结果记入工具账本，再写入对话快照。为什么不是只写对话？因为工具完成与对话保存之间可能崩溃。账本让恢复程序知道这个调用已经有结果。对有外部副作用的工具，还必须考虑“副作用已发生但本地账本未记下”的窗口，不能声称本地 SQLite 自动提供跨系统 exactly-once。

第三次 `step` 再调用模型。测试策略读取工具结果，构造 JSON 答案；它没有推理能力，只把证据复制成精确摘录。Harness 将状态记为 `finished`。但工程中的最终交付还要经过 `finalize`，这是一道应用层检查，不是模型自己说“完成”就能跳过。

## 5. 为什么完成状态还不够

`finalize` 做四组检查：执行确实完成；最终 JSON 结构符合要求；拒答标志与 claims 是否为空一致；每条引用仍指向当前 context 可见的 chunk，且文字是对应原文。

它会拒绝未知字段、非法类型、重复 JSON 键、超过上限的 claims，以及不存在或已撤销的来源。这些条件都是可以写单元测试的。对自由生成的改写，原文包含校验就不够了，必须引入额外的语义支持判断，并承认这种判断可能有误差。

特别重要的是“检索以后被撤销”。执行两步后，模型尚未得到最终回答，但工具结果已经保存在对话中。如果此时删除文档，第二次模型仍然可以根据旧工具结果生成旧摘录；因此最终交付需要再检查。该检查能阻止继续返回过期证据，但不能撤回已经传给外部模型的数据。真实系统还要定义授权快照、数据保留与外部传输政策。不能把交付前复验夸大成对既往数据流的回滚。

## 6. 恢复实验

测试 `test_persisted_run_resumes_without_reissuing_completed_tool` 使用临时 SQLite 文件。它在工具完成后关闭第一个 Store，再创建第二个 Store，加载同一 run ID 并继续执行。最后要求最终证据校验通过，工具调用计数仍为 1。

请手工阅读这段测试，分别指出“关闭对象”“关闭进程”“丢失本地磁盘”有什么不同。本测试证明重新打开持久化文件后恢复正确；它不模拟磁盘损坏、跨机器锁竞争或数据库主从切换。后两类问题属于后续真实服务约束，需要专门实验，而不是把当前测试名字改大。

## 7. 练习与参考解法

### 练习 1：撤销窗口

任务：在第一次工具执行完成后删除公共文档，再让 Harness 结束。验收：运行可以是 `finished`，但 `finalize` 的 `accepted` 为 false，claims 为空。

解法：按现有测试调用两次 `step`，执行 `corpus.delete('demo','cache')`，再调用 `run`。失败原因应是来源缺失、过期或无权访问，而不是 JSON 错误。这个区别告诉你失败发生在哪一层。

### 练习 2：身份冒充

任务：构造 ScriptedModel，工具参数增加 actor。验收：工具结果是 `invalid_arguments`，不会出现仅作者可见的文本。

解法：使用现有严格 object schema；不要为了让工具“更灵活”允许额外字段，再在业务函数里随手读取它。真实身份传递应该在工具闭包或显式受信任上下文层，不在模型可控制的参数中。

### 练习 3：非摘录主张

任务：保留合法 chunk_id，把最终文字换成一个源文中没有的结论。验收：最终答案被拒绝。

解法：修改 `state.final` 中某条 text 再调用 `finalize`。合法 ID 不是通行证；它必须与具体断言建立关系。纯摘录实现要求文字原样存在，语义生成版本则需要重新定义验证标准。

### 练习 4：增加 top_k

任务：允许模型请求 1 到 5 个结果。验收：0、6、字符串和布尔值都被拒绝；合法 k 不超过预算；身份仍然不能由模型选择。

解法：在 schema 增加 `integer` 的 `k` 和上下界，检索函数显式传入。注意 Python 的 bool 是 int 子类，验证器使用精确类型判断；用普通 `isinstance(x,int)` 可能把 true 接受成 1。最终输出字符预算也要检查，因为 top_k 增加并不保证上下文放得下。

### 练习 5：改变文档版本

任务：检索后用同一 doc_id 摄入新正文，再完成回答。验收：旧 chunk_id 不能当成当前有效来源。

解法：调用 `ingest` 更新版本，而不是直接改 chunks 表；版本化接口负责原子更新当前 revision。然后复用撤销窗口测试。观察删除和更新在结果上都能让旧证据失效，但审计含义不同。

### 练习 6：工具失败后的回答

任务：让检索函数抛一个普通异常，模型仍然必须得到结构化失败信息并有界停止。验收：不能无限重试，也不能假装有证据。

解法：用临时 Tool 或 mock 令函数报错。只读工具错误会包装成 `tool_failed`；测试策略发现 `ok=false` 返回空 claims。不要把异常堆栈和环境秘密直接作为模型可见工具结果。

### 练习 7：替换真实模型

任务：先学 A 卷 live adapter，把 EvidencePolicy 替换为真实模型，其他接口不变。第一轮只发一个小请求，限制模型／工具步数和输出，记录实际使用量。验收仍然由 `finalize` 决定，不因模型回答流畅而放宽。

参考路线：先保存离线金标准与故障集；确认适配器返回 Turn；向模型说明最终 JSON 契约；保留身份和预算在宿主；统计拒答、引用有效率、检索相关性与费用。API 输出不稳定，测试使用固定录制夹具验证协议转换，真实调用作为另一个有日期的实验层。

### 练习 8：并发恢复的边界

任务：两个执行者同时恢复同一 run ID。解释仅靠快照版本比较为何不能保证两个执行者都没有发出工具请求。验收：给出一个按时间排列的反例和一种明确所有权方案。

参考解法：两者都可能读取旧状态并开始工具，在保存阶段才有一个 CAS 失败。应在执行前争取租约／所有权，带 fencing token 或由单工作者队列串行化同一 run；外部副作用仍需业务幂等键。本项目不实现分布式租约，因此文档保留单 run owner 的约束。

## 8. 完整交付标准

能够画出模型、工具、对话、账本、语料版本和最终证据的关系；能够解释每一次保存发生在外部动作之前还是之后；能够复现两种失败并指出原因；能够用同一个接口换模型；能够区分精确引用验证与真实性验证。完成这些后，这个项目才成为你能维护的系统，而不是一次成功演示。
